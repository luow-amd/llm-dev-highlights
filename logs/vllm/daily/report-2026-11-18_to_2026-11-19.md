### 💬 高热度讨论分析

#### 1. #58838 [vLLM IR][RoPE] 将 RotaryEmbedding 移植为 IR op（CUDA + ROCm/AITER）—— 评论最实质、争议最集中

- **核心议题**：是否将基础 `RotaryEmbedding` 从 `CustomOp` 迁移为 vLLM IR op，以让 QK-norm+RoPE+KV-Cache 融合模式稳定匹配；难点在于 ROCm/AITER 路径的耦合。
- **多方观点**：
  - **作者 mpashkovskii（AMD）**：强调这是客户真实需求——"一台生产环境跑的是 Gemma 级"老"模型，这不是 legacy，而是他们依赖的模型；没有该融合就无法在 ROCm 上达到性能目标"。并给出融合 op A/B 约 20% 延迟下降、v1/v2 全扫描无回退的数据。
  - **olka-amd**：承担性能验证，陆续披露了从"draft stage"到"A/B 20.7% 延迟下降"再到"发现 1.6–3.4% decode GPU 时间回退并修复至 parity"的完整数据链，还指出**未融合路径与融合 RoPE+KV-cache 的 query 结果一度不一致**。
  - **dllehr-amd（AMD 维护者）**：提出关键顾虑——"传统 IR 方法正在慢慢淘汰，需要和更大维护者群体讨论，这么大改动若破坏所涉文件之一是否有风险"。
- **争议焦点**：**优化投入是否应只聚焦最新模型 vs 老模型的实际生产价值**；以及**在 IR 架构可能被淘汰的背景下，是否值得为老路径做大范围改动**。
- **结论**：最终于 11-18 17:07 **合入 main**，作者承诺的"可 retarget 到新 IR"未被采纳，说明维护者接受在过渡期维持老 IR 路径。

#### 2. #65193 [Bug][Quantization] MXFP8 线性 kernel 选择忽略激活方案（已关闭，5 条评论）

- **核心议题**：MXFP8 选择器无 `activation_quant_key`，导致 weight-only 检查点在 SM100 被静默导向 W8A8 FlashInfer，造成**静默精度损失**。
- **观点交锋**：
  - **kavyansh-1**（欲接手者）提出完整修复方案，并建议与 #59460 的 `executed_activation_key()` 对齐。
  - **selimfedakar**（报告者）表示自己已有实现并抢先提交 #65394，双方礼貌协商，kavyansh-1 转为 review 者。
  - **kavyansh-1 的后续质疑（关键）**：实测发现 `XPUMxFp8LinearKernel` 与 `FlashInferTrtllmMxfp8LinearKernel` 在 `_supports_quant_scheme(None)` 下仍返回 True，即**permissive default 使两个自量化 kernel 漏网**；并追问"是否应改为 **fail-closed**（W8A16 kernel 显式 opt-in）更安全"。
- **争议焦点**：**默认值方向（permissive vs fail-closed）**——permissive 意味着每个新增自量化 kernel 都必须记得主动退出，易漏；fail-closed 更安全但需逐个声明。
- **结论**：Issue 于 11-18 11:19 关闭，对应 #65288 合入。**fail-closed 的建议尚未被采纳为全局策略**，仍是值得跟踪的设计风险点。

### 🛠️ 重点技术变更

**1. #58838 RoPE IR 化（merged）—— 影响融合匹配与 ROCm AITER**
将 `RotaryEmbedding` 从 `CustomOp` 迁为 IR op，使 QK-norm+RoPE+KV-Cache 融合不再依赖 `custom_ops=["+rotary_embedding"]` 强制标志；关键是**保留了 `MatcherRotaryEmbedding`**（否则会破坏 AITER 的 `QkNormRopeKvCacheFusionPass`），并新增 `aiter` IR provider，ROCm 优先级默认偏好 AITER。这是**IR 架构迁移与 ROCm 后端特有融合的一次精细平衡**。

**2. #68019 + #68505 量化线性 kernel 统一（前者 merged，后者 open）**
`LinearKernel` 根类统一七大家族接口，四个选择器合并为一个 `_first_usable_kernel` 循环；#68505 进一步拆分为 `fp8/` 与 `int8/` 独立家族并共享 `prepare_int8_scaled_mm_weights`。影响：**大幅降低选择逻辑重复，为后续按 QuantKey 的 oracle 化铺路**，同时触及 ROCm/AITER、CPU 等多后端。

**3. #67325 新增 Inkling 2 Small（merged）**
594B 总参 / 17B 激活 MoE，含 DSpark 投机解码器与 23 层 ViT，支持 NVFP4/MXFP8 两种检查点。技术亮点包括：all-reduce + short conv + residual + RMSNorm 融合为单个 NVLink-multicast kernel；sequence-parallel prefill 在 8K chunk 上 -22%/-26%；Gluon relative-bias 解码 kernel 在 100K 上下文 batch-1 下 15.1→4.8 ms。**是当日最大体量的模型接入**。

**4. #68552 CUDA graph sizing policy 迁入 Platform（merged）**
将 SM100 硬件默认值从 `VllmConfig` 移入 `Platform`，通过可覆写方法路由 prefill/decode grid 生成。**明确声明 AMD/XPU 物理验证尚缺**——这是架构重构中"接口先行、后端补齐"的典型，需关注后续 AMD 验证是否闭环。

**5. #67363 / #67364 DSv4.1 ROCm 压缩 KV cache 与 indexer 元数据融合（merged）**
#67364 将 compression launch 与 compressed-cache 写入合并，4 个 kv-source 层 8→4 次 launch，C1 解码步 **-34.5%**，且 NVIDIA 侧无影响（CUDA 不触发融合路径，编译指令等价）。**是 AMD 侧"按模型深度定制"方法论的标准范例**。

### 💡 值得关注的问题

**1. 严重正确性 Bug（运行期崩溃/指标误导）**
- **#68595**：引擎 `sleep(level=1)` 后调用 `/resume`（而非 `/wake_up`）会接受请求但内存未回填，EngineCore 因 `Pointer argument cannot be accessed from Triton (cpu tensor?)` 直接崩溃，**服务器对所有后续请求不可用，需重启**。属高优先级。
- **#68601**：`/v1/completions` 带 `echo+logprobs` 且 prompt 处理中被 abort 时返回 HTTP 500 `IndexError`（40 次实验 10 次复现）。
- **#68610**：TP>1 下 `vllm:num_requests_waiting` 在调度器看到请求前就计入（#65466 副作用），导致网关误判限流。作者提供两种修复形态征求意见，**属"非回滚但需修正指标语义"的典型设计决策**。

**2. 量化默认值安全性（延续 #65193 讨论）**
kavyansh-1 指出的 **permissive default 导致 XPU/FlashInfer-TRTLLM 仍接受 weight-only 请求**，以及"fail-closed 是否更安全"的建议未被采纳为全局策略。**建议社区将 MXFP8/MXFP4 等选择器的默认语义（fail-open vs fail-closed）作为设计规范正式讨论**。

**3. MonoKernel 路线的可持续性（#68544）**
66 个 AMD MonoKernel PR 在途、依赖链深、按模型手写。需要在"性能极致化"与"维护/CI 成本"之间找到平衡；#68544 的追踪表是良好的可见性工具，但**评审资源分配需 AMD 维护者明确**。

**4. ROCm 10.2 升级受阻（#68392）**
pre-commit 失败 + 合并冲突，而下游（gfx1250-strict 用户）有明确时间诉求。**需尽快协调 rebase 与 CI 重跑**。

**5. 跨后端数值正确性（#68413、#65385、#68386）**
Triton decode attention 的 GQA head 映射、GDN FLA prefill 在 Hopper+triton 3.6 的非确定性、fused_qk_norm_rope 的 int32 溢出与 NeoX 部分旋转损坏——**新 Triton 版本 + 多后端前提下，正确性回归测试覆盖需加强**，尤其 #68413 已指出 SGLang 有对应修复可参考。

**6. 架构重构的后端验证滞后（#68552）**
CUDA graph sizing 迁入 Platform 后，**AMD/XPU 物理验证仍 outstanding**，需跟踪避免"接口已改、后端未验"的隐性回退。
