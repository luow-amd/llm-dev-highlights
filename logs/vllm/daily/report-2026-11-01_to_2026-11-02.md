### 🎯 AMD/ROCm 生态相关动态

#### 1. Quark 量化与 MTP 组合缺陷（本周期最核心的 AMD 相关议题）

- **Issue #65034**（open，标签 `rocm`/`quantization`/`speculative-decoding`）：用户 `ihejia` 报告在 ROCm 10.1、2×GPU（gfx1201）、Qwen3.8-27B-Quark-AWQ-MXFP4 上启用 MTP 投机解码时，引擎初始化失败。根因是 Quark 的 `quantization_config.exclude` 中混用了**模块名**与**权重名**（如 `mtp.fc.weight`），而 Quark 后端只匹配模块名，导致 BF16 MTP head 被错误构建为 MXFP4，加载时触发 shape 断言。
- **PR #65023**（`jhartika-amd`，open，标签 `bug`/`quantization`）：针对上述问题的修复——在构建 `QuarkConfig` 时把以 `.weight`/`.bias` 结尾的 exclude 条目映射为模块名；对融合层（`qkv_proj`、`gate_up_proj`）在所有分片都被排除时才整体排除。附带单元测试，并说明三个读取 exclude 列表的调用点（`get_quant_method_target`、`get_quark_ocp_mx_group_size`、`is_shared_expert_quant_fse_compatible`）现在均看到模块名。
- **PR #65078**（`jhartika-amd`，open）：在 **128-CU gfx950（MI350P）** 上为 Qwen3.8-27B 实现 dense mono decode，堆叠在 #61573（MI355X）之上，将 K1/K2 persistent kernel 的 grid 宽度改为按 CU 数自适应（256 或 128）。在 MI350P 上解码 TPOT 单请求改善 11.6%，8 请求时 +6.6% 吞吐；256-CU 构建保持字节级一致。当前因冲突需 rebase。

> **分析**：这组 Issue/PR 反映了 AMD 生态中 **Quark 量化工具链与投机解码（MTP）组合的边缘路径**仍在补全。修复本身不复杂，但暴露了 exclude 配置格式在“模块名 vs 参数名”之间的契约模糊性，属于典型的跨组件集成缺陷。

#### ① PR #63440 — Muse Spark monokernel 的“精度换性能”争议（已合并）

- **核心议题**：在 8×MI355X 上以 `--monokernel` 让 Muse Spark 解码层 1–60 走 persistent FlyDSL 启动，宣称 AgentX 交互性 +57%、吞吐 +28%。

### 🛠️ 重点技术变更

**1. PR #56492 — Extensible KV Cache（已合并，架构级）**
把 KV cache 的容量决策从“CUDA Graph 捕获前的 profiling 估算”改为“捕获 + warmup 后按实际空闲显存提交”。核心是用驱动虚拟内存 API 预留地址区间，捕获期间只 backing 实际触碰的块，warmup 后一次性映射剩余物理页。**地址不移动**，因此层视图与已捕获 CUDA Graph 继续有效。默认在 CUDA 与 **ROCm + V2 runner** 启用，宣称默认多出 4–10% KV cache，并可将 `gpu_memory_utilization` 的 8% 安全余量转为可用容量。这是本周期对推理引擎内存模型影响最深远的变更。

**2. PR #63440 — Muse Spark FlyDSL decode monokernel（已合并，AMD 性能）**
在 MI355X 上把解码层 1–60 的 verify step 变为 persistent FlyDSL 启动（1 或 3 个 launch 覆盖从 attention 输出到下一层 q/o-gate/KV insert）。AgentX 交互性 +35%~+57%，吞吐 +21%~+29%；GPQA/AIME/RULER 精度在噪声范围内。代价是 MoE 激活保持 BF16、真实 acceptance length 略降（详见高热度讨论）。**这是 AMD GPU 上“单内核 + 持久化”路线的标志性合入**。

**3. PR #65023 + Issue #65034 — Quark exclude 参数名匹配（AMD 量化修复）**
修复 Quark checkpoint 中以 `.weight`/`.bias` 命名的 exclude 条目从不匹配模块名的问题；对融合层采用“全部分片被排除才整体排除”的语义。直接解除了 `amd/Qwen3.8-27B-Quark-AWQ-MXFP4` 在 MTP 投机解码下的加载失败，并统一了三个 exclude 读取点的行为。**属于小而关键的生态兼容性修复**。

**4. PR #65022 — AITER MLA 元数据在 CUDA Graph 中的生命周期（AMD 稳定性）**
识别出 `functools.lru_cache` 持有的 `num_kv_splits_indptr` device tensor 在 cache 淘汰后内存被复用，导致 graph replay 读到垃圾 split offset、decode 输出静默乱码。方案是在 capture 期间保留所有发出去的 tensor 引用（约每个捕获 batch size 一个），并加回归测试（capture → 清 cache → 复用内存 → replay → 要求 bit-identical）。**这是一类隐蔽的“长时间运行后才出现”的生产风险，对所有使用 AITER MLA CUDA Graph 的 ROCm 部署都有意义。**

**5. PR #65092 — kpool decode indexer logits workspace 预留（AMD 稳定性）**
GLM-5.3-Flash 在 ROCm 上 `batch_size × next_n × max_pool_len × 4` 超出 profiling 时的 workspace 与最大 graph batch，触发 `Workspace is locked`。修复在 `sparse_attn_indexer_kpool` 的 profiling 阶段预留最坏情况 buffer，与 `rocm_aiter_sparse_attn_indexer` 的做法对齐。**与 #65022 同属“ROCm CUDA Graph + AITER”稳定性系列。**
