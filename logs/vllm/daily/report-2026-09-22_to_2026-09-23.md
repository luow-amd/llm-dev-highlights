#### 3. #58144 — `--api-key` 被 `/invocations` 绕过（安全，2 条高密度评论）

**核心议题**：`GUARDED_PREFIX = ("/v1", "/v2", "/inference", "/cohere")` 为**前缀黑名单**，而 SageMaker 路由 `/invocations` 挂载在根路径且**无条件注册**，导致所有启用 `--api-key` 的部署都存在未认证推理路径（0.27.1 与 0.29.0 均可复现）。

**观点与扩展**：
- **iharshlalakiya** 指出 #58028（"deny-by-default" 中间件）已覆盖此问题，并进一步点出**同类缺口远不止 `/invocations`**：`/tokenize`、`/detokenize`、`/pooling`、`/score`、`/rerank`、`/classify`、`/generative_scoring` 均未受保护；**Rust 前端 `auth.rs` 的 `GUARDED_PREFIXES` 同样漏掉 `/cohere`**，两个前端行为不一致。并表示若 #58028 未覆盖愿接手。
- **Yunzez**（报告者）：确认 #58028 修复方向正确，保留 issue 直至该 PR 合并。

**争议焦点**：前缀白名单/黑名单的中间件**设计形态本身**才是根因缺陷——每新增一个根路径路由都会自动继承该漏洞。

#### 4. #58146 — ROCm AITER FA 优先级修正（3 条评论）

**核心议题**：`VLLM_ROCM_USE_AITER=1` 时文档与基准推荐的解码路径是 `ROCM_AITER_FA`，但优先级列表把非 AITER 的 `ROCM_ATTN` 排在前面。

**观点交锋**：

#### 5. #58267 — CPU W4A16 Whisper 双重缺陷（2 条高密度评论）

**核心议题**：3-D 激活未展平 + packed checkpoint 假 bias 尺寸错误，两者叠加导致崩溃与 WER 100。

**观点**：**hclsys** 逐行核对并补充关键细节——(a) 3-D 缺口是 `mixed_precision/cpu.py:190-204` 单个 if/else 的"两行不对称"，`use_w4a8` 分支之所以幸免是因为 `int4_scaled_mm_cpu` 包装器内部展平；(b) **仅放宽 C++ assert 无效**，因为 wrapper 自身用 `input.size(0)` 预分配输出 `(B, N)`，rank 与尺寸双错，必须在 Python 侧做 flatten/reshape。作者 harshaladhav-amd 随即提交 #58268 并在 PR 中给出了完整的 LibriSpeech 对比表。

### 🔥 热门话题与趋势分析

**1. AMD 平台从"能用"转向"用得好"**
本周期 ROCm 相关 PR 大致分为三档：(a) **内核级重写/调优**（RDNA3/4 的 W8A8、KV-split、prefix_prefill、线性注意力）；(b) **融合与编译**（AsyncTP、FP8 attn output、inverse RoPE）；(c) **测试与 parity 补齐**（MI355 gfx950、MoRI、GDN、NPS2）。AndreasKaratzas 一人贡献了 4 个"MI355 parity audit 发现的问题 + 测试"型 PR，构成一次系统性的质量扫荡。

**2. 量化格式的"第二重舍入"问题浮出水面**
#58157（DeepGEMM 将 FP32 block scale 二次量化为 UE8M0，实测权重误差 ~2.6%）、#58210（MXFP8 LDS 预算门控错用版本字符串）、#58089（零块 NaN）共同指向一个趋势：**随着 MXFP4/MXFP8/FP8 blockwise 在 AMD 与 Blackwell 上普及，量化路径上的格式转换细节正成为精度与稳定性的主要来源**。目前防护措施仍以 `model_type` 硬编码清单为主，缺乏通用信号，这是一处结构性技术债。

**3. 安全与前端一致性**
#58144 揭示的不是单点 bug，而是 **路径前缀白名单中间件的架构缺陷**，且 Python/Rust 两个前端实现已出现行为漂移。这类问题在 SageMaker、Cohere、XPU/Ray 多路由共存的当下会持续放大。

**4. CPU / ARM64 与 Triton Dispatcher 重构的遗留回归**
#58214/#58217 指出 #56323 把内核移到 `triton_kernel_dispatcher_with_warmup` 后，6 处 module-global monkey-patch 失效（另 2 处 shim 签名不匹配），导致 arm64/macOS 上的规格解码 fallback 从未安装——**x86 CI 因有 Triton 而永远覆盖不到**。这是"重构未同步全部调用点 + CI 平台盲区"的典型案例。

**5. 投机解码的纵深推进**
#52988（Kimi-K3 变长解码支持 adaptive DSpark 验证，已合并）、#58151（DSv4.1 DSpark）、#58164（MRV2 padded prompt-tail 保持在 FULL graph）、#57396（异构词表投机解码移除 CPU-GPU 同步，已合并，吞吐 +20~30%）、#58203（Qwen3.5/3.8 多模态 + native MTP 组合在 profile_run 崩溃）。**"多模态 × MTP"的组合场景**正在成为新的故障高发区。

**6. AI 辅助贡献成为显性议题**

### 🛠️ 重点技术变更

#### ① #51915 — GLM-5.2-MXFP4 在 ROCm deepseek_v32 路径打通（已合并）

**技术价值**：不仅启用了一个新模型，更修复了 4 个**同时影响 DeepSeek-V3.2** 的潜伏缺陷。其中最有价值的是 **indexer-K cache 布局不一致**（写入端 `fused_norm_rope` 只实现 `[n_blocks, blk, head_dim]`，读取端在 block size > 1 时选择 `SHUFFLE`），这会让 indexer 对垃圾 K 打分、输出退化。另外 **`batched_gemm_a16wfp4` 仅支持 2 的幂 K 且非幂次时静默返回错误值**，GLM-5.2 的 `qk_nope_head_dim=192` 恰好落在此区间——这是一个典型的"无报错但有错"的 API 契约陷阱。该 PR 从 8 月 12 日创建，历经多次 rebase 与 pre-commit 失败，最终在 MRV2 默认开启的背景下被优先推进落地。

#### ② #50814 — MXFP4 仿真权重的加载期反量化（已合并）

**技术价值**：在通用 MXFP4 仿真后端（`vllm/model_executor/kernels/linear/mxfp4/emulation.py`）中加入默认关闭的 `VLLM_MXFP4_EMULATION_DEQUANT_AT_LOAD`。核心权衡是 **显存换延迟**：BF16 解码权重约为 packed MXFP4 的 2× 显存，因此必须 opt-in（与 MXFP8 仿真默认开启形成对照）。fxmarty-amd 在评审中提供了关键上下文——该思路早在 #35855 被拒，但 #45381 引入 MXFP8 仿真时实际采纳了同一模式，因此现在是在补齐对称性。**对 AMD 场景（MI355X + Quark MXFP4 走 emulation 路径）有直接提速意义。**

#### ③ #58098 — ROCm BF16 AsyncTP 融合（已合并）

**技术价值**：ROCm 此前**从未导入 `AsyncTPPass`**，且现有 GEMM 模式匹配不到 ROCm linear 层发出的不透明 `rocm_unquantized_gemm`。修复后覆盖 BF16 + all-gather / reduce-scatter 两种序列并行模式，并要求**强制新鲜 Inductor 编译**（防止暖缓存绕过 rewrite 见证）。8 个双 GPU 数值用例 + 4 个 Llama 配置 + 训练态 Qwen 对照（双 worker rewrite 计数均 112）构成较强验证。这补齐了 ROCm 在分布式编译融合上与 CUDA 的能力差距。

#### ④ #52988 — Kimi-K3 变长解码 / 自适应验证支持（已合并）

**技术价值**：让 K3 的 MLA 与 KDA 解码路径可被捕获为 **FULL varlen CUDA graph**，以适配 DSpark 自适应验证的 ragged per-request draft budget。关键改动包括 `_cudagraph_support` 提升为 `ALWAYS`、`query_len_support` 提升为 `VARLEN`、用 `searchsorted` 在设备侧按 query offset 展平行，以及 RecoverSSM 的可选共存（`--use-replayssm`）。评审中 **TheEpicDolphin 指出 `ALWAYS` 在关闭自适应验证时可能导致退化**，但确认该问题在 DSV4 部分 backend 上已存在，同意另开 PR 统一修复——这是一个"已知代价换功能推进"的明确决策记录。

#### ⑤ #58253 — RFC：以 Reviewer 角色扩充评审产能

**技术价值**：这不是代码变更，但可能对项目治理影响最深远。提案参照 Kubernetes 的 reviewer/approver 模型，设立 **Reviewer** 角色承担 triage 与初审，作者需先解决 reviewer 反馈（或由 committer 裁决）才能请求最终合并。动机被明确归因于两点：(a) 贡献量超出评审容量，PR backlog 巨大；(b) AI 生成贡献增加了甄别成本。该 RFC 尚无评论，但其与今日观察到的"154 新增 PR vs 59 合并（约 38% 合并率）"以及大量 `mergify` 自动冲突提醒高度吻合——**维持高吞吐评审已成为当前最紧迫的工程组织问题**。

### 💡 值得关注的问题

1. **#58253 RFC — Reviewer 角色**（尚无评论，但影响项目治理结构）：如果将 reviewer 反馈设为合并前置门槛，需明确 reviewer 的选拔、权限边界（能否 `/ci run`）与与 committer 的裁决关系。
2. **#58144 / #58028 — 认证中间件应改为 deny-by-default**：`/tokenize`、`/detokenize`、`/pooling`、`/score`、`/rerank`、`/classify`、`/generative_scoring` 以及 Rust 前端的 `/cohere` 均需一并覆盖，否则两个前端会持续漂移。
3. **#58191 — 水印功能可按请求 opt-out**：服务器配置 `--watermark-config` 后，客户端仍可发送 `"watermarking": false` 静默关闭，与 RFC #53916 "不可被下游修改"的设计目标矛盾。作者已提出 enforce 标志但尚在评审。
4. **#58214 — CPU / ARM64 规格解码静默失效**：6 处 fallback 从未安装，且 x86 CI 因有 Triton 而结构性无法覆盖。需要评估是否有其它平台也存在同类"monkey-patch 失效但无报错"的盲区。
5. **#58157 — DeepGEMM UE8M0 二次量化的精度治理**：当前的 `model_type` 硬编码排除清单不可持续，建议向"按量化路径属性"而非"按模型名"演进。
6. **#46249 所揭示的 xgrammar C++ 上游依赖风险**：vLLM 的 strict tool calling 正确性强依赖外部语法引擎，用户侧仅有 `VLLM_ENFORCE_STRICT_TOOL_CALLING=false` 这一牺牲功能的绕过手段，缺乏更细粒度的降级策略。
7. **#58203 — 多模态 + native MTP 组合崩溃**：图像 XOR MTP 均正常、两者同时启用即崩，属于典型的特性组合矩阵覆盖不足，建议纳入 CI 组合测试。
8. **#58236 — vLLM 0.29.0 预编译包 + FlashInfer 0.6.18 触发 CUDA kernel 编译错误**：用户耗时近一周才通过降级到 0.28.0 定位，反映依赖版本组合的验证成本过高。

---

**报告结论**：本周期 vLLM 的核心叙事是"**AMD 平台能力的横向铺开与纵向硬化**"——RDNA 消费级内核、CDNA AITER 集成、Quark MXFP4 量化路径、MI355/gfx950 测试 parity 四条线同时推进，且多个 PR 具备完整的内核级与服务级实测数据。与此同时，**认证中间件架构缺陷（#58144）、CPU/ARM64 重构回归（#58214）、量化格式二次舍入（#58157）** 三项横切问题与 **RFC#58253 评审产能治理** 一道，构成了下一阶段需要community集中投入的方向。
