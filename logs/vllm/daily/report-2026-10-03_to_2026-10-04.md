### 1. ✅ 已合并：[ROCm][RDNA3] 修复 W4A16 split-K 精度与确定性（#54706）
**这是本周期 AMD 生态最重要的变更，也是讨论最热烈的 PR。**

- **问题本质**：RDNA3（gfx11）的 W4A16 GPTQ kernel 通过 CAS 原子操作在 **bf16/fp16** 中累加 split-K 分片。由于窄化发生在累加**之前**，而低精度加法不满足结合律，导致"哪个分片先赢得 CAS"决定最终结果——**每一次前向传播都存在数值误差**，贪心解码时表现为 `argmax` 抖动（#50603 的线索），采样时则被采样噪声掩盖。
- **根因**：gfx11 缺少 packed bf16/fp16 原子指令（`global_atomic_pk_add_bf16` 仅 gfx94x 支持），原实现用 CAS 重试循环模拟，同时引入了执行顺序依赖。
- **修复方案**：保留计算 kernel 与 dispatch 不变，仅替换 epilogue——FP32 分片 → **固定升序 z 的 FP32 归约** → 最终一次性 cast 到 bf16/fp16。`k_split==1` 与 `z_count==1` 路径直接原地写回，无 scratch、无原子操作。
- **精度收益**：W7900/gfx1100 上最大绝对误差从 0.24–0.37 降至 0.062 级别。
- **性能收益**：经 JartX 审查建议将 scratch 由 `zeros` 改为 `empty`（证明所有 reducer 可见的 `(z,m,n)` 槽位恰有一个写入者）后，bf16 M=16 从 58.8µs 降至 53.7µs，所有 `k_split > 1` 形状提升 3.8–8.7%，确定性路径达到或快于此前的 CAS 对照。
- **独立验证**：@cadamcat 在 2× RX 7900 XT（gfx1100, ROCm 7.14, TP=2）上重建 `_rocm_C` 做 A/B，Muse-Glimmer-30B INT4 在 512 上下文由"8 次生成 6 个不同结果"变为 1 个，32/32 次生成完全一致。

### 4. 🟠 新增 Issue：legacy `fused_moe_lora` kernel 静默将 fp16 LoRA 操作数转 bf16（#59920）

## 💬 高热度讨论分析

### ① PR #54706 — [ROCm][RDNA3] W4A16 split-K 精度与确定性（8 条评论，已合并）
**核心议题**：CAS 原子累加 vs FP32 scratch 二次归约的架构取舍。

| 参与者 | 立场与观点 |
|---|---|
| @AIwork4me（作者） | 以精度为第一性，贪心不确定只是"可见症状"；接受把 scratch 从 `zeros` 改为 `empty` 的建议，换来 3.8–8.7% 性能回升 |
| @cadamcat（独立验证者） | 在 2× RX 7900 XT 上自行重建 `_rocm_C` 做 A/B，用"32/32 一致 vs 4 个 cell 中 2 个抖动"把结论从"合理叙事"变成"定论" |
| @JartX（原 CAS epilogue 作者） | 承认原始设计动机是让 bandwidth-bound 的 epilogue 保持单次 pass；但"低估了 CAS 带来的累积代价"。用 **NaN 毒化 allocator** 的方式验证了 `empty` 安全性（16/16 用例一致） |

**争议焦点**：单次 pass 的带宽优势 vs 确定性与正确性。最终结论是**正确性优先**，且通过 `empty` 替代 `zeros` 部分追回了性能损失，**在确定性路径上达到与 legacy CAS 对照持平或更快**。

## 🛠️ 重点技术变更

### ① PR #54706（已合并）— ROCm RDNA3 W4A16 确定性修复
**技术解读**：把"execution-order-dependent 的 CAS 原子累加"替换为"FP32 scratch + 固定升序归约 + 单次窄化"。关键在于证明了所有 reducer 可见槽位**恰有一个写入者**，从而允许 `at::empty` 代替 `at::zeros`，把确定性带来的性能损失几乎完全抵消。
**影响**：所有 RDNA3（RX 7000 系列 / gfx1100/1101/1102）上运行 GPTQ/AWQ W4A16 的用户，**重复推理结果不再随机漂移**；这是 AMD 消费级 GPU 上推理可信度的基础修复。

### ② PR #59160（已合并）— sleep 时释放 CUDA graph pool
**技术解读**：新增 opt-in `sleep_mode_offload_cudagraph`，把 CUDA graphs 捕获到 **cuMem 支撑的专用 pool**，sleep 时释放物理内存、wake 时重映射同一虚拟地址（**不重捕获 graph**）。
**影响**：大规模 MoE 部署中，sleep 模式此前无法回收的 GiB 级 graph pool 现在可释放，直接提升多模型/弹性部署的显存周转效率。

### ③ PR #59900 / Issue #59887（开放）— FlashInfer CuteDSL MegaMoE kwarg 兼容性
**技术解读**：FlashInfer 在 v0.7.1rc1 将字段 `in_kernel_fc2_reduce` 重命名为 `enable_in_kernel_fc2_reduce`，而 vLLM pin 的是 0.7.0.post1。修复只需**删除该 kwarg**（其在所有版本中默认均为 `False`），从而使修复不依赖 FlashInfer 版本。
**影响**：附带新增一个**可在 L4 上运行**的适配器契约测试，堵住了"仅 SM100+2GPU 才能测"的 CI 盲区——这是比单点修复更有价值的工程改进。

### ④ PR #59894（开放）— DSV4.1 Decoder replay 剪切层拆分
**技术解读**：第 20 层（cut layer）的 KV 在 replay 中被后续层与后续 step 读取，但其 **query 侧与 FFN 只服务于 replay 行**。按行拆分后，全上下文 indexer 打分（2·32·128·L FLOP/行，L=128k 时约 1.07 GFLOP）只对 replay 行执行。
**影响**：B200 上 DSV4.1-Flash DEP4 实测 128k 输入 +6.7% 总吞吐、32k 输入 +4.1%，TTFT 同步下降。

### ⑤ PR #59895（开放）— Marlin int8 激活分组 scale 归一化
**技术解读**：`marlin_act_int8_process_scales` 按 `abs().max()` 而非 `max()` 归一化，使负 group scale 在 int16 cast 后不溢出；**必须与 #48926（kernel 改按 signed int16 读取）同时或在其后合并**。
**影响**：对称 AutoRound W4A8 checkpoint 的 GSM8K 从 **0.0% 恢复到 74.0%**（W4A16 参考 76.7%）——这是一个此前完全不可用的量化配置。**合并顺序是硬约束，需维护者注意。**

## 💡 值得关注的问题

### 🔴 高优先级
1. **FlashInfer MoE-EP 后端的 fail-fast 缺失**（#59887 / #59903）：vLLM CUDA 镜像不携带 `nvshmem4py`，且后端支持检查不校验该依赖，导致用户在加载完整 checkpoint 后才失败。应把依赖检查前移到后端选择阶段。
2. **`fused_moe_lora` 静默精度损失**（#59920）：fp16 模型在 `fully_sharded=True` 或 `max_lora_rank > 128` 时被强制降为 bf16 点积，**无任何警告**。与 ROCm Triton 类型推断直接相关，建议合并修复 + 增加 dtype 断言。
3. **Marlin int8 修复的合并顺序**（#59895 ↔ #48926）：两 PR 互为前提，任一单独合并都会让情况更糟（表格显示 `uint16+abs().max()` 会让 `all_neg` 从"侥幸通过"变为 8/8 失败）。需要维护者显式协调。

### 🟠 中优先级
4. **Gemma 4 E4B AutoRound-GPTQ 在 0.24.0 回归**（#59905）：`audio_tower` 期望未量化的 `.weight`，而同 checkpoint 在 0.22.1 可正常服务，属明确版本回归，但当前无评论、无 assignee。
5. **多模态图片静默丢弃**（#59876）：请求级 `chat_template_kwargs` 存在时所有图片被丢弃且返回 200。报告者 @AbdulAliMamnun 已用 `render_chat` 在 main 与 v0.30.0 上**未能复现**，且逐条排除了"kwargs 合并丢图"的假设——意味着该问题可能位于特定模型配置（NVFP4 ModelOpt + gemma4 parser）的组合路径，**需要报告者补充最小复现**。
6. **`--api-key` 默认拒绝策略的争议**（#59892）：维护者 @DarkLight1337 明确表态*"API_KEY 的作用范围限制是有意为之，除非 @simon-mo 想改变"*。该 PR 会把 `/metrics`、`/docs`、`/server_info` 纳入鉴权，**属破坏性变更**，需产品层面决策。
7. **Qwen4Exp PLE 在 sm_86 无法编译**（#59868）：`fp8e4nv` 在 Ampere 消费卡不支持，且 `--engram-config cpu_offload` 是唯一可用路径——形成硬阻断，影响 3090 用户。

### 🟡 需要社区重新激活
8. **#41961（MI325X/RDNA4 Float8_e8m0fnu）**：修复方案已验证（MI300 复现成功、RDNA4 数据点存在），但被 stale 关闭且未并入 main。**建议转为 PR 提交**。
9. **#32732（Blackwell MLA + fp8 KV cache）**：RTX PRO 6000（sm_120）至今无可用 MLA 后端，社区有可移植的 SGLang patch（sgl-project/sglang#17908）可参考。
10. **批次不变性（Batch Invariance）的边界声明**：#59863 与 #59883 都反复强调"batch invariance ≠ prefill/decode invariance ≠ train/rollout 一致性"，并要求用独立的 opt-in 模式固定 requestwise 的 dispatch 顺序与精度契约。**这是 DeepSeek-V4 系列最值得跟踪的设计决策**，因为它直接决定 RL 训练与推理的一致性保障范围。
