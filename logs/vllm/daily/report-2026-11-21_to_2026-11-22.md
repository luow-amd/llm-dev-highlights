## 🛠️ 重点技术变更

### 1. #69028 `[Model] Add Inkling 2 Mini`（已合并）
**影响**：vLLM 正式支持 Thinking Machines 的 26B/3.5B-active 循环 MoE。技术亮点包括：loop core（layers 6–17）每 token 三遍共享权重，每遍保留独立 KV/conv-state cache，并从第二遍起合并前一遍 gated messages；支持可变循环（`loop_num_passes`）、DSpark 投机解码（读取目标层 hidden states）、text/image 输入及 `inkling` reasoning/tool parser（Python + Rust 双前端）。GSM8K 97.0%（TP1）。这是**新一代“循环/递归”架构**进入推理引擎的重要信号。

### 2. #69065 `[Kernel][GDN] Faster fused CUDA MTP decode for 16-bit recurrent state`（已合并）
**影响**：为 BF16/FP16 recurrent state 新增独立融合 kernel，使 16-bit state 达到 5.8–6.3 TB/s（原 ~4.0），**与 FP32 state 持平**；Qwen3.8-Flash-Next-FP8 上 decode step 最高 −5.3%。关键是 **FP16 state 现在能走融合 CUDA 路径**（此前回退 Triton）。输出与现有 kernel **bitwise 一致**（240 例 0 比特差异），设计借鉴 FlashInfer `cake_gdn`（已注明 Apache-2.0 归属）。这直接改善投机解码在长上下文/高并发下的状态带宽瓶颈。

### 3. #69191 `[ROCm][Attention] FlyDSL FP8 extend kernel`
**影响**：AMD `gfx950` 上 FP8-query prefill 的关键内核。**exp-free softmax** 把 e4m3 值的指数/尾数位直接写入字节（`x = n + f`，`n` 进 exponent 域、`round(8f)` 进 mantissa），用一次 FMA + 整数 round 替代 `exp2` + 转换。在 16k/98k 场景下 `unified_attention` 4.64 → **8.67**（+87%）。这是 **AMD 在 FP8 注意力 softmax 上针对 VALU 瓶颈的架构级创新**，且 sliding-window 层同样受益。

### 4. #66719 `[Bugfix][KV Offload] Store the chunks that fit`（已合并）
**影响**：修复“请求未存储 chunk 数超过 CPU tier 容量时**永远不被 offload**、每步重试并报 `cannot store chunks`”的问题。引入 `unconsumed_keys` 语义，CPU manager 按 `get_offload_key_position()` 位置排序、只存能容纳的最低位置 chunk。实测 `cannot store chunks` 401 → 0，store 传输 0 → 10，fs tier 由 0 → 119 chunk。讨论中社区还识别出**自驱逐**（later steps 驱逐自身 prefix）这一既有行为，约定在后续 issue 中结合 #64216/#57813 处理。

### 5. #69137 `KV transfer scheduler unconditionally frees blocks`（安全）
**影响**：若属实，这是一个**可被单个低权限请求触发、跨 tenant 拖垮 EngineCore** 的缺陷，且在 `v0.30.0` 与 `v0.33.0` 上行为未变。更严重的是**在途 DMA 可能把请求 A 的 KV 静默写入已属于请求 B 的 block**——不仅是 crash，还有**静默数据污染**。该问题已进入安全披露流程讨论，是本周期风险等级最高的事项。
