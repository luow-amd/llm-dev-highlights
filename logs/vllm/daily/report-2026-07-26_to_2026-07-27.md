**性能优化：**

- **[ROCm][Perf] 加速大 MoE ReLU-squared 激活 (PR #49872)**：`rlrs` 贡献，为 MI250X (gfx90a) 上的 MoE ReLU-squared 操作用一个 Triton 内核替换原有的两步操作，在 180K+ 行配置上实现了 **最大 1.32 倍** 的速度提升。
- **[ROCm][Perf] 添加 MI250X 选择性状态更新调优参数 (PR #49871)**：`rlrs` 贡献，为 MI250X 上的 Mamba 类选择性状态更新提供了针对性的内核启动配置（block/warp 大小），在 TP8 运行时，此操作的耗时降低了 7.7%。

### 💬 高热度讨论分析

**1. Issue #49896: DeepSeek-V4 在 SM12x 上因 NaN 导致非法内存访问 (DeepSeek-V4 on SM12x: NaN MQA logits drive top_k to emit uninitialized smem)**

- **核心议题**：用户 `linjiapro` 详细报告了在 Blackwell (SM120) 上运行 DeepSeek-V4-Flash 时，长 prompt 请求必然导致 CUDA 内存访问错误的根因。
- **观点与演进**：
    - **初始发现**：作者通过逐层审计，定位到 `fp8_fp4_mqa_logits` 在 SM120 上产生大量 NaN 的 logits。
    - **争议/误判修正**：作者最初认为是 DeepGEMM 的 MQA logits 内核本身有问题。但在进一步分析后，**修正为自己的结论**：NaN 并非源于 DeepGEMM 内核，而是产生于更早期的层（layer 0-1），且 `hidden_states` 在进入注意力层前就已经是 NaN 了。这一过程展示了严谨的 root cause 分析。
    - **后续发现**：作者进一步发现，NaN 的传递具有随机性（但在一台服务的生命周期内保持稳定），与 DeepGEMM 和 CUDA Graph 的组合有关，排除了许多常见影响因素。最终将问题缩小到 DeepGEMM 内核在 SM120 上的**非确定性行为**，并已在 DeepGEMM 项目上提交了 Issue (#392)。
    - **当前状态**：`linjiapro` 提交了 **PR #49897** 作为根因链上层的**紧急修复**：在 SM12x 上绕过有问题的 `top_k_per_row_prefill` 内核，使用 `torch.topk` 替代，将引擎崩溃转为定义清晰的行为。NaN 的根本修复（DeepGEMM 内核层面）仍在进行中。

**2. Issue #49921: BF16x3 路由 GEMM 在 family-120 (GB10/DGX Spark) 上被阻挡 (BF16x3 router GEMM gated off family-120)**

- **核心议题**：用户 `Reederey87` 指出，在 GB10 (SM121) 上，DeepSeek-V4-Flash 的专用路由器 GEMM 路径中，BF16x3 内核是唯一理论上适用的，但它被一个简单的架构族检查 (`is_device_capability_family(100)`) 错误地阻挡了。
- **观点**：
    - **发起方**：认为只需放宽架构检查到 family-120 即可。
    - **验证方 `hclsys`**：同意门控检查是问题所在，但在 GB10 上进行了实际编译测试后发现，**直接放宽门控会导致 CuteDSL 内核编译失败** (`NVVM backend compilation failed`)，因为该内核尚未支持 `sm_121a` 目标架构。
    - **结论**：讨论指出，无法简单地拓宽门控，这需要解决 `sm_121a` 的 NVVM 编译支持问题，或者开发替代的非 CuteDSL 内核路径。目前状态为 open，等待方案。

**3. Issue #49878: Gemma4 KV Cache 大小从 v0.25.1 到 v0.26 激增约 40% (Dramatic KV cache size increase for Gemma4)**

- **核心议题**：用户 `handcraftedbits` 报告，在未改变配置的情况下，从 v0.25.1 升级到 v0.26.0 后，Gemma4 模型的 KV Cache 分配空间增大 40%，导致 OOM。
- **观点**：
    - **用户**：提供了清晰的复现环境和日志证据，怀疑是一个回归。
    - **分析与解答 (`a-kaa`)**：精准定位到了 **PR #47728** (异步调度更改) 导致的。该 PR 引入了“两个并发批次”的概念来估算滑动窗口 KV Cache 的大小，在用户配置下，这导致计算时使用的“在途 tokens”翻倍，从而大幅增加了缓存需求。作者给出了详细的计算过程，完美匹配了用户报告的数字。
    - **状态**：Issue 仍为 open，但问题根因已被社区专家彻底定位。

**4. PR #49917: 根据 trtllm-gen 限制 FlashInfer 的 512 头大小（Gate FlashInfer 512 head size on trtllm-gen）**

- **核心议题**：PR #49917 旨在解决在非 Blackwell 架构上强制使用 FlashInfer 后端处理 512 维头尺寸时崩溃的问题。
- **观点**：
    - **PR 作者 `YM2132`**：认为应按架构族（SM100）来门控 512 头大小的支持，因为只有 Blackwell 的 `trtllm-gen` 内核支持此尺寸。这会让旧 GPU 在配置时立即报错，而不是在运行时崩溃。
    - **审阅者 `lesj0610`**：提出了**强有力的反对意见**。他指出 FlashInfer v0.6.15.post1 已经包含了对 SM8x 架构 512 头大小的支持，而 vLLM 当前最新版刚好 pin 了这个版本。因此，门控条件不应该是架构，而应该是**实际的 FlashInfer 内核可用性**。此外，根本的崩溃原因 `Unsupported max_mma_kv: 0` 是一个共享内存计算溢出问题，在 FlashInfer 的修复中已经解决。因此，`lesj0610` 认为这个 PR 不仅过时，而且长期来看会导致错误行为。
    - **状态**：PR 仍为 open，但审阅者的意见很关键，PR 很可能需要调整方向。

### 🔥 热门话题与趋势分析

1. **Blackwell (SM12x/SM120) 新架构适配攻坚期**：多个 Issue (#49896, #49921, #49926, #49886) 和 PR (#49892, #49891, #49897, #49917) 都围绕着 Blackwell 的适配。核心问题集中在：
    - **CUDA Graph 与确定性**：DeepGEMM 和 FlashInfer 的内核在 SM12x 上表现出非确定性或需要特殊的预热/图处理。
    - **数值精度**：FP4/E8M0 等新数据类型相关的 logits 计算出现 NaN。
    - **内核编译与兼容性**：CuteDSL、FlashInfer 等内核可能尚未完全支持新架构，导致编译或运行时错误。

2. **KV Cache 卸载与分布式推理成为核心工程方向**：大量的 PR 专注于 KV 卸载（Offloading）和跨节点 KV 传输（P2P），如 MoRIIO (#46116)、MLA 去重 (#48906)、SWA 加载修复 (#49052) 等。这表明 vLLM 正在从单机推理向**多节点、异构、弹性扩展**的分布式系统演进，以支持更大的模型和更高的并发。

3. **推测解码 (Speculative Decoding) 持续优化与维护**：Bug 修复（如混合精度 draft 模型 #49893，MTP 权重加载 #49856）和新特性（如 ReplaySSM #49887，动态推测长度 DSL 的 RFC）频繁出现，说明推测解码作为关键性能优化手段，仍在快速迭代中。特别是与量化技术的交互（#49893）成为了新的关注点。

4. **量化生态的深化与细节打磨**：多个 Bug 和修复针对特定量化方案的边界情况，例如 Compressed-Tensors 的混合精度 (#49893)、Marlin repack 的对齐要求 (#49862)、NVFP4 的 CV 告警 (#49890) 及 DeepGEMM FP8 的 CUDA Graph 兼容性 (#49928)。这表明主流量化方案（GPTQ、AWQ、FP8、NVFP4）的基本集成已趋稳定，但长尾的交互问题和微小的性能/正确性缺陷正被逐件解决。

### 🛠️ 重点技术变更

1. **PR #49888: 支持 gfx90a 上的 AITER 分页注意力**：这可能是本周期对 AMD 平台最重要的技术变更。它允许 MI250X 用户使用 AITER 后端，在 MoE 模型上获得了 **54.5% 的吞吐量提升**，极大地缩小了与 CUDA 平台的性能差距。此变更依赖于几个上游 AITER 和 CK 的 PR，表明 vLLM 正在深度集成 AMD 的底层优化库。

2. **PR #49897: 修复 DeepSeek-V4 在 SM12x 上的 NaN 崩溃**：这是一个“止血”性但至关重要的修复。通过将出现 Bug 的 Triton 内核替换为 `torch.topk`，将 DeepSeek-V4 在 Blackwell GPU 上的**确定性崩溃**转化为一种**次级正确性表现**（输出质量可能下降，但服务不会崩溃）。这为 BlackWell 上的进一步调试和最终修复创造了条件。

3. **PR #49900: 修复 Draft 模型下的混合精度量化加载**：此 PR 修复了一个**经典的前缀裁剪问题**。当一个量化检查点被用作 draft 模型时，其权重前缀被改变，导致量化配置的模块匹配失败。修复方案是在量化配置中记录根前缀，并在匹配前正确裁剪。这对于需要将量化小模型作为 draft 模型的用户来说是一个重要的可用性修复。

4. **PR #46116: MoRIIO 异构 KV 传输**：此 PR 的合并标志着 vLLM 在分布式推理架构上的一个进步。它允许 Prefill 和 Decode 阶段使用不同的并行策略（例如，Prefill 使用 Data Parallelism，Decode 使用 Tensor Parallelism），从而更灵活地利用集群资源并提升整体吞吐量。在 AMD MI300X 上验证了其效果。

5. **PR #49891: 修复 Full CUDA Graph 下 MTP 推测解码的输出损坏**：此 PR 发现了 CUDA Graph 和 FlashInfer prefilled 包装器之间的一个微妙交互问题。当 MTP 验证阶段调用 FlashInfer 的 prefill 路径时，包装器在 CUDA Graph 内部错误地分配了新张量，导致后续 replay 时读到陈旧数据。修复方案是为 prefill 包装器也进行 CUDA Graph 适配，是 Blackwell 性能优化道路上的关键细节。

### 💡 值得关注的问题

1. **DeepSeek-V4 在 Blackwell 上的全面支持仍需时日**。虽然 #49897 提供了崩溃的缓解方案，但 NaN logits 的根本原因（可能涉及 DeepGEMM 内核在 SM120 的非确定性）仍未解决，并且任何正确性修复都依赖于上游 DeepGEMM 的更新。此问题（#49896）是 Blackwell 用户的首要障碍。

2. **GB10/DGX Spark (SM121) 的性能潜力尚未释放**。除了 DeepSeek-V4 的问题，#49921 指出专门的路由器 GEMM 路径因 NVVM 编译问题无法启用，限制了该平台的性能。

3. **`stream_interval` 作为请求级参数引入 (PR #49754)** 的合并可能引发关于安全性和资源控制的新讨论。虽然已合并，但审阅者 `DarkLight1337` 的担忧（客户端不应随意降低服务端的流式间隔）值得社区进一步探讨，尤其是在多租户场景下。

4. **Process Checkpoint 生命周期 (PR #46877)** 的合并为未来实现模型热升级或弹性伸缩铺平了道路，但其依赖的 CUDA Checkpoint 等系统级特性尚处于非常早期的阶段，且存在用户 `matteso1` 报告的与 CUDA 兼容用户空间库的冲突问题，这将是未来集成的关键风险点。
