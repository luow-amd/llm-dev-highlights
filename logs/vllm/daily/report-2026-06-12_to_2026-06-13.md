### 💬 高热度讨论分析

1.  **#45388 / #45387 / #45406: KV-Cache调度器死锁问题**
    *   **核心议题**：当启用KV-Cache卸载连接器时，V1调度器在特定条件下会发生永久性死锁。表现为`Running: 0, Waiting: N, GPU KV Cache usage: 0.0%`，无法恢复。
    *   **观点**：
        *   **提交者 (`howarlii`)**：详细描述了死锁触发的精确条件（两个并发请求复用了已经被卸载到CPU的KV-Cache前缀，但单独各自都能放入GPU缓存）。
        *   **`waynehacking8`**：首先指出该场景已被某个前置PR修复（#44560），但更关键的是，他发现了更深层的结构性漏洞：即使有#44560的修复，在特定调度策略（如优先级调度）下，队列头部的不可调度请求会阻止后续`WAITING_FOR_REMOTE_KVS`状态的请求被处理，导致死锁。并提出了最小修复方案 #45406。
        *   **`Rishi-Dave`**：给出了最精确的根因分析：在`vllm/v1/core/sched/scheduler.py`文件中，第781行的`break`语句是罪魁祸首。当一个处于`WAITING`状态的请求（A1）因为资源不足阻塞了调度循环时，它会直接跳出，导致后面对`WAITING_FOR_REMOTE_KVS`状态的请求（B1）的推进机会被完全跳过，即使B1的异步数据加载已经完成。
    *   **争议焦点**：问题的根本原因到底是用户报告的特定场景，还是调度器逻辑中更普遍的结构性缺陷？结论是后者。
    *   **当前状态**：最关键的问题是调度器的逻辑缺陷，社区已经给出了多个分析和修复PR。此讨论反映了社区对调度器这一核心组件的高关注度和深度分析能力。

2.  **#45367: `/v1/messages`流式API中断问题**
    *   **核心议题**：vLLM的Anthropic兼容API在流式传输`message_start`事件时，因`exclude_unset=True`序列化选项，丢掉了带有默认值的`type`和`role`字段，导致严格的Anthropic SDK客户端无法解析，从而产生“假死”现象。
    *   **观点**：
        *   **提交者 (`markbdean01`)**：精确报告了该Bug的现象和根因，指出问题出在流式路径的序列化逻辑上。并提供了绕过此Bug的直接体验——让Claude Code在vLLM上完美运行。
        *   **`waynehacking8`**：快速响应，提交了修复PR #45376。
        *   **`bbrowning`**：起初表示需要自己复现，并坚持在修复前需要理解问题。随后通过添加调试日志，成功复现了`model_dump_json`前后数据不一致的问题，证实了Bug的存在。
    *   **争议焦点**：无。这是一个明确的Bug，讨论集中在如何高效、准确地修复它，以及代码审查的严谨性上。
    *   **当前状态**：问题已定位，修复PR已提交，并被合并。此事展现了社区在兼容性和边缘情况下的快速响应能力。

2.  **性能优化进入“深水区”**：
    *   **算子融合**：本周期有多个PR专注于Kernel层面的融合优化，如Fused K-RoPE + FP8量化 (#45370)，Fused RMSNorm + FP8量化 (#45428)等。这标志着vLLM的性能优化正从简单的模型并行和内存管理，深入到更底层的计算流水线优化，追求极致的硬件利用率。
    *   **MLA与稀疏注意力**：针对新一代模型常用的Multi-Latent Attention (MLA)，社区在指标计算 (#39457) 和消除性能瓶颈 (#45450, #45426) 方面持续投入，尤其在FlashMLA和DCP（解码上下文并行）的结合上。
    *   **推理引擎稳定性**：V1调度器的死锁问题 (#45388, #45387, #45406, #45414) 成为本周期最受关注的性能稳定性Bug。这表明，随着调度器逻辑日益复杂（支持KV卸载、异步调度、策略调度等），确保其在所有情况下不“死锁”是系统化工程的巨大挑战。

3.  **结构化输出与工具调用修复**：
    *   结构化输出（SD，如JSON Schema）与特殊解码机制（如扩散模型的块解码、推测解码）之间的冲突是一个新兴且复杂的问题 (#45436)。社区正在积极识别这些冲突点并添加相应的保护性逻辑或错误提示。
    *   各类工具的流式解析器（Streaming Parser）是本周期修复的高频领域，包括`Qwen3` (#45413)、`Gemma4` (#45479)、`Hermes` and `Qwen3`的`tool_choice=required`模式 (#45389) 等。这些修复集中在处理边界情况，如跨delta边界、多token输出、参数中含有特殊字符时的正确解析。

### 🛠️ 重点技术变更

1.  **#45163 [Model] Add DiffusionGemma Support**：这是一个里程碑式的PR。它引入了谷歌的扩散语言模型DiffusionGemma。其意义在于vLLM不再局限于传统自回归模型，开始支持扩散模型这种全新的生成范式。这需要处理模型特有的“画布”（canvas）、“去噪步”等概念，对引擎的调度和推理流程有深刻影响。
2.  **#45381 [Model] Add MiniMax M3 support**：MiniMax M3是目前非常热门的混合专家模型（MoE）。此PR为其添加了从模型配置、处理器、内核到推理/工具解析器的完整支持链。此外，它与MXFP8、MXFP4等量化格式的支持紧密结合，展示了vLLM对新主流模型的快速适配能力。
3.  **#35264 [KV Connector]: Support KV push from Prefill to Decode node using Nixl KV Connector**：这是一个大型功能，支持在KV缓存连接器中实现“推送”模式。在预填充-解码（P-D）分离部署中，以往解码节点需要去“拉取”KV缓存，现在预填充节点可以直接“推送”，显著降低了首Token延迟（TTFT），提升幅度可达1.2x至3.0x。这是提升大规模在线服务体验的关键技术。
4.  **#44893 [ROCm][gpt-oss] Pass GateMode.INTERLEAVE for MXFP4 W4A16 fused MoE**：此PR虽然只改动了一行代码，但其影响巨大。它揭示了在异构硬件和软件栈上运行复杂模型时的“隐性兼容问题”。更新后的AITER库不再容忍之前的默认参数，导致整个模型的推理结果完全错误（accuracy=0）。这个修复不仅解决了问题，更强调了在底层库升级时需要仔细验证参数兼容性的重要性。
