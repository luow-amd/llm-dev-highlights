1. **[Bug][ROCm][MoRIIO] MI300X SR-IOV VF READ over XGMI 崩溃 — Issue #61144**
   - 作者：`chunfangamd`（含 `-amd` 后缀，通常为 AMD 员工）。
   - 环境：vLLM `0.31.0+rocm723`、`amd-mori 1.0.0`、torch 2.13、HIP 7.2.53211；8× MI300X SR-IOV VF，gfx942，XGMI 全互联；模型 Llama-3.1-8B-Instruct。
   - 现象：`MoRIIOConnector` 在 `backend: xgmi`、READ 模式下，decode 在首个请求时发生 GPU memory access fault，EngineCore 死亡，后续请求失败；WRITE 模式正常，MI355X 裸金属 gfx950 下 READ/WRITE 均正常。
   - 影响：MI300X 虚拟化 + XGMI + MoRIIO READ 模式下 P/D 分离可能不可用，属于 AMD 平台关键稳定性问题。已有 ROCm 相关维护者被 CC。

2. **[ROCm][Perf][DSv4.1] 所有 backbone 层启用 mono decode — PR #61082**
   - 作者：`Fangzhou-Ai`。
   - 在 MI355X 上，通过 `VLLM_ROCM_MONO_DECODE=1`，将 DeepSeek-V4.1-Flash 全部 40 个 backbone 层以 K1+K2 整体运行，替代此前 30 层整体 + 10 层 vLLM attention/FFN 混合路径。
   - AgentX TP4、并发 1、3600s、Rust 前端：P90 interactivity 541.6→562.6 tokens/s/user（+3.9%），P50 +4.5%，ITL p50 1.760→1.680 ms；GPQA-Diamond、AIME25、RULER NIAH 准确率不变。
   - 影响：ROCm 上 DeepSeek-V4.1 解码路径进一步整层融合，提升交互性能且不损精度。

3. **[ROCm][Perf] 2×4 XGMI-island 节点上的 TP8 Island all-reduce — PR #61109**
   - 作者：`omar-bahaa`。

### 💬 高热度讨论分析
1. **#61126 [Attention] Remove cascade attention（评论最多）**
   - 核心议题：是否彻底移除 cascade attention。作者 `WoosukKwon` 主张移除，理由是默认关闭、FlashInfer 已硬禁用、async spec decode/DBO/CPU 等强制关闭、多数后端不支持，且仍带来每步 scheduler 扫描、分支和反复 bug；PR 净减少约 901 行。
   - 支持/反对观点：
     - `WoosukKwon`：移除不意味着移除 prefix caching；prefill 计算密集，共享 HBM 带宽收益不大；仅 FA4 对 GQA 支持 cascade；MRV2 本来不支持。
     - `noooop`：JEV 场景常见共享 prompt 模板，cascade attention 理论上可加速同 batch 共享前缀；并引用 FlashInfer multi-item scoring/cascade 相关 PR。
   - 争议焦点：prefill 阶段 cascade 是否真能带来收益；JEV 等共享模板场景是否应保留该优化。
   - 状态：Open，CI 已触发；插件 API 暂时保留为 deprecated no-op，后续再移除。

2. **#61083 [Core] Add sparse_disk weight transfer backend（评论 5 条）**
   - 核心议题：新增 `sparse_disk` 权重传输后端，通过共享存储上的 safetensors 文件传递稀疏 patch，无需 trainer 与推理 worker 之间的 NCCL 组，也无需 trainer GPU。
   - 观点：
     - 作者 `AravindKurapati`：展示 CPU 测试和 L4 GPU 端到端，支持 `SparseWeightPatch` API，worker 拒绝非 patch 文件。
     - `aoshen02`：要求更大模型和更多并行验证。
     - 作者补充：Qwen3-4B TP2、Llama-3.1-8B TP4，权重差异 0，greedy 8/8；但 Llama 在 `gpu-memory-utilization 0.85` 下 OOM，0.6 可通过。
   - 争议/关注：内存放大问题，sparse loader 会为每个权重创建全尺寸张量。
   - 状态：Open。

3. **#61120 [Bugfix] V1 spec decode 下 `thinking_token_budget` 重复 `</think>`（评论 3 条）**
   - 核心议题：MRV1 投机解码与 `thinking_token_budget` 同窗口自然结束时，会强制生成第二个 `</think>`。
   - 观点：
     - 作者 `brave30`：修复后与无 spec 输出 token 级一致；MRV2 不受影响。
     - `SeverinVisionary`：复现验证，固定 budget 下重复从 8/200 降至 0/200，动态 budget 下从 92/131 降至 0/131；提出多 token 结束序列跨 boundary 的问题。
     - `brave30`：straddling force point 在非 spec 下也存在，建议另开 issue；committed output 情况已在 `c5fe233` 修复。
   - 状态：Open，讨论质量较高，已发现边缘场景。

4. **#61079 [Bugfix][GLM-5.3-Flash] 恢复 MTP index sharing（评论 4 条）**

5. **#61072 [Spec Decode][DFlash2] 27B 公开 draft 配对全部净回归（评论 2 条）**

### 🛠️ 重点技术变更
1. **#61126 移除 cascade attention**
   - 技术点：删除 cascade attention 的 kernel、启发式、metadata、scheduler/KV-cache plumbing、model runner 逻辑、配置、测试和文档；插件 API 暂时保留为 deprecated no-op。
   - 影响：默认配置无行为变化，净减少约 901 行；消除每步 scheduler 扫描和多个后端分支，使多个历史 bug 变为 moot。但 JEV/共享前缀场景是否损失潜在优化仍有争议。

2. **#61149 升级 DeepGEMM 并适配 sparse indexer**
   - 技术点：将 vendored DeepGEMM pin 升级到 `1448881`，包含 26/09/30 公共 release 和 vendoring import 修复；适配 breaking MQA-logits API。
   - 影响：DeepSeek-V3.2、GLM-5.x、GLM-5.3、DeepSeek-V4/V4.1、HY-V4 的 DSA sparse indexer 在 SM90/SM100/SM120 保持工作；SM100 FP8 indexer cache 数值一致，改为 packed UE8M0 MXFP8 编码。标签含 ROCm，但 AMD 实测未展示。

3. **#61120 修复 V1 投机解码 `thinking_token_budget` 重复结束标签**
   - 技术点：在 budget 用尽的强制步骤中，若 accepted drafts 已包含自然结束序列，则跳过强制 `</think>`；后续 `c5fe233` 进一步处理结束序列已出现在 committed output 中的情况。
   - 影响：使 MRV1 + spec decode + thinking budget 输出与无 spec 解码 token 级一致，修复真实 agent 场景中的重复结束标签。

4. **#61056 NIXL host-buffer KV block 批量拷贝**
   - 技术点：在 CUDA 上 pin host transfer buffer，并用一次 `ops.swap_blocks_batch` 拷贝所有 `(layer, block)`；失败时回退 pageable memory。
   - 影响：host-buffer D2H/H2D 拷贝从 1.2–2.4 GB/s 提升到 8.7–16.3 GB/s；P/D `max_tokens=1` 请求延迟降低 1.7–3.6×，例如 7000-token prompt 从 1222.5 ms 降至 340.1 ms。

5. **#61144 MI300X MoRIIO READ over XGMI 崩溃**
   - 技术点：MI300X SR-IOV VF + XGMI + `MoRIIOConnector` READ 模式下，decode 首次请求触发 GPU memory access fault；WRITE 模式正常，MI355X 裸金属正常。
   - 影响：直接威胁 MI300X 虚拟化集群中 MoRIIO P/D 部署的可用性，是 AMD 平台当前最值得优先定位的 Issue 之一。
