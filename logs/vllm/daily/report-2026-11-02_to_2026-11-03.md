### 💬 高热度讨论分析

#### 1. #65190 — Muse Spark 长上下文"卡死"：从误诊到纠正（7 条评论，已关闭）

**核心议题**：用户 sawsa307 报告在 4×MI350X 上用 `SimpleCPUOffloadConnector` + DSpark 投机解码时，c40 并发下引擎吞吐归零（`Running:1, Waiting:39`），并怀疑是 KV 卸载与投机回滚导致的竞态。

**讨论演进**：
- **用户侧**：通过多轮 bisect 将触发条件收窄为"DSpark 多 token draft（n=7）+ 活跃 offload 同时存在"，并观察到 `invalid token id` 与 3.6x 预填充重算。
- **AMD 侧（hongxiayang）**：完整复现后给出相反结论——**不是死锁，是容量不足**。默认 8 GiB CPU tier 装不下工作集，每个后续轮次都重新预填充，30 分钟窗口内表现为"卡死"；将 `cpu_bytes_to_use` 调至 256 GiB/rank 后工作负载干净通过，~91% prompt token 命中缓存层。同时指出报告者使用的 nightly 缺少 #65125 修复，DSpark draft 本身无法加载。
- **结论**：报告者接受纠正并关闭，承认 "3.6x 重算" 实为 re-prefill churn，pending-store 冻结是 gauge 语义问题。仍保留一个未复现的 `invalid token id` 疑点待单独跟踪。

**意义**：这是一次高质量的"用户误诊 → 维护者复现纠正"闭环，也暴露了 offload 容量默认值在长上下文 agentic 负载下偏保守。

#### 2. #65204 — 扩展式 KV 缓存与卸载连接器启动失败（3 条评论，已由 #65225 修复合并）

**核心议题**：`--kv-offloading-size` 在启用 KV connector 后触发 granule 对齐，把 block 数向下取整到 0（stride 5,657,600 B → 2048 block 粒度，而显存只够 1375 块），导致启动即报错。

**观点/协作焦点**：
- luyixiao95 先表示认领，Vegetog 随后说明已开 draft PR #65210，双方友好协调由 Vegetog 继续。
- 最终 njhill 的 #65225 以"填充 segment 布局"替代"对 block 数取整"，且仅对注册 RDMA 的 connector 生效，`--kv-offloading-size` 保持实测块数。GB200 验证：`gpu_memory_utilization=0.014` 从启动失败变为 102 块正常运行。

#### 3. #65193 — MXFP8 线性核选择忽略激活方案（2 条评论，仍开放）

**核心议题**：`init_mxfp8_linear_kernel` 未接收 `activation_quant_key`，导致 Blackwell 上 weight-only（W8A16）MXFP8 检查点被静默路由到 W8A8 FlashInfer 内核，激活被量化到 FP8 而无任何警告。

**观点交锋**：kavyansh-1 提出完整修复方案（线程化 key + `_supports_quant_scheme` gate + 复用 #59460 的 `executed_activation_key()` hook）；selimfedakar 回复称自己提交 issue 时已同步完成实现，将自行开 PR，并欢迎对方 review。两人对技术方案完全一致，仅存在认领重叠，属于良性协作。对应修复 PR #65288 已提交。

#### 4. #60102 — gfx942 稀疏 MLA 预填充路由（8 条评论，已合并）

**核心议题**：把 gfx942 上 ≥512 query 行的稀疏 MLA 预填充路由到 AITER `pa_prefill_sparse`。

**多方验证与争议**：
- **jin-amd** A/B 测试发现严重回归：GLM-5.3-Flash 的 decode 行也被送进该路径，而 `pa_prefill_sparse` 无 split-K，2/16 行调用慢约 9×（32µs→293µs），端到端 TTFT 恶化 8.8%–18.3%。建议加 gate。
- **phambinhfin** 进一步测试指出：大数据量下 AITER 仍显著更快（534 行 0.626ms→0.310ms），反对对所有纯 decode 强制走 `decode_bf16`，主张保留路由并单独改进 decode split 启发式。
- **结论**：作者加 512 行 gate，MI325X 上 TTFT −9.5%~−15.9%、输出吞吐 +5.5%~+26.7%，多轮复测后合并。

#### 5. #63076 — MoE 路由 top-k Triton 化（9 条评论，已合并）

**核心议题**：当分组无法淘汰专家时，用寄存器常驻的 Triton sigmoid+bias top-k 替换 AITER `biased_grouped_topk`。

**讨论深度**：
- simondanielsson 要求先确认能否从 router 选择层消除 grouped op，作者调查后说明会改变 `routing_method` 元数据（DeepSeekV3→MiniMax2），影响 AITER mxfp4 内核的 `renormalize` 判定，因此改为在调用点替换。
- 过程中发现真实 bug：V2 runner 下 FULL CUDA graph 的 `cudagraph_runtime_mode` 为 `NONE`，导致替换从未生效；改用 `torch.cuda.is_current_stream_capturing()` 后修复。
- 最终按 reviewer 建议将 `_MAX_TOKENS` 限制为 1，把影响面收敛到单请求 decode，五模型 sweep 显示 0.4%–4.2% 提升。

### 🛠️ 重点技术变更

**1. #65225 — 扩展式 KV 缓存改为填充 segment 而非取整 block 数（已合并）**
修复 #65204 的启动失败。核心设计：仅对 `registers_kv_cache_memory()` 返回真的 connector（NIXL/Mooncake/MoRIIO/UMBP）做 segment 填充与 defragmenting commit，其余（含 `--kv-offloading-size`）保留实测块数。同时把 `UMBPStoreConnector` 纳入注册表，在 ROCm 上对 MoRIIO/UMBP 关闭 extensible cache。这是对 #56492 引入的回归的系统性收口。

**2. #60102 — gfx942 稀疏 MLA 预填充路由（已合并）**
在 gfx950 OPUS 路径之外新增 gfx942 的 `pa_prefill_sparse` 分支，门控为 `q.shape[0] >= 512` 且 dtype 匹配。关键工程价值在于社区通过多轮 A/B 发现了"decode 误入预填充内核"的回归，并推动引入行数阈值——这是一个典型的"性能补丁需要 workload-aware gate"的案例。

**3. #63076 — 分组无法淘汰专家时的 Triton top-k（已合并）**
在 `rocm_aiter_ops.biased_grouped_topk` 单一调用点做替换，覆盖 `GroupedTopKRouter` 与 `FusedTopKBiasRouter` 两条路径。修复了 V2 runner 下 CUDA graph 检测的 bug，并将范围收敛到单 token 批次。展示了在替换厂商内核时，元数据（routing method）与内核实现的强耦合风险。

**4. #64692 — 权重重载时原地回填派生张量（已合并）**
直接重载（direct reload）场景下，post-load 处理会重建 kernel 常量、逆缩放、decode 副本等派生张量，导致已捕获 CUDA graph 读到失效地址。本 PR 保证这些张量在重载后保持启动地址。覆盖 TRT-LLM MXFP4/NVFP4、CuteDSL、FlashInfer CUTLASS、ROCm gpt-oss AITER shuffle、Kimi-K3 AMD `_w_fold`、bf16x3 router split 等众多后端，是权重热更新能力的基石性修复。

**5. #65146 — DeepSeek-V4.1 MI355X 融合 mega-attention 预填充（开放）**
单 kernel 完成反量化、稀疏注意力（因果 top-k + SWA）、逆 RoPE、MXFP8 输出转换，移除独立的 dequantize/gather/sparse_fwd 三步及其 bf16 gather workspace。保守的 `is_available_for` 自动选择保证不影响其他配置。目前因 merge conflict 需 rebase。

### 💡 值得关注的问题

1. **#65106 / #65105（josh-schell-amd，开放）**：Kimi-K3 + DBO 在 8×MI355X 上 100% 复现的启动 OOM 与 workspace 锁定失败。前者需要 DBO 预热按 DP 聚合后的微批大小预留，后者需要重新审视 `max_num_seqs × max_model_len` 的 `paged_kv_indices` 分配策略。二者均阻塞 Kimi-K3 在 MI355X 上的默认配置可用性，优先级高。

2. **#65193 / #65288（开放）**：MXFP8 激活方案被忽略导致 W8A16 检查点静默降级为 W8A8。修复 PR 已提交但**尚未在真实 Blackwell 硬件上验证**（仅用模拟 SM100 能力），正式合并前需补硬件 E2E 与精度评估。

3. **#65190 遗留的 `invalid token id`**：虽然主因是容量误判，报告者仍观察到一次 `94008244196736`（0x558000005580，两个非法 token 拼接）的异常读回，怀疑与 #47282 的 load-path 跨流 WAR 相关。该问题未复现，建议保持关注。

4. **#65151（开放）**：WSL2 + gfx1151 的 HIP host wait 策略配置入口。涉及是否在 vLLM 层面暴露 ROCr/HIP 运行时调优面，需权衡"文档化 recipe"与"新增配置项"两条路径，且不应改变所有 AMD GPU 的默认行为。

5. **量化配置空间的收敛需求**：从 #54206、#65177、#65193 可见，`per_act_token_quant` / `per_out_ch_quant` 等自定义 flag 与 `QuantKey` 体系的并存仍在制造 bug（#61024 已提出后续迁移）。建议社区优先推进 `FusedMoEQuantConfig` 向 `QuantKey` 的统一。

6. **extensible KV cache 的稳定性**：#65204/#65225 之后，建议回归测试覆盖更多 block stride 与 connector 组合，尤其是 ROCm 上 MoRIIO/UMBP 被显式关闭 extensible cache 后的行为差异。
