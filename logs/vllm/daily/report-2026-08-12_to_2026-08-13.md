   为本周期最重要的 AMD 生态新增功能。面向 gfx950/MI355X 的 DeepSeek V4 MoE 层提供可选 FlyDSL 融合后端：将 EP dispatch → expert GEMM1 → activation → expert GEMM2 → EP combine 的多次 launch 链路融合为单次 `MegaMoEV2` 调用，使 dispatched tokens 保持驻留并合两次 GEMM 与 combine 为一次 launch。设计上默认关闭（`--moe-backend flydsl_mega_moe --enable-expert-parallel`），未选中时走原路径；要求 EP + fp4 experts + TP=1，否则抛 `NotImplementedError`（TP>1 时 shared expert 的 all-reduce 所有权不在 mega path 中，拒绝配置优于静默错误）。权重路径独立注册（`make_deepseek_v4_mega_expert_params_mapping`），并兼容 MTP/DSpark 两种推测解码路径，非 ROCm build 零 import 开销。

2. **PR #52056 — [Build][AMD] Update triton_kernels pin for RDNA MXFP4 matmul_ogs config**（`umarkovi-amd`）

### 🛠️ 重点技术变更

**1. PR #47808 — [Spec Decode] DSpark confidence-scheduled verification（已合并）**
该 PR 将 DSpark 的验证预算从固定 k 变为自适应：Triton kernel 按 draft 位置置信度（cumprod）排序并选取最大化"每毫秒接受 token 数"的前缀；batch 级预算由 CPU 基于双缓冲的 stale confidence 计算（无 sync），per-request 分配在 GPU 上用活值完成；EMA 平滑（alpha=0.8）。实测 c=256 时固定 7-token 验证比 no-spec 低 33%，而自适应方案保持 spec-decode 优势。这是推测解码调度从 "heuristic" 走向 "cost model" 的重要一步。

**2. PR #51918 — [ROCm][DSv4] FlyDSL fused mega-MoE backend**
对 ROCm 上 DeepSeek-V4 的 MoE 计算路径进行了重构级优化。融合后不仅减少了 launch 开销，还为 fp4 experts 的权重布局单独注册了 mapping 和 post-load shuffle（`shuffle_weight_a16w4`）。明确拒绝 TP>1 的设计体现了对正确性边界的严谨把握。该后端为 gfx950 上的 DSv4 部署提供了显著的性能提升空间。

**3. PR #52041 — [Core] Skip broadcasting mm tensor data to workers for prefix-cache-covered items**
针对多模态 prefix caching 命中时仍广播大张量的浪费，通过 placeholder span 是否完全落在 prefix-cache 覆盖区内判断"该 item 的 tensor 永远不会被消费"，从而跳过 EngineCore→TP-worker 序列化与共享内存广播。实测 26 张图时 TTFT 从 573ms 降至 124ms，per-image 斜率从 ~21ms 降至 ~2.9ms；重复图对照实验证明 per-unique-tensor 开销被完全消除。对视频/agent 类滚动视觉上下文场景影响重大。

**4. PR #50654 — [ROCm][Perf] Kimi-K3 Fused kernel for KDA decode**
KDA 三阶段（conv1d + delta-rule + gated RMSNorm）融合为单 HIP kernel 是 ROCm 上"融合 kernel 路线"的又一里程碑。表格数据显示 kernel 级最高 2.31× 加速，e2e 吞吐提升约 7%。gfx950 先行、后续架构逐步放开的策略也符合 ROCm 平台碎片化的现实。

**5. 合并的 PR #51464 + #51860 — ROCm Triton/MLA 基础路径修复**
两个合并在同一时段落地，前者修复 gluon MLA kernel 的编译问题（使 K3 可用），后者修复 fp8 KV cache + DSpark 场景下 TRITON_MLA 的 fp8 query 断言（使 K3 + DSpark + fp8 可用）。两者叠加后，ROCm 上 Kimi-K3 的最优配置（gluon + DSpark + fp8）首次成为开箱即用的完整方案，GSM8K 94.4%、acceptance 3.40。

### 💡 值得关注的问题

1. **Rust 前端 chat template 无评估预算限制（Issue #52025）**：116 字节请求体可占用 worker 55 秒，且 `--trust-request-chat-template=false` 在 Rust 前端是硬错误无法关闭，构成远程未认证 DoS 风险。社区需尽快引入模板渲染 fuel limit 或超时机制。

2. **hipgraphs dual-stream decode 的最终修复（PR #52024 / #52033）**：当前 revert 与修复版并存，需审阅者明确方向。race condition 的根因（shared hidden state 被 routed experts 修改）对其他 hybrid 模型也有警示意义。

3. **RDNA（gfx1201）平台 kernel 兼容性**：GPTQ qzeros 布局、FP8 KV cache 支持、3D split-KV gate 等问题叠加，使 RDNA 仍是 ROCm 支持中最薄弱的一环。随着 Radeon R9700 等新卡进入市场，该平台亟需更多针对性的 kernel 适配与 CI 覆盖。

4. **gpt-oss-120b MXFP4 + expert-parallel 无法启动（Issue #52051）**：modular MoE finalize 在 hidden_size 非 256 倍数时分配 padded buffer 导致 shape mismatch。这是 MXFP4/EP 组合路径中尚未覆盖的边界条件，会影响 Blackwell 集群上的 gpt-oss 部署。

5. **mnnvl allreduce workspace 在非 fabric 多节点上 30s 超时并伴随 GPU 内存泄漏（Issue #51986）**：auto backend 默认选择 mnnvl 后，IB-only 拓扑对 workspace 初始化的预检查缺失，导致启动慢且疑似 OOM。需要 topology-aware 的 backend 选择或优雅回退。

6. **DeepSeek-V4-Flash + DSpark 在 H100 上 CUDA_ERROR_ILLEGAL_ADDRESS（Issue #52065）**：v0.27.0 回归而 v0.26.0 正常。该问题叠加 #52042 的 benchmark_moe 崩溃，说明 DeepSeek-V4 相关代码路径仍处于快速迭代期，版本间稳定性有待加强。
