### 一、DeepSeek-V4.1-Flash ROCm 性能优化主线（核心贡献者：Fangzhou-Ai）

这是本周期 AMD 生态最重要的工作线索，围绕一个 RFC（#56506）和多个 PR/Issue 形成完整的性能攻坚链条。

**#56506 [RFC]: DeepSeek-V4.1-Flash 在 ROCm 上的性能**（新增 Issue，高热度）
- 在 MI355X（gfx950）、8 卡、TP4、MXFP4 MoE + DSpark MTP 下测量，单流 ITL 25.6ms，但并发从 1 到 32 时 ITL 仅劣化 1.9x 而单卡输出吞吐提升 13 倍，说明**设备远未饱和，存在巨大的每步固定开销**。
- 通过 `--enforce-eager` 捕获的 decode trace 显示：**每层 350 次 kernel 启动中 85% 来自 mHC block**（4×4 矩阵的 Sinkhorn 归一化记账），其中 mHC sinkhorn loop 占 48.6%、mHC pre/post mix + eager RMSNorm 占 36.6%。
- 值得注意的方法论警示：由于 roctracer 的 HSA 队列拦截与 hipGraph 重放死锁，必须使用 `--enforce-eager` 捕获 trace，因此**只有 kernel 启动计数和组成是可信的**，墙钟时间/占用率数据不可直接采信。
- 讨论中 Fangzhou-Ai 持续拆分并认领工作项：**1.1（mHC pre → AITER）已合并为 #56503**；**1.2（融合 mHC post+pre）提交为 #56513**；主动取消认领"融合 all-reduce + mHC post"（1.3），因为两者是替代关系而非叠加，且 AR+post 变体需要贯穿 `DeepseekV4Attention.forward` 的延迟 all-reduce 契约，改动过大。cr-zhao 认领 5.1（gfx950-safe prefill top-k combine）。
- 一个重要量化发现：**该 8 卡节点的两半 GPU 之间在相同工作负载上存在 0.96% 的差异**，导致单方向 A/B 测量把 +2.20% 的收益误读为 +0.32%。修正后的交叉估计为 ITL 降低 1.28%（95% CI [0.07%, 2.48%]）。这直接改变了后续工作项的收益评估尺度——**低于约 3% 的收益在本主机上需要交叉或交错设计，而非顺序 A/B**。

**#56503 [ROCm][DSV4.1][Perf] 使用 AITER mHC 处理 delayed pre block**（已合并）
- 将 V4.1 的 mHC block 从 eager Torch 参考实现迁移到 AITER，修复了"V4 已迁移但 V4.1 从未迁移"的遗漏。
- 报告了非受控 A/B 下的 ITL p50 从 25.58ms → **6.89ms**，但作者严谨地声明**这不是 3.7x 的每 token 加速**——agentic trace 是时间驱动的，更快的运行采样了更长、输入更长的请求段（均值输入 168K→206K tokens）。后续补充说明 MTP 接受长度两边均为 3.52，排除了接受率漂移的混淆因素，ITL 下降可归因于 step time。

**#56513 [ROCm][DSV4.1][Perf] 将 mHC post 步骤折叠进 delayed pre 投影**（新增 PR）
- 在 #56503 基础上，通过 `mhc_fused_post_pre_gemm_sqrsum` 每 seam 减少一次启动，5→4 次。构建在已合并的 #56503 之上，已 rebase 为单 commit。
- 采用"三个可选参数 + 一个分支"而非独立 op stack，代码量从 550 行/6 文件降至 350 行/5 文件。
- GSM8K 验证：baseline 0.9704 → #56503 0.9727 → 本 PR 0.9742（strict-match），三者都在约一个标准误范围内。

### 2. #53781 — HiSparse: host-resident sparse-MLA decode hot-buffering（已合并，8+ 条评论）

**核心议题**：在 GPU KV cache 之下增加 host-resident 层用于稀疏 MLA decode，按需从 pinned host memory 溢出/恢复。

**不同观点与立场**：

**争议焦点**：GLM 系列打包 cache pool 的 NIXL region 几何假设与 HiSparse 的页面粒度不兼容。这是**CI 覆盖不足导致的生产问题**，samsja 的详细报告对 HiSparse 的通用性提出了实际挑战。

## 🔥 热门话题与趋势分析

### 1. DeepSeek-V4.1-Flash 跨平台适配是绝对主线

本周期几乎所有高热度讨论都围绕 DSV4.1-Flash。从平台维度看：
- **AMD/ROCm（MI355X/gfx950）**：性能优化主线，mHC/AITER/MoE/稀疏解码全面开花
- **NVIDIA SM120/SM121（GB10、RTX PRO 6000）**：无法启动，SWA cache block 与 DeepGEMM 几何不匹配
- **NVIDIA SM90（H200）**：DSpark spec decode 崩溃（已有修复 PR #56448）
- **NVIDIA GB200/SM100**：WoosukKwon 主导的 input metadata Triton 融合、foraxe 的 attention output projection 捕获

### 2. mHC（4×4 矩阵 Sinkhorn）成为 AMD 性能分析的核心对象

一个 4×4 矩阵的记账操作贡献了每层 85% 的 kernel 启动和 37.5% 的 kernel 时间，这是本周期最反直觉、最有价值的性能发现。Fangzhou-Ai 的 trace 方法论（`--enforce-eager` 限制、kernel 计数可信而墙钟不可信）和交叉 A/B 设计（GPU 组间 0.96% 差异）为社区提供了可复用的性能工程范式。

### 3. AITER 集成为 ROCm 性能提升的主要途径

本周期 AMD 侧的性能优化几乎全部通过 AITER 实现：mHC 融合、AG/RS、MoE routing、稀疏解码 ASM 内核、FlyDSL MoE。#56433 和 #56502 也显示 AITER 内核选择的优先级列表改动可能引发**跨模型的正确性回归**（DS V3 TP4/TP8、Kimi K2 TP>2），提示 AITER 集成测试的覆盖面需要加强。

### 4. Speculative Decoding（DSpark/MTP/EAGLE）是跨平台热点

- ROCm：MiniMax-M3 自适应 DSpark 验证（#56451）、Kimi-K3 DFlash AttnRes 修复（#56434）
- NVIDIA：PP + MTP 支持（#46994，已合并）、DSpark warmup 崩溃修复（#56448）
- KV Cache：EAGLE SWA replay blocks 保留（#56449）

### 5. 管道并行（PP）与序列并行（SP）的 DeepSeek-V4.1 支持

## 🛠️ 重点技术变更

### 1. #56503 + #56513 — AITER mHC 迁移与融合（已合并 / 新增）

**技术解读**：DeepSeek-V4.1 的 mHC block 在 AMD 上仍运行 eager Torch 参考实现，而 V4 已迁移到 `MHCPreOp`/`MHCPostOp` dispatch 层。核心难点在于 V4.1 的**延迟 pre-mix 语义**——每个 sublayer 用前一个 sublayer 的 pre-mix 折叠输入，并返回当前的供下个 seam 使用，而 AITER 的 `mhc_pre` 既不返回 pre-mix 也不接受传入的 pre-mix。作者通过对比延迟与非延迟公式在相同输入上的输出（`post_mix max_abs_err = 0.000e+00`）证明 stagger 不改变 gate，从而将融合实现为现有 op 的三个可选参数 + 一个分支。

**项目影响**：直接命中 DSV4.1 在 MI355X 上的 decode 性能瓶颈；1.28% ITL 收益看似不大，但在 mHC 占 85% kernel 启动的背景下，为后续所有 seam 级优化树立了模板。

### 2. #56433 — 修复 AITER preshuffled FP8 block-scale 内核（已合并）

**技术解读**：这是一个**静默正确性 bug**——内核被置于优先级首位后，DeepSeek V4/V3/Kimi-K2 等 MLA 模型自动选择它，但存在四个问题：列主序/行主序 scale 混淆（形状恰好相同 `(M, N//32)` 因此无报错）、权重重复 B-preshuffle、`wo_a` BMM 层直接读取权重被破坏、`kv_b_proj` 被 MLA 用于构建 `W_UK/W_UV` 时出错。**TP1/TP2 正常但 TP4/TP8 结果错误**这一点尤其危险，因为现有测试只覆盖了 TP1/DP8。

**项目影响**：DS V4 和 V3 TP8 gsm8k 从 0 恢复至 0.9568/0.9458。提示 AITER 内核优先级列表的改动必须配套多 TP 配置的端到端正确性验证。

### 3. #53781 — HiSparse host-resident sparse-MLA decode hot-buffering（已合并）

**技术解读**：在 GPU KV cache 之下增加 host-resident 层，与非 always-host-resident 设计的不同在于：尽量保留 KV 在设备缓存，仅在需要回收 GPU 容量时溢出到 pinned host memory。核心是一个 fused CUDA resolver，将每个选中的 top-k 位置映射到三个可能位置之一（resident GPU page / 请求的 GPU hot buffer / pinned host pool），resident hits 在 hot-cache lookup 前返回，hot hits 更新 GPU 侧 LRU，misses 通过仅 gather 选中的 host 行来替换 LRU 条目。所有解析、替换、LRU 更新都在 GPU 上且兼容 CUDA graph replay。

**项目影响**：这是稀疏 MLA decode 内存层次结构的重大扩展。samsja 在 GLM-5.2/5.3 P/D 部署上的验证发现 NIXL region 几何在打包 cache pool 上的兼容性问题，提示该功能的通用化仍需更多模型形状的验证。

### 4. #56560 — MXFP8 权重一次反量化（新增 PR，JohnQinAMD）

**技术解读**：`RocmDotScaledMxfp8LinearKernel` 需要 `K % 128 == 0` 才能用 `tl.dot_scaled`。DSV4.1 的 shared expert `down_proj` 是行并行，其 K 被切分：TP1=2304、TP2=1152 都满足，但 **TP4=576（%128=64）、TP8=288（%128=32）不满足**，导致 fallback 到 `dequant_mxfp8_to_bf16` + F.linear。该 dequant 是 6 个 pointwise kernel，FP32 中间量是 FP8 源的 4 倍且两次往返 HBM，2.95MB 权重产生 56MB 流量。修复方式是在 `process_weights_after_loading` 中一次性转换并保持 BF16。

**项目影响**：TP4/TP8 下每 decode token 浪费 2.24 GB HBM 流量来产生 236MB 永不改变的权重。这是一个典型的"配置相关性能悬崖"，直接影响 DSV4.1 在 4 卡/8 卡部署下的经济性。

### 5. #56424 — 匹配稀疏 indexer 调用与注册 schema（新增 PR，khluu）

**技术解读**：#56228 给 `forward_hip` 加了 CUDA candidate-block 参数但未添加 ROCm 实现，导致 `rocm_aiter_sparse_attn_indexer` 收到 18 个参数而 schema 只接受 15 个，MI355 LM Eval Spec Decode 在评估前失败。修复方式是移除这三个参数并显式拒绝非 None candidate blocks，防止不支持的两级选择静默产生未过滤结果。同时扩展 ROCm MLA 注册测试套件，在 FakeTensorMode 下用真实注册 schema 验证 `forward_hip`。

**项目影响**：这是跨平台 API 演进中 ROCm 实现滞后的典型案例，扩展的注册测试套件可以防止类似 caller/schema 回归。

## 💡 值得关注的问题

### 1. DSV4.1-Flash DBO 全模型路径的 runtime NaN 未解决

#56440（0z5a）明确报告"DBO 全模型诊断 6/6 QA，5/8 continuation 完成，3/8 HTTP 400 伴随 runtime NaN"，并公开招募有 GPU 资源的贡献者协助修复。**这是 DSV4.1 在 disaggregated batch overlap 场景下的关键阻塞项**。

| 平台 | 状态 | 关键 Issue/PR |
|---|---|---|
| AMD MI355X (gfx950) | 性能优化中，正确性修复密集 | #56506、#56503、#56513 |

### 3. ROCm 7.2.x 的 ROCr 堆溢出

#56521（JohnQinAMD）指出 `ROCPROFILER_QUEUE_INTERPOSITION=0` 在 `docker/Dockerfile.rocm_base` 中强制启用了含未修复堆溢出的 legacy 路径。这是一个**上游 ROCm 问题**，需要在 ROCm 侧修复或调整 Dockerfile 默认值。

### 4. GLUON 日志刷屏对推理性能的实际影响

#56540 报告单个 job 出现 56,264 次 `GLUON backend not available` 警告。#56543 的 workaround 是显式指定 Triton backend，但根本修复在 AITER #5471。**这个问题虽然不导致功能失败，但大量日志 I/O 本身可能影响推理延迟**，特别是在高并发场景下。

### 5. AITER 内核优先级列表的正确性验证缺口

#56433 揭示的模式值得警惕：**一个被置于优先级列表首位的 kernel 可以在 TP1/TP2 正常工作但在 TP4/TP8 静默产生错误结果**，而现有 CI 只覆盖 TP1/DP8。建议在 AITER 内核集成时增加多 TP 配置的端到端正确性门禁。

### 6. HiSparse 在 GLM 系列上的 P/D 部署兼容性

samsja 的详细报告（NIXL region 几何崩溃 + 两个 workaround + 一个未解决正确性问题）表明 **HiSparse 的 CI 覆盖未包含 GLM 系列的打包 cache pool 形状**。虽然 #53781 已合并，但生产部署的通用性仍需验证。

### 7. 性能测量方法论引发讨论

Fangzhou-Ai 在 #56506 和 #56503 中反复强调：GPU 节点两半之间存在 0.96% 的固有差异，**低于约 3% 的收益在本主机上必须用交叉或交错设计测量**，顺序 A/B 会导致错误结论（+2.20% 被误读为 +0.32%）。这对社区的性能 PR 评估标准提出了重要方法论建议，可能值得形成文档规范。

### 8. breakable cudagraph 捕获期间的多流重叠行为待澄清

Fangzhou-Ai 在 #56506 中提出的三个问题之一——"breakable-cudagraph 捕获期间串行化多流重叠是否有意为之"——尚无维护者回应。这关系到 ROCm 上 CUDA graph 与多流执行的交互策略，可能影响后续所有 graph 相关性能优化。
