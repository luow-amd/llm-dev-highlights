#### 1. 新增/未关闭 Issue — ROCm 平台稳定性问题集中

- **[#54831] KV offloading 无法用于 GLM-5.3（DSA indexer）**  
  报障环境：MI350X（gfx950）、ROCm 7.2.3。GLM-5.3-Flash 的 sparse-MLA indexer `tail_cache` 的 `block_size=4` 不满足 prefix-hash 对齐断言，`--mamba-cache-mode align` 也无法触及该 KV 组。用户在跟进评论中进一步验证了 LMCache 0.5.4 独立栈同样撞墙，且暴露出 `get_kv_cache_layout` API 移除等上游兼容问题。该 Issue 反映**混合线性注意力模型在 KV offload 场景下暴露的块对齐与缓存布局设计缺口**。

- **[#54761] ROCm 上 DCP 和“非 FP8 KV dtype”路径不可达，但错误提示指向不存在的修复**  
  这是对 ROCm 平台可用性较尖锐的批评：DCP 要求 attention 后端在 decode 阶段返回 softmax LSE，但统计显示 ROCm/AITER 的 3 个 MLA 后端均无 LSE 支持，而 CUDA-only 后端才有。ROCm 上该模型只有一个可用后端 `ROCM_AITER_MLA_SPARSE`，错误信息却建议用户“切换 backends”，实际无路可退。

- **[#54775] KDA/gated-delta-rule chunked-scan 临时缓冲区在 memory profiling 之外**  
  在 GLM-5.3-Flash（34 层 KDA + 11 层 sparse MLA）、MI350X、`--gpu-memory-utilization 0.93` 下，81,920 max-num-batched-tokens 时 16 个并发请求中有 11 个触发运行时 OOM，且导致引擎整体 shutdown。启动阶段 memory profiling 未计入该线性扩张的中间缓冲区，导致 KV cache 配额偏大。

- **[#54732] AITER topK metadata buffer 忽略 `pcp_size`，PCP 启动即失败**  
  在 `--prefill-context-parallel-size > 1` 且使用 fused shared experts 时，AITER topK 元数据缓冲按 `max_num_batched_tokens * dp_size` 初始化，未乘 `pcp_size`，导致 warmup 时断言失败。用户已给出最小修复：`max_num_batched_tokens * dp_size * pcp_size`。

- **[#54728] Feature Request：为 gfx1030（RDNA2）加入 Dockerfile 架构与 gate**  
  社区希望在官方 ROCm 镜像中纳入 gfx1030，并需要有 properly gate 的 RDNA2 HIP 内核。

#### 2. ROCm 相关新增 PR — 性能优化与 bugfix 并行

- **[#54805] 回退 AITER PA gluon decode 路径（ROCM_AITER_FA）**  
  因 gluon decode kernel 要求 batch 内 query length 统一，而 speculative draft truncated 时 scheduler 会产出 ragged batch，导致 MiniMax-M3 + EAGLE3 + shuffle KV layout 崩溃。该 PR 暂时回退 pa gluon 相关改动、保留 shuffle layout 修复，等待 AITER 上游内核支持 per-row query lengths。这是典型的“先恢复可用性，再等上游补洞”策略。

- **[#54845] gfx950 低 M 值 FP32 Router GEMM（Triton in-tree）**  
  针对 MoE router 在 M=1~32 的启动瓶颈，新增 Triton GEMM 快速路径。M=4/16/24 时相对 `F.linear` 延迟降低约 50%；MiniMax-M3 TP4 端到端吞吐提升 3%~8%。

- **[#54855] 将 DSV4 大 sparse prefill 路由到 AITER OPUS kernel**  
  面向 gfx950，把 DeepSeek V4 大规模 sparse-MLA prefill 导向 AITER `pa_sparse_prefill_opus`，8k/1k、48 并发下端到端吞吐提升约 4.96%。

- **[#54857] 融合 MLA dual RMSNorm + FP8 组量化（DeepSeek R1 ROCm 路径）**  
  将 R1 每层两个 kernel（q latent 的 RMSNorm+FP8 quant 与 kv latent 的 RMSNorm）合并为单个 AITER HIP kernel `fused_qk_rmsnorm_group_quant`。decode 场景每层耗时由约 8µs 降到 4.8µs。

- **[#54787] Fused allreduce + GemmaRMSNorm 快速路径（ROCm）**  
  在 ROCm 上为 MiniMax-M3 添加类似 FlashInfer 的融合 allreduce + RMSNorm 路径，避免每层两次 kernel launch。

- **[#54776] APU 统一内存记账修复（ROCm）**  
  修复 AMD APU（Strix Halo/gfx1151）在 GTT 与系统内存压力下的 free-memory 计算：`min(hip_free_memory, psutil.virtual_memory().available)`，避免负值 accounting 与错误的内存压力判断。

- **[#54820] DeepSeek-V4 DSpark：去除 ROCm 端冗余占位共享词表分配**  
  将 draft-side 的 `embed_tokens`/`lm_head` placeholder 延迟到目标模型 aliasing 后创建，减少 Strix Halo TP=2 启动时约 1.73 GiB/rank 的瞬时内存开销。

- **[#54706] RDNA3 W4A16 split-K 非确定性修复**  
  修复 gfx11 上 scalar/WMMA split-K 使用低精度 CAS 累加导致的不同顺序不同结果问题。改为“FP32 per-split 固定顺序归约 + 最后一次 cast 输出”，官方数值 M=1 最大误差从约 0.028 降至 0.0061。

- **[#54770] Quark per-block FP8 scales 注册修复（DeepSeek/ROCm）**  
  将 Quark 导出的 per-block FP8 线性 scale 注册为 `weight_scale`，与 Quark 实际格式一致；同时删除 DSV4 AMD mapper 里错误的 `weight_scale -> weight_scale_inv` 重写。属于量化兼容性层面的根治式修复。

- **[#54702] Quark：identity `packed_modules_mapping` 需遵循 `layer_quant_config`**  
  修复 Quark 配置中某模块被映射到自身时静默丢失 layer 级量化配置的问题，避免混合精度 checkpoint 加载时才 shape mismatch。

### 💬 高热度讨论分析

整体上，本 24 小时窗口内多数新增 PR 仍处于早期 review 阶段，评论不算密集。高价值讨论主要来自几条长期跟踪链与技术 RFC。以下选取含金量较高、多方参与或横跨多个开发阶段的讨论。

#### 1. Issue #46856 —— ROCm/GLM-5.1 长上下文损坏问题：从“临时缓解”到根因修复

这是本窗口关闭的长线热门 issue，最早于 2026-06-26 报出：GLM-5.1-FP8 在 `ROCM_AITER_MLA_SPARSE` 后端、gfx942/MI300X 上，ISL 76K~137K 时产生确定性/非确定性混杂的损坏输出（coherent 约 66%、corrupt 约 19%、empty 约 15%）。

各方观点与推进：

- **报障者 @psakhamo**：通过大量对照实验确认 corruption 并非 CUDA graph 引入，eager/compile 均存在；将 KV cache 从 fp8 改为 bf16 可把损坏率降到约 19%，说明与量化 KV 精度相关。
- **@Rohan138**：指出与 #47042 高度相关，并给出临时修复 #47567（禁用 persistent kernel）。
- **@maeehart**：从更底层定位到“sparse-MLA persistent-metadata cache-key collision”，即 persistent metadata 的缓存键未区分每请求 context/query length。PR #47766 保留 persistent kernel 并从源头修复。
- **@Alexei-V-Ivanov-AMD**：补充 AMD 侧验证：如果测试协议配合 `--reasoning-parser glm45`，部分被判定为“corrupt”的输出实际是 reasoning/scratchpad 提取方式造成的歧义；但 needle-in-a-haystack 在 NVIDIA B300 上也会失败，说明评测方法本身存在跨平台陷阱。

**最终结论**：Issue 于 9 月 1 日关闭。根因修复 #47766 可在 137K context 下恢复 10/10 检索准确率，AMD/社区开发者同时提醒“评测 pipeline 与 reasoning parser 配置也会显著影响 corruption 判定”。

#### 2. Issue #54766 + PR #54768 —— XPU 2-rank custom all-reduce

讨论核心：Intel Arc Pro B70 上 TP=2 只能达到单卡 61.4% 吞吐的问题。作者 @recutita 将瓶颈归因于 oneCCL 每次 collective 固定 85~91 次 Level Zero API 调用，且 host 侧同步阻塞；decode 每 token 需要 129 次 collective。

讨论中的主要视角：

- **@recutita（提案方）**：认为开销是“每次调用”而非“每字节”。提出用 Level Zero IPC + kernel 内 rank handshake，绕开 oneCCL；按消息大小分三档：≤128KiB 走 device-sync kernel、128KiB~1MiB 走 copy-engine、>1MiB 走 oneCCL。默认关闭，任何失败都可降级。
- **@xinyu-intel（Intel 维护视角）**：方向认可（“following CUDA 是 correct direction”），但要求先看 code，并希望明确何时用 custom kernel、何时保留 oneCCL；同时询问实际拓扑（PCIe switch / root complex / UPI），并提出是否可先尝试 full decode XPU graph。
- **@recutita 的回复**：给出了具体拓扑：单 AMD socket、两块卡分别挂在 root complex 不同 root port 下的独立 switch；并提供了 threshold 微基准。同时指出 `current_link_width` 在 sysfs 中是 x1 Gen1 误报，不能作为调优依据。

**争议焦点**：custom kernel 与 oneCCL 的使用边界、XPU graph 是否是更优先的解法、以及该优化能否推广到更大 scale。

#### 3. Issue #54744 + PR #54825 —— GLM-5.3 关闭思考后仍泄漏到 content

这组 issue/PR 展示了一条非常典型的“parser 与 chat template 不一致”链路：

- 客户端发送 `chat_template_kwargs: {"enable_thinking": false}`，这是 GLM-4.5/4.6 的官方关思考方式；
- GLM-5.3 的 template 实际**不读取该参数**，模型照样生成思考过程；
- 但 reasoning parser 读到 `enable_thinking=false` 后关闭 reasoning extraction；
- 结果 raw scratchpad 和 `` 残片直接进入 `message.content`。

讨论中的技术路线收敛：

- **@he-yufeng** 认领修复：不能简单忽略 kwargs，因为 GLM-4.5/4.6 确实需要禁用 extraction；也不能在 streaming 路径做无脑 buffering，否则会伤害真正关闭思考的模型。最终修复（#54825）是“输出驱动”：关闭 extraction 后若检测到 dangling think end tag，就按 thinking-armed config 切分；无 tag 时则原样通过。非 streaming 的泄漏被闭合，streaming 路径的局限在 PR 描述中明确说明。

#### 4. Issue #54785 —— XPU graph + MTP k=4 的确定性崩溃边界

虽然该 thread 主要是 @MikkoP88 的深度调试记录，但其价值极高，值得作为高热度内容：

- 现象高度反直觉：MTP `num_speculative_tokens=4` 时 logits 不稳定、top-1 变化可达 1.5 nats；`k<=3` 则 bit-stable。
- 作者通过大量 boot/arm 实验将范围收窄：capture 是必要条件、padding 不是触发因素、bs 回退干净、字节级可复现；
- 最新 addendum 进一步发现：**短 prompt 触发损坏，长 context 干净**，且可排除 triton multi-query verify kernel、CPU scalar sync、compilation 等嫌疑。

这里的“讨论”并非多方角力，而是一份高质量的第一现场 Problem Report，对后续 XPU 图模式与 MTP 组合的 debug 有重要参考价值。

### 🔥 热门话题与趋势分析

#### 1. DSA/MLA/混合注意力模型成为前端复杂性主要来源

GLM-5.1/5.2/5.3、DeepSeek-V3.2/V4、MiniMax-M3、Qwen4Exp 等模型大幅提升了 vLLM 对“稀疏 + 线性注意力 + 多头潜在注意力”混合架构的适配难度。本窗口内大量工作围绕：

- KV cache 分组与 block-size 对齐（#54831、#54743、#54756）；
- indexer / sparse-MLA metadata 的 correctness（#46856、#47766、#54761）；
- KDA/gated-delta-rule chunked scan 与 Mamba cache mode（#54775）。

#### 2. KV offload / KV connector 生态进入“混合模型深水区”

Mooncake、LMCache、SimpleCPU、OffloadingConnector 等 KV 分发/卸载方案均开始覆盖 DSA/MLA/Mamba 混合模型，但随之而来的是：

- 不同 KV cache group 的 block size 与 hash granularity 冲突；
- prefix-cacheable 与非 prefix-cacheable group 的边界；
- DCP 下的跨 rank 数据传输。

#### 3. QuantKey 驱动的量化重构成为新主旋律

ModelOpt six-in-one LinearMethod redesign（#49381）与 Quark 的 QuantKey 改造（#52958）显示：vLLM 正在把量化方法从“每格式一个类”收敛成“由 QuantSpec 驱动的通用方法 + 可插拔 scheme”。后续碎片化回归修复（#54770、#54824、#54573）也说明该重构仍需时间稳定。

#### 4. Speculative decoding 继续向“图捕获安全 + 多级 MTP/DP”推进

- #54790：sparse MLA 后端在 DCP 下启用 fused draft metadata，默认关闭；
- #54716：修复 M-RoPE 模型上 draft token 槽位使用绝对位置而非时序坐标的错误；
- #54798：新增 MR V2 DP+EP idle rank 的 target execution contract。

#### 5. Rust 前端开始深水区补账

#54884、#54883 将 token-attributed text 引入 reasoning/unified parser，下一步即可正确上报 `reasoning_tokens`。这是 Rust 前端从“跑通请求”走向“usage accounting 精确”的重要铺垫。

### 🛠️ 重点技术变更

#### 1. #49381 —— ModelOpt LinearMethod 全面改为 QuantKey 驱动（已合并）

将六个近重复的 ModelOpt LinearMethod 类收敛为一个 generic `ModelOptLinearMethod`。新增量化格式从“派生类”变为“resolve() 数据行 + 复用 scheme”。尽管 MoE 与混合精度保持不动，但这显著降低未来 FP8/NVFP4/MXFP8 格式的维护成本。该 PR 也修正若干“错误假设造成静默垃圾输出”的潜在 bug。

#### 2. #51485 —— Sleep mode 下释放 NCCL communicator 显存（已合并）

通过 `ncclCommSuspend(NCCL_SUSPEND_MEM)` / `ncclCommResume` 在 sleep 时释放约 1GiB/rank（TP4）的 NCCL 动态 GPU buffer，同时保持通信器身份与连接状态。默认 `--enable-nccl-comm-suspend=false`，属于新实验能力的“安全落地”典型做法。

#### 3. #52958 / #54573 / #54824 —— Quark 量化控制链路重构及回归修补（已合并）

`QuantKey` 进入 QuarkConfig 是 Quark 支持线的重要架构调整，使 weight/activation quant key 在 layer 实例化前即可决定 quant method。紧随其后的 FSE 兼容性修复、GPT-OSS MoE weight_dtype 恢复，说明该重构对真实 AMD checkpoint 产物的兼容性需要持续用 AMD CI 背书。

#### 4. #52650 —— ROCm 镜像内置 Mooncake（已合并）

通过 upstream build recipe 固定 Mooncake ROCm wheel commit，使 `mooncake_transfer_engine_rocm` 成为 ROCm 镜像的一部分。对 AMD 用户的 Mooncake connector 可用性是显著改善。上游 release tag 更新后应尽快切回正式版本。

#### 5. #54513 —— Qwen3.8-Flash-Next QSA indexer 拆分 prefill/decode 路径（已合并）

将混合 batch 拆成 decode 与 prefill 两路，分别调用专用 kernel，并引入 `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB` 提高 indexer workspace 上限。Qwen QSA 生态的性能与可调性迈出第一步，未来仍有很大 kernel 优化空间。
