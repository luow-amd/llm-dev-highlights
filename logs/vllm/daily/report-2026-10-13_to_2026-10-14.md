### 🎯 AMD/ROCm 生态相关动态

#### 1. 已关闭的重要 AMD Issue

**#54359 [ROCm] GLM-5.3-Flash kpool indexer 静默覆写自身 KV cache（已关闭）**
- 核心问题：ROCm 上 `DeepseekV32IndexerBackend.get_supported_kernel_block_sizes()` 返回 `[1, MultipleOf(16)]`，使 640-token 的 manager block 被当作原生支持，`blocks_per_kv_block == 1`，导致没有生成 kernel 粒度的 block table。最终 4096 个 pool 条目只写入 864 个不同 slot（约 79% 的 indexer key 错误）。
- 影响面：长上下文召回率显著下降、`temperature=0` 不再可复现、tool_choice="auto" 成功率从 100% 跌至 83.3%。
- 多方验证：`stefanskiasan`（首发）、`zzw09773`（8×MI325X 独立复现）、`JPedro2`（gfx950 内存访问故障）、`mholopai-amd`（MI355/gfx950 独立确认）、`mustafayildirim`（一度"无法复现"后自我更正）。
- 结论：由 `vllmellm` 标记修复于 #59412 后关闭。

**#56380 [Bug][ROCm] GLM-5.3-Flash indexer block-table mismatch on gfx942（已关闭）**
- 与 #54359 同源问题，从 gfx942 侧独立报告：`prepare_kernel_block_sizes` 未遵循 `MLAAttentionSpec.storage_block_size`，导致 262144-token 设置下 410 列 block table 实际只能寻址 52480 token 位置。
- 由 `vllmellm` 确认 #59412 修复后关闭。

### 💬 高热度讨论分析

#### 1. #54359 — GLM-5.3-Flash kpool indexer 覆写（10+ 条评论，已关闭）

**核心议题**：ROCm 上 kpool sparse indexer 静默覆写 KV cache，模型仍输出流畅文本但长上下文召回严重退化。

**多角度观点**：
- **首发者 stefanskiasan**：给出 8×MI350X、gfx950、TP8、ROCm 7.2.3 的完整 A/B 数据（0/6 vs 8/8 NIAH 召回），并指出 tool calling 从 83.3% 恢复到 100%。
- **zzw09773（8×MI325X）**：独立复现并指出 `DeepseekV32IndexerMetadataBuilder` 的 virtual-block split 只处理 `kernel_block_size <= spec.block_size`，`128 % 2176 != 0` 时静默跳过。
- **JPedro2**：报告 gfx950 上的 GPU memory access fault，日志已被清理但保留了两个 GPU core dump。
- **mustafayildirim**：一度声称 nightly `dee37d891` 无法复现（"recall intact"），随后**公开更正**为自己此前是 allocator 布局的运气，重新部署后 4 次启动全部 miss——这段"错误纠正"的公开过程是本次讨论质量最高的部分之一。
- **mholopai-amd（AMD 员工）**：在 MI355/gfx950 上做独立确认，并进一步分离出 MTP-off 残留问题（`Glm5NextTailCache` 的 ring 大小计算），明确"这不是 #57536 的 patch 没应用"。

**争议焦点**：跨硬件（gfx942 vs gfx950）、跨 MTP 配置（MTP off/on）下故障模式是否同源；`[1, MultipleOf(16)]` 的宽松声明是否是根因。最终由 `vllmellm` 确认为 #59412 修复后关闭。

#### 2. #61359 — `truncation_side` 掉落 tokenizer 特殊 token（存在竞争性 PR）

**核心议题**：显式设置 `truncation_side` 时（即使等于 tokenizer 默认值），特殊 token（BOS/[CLS]/[SEP]/Qwen3-Embedding 的 EOS）会在截断端被切掉。

**不同立场**：
- **Asthenia0412（Draft PR #61524 作者）**：当显式 side 等于 tokenizer 默认时，应让 tokenizer 自己截断（保留特殊 token）；只有请求侧不同于 tokenizer 默认时才走 slice。
- **roydonsequeira（Issue 作者）**：指出 #61363 已同时修复两侧并有测试；并直接反驳 #61524 的覆盖面——"Matching the tokenizer's side covers only one of the two. vLLM sets the tokenizer's side per runner... on an embedding server `truncation_side="left"` still takes the slice and drops `[CLS]` for BERT-style models."

**争议焦点**：transformers 总是从 `tokenizer.truncation_side` 截断，`truncation_side` 参数被忽略；因此对 embedding server 上 `left`（Cohere `truncate="START"` 映射到此）的场景，必须走自定义 slice 而不能只依赖 tokenizer 默认一致性。目前 #61359 仍 open，#61524 为 Draft。

#### 3. #61406 — vLLM Simulator RFC（与已有工作重叠）

**核心议题**：提出 vLLM Simulator，包含 CPU meta-tensor CI 与硬件感知性能仿真两层能力。

**不同立场**：
- **sagearc**：指出与 #47922 高度相似。
- **lucifer1004**：详细列出重叠面并主张收敛而非双轨——#47922 已构建 meta device 上的真实 v1 engine（含 forward 替换与 CPU-only 运行）；RFC #61305 + 实现 #61506 已提供 step timing provider（linear、k-NN table、replay、plugin）、真实部署录制、real/fast-forward/virtual clocks、TP/PP/DP、投机解码、KV offloading、NIXL disaggregated prefill 的覆盖，已在真实 H200 部署上验证。#61407（meta-mode forward for CI）与 #47922 互补。

**结论**：目前仍在讨论如何合并两条设计线，#61506 已作为 PR 打开。

#### 4. #61378 — ROCm default_first（已合并，含深入硬件机制讨论）

**核心议题**：DeepSeek-V4 的 CSA/HCA 多流路径在 ≤96 token 时把默认流链最先入队。

**不同观点**：
- **shen-shanshan**：gfx950 实测，小 token 数 default-first 更快，batch 饱和后略慢，因此在 ≤96 时启用；建议加硬件类型→阈值的 dict。
- **mawong-amd（AMD）**：从 HIP runtime 角度补充关键机制——图重放时 HIP 可跨内部图流调度，受 `DEBUG_HIP_GRAPH_SEGMENT_SCHEDULING` 控制（默认 1=BFS 发现序），capture 时的入队顺序"often but may not necessarily"决定 HW queue 放置；不同 HW queue 的分段因额外 barrier packet 会晚几微秒启动。并指出 DSv4.1 目前总是 `default_first=True`，可能可复用相同调整。

**价值**：这是一次"上层调度优化 + 底层 runtime 机制"的良性互补讨论。

### 🛠️ 重点技术变更

#### 1. #61482 — DSv4-Pro Mono decode layer on MI355X（AMD 生态最重要新增 PR）
把 #60397 的 DSv4.1-Flash mono decode kernel 抽为共享包 `vllm/models/common/amd/mono/`，DSv4-Pro 通过 `MonoSpec`（宽度、数值、变体标志）和约 300 行的 `MonoDecode` 子类复用同一套 kernel。**意义**：这是 AMD 侧第一次把 mono kernel 做成可被多个模型共享的基础设施，而非每个模型自带一份。与 RFC #60904/#61311 规划的 runtime 层（routing、fail-stop、guards）互补。性能上 c1 P50 吞吐 +24%、inter-token latency P50 −20%。

#### 2. #61398 — RoPE 迁移到 vLLM IR（ROCm/AITER）
把 RoPE 从 plain CustomOp 迁移到 `vllm.ir.ops.rotary_embedding`，保留 `MatcherRotaryEmbedding` 使 AITER 的 `QkNormRopeKvCacheFusionPass`（#42749）不被破坏。解决了 `vllm/config/compilation.py` 中长期存在的 `# TODO: support rope native forward match blocks` 与 #28042（RoPE 只在注册为 custom op 时才匹配融合）。**意义**：RoPE 现在在所有路径（native/CUDA/HIP）上发出同一 IR 节点，融合匹配不再依赖 `custom_ops` 全局 flag，实际 kernel 由 IR op 优先级在 lowering 时选择。代价是编译时间 +10 秒（一次性启动成本）。

#### 3. #58555 — gfx942 DCP causal multi-token verify 路由到 Triton split-KV（已合并）
gfx942 上 `ROCM_AITER_MLA` 缺 DSpark/MTP target verify 的 kernel：无 ASM heuristic、无 cprr kernel，且 AITER segmented MLA 在 bf16 KV TILE-128 / fp8 KV 128 heads 时超过 gfx942 的 64 KiB LDS（`OutOfResources: Required: 131072`）。本 PR 为该形状添加 TRITON DCP 路由，运行 split-KV `decode_attention_fwd`，MLA 层照常合并 per-rank fp32 LSE。split 数受 batch 占用限制（无限制时 scratch 8–16 GiB 溢出 int32 offset，受限后 0.25 GiB）。**意义**：解锁 gfx942 上 Kimi-K3 DSpark + DCP8 的完整部署路径。

#### 4. #56273 — 打包 NVFP4 Qwen4Exp PLE embeddings（已合并）
支持 `local-inference-lab/Qwen3.8-Flash-Next-NVFP4` 的 packed NVFP4 ngram 表（每 160 值行 = 80 个 E2M1 字节 + 10 个 E4M3 block scale + 1 个 FP32 global scale），使 26.822 GiB 表可常驻 CUDA memory，在单张 DGX Spark（97.47 GiB 模型加载）上运行，无需 CPU/disk offload。**意义**：为 MoE 大模型在低显存设备上的部署提供了一条新的可行路径，且已通过生产用户（sethforprivacy）验证。

#### 5. #61559 — 回退 AITER 到 v0.1.24.post1 修复 DSv4.1 mono decode 数值
AITER v0.1.25（#61230）改变 gfx950 MXFP4 fused-MoE 数值，导致 `test_dsv41_mono_numerics` 11/11 确定性失败。**意义**：暴露了一个 CI 可见性缺口——该步骤的 `source_file_dependencies` 不包含 ROCm base image，因此 regression 在 `main` 上不可见，只在触及 `vllm/models/deepseek_v41/amd/` 的 PR 上以"永久红灯"形式出现。本 PR 同时修复了这个依赖关系，使下一次 AITER bump 必须经过该测试。
