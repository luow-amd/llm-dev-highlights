### 🎯 AMD/ROCm 生态相关动态

AMD 生态是本周期最活跃的板块之一，贯穿新增 Issue、新增 PR 与合并 PR，覆盖 AITER 集成、FP8 量化路径、内核移植与 CI 基础设施优化。以下按类型梳理：

#### 1. AITER 集成与 API 规范化（核心方向）
- **Issue #51541 [ROCm][AITER] Port FlyDSL int4 MoE integration to AITER fused_moe API**（新增）
  用户 `coderfeli` 提出当前 `fused_flydsl_moe.py` 直接调用 AITER 内部接口（`moe_sorting`、`compile_moe_gemm1/2`），导致 vLLM 侧需要自行维护 routing buffer、pointer ABI、JIT 缓存与 tile-config 表。建议迁移至 AITER 官方 `fused_moe` API，由 AITER 统一负责排序、量化处理、kernel 选择与 tuned 配置。这反映了 AMD 团队正努力收敛 AITER 的对接面，降低上游接口变动对 vLLM 的影响。
- **PR #51563 [ROCm] Migrate W4A16 FlyDSL MoE to AITER API**（新增）
  由 `coderfeli` 提交，是该 Issue 的对应实现，将 preshuffled W4A16 权重路由至 AITER 的端到端 fused MoE API。此 PR 与 #51541 形成“Issue + 快速跟进 PR”的组合，说明 AMD 内部对 AITER 接口整洁度有明确规划。

#### 2. AITER 在特定硬件上的功能增强
- **PR #51551 [ROCm][MLA] Add guarded gfx942 FP8 context prefill**（新增）
  `maeehart` 提交，利用 ROCm/aiter#4645 新增的 D192/V128 kernel，为 Kimi-K3 MLA 提供 gfx942 上的 FP8 context prefill 路径（通过 `VLLM_ROCM_KIMI_K3_FP8_PREFILL=1` 开启）。在 MI325X TP8 上实现 120 万 token TTFT 从 464s 降至 406s（1.14x 加速），并保留了 BF16 路径作为兜底。这是 AMD 针对超长上下文场景的重要性能优化。
- **PR #51598 [ROCm][RFC] Enable scoped AITER W8A8 support on gfx1100**（新增，Draft）
  用户 `01xjw` 试图在 RDNA3（gfx1100）上启用受限的 AITER W8A8 路径，依赖上游 ROCm/aiter#4512 与 #4648。该 PR 明确声明“fail-closed”原则：仅允许 INT8 linear 与 GDN 路径，MoE oracle、FP8、统一注意力等仍保持禁用。已知局限：低并发端到端吞吐比独立 Triton 基线低 3.7%–8.7%，且需本地重建 gfx1100 ROCm 扩展。此 RFC 本身即表明 RDNA 系列在 vLLM 官方路线图中仍属“实验性支持”。

#### 3. ROCm 平台缺陷修复与移植
- **Issue #51530 [Bug]: DeepSeek-V4 sparse indexer 在非 MI3xx GPU 上不可用**（新增）
  `ben0112` 报告了三个相互叠加的阻塞点：错误提示要求启用 AITER，但 `_aiter_ops.py` 在非 MI3xx 平台直接忽略该环境变量；即使绕过平台门禁，RDNA3/3.5 上 AITER Triton 的 fp8 `tl.dot` 又无法编译。虽然在树中存在可工作的 torch fallback，但因上述门禁不可达。该 Issue 揭示了 ROCm 平台支持中 **“错误提示误导-平台门禁-内核不可编译”** 的连环问题。
- **PR #51555 [ROCm] Portable Triton paged-MQA-logits kernel + vectorized torch fallbacks**（新增）
  对应修复 #51530，提供平台无关的 Triton kernel（在 kernel 内将 fp8 反量化为 bf16），并为两个 torch fallback 分支向量化、消除 host sync 的 `.item()` 调用。已在 2× gfx1151（Strix Halo）上完成硬件验证。
- **Issue #51580 [Bug]: v0.26.0 镜像在 gfx942 上经 AITER fused-MoE 出现 NaN logits**（新增）
  该 Issue 带有 `rocm`、`bug`、`kimi` 标签，报告 Qwen3.5-397B-A17B-FP8 在 MI325X 上从第二个 decode 步开始产生 NaN，通过组件隔离定位到 AITER fused-MoE 路径，且 `main` 分支已修复，需 backport 至 0.26.x。这暴露了 AITER 路径与发布版本之间存在不小的同步滞后。
- **PR #51585 [ROCm][Bugfix] Preserve CPU query offsets during capture**（新增）
  `akii96` 修复了 ROCm CUDA graph 捕获期间 `RocmAttentionMetadataBuilder` 清空 CPU query offsets，导致后续 metadata builder 读到 query_len=0 的问题。修法为仅清零设备端 offsets，保留 CPU 副本。

#### 4. CI 基础设施
- **PR #48646 [ROCm][CI] Reuse equivalent ROCm CI images**（已合并）
  `AndreasKaratzas` 将 ROCm 基础镜像拆分为独立可缓存的依赖阶段，按内容标识复用镜像，并保持 csrc/Rust 编译缓存的稳定性。该 PR 于本周期合并，将显著降低 ROCm CI 的构建时间和带宽消耗。

**小结**：AMD 侧呈现出清晰的“平台分级”策略——CDNA（MI3xx）享受最完整的 AITER 加速，RDNA3/4 需通过 RFC 和条件编译逐步开放能力；同时 AMD 工程师（`maeehart`、`coderfeli`、`01xjw`、`akii96`等）在持续推动 AITER 接口的规范化与跨架构兼容，这是 vLLM ROCm 生态走向成熟的重要信号。

#### 1. Issue #51571：异步 MTP align 模式的竞态条件
- **讨论规模**：约 4 条实质对话。
- **核心议题**：`async scheduling + MTP 投机解码 + hybrid Mamba/GDN + align cache 模式`下，模型迭代 N 产生的 accepted 计数被异步复制到 `InputBatch.num_accepted_tokens_cpu_tensor`，但下一轮迭代前 `_update_states()` 调用 `condense()` 变更同一存储的行索引，导致 `_prepare_inputs()` 读取到错位/损坏的计数，进而引发状态拷贝偏移。
- **观点与进展**：
  - 报告人 `QwertyJack` 提供了详尽的源码级审计，对比了关联 PR #42574（优化可跳过场景，但未解决行突变问题）与 #40172（当前 fused postprocess 设计）。

  - 随后出现了对应的 **PR #51599**，将 D2H 写目标改为 runner 的独立 CPU buffer，并补充了回归测试。该 Issue 快速从“报告-分析-认领-修复”全流程走完，体现了高频调度路径 bug 在社区中的响应优先级。

### 🛠️ 重点技术变更

1. **PR #51538：[Bugfix] DSpark 配合 FLASHINFER_MLA_SPARSE_DSV4 全链路修复**
   - 影响面：DeepSeek-V4-Flash + DSpark 投机解码在 SM120 后端上的可用性。
   - 技术要点：修复 5 个独立缺陷——非因果 draft batch 的 SWA 宽度（192 而非 256）、CUDA graph workspace lane 隔离、graph replay 时 `sample_idx_mapping` 的零填充、draft KV 写入 null block、Philox 随机数范围分离。
   - 价值：整合了之前 #51042 的工作，并协调了贡献者归属（`ilmarkov` 为 Co-author）。该 PR 表明 Blackwell 稀疏 MLA 后端与投机解码的叠加已趋于成熟。

2. **PR #51590：[Memory] 度量完整 CUDA 图捕获足迹，优化 KV 预算**
   - 影响面：所有 GPU 平台的内存规划准确性。
   - 技术要点：改进 `profile_cudagraph_memory()`，从“采样两个描述符并在模式间外推”改为“一次端到端跨度内覆盖所有描述符”，并将 profiling 期间的 KV-cache/attention metadata 设置和 retained memory 纳入估算。Kimi-K3 在 8×MI355X 上的估值从 ~1.3 GiB/GPU 修正到 ~4.7–16.9 GiB/GPU，直接修复了 KV 使用率 3–16% 时出现 OOM 的问题。
   - 价值：这是纯内存规划修正，不触碰 kernel/图捕获逻辑，却能有效防止 agentic 工作负载的隐性 OOM。

3. **PR #51551：[ROCm][MLA] gfx942 FP8 context prefill（默认关闭）**
   - 影响面：Kimi-K3 在 MI325X 上的超长上下文 TTFT。
   - 技术要点：使用 ROCm/aiter#4645 的 D192/V128 kernel；仅限 BF16 Kimi-K3 MLA、gfx942、12 heads、D192 Q/K 等固定形状；Q 仅量化一次并在 context segments 间复用 per-head scale；设有 786432 token 的保守激活阈值。
   - 价值：这是 AMD 长上下文场景的标杆优化，提供了“FP8 高吞吐 + BF16 兜底”的渐进式路径。

4. **PR #51599：解耦异步 Mamba align D2H 计数与 InputBatch 行漂移**
   - 影响面：hybrid 模型（Qwen3-Next、OLMo-hybrid 等）在异步调度下的 MTP 正确性。
   - 技术要点：将 D2H 写目标从可变 `InputBatch` 切换为 runner 级不可变 CPU buffer；`_prepare_inputs()` 从该 buffer 读取历史计数；单元测试模拟 condense 后的行移位，确保真实计数被保留。
   - 价值：精准修复了“非阻塞拷贝 + 行索引变动”的竞态，且修复范围仅限异步调度路径，风险可控。

5. **PR #50999（已合并）：单节点 executor 改用 file:// rendezvous**
   - 影响面：所有多进程/单进程 executor 的启动稳定性。
   - 技术要点：将 `get_open_port()` 探听-绑定方式替换为 `file://` + `torch.distributed.FileStore`，彻底消除并发启动时端口竞争导致的 EADDRINUSE。测试验证多节点场景下仍使用 TCP rendezvous，不做越界修改。
   - 价值：大幅降低多 worker 并发启动的偶发失败率，是提升分布式部署体验的基础性修复。

### 💡 值得关注的问题

1. **ROCm RDNA（非 MI3xx）支持策略的明确化**：Issue #51530 已展示出 RDNA3/3.5 在错误提示、平台门禁、内核编译三层的矛盾。PR #51555 作为修复雏形，以及 PR #51598 作为 gfx1100 的 RFC 草案，体现了社区正在试探性扩展支持范围。建议关注这两个 PR 的评审意见，以判断官方是否愿意投入资源支持 RDNA 系列。

2. **v0.26.0 的 backport 请求（#51580）**：AITER fused-MoE 引起的 NaN 是一个“影响生产”的缺陷，已确认 main 分支修复，但 release 镜像仍受害。此案例将考验 vLLM 的 release backport 流程效率，也提示用户在大规模升级前验证 AITER 路径。

3. **GatedDeltaNet / Mamba 状态管理的一系列问题**：除了 #51562（首块误判）和 #51571（异步竞态），根因都是“状态槽复用未清零 + 无状态门控”。这提示 vLLM 可能需要引入更统一的状态页生命周期管理，而非逐个后端打补丁。

4. **Heterogeneous vocab + local argmax 的配置互斥**：Issue #51561 发现两个独立特性共同开启时会静默产生错误 draft ID 映射。这类“选项组合爆炸”类问题，应从参数校验层面避免而非仅靠代码顺序补救。

5. **`/v1/responses` 的长期兼容性**：虽已被 stale 关闭，但工具调用聚合 bug 和 OpenAI SDK 类型缺失仍然存在。建议维护者跟踪根因修复 PR，并考虑在官方文档中明确 /v1/responses 的兼容性边界，避免后续用户重复踩坑。
