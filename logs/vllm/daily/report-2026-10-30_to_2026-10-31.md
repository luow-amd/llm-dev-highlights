### 1. Issue #43750 — [XPU] compressed-tensors WNA16 MoE selector 忽略 XPU（已关闭，10 条评论）

**核心议题**：XPU 上加载 compressed-tensors W4A16 MoE 模型崩溃（`_C.gptq_marlin_repack` 不存在），因为 backends 选择器只排除了 ROCm、未排除 XPU（`torch.ops._C` 在 XPU 构建下为空）。

**多方观点**：
- **Alex-ai-future**：推动 PR #42727 作为修复路径，邀请用户测试。
- **XboxGirl（报告者）**：测试发现 #42727 走的是 AWQ/INC 路径，**compressed-tensors 格式不经过该路径**；自己深入 `vllm_xpu_kernels` 分析，认为 oneDNN int4 GEMM 路径可支持 compressed-tensors W4A16。
- **jikunshang**：询问 #42727 已合并是否可关闭。
- 最终因 90 天无活动被 stale bot 关闭。

**争议焦点**：XPU 与 ROCm 在「Marlin 不可用」上同构，但修复方式（绕过 selector vs. 新增 XPU kernel）尚未收敛。

### 2. Issue #46707 — [RFC] 支持 Domino 投机解码（已关闭，5 条评论）

**核心议题**：Domino 投机解码（并行 draft + logit 空间低秩残差修正）能否在 vLLM 落地。

**观点**：
- **benchislett（维护者）**：建议尽量在 `qwen3_dflash.py` 内实现，Domino 视为无状态的 `compute_logits` 模块，`method` 仍用 `"dflash"`；**tree drafting 明确不在范围**；初版 PR 无需重度优化。

- **benchislett**：最终以「Deprioritized due to DSpark」关闭。

**结论**：DSpark 路线胜出，Domino 暂缓。

### 3. Issue #45661 — NvFp4 MoE backend 不支持部署配置（已关闭，4 条评论，技术密度高）

**核心议题**：SM120（RTX PRO 6000）上 DeepSeek-V4-Flash-NVFP4 报 `NotImplementedError: No NvFp4 MoE backend supports the deployment configuration`。

**多方观点**：
- **waynehacking8（根因分析）**：`NVFP4_BACKENDS_WITH_CLAMP` 只有 `FLASHINFER_TRTLLM`（SM100-only）；`FLASHINFER_CUTLASS` 实际上支持 clamp 与 SM120，只是没被列入；#41834 已修复。
- **danielwoz（实测）**：在 jasl 的 `ds4-sm120` fork 上，Marlin NVFP4 路径 + SwiGLU clamp 在 SM120 上跑通（~59 tok/s），认为 Marlin 路径值得被纳入 clamped backend 集合。
- **Tobi-Adesoye**：从 ragged sequence layout / 非连续内存角度给出分析，但表述偏泛。

**争议焦点**：CLAMP 后端集合过窄 vs. Marlin 路径是否应被认可为 clamp-capable。

### 4. PR #54307 — Mooncake Store 异构 TP + Hybrid KV cache 共享（已合并，10 条评论）

**核心议题**：将异构 TP Store 布局从 Full Attention 扩展到统一 Hybrid KV cache（Attention + Mamba/GDN）。

**观点**：
- **Dao007forever（审查者）**：建议推迟「Attention chunk 在完整 hybrid checkpoint 之前发布」与「逐 group 部分成功/重试」，以简化 PR；并指出 lookup 只检查 page-end chunk、不检查中间 chunk 的 bug（`block_size=16, store_chunk_size=4` 下会复现缺 3 个 Attention 对象）。

**结论**：按审查意见修复后合并，体现「先合并核心、再拆分 follow-up」的 vLLM 审查风格。

## 🛠️ 重点技术变更

### 1. #61837 — Step-5-Preview ROCm 支持（已合并）
**技术价值**：为 Step-5 稀疏注意力（CSA）建立 `common/` + `amd/` 的分层架构，CSA 在 prefill/chunked prefill/decode/MTP verify 全路径跑通，主 paged KV 走 AITER unified attention；支持 BF16 与 FP8 E4M3 KV（FP8 需 `--block-size 32`）；MTP-3 在 gfx950 上 GSM8K 96.6%/97.0%、约 2.3x 加速。
**影响**：AMD 平台首次完整支持 Step-5 系列，且证明「common 与 amd 共享稀疏状态（summary cache、speculative tail ring、region scoring）」的架构可行。

### 2. #64094 — gfx950 prefix-cache SWA replay（已合并）
**技术价值**：在 gfx950 上重新启用 DSv4.1 的 prefix-cache SWA bounded replay。关键在于确认两个 ROCm 消费者（AITER sparse MLA 读 `_compute_swa_indices_and_lens_kernel` 已 clamp 的 slot id；默认 Triton gather 路径在 `ComputePrefillMetadataKernel` 与 `combine_topk_swa_indices` 双重 clamp）都安全，因此 gfx942 保持 off、gfx950 放行。
**影响**：MI355X 上并发 128/256 吞吐 +13.5%/+12%，精度不变；展示了「按 GPU 微架构精细化开关」的策略。

### 3. #64004 — Kimi-K3 MXFP4→int4 requant 加速（已合并）
**技术价值**：纯 TP8 下 requant 从 ~19min 降到 25s，权重逐字节一致。说明优化的是内存/并行策略而非数值路径。EP8 同样从 4min38s 降到 24s。
**影响**：Kimi-K3 在 MI325X（gfx942）上的部署启动时间从 22.5min 降至 3.5min，极大改善运维体验；是 AMD 量化路径（#51274 int4_per_group_32）的关键性能补丁。

### 4. #63761 — Qwen3.5 内核 int32 token offset 溢出修复（已合并）
**技术价值**：6 个 Triton 内核（`_fused_qk_rmsnorm_rope_gate`、`store_cache_checkpoints`、`_fused_post_conv`、`chunk_gated_delta_rule_fwd`、`solve_tril` merge、`RMSNormGated` layernorm）在 `token * stride >= 2^31` 时溢出，导致错误输出或非法访存。逐个 commit 改为 int64 并附回归测试。
**影响**：`--max-num-batched-tokens` 在 174,763+ 时启动 profile 即触发；A100/H200 外部独立复现并确认。是长上下文/大 batch 场景的关键正确性修复。

### 5. #64630 — SleepMode 精确尺寸 pinned CPU 备份（已合并）
**技术价值**：level-1 sleep 原先用 `torch.empty(size, pin_memory=True)`，但 CachingHostAllocator 会向上取整到 2 的幂并缓存，导致 Mistral Large 4 TP8 上 85.19 GiB/GPU 备份膨胀到每节点 +578 GiB 主机内存且不归还 OS。改为 `mmap` + `cudaHostRegister` 精确尺寸、按 allocation 复用、丢弃时释放。
**影响**：大规模部署下 sleep/wake 的主机内存开销显著下降，且保持重复 sleep 的速度优势。

## 💡 值得关注的问题

1. **Issue #64758 — Kimi-K3 NaN 传播导致 `!!!!` 输出**：FlashMLA SM90 decode PDL race + FlashKDA prefill 将单个 NaN 扩散到同 batch 多个请求。AIME25 在一次评测中 0.883→0.700，516 个 reasoning 输出中 56 个受影响。已有 FlashKDA#16、FlashMLA#41、pin bump #64759 的修复草案，但**尚需内核 PR 合并后才可上游化**，影响所有 Kimi-K3 生产部署。

2. **Issue #64714 — `MessageQueue.shutdown()` 无法唤醒阻塞在 overflow payload 的 reader**：`recv()` 是裸 `socket.poll(None)`，cancel socket 未注册、`shutting_down` 结构上不可达，导致 worker 永久阻塞、GPU 内存无法释放、watchdog 失效。`adenzhou1350` 已独立复现 remote reader 场景。这是分布式执行器的正确性隐患。

3. **Issue #64855 — gfx950 sparse indexer padded decode 在 ragged spec-decode 上产生错误 logits/top-k**：由 `jbelofamd` 报告，定位到 host 侧 metadata 与输入切片，与 ROCm 版本无关。影响 MI355X 上的 spec-decode 正确性，尚无修复 PR。

4. **Issue #64791 — `HSA_SCRATCH_SINGLE_LIMIT` 未在 ROCm 镜像中设置**：MI355X 上每 dispatch scratch 分配/释放造成 ~130us GPU 空闲，设 4 GiB 上限后端到端 +4-5%。建议在 `docker/Dockerfile.rocm_base` 中与 `HSA_NO_SCRATCH_RECLAIM` 并列——这是一个**低成本高收益的镜像级配置**，需 AMD 镜像维护者确认。

5. **Mistral Large 4 Responses API 两个兼容性 Issue（#64789 / #64793）**：`input_text`/`output_text` 未归一化为 `text`、`developer` role 未映射为 `system`。`mistral-common` 1.13 严格校验，vLLM 的 Responses→Chat 转换层需在边界处做 normalization。已有社区成员给出具体 diff，等待维护者确认。

6. **PR #64844 — Speculative round contract**：允许自定义 speculator 接管 verify plan（chain/tree/custom mask）、accepted path、per-step budget 与 admission cap。这是 Spec Decode 插件化的重要设计决策，当前开放中，需关注维护者对「计划降级（lowering）」与「recurrent 层 tree verify」的最终意见。

7. **PR #64700 — per-block KV cache 状态移出 cyclic GC**：全量 GC 从 86-295ms 降至 0.1-0.2ms（256 请求 × 128K 上下文），是长上下文高并发场景的显著收益，但属于引擎核心数据结构变更，需关注审查中的兼容性讨论。
