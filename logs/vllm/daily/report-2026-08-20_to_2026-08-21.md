### 💬 高热度讨论分析

本周期讨论最深入的议题集中在两个正确性 Bug 上（按评论量与讨论深度排序）：

#### 1. Issue #53066：v1 detokenizer 的 stop 字符串截断推理内容（4 条评论）

**核心议题**：vLLM v1 detokenizer 将客户端 `stop` 字符串与**整个输出流**（含 reasoning 段）匹配。对于 think-in-prompt 模板（DeepSeek-V4 家族、Qwen3 家族），模型在推理段内部就会复述 `Question:` 等短语。若客户端发送 stop 序列（lm-evaluation-harness **每次请求都会发送 `stop[:4]`**），则会静默切断 reasoning——导致 `content: null` 和基准分数骤降。这被作者定性为一个 **serving-layer 问题伪装成 model problem**。

**观点交锋**：
- **Capicua25x（报告者/修复者）**：提供了完整修复分支（`fix/suppress-stops-in-reasoning`），核心机制是检测 prompts 末尾是否为 reasoning 起始标记，在关闭标记出现前抑制 stop 匹配。提供了强数据支撑：GSM8K n=50 从 0.66-0.84 → 0.98 准确率。
- **he-yufeng（审阅者）**：认可修复机制的正确性，但提出关键疑问——**若模型永不输出闭合标记（reasoning runaway 或模板不匹配）**，客户端 stop 将在整个响应期间保持休眠，只有 `max_tokens` 能兜底。这是改变所有携带 stop 请求默认行为的交互问题。
- **Capicua25x 回应**：该 guard **永远不会把成功变成失败**——reasoning 不关闭的 run 无论有无 guard 都是失败的，区别只是从"N tokens 后 content:null"变为"max_tokens 后 content:null"，成本增量仅在于已失败请求的计算开销。另指出 LM-Eval 是最大的受影响方（`local-chat-completions` 默认行为）。

**当前状态**：开放中，修复分支含 CPU 行为测试，可作为上游补丁基础。

#### 2. Issue #53051：Prefill 误调度进 spec-decode FULL cudagraph（4 条评论）

**核心议题**：启用投机解码时，若 prefill 的 token 数恰好等于 `uniform_decode_query_len * num_reqs`（如 `num_speculative_tokens=2` 时任意 3-token prompt），`_is_uniform_decode` 的**纯形状检查**会将 prefill 误判为 uniform-decode batch，调度进 FULL cudagraph。对 GDN/线性注意力混合模型（Qwen3-Next）而言，FULL 图回放会**跳过所有循环状态写入**，导致"零初始状态"运行，输出确定性垃圾。

**观点交锋**：
- **allenzz-dev（报告者/修复者）**：完成根因定位（逐块 GDN 状态池校验和），提出 PR #53059 从源头修复分类逻辑。同时指出第二层隐患——`GDNAttentionMetadataBuilder` 的 persistent buffer 刷新仅发生在 decode 分支，建议增加 FULL 图回放断言。
- **jschmied（验证者）**：在 GB10/sm_121a 上**无法复现**——因为该环境只使用 PIECEWISE cudagraph 模式，不存在 FULL graph 可被误调度。他明确表示"不是要反驳报告，而是缩小触发条件"，这种验证方式对定位边界非常有价值。

**当前状态**：开放；有三个修复方案并存（#53059 分类修复、#47123 force_uniform_decode、#49918 独立记录同根因）。

#### 3. PR #53141：移除 FP4 ASM GEMM 环境变量（3 条评论）

**核心议题**：`VLLM_ROCM_USE_AITER_FP4_ASM_GEMM` 默认关闭导致 MXFP4 dense 线性层使用 Triton 内核，但该内核 VGPR 溢出（256×256×256 8-warp tile 占满 256 VGPRs），性能显著劣于 asm 路径。

**讨论焦点**：CI 权限流程（作者触发 CI 被拒，需 reviewer 授权），以及对默认行为变更的确认。**当前状态**：开放，CI 已通过，等 review。


### 🔥 热门话题与趋势分析

#### 1. DeepSeek-V4 系列在 ROCm 上的深耕（7 项相关 PR/Issue）

vLLM 对 DSV4 的 AMD 支持正在从"可用"走向"好用"：mHC 融合（38% 提升）、DSA indexer QK 融合、MXFP4/FP8 异构专家融合、aux-stream 压缩重叠。同时多个正确性修复（#53108 MoE 全零输出、#50803 指数器数值、#53110 MXFP8 指数）表明 AMD 团队正在系统性强化 DSV4 的数值可靠性与性能下限。

#### 2. 融合算子成为性能优化主旋律

本周期约 10 个 PR 在做 kernel fusion：从注意力后置、MoE 前置、KV cache 写入到 all-reduce 路径，几乎每个环节都在消除 kernel launch 开销。这反映了在 LLM 推理进入 memory-bound 阶段后，**减少 kernel 间隙比提升单个 kernel 峰值更重要**。

#### 3. 混合架构模型（GDN/线性注意力）的系统性适配问题

Qwen3-Next、Kimi-K3、MiniMax-M3 等 GDN 混合模型引发两类 Bug：#53051 的 CUDA Graph 状态丢失，以及 #53066 的 detokenizer 交互问题。新架构带来的状态管理与输出解析复杂性正在挑战 vLLM 既有抽象边界。

#### 4. 量化精度与性能的拉锯战

MXFP4/MXFP8/FP8 并存导致量化 kernel 复杂度飙升：本期涉及量化精度修复（#53110）、量化感知路径增强（#53151）、量化兼容性检查（#53068/#53097）。AMD 团队在推进融合性能的同时也在收紧数值正确性。

#### 5. V2 Model Runner 迁移的阵痛

#53155 揭示 MRV2 在 gfx950 上对 GLM-5.2 有 30-37% TPOT 回退（MRV2 约 3.0ms + breakable cudagraph 约 1.2ms），并因此将 GLM-5.2 保留在 MRV1。这标志着模型运行器迁移需要更多的平台级回归验证。


### 🛠️ 重点技术变更

#### 1. PR #51665 [Fix weight tying]（已合并）

**技术解读**：vLLM 此前仅依据 `tie_word_embeddings` 配置决定是否绑定 lm_head，从不核查 checkpoint 实际内容，导致配置声称绑定时真实 lm_head 被静默丢弃、输出乱码。修复后 `ModelConfig.maybe_untie_word_embeddings` 会读取 safetensors 元数据，构建未绑定模型后加载权重，再用 `torch.equal` 复核是否应重新绑定。同时 `AutoWeightsLoader` 通过别名检测跳过了约 50 个手写的 lm_head skip。**影响**：一次性根除了所有模型的权重绑定静默错误，是 vLLM 加载可靠性的重要基石。

#### 2. PR #48915 [Per-request acceptance stats in OpenAI API responses]（已合并）

**技术解读**：投机解码的接受率此前只能通过 `/metrics` 看全局平均。该 PR 新增 `--per-request-spec-decode-metrics summary|detailed`，在响应顶层 `metrics` 对象返回 `mean_acceptance_length`、`draft_acceptance_rate`、`acceptance_histogram` 等字段。**影响**：AIPerf 等工具终于可以按请求评估投机解码收益，为动态调整投机参数提供了数据基础。

#### 3. PR #53040 [Fuse shared experts into MegaMoE]（已合并）

**技术解读**：DeepSeek V4 中 replicated FP8 shared expert 与 routed FP4 MegaMoE 原本串行执行，PR 让 SM100 的 MegaMoE 内核将 shared L1、routed dispatch/MMA、shared L2 与最终 FP32 累加统一调度。**影响**：TPOT -13.19%、吞吐 +14.98%，是 NVIDIA 路径上 DSV4 的重大性能突破。

#### 4. PR #51585 [Preserve CPU query offsets during capture]（已合并）

**技术解读**：ROCm 全图捕获时，`RocmAttentionMetadataBuilder` 为防非法内存访问将设备端 query offsets 清零，但**连 CPU 端也一并清除**，导致后续 metadata builder（MiniMax-M3 的 indexer）读到 query length 为零而断言失败。修复仅清零设备端、保留 CPU 端。**影响**：修复了 ROCm 上混合注意力模型全图捕获的启动崩溃。

#### 5. Issue #53136 [ROCm All-reduce 8-16 MiB 死区]

**技术解读**：`CustomAllreduce.should_custom_ar` 的 per-world-size 表是 CUDA-only；ROCm 上消息大小落入 8-16 MiB 区间时被迫路由到 PyNCCL/RCCL，而 RCCL 的 generic collective 内核在 TP=8 + chunked prefill 下因 `hipErrorLaunchOutOfResources` 崩溃（701）。**影响**：TP=8 且存在非对齐剩余 chunk 时不定期崩溃，作者已定位到 qwen 的 `pynccl_comm.all_reduce()` 调用点，等待社区修复。
