**核心议题**：为 Reflection 的 Beam-1.0-501B-A23B 提供 AMD 本地实现，并验证精度。

**讨论过程与观点**：
- **kaiwu-reflection（模型方）**：主动提供 `beam-verifier` 工具，并指出他们没有 AMD 卡，希望社区用 verifier 验证 GPQA-Diamond 和 AIME 2026。

- **AymenKallala（模型方）**：建议先跑 `beam-verifier verify` 看 100% Pass，并怀疑 `--max-model-len 16384` 截断推理 trace，尤其 RE=max 时。

**争议焦点与结论**：初期精度偏差源于**配置问题而非实现问题**。最终形成"模型方提供验证工具 + 实现方硬件验证 + 交叉复现"的良性协作模式，是 AMD 生态中开源协作的典范。

#### 2. #54625 [Core] Cache-aware admission ordering（已合并）

**核心议题**：在 FCFS 等待队列的有限 look-ahead 窗口内，优先接纳前缀已在 KV cache 中的请求，避免冷请求驱逐热前缀。

**不同观点**：
- **fululi12（作者）**：给出 Kimi-K3 FP4 / 8×MI355X 的 agentic trace 数据，admission reorder 从 1,220 增至 1,581（window 16→64），建议默认 window=64。
- **ChuanLi1101（reviewer）** 提出 5 条尖锐意见：
  1. 测试只验证了 `warm` 在 `cold` 前，**未验证冷请求驱逐热前缀**这一核心 claim；
  2. threshold 默认 0 意味着只要窗口开启就在每步重排序，**是公平性变更**，默认应"仅在 cache 压力下生效"；
  3. 每步对窗口内所有请求做 `find_longest_cache_hit`，需限制成本或设小默认窗口，且无 hybrid/Mamba 覆盖；
  4. 窗口内含 blocked/半计算请求的重排序未测试；
  5. 不应与 #54627 的性能混在一起报，应单独引用 window-only 行。
- **fululi12 回应**：承认 4 条是自身缺口，承诺补充驱逐测试；澄清 `cache_aware_admission_window=0` 默认关闭，仅当用户 opt-in 后才涉及公平性问题。

**争议焦点**：**默认阈值语义**（`0` 是"始终应用"还是"仅压力下应用"）以及**性能收益与公平性/成本之间的权衡**。最终 merged 版本保留 opt-in 设计，是折中结果。

#### 4. #63367 [ROCm][DSv4.1] Engram gate 分片（已合并）

**核心议题**：将 TP>1 时的 all-gather 从完整 `wkv` 输出降为按 dim 分片。

### 🛠️ 重点技术变更

#### 1. #54725？不——#62725 [ROCm][Bugfix] gfx942 MLA verify 支持 >4 token

**技术解读**：AITER 的 persistent bf16 MLA decode 只有最多 4 个 query token 的 kernel，而其 non-persistent fallback 在 MI300X 上：
- 32 heads 时返回错误结果
- 64/128 heads 时忽略 causal mask
- 16 heads（TP2 下 padded rank）在 KV cache 超过 4GiB 后**静默**读错 KV 页

该 PR 新增 Triton verify kernel，按 (token, head) 行块读取 KV tile，支持任意长度 draft。在 DeepSeek-V2-Lite TP2 k=7 下，GSM8K 从 **0.004 恢复到 0.605**，同时输出 tok/s 在 c1/c32 下领先现有 row-view 路径 14–56%。**这是本周期最重要的正确性修复之一**，因为原 bug 是静默的。

#### 2. #64898 [Perf][Qwen4Exp] 融合 HyperConnection up 投影与 gate mix

**技术解读**：在 B300 SM100 上，将 rank 320→4×2560 的 up projection 与 sigmoid gate + 4 路均值融合为单个 tcgen05 kernel。关键优化：
- TMA 加载 `xn`
- CTA pair 上 256 行 tile + 64 列 tile + 4 epilogue warpgroups
- `tanh.approx` sigmoid

M=16384 时达 105µs，**52% HBM SOL**，相对 cuBLAS+Triton 链提速 **2.19×**。这体现了 **SM100 tcgen05 上"融合即性能"** 的趋势。

#### 3. #63367 / #59802 Engram gate 分片 + mHC gate 重叠（DSv4.1 ROCm）

**技术解读**：两个 PR 互补：
- #63367 在数学上证明 gate 只需 per-token 的 dim 和，故可只 all-gather 值切片 + 8 个 FP32 部分和，通信量降低 5×；
- #59802 将 gate 投影移到 side stream，与 attention/FFN 重叠。

两者叠加后，TP4 MI355X 上 DeepSeek-V4.1-Flash 的长上下文 TTFT 与 TPOT 均有明显改善，且精度在噪声内。**这表明 ROCm 侧的优化已进入"算子级 + 通信级"协同优化阶段。**

#### 4. #65643 [Refactor][PCP] 物理拓扑与 attention 执行布局解耦

**技术解读**：将 Model Runner V2 中的物理 PCP 拓扑与 layer backend 需求、per-forward attention 布局分离。修复 TP1/PCP4/DCP4 在复制 DFlash/DSpark draft 时被错误改写为 PCP1/DCP4 并导致配置校验失败的问题。**这是为 spec decoding + 长上下文并行铺路的基础设施重构**，虽然当前仍是 draft。

#### 5. #51808 [Online Quantization] MXFP4 activation override

### 💡 值得关注的问题

#### 1. #65734 动态 FP8 scale 被 CUDA-graph padding 行污染（高优先级）
这是**静默正确性 bug**：单请求看似正常，并发下产生乱码。建议社区统一引入 `torch.zeros` 初始化 attention 输出缓冲区的规范，或改用带 padding mask 的 scale 计算，避免相同根因分散在 MLA、dense attention、Inkling 等多条路径反复出现。

#### 2. #65632 Kimi K3 的"AMD 质量问题"需明确定性
giuseppegrossi 的 API 不匹配假设若成立，则**这不仅不是 AMD 的问题，甚至不是 vLLM 的 bug**，而是跨框架协议兼容性问题。建议尽快给出测试结论，避免误导社区对 AMD 平台的判断。

#### 3. #65643 PCP 拓扑重构仍是 draft
物理拓扑与执行布局解耦是 spec decoding + 长上下文并行的关键基础设施，但当前 E2E 生成与模型精度验证仍未完成，建议关注其后续推进。

#### 4. #65769 CuMemAllocator.discard 保留 asleep 分配的 CPU 备份
该 Issue 揭示 `discard()` 在 `is_asleep` 分支只警告、不清除 `cpu_backup_tensor`，4GiB kv_cache 测试中 RSS 保持 ~4095MiB 不下降。虽然作者已澄清**标准 `CuMemBackend.suspend(level=1)` 不卸载 kv_cache**，但对自定义 sleep-mode backend 和 `XpuMemAllocator` 同样存在该缺陷。建议社区固化 `discard` 语义（"内容不会被恢复" ⇒ 应释放备份）。

#### 5. AITER 版本依赖管理需规范
本期多个 PR 显式依赖尚未发布的 AITER PR（ROCm/aiter#7458、#7347、#7444），依赖链为 `Dockerfile.rocm_base` 的 `AITER_BRANCH`。一旦 AITER 分支变动或分叉，vLLM 侧的 PR 可能集体失效。建议推动 AITER 更频繁地发布带 tag 的版本，并在 vLLM 侧建立依赖矩阵。

#### 6. Rust Frontend 的 pinned divergence 需要明确治理
#65757 将 Kimi K3（长空格序列）与 Hy3（含 CR 文本）记录为"pinned divergences"，即已知与 Python 不一致但暂不修复。这类 divergences 长期存在会削弱"Rust 与 Python 等价"的承诺，建议跟踪其修复计划。

#### 7. DSv4.1 Mono 的架构依赖需要文档化
#65749 明确标注"CI 无 MI350X"、`MI355X on this branch is TODO`；#63027 benenzhu 的测量也区分了 TP2/TP4、gfx950/gfx942。建议在 mono 路径文档中明确列出**经过验证的硬件 × TP × ratio 组合矩阵**，避免用户在不支持的配置上踩坑。
