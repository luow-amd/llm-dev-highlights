## 💬 高热度讨论分析

### 1. #52362 `[ROCm][DSv4] Enable DSpark adaptive verification`（评论 9+，多方对峙）

**核心议题**：为 DeepSeek-V4 在 ROCm 上启用 DSpark 置信度调度的自适应投机验证。

**不同立场**：
- **作者 tuukkjs + larryli2-amd（AMD）**：MI350X 上高并发显著加速，低并发与 fixed K=7 相当。
- **ChuanLi1101（reviewer）提出 5 点尖锐质疑**：
  1. `_rocm_supports_flattened_device_query_lens()` 实为 `is_rocm()`，与宣称的 "DSv4-only" 不符，且接入了共享 `_use_flattening`；
  2. 性能数字依赖 V2 + breakable CUDA graphs，但当前 ROCm 上二者是关闭的；
  3. **MI355 ShareGPT 上 c4-c32 自适应比 fixed K=7 慢 5-8%，仅 c64+ 才反超**；
  4. 新测试全是 CPU mock，无 AMD CI job，无真实 MLA/SWA GPU graph replay；
  5. MI350 用了私有 AITER wheel，stock nightly 需要 `AITER_USE_CK_MOE_SORTING=1` 才不 fault。

**作者回应**：逐条修正（收窄 predicate 到 `DeepseekV4ForCausalLM` 并加 V4.1 override），并做了细致的 causal ablation——证明低并发回退是三个机制叠加（adaptive manager/reallocation -2.23%、varlen graph envelope -3.18%、device-ragged flattened-indexer -2.52%），而非 trimming 单独导致。

**争议焦点**：**特性默认开启 vs. 平台就绪度**——作者承认低并发劣化可复现（c4 -6.49%、c32 -4.15%），但仍推进合并。最终 PR 在 #57526 同日被合入，说明 maintainer 接受了 "高并发收益 + 低并发可接受回退" 的取舍。

### 2. #57526 `[Perf][ROCm] Add a ROCm path for Hy4 and compile the backbone`（评论 8+，精度验证拉锯）

**核心议题**：Hy4 此前是 `vllm/models/` 下唯一没有 `amd/` 路径的模型，ROCm 直接跑 NVIDIA backbone；补上 `@support_torch_compile` 后 cudagraph 恢复，解码延迟降 13×。

**争论在于正确性验证**：
- **tjtanaa（AMD maintainer）** 要求 e2e accuracy 结果。
- **akii96** 先跑 GSM8K 得 71.49%，但 ~18% 样本因 harness 在 reasoning 中途截断而空白，遂转向 GPQA-Diamond（32k: 79.80%，64k: 85.35%）。
- **tjtanaa 追问**：HF 卡上原始 GPQA-Diamond 是 ~92%，能否复现？
- **jamesETsmith 介入**：自测最高 88%，但开启 GPT-OSS answer extraction 后达 ~93%；并独立在 SuperChem 上验证 67.60%，与腾讯报告 66.4% 吻合。
- **akii96 补做三种打分口径对比**：lm-eval flexible-extract 87.37% / explicit-declaration 89.39% / gpt_oss extract_abcd **91.92%**，指出差异主要来自评分 harness 而非模型本身。

**争议焦点**：**评估方法论**——同一批生成用不同 extraction 规则可差 4.5 个百分点。此讨论对社区有普遍价值：benchmark 数字需连同打分 harness 一并报告。最终 PR 在 e2e 验证充分后被合入。

### 3. #50592 `[Kimi-K3][AMD] Return KDA and MLA projection outputs directly`（评论 10+）

**核心议题**：移除 Kimi-K3 AMD attention 路径中每步 93 次（69 KDA + 24 MLA）投影后拷贝。

**观点交锋**：
- **Fangzhou-Ai 用 profile 给出可信估算**：C16 时 93 个 copy 组约 0.495 ms/step，KDA 占 0.37 ms ≈ **1.1% of pure-GPU period**；同时提醒作者报告的 TPOT 是 e2e 含 host 开销，与 GPU-only 百分比不可直接比较。
- **作者 LiuYinfeng01 补充 A/B**：C16 TPOT -0.97%、吞吐 +1.02%，并坦诚方法论局限（顺序测量非交错、无 GPU 进程快照）。
- **hongxiayang（AMD）点破关键**：*"comments above are kind of 'AI' sense and hard to see where is the performance gain end-to-end."*
- **Fangzhou-Ai 一句话总结**：*"The perf gain is very minor as expected. In a word this PR saved on copy/paste in the decoding stage... real but very small."*

**结论**：PR 以 "正确清理、收益真实但微小（~1%）" 定调并被合入。此讨论反映 AMD 社区对**性能声明严谨性**的自我要求。

### 4. #51360 `[Frontend] Add reusable TP1 initialized-engine snapshots`（评论 8+，设计路线之争）

**核心议题**：Engine 初始化后、HTTP 服务启动前的进程树快照与恢复。

**冲突观点**：
- **作者 matteso1** 把范围严格限定在 "same-host TP1 快照 artifact 路径"，无 runtime sleep/wake、无跨机、无 1-to-N。
- **fuhefei** 团队已独立设计 "sleep L3 模式"——frontend 保留、只释放/恢复 EngineCore，作为 sleep 模式的一部分而非独立离线命令。作者回应：二者互补，欢迎 Slack 对比。

**结论**：PR 已合并（H200 验收通过：Qwen3-0.6B 两次 restore 后 token/logprob 完全一致；Qwen3-32B 上 warm 54.7s vs compact restore 20.4s）。设计边界之争留待后续 PR。

### 5. #45635 `[AuxOutput] Add block-keyed storage for routed-expert outputs`（评论 10+，生命周期难题）

**核心议题**：为 MoE routed-expert output（R3）引入 block-keyed 存储 connector，使其在 prefix caching + async scheduling 下正确复用。

**关键技术争点**：aoshen02 指出 **async scheduling 下 step N+1 可能 preempt request A 并复用其 KV blocks，早于 `update_from_output()` 读取 A 的 R3**，导致新请求覆写 A 的 R3 slot；建议用 `defer_block_free`。该 PR 已合入。

## 🛠️ 重点技术变更

### 1. #57526 — Hy4 的 ROCm 前缀路径与 13× 解码加速
**技术解读**：`@support_torch_compile` 缺失导致 `cudagraph_mode` 被静默 resolve 为 `NONE`（PIECEWISE 被 OVERRIDE，FULL_AND_PIECEWISE 经 `without_piecewise()` 落入 `FULL_DECODE_ONLY` 后在 gfx942 上 capture 失败）。补上装饰器后，默认 cudagraph 模式下 TPOT 由 311.7 ms → 23.8 ms。
**影响**：为后续所有 ROCm 侧 Hy4 kernel 工作（如 #57960 的 MXFP8 AITER enablement）提供落地点。同时揭示一个普遍性隐患——**任何缺少 `@support_torch_compile` 的模型在 ROCm 上会静默退化为 eager**，这个问题值得 CI 层面加检查。

### 2. #57923 — AITER MLA FP8 prefill workspace 启动 OOM
**技术解读**：AITER v0.1.22post1 拾取 ROCm/aiter#3606 后，MLA metadata scheduler 给出过松上界（假设每个 request 都用 max_qlen）。在 `max_num_batched_tokens=16384` 时预留 128.03 GiB 导致启动即崩。
**修复**：短期用 token budget 约束总量（16384 → 2.62 GiB）；长期需 AITER 提供 budget-aware 接口。**这是典型的第三方依赖变更引发 OOM 的案例**，表格中 `1.88 GiB → 64.03 GiB → 2.56 GiB` 清晰展示了问题幅度。

### 3. #57979 + #58008 — GLM-5.3-Flash 组合优化
**技术解读**：#57979 让 KDA decode kernel 感知 `stride_b/h/s/d`，移除 4 处 `.contiguous()`；#58008 将原本 18 个 PyTorch elementwise kernel 的 `fit_kpool_indices_to_aiter` 合并为单个 Triton kernel。
**影响**：在 MI350 TP8、`max-num-seqs 512`、`ROCM_AITER_MLA_SPARSE` 下，1k/1k 高并发 TPOT 改善 3-4.2%、吞吐 +2-7%。这代表 AMD 对当前旗舰 MoE 模型的持续打磨已进入 "消除 launch 开销" 的精细阶段。

### 4. #51360 — 可复用 TP1 Engine 快照
**技术解读**：利用 CRIU 4.2.1 + CUDA plugin + cuda-checkpoint，在 Engine 初始化完成、HTTP 服务启动前 dump 进程树，restore 时跳过重复初始化。
**影响**：Qwen3-32B BF16 TP1 上 warm 54.7s → compact restore 20.4s，compact artifact 仅 5.88 GB（模型 65.54 GB 外置）。这为 **同一 host 上的快速冷启动 / 多副本快速拉起** 提供了新路径，与 RFC #34303、#37921/#37925 的 CUDA checkpoint 谱系一脉相承。项目已有 "sleep L3 模式" 的并行设计（fuhefei），需关注两条路线是否趋同。

### 5. #45635 — AuxOutput Connector（R3 / 路由专家输出）
**技术解读**：首次引入 AuxOutput Connector 抽象。核心洞察：prefix-cache 命中会跳过模型执行 → cached token 不产生新 R3；GPU/KV slot 会复用 → 物理地址不是稳定身份；投机解码会产生后续被拒的 row。因此必须用 **与 KV 兼容的 block hash** 做 key，把 R3 建成不可变 block。
**影响**：为 MoE 的 expert-routing 可观测性、以及未来的 DSA / logprobs 辅助输出提供了通用生命周期层。aoshen02 指出的 async scheduling 覆写风险已通过 `defer_block_free` 解决，这个并发正确性问题值得后续类似 connector 设计参考。

## 💡 值得关注的问题

1. **AMD CI mirror 声明漂移（#57956，开放）**：43/141 处不一致，其中 28 组标记为 MI355 实际跑在 MI300（gfx942）。Bevisy 的 #57972 只修复了 23 个 step，剩余 39 个 mirror 仍待 AMD 侧 "placement call"。**建议 AMD maintainer 明确低 tier 声明与未实现 step 的处理策略**，否则新增的 parity checker 只能持续报警。

2. **AITER 版本耦合的长期治理（#57923 引出）**：本周期三个独立 bug 都源于 AITER 版本行为变化（workspace 上界、quant 门控、activation 判定）。建议建立更显式的能力探测接口，而非依赖版本号或模式匹配。

3. **API 批量路径的一致性测试缺口**：Ningke-Li 的系列 Issue（#57944/#57935/#57950/#57929）指向同一类问题——**`/v1/*/batch` 组装器在推理成功后重新解释 raw output 时，与流式路径的解析规则不一致**。可能存在一批同类 bug 尚未被发现，值得系统性排查。

4. **`support_deep_gemm()` 的 capability family 匹配过宽（#58022）**：`is_device_capability_family(100)` 会误纳 SM107，导致 `cuModuleLoadData → CUDA_ERROR_ASSERT`。这暗示 **vendor 侧新增 SKU 时，vLLM 的 capability 判断需要更细粒度枚举**。

5. **stale bot 对已修复 Issue 的误伤（#43390 / #43364）**：#43390 实际上已被 #42863 修复并明确回应，但仍因 90 天无活动被自动关闭。建议在自动关闭前检查是否存在关联的 merged PR。

6. **V1 `InputBatch` prompt-embedding 张量泄漏（#57974，开放）**：256 MiB / 8 slot；在 `max_num_seqs=256` 且 shape 为 `(4096,4096)` BF16 时理论可达 8 GiB host 内存滞留。`khushali9` 已定位到 `remove_request()` 未清 `req_prompt_embeds[req_index]` 且 `condense()` 空 batch 分支不清 dict，PR 正在推进。这是一个**容易被忽视但后果严重**的资源泄漏模式，值得在其它 per-slot 字典（如 multi-modal cache、adapter cache）中对照排查。

7. **RDNA3 生产级栈的表达渠道（#57925）**：JartX 以 `DO NOT MERGE` tracking PR 的方式请求 maintainer 指导拆分，暴露了**非 CDNA 架构贡献缺乏官方流程**的问题。RDNA3/4（gfx1100/gfx1201）在消费级与工作站市场占比显著，本周期另有 #57969（gfx11 WMMA padding）、#58060（RDNA3/4 narrower KV tile，kernel 2.25-2.67×）两份独立优化，说明社区需求真实存在。是否设立 RDNA 专项 CI lane，值得 maintainer 讨论。
