### 💬 高热度讨论分析

#### 1. #56851 — [RFC] `/inference/v1/generate` 请求级 text 与 derender 输出（11 条评论，已关闭）

**核心议题**：P/D 部署中，流式 derender 采用「每个 SSE chunk 一次 HTTP round trip + 客户端回传 `stream_state`」的无状态设计，导致解析路径每次都要重放全部输出 token，对 TPOT 关键路径造成压力。

**多方观点**：
- **`shimib`（性能数据提供方）**：在 GKE 1×A100-40G / Qwen3-8B 上测得 derender 层「detokenize + parse」的 CPU 成本约为同进程内的 **9×**，前端总 CPU 是耦合服务器的 1.6–1.9×，多千 token 推理输出 E2E p50 **+15%**；认为「无状态 derender 是把成本搬了个位置，还加了溢价」。
- **`nilig`（llm-d 视角）**：支持 `output_mode` 方案，保持 `tokens` 为默认，`text` 作为第一阶段；强调把 detokenize 放回 decode server 能避免额外跳数；建议 `/abort_requests` 在 decode pool 加载 tokenizer 时也可用。
- **`hickeyma`（RFC 作者）**：接受 p50 数据并写入 motivation，但纠正了 logprobs 成本的归因——只设 `output_mode="tokens"` 不能省 tokenizer 成本，还需 `detokenize: false` 或 `--tokens-only`；并在多次迭代中响应 stop string、EOS、#55029 依赖等问题。
- **`DarkLight1337`（维护者）**：倾向用 discriminated union（`GenerateTextResponse` / `GenerateTokensResponse` / `GenerateDerenderResponse`）而非单类可选字段，这样 `logprobs` 类型可以按 mode 声明。

**争议焦点**：derender 放 decode pod 还是独立 tier？CPU 放大 9× 是否被自适应 chunk 合并抵消？stop string 被引擎裁掉后 `/derender` 会重新解码回来，parity 如何定义？

**结论**：RFC 关闭，Phase 1 已作为 **#58588**（draft）推进；`output_mode` discriminated union 方案被采纳。

#### 2. #63801 — [Perf][HiSparse] 有界 copy worker 预取投机组（8 条评论，已合并）

**核心议题**：扩展 HiSparse 的共享索引组预取到多 token 投机验证（含 MTP），并限制 compact-gather launch 不随 batch 膨胀。

**多方观点**：
- **`zhenwenqi2024`（作者）**：给出 8×H200 / GLM-5.2-FP8 / TP8 / MTP3 / 64K input / C32 的 ABBA 数据：8K 输出吞吐 **+2.35%~+3.00%**，TPOT **−4.10%~−5.41%**，TTFT 基本不变。诊断 profile 显示暴露的 gather 时间 14.99 → 5.32 ms。
- **`MatthewBonanni`（维护者）**：可以复现性能收益，但发现一个疑似 topk 相关的 race，正在调试。
- **后续**：`MatthewBonanni` 自行定位到 **FlashInfer 的 MNNVL fused allreduce + residual + RMSNorm kernel 存在 cluster-barrier race**（`LamportFlags::ctaArrive` 只 warp 0 调 `__cluster_barrier_wait()`，其他 CTA 对可能不存在的 peer 做 DSMEM 写），并附带独立复现与修复；结论是**不是本 PR 的 bug**，PR 的额外零拷贝 host-memory gather 只是把上游 bug 暴露出来。

**结论**：PR 合并，race 交由 FlashInfer 修复；社区共识是 HiSparse 的性能收益成立。

#### 3. #63406 — [Core][CUDA Graph] 分离 prefill / decode 捕获尺寸（7 条评论，已合并）

**核心议题**：在主分支上，prefill 和 uniform decode 共用同一个 token 列表决定 CUDA graph 捕获尺寸；当 speculative K=7 时 q=8，1024 token 上限只覆盖 128 并发请求，更大的 batch 被迫退化为 eager。

**多方观点**：
- **`Pb314314`（作者）**：新增 5 个配置字段，按 prefill（token）和 decode（request）分别配置捕获网格。自报数据：dense 模型（Qwen3.8-27B）mixed-batch 延迟最多 **+12%**，MoE 模型普遍受益（MiniMax 4–7% 波动）；更新后的 prefill 网格在 384/640/896 有精确命中，769 只 round 到 896 而非 1024。
- **`Rockyeast`**：提供 H200（SM90）数据，指出本 PR 在 SM100 以外仍保留 512-token 上限，所以 Hopper 不受影响；对 3B-active MoE 模型，>512 token 的 prefill 在 Hopper 上是 launch-bound，按 64 步长网格能显著降低 TTFT。

**结论**：合并。SM100 默认采用 8192-token prefill 网格 / 1024-request decode 网格；Hopper 保持原默认，后续 **#64825** 会基于此 PR 的配置字段跟进。

#### 4. #62750 — Block Hadamard 输入旋转（8 条评论，已合并）

**核心议题**：线性层前对输入做 block Hadamard 旋转 `(xH)(WH)^T = xW^T`，散布 outlier 以降低 block-scaled 量化误差；同时覆盖 online 量化和 Quark 带 online rotation 的检查点。

**多方观点**：
- **`simondanielsson`（reviewer）**：强烈要求**提供不依赖 AITER 的路径**（emulation/debug fallback），并要求给出 **GPQA Diamond 5 次重复**的精度对比（而非仅 GSM8K）；同时质疑为何要与 MXFP4 权重键绑定，认为「非加速旋转 + GEMM 不应依赖 weight quant key」。
- **`mjkvaak-amd`（作者，AMD）**：解释这是 `InputHadamardLinearMethod` 包装任意 linear method，不依赖 weight format；AITER 融合在 follow-up **#63272**（ROCm/aiter#6734）中解决性能问题，当前已有 PyTorch 旋转路径可用于评测；并展示 reviewer 建议的表格。
- **`tjtanaa` / `simondanielsson`**：小 comment 后转向 OK。

**结论**：合入。性能回归（PyTorch 旋转）由 #63272 融合进 AITER HIP MXFP4 quant 解决。

#### 5. #65479 — [ROCm][MiniMax-M3.1] MXFP8 linear on AITER FlyDSL（6 条评论，仍开放）

**核心议题**：为 gfx950 接入 AITER tuned FlyDSL MXFP8 GEMM，宣称 1.2–1.9× 单 GEMM 提升、DSpark3 conc-32 decode profile 中 MXFP8 linear 总时间 7.46 ms → 4.28 ms。

### 🛠️ 重点技术变更

**1. #63406 — prefill / decode CUDA graph 捕获尺寸分离（已合并）**
将「CUDA graph 的 batch 概念」拆成 token（prefill）与 request×q（uniform decode）两个维度，新增 5 个配置字段。直接解决 speculative K 大时 decode graph 覆盖不足、>1024 token 的 mixed batch 走 eager 的问题。这是 Q4 roadmap #61024 的组成部分；SM100 默认 8192-token prefill 网格、1024-request decode 网格。**对生产部署影响显著**：MoE 大模型受益明显，dense 模型需要按架构调网格。

**2. #56307 — gfx1151 HIP GDN prefill 后端（已合并）**
把 GATED_DELTA_NET 的 chunked delta rule（WY 表示 / UT 变换）实现为单 HIP kernel，一个 block 走完一个 (head, seq) 的所有 chunk，状态常驻寄存器、chunk 中间量放 LDS，避免 `h`/`w`/`u` 落 DDR。**精度更高**（相对 fp64 误差 0.53×）且**更快**。这为 RDNA3.5 长上下文 prefill 提供了 CDNA 之外的第一条原生路径。

**3. #62750 — Block Hadamard 输入旋转（已合并）**
提供通用的 `InputHadamardLinearMethod`，包装任意 linear method，在 PyTorch 内做 block Hadamard 旋转。既支持 online `mxfp4_hadamard32`，也支持加载 Quark 带 `input_rotation` 的检查点。**这是 MXFP4 量化精度工程的关键基础**：follow-up #63272 把旋转融合进 AITER 的 MXFP4 激活量化，从而在不增加 serving 开销的前提下获得精度收益。

**4. #60418 — RDNA3/RDNA4 上 TRITON_ATTN 优先级提升（已合并）**
在 gfx1201/gfx1100 上把 `TRITON_ATTN` 放到 `ROCM_ATTN` 之前，并配套添加按 padded head size（64/128/256 配置）划分的 prefill/chunked/mixed/2D decode/3D decode 启动参数。`fp8_e5m2` KV 缓存这是唯一例外。这标志着 AMD RDNA 路径从「ROCM_ATTN 优先」转向「Triton 调优优先」。

**5. #65431 — Gemma 4 native packed vision tower（开放，值得跟踪）**
用 `cu_seqlens` 打包的图像/视频帧替代 padding，使 Gemma 4 可运行在任何 `--mm-encoder-attn-backend` 上，并复用 DiffusionGemma / EmbeddingGemma2。H100 验证发现两个待修问题（TF32 容差、整 batch eager 调用消耗 KV cache），说明**多模态 encoder 的 CUDA graph 与 packing 组合仍需打磨**。

### 💡 值得关注的问题

1. **#65550（open）— sliding window + full-prompt KV connector load 读到 null block**：FlashAttention 的 sliding window 是 `(W-1, 0)`，而 NIXL 只保留从 N-W+1 开始的块；当 `N-W+1 ≡ 0 mod block_size` 时重算的 token N-1 读到已释放的块。`Aravind0403` 已提 PR #65584（让 connector 对 sliding-window 模型少传一个 token），并汇总了 #59330（prefill backoff）和 #60545（传输 hidden state）两条替代路线。**影响 P/D 部署正确性，值得跟踪**。

2. **#65500 与 #62092 的 overlap**：`alexm-redhat` 发现的 `ROCM_ATTN` 对 head_dim ≠ 64/128 静默回退到慢速 Triton kernel 是真实性能问题，但修复被要求合并进 #62092 的整体后端选择重构，而不是局部调换优先级。**关注 #62092 的推进**。

3. **#65479 的 `QuantizedActivation` 兼容性**：MiniMax-M3.1 的 5 笔 fusion PR 与 AITER FlyDSL GEMM 之间存在「kernel 选择顺序决定 fusion 是否生效」的隐式耦合，需要在 AITER v0.1.28 落地前明确接入顺序，否则合入顺序错会静默丢收益。

4. **#65390 — 纯文本模型需要 torchvision**：`kernel_warmup()` 的 import 守卫在 `isinstance` 检查之前就失败，且 `torchvision` 在 build requirements 但不在 runtime，导致 15 分钟 JIT 后才报缺失依赖。这是 ROCm 打包 + warmup 逻辑的双重问题，尚未有 PR。

5. **#65378 / #65413 — UMA 集成 GPU 上 extensible KV cache undersize**：已由 #65413 修复并合并（GB10 上 216 → 1302 blocks），说明 DGX Spark 等 UMA 设备的 KV cache 内存核算需要与 classic sizing 路径对齐。**其他依赖 `cudaMemGetInfo` 的路径值得审计**。

6. **RFC #56851 关闭后的 Phase 1 #58588（draft）**：`hickeyma` 询问 `shimib` 能否为 Phase 1 提供 Section 12 的 benchmark，目前尚未回复。该 RFC 涉及 decode tier CPU 预算与 TPOT，如果 Phase 1 不能重复 RFC 中的性能对比，可能影响后续设计决策。

7. **AI 辅助 PR 的治理**：本周期既有明确声明使用 AI 的 PR（#65397、#65480），也有 `BeiningWu` 因无法逐行 attest 而放弃提交 PR 的案例。`AGENTS.md` 的「客观评估价值，无显著收益则关闭」条款正在被实际使用（CI bot 会提示），值得关注其对贡献门槛的影响。
