### 💬 高热度讨论分析

**1. Issue [#50147] Kimi-K3 并发负载下的非法内存访问崩溃**

*   **核心议题**: 用户在 NVIDIA DGX B300 上运行 Kimi-K3 模型时，遇到并发的、变化位置的非法内存访问崩溃，且崩溃频率与并发数正相关。
*   **核心观点**:
    *   `amitwaisel` (报告者): 详细描述了三种不同场景下的崩溃，并认为是同一个早期异步设备故障的后续表现。同时，该用户指出这是一个 NVIDIA 问题，而非 ROCm，因为自动标签规则误将其标记为 ROCm 相关。
    *   `github-actions`: 自动识别了可能相关的 ROCm 维护者，但由于是误触，导致问题进入了错误的处理队列。
*   **争议焦点**: 无。这是一个对 K3 模型稳定性至关重要的 Bug 报告，社区和报告者都认可是由于模型中 Mamba/SSM 与 Prefix Caching 的交互问题引起的，与硬件平台关系不大。
*   **当前状态**: **Open**。报告者和维护者正将其链接到 K3 模型的主跟踪 Issue #50001 以协调解决。

**2. Issue [#50064] ROCm AITER MLA 稀疏元数据属性缺失导致 DSv4 模型启动失败 (已关闭)**

*   **核心议题**: 在 AMD ROCm 上，任何稀疏 MLA (DSA) 模型（如 DeepSeek-V4）都无法启动，因为 `ROCMAiterMLASparseMetadata` 类缺少关键的 `num_decode_tokens` 属性。
*   **核心观点**:
    *   `haosdent` (报告者): 精准定位了根因，并指出该元数据类还缺失其他字段，根本性修复需要更全面的同步。
    *   `giuseppegrossi` (AMD 员工): 确认可以复现，并表示一个最近合并的 PR [#48886](https://github.com/vllm-project/vllm/pull/48886) 已经修复了此问题。
*   **争议焦点**: 无快速归因和修复是这次讨论的亮点。
*   **当前状态**: **Closed**。问题已通过另一个 PR 解决，维护者跟踪紧密。

**3. Issue [#50135] Intel GPU 内存启动错误**

*   **核心议题**: 用户在 Intel B70 GPU 上双卡部署 Qwen3.6-35B-A3B 模型（FP8 量化）时，vLLM 报告单卡 (`xpu:0`) 的可用内存不足，尽管两张卡的总内存足以容纳量化后的模型。
*   **核心观点**:
    *   `azhuvath` (报告者): 最初遇到了内存不足错误，但后来自己发现是因为有其他容器占用了 GPU 资源，导致错误信息具有误导性。他建议 vLLM 应给出更清晰的提示，说明“GPU 已被占用”，而不是仅仅说“内存不足”。
    *   `eslam-ahmed43`: 表示有兴趣解决此问题。
*   **争议焦点**: 核心在于错误报告的清晰度与准确性。
*   **当前状态**: **Open**。虽然用户找到了原因，但提升错误提示质量的讨论仍在继续。

**4. Issue [#50151] 推荐特性：GPU 间负载均衡的 MoE 路由**

*   **核心议题**: 用户 `tniemine` 提议并展示了一个 MoE 专家间的负载均衡路由特性。通过引入 `capacity_factor`，将 Token 均匀地分配到各 GPU 专家上，以牺牲微小精度换取显著的性能提升。
*   **核心观点**:
    *   `tniemine` (提案者): 提供了一个清晰的性能对比表格，证明该特性在 DeepSeek-V3 上能提升吞吐量，同时 GSM8K 准确率下降有限。他提议将此作为新特性加入。
*   **争议焦点**: 无。这是一个积极的建设性提议。
*   **当前状态**: **Open**。被标记为 `feature request` 和 `rocm`，正等待社区及维护者讨论。

**5. Issue [#50095] NVIDIA DeepSeek-V3.2 / GLM-5.2 融合注意力绕过了 DCP 处理**

*   **核心议题**: NVIDIA 提供的 DeepSeek-V3.2 和 GLM-5.2 模型代码中，其定制的融合注意力 `forward` 函数跳过了 vLLM 标准的深度上下文并行 (DCP) 处理逻辑，导致多 DCP 场景下的正确性问题。
*   **核心观点**:
    *   `foraxe` (报告者): 非常专业地指出了三个具体问题：错误的 KV 槽检查、未考虑 DCP 几何信息的稀疏索引器、以及缺少部分注意力结果的合并。
*   **争议焦点**: 无，这是一个清晰的技术 Bug。
*   **当前状态**: **Open**。此问题提醒社区，当使用 NVIDIA 提供的专有模型代码时，需要仔细审查其与通用框架特性的兼容性。

### 🛠️ 重点技术变更

1.  **[PR #50088] [MoE] Latent-MoE runner, fused MoE tail, SituGLU activation and single-group top-k routing**: 这是对 MoE 基础架构的一次扩展。它为未来可能出现的新型 MoE 变体（Latent-MoE）铺设了道路，引入了新的激活函数 (SituGLU) 和针对性的 Top-K 路由优化。虽然目前不注册新模型，但它为后续模型集成提供了关键的基础构建块。

2.  **[PR #50168] [RFC] Add LUT-B quantization accuracy prototype**: 这是一个具有前瞻性的工作。它针对 NVIDIA 的下一代 Rubin 架构的 LUT-B (Look-Up Table-Based) 权重压缩，建立了一个逻辑参考模型进行正确性评估，并提供了从现有量化格式（如 NVFP4）重打包的路径。这项工作能在实际 GPU 可用之前，就评估新量化方案的精度。

3.  **[PR #49612] [KV Connector] Support NIXL heterogeneous P/D block sizes for hybrid models**: 这是一个重要的基础设施改进。在 P/D (Prefill/Decode) 分离部署中，混合模型（如 Mamba）的不同层（Attention vs. SSM）可能会有不同的块大小。此 PR 移除了之前强制要求所有块大小统一的严格限制，允许 NIXL 在这种异构场景下正常工作，为更广泛的 P/D 分离混合模型部署铺平了道路。

4.  **[PR #50195] [Frontend] Add stateless /v1/responses/render endpoint**: 此 PR 引入了一个无状态的 Prompt 渲染端点。它将请求的 Prompt 生成逻辑从有状态的服务循环中剥离出来。这使得高延迟的渲染任务（如包含大量历史消息或复杂工具定义的对话）可以卸载到单独的服务或进程中处理，从而提升主推理服务的 GPU 利用率和响应速度。这是对 Serverless 架构和微服务设计的重要补充。

5.  **[PR #49757] [BugFix] Stop dummy runs from writing mamba state through stale block-table rows**: 这是一个精妙且关键的 Bug 修复。它揭示了在生产环境中可能发生的一个隐蔽问题：用于启动预热或填充的“哑运行”可能会通过失效的块表行，覆写真实用户的 Mamba/SSM 状态。此 PR 通过在被移除的行和哑运行的行上写入零值，修复了潜在的静默数据损坏，对保证混合模型的推理正确性至关重要。
