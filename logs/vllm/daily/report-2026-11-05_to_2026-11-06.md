#### ① #65941 [MM] Nemotron VL 使用 CV-CUDA 在 GPU 上 resize（评论最激烈）
- **正方（作者 brandonpelfrey，NVIDIA 员工）**：CV-CUDA 可将视频 TTFT 降低 24-49%（GB300/B200/H100/H200/B300 多 SKU），精度在噪声范围内（MMMU-Pro、Perception Test 多数据集验证），scratch buffer 上限 512MiB 并在 profile run 中预留。
- **反方（milesial）**：直接指出 **CV-CUDA 的 workspace 实际上依赖帧数与帧尺寸**，并给出了 1024×1024 与 768×768 混合输入下 510MiB + 576MiB 双份保留导致约 1,086MiB 的 OOM。`cvcuda.clear_cache()` 只清对象缓存，**不释放原生 workspace**。
- **争议焦点**："上限 512MiB 并在 profile 中预留"的声明是否成立。milesial 在 H100 上复现了 OOM，作者尚未回应。
- **状态**：open，且已因冲突需 rebase。

#### ② #59124 ROCm FlyDSL FP8 prefill 后端（40 天长评审，已合并）
- **simondanielsson 的评审**：建议做成独立 prefill 后端、接入现有 attention 正确性测试、若想默认开启需更大 benchmark sweep。
- **ChuanLi1101 的三条硬核技术建议**：①quantizer grid 按最大 tensor 大小取，V 更小会导致越界指针；②每次调用都分配临时 buffer，短输入有约 50µs 开销；③当选后端时应直接禁用 ASM FP8 prefill，而非依赖元数据缺失来绕过。
- **作者的响应**：改为独立 `ROCM_AITER_FLYDSL_FP8` 后端并继承 `AiterFlashAttnPrefillBackend`（无法处理的输入回退 BF16）；对越界指针做了 per-program trip count 与 `start < N` 守卫并新增边界测试；**明确保留 opt-in**，"短 prefill 收益小，FP8 精度需要更长上下文评估"。
- 结论：opt-in 落地，**默认仍走原路径**。

#### ③ #64352 直接重载时 MoE padding 归零（已合并）

### 🔥 热门话题与趋势分析

**1. ROCm 性能优化进入"按 kernel / 按 shape / 按 XCD"的精细化阶段**
Fangzhou-Ai 的 MiniMax-M3.1 系列（#65478/#65481/#65530/#65267）展示了成熟的性能工程方法论：从 profiler 定位具体 kernel 发射数、到 roofline 计算、到按 XCD 分层、再到 GSM8K + SPEED-Bench 双 A/B 验证、最后诚实报告非目标 shape 的回归。这是 AMD 侧优化质量的显著提升。

**2. AITER 已成为 AMD 优化的"事实标准库"**
本周多条 PR（#65992/#65858/#65898/#65899/#66036/#65937）都直接依赖特定 AITER 版本或 aiter PR（如 #7461、#7017、#6520）。**这带来版本锁定风险**：多处明确"fallback to Triton when aiter lacks the kernel"、"draft until aiter merges"。

**3. 量化是跨平台交叉最多的领域**
MXFP4/MXFP8/NVFP4/INT4/W4A16 在 MiniMax-M3、DeepSeek-V4.1、Qwen3.8、gfx942/gfx950/gfx1151 上各自有独立路径。**Quark（#65918）与 compressed-tensors / ModelOpt 的 KV scale 加载问题（#65944、#65946）** 说明量化格式的"静默降级"仍是最常见的问题类型。

**4. 权重重载 / RL 场景成为独立热点**
#65897（B-preshuffle 在 kernel 内部重做）、#64352（MoE padding 归零）、#66002（直接重载的 opt-in 协议）、#65914（统一 `finalize_model_weights`）共同构成 RL weight sync 主题。

**5. 挂起/静默错误类 Issue 集中在 AMD 平台**
#65952（TP8 + MTP 挂起）、#65925（MI355X memory fault）、#65919（Ray 环境变量）——都是"配置组合正确但运行时失败"的类型，与 NVIDIA 侧本周期 Issue（#65868 MRV2 KV OOM、#65944/#65946 KV scale 未加载）性质不同：**AMD 侧更多是与 ROCm 运行时/驱动交互的稳定性问题**。


### 🛠️ 重点技术变更

#### 1. #59124 ROCm FlyDSL FP8 Prefill 后端（已合并）
**影响**：为 Kimi-K3 在 MI355X 上提供 opt-in 的 FP8 prefill 路径，TTFT p90 −15.8%、ITL p90 −8.7%（TP8/DCP8，c48 agentic replay）。**架构意义大于单点性能**——它把 MLA prefill 后端从原来的单体 `ROCM_AITER_FA` 拆出独立可插拔后端，并接入 `PREFILL_BACKENDS_TO_TEST` 正确性套件。后续所有 MLA prefill 优化都可能沿用此模式。

#### 2. #65992 HIP Mega-MHC（DeepSeek-V4.1 fused mHC seam）
**影响**：把原来 AITER 的**两次 Triton 发射**改为单次 HIP 发射，且覆盖 #59802 中侧流的 gate。在 gfx950 上，4096 tokens 的 seam 从 140.8µs → 95.9µs（**降 32%**）。这在 DeepSeek-V4.1 的 decode 路径上会累积（每 decoder layer 2 个 seam + DSpark draft 的 seam）。数值不是 bitwise 相等（fp32 求和顺序不同），作者用"新残差必须在 float64 参考的 1 个 bf16 ulp 内"作为判据。

#### 3. #65918 Quark MXFP4 MoE 激活旋转
**影响**：这是 **Quark 量化与 ROCm/AMD 生态的关键接合点**。Online Hadamard 旋转是 MXFP4 量化保精度的标准技术（`(xH)(wH)^T = x w^T`），但 vLLM 的 fused MXFP4 MoE 会**内部量化**第二次 GEMM 的输入，导致旋转失效。该 PR 的做法是**拒绝 fused kernel**、改走 emulation experts，代价是性能，但保证正确性——并在多处显式 raise 而非静默路由。**这反映了 vLLM 在量化正确性上"宁慢勿错"的正确取向**。

#### 4. #64352 + #66002 RL 直接重载体系
**影响**：这两条合并/新开 PR 共同构建了 **RL 场景下权重热更新的安全网**：MoE expert padding 在重载前归零 → 保证后续后处理与 cold start 位级相同；模型通过 `SupportsDirectReload` 协议声明是否已验证，未声明的模型**每次更新打一次警告**；三种"运行时检查看不到的 bug"组件直接拒绝。这是 RL + vLLM 组合从"能跑"到"可信"的重要一步。

#### 5. #63364 ROCm int4 skinny GEMM 编译单元拆分
**影响**：9-arch wheel 冷构建 **52% 时间削减**（1263s → 600s）。对 CI 与用户自编译体验是立竿见影的改进，且无任何 kernel / dispatch 变更。fxmarty-amd 的 5-PR 系列（#62717/#63364 + 其他 3 条）合计把 9-arch 构建从 1263s 降至 472s（**−63%**），是典型的"工程基础设施投资"。
