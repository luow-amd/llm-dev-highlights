## 💬 高热度讨论分析

### 1. #56790 — RDNA3 fused MoE gated-activation 假设（7 条评论，已关闭）

**核心议题**：RDNA3 `wna16` 路径把激活缓冲区按 `N_gate_up // 2` 分配，隐含 gated activation 假设；非 gated 的 `relu2_no_mul` 在 CUDA graph 捕获时触发 `336 vs 672` 断言。这是 #44489（online-FP8 路径同类问题）在 RDNA3 上的翻版——但症状相反：#44489 过度分配导致 OOM，本问题分配不足导致 shape 断言。

**观点与立场**：
- **报告者 Fenstone-Markit**：提供完整复现、根因定位和一行修复补丁，并验证 4×RX 7900 XTX TP=4 可正常服务。同时指出持久解码缓冲与 fallback 路径已"漂移"，只有前者有问题。
- **gokay-ai**：主动认领，但随后核查 `main` 发现 `rdna3_moe.py` 已用 `activation.is_gated` 正确分配，判断为 #55522 模块化迁移前的旧路径，遂撤回重复 PR。
- **报告者回应**：确认 stale，但补充**关键运营提醒**——AMD 已发布的 `rocm7.14.1_rdna` 镜像仍带迁移前 dispatcher，其他 RDNA3 用户会持续踩坑，需一行本地补丁等待镜像更新。

**结论**：上游已修复，Issue 关闭；争议焦点转向**发布镜像与 main 的版本落差**如何治理。

### 2. #56830 — 启动内存 profiling 断言与 GPU 共租（3 条评论，open）

**核心议题**：`Worker.determine_available_memory` 在 profiling 后空闲内存**增长**时断言失败。作者 PeganovAnton 系统梳理三类场景：独占离散 GPU（不触发）、离散 GPU 有共租进程释放内存（触发）、**统一内存/集成 GPU 无任何共享也触发**（如 DGX Spark GB10）。

**观点与立场**：
- **作者**：认为该 guard 基于代码注释中的假设（"其他进程 profiling 期间不改变内存占用"），在集成 GPU 上任何主机进程的内存波动都会误触发，与文档宣称的 GPU 共租支持矛盾。
- **hclsys**：指出 #55828 已在途修复——用 NVML 的**本进程设备内存**替代设备级空闲内存差值，仅在设备级路径保留断言。并实测 DGX Spark GB10 上 `NvmlCudaPlatform` + `is_integrated_gpu()=True`，`nvmlDeviceGetComputeRunningProcesses` 能正确上报自身 PID，而 `nvmlDeviceGetMemoryInfo` 确为 `NotSupported`。
- **hclsys（第二次实测）**：用**完全没有 CUDA 上下文的 CPU churner**（`bytearray(8GiB)` 反复分配释放）证明仅主机分配即可触发断言；打上 #55828 后扰动被如实上报而非 abort。

**争议焦点**：断言是否应保留（作为共租误用检测）还是应改为报告性指标。当前 #55828 的"双路径"方案获得实证支持。

### 3. #48498 — Gemma3n sparse GELU Triton kernel（7 条评论，已合并）

### 4. #52228 — 自适应验证的接受率估计（6 条评论，已合并）

**核心议题**：在此之前自适应验证仅用于带 confidence head 的 DSpark；本 PR 用一个在线接受率估计器（特征为 `logit(max q)`，即草稿分布最可能 token 的对数几率）将能力扩展到**所有基于 draft model 的 speculator**（MTP、EAGLE3、DFlash 1&2）。

**观点与立场**：

**结论**：扩大了自适应验证的适用范围，同时明确"基座模型注意力后端必须支持变长验证"这一前提。

## 🛠️ 重点技术变更

### 1. #56893 — DeepSeek-V4.1 全 KV 走 MXFP8（已合并）
FlashMLA 为 V4.1 提供专属 paged record：数据行 512B fp8 e4m3（**含 RoPE 维度**），scale 行 16 个 UE8M0（每 32 维一个，即 MXFP8），每 token 528B（V4 为 584B，**小 9.6%**），TMA stride 512B。由于 `block_size` 必为 32 倍数，V4.1 每页恰为 512B 倍数，"V4 record 所需的 padding 消失"。仅限 SM100（SM90/ROCm/FlashInfer SM120 保持 V4 record），且**无需新 cache dtype 或 flag**——`fp8_ds_mla` 随架构解析。这是对 KV cache 内存布局的精细优化，直接扩大可用 KV 容量。

### 2. #56633 + #56513 — mHC post 融合（NVIDIA 与 ROCm 双实现，均已合并）
DeepSeek-V4.1 在每个 sublayer 接缝处执行 mHC post + 下一个 sublayer 的 delayed pre。NVIDIA 侧 `mhc_fused_post_pre_delayed_tilelang` 在寄存器内计算更新后的残差并直接喂给 pre-norm GEMM，消除中间读回；ROCm 侧通过 `mhc_fused_post_pre_gemm_sqrsum` AITER 内核达成同等效果。两者均在 Engram 注入处**不能融合**（Engram 需读取 post 与 pre 之间的残差），保留分核路径。ROCm 版 GSM8K strict 0.9742 vs 基线 0.9704。

### 3. #52228 — 自适应验证接受率估计（已合并）
通过在线估计器预测草稿 token 接受概率，使 MTP/EAGLE3/DFlash 1&2 均可用自适应验证，不再依赖 confidence head。AUC 分析显示估计器在深草稿位置优势明显。扩展了 speculative decoding 的适用面，并明确了"基座注意力后端需支持变长验证"的前置条件。

### 4. #51084 — Proton CUDA graph 归因（已合并）
为默认 model runner 增加 Proton 图重放归因，使重放的 kernel 保留捕获上下文（含 Triton 启动元数据）。引入 `WorkerProfiler.capture_cuda_graphs()` 钩子，并**明确拒绝** `periodic_flushing`（后端与 wrapper 各自持有 phase 所有权会冲突），为后续 #56895 的异步周期 profiling 铺路。njhill 亲自重构封装后合入。

### 5. #54965 — ROCm W4A16 零点打包（已合并）
`RDNAHybridW4A16LinearKernel` 加载时把非对称零点展开到激活 dtype，造成 4x DRAM 流量。改为保持 packed int4（每个 int32 内 8 个），gemma-4-31B TPOT **-26.4%**。社区在 RX 9070 XT 16GB 上复现一致结果，体现了 vLLM 对**加载期内存布局 vs 运行期带宽**权衡的优化思路。

## 💡 值得关注的问题

1. **#56945（open）— ROCm 镜像默认配置严重次优**：`rocm/vllm` 不设 `VLLM_ROCM_USE_AITER`，导致 AMD 卡片开箱即用损失高达 3.7x 吞吐。这不仅是性能问题，更是**用户体验与 AMD 硬件价值主张**问题，建议优先在镜像/文档层面解决。

2. **#56790 的余波 — 发布镜像与 main 的版本落差治理**：AMD 官方 `_rdna` 镜像仍带预迁移 dispatcher，RDNA3 用户会持续遇到已修复的 bug。是否需要为发布镜像建立"已知落后差异"清单或加速镜像发布节奏，值得社区讨论。

3. **#56830（open）— 内存 profiling 断言与统一内存架构**：GB10 等统一内存设备上，纯 CPU 分配即可误触发启动失败。应推动 #55828 尽快落地，并评估断言是否应降级为告警。

4. **#56900（open）— Qwen1.5-MoE torch.compile 退化输出**：`VLLM_COMPILE` 下产生 `'the\nthe\nthe...'` 退化文本，关闭 compile 正常。CUDA graph、compile cache、custom_ops 均不影响，症状稳定可复现——属于**静默正确性缺陷**，风险等级高。

5. **#56887（open）— moe_wna16_gemm 非确定性**：split-K 部分和用 16-bit `atomicAdd` 合并，非 run-to-run 确定。对需要可复现性的训练/评测场景是硬伤。

6. **#56785（open）— HiSparse MLA indexer 默认配置崩溃**：GLM-5.3-Flash 在 GB200 NVL4 上 5/5 启动失败，`logical_topk_ready` 在 capture segment 内记录但在 eager break 后等待，属默认配置崩溃。

7. **#56829（open）— cu129-nightly 镜像依赖错配**：torch 2.14.0+cu130 与 torchvision/torchaudio cu129 混装，`vllm serve` 直接 `operator torchvision::nms does not exist`。发布工程问题，影响所有 nightly 用户。

8. **#56772（open）— canonical MLA+DSA 次级传输 TP 依赖行大小**：`canonical_layout: true` 声称拓扑无关存储命名空间，但次级传输仍用完整对齐主层级行，导致 P2P 连接校验或文件系统提升失败。涉及 KV 卸载架构的一致性承诺。

9. **AITER v0.1.22 升级路径**（#56885）：需确认 ROCm 10/TheRock 分支的处理策略，以及 `aiter.ops.triton.*` 重组 shim 的长期稳定性。
