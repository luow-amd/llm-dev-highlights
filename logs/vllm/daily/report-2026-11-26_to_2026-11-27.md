### 🎯 AMD/ROCm 生态相关动态

本周期 AMD 生态动态极为丰富，按主题归类如下。

#### 1. 性能回归修复（高优先级）

**Issue #70172 / PR #70220 — 混合精度 KV cache 导致 14× 解码退化**
- **问题**：MI300X 上 `--kv-cache-dtype fp8 --kv-cache-dtype-skip-layers 0`（Qwen2 第 0 层保留 BF16 以修复 key bias）使 decode 从 4.55 ms/token 劣化至 63 ms/token。根因为跳过层导致所有 FP8 层的 block 被 stride-padding，使 `has_native_kv_cache_layout()` 检查失败，回退到 Triton，禁用 ROCm 自定义 paged attention。
- **修复**：PR #70220（Super262）让 CDNA HIP paged-attention reader 接受 LBHNC 布局的 stride-padded block，实测 32K 单请求 decode **15.93× 加速**（65.69 → 4.12 ms/token）。这是本周期单项收益最大的 ROCm 修复。

#### 2. MORI 专家并行（EP）修复

- **Issue #70128 / PR #70129**（raviguptaamd）：MORI EPv1 把 `world_size × max_num_tokens` 整个接收缓冲交给 experts，即使实际收到的 token 很少，`TritonExperts` 也会对全容量计算激活和 top-k 归约。MI355X 上 C=8 吞吐从 436 tok/s（16K buffer）劣化到 1436 tok/s（4K buffer）。修复方式是引入 `mori_recv_rows_bound()`，对接收视图切片并将越界行 expert id 置 -1 / 权重置 0。
- 该 Issue 的表格还揭示：单主机 EPv2 默认路径比 EPv1 慢 3.3–13×，尚未定位。

#### 3. 大型模型性能追踪

- **Issue #70158**（xaguilar-amd）：Mistral Large 4（1T-A52B，block-FP8，TP8 on 8×MI325X）性能优化总表。列出 indexer cache 迁移、`top_k_per_row_decode` 不拆分行（TPOT −27% @1K/C1）、AITER FlyDSL multi-block top-k（TPOT −27% @1K/C1）、AITER decode top-k 按 (arch, CU) 分带等。多数工作作为 stacked PR 落在 main 与 AITER 上。

### 💬 高热度讨论分析

> 注：周期内最热烈的几条讨论集中在设计取舍，其中多条以实质性技术审阅为主。

#### 1. PR #70131 — GLM-5.3-Flash KDA ReplaySSM 解码/验证内核（5 条实质评论）

- **议题**：通过 `--use-replayssm`，每请求只保留 1 个 recurrent-state checkpoint 加短 u/k/g 环（32 行、窗口 16），KDA 层每个 decode/verify step 走单个融合 kernel。B200 TP4 上 c1–c64 输出 +1.05–1.10×，KV 内存降约 20%。
- **tomasruizt 的观点**（4 连问）：
  1. 基准关闭了 prefix caching，但生产环境的长 agentic 工作负载必须支持，否则每次交互都要重新 prefill 50 万 token；并指出 "Prefill 已写入完整状态，只有 decode 期间结束的块需要 materialize（可参考 Mamba2 的 `replayssm_materialize()`）"。
  2. `check_supported()` 把请求数卡在 256，而 vLLM 在 B300 上 `max-num-seqs=1024` 是默认值，会直接报错——是否可放宽。
  3. Mamba2 的 ReplaySSM 环放在单一 Mamba page 内，而本 PR 在 spec-decode 时分配第二个页，建议对齐 Mamba2 模式。
  4. 建议让 latency-specialized decode 的 KDA 阶段委托给 ReplaySSM kernel，以免低并发下 `--use-replayssm` 反而变慢。
- **gcanlin 的追问**：要求与 #66551 做 micro bench 对比。
- **作者回应**：作者在多处表示"考虑"，但报告中未见最终合并前的明确答复；评论主线反映的是**功能正确性与生产可用性（prefix caching、max-num-seqs、内存布局一致性）**的阻力，而非性能数字本身。
- **状态**：Open。

#### 2. PR #70136 — 缓存 vision encoder 中插值后的 `get_abs_pos` embedding（4 条实质评论）

- **议题**：在 `ImageEncoderViT`、`DeepCLIPVisionEmbeddings`、`Step3VisionEmbeddings` 中用共享的有界 `InterpolatedPosEmbedCache` 缓存 bicubic-antialias 插值结果。Ascend 910 上 SAM `64→48` 从 0.410 ms 降到 0.0011 ms。
- **DarkLight1337 的核心担忧**：GPU 缓存是推理时惰性增长，`profile_run()` 测不到，请求若用 `mm_processor_kwargs` 引入新分辨率，KV cache 占满剩余显存后可能 OOM。
- **作者方案迭代**：先回应"三个 encoder 的目标分辨率是已知的"，再提出改为 **`process_weights_after_loading()` 中静态预计算**，`forward()` 严格只读，对未知尺寸回退到未缓存 `F.interpolate`；最终按内存预算（16 MiB/模块实例）而非条目数限容，并补齐单元测试。
- **状态**：Open，已按 reviewer 反馈修改。

#### 3. PR #70245 — KV Offload：将 hint 的前缀预取进 GPU KV cache（3 条评论）

- **议题**：请求可在 KV-hint envelope（#53421/#53423）中携带前缀 block hash，连接器在请求到来前完成 reserve/load/publish，使 prompt 到达时命中普通 prefix cache。V100-32GB 上 16k 前缀 1.428 s → 0.369 s。
- **作者自陈的争议点**：与 #58198（in-engine 方法）与 #59708（通用 `vllm.copy_to`）在 `block_pool.py` 和 offloading connector 上重叠，**希望审阅者决定保留哪个接口**；并已删除三个无人调用的 `KVCacheManager` facade。
- **状态**：Open，waiting for review。

#### 4. 已关闭 Issue #48504 — GDS 文件系统 KV-cache offload RFC（8 条评论）

- **议题**：把 GDS 作为完整 `FilesystemSpec(OffloadingSpec)`，而非 read-only 特例；将 GPU block→pointer 解析从 `cpu/gpu_worker.py` 上移到 `offloading_connector/worker.py` 共享。
- **orozery 的分步路径**：① 共享 worker 代码迁移（`OffloadingWorker.submit_*` 改收 GPU 指针）→ ② 完整 load/store 的 `FilesystemSpec` 与插件化 transport → ③ NIXL GDS → ④ flag 控制的 read-only MultiConnector 组合。作者据此更新 RFC。
- **结局**：因 90 天无活动被 stale bot 自动关闭，但讨论本身已形成清晰的未来路线（代码归属与 #44865 的协调点被显式记录）。属于**"已设计但未实施"**的活跃方向。

### 🛠️ 重点技术变更

**1. PR #70004 — HY4 在 ROCm 上补齐 `fp8_ds_mla` + ShardQ + iHC SP（已合并）**
- 关键点：AITER 的 Triton sparse MLA kernel 已接受 attention sink，但 vLLM 在 `fp8_ds_mla` 路径上从未传参，导致 `--kv-cache-dtype fp8_ds_mla` 启动即 assert。PR 修复 sink 传递、让 HY4 Flash 的滑窗层在 ROCm 上 opt-in `fp8_ds_mla`、为 sparse MLA 加 ShardQ（按 local head 数门控，TP2/TP4 会因 kernel tile 已满而变慢，故仅 <16 head 启用）、并把 iHC SP 移植到 AMD HY4 模型。TP8 下 128K prefill ShardQ −19%、iHC SP −21%，GSM8K 与 main 相差 0.1pp。**这是 AMD 平台上 MLA 稀疏后端能力对齐 NVIDIA 的重要一步**。

**2. PR #70220 — CDNA paged attention 支持 stride-padded LBHNC（对应 Issue #70172）**
- 混合精度 KV（部分层 BF16、部分层 FP8）会因 block 对齐被 padding，使 `has_native_kv_cache_layout()` 失效，全体退回 Triton。PR 让 HIP writer 与 CDNA reader 在 metadata 中记录 LBHNC 布局，并允许 reader 使用给定的 block stride，仅对 contiguous 的 per-layer view 走 HIP。MI325X 32K 单请求 decode 从 65.69 ms/token 降至 4.12 ms/token。**该修复直接解开了一个用户可见的 14× 性能陷阱**。

**3. PR #67218 — MoRIIO WRITE 模式未释放预填块**（已合并）
- 在 WRITE 模式下，decode 侧释放 transfer 或请求复用已结束的 transfer id 时，prefill 侧会一直持有完成请求的 KV block 直到进程重启。PR 保证每个此类请求都能拿到完成报告。MI355X + Qwen3-0.6B 上，32/32 早期释放请求在 main 上全部滞留，PR 后 0 个；GSM8K 精度不变。**这是 P/D 分离生产环境的内存泄漏修复**。

**4. PR #67064 — NIXL P/D 在 Mamba prefix-cache checkpoint 处截断 prefill**（已合并）
- 问题：Mamba `align` prefix caching 下，P 计算 N-1 token 并发送运行态，但 C（prompt checkpoint）留在 P，导致后续本地 turn 在 D 上重算整个历史（#63610 实测 0/123,032 prompt token 命中）。PR 让 P 把 prompt 截断到 checkpoint，D 自行重算 `[C, N)`；哈希与 EAGLE/MTP block drop 复用 core 的 `get_mamba_prefill_checkpoint_position`。**这是长对话 P/D 分离能否命中的关键机制**。

**5. PR #70148 — W4A16 线性层通过 AITER/hipBLASLt 跑在 RDNA（gfx1151）**
- 与 #63280（AITER Triton `gemm_a16w4`，gfx942）互补，二者在对方硬件上 decline。gfx1151 上 gsm8k 精度在噪声内、吞吐 1.35×，且开启了新的 RDNA 量化路径。**表明 vLLM 的 AMD 后端正在从 CDNA 向 RDNA 消费级/工作站扩展**。
