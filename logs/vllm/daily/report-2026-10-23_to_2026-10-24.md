## 💬 高热度讨论分析

### ① #63343 — SM120 上 adaptive verification 被拒绝（5 条评论，DSv4.1 生态）

- **核心议题**：`Lei-010` 报告 8×RTX PRO 6000 Blackwell（SM120）上 `enable_adaptive_verification=true` 在 `profile_cudagraph_memory` 阶段确定性失败，根因是 `DeepseekV41IndexerBackend` 硬编码模型绕过后端选择器，直接撞到 `supports_device_cpu_query_lens_mismatch()` 的 device-query-lens 门控（只开放 SM90/SM100）。
- **多角度观点**：
  - `SebastianGode`：在 SM120 上复现。
  - `adenzhou1350`：**从 vendored DeepGEMM pin 源码出发**指出当前默认 pin 的 SM120 metadata 分支其实已接受 varlen `indices`（`next_n==1`，contiguous int32），paged-logits dispatcher 也显式允许 varlen，因此建议先验证 native varlen 路径再扩展能力门控。
  - `Lei-010`：连续 **三轮生产 A/B 数据**：（1）static batch-size schedule（`num_speculative_tokens_per_batch_size`）已捕获大部分收益，且 `VLLM_USE_V2_MODEL_RUNNER=1` 让结果更干净；（2）probabilistic draft + block rejection pair 在 batch-size schedule 之上再 +2–3%，而 `[[1,8,3],[9,1024,2]]` schedule 反而无益；（3）在 spec-decode 栈上叠加 scheduler knobs 均无收益，`--max-num-batched-tokens 8192` 在 c64 下 **−40% 崩溃**，`--async-scheduling` 用 mid-concurrency 换高并发（c8 −4.8%，c64 +1.3%）。
- **争议焦点**：device-query-lens 能力门控的覆盖范围应由谁（模型侧硬编码 vs 后端选择器）决定；SM120 是否已有可用的 varlen 路径只是没被启用。

## 🛠️ 重点技术变更解读

### 1. MI350P（128 CU gfx950）启用路径（#63340 + #63341）

**技术要点**：mono decode kernel 采用 "一个 CU 一个 resident CTA" 的网格设计，`BLOCKS` 必须等于 GPU CU 数。MI350P 的 128 CU 触发 `assert BLOCKS < DOWN_TASKS <= 2*BLOCKS` 失败（320 task / 128 CTA 需要 3 pass）。#63341 通过 `resolve_tiling(arch, cus)` 做架构选择、修复 JIT cache key 的 latent collision，并以 fail-closed 方式拒绝 MI350P，避免"静默构建出编译期断言失败的 grid"。

**影响**：这是 AMD 在 CDNA4 时代扩展 SKU 覆盖的关键路径。一旦 k-pass 分解完成，MI350P 可复用 MI35x 的全部 mono decode 优化，无需维护分叉分支。

### 2. ROCm 9-arch build 从 1263s → 472s（#63364 + #63365）

**技术要点**：通过 `-DWVSPLITK_INT4_LANE=N` 把单个巨型 TU 拆成多个 per-N_in 编译单元，每个单元用 `if constexpr` 只生成自己的 case；公共 API 放在小 TU 中按 `in_b.size(0)` 转发。同样的手段用于 `fused_muse_spark`（按 head_dim 64/128/256 拆）。**关键洞察**：单 arch build 不变（因为该 TU 不是瓶颈），9-arch build 才是收益来源——说明现代 GPU 编译的瓶颈在"多架构组合爆炸"，而非代码量。

### 3. NIXL 在 ROCm 上重新启用 `rocm_ipc`（#62827，已合并）

**技术要点**：NIXL 以 peer error handling 打开 UCX endpoint，旧 UCX pin 下 `rocm_ipc` 不 advertise 该 capability，读写回退到 TCP 模拟（或 #49251 的 host-staged pipeline，后者 `/dev/shm` 耗尽导致 decode engine 崩溃）。UCX v1.23.0-rc1（含 openucx/ucx#11977）新增 capability，`UCX_RMA_PPLN_ENABLE=y` 不再需要。额外设置 `UCX_ROCM_IPC_SIGPOOL_MAX_ELEMS=inf` 避免多请求 NIXL 读时 HSA signal 池耗尽。

**影响**：**MI355 上 256 MiB GPU↔GPU NIXL READ 从 0.48 GB/s（override 后 8.8 GB/s）提升到 60.9 GB/s**，1P1D GSM8K+NIAH 从 hung 变为 10/10 通过。这是 AMD P/D 分离可用性的基础设施级修复。

### 4. MoRIIO 传输契约 RFC（#63336）

**技术要点**：系统梳理 READ/WRITE 模式下的失败路径，指出三类问题——（a）READ 模式 prefill 固定 60s 后释放 block，decode 仍可能排队/正在读取；（b）READ batch 首个失败即判 FAILED，sibling 仍在 DMA 就释放 prefill；（c）WRITE finalize 失败释放源 block 但不通知 decode。RFC 提出统一的"KV 内存何时可重用"契约与 bounded failure 语义。

**影响**：这是**目前 AMD P/D 生态系统最关键的架构级 RFC**。MoRIIO 的失败语义若不确定，生产环境的 agentic 长上下文负载会面临静默数据损坏风险。

### 5. Muse Spark AITER MXFP4 per-slot 输出（#63290 / #63298）

**技术要点**：Muse Spark 的 MoE 在 top-k 加权求和前对每个 expert 输出做归一化，因此需要 `[T, top_k, H]` 的 per-route 输出。旧方案把输入复制 top_k（8）倍，在 60 个 MXFP4 MoE 层上做 8× 的量化、排序与 stage-1 计算。新方案通过 AITER `fused_moe(..., per_slot_output=buf)` 直接在 `[T, top_k]` 上路由，stage 2 改为 per-route writer，**route 输出 bitwise 不变**，TTFT −9~−12%，c64 吞吐 +10%。

**影响**：这是"消除算法层面的冗余计算"而非 kernel 微优化的典型案例，对 Muse Spark 这类**需要 per-expert 归一化**的模型架构具有普适参考价值。

## 💡 值得关注的问题

### 1. MoRIIO 正确性契约（RFC #63336）——**最高优先级**
KV 内存重用的失败语义尚未统一，READ 模式 60s 固定超时可能导致 decode 读到其他 request 的 KV 且 **MoRI 报告 success**。这属于静默数据损坏，生产环境不可接受。建议社区尽快就 RFC 达成共识并落地测试。

### 2. AITER 公共 API 治理
#63290 与 #63298 的讨论揭示了 vLLM↔AITER 的持续张力：短期需要在 pinned release 上工作，长期需要公共 API。当前多条 PR（#63392、#63409、#63272）依赖 aiter 未合并 PR 或未发布 release，**版本时序风险反复出现**。建议推动 AITER 建立更明确的 API stability 契约。

### 3. SM120 上的 adaptive verification 门控（#63343）
`adenzhou1350` 指出 vendored DeepGEMM pin 已有 SM120 varlen 实现，但 vLLM 的能力门控仍只开放 family 100。**这可能是"能力声明与实际 kernel 支持脱节"的系统性问题**，值得排查其他 backend 是否也有类似门控滞后。

### 4. 编译时间与 9-arch 矩阵
#63364/#63365 证明单 TU 可拖垮整个 build。建议评估其他后端（CUDA、XPU）是否有类似"千秒级 TU"，并考虑把 per-lane 实例化作为通用模式推广。

### 5. MI350P 的 k-pass 任务分解（#63340）
当前 MI350P 以 fail-closed 拒绝，实际启用需要重写 MoE down 与 attention `wo_b/wo_a` 的设备循环以支持最多 3 pass/CTA。**这是 AMD CDNA4 小 SKU 覆盖的关键阻塞项**，且验收标准明确要求"256-CU 部分 byte-identical"，实现需谨慎。

### 6. Kimi-K3 BF16 KDA 精度取舍（#58743 讨论）
`ChuanLi1101` 指出原 PR 缺少 matched FP32 baseline 与内存占用数据，`YukioZzz` 补充后（FP32 97.27% vs BF16 96.89%）合并。**这提示"opt-in 精度模式"应默认附带 matched baseline**，建议作为 review checklist 固化。

### 7. #41515 关闭但根因未明
kv_offload + HMA 的 assert 问题在关闭时仍无明确修复 PR 链接，且 `naveline67` 注释 assert 后卡 100% CPU。**建议社区确认是否有后续 issue 跟踪该根因**，避免"关闭即遗忘"。

### 8. RDNA 路径的精度与稳定性
#63383（gfx1151 attention 4.1×）、#63402（int8 lm_head）、#63396（gfx1250 W4A4 MoE 修复间歇性 garbage）显示 RDNA 性能提升显著，但 #63396 的"非 preshuffle 权重返回间歇性垃圾"说明**新硬件的 kernel 稳定性仍需更多 bitwise 验证**。
