**1. [Bug][ROCm] Issue #55452：AITER split-K workspace 在 CUDA graph 捕获阶段崩溃**

- **报告人**：stefanskiasan
- **核心问题**：ROCm + AITER 环境下，`--max-num-seqs` 超过 64 时启动在 CUDA graph 捕获阶段中止。AITER 的 split-K 中间 workspace 以 `hipStream_t` 为 key 注册管理（`SplitkWsRegistry`），eager 模式下首次查找会惰性创建条目，而在 graph 捕获期间则拒绝创建并直接抛错。vLLM 在捕获阶段从未调用 `aiter.opus_gemm_workspace_init()` 预热，因此当某个 shape 首次解析到 split-K tuned 条目时即崩溃。
- **关键细节**：并非用户自定义 tuning 表导致——AITER 自带的 a16w16（bf16）表中就存在该路径。
- **影响**：这是 ROCm 平台使用 AITER 时的启动阻断缺陷，需要 vLLM 在 graph 捕获流的正确位置插入预热逻辑。
- **状态**：open，尚无修复 PR；github-actions 已自动 CC AMD 相关维护者。

**2. [Refactor][ROCm] PR #55522：RDNA3 W4A16 MoE 迁移至 oracle/experts 架构**

- **作者**：JartX
- **核心内容**：将 RDNA3（gfx1100）W4A16 MoE kernel 从独立 quant-method 类迁移至标准的 oracle 后端 + experts 类模式（`WNA16MoEBackend.RDNA3` + `Rdna3WNA16Experts`），删除了 `rocm_moe_rdna.py` 和 `compressed_tensors_moe_wna16_rdna3.py` 两个专用文件。
- **附带修复**：原 `RoutedExperts` 子类不在 `intermediate_size_full` 类名列表上，导致 gfx1100 上 W4A16 MoE 模型加载崩溃（`KeyError: 'intermediate_size_full'`）。回归父类后修复。
- **行为变更**：非对称量化 checkpoint 回退到 Triton（原实现静默忽略非对称零点）；LoRA 回退 Triton 而非丢弃 delta；activation 层开始遵循 swiglu clamp/alpha/beta。
- **验证**：2× RX 7900 XTX（gfx1100）TP2 + CUDA graphs，Qwen3.6-35B-A3B-GPTQ-W4A16-G32 实测通过。
- **状态**：open，待 review。

### 💬 高热度讨论分析

**1. PR #55471：[NIXL] 本地失效 pull peer 元数据恢复**（评论数最多，存在争议）

- **核心议题**：当 pull peer 的本地 NIXL 元数据丢失而 Prefill 端仍然存活时，如何恢复通信而不误判对端死亡。
- **观点分歧**：
  - **xijiaat（PR 作者）**：在生产环境真实遇到传输失败事件后，提出应区分"单纯传输错误"与"生产者死亡"——只有在本机元数据确实缺失时才做恢复；不应将一次传输失败当作 Prefill 死亡的证据。同时强调 outstanding-read 保护与 handshake 顺序。
  - **YannikHinteregger（#50047 作者）**：质疑该失败模式在 vLLM 中是否能自然发生——Python 侧缓存与 NIXL native 元数据总是成对清理，不会自行漂移。建议将 #55471 的触发条件并入 #50047，并指出 maintainer（NickLucche/chaunceyjiang）倾向于由更上层（router）统一检测 engine 故障。
  - **xijiaat 的回应**：承认生产事件无法完整证明缓存漂移序列，但坚持应以积极方式修复潜在状态不一致；同意将修复并入 #50047，同时列出 4 项必须保留的行为约束（触发范围、pending 恢复、handshake 排序等）。
- **争议焦点**：修复应放在 NIXL 连接层、vLLM Python 层、还是 router 协调层？两个 PR 的合并方式与代码归属。
- **当前状态**：双方已达成初步整合意向，等待 maintainer NickLucche 裁决。

**2. PR #55430（含评论扩展）：Qwen3.8-Flash-Next tile-union QSA prefill 优化**

- **核心议题**：RTX 3070 Ti 上 AWQ kernel 的优化方案，是否可以用 `fma(q, scale, -zero*scale)` 代替 `sub.f16x2 + fma`。

### 🛠️ 重点技术变更

**1. PR #55119（合并）：GLM-5.3-Flash 的 EPLB（Expert Parallel Load Balancing）支持**

- 结合 `--enable-eplb` + `--eplb-config`（含冗余专家、异步更新），使 GLM-5.3-Flash 这类深层 MoE 模型在 TP 环境下通过专家负载均衡提升吞吐。测试命令覆盖 TP4 + async EPLB 场景，修复了 EngineCore 启动崩溃。

**2. PR #55299（合并）：DeepSeek-V4 稀疏索引 prefill workspace 的 -1 sentinel 播种**

- `combine_topk_swa_indices` 只写入每行有效前缀，其余列依赖 `-1` sentinel 配合 `topk_length`。调用者提供 workspace 的路径未做播种，多 chunk plan 时可能读取未初始化内存作为 KV 索引，在 CUDA graph 捕获阶段触发 illegal memory access。
- 修复覆盖 CUDA 主路径 + ROCm/XPU 变体的一致性修正（含 compressor_utils 已有同类修复的二次实例化确认）。

**3. PR #49410（合并）：Intel Diamond Rapids 原生 AMX-FP8 Attention**

- 引入 `AMX_FP8` ISA：QK 点积用 `_tile_dpfp8ps`、PV 用 `_tile_dpbf16ps` 硬件指令，避免现有 AMX 路径对 FP8 KV 先反量化再 BF16 MMA 的开销。自动选择逻辑为：FP8 KV-cache + 硬件支持时 `amx_fp8` 优先于 `amx`。
- 附带构建基础设施升级（Ubuntu 25.04 + GCC-15）与 GCC ICE workaround。
- 性能：Decode KV8K 1.58x→1.61x、Prefill Q128/KV128 0.30x→0.77x、Prefill Q512/KV512 0.56x→0.96x（相对 BF16 AMX 的加速比）。

**4. PR #53614（合并）：Kimi-K3 内部 prefix checkpoint——partial prefix caching + spec-decoding + connector restore**

- 在 #52789 基础上扩展：支持投机解码/Eagle block rewind、`prefix_match_unit < Mamba block size` 的部分前缀缓存、以及经 MooncakeStore 等 KV connector 恢复的 checkpoint block。
- Cache manager 与 FlashKDA worker 共享同一套 checkpoint 有效性规则，仅在 worker 可写时分配和哈希 checkpoint block；对齐的 partial checkpoint 从 provisional boundary 重新 key 到 FlashKDA 实际导出的 state position。

**5. PR #55528：[Bugfix] V3.2 sparse MLA 的 packed block stride 对齐**

- 针对 #55431/#55434 的深层几何问题：allocator 按逻辑 page bytes 求和，未考虑不同 segment 的物理行宽（metadata 656/352/132 字节）。物理行对齐要求不满足时，BLHNC 布局会导致稀疏行索引越界。
- 修复方案：声明 `block_stride_alignment_bytes`，将总 stride 对齐到各 segment 行宽的 LCM，并贯穿分配、容量检查、auto-fit 和 PP 重规划。
- 对齐后的容量代价约 0.17%~0.49%（按 synthetic inventory 估算），BF16 MLA 无额外代价（天然对齐）。

### 💡 值得关注的问题

**1. VLLM_KV_CACHE_LAYOUT=BLHNC 的安全网缺失（#55431 + #55434 系列）**

该案例暴露了三个层面的防御空白：后端声明缺失 → 布局解析通过；校验函数对"非 block-compact"以外的异常布局不够挑剔（只看 is_block_compact，不检查实际对齐）→ 布局校验通过；最终到内核绑定时才以 assert 失败。跨层 invariants（布局合法性、行对齐、page 几何、connector 元数据）缺乏系统性建模，是此类 bug 反复出现的根因。建议从长远角度考虑统一 KV cache 几何契约的声明与校验机制。

**2. DeepSeek-V4-Flash TP=16 on SM120 的"幽灵检查"（#55526）**

- 检查函数 `has_flashinfer_sparse_mla_sm120_config(8,128)` 在 Python 直接调用返回 True，但在 Ray worker 内 `DeepseekV4FlashInferSM120Attention.__init__` 中执行却抛错。TP=8 正常、TP=16（rank 上 8 q-heads）失败。
- 目前无评论，但该复现路径若真实存在（可能是 flashinfer 内部 lazy import 或环境差异），将直接影响 Ray 多节点 + Blackwell 消费卡用户。

**3. Mamba2 的 deterministic serving（#55524 RFC + #55525 实现 PR）**

NolenLiang 提出 SSD（prefill/chunked scan）与 SSU（decode recurrent）两套 kernel 数值不 bit-identical，导致调度影响输出。提供大量 kernel 级证据后给出 opt-in 的 `--mamba-exact-replay` 方案。这是将"batch-invariant/deterministic serving"从口号落地为工程机制的尝试，与 RL 训练-推理对齐（RLHF 中 trainer 用 chunked scan 评分、采样用 recurrent 解码）直接相关。值得 RL 和 hybrid model serving 方向的关注者跟进。

**4. KV offload 在 NVIDIA Confidential Computing 下的体系性不可用（#55428）**

`cudaHostRegister` 在 CC 模式被禁用是 NVIDIA 文档明确写出的限制，但 vLLM 所有内建 offload 路径均依赖它。对 TDX/H200 CC-On 用户群体而言，KV offload 在到达实际传输前就崩溃。michaelmanly 的追问也侧面体现了 CC + vLLM 在生产环境中的实际部署痛感，这是一个被低估的部署场景。

**5. 老 RFC #33314 的关闭暴露量化方法层重构推进困难**

"Decouple kernels from checkpoint layout"这一主题讨论了 7 个月、涉及多位核心维护者（mgoin、LucasWilkinson、tjtanaa），最终因 90 天无实质活动被自动关闭。同期 #53462（SM110a 上 GDN MTP cubin 缺失，后经 PR #53835 合入修复）与 AWQ/NVFP4 kernel 的各种碎片化问题，连续指向同一个长期架构债——kernel 选择被 checkpoint 格式/硬件 arch 的隐式耦合所牵制。这类结构性重构需要专门立项和专人推进，否则会在自动关闭流程中被反复淹没。
