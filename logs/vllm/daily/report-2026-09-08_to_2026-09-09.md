#### 1. RDNA4 FlyDSL 原生加速系列（重大新方向）

这是本周期最值得关注的 AMD 技术动向：以 `big-yellow-duck` 为代表的贡献者围绕 AMD RDNA4（gfx1200/gfx1201）提交了一系列 **vLLM 自有 FlyDSL 内核实现**，意在摆脱对 AITER/PyNCCL 的单一依赖：

| 编号 | 类型 | 标题 | 要点 |
|---|---|---|---|
| #55916 | Issue/RFC | Add an RDNA4 FlyDSL all-reduce backend | 提出 TP2/TP4/TP8 下基于 FlyDSL 的 all-reduce 方案，目标是降低 graph-replayed 集合通信延迟，并设定了 0.98× PyNCCL 性能门槛 |
| #55917 | PR | [ROCm][Perf] Add FlyDSL RDNA4 all-reduce | 实现 #55916；仅保留满足性能与正确性门槛的路径；eager 直接 P2P 因 profiling 中发现 peer-progress stall 而改为仅 graph 使用 |
| #56005 | PR | [ROCm][Perf] Add RDNA4 FP8 block-scale FlyDSL kernels | 块级 FP8（E4M3FN）矩阵乘法，支持 decode/prefill 两种 kernel 族，自动优先于 AITER/Triton |
| #55996 | PR | [ROCm][Attention] Add RDNA4 FlyDSL SplitKV with RDNA3 Triton fallback | SplitKV paged decode，支持 BF16/FP16、FP8/FNUZ、GQA 1~16；Triton 版作为正确性兜底，需要 maintainer 裁决与 #45916 的重叠 |

**分析**：这套系列标志着 vLLM 在 RDNA4 上开始建立“自研 Python/FlyDSL kernel + 可测路由策略”的高性能路径，而不再完全依赖 AITER。设计上游刃有余：保留 PyNCCL/存在 AITER 作为安全回退，且都有“measured/correctness-checked”门槛。目前均为 open/draft 状态，需要关注 maintainer 对 FlyDSL 技术栈的接纳度。

### 💬 高热度讨论分析

#### 1. PR #54787：fused allreduce + GemmaRMSNorm 的性能“十字路口”

**核心议题**：在 MI355X（gfx950）TP4 上，将 allreduce 与 GemmaRMSNorm 融合为单 kernel（aiter 路径）并非在所有 shape 上都更快。

- **Fangzhou-Ai** 提供了一组非常精细的 A/B 数据：在 M=1~16 时 fused 有明显优势（最高 -14.66%），但 M≥32 后显式 allreduce + norm 反而快 +4.6%~8.15%。根因是 one-stage 与 two-stage allreduce 的边界，以及 two-stage 模式下 fused kernel 的 push 策略远慢于 pull。
- **benenzhu** 在 MI355X 复现后承认 fused 路径必须加 gate（限制在 one-stage 边界内的 M 范围）。进一步分析指出：two-stage fused 慢的原因来自 `tmp` 分片写入方式和 stage-2 norm kernel 本身比 Triton 慢 ~1.1us。
- **结论**：这成为一次典型的“融合 kernel 必须基于实测而非直觉”的案例；PR 增加 size gate 后合并，评审中的 A/B 数据对最终设计起了决定性作用。

#### 2. PR #53856：ROCm paged attention V cache padding NaN 修复

**核心议题**：ROCm paged attention 在 seq 未占满最后一个 block 时，向量化 V cache load 会读入未写的 slot；若 slot 含 NaN，会通过 `0 × NaN` 污染输出。
- **cadamcat（gfx1100 RX 7900 XT 实测）**：K cache 单独投毒不产生错误，V cache 单独投毒使 4096 长度全部变 NaN；确认 gfx11 上问题真实存在，且证明修复有效（4/4 修复，0 新损坏）。
- **aoshen02** 在 gfx950/MI350X 上补充 `auto` dtype（BF16/FP16）毒化矩阵，证明修复并非仅对 FP8 有效。
- **进一步的数据点**：该 fix 对 HunyuanOCR (gqa_ratio=2) 本身是“byte-inert”，因为 gfx11 gate 未覆盖该 shape，只有叠加 #54210 的 gate widening 才有意义。
- **结论**：ROCm 多代 GPU（gfx9/gfx11）协作验证的样例，说明 vLLM 在跨架构正确性问题上已形成较好的社区互验机制。

#### 3. Issue #32434：TRITON_ATTN + spec decode 在 ROCm 上无输出的关闭争议

**核心议题**：gpt-oss 在 ROCm 上，TRITON_ATTN 后端 + spec decode 不产生推理输出，是否真的修复？
- **hongxiayang** 倾向认为附带的 PR（切到 AITER unified attention）已修复。
- **AndreasKaratzas** 提出异议：PR 只是把路径改写为 AITER，TRITON_ATTN 本身的问题并未修复，不应关闭。
- **Arkar-Hema** 报告在 MI300X 上未应用修复也能通过测试；但 **AndreasKaratzas** 质疑其是否真正使用了 TRITON_ATTN（默认路径为 ROCm attention）。
- **结论**：issue 最终被关闭，但关注的“Triton attention 自身缺陷”仍悬而未决，属于典型的状态管理混乱。

#### 4. PR #55839：MooncakeStore 过时 save metadata 的防御到底该给谁做？

- **anish-shanbhag** 提交了一个防御性 guard：当 save 请求的 block 元数据已过期时，不再让进程 crash，而是丢弃该次 cache 写入。带真实负载证据（修复前 5.5 分钟崩溃，修复后跑满 3600 秒）。
- **作者自己发现** #55066 已经实现了相同守卫（且额外回滚了 request tracker save watermark），于是主动关闭 PR。
- **结论**：代表了当前开源协作中常见的重复工作，也反映出 Mooncake/vLLM 侧的 KV connector 处于活跃开发且对可靠性的要求极高。

#### 5. Issue #48953：Intel Arc B50 的 XPU IPC 问题（附持续排障）

**核心议题**：2× Arc B50 (Battlemage) TP=2 下 `zeMemOpenIpcHandle INVALID_ARGUMENT` crash。
- **marcinkuk** 做了极系统的复现与 mitigations 测试：单用 `CCL_TOPO_P2P_ACCESS=0` 不够，必须配 `CCL_ZE_IPC_EXCHANGE=sockets` 等整套 oneCCL 环境变量才能启动。
- **yisustc（维护者）** 指出关键点是 pidfd 与系统 `ptrace_scope` 配置的兼容性，并给出 `/proc/sys/kernel/yama/ptrace_scope` 的排查建议。
- **现状**：该 issue 已关闭，但 B50 的底层通信问题是否彻底解决仍取决于系统内核/oneCCL 配置。

### 🔥 热门话题与趋势分析

- **RDNA4 消费级显卡进入 vLLM 一二级关注梯队**：FlyDSL（Python DSL 编写的 RDNA4 kernel）被大量用于 allreduce、SplitKV、block-scale FP8。vLLM 社区开始用“native + Python-controlled kernel”路线填补 RDNA4 在 AITER 之外的性能空白。
- **AITER 的依赖深化**：ROCm 侧的 kernel 越来越依赖 AITER，同时也在小心地把“vLLM 自身集成逻辑”与“AITER 能力边界”解耦（例如 #55860 要求去 aiter config 查 tuned kernel，#55991 要求 AITER 不适合时自动 fallback 到 native/Inductor）。
- **AMD Quark 量化在 MoE 层的持续补齐**：#47972（linear）+ #52263（fused MoE）打通 Quark per-block FP8 主线。
- **Rust frontend 加快对齐 Python FastAPI**：`pythonic`/`olmo3` tool parser、timed-trace replay、render endpoint 缺失等，Rust 前端逐渐进入“功能补齐期”而非早期验证期。
- **Speculative decoding + Hybrid Mamba/GDN**：Uno 共享模型 draft（#55947）、Mamba checkpoint token（#55873~#55876 三连 PR）说明 vLLM 在 speculative/混合架构上投入很大。
- **确定性/可复现性成为新议题**：Batch-invariant 相关 PR（#55895、#55868、#55958）集中出现，覆盖 Mamba2 kernel tile 固定、GDN 前缀缓存、平台支持性等。
- **高质量 issue 报告增多**：部分 issue（#55904、#55870）写明了最小复现、根因分析和边界条件，且附有 no-GPU repro，大幅降低 maintainer 排查成本。

### 🛠️ 重点技术变更

1. **AMD Quark per-block FP8 fused MoE（#52263，已合并）**  
   补齐了 Quark 量化模型在 MoE 层上的加载空白。实现上复用 `CompressedTensorsW8A8Fp8MoEMethod` 的 `BLOCK` 策略，按 128×128 block grid 分配 scale，并使用 Quark 原生参数名以省去 mapping。该 PR 直接影响 Quark 用户能否在 vLLM 上正常服务 MoE 模型。

2. **RDNA4 FlyDSL 系列（#55916/#55917/#56005/#55996）**  
   如果合并，将给 ROCm 平台带来：
   - Python/FlyDSL 实现的 all-reduce（带 0.98× PyNCCL 性能门槛）；
   - block-scale FP8 GEMM 的 vLLM 自研路径；
   - SplitKV decode 的 FlyDSL 实现与 Triton fallback。
   这套组合意味着 vLLM 在 AMD 消费级显卡上开始建立独立的 kernel 库，降低对特定第三方库的路径依赖。

3. **ROCm paged attention V cache padding 修复（#53856，已合并）**  
   修正了“只 mask logits、不 mask V”的经典遗漏。对 `gfx9/gfx11/gfx12` 做针对性修补：跳过完全无效的 vector，并在穿过 seq_len 的边界 vector 上做 mask。属于高影响低风险的正确性修复。

4. **移除 GPTQ group/dynamic activation ordering（#54809，已合并）**  
   全栈移除 actorder（`g_idx`），涉及 checkpoint 格式、kernel、dead code。上游 llm-compressor/compressed-tensors 已移除该特性，vLLM 同步收窄支持面，能显著降低多平台（ROCm/CUDA/CPU）kernel 维护成本。

5. **Rust 前端/规模外 API parity（#55849/#55850/#55937 等）**  
   虽然分散，但 `pythonic` tool parser、`olmo3` parser、以及 vllm-bench timed-trace replay 的引入，透露 vLLM 正在将越来越多的 Python-only 功能迁移到 Rust 前端，以统一部署形态。

### 💡 值得关注的问题

1. **FlyDSL 技术路线归属与评审**：RDNA4 系列 PR 目前以“measured/routed”策略自证安全性，但其与 AITER 的功能重叠、以及 Python/FlyDSL 内核的可维护性，需要维护者给出明确意见，特别是 #55996 的 Triton fallback 与 #45916 的关系。
2. **ROCm batch-invariant（bitwise reproducible）支持缺口**：#55958 选择在 ROCm 上直接报错而不是“半支持”，但如果用户需要跨 CUDA/ROCm 的可复现推理，平台团队应尽快补上 matmul override 与 tuned config 的 ROCm 实现。
3. **Issue #55904 的 KV offload 缓存污染风险**：当用户在共享 PVC 上跑多实例、且 KV cache layout 不同（LBNHC vs LBHNC）时，旧缓存会被误命中并产生“无报错的随机乱码”，建议在 namespacing 中纳入 layout 维度并审计既有部署。
4. **Mamba/GDN checkpointing 三连 PR（#55873/#55875/#55876）**：目前均有 merge conflict，依赖栈较长；若希望合入，需要一个明确 rebase 计划和一个主 reviewer 持续跟进。
5. **Rust frontend 的 `/v1/chat/completions/render` 与 `/openapi.json` 404**（#55994）：在 turn 到 Rust frontend 时属于可见的 API surface 回退，建议在实现 parity 前至少让启动阶段给出清晰 warning，而不是返回裸 404。
6. **FlexAttention 在 AMD CI 上的 16-variant 限制**（#55888、#55840）：这暴露了测试套件在 `torch.compile`/Dynamo 高版本下的脆弱性；修复思路是让测试使用“自动选择 attention backend”，而不是强制 FP32/Flex 高精度 fixture。
