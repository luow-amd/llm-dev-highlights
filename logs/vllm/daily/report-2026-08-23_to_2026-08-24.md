## 🎯 AMD/ROCm 生态相关动态

本周期 AMD 生态非常活跃，**这是近期 AMD 上游提交强度最高的一天之一**，覆盖解码内核、稀疏注意力、部署工具链、CI 减负四个层面。

### 1. [ROCm] 融合 KDA 解码扩展到 DSpark 投机解码（#53475）

作者 xiaohuguo2023（基于 MI355X/gfx950 工作），将现有 1-token 融合 KDA 解码 HIP kernel 扩展至 DSpark 投机解码路径（`num_spec<=2`, qlen=3）：

- 新增 qlen 循环、2-D SSM 索引、`cu_seqlens`/`num_accepted_tokens` 参数，保持 conv 状态长度 `width-1+num_spec`
- 微基准：Triton 链 3.53 ms/step → 融合 HIP kernel 在 HIP graph 中 0.59 ms/step（约 **6 倍每步下降**）
- 明确**排除了** MLA FP8 prefill、prefix-cache 等边界。作者同时提交了 #53487，将 KDA mixer 从 piecewise CUDA graph 中分裂出来（MI355X 场景不启用 breakable CUDA graph，KDA mixer 此前一直是 eager Triton launch，被视为 conc=1 launch-bound 路径）。

**影响**：这是 KDA 解码在 AMD 平台从 Triton 链到融合 HIP kernel 的一次关键跨越，直接针对 MI355X 上 DSpark 每步的 host bubble（~13 ms）。

### 2. [ROCm][MLA] Aiter Gluon 稀疏 MLA kernel（#53492）

作者 cagrikymk，为 `ROCMAiterMLASparseBackend` 增加 Aiter Gluon 后端（默认关闭，以 flag 显式开启），面向 GLM-5.2 在 MI355 上的稀疏 MLA。GSM8K 上不降精度（strict-match +0.23pp），性能上：

- Prefill-heavy（ISL 8192）：输出吞吐 **+4.9%~+8.6%**，TTFT 中位数 **-9.0%~-12.4%**
- Decode-heavy（ISL 1024）：吞吐 +4.5%~+6.0%，TTFT 在大并发下最多 **-22.8%**
- 所有并发档位 TPOT 下降约 4%~8%

这是 Aiter 生态对 GIANT 模型 MLA 场景在 ROCm 上落地的重要一步。

### 3. [ROCm][Perf] Lightning Indexer score/top-k 三管齐下（#53448）

作者 akii96，针对 MiniMax-M3 稀疏注意力在 gfx950 上 indexer 占 GPU kernel 时间 8.9% 的问题：

- 解码侧：index cache 从 bf16 降为 **e4m3**，读取字节减半，memory-bound 循环的 prologue 可从更深 pipeline 收益
- Prefill scorer：按 KV 轴分块消除 469:1 的 workgroup 负载不均
- Top-k：每个 program 携带多行 query（8~32 行自适应），摊薄固定排序网络开销

### 2. Issue #53430 → 双 PR 平行修复：BatchedTritonExperts 非确定性

**核心议题**：未量化 `BatchedTritonExperts` 在完全相同的输入上多次运行可返回不同的 BF16 结果，且该波动足以改变 greedy 下 top-1 token。举报者 bossjoker1 给出 20 行最小复现。

**根因**：`TopKWeightAndReduceNaiveBatched.apply` 使用 CUDA `index_add_`。当多个 expert 路由到同一 token 时，原子加的顺序不确定，BF16 非关联浮点加法产生低位噪声。

**关键互动**：
- wuhangxian 在 issue 评论中宣布自己开了 #53440 修复：scatter 到 `(T, topk, K)` buffer（每个位置至多写一次）+ 复用 `ops.moe_sum` 固定顺序 FP32 累加
- 随后 wuhangxian 又发现 **12 分钟内**出现了一个独立收敛到几乎相同方案的 PR #53442（taking-lying-flat，scatter + `moe_sum`，同样的临时 tensor 代价）。wuhangxian 主动公开说明两个 PR 设计决策一致，请维护者任选其一
- #53440 在 RTX PRO 5000 (SM120) 验证 19/19 次重复 bitwise 一致

**争议焦点**：无实质争议，反而是开源的"平行宇宙"正面案例——两个独立贡献者几乎同时给出同一正确设计。此类重复 PR 被以高度协作的方式公开透明地处置。

### 3. PR #53450 强制 attention backend 环境变量 —— 生产事故驱动的逃生舱

**核心议题**：MTP 草稿模型不经 `--attention-backend` 传参，在 DGX Spark（SM121）上自动选中 FLASHINFER 后与 fp8 KV 组合触发非法内存访问崩溃。作者 jianyi85 提出 `VLLM_FORCE_ATTN_BACKEND` 环境变量一把梭。

**讨论亮点**：
- 作者在 PR 评论里给出了**非常扎实的事故证据链**：崩溃时 `preempted_req_ids=[]`、`record_stream` 加固无效、`PIECEWISE` cudagraph 无效 → 指向 in-step kernel corruption 而非调度竞争；强制 TRITON_ATTN 后 5 轮复现全部干净
- 明确边界："完整修复应把 `attention_config.backend` 接入 draft model 的选择逻辑；env 只是最小逃生舱，也用于 bisect 后端特定故障"
- 补充了 4 个单元测试覆盖 force/fallback/unknown/precedence

**观点**：这是"生产可用性优先"与"干净架构优先"之间的典型张力。作者坦诚这是一个最小 hack，但同时给出数据证明其必要性和有效性。

## 🛠️ 重点技术变更

### 1. [RL] P2P RDT 分片权重同步（#43375，已合并）

第四个权重传输后端 `sharded_rdt`：各 inference worker 只拉取自己在张量/专家并行下实际消费的权重切片，大 MoE 每 worker 移动 `total_bytes/num_workers` 而非全量。实现思路新颖：初始化时对零存储 placeholder 跑一次 `load_weights`，把 vLLM 自身 loader 的切片操作（`narrow`、`t`、`view`…）记录为可重放 op chain。实测 Qwen3-235B-A22B 在 8 trainer → 8 inference GPU 上 warm sync 仅 **3.3 s（43 GiB/s）**，对比 TP8 的 6.1 s @ 26-28 GiB/s。对超大规模 RL 训练/推理协同是一次数量级体验提升。

### 2. [ROCm] 融合 KDA 解码扩展 DSpark（#53475）

将 MI355X 上 Triton 链式的 DSpark KDA 解码替换为融合 HIP kernel（conv + recurrent KDA + gated RMSNorm）。微基准显示每 decode 步从 3.53 ms 降至 0.59 ms（HIP graph 内），且这是纯 vLLM 侧改动，不依赖 nightly Aiter。虽然 serving A/B 尚未发布，但 kernel 级 6 倍差距足以说明 launch-bound 路径的收益空间。

### 3. [ROCm][MLA] Aiter Gluon 稀疏 MLA（#53492）

GLM-5.2-MXFP4 在 MI355/TP8 上，通过启用 Gluon 后端获得 4.5%-8.6% 吞吐提升和最高 22.8% TTFT 下降。0.9477→0.9484 的 GSM8K 精度（flexible-extract）确认无损失。这是 Aiter 在后训练量化模型 + 稀疏注意力上的一次成功展示。

### 4. 投机解码 K=0 跳过 draft sync forward（#53426，opt-in）

DSD（Dynamic Speculative Decoding）解析 K=0 时，vLLM 每步仍执行一次 draft model prefill 以保持 KV 同步。在高并发（spec 表恰好解析 K=0 的典型区间）下开销为 **4%-11% decode 步时间**。此 PR 提供默认关闭的显式 opt-in：仅 `mtp` 方法可选；EAGLE 家族因实测 resume 后 acceptance 崩溃被拒绝（一个 EAGLE3 checkpoint 直接 collapse）；其他未测量变体（gemma4/dflash/dspark/multi_module_mtp）一律拒绝。这是"安全由草稿器架构决定、不能可靠预测"前提下的保守设计。

### 5. BatchedTritonExperts 确定性修复（#53440/#53442）

将 `index_add_`（CUDA 原子加，顺序不确定）替换为 scatter 到 `(T, topk, K)` buffer + `ops.moe_sum`（固定 top-k 序、FP32 累加）。修复后 19/19 次重复 bitwise 一致。此修改影响所有走 BatchedTritonExperts 的 MoE 模型在 greedy/固定 seed 下的可重现性，也是 vLLM 走向可复现推理的关键一环。

## 💡 值得关注的问题

1. **DFlash2 草稿模型在 main 上持续不可加载**（#53428）：已存在两个修复 PR（#53435/#53449）均待 review。任何从源码构建并使用 DFlash2 的用户均被阻塞，且无法针对当前 main 重新测量 DFlash2 性能。

2. **MTP 下 prompt_logprobs 静默损坏**（#53488）：无报错、HTTP 200、仅部分 chunk 损坏（部分 logprob 和偏离 10 倍以上），跨两个构建、两个量化格式、两个 MTP 头复现。这是慢性的**数据面正确性问题**，比崩溃更隐蔽，值得优先调查。

3. **MTP + fp8 KV + FLASHINFER 在 DGX Spark 上的非法内存访问**（#53450 背景）：生产环境 2 分钟内必现，作者的排查已经排除了同步竞争、cudagraph 模式、`record_stream` 加固等因素——更接近 kernel 内内存破坏。虽然提议的 env 可绕行，但**根本修复（MTP 草稿器继承主模型的 attention backend 配置）仍未落地**。

4. **LMCache wheel 与 vLLM 镜像 PyTorch ABI 不匹配**（#53424/#53441）：`lmcache.c_ops` 静默 fallback 到 torch baseline，用户无感知但性能损失显著。修复方案（sdist 构建）已提交，但该问题说明 wheel 发布流程缺少 ABI 兼容性 CI。

5. **ExampleConnector 的 KV keying 缺陷**（#53495/#53496）：cache_salt、LoRA、prompt_embeds 三个维度全部未参与外部 KV key 派生，造成跨租户 KV 泄漏。修复采用 `block_hashes` 链式 key（与 SimpleCPUOffloadConnector 一致），但 `HF3FSKVConnector` 存在同类问题（#51748），社区需要一套 conformance suite（#53194）来一劳永逸。

6. **YAML 配置中下划线键 + false 值被静默丢弃**（#53478）：`enable_prefix_caching: false` 不生效且无警告，已导致生产环境误开启 prefix caching 数周。该 PR 已关闭（作者主动撤销），但暴露的"拼写错误键静默失效"问题仍待后续方案。

7. **多个 KV offload RFC 重叠**（#53485/#53486/#53484）：#50031 与 #51240 用不同信号（吞吐 EMA vs 延迟 EMA）实现同一 backpressure 机制。#53485 提议统一并扩展 admission policy，但三个 RFC 的合并节奏需要维护者明确优先级，否则存在重复实现风险。
