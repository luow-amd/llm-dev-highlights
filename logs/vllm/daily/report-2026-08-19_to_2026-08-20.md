### 💬 高热度讨论分析

#### 1. Issue #52897：priority 调度策略下 align-mode 前缀缓存命中率恒为 0

**核心议题**：生产环境中以 `--scheduling-policy priority` 运行时，align-mode Mamba 前缀缓存一次都不命中（0/996,052 查询），而 FCFS 策略下有 17.5% 命中率。

**多方观点**：
- **nicolamoresi（报告者）**：初步归因于 #51113 正确性修复（对齐模式快照只在精确块边界缓存）未考虑 PRIORITY 策略的 chunk 对齐行为。
- **982945902 / he-yufeng（社区复现者）**：在 CPU-only 调度器复现中，两种策略下首次请求 chunk 端点相同（`[1600, 3602]`），第二次请求均报告 1600-token 本地命中，**无法复现策略导致的零命中**，要求提供更多细节。
- **nicolamoresi（修正）**：重新测量后发现报告过度简化——实际是"预算压力下分块错位 + LRU 驱逐"的组合效应，而非策略本身的结构性问题，且 `num_preemptions_total=0` 排除了抢占因素。
- **he-yufeng（代码级分析）**：确认 `_mamba_block_aligned_split` 在 per-step 预算低于 1600 块宽时确实产生 off-boundary 状态；同时指出需区分"从未缓存"与"缓存后驱逐"两种场景。

**当前状态**：Open。社区建议在分块助手处增加"off-boundary chunk end"计数器，并捕获 block-cache size/eviction 指标以区分两种失效模式。

#### 2. Issue #52959：Mamba Align 模式内部状态检查点（RFC）

**核心议题**：`mamba_cache_mode="align"` 目前只能在模型 forward 结束时提交循环状态。若 prefill 跨越最后一个可复用边界，必须拆成两次 forward（如 `[0, 7680)` + `[7680, 8000)`），重复执行完整模型。RFC 建议在 `MambaSpec` 中增加 `support_internal_checkpoint`，让单次 forward 同时产出检查点状态与运行状态。

**不同观点**：
- **yewentao256**：最初在 #52789 中也用了 `support_internal_checkpoint: bool = False`，但后来发现 `num_prefill_checkpoint_blocks: int = 0` 更便于扩展到其他场景。
- **ZeldaHuang**：提出在部分前缀缓存下能否只存储最后一个 prefix-match 单元的检查点（每请求单次 forward 只需一个检查点）；并提到 FlashKDA#7 已支持导出内部状态，且 #52789 中有类似工作。
- **ZJY0516**：回应部分前缀缓存问题是用于 eagle block drop，非 eagle 场景可跳过。

**当前状态**：Open。这是一个活跃的设计讨论，涉及 Mamba 前缀缓存与推测解码的交叉优化。

### 🛠️ 重点技术变更

#### 1. PR #52861 — DSA 模型 CUDA 默认路由（已合并）
将 DeepSeek V3.2 / GLM-5.2 的 NVIDIA 路径从通用 compiled MRV1 切换到 CUDA 非编译 MRV2 + breakable CUDA graphs，实现并发 1~1024 下 +8%~+16% 的吞吐提升。这是**架构级默认路径切换**，影响所有 NVIDIA 上的 DSA 模型用户。ROCm 保持 MRV1 compiled 默认，避免跨平台行为漂移。

#### 2. PR #52966 — CT block FP8 与 Marlin 的兼容修复（已合并）
`MarlinFP8ScaledMMLinearKernel` 此前无条件访问 `weight_scale_inv`，而 Compressed Tensors 暴露的是 `weight_scale`，导致 TP worker 加载 QKV 投影时失败。修复后 Marlin block 路径与其他 block kernel 遵循同一双名称契约。体现了**量化后端之间约定不一致**的通用问题。

#### 3. PR #52948 — DeepSeek 双向注意力 embedding 支持（已合并）
为 DeepSeek-V2/V3 骨架引入 `is_causal=False` 支持（encoder-only 注意力），使 `Giga-Embeddings-instruct-10B-A1.8B-0826` 这类基于 DeepSeek 的 embedding 模型可以在 vLLM 上运行。实现方式克制：仅在非 MLA 路径生效且默认行为完全不变。

#### 4. PR #52704 — OCP MX MoE 静默跳过 mxfp6 激活 QDQ（已合并）
这是一个"安静的正确性杀手"：4 个 mxfp6 方案因 quant_dtype 映射产生 `"mxfp6"` 字符串而不是 dispatcher 认识的 `"mxfp6_e3m2"` / `"mxfp6_e2m3"`，落入 else 分支后**完全不量化激活**，精度数据虚高且无任何报错。修复后增加了端到端测试（此前 bit-identical 比较可捕获此问题）。

#### 5. PR #52819 — ROCm Triton 3.7 bump（已合并）
一个 stopgap 修复，包含 Triton 3.7 回归和 Kimi K2.6/K3 的 pybind11 3.1.0 问题。它在 v0.28.0 发布窗口内被快速合入，同时暴露了 AMD CI 中 Llama 4 权重加载异常缓慢的新问题。

### 💡 值得关注的问题

1. **MiniMax-M3 AITER 稀疏 PA 的静默输出损坏（#52860）**：AITER 原型路径在 spec decode + FP8 KV 下产出看似正确但实际错误的回复，且无任何报错。这是"quiet failure"类问题，社区应推动该路径的 opt-in 或默认关闭（已有 #52893 提案）。
2. **Qwen3-Next GDN + MTP 的接收崩溃点漂移（#52873）**：异步调度开关会移动触发点约 11k token，提示这是累积性 per-step 计数器问题而非固定位置溢出。该问题"确定性 per-config 复现"但"跨配置漂移"，暗示了 int16 类型位置/偏移在 drafter 路径中的潜在缺陷。
3. **DeepSeek-V4 ROCm 优化第二阶段（#52911）**：RFC 提出的"先换 kernel 再开 overlap"顺序很有价值——#51794 的失败教训（并行流中的未优化 kernel 与主流争抢资源导致 all-reduce 尾部抖动）说明性能优化存在"时序依赖"。
4. **xgrammar/outlines 结构化输出的静默约束丢失（已合并 #49996）**：xgrammar 保留 pattern 丢弃 length bound，outlines_core 保留 length bound 丢弃 pattern——两个主流后端的 JSON Schema 编译行为是镜像缺陷。vLLM 选择在服务边界拒绝混用，上游修复仍在等待中。
5. **NIXL/UCX 在无 AVX CPU 上的进程级崩溃（#52885）**：原生库初始化器中的 abort 无法被 Python 捕获，即使完全不使用 KV transfer 也会触发。此问题影响虚拟化环境中的 CPU 型号遮蔽场景，PR #52920 的 CPUID 检测方案值得关注。
6. **Mamba Align 模式前缀缓存与调度策略的相互作用（#52897）**：虽然调度策略本身不是零命中的根因，但预算压力下 off-boundary 状态不断产生又无法缓存，实际部署中会导致缓存效率显著下降。建议增加诊断计数器来量化该现象。
