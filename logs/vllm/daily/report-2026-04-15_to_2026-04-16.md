### 🎯 AMD/ROCm 生态相关动态
本周期 AMD 相关贡献活跃，涵盖了从底层通信原语到上层量化支持的多个方面。

1.  **PR #39875 - [Core] Add Ring Attention Primitives for Context Parallelism**
    *   **贡献者**: `knitcapcat-amd` (AMD 员工)
    *   **内容**: 为预填充上下文并行 (PCP) 引入了环注意力 (Ring Attention) 通信原语和计算框架。这是一个**基础设施级别的构建块**，允许 Q 保持本地，K/V 在 CP rank 间通过 P2P 环传输，通过在线 softmax 校正增量合并结果，旨在实现通信-计算重叠。
    *   **影响**: 为 AMD 平台（及所有支持平台）上的长上下文、高并行度推理提供了新的、高效的注意力后端算法选择，是 PCP 路线图的关键一步。

2.  **PR #39953 - [ROCm] Fix TurboQuant on ROCm: backend routing, flash-attn compat, int64 overflow**
    *   **贡献者**: `aditi-amd` (AMD 员工)
    *   **内容**: 修复了 TurboQuant 在 ROCm 平台上的三个关键问题：1）正确路由 `turboquant_*` KV 缓存类型到 TurboQuant 后端；2）包装 `flash_attn_varlen_func` 以处理 ROCm 上缺失的 `out=` 关键字参数；3）在 Triton 内核中将索引转换为 int64 以避免大 KV 缓存溢出。
    *   **影响**: 使 TurboQuant 量化功能能够在 AMD MI300X 等硬件上稳定运行，扩展了 AMD 平台上的高效推理选项。

3.  **PR #39931 - [Feature] TurboQuant: support hybrid models and uniform quantization**
    *   **贡献者**: `JartX` (关联 ROCm 标签)
    *   **内容**: 修复了 TurboQuant 在 Qwen3.5 等混合模型（如 Mamba + Attention）上的启动失败问题。确保 TurboQuant 仅应用于 `full_attention` 层，并为排除的层正确回退到默认后端。
    *   **影响**: 增强了 TurboQuant 对复杂模型架构的兼容性，这对支持广泛模型生态的 AMD 平台尤为重要。

4.  **PR #33773 - [ROCm][FEAT] Integrate aiter gemm w8a8 ptpc** (已合并)
    *   **贡献者**: `vllmellm`
    *   **内容**: 集成 aiter PTPC (Per-Tensor Per-Channel) GEMM 内核来优化 AMD ROCm 平台上的 FP8 推理性能，利用 `bpreshuffle` 和 `ck` 算子提供相比 `torch.scaled_mm` 显著的性能提升。
    *   **影响**: **已合并**。直接提升了 AMD 硬件上 FP8 量化模型（如 Qwen3-8B）的推理吞吐量，是 ROCm 性能优化的重要成果。

### 💬 高热度讨论分析

1.  **Issue #39885 - Gemma4 流式推理泄露**
    *   **核心议题**: 使用 `--reasoning-parser gemma4` 并开启流式传输时，在多轮对话的工具调用结果后，推理内容会错误地泄漏到 `content` 字段。
    *   **各方观点**:
        *   `KrxGu`: 指出这是一个流式解析器/状态错误，而非模型行为问题。证据是非流式模式正常，流式模式下 `delta.reasoning` 为空。他愿意参与修复。
        *   `DarkLight1337`: 表示未参与该模型相关工作，建议联系更了解 Gemma 4 的同事 (`@ywang96`, `@chaunceyjiang`)。
    *   **争议焦点**: 暂无直接争议，更多是确认问题性质和寻找负责人。
    *   **当前状态**: 问题处于开放状态，已明确为 bug，等待相关人员处理。PR #39898 声称修复此问题，但尚未合并。

2.  **Issue #39928 - Qwen3.5 DFlash 在 SM90 上输出异常**
    *   **核心议题**: 在 H100 (SM90) 上使用 DFlash 投机推理时，Qwen3.5-9B 对同一短提示词的输出极其不一致（产生乱码或 NaN），而无 DFlash 时稳定。
    *   **各方观点**:
        *   `mgoin` (提交者): 推测可能与短提示（位于第一个块）导致的块损坏有关。
        *   `benchislett`: 证实了问题，并补充在 EAGLE3 上也复现，但 MTP 或无投机推理时正常。认为可能是**子单块提示词**的特有问题。指出 `enforce-eager` 模式下工作正常。
    *   **争议焦点**: 无对立观点，讨论聚焦于问题根因的假设（首块处理、投机推理与短提示的交互）。
    *   **当前状态**: 问题开放中，社区正在积极定位根本原因，可能与 Blackwell 架构及投机推理的特定交互有关。

3.  **Issue #32436 - GLM 4.7 工具调用问题** (历史讨论热烈，本次关闭)
    *   **核心议题**: GLM-4.7 的工具调用解析器 (`tool-call-parser glm47`) 存在 bug，容易导致错误，影响 Claude Code 等智能体应用。
    *   **各方观点**:
        *   **用户群体**: 多个用户报告了使用 Anthropic endpoint 时工具调用失败、推理内容泄露等问题，而非 OpenAI endpoint。
        *   **贡献者**: 提供了临时修改方案（修改 `anthropic/serving.py`），但指出可能带来其他影响。
    *   **争议焦点**: 问题持续时间长，影响第三方应用，用户对修复和 Docker 镜像更新的速度有期待。
    *   **最终结论**: 该 Issue 在本次周期内被关闭，但关闭原因未明确说明是彻底修复还是过期。相关修复 PR (#32321) 早已合并，但可能遗留了与特定 endpoint 的兼容性问题。

### 🛠️ 重点技术变更
1.  **PR #30566 - Update to transformers v5** (已合并)
    *   **技术解读**: 将核心依赖 Transformers 从 v4 升级到 v5.5.3。这是一个**重大变更**，涉及大量依赖版本调整和代码适配。
    *   **影响**: 解除了长期以来的版本限制，使 vLLM 能够支持基于 Transformers v5 的新架构。作为代价，暂时放弃了对一些老旧或不兼容模型（如 Plamo2, OpenCUA）的支持，并引入了新的 CI 测试来保障向后兼容。

2.  **PR #39875 - 环注意力原语** (如前所述)
    *   **技术解读**: 实现了用于上下文并行的 Ring Attention 算法框架，包含异步环 P2P 通信器 (`ring_comm.py`) 和集成了在线 softmax 合并、KV 打包、双缓冲的注意力操作 (`ring_attn.py`)。
    *   **影响**: 为将来支持超长序列的、通信高效的并行推理提供了底层支持，是性能扩展的关键技术储备。

3.  **PR #39890 - 官方 TurboQuant 分组模式**
    *   **技术解读**: 在原有 “_nc” (非官方) 模式基础上，新增了官方论文对齐的 `turboquant_4bit` 和 `turboquant_3bit` 分组 KV 缓存模式，实现了分组感知的 MSE+QJL 键打包和相应的 Triton 存储/解码路径。
    *   **影响**: 为用户提供了更标准、可能更高效的 TurboQuant 选项，同时保持向后兼容，推动该量化技术的成熟。

4.  **PR #39851 & #39873 - 修复 CUDA 镜像不匹配与模块检测**
    *   **技术解读**: #39851 通过固定 `nixl-cu12` 和 `nixl-cu13` 版本来解决 Docker 镜像中 CUDA 版本与 `nixl_ep` 库链接不匹配的问题。#39873 则修复了 `_has_module` 函数，使其通过实际 `import_module` 来检测模块可用性，而不仅仅是 `find_spec`，从而避免了因依赖缺失导致的启动崩溃。
    *   **影响**: 解决了近期 CI 和用户部署中遇到的紧急问题，保证了 Docker 发行版的稳定性和可靠性。

5.  **PR #39874 - MIG 分区 NVML 回退**
    *   **技术解读**: 检测到 MIG 分区时，自动回退到使用 `torch.cuda` API 而非 NVML 来查询内存信息，解决了 NVML 在 MIG 上无权限导致的错误掩蔽和内存报告不准确问题。
    *   **影响**: 使 vLLM 能够在 MIG 环境下正确运行和报告内存使用，避免了因错误信息导致的配置错误。

### 💡 值得关注的问题
1.  **Gemma 4 引擎挂起** (Issue #39914): 在长提示词（>4k）预填充时，因交错注意力 (Interleaved Attention) 和 p-RoPE 实现问题导致引擎完全挂起。这触及了新模型复杂架构与现有调度器/内核的兼容性深水区。
2.  **跨实例推理方差** (Issue #39903): 相同配置和模型在不同 vLLM 服务实例间产生约 10 分的巨大评测差异，而实例内部稳定。这可能暗示了某些非确定性的初始化或底层计算问题，对严谨的评测工作流构成威胁。
3.  **专家并行容错性 RFC** (Issue #39942): 提出了对专家并行 (EP) 过程组中 Collective 操作进行容错设计的方案，旨在防止单个 EP rank 故障导致整个服务器挂起。这是一个面向生产环境高可用的重要架构改进讨论。
