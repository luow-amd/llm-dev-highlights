#### 1. 🔴 关键性能回归修复：RDNA4 FP8 内核选择错误

**Issue #57838**（用户 `taisunyoung`）报告了一个严重的性能回归：从 v0.28.0 起，`RowWiseTorchFP8ScaledMMLinearKernel` 开始在 RDNA4（gfx1201）上被错误选中，导致：
- v0.28.0 上 decode 吞吐从 35.45 tok/s 降至 32.22 tok/s（**-10%**）

**修复 PR #57861**（用户 `Cross2pro`）已经提交：在 gfx1200/gfx1201 上禁用 `RowWiseTorchFP8ScaledMMLinearKernel`，保留其他 ROCm 架构的 RowWise 路径。已在 CPU 侧通过 `test_scaled_mm_kernel_selection.py`（10 passed）。**这是本周期最具行动性的 AMD 议题**，值得 AMD 团队尽快复核并推进合并。

### 🔥 热门话题与趋势分析

#### 话题 1：注意力 sink 的在线权重更新正确性（RFC #57795 及其 8 个堆叠 PR）

`Ronald1995` 提交了一个系统性审计，指出**20 处直接 `copy_` 写入注意力 sink 参数的位置**，绕过了 `param.weight_loader`——在 RL 在线权重更新/分层重载路径下，sink 的 kernel tensor 不会被更新，导致静默错误。涉及 DeepSeek V4/V4.1（cpu/xpu/amd/nvidia 四个后端）、MTP、DSpark、HY-V4、MiMo-V2、GPT-OSS 等 19 个文件。

**趋势判断**：这反映了 vLLM 从"推理引擎"向"RL 训练基础设施"演进的必然要求——**在线权重更新的可观测性与正确性**成为新一类 bug 的来源。

#### 话题 2：MoE 专家粒度的显存驻留（RFC #57794）

`Mohammad-Nabulsi` 提出复用 EPLB 已有的 per-expert 负载统计窗口，通过新增 `cold_expert_fraction` 参数将"冷尾"专家降级到 host memory，而非常规的整层或整参数 offload。

**关键论点**：per-token swap-on-demand 不可行，因为路由是数据依赖的，在 L-1 层输出前无法知道 L 层需要哪些专家。作者引用了 63.2 µs 的 host-gather 成本作为论据。

**趋势判断**：**MoE 显存管理与 EPLB 的深度耦合**可能是下一代 vLLM 大规模 MoE serving 的关键方向。

#### 话题 3：DecodeBenchConnector 在大 batch 下的 KV cache 重复填充（Issue #57847）

`Pipiho` 报告了 hybrid KV cache 布局下，同一 state tensor 被按请求重复填充，在 batch size=256 的长上下文 decode 基准中导致 worker RPC 超时。**已在 MLU 后端复现**，但问题定位到上游 `DecodeBenchConnector` 实现。

#### 话题 4：CUDA Graph 与异步工作的交互正确性

除 #57785/#57759 外，`quanliu1991` 的 Issue #57794 提到了 FULL_AND_PIECEWISE capture 在 host load 15–21 时的不稳定，两者构成了**CUDA graph 捕获期侧流同步**这一主题簇。

#### 话题 5：工具调用解析器的尾部参数丢失（Issue #57827 / #57826）

`DingNova` 发现 `minimax_m2` / `glm47_moe` / `deepseek_v4` 三个 arg converter 在模型未闭合最后参数标签时会丢参，属于 #57699 同类 bug（qwen3 已修）。`he-yufeng` 提交 PR #57836 修复。

#### 话题 6：多模态 prompt 占位符的静默错误

`twu3202`（PR #57781）和 `aoshen02`（PR #57796）分别修复了两类多模态占位符问题：**引用模型占位符 token 导致误绑定**，以及**已展开 prompt 被二次展开**。两者都强调"此前是静默成功"，属于多模态输入的健壮性提升。

### 🛠️ 重点技术变更

#### 1. PR #57861 — RDNA4 上禁用 RowWise FP8 scaled MM（**最高优先级修复**）

**技术细节**：`RowWiseTorchFP8ScaledMMLinearKernel.is_supported` 在 v0.28 放开后错误地在 RDNA4 上被选中，而该硬件上 ChannelWise 实际快 10–24%。修复方式简洁：在 `is_supported` 中显式拒绝 `gfx1200`/`gfx1201`。

**影响**：对使用 RDNA4 运行 FP8 compressed-tensors 权重（gemma-4-12B、Qwen3-14B）的用户，这是一个直接可感知的性能回退；该 PR 若合并将修复 3 个版本窗口的回归。

#### 2. PR #54894 — DSV4 FP8 `wo_a` 输出投影（**已合并**）

**技术细节**：用 AITER `inverse_rope_group_quant` 融合 inverse RoPE 与 per-token E8M0 组量化，再用 `batched_gemm_a8w8_mxscale` 消费量化激活和原生 FP8 `wo_a` 权重，取代原 BF16 grouped einsum。

**影响**：
- 8×MI355X、TP1/PP8、100K-token prefill：TTFT **-7.35%**，输入吞吐 **+7.93%**
- GSM8K 完整 1319 题验证：**0.9651 vs 0.9629**（FP8 vs BF16），精度无损
- 需要 AITER ≥ 0.1.20，有 capability probe 和 BF16 fallback

#### 3. PR #57760 — Quark PTPC-FP8 运行时布局支持

**技术细节**：
- ROCm sparse MLA 路径下 `wo_a` 重建：接受 per-channel scale，处理 Quark 加载的 `[in, out]` 权重（需在缓存 BF16 布局前转换）
- `engram.embed` row-wise FP32 scale：`ParallelEngramEmbedding` 支持 1-D FP32 scale shard，新增 Triton lookup 分支

**影响**：这是 `amd/DeepSeek-V4.1-Flash-Quark-PTPC-FP8` 在 ROCm 上可运行的**最后一块拼图**（依赖已合并的 #57071），GSM8K 精度与原始模型持平。

#### 4. PR #57815 — 在稀疏索引器上拒绝 batch-invariant 模式

**技术细节**：`VLLM_BATCH_INVARIANT=1` 在 DSA/稀疏索引器模型上看起来有效但实际无效——所有 top-k 后端（auto/per_row/persistent/cooperative）都依赖 batch 组成（padded column count、occupancy、max seqlen、64 行阈值）。该 PR 在构造时显式拒绝，而非静默返回非 batch-invariant 结果。

**影响**：作者特别引用了 GLM-5 技术报告——非确定性稀疏选择曾在 RL 训练几步后导致熵急剧下降和性能崩溃。这一改动虽小，但对 RL 训练的正确性至关重要。

#### 5. PR #56685 — Humming 特性整合（**已合并**）

**技术细节**：为 Humming 量化增加 Hadamard 变换、SM120/SM121（NVFP4/MXFP4/MXFP8）支持、更多输入量化模式（`static_per_tensor`/`static_tensor_dynamic_group`/`dynamic_group_tensor`），以及统一的 `process_input` 融合内核。

**影响**：扩展了 vLLM 在 Blackwell 平台上的低精度量化覆盖面，特别是对 NVFP4 的支持。
