#### 一、MonoKernel / Mono-decode 体系（本周期最大技术主题）

AMD 正在系统性推进"每层一次持久化内核启动"的 MonoKernel 方案，覆盖多个旗舰模型：

| PR/Issue | 贡献者 | 模型 | 关键数据 |
|---|---|---|---|
| **#60904 (RFC)** | `dllehr-amd` | 通用标准 | 8×MI350X 上 GLM-5.2 decode 每步内核启动从 ~2459 降至 ~210；batch=1 提速 2.31×（FP8 attention 下 2.85×） |
| **#60831** | `amd-sriram` | GLM-5 (glm_moe_dsa) | 8×MI355X TP8：TPOT 降 40.9%（conc 4）/ 27.4%（conc 8） |
| **#60833** | `mjkvaak-amd` | Qwen3.8 (2.4T-A95B) | TP8 MI355X，Draft 阶段 |
| **#60793** | `amd-mghanimi` | Kimi-K3 MoE | MI355X 单 MoE 层 47.5→36.9µs；端到端 +14.8% 吞吐 |
| **#60889** | `dllehr-amd` | GLM 5.2 | Scaffold PR |
| **#60397 (已合并)** | `Fangzhou-Ai` | DeepSeek-V4.1-Flash | MI355X K1/K2 持久化启动，替换 ~40 内核 |

**技术要点**：
- **统一开关 `VLLM_ROCM_MONO_DECODE=1`**，模型层通过 `vllm/models/<model>/amd/mono/` 组织，共享 `common` 框架（mailbox、peer buffer、GEMV stage）。
- RFC #60904 提出**标准化约 650 行的 shared library** (`vllm/models/common/mono/`)，使新模型只需增加 ~400 行即可接入，避免 6k–24k 行的重复栈。目前 ROCm-only，CUDA 待联合作者加入。
- 关键技术手段：FlyDSL 持久化 kernel + 对称 peer 内存内 all-reduce + 单 launch 融合 sparse indexer。

**注意**：所有 5 个 Mono 相关 PR 都带有 `needs-rebase` 标签，Mergify 均报告合并冲突，提示这批 PR 之间有大量相互依赖和与主线冲突，**合并队列可能存在风险**。

### 🛠️ 重点技术变更

#### 1. **MonoKernel 标准化 RFC（#60904）— 可能改变 AMD 性能代码的组织方式**

这是本周期最具战略意义的文档。当前 AMD 已有 GLM-5.2、DeepSeek-V4.1、MiniMax-M3、Kimi-K3 四套独立 MonoKernel 栈，RFC 主张：
- 模型层循环统一调用 `mono.forward_layer(...)`，**module tree 与 parameter name 不变**；
- 共享 `vllm/models/common/mono/`（~650 行）承担 refusals、routing、fail-stop、health words、peer memory、cache re-binding；
- 单模型新增内核成本从 6k–24k 行降至 ~400 行。

**影响**：若采纳，AMD ROCm 高性能路径将从"复制-修改"模式转向"标准接口"模式，显著降低 MI350X 系列内核的维护熵。CUDA 侧明确预留联合作者接入。

#### 2. **GLM-5.3-Flash 通用 packed KV 布局（#57169，已合并）**

将 `kernel_block_size` 从 `BlockTable` 下沉到 `AttentionGroup`，使**同一 KV cache group 内不同 backend 可使用不同 kernel block size**。这是 KV cache 管理架构的一次分层解耦：
- block table 保持 manager 粒度
- 每个 AttentionGroup 映射到自己 backend 所需的 kernel block
- `block_stride_alignment` 接收 `MultipleOf(n)`，支持 packed block 拆分为 whole kernel blocks

**跨厂商代价**：AMD `ROCM_AITER_UNIFIED_ATTN`、`rocm_aiter_mla_sparse` 与 SM90/SM100 稀疏 MLA kernel 均需补充 `BLHNC` 处理。作者在 MI350X 与 H200 双平台完成 GSM8K + P/D 验证后方合并。

#### 3. **MoRIIO READ 语义修正（#60808）与 hybrid READ 泛化（#60867）**

`#60808` 主张 READ 必须在 `start_load_kv` 内 await 全部传输，理由：
- 现有 `wait_for_layer_load` hook **漏掉 sparse-attention indexer caches**（`DeepseekV32IndexerCache` 无 `@maybe_transfer_kv_layer` 装饰）；
- **MTP/EAGLE drafter 会自行选择 cudagraph 模式**，可能在 PIECEWISE target 之后重放 FULL 从而跳过 hook。

症状是长上下文 P/D 下的间歇性 recall miss——**极难复现但影响正确性**。该 PR 以净删除 48 行完成修复。

`#60867` 在此基础上，使 GLM-5.3-Flash（2 个 attention group + KDA + MTP）首次可在 `main` 上启用 hybrid-READ 分离部署。

#### 4. **ROCm cuMem CUDA-graph pool 卸载启用（#59523，已合并）**

原 `VllmConfig.use_cumem_cudagraph_pool` 仅认 `is_cuda()`，ROCm 上即使 opt-in 也是 inert。本次放开到 `is_cuda_alike()` 并解决两个 ROCm 特有问题：
- `create_and_map` 中 legacy stream 上的**阻塞 `hipMemset`** 会破坏图捕获（`hipErrorStreamCaptureImplicit`）→ 改为在 `wake_up` 阶段对 discarded allocation 清零；
- `mawong-amd` 深入调查后确认：**当前驱动（≥6.10）在释放后已 scrub VRAM**，清零仅在旧驱动下必要，代价约 35ms/150GB KV wake。

**影响**：MI355X 上 sleep/wake 输出正确，显存可回到睡前水平（剩余 0.85–1.5GB 为 HIP 自身 graph memory，可作 follow-up）。

#### 5. **ROCm release 镜像瘦身（#60890）**

在没有牺牲任何功能（vLLM、torch、triton、aiter、flash-attention、MoRI、NIXL、LMCache 全部保留）的前提下，压缩后减小 2.0GB / 磁盘减少 9.4GB，冷拉取解压时间降 19.5%。对于 ROCm 用户群体，这意味着**更低的部署摩擦和 CI 时间成本**，属于高杠杆的工程改进。

**1. 【架构决策】MonoKernel 标准是否会成为 vLLM 上游的正式接口？**
