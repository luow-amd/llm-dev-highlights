#### 1. **#53987 [Spec Decode][ROCm] FLy：熵门控延迟验证**（跨越 8–10 月，评论最多）

- **核心议题**：引入一种**有损**的投机解码验证策略——目标熵高且后续 W 个 draft 全部通过时，可接受一个孤立拒绝。无需额外 checkpoint 或 target forward。
- **观点分歧**：
  - 审阅者（eecspan 转述）明确两条硬性要求：**MRV2 兼容是 must-have**；评测集过时（Llama 3.1 70B + GSM8K/HumanEval/MBPP"过于简单"），要求至少加入 DSV4/GLM5.3/Kimi K3/Qwen3.8 之一 + TerminalBench/SWEBench-Pro/HLE/GPQA-Diamond。

- **争议焦点**：**有损解码是否可默认开启**。结论是 opt-in，标准验证仍为默认；同时明确"单次测量、非质量保证"。
- **状态**：✅ 2026-10-19 合并，历时近两个月。

#### 3. **#62444 [KV Offload] 刷新 GPU 命中前缀的 CPU LRU**（3 条评论，含实质性设计争论）

- **核心议题**：eager 模式下，持续命中 GPU 前缀的 KV 在 CPU 侧从未更新 LRU 位置，反而最先被淘汰。MI355X 上 Kimi-K3 agentic 基准 +9.9% tok/s/GPU，TTFT 9.4s → 5.6s。
- **观点**：
  - SherifWaly：实际遇到长上下文 + 高并发下 prefix cache 命中率大幅下降，patch 后解决。
  - ivanium：**方向认可，但实现不够干净**，建议在 lookup 时直接 touch 对应 prefix block，而不是照搬 `free` 的反向遍历。
  - 作者（whx-sjtu）随后重写为 `cpu_coordinator.find_longest_cache_hit` + 反向 touch/free，覆盖 full-attn、SWA、Mamba boundary。
- **状态**：Open，已按 review 重构一版。

#### 4. **#62510 [KV offload] SSM 组 checkpoint 的占位事件**（2 条长评论，契约级讨论）

- **核心议题**：`OffloadingEventsTracker` 对 SSM / sliding-window 组只发 `block_size=0` 的 placeholder `BlockStored`，外部索引器（Dynamo KV router）因此高估可复用前缀——实测路由器认为可复用 3 个 block，引擎实际复用 0，每请求搬移并丢弃 57 MB。
- **观点**：
  - adenzhou1350：做了 6 项独立 CPU 组件检查，验证 Mamba lookup 的实际语义（16-token state page、4-token hash unit、28 boundary 等），指出 GPU 侧 partial-checkpoint 事件携带的是"一个 boundary hash + block_size=4"。
  - he-yufeng：**逐行读完 tracker，认为 placeholder 是"有意为之"而非疏漏**——`record_store`/`record_lookup` 对所有 `sliding_window_size_in_chunks is not None` 的组直接 early-return，所以从未采集元数据。指出 #62538（同日关闭、未 review）曾选"只描述承载 chunk 末尾循环状态的 block"，但留下两个未决问题。
- **争议焦点**：这不是局部补丁，而是**wire contract 决策**——自描述 SSM 事件到底"表示什么"。需要明确 parent hash 语义、ownership、BlockRemoved 配对规则。
- **状态**：Open，社区尚未收敛。

#### 5. **#62466 / #62467 persistent_topk 越界索引**（2 条评论，闭环最快）

- he-yufeng 逐层确认根因：`load_float4_predicated` 用 `-inf` 填充尾部 lane → Phase 1 无条件计 bin → Phase 2 的 `vec_valid` 只约束 vector 不约束 `elem_idx` → Phase 3 用越界 index 读 logits（compute-sanitizer 报 OOB）。
- 同时明确指出**可达性极低**：默认配置下 `candidate_topk_blocks × candidate_block_size = 2048 × 8 = 16384` 覆盖所有 ≤8192 行，"no shipped model reaches this bug"。
- 修复 PR #62467 当日合并，测试 294 passed。

### 🛠️ 重点技术变更

#### 1. **#60731 [ROCm][Perf][DSv4.1] MI300X/MI325X Mono decode**（✅ 合并）
将 DeepSeek-V4.1-Flash 的标准 decoder layer 从 **32 个 kernel 合并为 2 个**（gfx942 移植自 gfx950 #60397），opt-in `--monokernel`。MI325X TP4 + DSpark 5 drafts 实测：AgentX c1 交互性 P50 **216.85 → 503.53 tok/s/user（2.32×）**，c2/4/8 的 P90 分别 2.41×/2.22×/1.99×；单层 115 µs vs 320 µs。GSM8K 0.9247 → 0.9270（p=0.49，不显著）。**这是 AMD 单卡 decode 延迟优化迄今最显著的收益之一**，且严格限定在 `vllm/models/deepseek_v41/` 与 DSpark 8 行 hook 内，符合 RFC #60904 的"不碰共享代码"要求。

#### 2. **#62475 ROCm 编译并行化**（🔵 Open）
9 分钟单核编译是 ROCm 开发体验的核心痛点。7.6× 提速不仅是 CI 成本问题，更直接影响**开发者迭代速度**与 ROCm wheel 发布节奏。代价（+11.6% 二进制约 23MB、+30% CPU 总功）可接受。遗留的 `-fno-gpu-rdc` 依赖被作者自己标为风险点，值得跟踪。

#### 3. **#61943 AITER top-k for DSV3.2/GLM-5 sparse indexer**（✅ 合并）
在 gfx950 + AITER 下，为 `index_topk=2048` 的稀疏 indexer 启用 AITER top-k（decode + 最长行达 32K 的 prefill chunk）。GLM-5.2-MXFP4 128K/1K TPOT 在 c1/c8/c16 下 **−7.0%/−4.6%/−3.0%**，8K/1K 在噪声内，GSM8K/passkey 不变。这是**长上下文场景的针对性优化**，也是 AITER 适配层复用的典型案例（复用 #52882 为 V4 加的 adapter）。

#### 4. **#62467 persistent_topk 越界修复**（✅ 合并，当日闭环）
问题从 #62466 提出到 #62467 合并仅 4 小时，是"高质量 issue + 精准根因 + 及时修复"的范本。虽然实际可达性低，但它揭示了一个**通用陷阱**：`load_float4_predicated` 的 `-inf` 填充 lane 会被当作真实元素参与 histogram，一旦阈值落入 `-inf` bin 就污染候选集。对任何基于 float4 + histogram 的 top-k 实现都有借鉴意义。

#### 5. **#62560 MRV2 sampler warm-up**（🔵 Open）
`capture_model()` 末尾的 `empty_cache()` 清掉 sampler 的 fp32 logits 副本缓存，导致负载爬升时每遇到更大 batch 就新分配一块且小块不释放。V1 早已在 `compile_or_warm_up_model` 中"故意"在 capture 后跑一次最大 batch sampler，MRV2 遗漏了这一步。Qwen3-4B 显存增长 **+1.78 GB（18 步）→ +0.11 GB（1 步）**，Gemma-4-31B TP4 每卡 **+0.24 → +0.003 GB**。测试恰好在 **AMD Radeon AI PRO R9700** 上完成，是 RDNA 平台参与核心缺陷验证的一个信号。

### 💡 值得关注的问题

1. **#62510 SSM 事件契约亟待决策**：placeholder `BlockStored` 是"有意设计"还是"待补缺陷"目前社区尚未统一。这直接影响 Dynamo KV router 等多级缓存外部索引器的正确性，且与 `record_store`/`record_lookup` 的 early-return 逻辑耦合。建议维护者明确 wire contract 后再接受补丁。

2. **#62558 TurboQuant + GDN 混合模型的复合缺陷**：manager block 无法拆分成 kernel block（1712 vs 16）、fp8 drafter 放大 KV 页、RDNA gfx1201 平台。三个问题叠加，涉及 `get_supported_kernel_block_sizes`、`--mamba-cache-mode align`、投机解码 draft 层的内存核算。**这是 RDNA 上最值得跟踪的量产阻塞问题**。

3. **#62606 gfx950 `ROCM_AITER_UNIFIED_ATTN` 静默错误**：2–4 GiB 单层 KV cache 时无报错输出错误，根因在 aiter 的 32-bit buffer load。这类**静默错误对生产环境影响最大**，且 vLLM pin 的 aiter v0.1.25/v0.1.26 均受影响，需要下游 aiter 修复并同步。

4. **#62588 MI300X SR-IOV 多进程挂起**：DigitalOcean devcloud 单 VF、GFX 100%、无 wave。如果确认是 SR-IOV 下 MEC/RLC 固件或 `amdgpu` 6.19 的问题，将影响云厂商多租户部署 vLLM 的可行性，需硬件/驱动侧协同。

5. **#62484 CPU build 在 NVIDIA driver 可见时失败**：Triton `_create_driver()` 优先选 NVIDIA 后端（即使 PyTorch 为 CPU-only），导致 `_gumbel_sample_kernel` 调用 `torch.cuda.current_device()`。WSL2 / 有独显开发机上是常见场景。作者给出两个 workaround（`TRITON_DEFAULT_BACKEND=cpu`、`CUDA_VISIBLE_DEVICES=""`）但尚未修复。

6. **#61673 已关闭但需复盘**：cascade attention + `SimpleCPUOffloadConnector` 下**请求用他人 KV 前缀解码**——这是数据正确性最高级别的 bug，Issue 关闭但未见关联修复 PR 的显式说明，建议跟踪其修复落地情况。

7. **#62475 的 `-fno-gpu-rdc` 隐性依赖**：作者明确警告 `warpReduceMax` 是 header 中的非内联 `__device__` 定义，能链接仅因 `-fno-gpu-rdc`；一旦启用 RDC 或加入 host-side helper 即断链。这是 ROCm 构建链上的**技术债标记**，应纳入后续清理计划。
