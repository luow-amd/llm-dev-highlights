## 🎯 AMD/ROCm 生态相关动态

### 1. 严重开放问题：GLM-5.3-Flash 在 gfx950 上低并发乱码（#59413）

这是本周期**最值得警惕的 AMD 问题**。`simondanielsson` 报告在 8×MI350X、TP8、`ROCM_AITER_MLA_SPARSE` 后端下，低并发（concurrency 1/2）时 GSM8K 准确率跌至 0.0015，温度设为 0 后输出明显乱码（如 "Paris人为 primal Voting..."）；gfx942 上不复现，TP2/TP4 正常。`vllmellm` 随后确认可复现，并给出**关键线索**：设置 `VLLM_ROCM_USE_AITER_MOE=0` 可在并发 1 时恢复连贯输出。目前 Issue 仍开放，尚无根因结论，疑似 AITER MoE 在 gfx950/TP8 低并发路径上的数值或调度缺陷。

**关联对照 #59416**（已关闭）：gfx942 上 GLM-5.3-Flash 在长 prefill 时崩溃，根因是 AITER 0.1.22.post1 的 FlyDSL `fp8_mqa_logits` 中 `_fn_to_fnuz_i64` 将 Python `int` 传给 `raw.shrui(32)`，被 FlyDSL 0.3.2 拒绝；通过 AITER 0.1.23 bump（#58867）已修复。AMD 员工 `jin-amd` 提供了完整的根因分析与 MI325X 对照实验，是 AMD 员工参与 upstream issue 诊断的典型案例。

## 💬 高热度讨论分析

### ① #59413 GLM-5.3-Flash 在 gfx950 低并发乱码（4 评论，开放）

**核心议题**：MI350/TP8 + AITER MLA sparse 后端下，低并发时模型输出完全退化，高并发反而正常。

**各方观点**：
- `simondanielsson`（报告者）：提供温度 1/温度 0 对照、并发 1/2/8 对照，指出 TP2/TP4 正常，怀疑与 TP8 相关。
- `vllmellm`（AMD 侧）：确认在 gfx950 TP8 上复现，TP2/TP4 正常；**并提出关键定位信息**——`VLLM_ROCM_USE_AITER_MOE=0` 在并发 1 时可恢复连贯输出，暗示问题落在 AITER MoE 路径。

**争议 / 焦点**：乱码只在低并发出现、TP8 特定，且与 MoE 后端开关强相关，指向 AITER MoE 在 gfx950 上的 kernel 选择或 reduce 逻辑。目前无定论，需 AMD 侧进一步二分定位。

### ② #55368 AITER MoE padding（10 评论，已合并）

**核心议题**：CK 2stages MoE kernel 要求 inter_dim 对齐，K2-Horizon-375B 的 224/448 触发 `device_gemm ... does not support this GEMM problem`。

**各方观点**：
- `sshlyapn`（作者）：分配时 padding 是功能性修复，且 AITER 本身会受益（TTFT +23%、TPOT +6.5%），并已在 ROCm/aiter#5444 立项从 AITER 侧根治。
- `tjtanaa`：质疑能否用 `AITER_ONLINE_TUNE=1` 免于 padding 开销。作者回复：tile width 非可调参数，CK 按 inter_dim 直接派发，tuning 无解。
- `ChuanLi1101`：提出三点合并前必须：**expert-group 舍入需要数值验证**（不能只看 kernel 存在）、**需量化 padding 带来的额外计算**、**明确说明 fp8 对齐未受影响**。作者逐条回应并补充 K2 Horizon 端到端数据。

**结论**：合并。争议体现了 AMD 侧"在 vLLM 打补丁 vs 在 AITER 修根因"的典型权衡。

### ③ #58819 DeepSeek V4.1 a4w4 MoE（6 评论，已合并）

**核心议题**：AITER a4w4（FP4 激活）路径的接口正确性与默认行为。

**各方观点**：
- `ChuanLi1101` 提出四点 review：调用私有 `_fused_moe_impl` 会绕过 `shared_w1` 分支（DeepSeek V4 将来会 break）、env 变量 `"true"` 会崩溃、AITER pin 版本与注释不符、建议改用公开 `fused_moe(quant_dtype_a=...)`。
- `Fangzhou-Ai`（作者）全部确认并修复：改用公开 API、增加 `fused_moe_supports_quant_dtype_a()` 签名探测、启动时清晰报错；并补充 TP2/MI355X GSM8K A/B（a4w4 0.9727 vs a8w4 0.9735，1 stderr 内）。

**结论**：合并。是一次"私有 API 依赖"风险的教科书式修正。

### ④ #59510 derender 批处理隐藏 stop 文本（5 评论，开放）

**核心议题**：`/derender` 反解码时 stop token 泄漏，讨论"如何判断最后一个 token 是否应丢弃"。

**各方观点与戏剧性转折**：
- `shimib` 先建议更简洁的规则：`finish_reason=="stop"` 且无 stop 字符串匹配即丢弃最后一个 token。
- 作者 `pOpO1-9` 采纳。
- `shimib` 随后**主动走回**：该规则在 `test_e2e_token_identity`（`encode(derender(ids)) == ids` 的 RL 不变量）等 7 个已有测试上失败，因为测试的输入不含尾随 stop token；"真实引擎会补回 stop/EOS id，但 derender 不应假设输入如此"。
- 最终恢复为成员检查规则（client `stop_token_ids` ∪ `tokenizer.eos_token_id` ∪ generation_config eos list）。

**结论**：开放。这是本周期最有价值的技术讨论之一，展示了"正确规则"必须同时满足真实流量与测试契约。

### ⑤ #57084 面向编码 agent 的 PR checklist（9 评论，已合并）

**核心议题**：agent 生成的 PR 描述冗长问题。

**各方观点**：`faradawn` 建议限制 100–200 词，`AndreasKaratzas` 给出自身 prompt 实践（3–5 bullet + 3–6 句动机 + 表格），`njhill` 建议补充"禁止在主执行线程做 CPU↔GPU 同步检查"等条目，`benchislett` 折中为"header 段限制 1–2 行摘要，Validation/Notes 允许详尽"。**结论**：合并，成为 vLLM 首个正式 agent 贡献规范。

## 🛠️ 重点技术变更

**1. #58819 [ROCm][Perf] DeepSeek V4.1 a4w4 MoE（已合并）**
为 DeepSeek V4.1 增加 opt-in 的 FP4 激活 MoE 路径。作者发现 AITER INTERLEAVE 阶段一 GEMM 在 fp4x2 下无 tuned FlyDSL 配置会静默退化，最终改为 ATOM 的 `GateMode.SEPARATED` 布局（单 flag 翻转）。**影响**：为 ROCm 上的低精度 MoE 提供新选项，但默认关闭，且强制校验模型类型，避免对未验证模型静默生效；同时修正了对 AITER 私有 API 的依赖。

**2. #55368 [ROCm][MoE] AITER MoE 分配时 padding（已合并）**
修复 AITER CK 2stages MoE 对 inter_dim 的对齐要求，并通过 expert-group 数舍入规避 AITER 只实例化 `NUM_GRP∈{1,2,4,8}` 的问题。**影响**：使 K2-Horizon-375B 等非对齐形状模型能在 ROCm 上运行；AITER 侧收益 TTFT +23%、TPOT +6.5%；同时明确了 fp8 对齐路径不受影响。

**3. #59393 + #59395 Rust 前端文法重构（已合并）**
将结构化标签文法快照从单行 JSON 改为可读 outline，并将 argument grammar 拆分为"通用 schema 解析"与"模型特定渲染"。**影响**：把新参数格式从"依赖 XGrammar 发版"解绑，解决 Kimi K3 union 类型标签与值不匹配问题，并防止 `$ref` 嵌套导致的指数级展开（4^12 选项、>30s 编译）。这是 Rust 前端走向可维护化的重要基础。

**4. #55422 Docker 构建期编译 Python 字节码（已合并）**
8 个 Dockerfile 设置 `UV_COMPILE_BYTECODE=1`。作者做了严格的隔离实验（同源、同解释器、244 个发行包、26,734 个文件匹配，缓存前后对照），首次正确响应中位数 47.69s vs 57.04s，节省约 10s；导入跟踪显示 5,118 次源码编译 → 0 次、编译耗时 8.20s。**影响**：容器冷启动显著提速。

**5. #59538 RFC 可复用 KV 压缩层（开放）**
提出算法库 + 配置选择 + 编解码的抽象，KVServe 管理压缩工作流，Mooncake P/D 为首个集成。引用实测：Llama-3.1/Qasper P/D 在 10–50 Gb/s 链路上通信占 JCT 的 16%–60%。**影响**：若落地将直接影响 D 分离与 KV cache 复用的成本结构。

## 💡 值得关注的问题

1. **gfx950 低并发乱码（#59413）仍未定位**——目前仅到"AITER MoE 开关可缓解"，建议 AMD 侧尽快二分 MoE 后端的具体 kernel（CK 2stages？FlyDSL？）并检查 TP8 下的 reduce/通信路径。若为真，这是 MI350/MI355 生产部署的阻塞性问题。
2. **ROCm 原生解码上限提升的评审未闭环（#59420 / #59421）**——`AndreasKaratzas` 提出的"是否应改在 AITER 侧修复"和"性能回退"两问尚未得到作者回复，可能拖慢合并。
3. **#59413 与 #59416 的 gfx942/gfx950 行为分化**——同一模型在两代 CDNA 上表现迥异，提示 AMD 需要在 CI 中强化 gfx950 的模型级回归覆盖（当前多数 ROCm CI job 以 gfx942/MI355 混合为主）。
4. **Quark 的加载路径健壮性（#59443）**——`from_quant_config` 对未知 config 一律抛错，新增量化方案时会重复踩坑；建议引入 default-allow 或更细的 capability 声明。
5. **#59460 `VLLM_STRICT_QUANT_SCHEME`**——显式化激活量化回退是一个正确的方向，但需确认严格模式不会改变后端优先级、且与 #59438 的 `activation null` 语义一致。
6. **#59502 模块级权重重载 RFC**——涉及 CUDA graph 捕获下派生状态地址失效、在线量化 per-expert 完成等深层问题，影响 RL 训练框架与 vLLM 的耦合方式，建议社区重点评审。
7. **#59538 KV 压缩层 RFC**——KV 传输/存储压缩会牵动 NIXL、Mooncake、LMCache 等一整条连接器链路，抽象边界需及早定清。

---

**报告结论**：本周期 vLLM 的 AMD 侧工作呈现"性能优化加速 + 新模型适配 + 旧 bug 清理"三线并进，但 **gfx950 上的 GLM-5.3-Flash 乱码**是必须优先解决的可靠性红灯。通用方向上，KV/权重/压缩三项可复用性 RFC 与 Rust 前端重构，标志着项目正为长生命周期、分离式、热更新的下一阶段部署形态打基础。
