#### ③ Issue #61539 —— RFC：Routed-expert capture 的显式行布局（✅ 已关闭）

- **核心议题**：`RoutedExpertsCapturer` 目前靠行数与 `dp_metadata` 推断 DP rank 行归属，对 out-of-tree MoE backend（如 Ascend 的 all2all 不均匀 TP 分片）不安全。
- **三种竞争方案**：
  1. **#62441（Liamup777）**——显式 layout：在 router/capture 之间传递 row layout，改公共路由代码，附带 17 配置 / 144 HTTP 请求的大规模 Ascend A3 验证。
  2. **Platform.get_routed_experts_local_rows（Ronald1995）**——更小的替代：在 Platform 接口加 hook，默认返回 `None`，保持现状；代价是共享恢复逻辑减少、后端各自实现。
  3. **#64689（Liamup777）**——折中：在 **MoERunner / MoE layer** 上挂 `restore_routed_experts_rows(topk_ids)`（不挂 Platform），保留默认 DP/TP 恢复，改动面最小。
- **最终结论**：#64689 合并入 main；作者在 2026-11-10 明确「#62441 已被 supersede，RFC 关闭」，Ascend 侧 patch 移除另由 vllm-ascend#20765 跟踪。
- **启示**：这是**「大重构 vs 小 hook」** 设计权衡的教科书案例——社区最终偏好在 MoE 层而非 Platform 层引入扩展点，以最小化公共代码改动。

#### ④ PR #66605 —— 外部 KV connector 声明 KV cache 注册（🆕 Open）

- **核心议题**：让 out-of-tree KV connector 通过 `registers_kv_cache_memory()` 声明是否需要为 RDMA 注册 KV cache，否则 `ibv_reg_mr` 会因 extensible KV cache 分块分配而失败。

- **影响**：与 LMCache MP、NIXL、Mooncake 的 extensible KV cache 生态直接相关，不只是 AMD 生态受益。

#### ⑤ PR #60390 —— Qwen4Exp PLE 表跨 DP replica 共享（✅ 已合并，范围收窄）

- **核心议题**：原实现支持**跨独立 engine 进程**共享 PLE 表（flock + `.ready` 协议），被 reviewer gau-nernst 收窄为仅 `dp_shared_memory` 路径（同一 engine 内共址 DP replica 共享）。

### 🛠️ 重点技术变更

**1. #66532 Kimi K3.1 ROCm TP8 支持（已合并）**
为 Kimi K3.1 引入 AMD 专用模型文件：FP8 indexer、FlyDSL sparse MLA kernel、packed hybrid block size 及 KDA 更新。MI355X gfx950 现可在 TP8 下服务 K3.1。技术意义在于**首次让 Kimi 系列在 ROCm 上与 NVIDIA 同步可用**，但 Pundit 的 5 项发现（含 DCP>1 崩溃、gfx950 启动期 gating）需要后续补丁。

**2. #66564 Quark MXFP4 MoE + 动态 MXFP8 激活（jimmy-adams）**
新增 `w_mxfp4_a_mxfp8` scheme，在 gfx950 + AITER 上经 `moe_gemm_a8w4` 执行：GEMM1 内联 SwiGLU-OAI 并输出 MXFP8，GEMM2 消费；MiniMax2 路由参数直通 AITER。这是**AMD Quark 量化栈向前沿 MoE 模型推进的关键一步**，也体现 Quark 与 AITER 的深度耦合。

**3. #63847 persistent_topk 上 ROCm（已合并，AndreasKaratzas）**
用 hipcc 编译 `persistent_topk` / FilteredTopK / sampled_topk，gfx950 上走 `sampled_topk_kernel`。**同时修复了一个隐蔽 bug**：`rocm_fp8_paged_mqa_logits` 的 decode logits 与 top-k workspace 在共享 workspace 均从 offset 0 开始（gfx942 上 corrupt row 0），通过把 logits 放在 top-k workspace 之后解决。这类 CUDA 侧不存在、ROCm 侧独有的内存布局问题是 AMD 后端成熟的典型障碍。

**4. #66644 AITER MegaMoE 接入 DSv4.1（已合并）**
V4 MoE 基类早已支持 MegaMoE，但 V4.1 硬编码 `use_mega_moe = False`。本 PR 移除该限制，MI355X DP8/EP8 + DSpark 下 GSM8K 略升。**使 DSv4.1-Flash 能充分利用 AITER 融合 MoE 内核**，是 #66587 追踪器中多个上游优化的落地前提。

**5. #60390 PLE 表共享（已合并，范围收窄）**
让同一 engine 内 DP>1 且 PLE CPU offload 时共址 replica 共享一张表（Qwen3.8-Flash-Next FP8 每 rank 48 GiB），显著降低显存与主机内存压力。跨独立 engine 进程共享（作者真实需求）被拆为后续 PR。**代表大模型 CPU offload 内存优化的重要方向**。
