### 🎯 AMD/ROCm 生态相关动态

本章节特别关注与 AMD 生态相关的所有改动，包括构建修复、性能优化、新硬件支持和 CI/CD 建设。

1.  **【关键修复】ROCm 构建失败紧急修复：** Issue #44641 报告了因上游 PR #44334 引入的 Torch 2.11 特有 API 导致 ROCm 镜像（使用 Torch 2.10）构建失败的问题。**AMD 员工 `tjtanaa`** 迅速响应并提交了 PR #44648，该 PR 已被合并。此修复为 ROCm 平台回退到旧版 ABI，确保了 vLLM 在 AMD GPU 上的基础构建能力和 `silu_and_mul_per_block_quant` 等关键算子正常工作。

2.  **【Quark 兼容性强化：**
    *   PR #44626 (`xaguilar-amd`): 修复了使用 **Quark** 工具量化的 FP8 注意力权重因 scale 编码不一致而无法使用 AITER 预洗牌 GEMM 加速的问题。通过修改 `is_per_channel()` 判断逻辑，使 Quark 量化的 attention 层能调用更快的 `gemm_a8w8_bpreshuffle` 内核，在 Kimi-K2.5 模型上预填充和解码阶段分别获得了 11-13% 的加速。
    *   PR #44651 (`xuebwang-amd`): 为 AITER 融合共享专家路径添加了量化兼容性防护。检测到 **Quark MXFP4** 量化的 DeepSeek-V2/V3/Kimi-K2 模型时，会自动禁用不兼容的 `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1` 配置，防止模型推理出垃圾结果。

3.  **【NVFP4 仿真加速：** PR #44667 (`fxmarty-amd`): 针对在缺乏原生 NVFP4 硬件的平台上（如 AMD MI350），引入一个融合 Triton 内核，将 NVFP4 权重反量化过程与 MoE MLP 的 GEMM 计算融合，避免了在 HBM 中物化大型中间 BF16 张量。对于 Kimi-K2.6-NVFP4 模型，该优化带来了高达 **10.8 倍**的加速。

4.  **【高层 CI 路线图倡议：** 贡献者 `functionstackx` 提出了两个关于 AMD CI 的重大 Feature Request：
    *   Issue #44711: 提议在 MI455X GPU 上建立 Day 0 CI，并为 2026 年的前沿 MoE 模型建立多节点、FP4、预填充分离的推理测试。
    *   Issue #44710: 提议在 AMD Advancing AI 2026 大会（2026年7月22日）前，将 AMD 测试组的门禁状态覆盖率提升至 90%。

5.  **【其他 AMD 相关优化与修复：**
    *   PR #44679 (`Rohan138`): 修复了 `rocm_aiter_fused_experts` 中 `intermediate_pad` 在 TP>1 时计算不准确导致的精度下降问题。此前，AITER 在不同 TP 规模下使用不同内核，导致 TP=8 时精度显著下降，此修复恢复了正确性。
    *   PR #40426 (`hanlin12-AMD`): 合并了 AITER hipBLASLt GEMM 在线调优支持，通过环境变量启用。
    *   PR #42832 (`akii96`): 合并了 GPT-OSS 模型在 ROCm 上的 RoPE + 静态 FP8 量化 + KV Cache 融合优化，提升了解码性能。

    *   PR #44623 (`qli88`): 提供了一个 Triton 版本的 `SiluAndMulWithClamp` 算子，以支持 ROCm 平台。

### 💬 高热度讨论分析

1.  **Issue #44641 (ROCm Build Failure):**
    *   **议题：** PR #44334 引入的 Torch 2.11 特性导致 ROCm 构建失败。
    *   **观点：**
        *   `vllmellm` (报告者): 明确指出问题源于条件编译不准确，将 Torch 2.11 特有的 API 暴露给了使用 Torch 2.10 的 ROCm 用户。
        *   `tjtanaa` (AMD开发者): 快速确认问题并提交了修复 PR #44648，提出回退到旧 ABI 的方案。
        *   讨论焦点在于修复的权衡：是临时回退（可能会带来性能或功能损失），还是寻找更优雅的解决方案。最终快速合并了修复方案以恢复构建。
    *   **争议焦点：** 无重大争议，核心是快速恢复稳定构建。
    *   **状态：** 通过 PR #44648 解决并合并。

2.  **Issue #44632 (Missing Logger Output with DP):**
    *   **议题：** 使用内部数据并行 (DP) 负载均衡和多个 API 服务器 (`api-server-count > 1`) 时，日志输出部分丢失。
    *   **观点：**
        *   `ShadowcatBW` (报告者): 详细描述了日志丢失的现象，指出在 DP 场景下关键监控指标缺失。
        *   `charukeas-t`: 迅速响应，表示已理解问题并会提交修复。其后续提交的 PR #44646 分析了根因：`StatLoggerManager` 为“避免不完整统计”而静默禁用了所有 API 服务器的日志。
    *   **状态：** PR #44646 已创建用于修复此问题。

3.  **PR #44677 (DBO ++: Overlap TP all-reduce with compute):**
    *   **议题：** 通过双批次重叠 (Dual-Batch Overlap, DBO) 技术将 TP 通信时间与计算时间重叠，以优化 Prefill 性能。
    *   **观点：**
        *   `blackwargreymonX` (作者): 介绍了 DBO 技术，将 forward 拆分为两个微批次，利用独立 CUDA 流让 all-reduce 与计算并行，在 Qwen3-32B 模型上实现了最高 10-12% 的 Prefill 性能和吞吐量提升。
        *   `mgoin` (维护者): 提出建设性意见，指出对比基线不应是 eager 模式，而应是 `VLLM_COMPILE + PIECEWISE` 模式，以更公平地评估 PR 带来的增益。作者接受建议，将补充相应对比数据。
    *   **争议焦点：** 无原则性争议，主要是关于基准测试设置的科学性。
    *   **状态：** 讨论进行中，作者承诺将更新性能对比数据。

4.  **PR #40426 (AITER hipBLASLt Online Tuning):**
    *   **议题：** 为 AITER 添加 hipBLASLt GEMM 在线调优功能。
    *   **观点：**
        *   `hanlin12-AMD` (作者): 提供详细的性能对比和精度测试，证明在线调优能显著提升性能。
        *   `tjtanaa` (AMD维护者): 参与多次审查，要求提供 `lm_eval` 精度分数和速度提升数据，并反复确认代码在审查变更后的稳定性和准确性。
    *   **争议焦点：** 无显著技术争议，审查过程严格，要求充分的数据支撑。
    *   **状态：** 经过多轮审查和要求，最终合并。

### 🛠️ 重点技术变更

1.  **PR #44648 ([Bugfix] [ROCm] [Critical] fallback to regular abi for ROCm):** **【关键】** 这是解决 ROCm 构建失败的“救火”修复，直接关系到 AMD 用户的日常使用。通过条件编译，为 ROCm (Torch 2.10) 回退到旧的 ABI，确保了稳定版本的可用性。

3.  **PR #44651 ([ROCm][Bugfix] Add quantization compatibility guard...):** 该 PR 体现了工程实践中防御性编程的重要性。它避免了因配置不兼容导致的“静默错误”（模型跑出错误结果而无警告），通过主动检测和降级，不仅提升了用户体验，也降低了排查问题的难度。

4.  **PR #44636 (Move DP sync to a dedicated CUDA stream):** 这是一个典型的性能优化，通过将 DP 同步操作移到专用的 CUDA stream 上，避免了与模型计算主流的同步阻塞。在 DP 规模较大（如32路）且使用 spec decode 的场景下，性能提升非常显著（TPS 提升超 40%）。

5.  **PR #44652 [Triton][Spec Decode] Non-causal support...:** 该 PR 为 Triton 注意力核增加了非因果注意力和多查询验证的支持，这是实现 DFlash 等推测解码方法所必需的。此举将提升 Triton 后端的通用性和在推测解码场景下的表现。
