### 🛠️ 重点技术变更

#### 1. #60413 — RDNA3/RDNA3.5 的 W4A8 int8-dot MXFP4 GEMV（已合并）

这是本周期对 AMD 消费级/iGPU 生态最具实际价值的合并。技术要点：
- 用 `v_dot4_i32_iu8` 做每 32 元素一组的 int8 点积；由于 E2M1 值 ×2 后是 [−12,12] 的整数，权重可经 16 项查表**精确**映射到 int8，每组仅需一次 fp32 乘法合并 E8M0 权重 scale 与激活 scale。
- **直接读取 Quark OCP MX 检查点布局**（`[N, K/2]` uint8 E2M1 + `[N, K/32]` uint8 E8M0），无 repack、无额外权重内存——这对 Quark 用户很关键。
- M≤8 与 M>8 的 split 封装在 custom op 内，torch.compile 与 CUDA graph 只看到一个 op。
- 收益：gfx1151 单流 decode 较默认 emulation **5.8x**；代价是 int8 激活舍入与检查点声明的 MXFP4 QDQ 不完全一致，因此 **opt-in**。

#### 2. #61482 — DeepSeek-V4-Pro 的 MI355X mono decode 层（已合并）

将 decode 层实现为两次 persistent FlyDSL launch，独立打包在 `vllm/models/deepseek_v4/amd/mono/`，并显式保留 **ROCm/ATOM 的 MIT 归属与 AMD 版权**。作者放弃了与 V4.1-Flash 共享抽象的路径，选择"先独立、后做 vendor 抽象"，这在评审上是明智的（缩小 diff）。需注意其性能数据复用了历史 baseline、未重跑，delta 包含栈差异。

#### 3. #63491 + #63483 — MiniMax-M3.1 的 SP prefill 与 DBO under pure TP

- **#63483** 的核心不只是 DBO：它记录了 ROCm 上 **hipBLASLt handle 预热缺失导致 DBO step GPU hang** 的根因与修复，并让 comm stream 运行在高优先级。这个知识点对其他使用 comm/compute overlap 的 ROCm 特性有复用价值。
- **#63491** 把 residual stream 按 token 切分，把每层两次 bf16 TP all-reduce 换成 o_proj all-to-all + reduce-scatter，并让 norm/quant/router 只在 1/4 token 上运行；MoE 使用 FlyDSL 的 MXFP8/MXFP4 prefill 链。收益显著（32K TTFT −33%，8×16K 并发 +50%），但 opt-in、代码量大，需关注长期维护成本。

#### 4. #63527 — Muse Spark monokernel 叠加 fp8 KV

这是一个"两个加速手段不能共存"的典型解除。技术约束写得很清楚：Phase A / B2 不碰 cache（vLLM 插入并 attend），只需 guard；K1 在 kernel 内做 e4m3 插入并用 `v_cvt_pk_fp8_f32` RNE 舍入到 ±448，**字节与 stock ROCm 插入逐位一致**；split core 读 e4m3 page 后在寄存器内扩到 bf16 并乘 `k_scale`/`v_scale`；`kv_fp8` 作为 build key 只在 cache 为 fp8 时编译。这种"cache dtype 作为编译变体"的处理值得其他 kernel 参考。

#### 5. #63513 — Mooncake 跳过 KV 块中的 padding（未合并）

混合模型的 KV cache group 共享一次分配，Mooncake 此前为每个 group 的每一层注册并整页拷贝，导致 Kimi-K3（DCP8）每个 KDA value 的 **30% 是无效字节**（20.7% 属于其他 group 的 slot、9.0% 是 state padding）。PR 引入 `block_used_len` 与 `block_len` 分离，只拷贝实际使用的字节，单个 KDA state 从 ~359MB 降到 253MB。这是"分布式 KV store 带宽/容量优化"中少见的、数据非常扎实的一类改动。

### 💡 值得关注的问题

1. **#63455 — ROCm 上 AWQ 完全走不到 W4A16 kernel**。根因明确（`get_quant_method` 中 ROCm 无条件走 legacy 路径），影响 gfx11/gfx12 上的 4-bit decode，当前**无 AMD 维护者回应**。这是本周性价比最高的修复入口，且与 #60413 的 MXFP4 工作同属 RDNA 量化路径。

4. **#63518 / #63473 — 两个静默精度劣化**：AITER ASM attn kernel 丢弃 sink（依赖上游 ROCm/aiter#6906），以及 flashinfer_cutlass MoE 在 SM120/SM121 上输出损坏。建议社区在 CI 中对"sink 模型 + 投机解码"和"非 SM100/103 的 MoE 后端"增加数值断言。

6. **#63549 — async scheduling + preemption 的 KeyError 影响面极广**。作者代码级检查显示该问题自 #27756（v0.11.1）起存在，且 v0.24 的 #45840 移除了 `assert not scheduled_in_prev_step` 保护。在 500–800 并发、长 prompt、触发 preemption 的场景下会拖垮整个 EngineCore。建议提升优先级并补充 preemption + async scheduling 的 CI 用例。
7. **#63505 — GD​N hybrid + PP 在 sm_86 的 Inductor 触发型回归**。目前定位到"编译产物而非 CUDA graph"，下一步应优先导出 `triton_poi_fused_mul_silu_slice_2` 定义与 call site，判断是共享 PP/GDN state 绑定问题还是 Triton 代码生成问题。
8. **#63527 / #63547 / #63528 — M3.1 系列 PR 的验证完整度不一**。#63547 明确声明 AgentX 扫频与精度对比尚未运行，#63527 当前有 rebase 冲突，#63528 的基准详尽但依赖 #63232 的私有扩展。建议在合入前统一要求 MI355X 上的端到端精度基线（GSM8K/GPQA/NIAH），避免"性能 PR 合入但精度问题滞后暴露"。
