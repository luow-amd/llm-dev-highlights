#### ② Issue #57721 — Mamba 混合模型 + 投机解码无法启动（page padding 未计入 num_spec）

- **核心议题**：`ibm-granite/granite-4.0-h-tiny` 在 `num_speculative_tokens >= 2` 时启动即 `AssertionError: page_size_padded >= page_size`。
- **根因分析（`khushali9`）**：`get_mamba_state_shape_from_config` 未传 `num_spec`，而运行时 `MambaMixer2.get_state_shape` 已包含 `num_spec`，导致规划的 padded page 尺寸过窄。
- **纵深观点**：
  - 已解决模型：`mamba2.py`、`nemotron_h.py`、`qwen3_next.py`、`olmo_hybrid.py` 均已正确传参。
  - 遗漏模型：`granitemoehybrid.py`、`falcon_h1.py`、`zamba2.py`（`mamba2_state_shape` 路径）。
  - **额外发现**：`lfm2.py` / `lfm2_moe.py` 调用 `short_conv_state_shape` 时同样遗漏，**且不在 #47635 的修复范围内**，属同一缺陷的未被覆盖实例。
- **当前状态**：open；已确认 #47635 可修复其中 3 个模型，`lfm2` 需追加一行修复。

#### ③ Issue #57725 — 畸形结构化输出返回空消息 500 + 自引用 `$ref` 生成中途杀死请求

- **核心议题**：两类问题：(1) 9 种畸形 JSON schema / regex / grammar 均返回 `500` 且 `message` 为空；(2) 自引用 `$ref` 通过验证后，在生成首个 token 时 FSM 崩溃。
- **多角度验证（`zhaoyboo`）**：

### 🛠️ 重点技术变更

#### 1. **#57750 — RDNA3 上禁用 AITER attention query 量化**（AMD 生态最关键修复）
RDNA3（gfx11）无低精度 WMMA，AITER 强制量化 Q 后 Triton 编译器在 gfx1151 上表现异常（默认将 fp8 矩阵乘算子上转为 fp16 而非 bf16，引入大量 `cmp` 指令）。在 Gemma4 full-attention 预填充上，bf16 Q 比 fp8 Q **快 4~5 倍**（32768 序列：24553µs → 5692µs）。此修复对 **RDNA3 消费级/工作站 GPU 上的长上下文推理体验至关重要**，也揭示了 Triton 编译器与 AMD ISA 协同的深层问题，未来可能推动上游 Triton 修复。

#### 2. **#57508 — MiMo-V2.5 融合 fp8 qkv_proj 分片修复**（已合并）
修复 `XiaomiMiMo/MiMo-V2.5` 在**任意 TP 尺寸下都无法加载**的问题。根因是 checkpoint 的融合 `qkv_proj` 按 `ckpt_tp = config.num_key_value_heads` 预分片，而 `_shard_fp8_qkv_proj` (#45200) 假设每个 KV head 一个 chunk。SWA 层 8 KV heads 跨 4 chunks（每 chunk 2 heads）触发 `tensor a (1856) vs b (1792)` 尺寸错误。影响所有平台，**不限于 AMD**，但由 `vllmellm`（ROCm 相关 CC 名单成员）提交。

#### 3. **#49435 — 统一 SM90/SM100 `fp8_ds_mla` cache scale 契约**（已合并）
将 scale 值统一为 `2 ** ceil(log2(max(amax / 448, 1e-4)))`（2 的幂），保证 SM90（转 BF16）与 SM100（转 E8M0）**读取路径都能精确表示**。涉及 FlashMLA 及 DeepSeek-V3.2/Kimi-K3 三个写入器。这对**跨架构精度一致性**有直接价值，但作者明确标注 **SM90 模型评估仍未完成，是合并前必做项**——评审时需关注这一点。

#### 4. **#54176 — EPD 动态代理**（已合并）
为 EPD（Encode-Prefill-Decode）架构引入启动器管理的动态实例注册，支持 `encode` / `prefill` / `decode` / `prefill_decode` 角色。核心是让外部 launcher 通过 HTTP 注册实例，代理据此确定拓扑。对**多模态大模型三阶段推理部署**有直接意义，但 `omerpaz95` 关于"核心 vs. 示例边界"的质疑提醒我们关注这类新 API 面的长期维护成本。

#### 5. **#56497 — Model Runner V2 支持自定义 logits processor**（已合并）
为 MRV2 引入新的 `LogitsProcessor` ABC 和 `LogitsContext`（每步 batch 布局，因为 V2 每步会重排行），移除 V2-unsupported 门控。这标志着 **MRV2 功能逐步与 V1 对齐**，对 RL rollout、自定义采样策略等场景意义重大。

### 💡 值得关注的问题

1. **#57750 的 Triton 编译器根因**：RDNA3 上 fp8→fp16 隐式转换的编译器行为本身尚未修复，ASTER/RoCm 上游（ROCm/aiter#5601）仍在处理。vLLM 侧的 workaround 是权宜之计，长期方案需跟踪 Triton 上游进展。

2. **#49435 的 SM90 评估缺口**：作者自述 SM90 模型评估未完成即标记为 ready 并最终合并，V3.2/Kimi K3 的 cache scale 变更**改变了 SM90 量化行为**，建议关注后续是否有回归报告。

3. **#57704 的占位符实现**：PR B（AITER fp8 CP indexer）当前 `_score_shard` / `_select_topk` 仍为 `NotImplementedError`，**不应视为可用代码**，可能污染 reviewer 注意力，建议作者明确标注 Draft 或完成实现。

4. **#57740 多模态占位符安全**：用户文本中的 `<|image_pad|>` 与模板占位符 token id 相同，可能被用于**绕过视觉安全判定**。这是一条安全相关路径，虽已由 `Epsilon006` 认领，但需要谨慎设计修复（token-value 匹配 → prompt 来源区分）。

5. **#57719 vs. #57680 的"复现性危机"**：两起高关注度 Issue 均出现"报告者声称，验证者无法复现"的对立。这反映出 vLLM 版本迭代速度下，**报告者与验证者基线不一致**是常见问题，建议社区推动 Issue 模板强制要求 nightly commit hash 与 `collect_env.py` 输出。

6. **EPD 动态代理的架构边界**：`omerpaz95` 对 #54176 的范围质疑虽未被采纳，但反映了 vLLM 在"核心引擎"与"示例部署代码"之间的边界模糊问题，未来类似的部署工具类 PR 可能需要更清晰的 SIG 归属。
