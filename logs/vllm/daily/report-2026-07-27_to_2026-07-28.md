### 🎯 AMD/ROCm 生态相关动态

本周期内，AMD/ROCm 生态是项目活跃度最高的领域，贡献量巨大。具体动态如下：

*   **1. 新模型与特性支持：**
    *   **PR #50000: [New model] Kimi K3**: 这是一个里程碑式的 PR，为 vLLM 带来了对 Kimi K3 模型的支持。该 PR 得到了 AMD 团队的积极参与和贡献。
    *   **PR #48841: [ROCm] [Model] Enable TML inkling**: 在 ROCm 平台上启用了 `lightseekorg/Inkling-MXFP4` 模型（一种高效的 FP4 量化模型）。
    *   **PR #50068: [Model] Enable Qwen3.8 for AMD Rocm**: 注册了对 Qwen3.5 系列模型的 ROCm 支持，包括密集和 MoE 架构，并显式处理了 Gated DeltaNet 的 Mamba 缓存。

*   **2. 性能优化：**
    *   **PR #50017: Chunked prefill paged decode masked load perf [ROCm]**: 修复了 paged attention kernel 中因全量 masking 导致的 10-15% 性能回退，仅对最后一个数据块执行 masking，在 MI350X 上恢复了性能。
    *   **PR #49937: [ROCm] Add AITER FP8 ViT encoder attention**: 为多模态视觉编码器引入了基于 AITER 的 FP8 注意力实现，在 MI300X 上实现了 1.38 倍至 1.79 倍的速度提升。
    *   **PR #49953: [ROCm][AITER] Add GDN long-prefill split-QKV fast path**: 为 Qwen3.5 模型的 GDN 层引入了基于 AITER 的长预填充快速路径，通过优化内存布局，在特定工作负载下实现了超过 7% 的吞吐量提升。
    *   **PR #50007 & #50006: [ROCm] Add tuned selective_state_update ... config for AMD Instinct MI325X**: 为 MI325X 显卡添加了针对 Mamba2 模型中 `selective_state_update` 内核的调优配置，包括 float32 和 float16 两种数据类型，以释放模型解码性能。
    *   **PR #50054: perf(rocm): fuse Kimi-K3 KDA decode gate**: 为 Kimi K3 模型在 ROCm 上融合了解码门控操作，使用已有的优化内核，相比原生分解实现，速度提升了 6.26 倍。
    *   **PR #50008: perf: drop redundant -inf prefill of decode paged MQA-logits buffer**: 移除了解码路径上一个冗余的 `-inf` 填充操作，减少了 HBM 写入开销。
    *   **PR #44527: [ROCm][DSv3.2] Eliminate per-decode FillFunctor launches**: 清除了稀疏 MLA 解码热循环中的冗余 `FillFunctor` 内核调用，在 MI355X 上实现了约 44% 的解码循环加速。
    *   **PR #48739: [Perf] Make merge attention context count a runtime argument**: 将 Triton kernel 中一个导致大量重编译的常量参数改为运行时参数，大幅降低了首次启动延迟和 p95/p99 延迟。

    *   **当前状态**: 开放中，是未来几日开发工作的核心焦点。

2.  **Issue #50013: [Feature]: AMD Kimi K3 MoRI MI355X disagg**
    *   **核心议题**: 用户请求在 AMD MI355X 上获得对 Kimi K3 模型的 **MoRI 分离式推理（Disaggregated Inference）** 支持。尽管 AMD 团队在 Day 0 就支持了 Kimi K3，但分离式推理（即预填充和生成在不同 GPU 上）功能尚未生效。
    *   **参与者观点**: 提交者对 AMD 团队的快速支持表示祝贺，并急切地询问分离式推理何时可用。这表明，**分离式推理** 已成为大规模部署中一个关键的、亟待满足的需求。
    *   **争议焦点**: 无争议，普遍认为这是 AMD 平台需要跟进的重要方向。
    *   **当前状态**: 开放中。GitHub Actions 自动 CC 了 ROCm 相关维护者，并且有贡献者表示愿意承接此问题。

3.  **Issue #50046: [Bug]: Qwen3.5 GDn attention crashes at warmup with torch.compile stride mismatch**
    *   **核心议题**: Qwen3.5 模型在启用了 `torch.compile` 的 CUDA Graph 初始化阶段崩溃，报错为 stride 不匹配。用户通过二分法确定了该 Bug 在 7月 的一份代码提交中引入。
    *   **参与者观点**: 报告者 `janbernloehr` 进行了深入的根因分析，将问题定位到模型中的 `splitting_ops` 边界。他尝试在 vLLM 侧添加 `contiguous()` 操作作为修复，但未能成功，这说明根因可能更深层，涉及到 PyTorch 的 `torch.compile` 实现或与 Triton 的交互。
    *   **争议焦点**: 修复方法存在分歧。报告者发现简单的 `contiguous()` 调用无效，暗示问题本质是 `torch.compile` 编译图的优化方式导致，可能需要在 PyTorch 或 vLLM 层面有更复杂的处理。这再次暴露了 `torch.compile` 与高级模型算子结合时的脆弱性。
    *   **当前状态**: 开放中。

4.  **Issue #49980: [Bug]: FlashInfer builder ValueError with Llama-4 chunked local attention**
    *   **核心议题**: 使用 FlashInfer 注意力后端时，Llama-4 模型在处理大预填充请求时，因分块注意力机制导致缓冲区大小不足，引发 `ValueError`。
    *   **参与者观点**: 报告者 `janbernloehr` 对根因进行了精确定位：`FlashInferMetadataBuilder` 在初始化时基于 `scheduler_config.max_num_seqs` 分配缓冲区，但分块注意力逻辑可能产生超过此上限的虚拟批次，导致溢出。评论者 `thegoldenflow` 验证了这一分析，并提出了一个重要担忧：重新分配缓冲区会改变 CUDA Graph 捕获的固定内存地址，可能导致已捕获的 Graph 失效。
    *   **争议焦点**: 修复 `ValueError` 和保持 CUDA Graph 稳定性的权衡。简单的“按需扩容”修复可能会破坏 CUDA Graph，提出了一个需要更精细设计的难题。
    *   **当前状态**: 开放中。

### 🛠️ 重点技术变更

1.  **PR #50000: [New model] Kimi K3**：这是本次报告中最具影响力的 PR。它标志着 vLLM 对新一代长上下文高性能模型生态的承诺。其技术复杂度和代码量（详尽的 `body`）表明这是一个重大特性。

2.  **PR #49979: [Kernel] Add SM90 W4AFP8 grouped MoE CUTLASS operator**：这是一个纯粹的内核层贡献，为 Hopper SM90 架构引入了 W4AFP8 (4-bit weights, FP8 activations) 的 MoE CUTLASS 算子。它通过利用 CUTLASS 库提供了性能起点，为未来集成更高效的量化方案奠定了基础。

3.  **PR #50009 & #50010: [DCP][Performance] Replace bounded decode collectives with CUDA VMM peer views**：这是一个极具创新性的性能优化提案。通过使用 **CUDA VMM 映射技术**，将反向通信（如 AllGather）转换为直接的内存读写（Peer Loads/Stores），从而规避了 NCCL 的通信开销。这针对的是 DCP (Distributed Context Parallelism) 中稀疏注意力模型的计算瓶颈，展示了 vLLM 在通信优化上不局限于传统方法的思路。

4.  **PR #49823: [Bugfix][KV Offload][P2P] Fix EngineCore crash reconnecting to a reaped peer**：这个 Bug 修复非常关键且深入分析了复杂问题。它修复了在 P2P KV Cache 卸载场景中，当 `EngineCore` 尝试重新连接到一个刚刚被回收的 peer 时发生的崩溃。根因涉及三个相互关联的缺陷（死连接残留、`mark_dead` 和 `close` 共用标志、`close` 未清理监控 socket），修复需要深刻理解 vLLM 的 ZMQ 连接管理内部机制。

5.  **PR #49952: [Bugfix][KV Offload] Reserve primary-tier headroom so speculative promotions don't starve running stores**：该 PR 解决了 KV Cache 分层卸载中的优先级反转问题。当从二级存储（如磁盘）向主存 (CPU) 推测性预加载 (promotion) 时，可能会耗尽主存空间，导致当前正在运行请求的二级卸载 (store) 被饿死（即无法分配存储空间）。修复方案是为主存保留一部分缓冲空间，专门用于保护实时卸载操作，优先保证已计算 KVCache 的落地，而不是猜测未来请求的需求。这体现了系统设计中对确定性路径的保护优先于投机性优化。
