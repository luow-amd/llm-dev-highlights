### 🎯 AMD/ROCm 生态相关动态

#### 一、AMD 贡献者主导的性能优化 PR

**1. PR #61021 —— `[ROCm][Perf] Fuse add-RMSNorm into AITER FlyDSL INT4 QuickReduce`（作者：mjkvaak-amd）**
- 在 FlyDSL INT4 QuickReduce 路径上，将 prefill all-reduce + add-RMSNorm 融合为单个 FlyDSL kernel，取代回退到 HIP QuickReduce + RMSNorm 的做法。
- 依赖 ROCm/aiter#6369（`QuickAllReduceInt4.allreduce_rmsnorm`），当前为 draft，需等待 AITER 下一个 release 才可合并。
- **性能数据**：`amd/Qwen3.8-2.4T-A95B-Quark-MXFP4`（TP8, MI355X）下，输出吞吐 geomean 提升 **+4.4%**（12 个测试点范围 +1.5%～+7.0%），平均 TTFT 改善 **−7.2%**，平均 TPOT 改善 **−4.1%**。
- 仅在 `VLLM_ROCM_QUICK_REDUCE_USE_FLYDSL=1` 且 gfx950 上生效，对其他配置零影响。

**2. PR #61020 —— `[ROCm][Perf] Quantize to MXFP4 in the FlyDSL QuickReduce + RMSNorm epilogue`（作者：mjkvaak-amd）**
- 在 #61021 基础上，继续将 MXFP4 激活量化融入 FlyDSL QuickReduce + RMSNorm kernel，避免再启动独立的量化 kernel。
- 声称 FP4 字节与 `per_1x32_f4_quant_hip(out, shuffle=True)` **逐比特一致**。
- 同样依赖 aiter#6369，当前 draft；#61020 与 #61021 是同一栈的两个连续提交，仅在 gfx950 + FlyDSL 开启时改变行为。

**3. PR #60997 —— `[ROCm][Perf][Kimi-K3] Mono decode kernel: port to gfx942 (MI300X / MI325X)`（作者：xaguilar-amd）**
- 将 Kimi-K3 的 mono decode 内核（#60683 原为 gfx950 专属）移植到 gfx942，使 MI300X / MI325X 也能运行。
- gfx942 侧的技术调整包括：**64 KB LDS 分块加载**、**无 MXFP4 MFMA**（改为读取 vLLM 的 gfx942 int4 重量化专家 + aiter 的 a16wi4 布局）、**16x16x32 bf16 MFMA 拆成两个 16x16x16 MFMA**、permlane 换成 `shuffle_xor`。
- `mono_decode.py` 现接受 gfx942，但**拒绝 CU < 256 的 GPU**（如 CPX）。
- 在 **8× MI325X** 上验证通过：K1/K2/独立 MoE 与 unfused 参考实现 cos ≥ 0.99997，资源占用 LDS ≤ 62.5 KB / 64 KB、≤ 224 VGPR、无 spills。

**4. PR #61004 —— `[ROCm][DSv4] Fuse the shared expert into AITER MegaMoE`（作者：AMD-yanfeiwang）**
- 新增 opt-in 环境变量 `VLLM_ROCM_AITER_MEGA_MOE_FUSE_SHARED_EXPERTS=1`，将 DeepSeek-V4 的共享专家作为一个额外本地专家并入 AITER MegaMoEv2，对应 NVIDIA DeepGEMM 的 #53040。
- **性能数据**：DeepSeek-V4-Pro on MI355X（DEP8），decode ITL 下降 **4–9%**（并发 1–64），输出吞吐提升 **3–8%**，GSM8K 在标准差内。
- **⚠️ 该 PR 现正处于 ROCm 维护者精度质疑之中（详见高热度讨论章节）。**

**5. PR #61001 —— `[ROCm] MonoSpec + abstractions`（作者：simondanielsson）**
- 仅标题可见，body 为占位结构（Overview / Claims / Validation / Details 均空），需持续跟踪。

**6. PR #60990 —— `[Bugfix][ROCm][MiniMax-M3] Reject unbuilt index-head counts in the AITER indexer`（作者：AndreasKaratzas）**
- MiniMax-M3 有 4 个 index head，attention TP=1（如 DP attention）时每 rank 分配 4 个头，但 AITER 只为 **1 或 2 个 index head** 构建了 sparse score kernel。
- 修复后选择器显式拒绝未构建的 head count，调用方回退到平台无关的 indexer，错误从内核 dispatch 崩溃提前到加载期明确报错。
- 在 MI355（gfx950）上验证：`pytest tests/kernels/attention/test_minimax_m3.py` **10/10 通过**（每轮 157 passed, 14 skipped）。

#### 三、AMD 生态相关的 Issue

**1. Issue #61003 —— `[Bug] DFlash draft model: fp8 ignored_layers are not aliased to global layer indices`（报告人：bkvargyas）**
- 标签：`rocm`、`speculative-decoding`、`quantization`。
- 环境：vLLM 0.31.1rc1 nightly ROCm 10 镜像，**2× Radeon AI PRO R9700（gfx1201），TP=2**。
- 目标模型：`unsloth/Qwen3.8-27B-NVFP4`（compressed-tensors NVFP4，64 层）；草稿模型：`z-lab/Qwen3.8-27B-DFlash2` 的 FP8 block-128 转换（5 层）。
- **根因**：`_add_global_draft_layer_exclusions`（在 `qwen3_dflash.py`）只修补 `quant_config.exclude_modules`，但 `Fp8Config.from_config` 实际把 `modules_to_not_convert` 读进 **`ignored_layers`**。因此全局编号别名 `layers.64.attention_conv.kernel_projection` 永不匹配，被排除的 bf16 分组卷积投影被错误建成 fp8 线性层。
- **性能影响**：接受率从 **4.3 降至 1.0**，解码速度从 **~210 tok/s 降至 46 tok/s**（输出正确，因目标模型仍验证每个 draft）。
- **回归溯源**（由 bitslizer 独立复现确认）：`#57934 "[SpecDecode] Add LiLiCorr drafter"`（merged 2026-09-25）同时改动了 `qwen3_dflash2.py`（`quant_config=None` → `quant_config=quant_config`）并新增 `_add_global_draft_layer_exclusions()` 辅助函数，但新函数的测试只覆盖 `exclude_modules`。首个坏版本：**v0.31.0**（最后好版本 v0.30.0）。
- 对应修复 PR **#61010**（he-yufeng）已提交，扩展别名逻辑到所有排除列表属性（`exclude_modules`、`ignored_layers`）。

**2. Issue #61027 —— `[Bug]: CPU MXFP4 MoE (gpt-oss) broken on AMD EPYC after AMX gate`（报告人：tarukumar）**
- 标签：`rocm`、`gpt-oss`、`quantization`。
- 问题：在 AMD EPYC（Zen）上服务原生 MXFP4 `gpt-oss`（如 `RedHatAI/gpt-oss-120b`）时，从 vLLM 0.28+ 起失败。
- **根因**：`#50801 "[CPU] Refine CPU kernel dispatch"`（merged 2026-08-03，进入 v0.28.0）把 `CPUExpertsMxfp4._supports_current_device()` 从 `is_cpu()` 扩展为 `is_cpu() and get_cpu_architecture() == X86 and torch.cpu._is_amx_tile_supported()`。**AMD EPYC 无 AMX 指令**，但 MXFP4 oracle 仍选择 `Mxfp4MoeBackend.CPU`，随后 AMX gate 拒绝部署。
- 报错：`ValueError: Mxfp4 MoE backend 'CPU' does not support the deployment configuration since kernel does not support current device cpu.`
- 目前没有 non-AMX CPU fallback，属于 v0.28.0 引入的功能回归。

**3. Issue #61024 —— `[Roadmap] vLLM Roadmap Q4 2026`（发起人：simon-mo）**
- 标签含 `rocm`、`quantization`、`kimi`、`k3`。

### 💬 高热度讨论分析

本周期讨论热度相对分散，人类评论较集中的议题如下：

#### 1. **PR #61004：AMD MegaMoE 共享专家融合的精度争议（最热）**

- **核心议题**：把 DeepSeek-V4 的共享专家作为额外本地专家并入 AITER MegaMoE，性能提升明确（吞吐 +3~8%），但代价是共享专家从 MXFP8 被 requantize 到 MXFP4。
- **benenzhu（ROCm 维护者）**："adding this will quant the shared expert from `mxfp8 -> mxfp4`. Need more tests on other benchmarks? May run more comparison on GPQA-D and MMMU-PRO evals?"
- **tjtanaa（ROCm 核心维护者）**：更明确地指出——"Requantizing shared experts just to fuse the shared experts has been known to cause large accuracy degradation, that is why AITER later developed a heterogenous fused shared expert MoE kernel instead of requantizing the shared experts"，并要求 **披露 NIAH 精度和更多对比**。
- **争议焦点**：性能提升（decode ITL 降低 4–9%）与潜在精度下降之间如何权衡；AITER 已有更优的异构融合方案，是否需要为此走 requant 路线。
- **当前状态**：PR 保持 open，CI 已触发（Buildkite #94035），等待作者补充精度数据。

#### 2. **Issue #61003：DFlash draft fp8 排除层失效（深度独立复现）**

- **核心议题**：草稿模型的 `ignored_layers` 未按全局层索引别名，导致 bf16 投影被错误加载进 fp8 参数，接受率从 4.3 掉到 1.0。
- **bkvargyas（报告人）**：给出完整最小复现路径、错误日志、量化配置结构，并明确指出问题位于 stock draft-model 构造路径。
- **bitslizer（独立复现者）**：增加关键证据——**首个坏版本 v0.31.0（last good v0.30.0）**、**回归提交 #57934（73a78e6f1f）**、per-layer dump、单 GPU 不同目标量化下的独立复现。评论开头声明"the below was tested and written by Opus 5.5"，是 AI 辅助开源贡献的一个明确案例。
- **争议焦点**：新辅助函数的测试只覆盖 `exclude_modules`，说明 PR review 中量化配置属性覆盖不足。
- **当前状态**：修复 PR #61010 已提交并通过 12 passed / 10 skipped（GPU-gated）。

#### 3. **Issue #61043：结构化输出在 shutdown 期间崩溃**

- **核心议题**：`EngineCore.shutdown()` 先释放 structured-output backend，再停止 executor 与 scheduler；`clear_backend()` 销毁 backend 后**保留引用**（`XgrammarBackend.destroy()` 为 `del self.compiler`），导致 shutdown 期间到达的请求触发 `'XgrammarBackend' object has no attribute 'compiler'`。
- **DimensionSTP（修复者）**：提交 #61047，选择"取消排队编译任务 + 等待运行中编译"的方案，而不是重排 shutdown 顺序。
- **BRANTD-veta（报告人）**：认可修复方案，特别指出 `clear_backend()` 现在正确设置 `self.backend = None`，"closes the second half of the problem"，并赞同用 drain 而非 reorder 关闭竞态窗口。
- **争议焦点**：实际无争议，是一次"报告人-修复者"的良性互动；但报告人点出仅重排 shutdown 顺序是"narrowing"而非"closing"窗口，体现了对竞态本质的准确判断。
- **当前状态**：#61047 已由作者请求 review（@aarnphm）。

#### 4. **PR #59880：KV connector 投机块预留的多组块大小问题（已合并）**

- **核心议题**：异步 KV load 下的投机 decode 块预留在多 KV cache group 下会欠预留，导致请求被 admit 但无法启动解码（deadlock）。
- **bzsuni（作者）**：将预留从"单块大小换算"改为 **各 manager 按其自身 block_size 求和 `cdiv(N, B_g)`**。
- **njhill（维护者）**：确认修复正确，但提出**过度预留**问题——对 Mamba group 也按 `cdiv(..., mamba.block_size)` 预留 1 块，而 Mamba 在 non-align 模式下已由 `MambaManager.get_num_blocks_to_allocate` 计入，align 模式下 lookahead tokens 被显式忽略。建议让每个 manager 自己承担 lookahead 需求以提升精度。
- **争议焦点**：正确性与额外开销之间的权衡。
- **当前状态**：**已合并**（2026-10-11 03:55:41），njhill 的建议作为后续优化留待新 PR。

#### 5. **Issue #60970：Rust 前端下 Qwen3-ASR 不等长音频批次导致 EngineCore 崩溃**

- **核心议题**：Rust 前端按 clip 逐个发出 2-D `[n_mels, padded_seq]` 张量；模型契约要求单个 flat `[n_mels, total_seq]`，`_reduce_data` 只在形状全等时 stack，不等于时长音频触发 rank-3 校验错误，最终杀死 EngineCore，**8/8 并发请求全部 HTTP 500**。
- **frank-suwen**：主动声明已定位根因（`unpad_and_flat_audio_features()` 只处理 stacked tensor）并准备提交修复，随后发现报告人已开 #60979，**主动退让**以避免重复劳动。
- **争议焦点**：无争议，是一次高效协作的正面案例。
- **当前状态**：#60979 已提交并通过 H100 端到端验证（修复前 18 failed/19 passed，修复后 37 passed；修复前 8/8 HTTP 500，修复后 8/8 OK）。

### 🛠️ 重点技术变更

#### 1. **PR #60684 —— `[Perf][MiniMax-M3] MSA prefill attends with the E4M3 query`（已合并，2026-10-11 05:40）**
- 目标：避免 MSA prefill 每次都把仅以 E4M3 写入的 query 反量化回 BF16 缓冲。
- 技术变化：`MiniMaxM3SparseMSAImpl` 在 prefill 时**直接传递 E4M3 query**，两个 `fmha_sm100` prefill kernel 原生支持。同步 bump `fmha_sm100` 从 `be4a52a` 到 `968061a`（含 Blackwell prefill port）。
- 影响：**FP8 KV cache 下 prefill 单层快 26–37%**，**NVFP4 KV cache 下快 8–13%**（GB300）。BF16 cache 及默认 Triton decode 路径完全不受影响。

#### 2. **PR #59880 —— `[Bugfix][KV Connector] Fix speculative block reservations across KV cache groups`（已合并）**
- 修复异步 KV load 下、多 KV cache group 且块大小各异时的投机块预留欠账问题（deadlock）。
- 修改：由单次换算改为按 manager 逐个 `cdiv(N, B_g)` 求和。njhill 已确认正确性，并指出 Mamba group 的过度预留问题作为后续优化。
- 影响：**修复 P/D 分离部署在 KV 内存压力下的潜在死锁**，对多组 KV cache 的 MoE + MTP 场景尤为关键。

#### 3. **PR #60997 —— `[ROCm][Perf][Kimi-K3] Mono decode kernel: port to gfx942`**
- 让单内核（mono）decode 路径在 MI300X/MI325X 上可用，缩小 gfx950 与 gfx942 之间的性能/功能差距。
- 关键技术处理：64KB LDS 分块、禁用 MXFP4 MFMA（改用 int4 requant + aiter a16wi4 布局）、指令级降级（MFMA 16x16x32 → 两个 16x16x16，permlane → shuffle_xor）、以及 CU < 256 的硬件守卫。
- 影响：**扩展 AMD 生态对 Kimi-K3 长上下文解码的硬件覆盖范围**。

#### 4. **PR #61011 —— `[Bugfix][V1] Retain the EAGLE hit blocks below a sliding window across a KV connector import`**
- 修复 P/D 分离下 EAGLE-family drafter（DFlash, window 2048, block 64）+ 滑动窗口 + prefix caching 场景：decode 端 KV connector import 后，后续长于 window 的 prompt **全部 prefix cache miss**。
- 修复：为 EAGLE group 扩展 `extra_retained_tokens`（65 tokens），确保 `get_num_skipped_tokens` 落在正确的整块边界。
- 影响：**修复 P/D 分离 + 稀疏滑动窗口 EAGLE 下严重的 prefix cache 命中塌陷**。

### 💡 值得关注的问题

#### 1. **#61027 —— AMD EPYC 上 CPU MXFP4 MoE 回归（功能级）**
v0.28.0 引入的 AMX gate 实际上把 CPU MXFP4 MoE 变成"Intel-only"，AMD EPYC 用户被直接拒绝部署。建议关注：是否需要增加 non-AMX CPU fallback，或在 `oracle/mxfp4.py` 中显式拒绝并给出可操作提示。**目前尚无对应修复 PR。**

#### 2. **#61052 —— NVIDIA vGPU 上 CPU KV offload 崩溃（Xid 31）**
`cuMemcpyBatchAsync` 在 H200 NVL SR-IOV vGPU（驱动 595.91.x）上对单描述符 in-bounds 拷贝也触发 GPU MMU fault。作者已快速提交 #61054 提供 `VLLM_KV_OFFLOAD_DISABLE_BATCH_MEMCPY=1` opt-out，同时覆盖 C++ `swap_blocks_batch` 与 Python `copy_blocks` 两条路径。**值得跟进**：ROCm（`hipMemcpyBatchAsync`）是否也存在同类问题尚待验证。

#### 3. **PR #61004 —— AMD MegaMoE 共享专家融合的精度门槛**
ROCm 维护者 benenzhu / tjtanaa 明确要求 NIAH、GPQA-D、MMMU-PRO 的额外精度对比数据。若 requant 到 MXFP4 的精度下降被证实不可接受，可能需要转向 AITER 的 heterogeneous fused shared expert MoE kernel。**该 PR 的推进与否将影响 DSv4 在 MI355X 上的 decode 延迟优化路径。**

#### 4. **#61053 —— TP ranks 因 Inductor autotune 的 add+RMSNorm 规约差异导致 MoE 专家路由分歧**
该 Issue body 在提供的数据中**未显示**，仅有标题。但"TP 各 rank 因 autotune 产生不同归约结果，导致同一 token 路由到不同专家"是推理一致性层面的严重隐患，**强烈建议社区关注并跟踪**。

#### 5. **#61049 —— Stateless DP group formation 端口池路径的静默重绑定**
Leader 在 `EADDRINUSE` 后静默重绑 pooled rendezvous port，而成员在整个 timeout 期间仍重试陈旧端口。这是分布式启动期的"半失败"状态，诊断困难，**建议跟进是否需要"快速失败"语义**。

#### 6. **#61043 / #61047 —— 结构化输出 shutdown 竞态**
虽已有修复方案，但暴露出 `EngineCore.shutdown()` 中"先释放 backend，后停止 executor"的顺序问题。同类问题（其他 backend 半销毁状态）可能存在于其他资源，**建议审视 shutdown 顺序的统一原则**。

#### 7. **PR #61004 的 review 与响应节奏**
该 PR 已由 CI 触发并有两位 ROCm 维护者提问，但尚无作者答复。**建议关注 AMD 团队是否会提供所需精度数据，或是否将路线转为 AITER heterogenous 方案。**

#### 8. **长期：stale 自动关闭掩盖的真问题**
#45318（Ray executor teardown 混淆真实 init 错误）、#45101（FP8 MoE + LoRA 的 `tl.dot` 混合 dtype）等技术分析质量很高但被 stale 关闭。**建议社区考虑对这类"有高质量分析但未修复"的 Issue 建立迁移或归档机制**，避免反复重开或重复研究。
