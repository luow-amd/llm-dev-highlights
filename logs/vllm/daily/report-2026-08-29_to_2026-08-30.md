#### 新增 Issue（3 个）

- **#54359** `[Bug][ROCm] GLM-5.3-Flash kpool indexer overwrites its own KV cache`
  - **核心问题**：在 ROCm 上，`DeepseekV32IndexerBackend.get_supported_kernel_block_sizes()` 返回 `[1, MultipleOf(16)]`，导致混合块对齐器选择了 640 token 的存储块，而实际 DeepGEMM/AITER kernel 按 128 token 页寻址，造成 5 倍超额订阅，4096 个池条目只写入 864 个槽位，约 79% 的 key 错误。
  - **影响**：长上下文召回率降至 0/6，工具调用成功率仅 83.3%，且 `temperature=0` 无法复现。
  - **社区反馈**：已有第二站点（8×MI325X）独立确认同一根因，并补充了 metadata 构建器的更细粒度问题。
  - **状态**：open，但提交者已给出修复后 8/8 召回、100% 工具调用成功率的验证数据。

- **#54369** `[Perf][ROCm] Sparse-MLA/kpool backends fall back to rebuilding attention metadata per draft step`
  - **问题**：`ROCM_AITER_MLA_SPARSE`、`DEEPSEEK_V32_INDEXER`、`KPOOL_TAIL` 后端不支持 fused multi-step draft decode，每步 draft 都需要重建 attention metadata，导致 MTP 推测深度在 k=4 后吞吐下降（k=6 时 tok/s 从 1642 降至 1623，k=8 时骤降至 1155）。
  - **意义**：揭示了 ROCm 后端在投机解码融合能力上与 CUDA 的结构性差距。

- **#54376** `[ROCm] Fused shared experts unavailable for GLM-5.3-Flash`
  - **两大障碍**：① `Fp8Config` 未在 FSE 兼容性门控中处理；② `glm5next` 模型未连接 FSE 且 MTP 块构造缺少 `mtp_block` 组件。
  - **进展**：提交者已在 issue 中自行解决，给出三个小补丁并附带端到端测量数据。

#### 合并 PR（4 个，含跨平台）

- **#51171** `[ROCm][MLA] Reach FULL cudagraphs for AITER MLA speculative decoding`
  - 解决 AITER MLA 投机解码无法进入 FULL cudagraph 的两个障碍：DSpark draft group 的 attention 能力误报，以及 `AiterMLAImpl.forward_mqa` 内 HIP 图捕获不允许的 host 同步和动态分配。

### 💬 高热度讨论分析

#### 1. #49921 `[Perf] BF16x3 router GEMM gated off family-120 Blackwell`（8 条评论）

- **核心议题**：GB10（sm_121）上，DeepSeek-V4-Flash 的 fp32 router 因 `is_device_capability_family(100)` 门控，无法使用 BF16x3 专用 GEMM，退化为 BF16 精度 logits。
- **多方观点**：
  - `hclsys` 实测 CuteDSL BF16x3 在 sm_121a 上 NVVM 编译失败，不能简单放宽家族门控。
  - `gau-nernst` 指出 DSv4-Flash 实际 router 权重是 BF16，门控导致 fp32 参数回退，应直接用 cuBLAS BF16×BF16→FP32 out_dtype。
  - `Reederey87` 在 2×GB10 生产环境 A/B：解开 cuBLAS tier 后 router logits 更精确，但 spec-decode 接受率从 0.638 降至 0.574——更精确的 logits 反而与 drafter 不匹配。
- **争议焦点**：是否全局启用该 tier？精确 logits 对投机解码的副作用如何取舍。
- **结局**：PR #54048 合并，将 cuBLAS tier 门控放宽到所有 CUDA 架构，保留专用 kernel 门控。该 issue 随 PR 合并而关闭。

#### 2. #54359 `[Bug][ROCm] GLM-5.3-Flash kpool indexer overwrites its own KV cache`（4 条评论 + 超长正文）

- **核心议题**：ROCm 上 kernel block size 声明与实际 kernel 行为不一致，导致 KV cache 被静默覆盖。
- **观点**：
  - `stefanskiasan` 给出详细根因分析和修复后的大规模测试数据（0/6 → 8/8 召回、工具调用 83.3% → 100%）。
  - `zzw09773` 在第二站点（MI325X）独立复现，通过不同路径确认同一机制，并披露 `select_common_block_size` 的 2176 block size 问题。
- **争议**：无实质分歧，主要是在不同硬件上互相印证。
- **状态**：open，等待官方修复合并。

#### 3. #54360 `[Bug]: Speculative decoding silently disables prefix-cache hits for hybrid GDN models`（4 条评论）

- **核心议题**：nightly 上混合 GDN 模型开启 MTP/DFlash 后，`prefix_cache_hits_total` 变为 0，长提示词重复请求全量重算。
- **观点**：
  - `jschmied` 在 0.27.1 上发现命中率降为 42.5%（非完全归零），并定位到 PR #52244 可能与其相关。
  - `erdholion` 做了精确 A/B，发现 hash unit 从 1568 变为 1600，且总是丢失一个 unit；同时 `cached_tokens` 在 API 响应中消失，客户端无法感知。
- **争议焦点**：是 nightly 回归还是 prompt 几何差异？最终统一为 #52244 描述的边界规则问题。
- **状态**：open，修复 PR #52244 存在但未链接。

#### 4. #53938 `[RFC] Config-driven AITER auto-enable instead of a manual opt-in?`（4 条评论）

- **核心议题**：是否要做一个维护者维护的 AITER 兼容性表，自动启用验证过的配置组合。
- **观点**：
  - `Rohan138`（AMD）回应：曾考虑过但放弃，因为维护成本高；建议改为 config object 方式，类似 `--moe-backend`。
  - `AndreasKaratzas` 同意：当前优先补齐两库间的连接差距。
  - `wjabbour` 接受反馈，关闭 issue。
- **结局**：closed，但提出了更具体的 config object 方向，可能为后续 AITER 架构演进铺垫。

#### 5. #54318 `[Bug]: Qwen3.8-Flash-Next-FP8 fails to start on A100 due to fp8e4nv unsupported in SM80`（4 条评论）

- **核心议题**：官方 Docker 镜像在 A100 上无法初始化 fused MoE kernel，`fp8e4nv` 不支持 SM80。
- **观点**：`wtdcode` 提供 `vllm-backport` 作为 workaround，用户验证后解决。
- **争议**：无，属于支持边界问题，但反映了 FP8 模型对老架构的兼容性短板。
- **状态**：open（实际上用户已解决，但 issue 未关）。

   - #54360 显示 MTP/DFlash 与 APC 的兼容性在混合 GDN 模型上出现退化；#54369 则是 ROCm 后端 MTP 融合能力缺失。两者都指向投机解码是当前生产部署中最易出问题的领域。

3. **跨架构内核门控调整**
   - #54048（cuBLAS router GEMM）和 #54378（Gloo 后端）都体现 vLLM 在非 NVIDIA 旗舰架构上的适配投入。特别是 family-120（GB10）和 AMD RDNA 用户开始获得官方级别的支持。

4. **前端与协议层 Bug 增多**
   - `content=null` 渲染为 "None"（#54337/#54368）、pooling padding 顺序错误（#54364）、视频 base64 缺乏校验（#54323）等，显示随着 API 生态扩大，边缘用例正在被补齐。

### 🛠️ 重点技术变更

#### 1. 合并：#51171 `[ROCm][MLA] Reach FULL cudagraphs for AITER MLA speculative decoding`
- **技术内容**：修复 AITER MLA 后端在投机解码时无法捕获 FULL cudagraph 的两个根本原因——attention 能力误报和 HIP 图捕获区域内存在 host 同步/动态分配。
- **影响**：MI355X 上单流吞吐提升 3.55 倍，多流 1.94 倍，是 ROCm 投机解码性能的重要里程碑。

#### 2. 合并：#54048 `[Bugfix][MoE] Enable cuBLAS out_dtype router GEMM on all CUDA archs`
- **技术内容**：将 cuBLAS BF16×BF16→FP32 out_dtype tier 从 `allow_specialized_router_gemm` 门控中解耦，改为 `is_cuda() or is_rocm()`，覆盖 Hopper、SM100、family-120 及 Ampere 等所有架构。
- **影响**：修复 GB10 等 family-120 设备上 router logits 被 BF16 舍入的问题；因 `gau-nernst` 确认 Ampere 也支持，最终对所有 CUDA 架构开放。

#### 3. PR #54341 `[Bugfix] Stop advertising fp8_e5m2 where the KV writer stores e4m3`
- **技术内容**：发现 Triton KV 写入器总是存储 `platform.fp8_dtype()`（即 e4m3），但后端支持列表包含 `fp8_e5m2`，导致位模式被错误解码。
- **影响**：阻止了一个静默数据损坏问题，对 ROCm/CPU 等所有使用 Triton 写入器的后端都有意义。

#### 4. PR #54378 `[Distributed] Implement stubbed collective operations for Gloo backend`
- **技术内容**：在 `DeviceCommunicatorBase` 中实现 Gloo 后端的所有集合通信操作，并增加 `VLLM_DISABLE_PYNCCL` 完全禁止加载 PyNCCL 的路径。
- **影响**：为 AMD RDNA 用户提供绕开 RCCL 崩溃的可行方案，也是未来实现 RDNA 自定义 allreduce 的基石。

#### 5. Issue #54359 `kpool indexer overwrites its own KV cache`
- **技术内容**：ROCm 专属的 KV 缓存条带化错误，导致 GLM-5.3-Flash 长上下文召回和工具调用受损。
- **影响**：虽未合入补丁，但提交者已在 issue 中给出经过验证的修复方案（修改 backend 声明的 block size）并附性能对比，是 ROCm 社区急需解决的问题。

### 💡 值得关注的问题

1. **#54359（ROCm GLM-3.5 KV 缓存损坏）**：影响长上下文和工具调用，且是静默错误（不崩溃、无 warning），生产环境极难察觉。建议 AMD 维护者优先处理，提交者已提供完整复现和补丁思路。

2. **#54360（投机解码禁用前缀缓存）**：混合 GDN 模型 + MTP/DFlash 在生产中可能完全失去前缀缓存收益，且 API 不返回 `cached_tokens` 导致客户端无法感知。PR #52244 已提出修复，应加速 review。

3. **#54331（sm_120 NVFP4 + CUDA graphs 崩溃）**：RTX PRO 6000 上持续 7 分钟必崩，`enforce_eager` 是唯一逃生舱，但代价是性能。该问题跨越 0.26→0.28 多个版本，反映 Blackwell 消费级架构与 CUDA graphs 的兼容性隐患。

4. **#54363（文件系统 KV offload 数据完整性 RFC）**：目前无 checksum、无 I/O 超时，磁盘位翻转会导致静默错误输出。该 RFC 提出了具体设计（checksum、deadline、临时文件清理），是 KV offload 走向生产级的关键文档。

5. **#54369（ROCm MTP 深度受限）**：稀疏 MLA 后端无法 fused multi-step draft decode，导致 k>4 后吞吐反而下降。这是 ROCm 投机解码性能的长期短板，需要关注后续是否支持 fused decoding。
