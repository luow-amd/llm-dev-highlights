### 🔥 热门话题与趋势分析

#### 1. AMD 软件栈进入“内核级性能竞赛”阶段
当日可见的 AMD 相关 PR 超过 20 条，覆盖：
- **RDNA 消费级/工作站**：gfx115x、gfx1200/1201、gfx1100 的 attention/MLA 内核；
- **CDNA MI300/MI325/MI350/MI355**：gfx942/gfx950 的 FlyDSL sparse MLA、AITER 融合、INT4 QuickReduce、monokernel 专用 decode；
- **框架层**：online quantization 统一、ROCm stable ABI wheel、AMD CI 模型矩阵。
趋势是从“能跑”转向“按模型/按 shape 榨取 kernel 效率”，并且大量 PR 直接附带 MI355X/MI325X 的端到端吞吐、TTFT/TPOT、GSM8K 数据。

#### 2. 量化生态的“统一”与“精度纠偏”并行
- **统一**：#67529 用 `--quantization-config` 取代 ROCm 专用 env var；#59460 引入 `VLLM_STRICT_QUANT_SCHEME`；#61815 把 lm_head 纳入 online targets。
- **纠偏**：#67441 修复 NVFP4 merged linear 的 global scale 丢失；#67603 暴露 Quark W4A4 在 Blackwell 的加载失败与 bias 丢弃；#67413 修复 `moe_wna16` 对 checkpoint 排除层的误量化。
这表明量化路径的“静默降级/静默错算”正成为社区重点清理对象。

#### 3. 正确性与安全问题集中出现
- **stride 校验缺失**：#67411 `fused_add_rms_norm` 对非单位最内层 stride 静默算错，并进一步报告 501 次 invalid global read；#67484 修复 static FP8 RMSNorm 的同类问题。
- **缓存键不完整**：#67558 视频帧列表的 multimodal hash 未包含 per-request image decode 选项，导致跨请求缓存复用；#66422（已关闭）此前报告 uuid 与内容摘要共享 keyspace 导致缓存污染。
- **鉴权绕过**：#67556 `--api-key` 未保护 SageMaker `/adapters` 别名路由，可未授权 load/unload LoRA。
- **构建一致性**：#67595 `pip install vllm==0.33.0` 解析出 nvcc 13.5 + cuda-toolkit 13.0 的不一致工具链，破坏 FlashInfer JIT。

#### 4. PD 分离 / KV Connector 持续深化
- #65336 NIXL 从 PP prefill stages pull KV（已合并）；
- #67593 NIXL chunked prefill push for hybrid models（open，stacked on #67203）；
- #67415 Mooncake sparse Draft-window page fill（open，RFC #66751 第二实现）；
- #67539 DeepSeek V4.1 Engram pool over NVLink/RDMA（open）。
KV 传输正在从“整请求 push/pull”走向“分块、稀疏页、混合 cache group、异构 TP”的细粒度阶段。

#### 5. 模型支持与 recipe 建设同步加速

### 🛠️ 重点技术变更

#### 1. #67445 ROCM_RDNA_ATTN 扩展到 gfx1150–gfx1153 与 RDNA4
这是当日 AMD 侧技术含量最高的性能 PR 之一。它不只是“加表”，而是重新定义了 RDNA 后端的选择策略：
- gfx1150–gfx1153 默认走 `ROCM_RDNA_ATTN`，不支持的部分回退 Triton；
- RDNA4 通过 `--attention-backend ROCM_RDNA_ATTN` opt-in；
- 内核针对 1024 VGPR/SIMD lane 重新调优 prefill occupancy，避免 spill；
- 与 #67344 的 16-token KV block 偏好形成耦合，否则默认 block size 64 会让内核无法命中。
**影响**：RDNA 从“能跑 Triton”进入“有专用高性能 attention 后端”的阶段，对消费级 Radeon、Strix Point 及 RDNA4 工作站的推理吞吐有直接意义。

#### 2. #64534 Mistral Large 4 合入 + #67568 release cherry-pick
Mistral Large 4 是当日合入的最大模型 PR，覆盖：
- Sparse MLA + DSA indexer、cross-layer KV sharing、SSMax；
- DSpark 投机解码；
- DCP/PCP 长上下文、NIXL P/D、HiSparse host KV offload；
- NVIDIA Blackwell/Hopper 与 **AMD ROCm MI350 系列**内核。
**影响**：为 1T 级 MoE 模型提供了 vLLM 的完整 serving 路径，同时把 AMD MI350 纳入官方验证硬件矩阵；后续 adaptive verification、GB300 支持等以 follow-up 推进。

#### 3. #65336 NIXL 支持从 PP prefill stages pull KV
该 PR 解决了 PD 分离中“prefill 侧使用 PP”的实际部署形态：
- 统一 `_remote_stages[engine_id][pp_rank]` 表示，PP1 退化为单 stage；
- D 侧按 stage 选择持有对应 layer 的 worker，支持 HMA 的 attention-only group；
- 对没有相关 block 的 stage 只发通知、不发 READ；
- 引入 request-level 完成屏障，避免单 stage 失败导致其他 stage 提前释放 block。
**影响**：使 PP prefill + PP1 decode 的组合可用于生产，扩展了 NIXL connector 的拓扑覆盖；但也暴露出 MLA/indexer 类 cache 在 HMA guard 下的兼容性边界。

#### 4. #59460 量化回退显式化 + `VLLM_STRICT_QUANT_SCHEME`
该 PR 把“请求 W8A8/W4A4、实际跑 W8A16/W4A16”的静默行为变成：
- 每个 kernel 声明 `executed_activation_key(...)`；
- 选择阶段统一比较并给出一次性 warning；
- `VLLM_STRICT_QUANT_SCHEME=1` 时拒绝降级，按优先级继续寻找真正支持该 scheme 的 kernel，否则启动失败。
**影响**：这是量化可观测性的基础设施；后续 #67529 的 online quantization 统一、#67441 的 NVFP4 scale 修复都可以挂在这套语义上。但讨论也暴露了 linear 路径缺少 MoE 已有的统一 contract，统一量化接口仍是未完成事项。

#### 5. #67529 用标准 online quantization API 替换 ROCm 专用环境变量
该 PR 删除 `VLLM_FP8_MOE_REQUANT`、`VLLM_FP8_MOE_REQUANT_ACT`、`VLLM_ROCM_MUSE_MOE_ONLINE_QUANT` 背后的 bespoke 代码，改为：
- `--quantization-config.moe mxfp4`；
- `--quantization-config.moe '{"weight":"mxfp4","activation":"mxfp8"}'`；
- 旧 env var 保留重定向 + `warning_once`，计划 v0.35.0 移除。
**影响**：减少 ROCm 与 CUDA 在量化配置上的分叉，使 Mistral Large 4、Muse Spark 等模型的 MXFP4 routed-expert 路径走同一套 online quantization infra；对 AMD 平台的长期可维护性利好。

### 💡 值得关注的问题

1. **#67411 `fused_add_rms_norm` 非单位最内层 stride 静默错误 + 越界读**
   不仅结果错误（transposed input 最大 diff 8.75，4035/4096 mismatch），还在 `PYTORCH_NO_CUDA_MEMORY_CACHING=1` 下被 Compute Sanitizer 报告 501 次 invalid global read。虽然作者说明需要进程访问权限、不属于安全公告范围，但作为 kernel 正确性缺陷应优先修复；#67484 已处理 static FP8 RMSNorm 的同类问题，但 `fused_add_rms_norm` 本身仍需跟进。

2. **#67556 `--api-key` 未保护 SageMaker `/adapters` 路由**
   `POST /adapters`、`DELETE /adapters/{name}` 与受保护的 `/v1/load_lora_adapter` 调用同一 handler，但未纳入 API key middleware。运营者按 `docs/usage/security.md` 配置网关后仍可能暴露 LoRA load/unload，属于配置安全边界问题。作者已表示有本地修复，待 PR。

3. **#67558 视频帧列表缓存哈希未包含 per-request image decode 选项**
   在 `--trust-request-mm-kwargs` 下，相同帧、不同 `rgba_background_color`/`image_mode` 会命中同一 multimodal hash，导致 processor cache / prefix cache 复用错误结果。与已关闭的 #66422（uuid 与内容摘要共享 keyspace）属于同一类“缓存键不完整”问题，建议统一审视 multimodal cache key 的构造。

4. **#67595 CUDA 工具链解析不一致**
   `vllm==0.33.0` 从 PyPI 安装时解析出 nvcc/nvvm/crt 13.5.x + cuda-toolkit 13.0.x，导致 FlashInfer JIT 因 CCCL 头文件不兼容或 PTX ISA 版本不匹配而失败。作者已提 #67596 固定四个工具链包版本，建议尽快合入并补充 CI 约束。

5. **#67603 Quark W4A4 在 Blackwell 上的加载失败与 bias 静默丢弃**
   Quark `w_mxfp4_a_mxfp4` gpt-oss checkpoint 在 SM100 上选中 `CUTLASS_MXFP4_MXFP4` 后 `process_weights_after_loading` 报错；同时 CUTLASS W4A4 内核不应用 expert bias。对使用 Quark 量化格式的 AMD/NVIDIA 用户都有影响，需明确后端能力声明与 fallback 策略。

6. **#67551 ROCm stable ABI wheel 缺少执行者**
   技术上被认为是可行的，但 janeyx99 明确指出需要一位有 ROCm 机器的人推进。若长期无人认领，ROCm wheel 与 CUDA wheel 的跨 PyTorch 兼容性差距会持续存在。

7. **#67545 与 #67469 的重复/互补边界**
   njhill 认为 #67545 是 #67469 的重复；作者复查后指出 #67469 未覆盖 FlashInfer autotune warmup 直接传 `max_num_batched_tokens` 到 `_dummy_run` 的路径，二者互补。此类“同一根因、不同触发路径”的 PR 需要 maintainer 明确合并策略，避免修复遗漏或重复劳动。

8. **AITER/FlyDSL 外部依赖版本管理**
   #67550、#67584、#67444、#67501、#67541 均依赖 ROCm/aiter 的特定 PR 或版本，部分 PR 在依赖未进入 pinned release 时只能保持 draft 或 no-op。建议在 CI 中增加 AITER 版本矩阵或显式 dependency 检查，降低“内核已合入但 vLLM 未启用”的窗口期。
