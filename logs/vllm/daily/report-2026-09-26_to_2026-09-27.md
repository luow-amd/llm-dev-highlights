#### 2. Kimi-K3 ROCm AttnRes 内核优化（PR #58861）
- **作者**：xiaohuguo2023，标签 `rocm`、`kimi`、`k3`
- **内容**：优化 `vllm/models/kimi_k3/amd/ops/attn_res.py` 中的 AMD AttnRes 内核。该内核在 Kimi-K3 解码中每步运行 187 次（93 层 × 2 次 + 最终 1 次），是解码延迟的关键路径。主要改动包括：
  - **寻址优化**：前缀、delta、block、输出 pitch 从 `tl.constexpr` 改为运行时整数，避免每行 stride 编译独立内核；使用 `tl.assume` 标记正数；D tile 使用 `tl.max_contiguous`/`tl.multiple_of`；在 `HAS_DELTA` 路径上才假设 delta pitch 为正。
  - **启动与循环优化**：解码阶段每个 token 启动一个 program，单 tile 覆盖所有 source（`BLOCK_L = next_power_of_2(num_blocks + 1)`，8 warps）；prefill（≥256 token）保持单 source tile、4 warps，并用 `tl.range(..., num_stages=2)` 软件流水；softmax 改用 `exp2`，将 `log2(e)` 折叠进 logits。
- **验证**：在 MI355X（gfx950）、Triton 3.8 上与旧内核逐位对比，覆盖 decode（hidden 7168）、padded rows、prefix/delta/block pitch 非 16 整除等场景。
- **影响**：这是针对 AMD Instinct MI355X 的定点优化，直接提升 Kimi-K3 在 ROCm 上的解码吞吐。

#### 4. RoPE IR 迁移补全 ROCm/AITER 路径（PR #58838 + Issue #58841）
- **作者**：mpashkovskii，标签 `rocm`、`torch.compile`、`nvidia`、`vllm-ir`
- **背景**：这是对之前失败尝试（#43199、#39488/#41773/#42264，均已关闭未合并，最后状态为 merge conflicts）的复兴。RoPE 目前仍不是当前 `main` 上的 IR op，导致 QK-norm+RoPE 融合模式在未注册 `custom_ops=["+rotary_embedding"]` 时无法匹配（#28042）。

  - 范围限于基础 `RotaryEmbedding`（Neox / GPT-J）；`DeepseekScalingRotaryEmbedding`、mRoPE、flashinfer、`key=None` 跨层 KV 共享路径留作后续。
- **配套追踪 Issue #58841**：Gemma4 在 ROCm/AITER 上的 QK-norm+RoPE（head_dim 512）融合追踪，同时覆盖 CUDA。
- **影响**：这是 ROCm 上 RoPE 融合路径的关键修复，避免在移除 custom op 强制注册后静默回退到非 AITER 路径。但该方向历史上多次失败，需关注本次能否通过审查。

#### 3. Issue #42147：Qwen 3.6 AWQ 加载 OOM（5 条评论）

- **核心议题**：Qwen3.6-35B-A3B AWQ 在 RTX 4090（24GB）上加载时 OOM，即使使用 `--language-model-only` 等参数。
- **不同观点与证据**：
  - **@ZJY0516**：认为模型本身难以放入该 GPU。
  - **@wenyili**：深入分析指出 OOM 发生在 **profiling 阶段**而非真实 KV cache 分配——`_init_minimal_kv_cache_for_profiling` 为 cudagraph capture 设置"最小"KV cache，但该模型是 hybrid（Mamba `linear_attn` + `self_attn`），32 层分成 **8 个 KV cache group**，block_size 被提升到 **2096** 以对齐 attention 和 mamba 页。每组 profile cache 大小为 `max_cudagraph_capture_size × block_size = 512 × 2096 ≈ 1.07M tokens`，fp8 KV 下约 **1 GiB**；**8 组 × ~1 GiB ≈ 8 GiB** 仅用于 profiling，加上 15.4 GiB 权重，导致 OOM。还指出 `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0` 设置并不能跳过 cudagraph profiling。

- **最终状态**：**2026-09-27 被自动关闭**，但 @wenyili 的分析具有长期参考价值，建议社区将其转化为文档或改进 profiling 内存估算。

#### 4. Issue #58849：WSL2 pinned memory 性能（1 条评论，但内容深入）

- **核心议题**：在 WSL2 上，`VLLM_WSL2_ENABLE_PIN_MEMORY=1` 使默认 V2 runner 每 decode step 快约 12%（Qwen3-8B-AWQ：8.7-9.0 → 7.7-7.8 ms/token），吞吐在并发 1 时 +13-14%。GPU-busy 时间不变（7.56 vs 7.61 ms），但默认情况下 trace 显示 pageable H2D copy 且 GPU 每步 idle 1.29 ms，pinned memory 下仅 0.16 ms。
- **报告者后续发现**：根因是 **V2 对缺失 pinned memory 的 fallback 使用阻塞式 `copy_()`**。PyTorch 的阻塞 H2D copy 以 `cudaStreamSynchronize` 结束，导致准备 step N+1 等待 step N 完成，每步 16 次。给出的两行修复：
  ```diff
  # vllm/v1/worker/gpu/buffer_utils.py, NonUvaBuffer.uva()
  -            return self._uva.copy_(self.cpu)
  -        return self._uva[:n].copy_(self.cpu[:n])
  +            return self._uva.copy_(self.cpu, non_blocking=True)
  +        return self._uva[:n].copy_(self.cpu[:n], non_blocking=True)
  ```
  打补丁后：wall time 8.88-9.08 → **7.63-7.66 ms**，`cudaStreamSynchronize` 从 16.3 降到 **0**，GPU idle 从 1.32-1.46 ms 降到 0.01-0.18 ms。**无需启用 pinned memory 即获得与 pinned memory 相同的性能**。
- **争议/关注点**：之前 #41496 的审查在 WSL2（RTX 5080，4B 模型）上测得 pinned memory 有 <2% 吞吐成本，与本次结果相反。报告者表示愿意在该设置上测试默认值变更。
- **状态**：Open，等待社区复现和评审。这是一个**高价值、低风险**的性能修复候选。

#### 5. PR #58838 / Issue #58841：RoPE IR 迁移的历史争议（引用讨论）

- **核心议题**：RoPE 从普通 `CustomOp` 迁移为 vLLM IR op，使 QK-norm + RoPE(+KVCache) 融合模式无需强制 `custom_ops=["+rotary_embedding"]` 即可匹配。

### 🔥 热门话题与趋势分析

#### 1. 推测解码（Speculative Decoding）稳定性与正确性
- Issue #42261（Gemma4 MTP 崩溃）、PR #57263（Gemma4 DSpark adaptive verification with FlashInfer）、PR #58863（Qwen4Exp RecoverSSM for GDN 和 PLE short conv）、PR #56723（DCP target model with non-DCP Dspark）均围绕推测解码。

#### 2. 混合模型（Hybrid Models）的 KV Cache 与 Metadata 管理
- PR #58851（MRV2 跨 KV cache group 共享 GDN/Mamba/KDA batch metadata）：Qwen3.6-35B-A3B + DFlash 有 46 个 group，其中 30 个 GDN，每步重复构建 batch-level metadata。本 PR 泛化 #58762 的临时方案，覆盖 GDN、Mamba1/2、ShortConv、Kimi-K3 KDA。

### 🛠️ 重点技术变更

#### 1. PR #58838：RoPE 迁移为 vLLM IR op（ROCm/AITER 路径补全）
- **技术解读**：将基础 `RotaryEmbedding` 从 `CustomOp` 迁移为 IR op（`vllm.ir.ops.rotary_embedding`），使 QK-norm + RoPE(+KVCache) 融合模式匹配稳定 IR 节点。关键在于**保留 `MatcherRotaryEmbedding`** 并新增 `aiter` IR provider，避免移除 `+rotary_embedding` 强制注册后静默禁用 ROCm AITER RoPE。IR op 优先级在 lowering 阶段选择实际内核（native vs `_C` vs AITER Triton）。
- **影响**：解决 #28042 长期问题，统一 CUDA/ROCm 的 RoPE 融合路径。范围限于基础 RoPE，后续需覆盖 DeepseekScaling、mRoPE 等。这是编译架构层面的重要重构。

#### 2. PR #58851：跨 KV cache group 共享 GDN/Mamba/KDA batch metadata
- **技术解读**：混合模型每步在每个 KV cache group 重建 batch-level attention metadata，但相同 builder class 的 group 仅 block table 不同。`build_attn_metadata` 向每个 group 的 `CommonAttentionMetadata._cross_group_cache` 传入 dict，第一个 group 存储 batch-level metadata，后续 group 仅添加依赖 block table 的部分（state indices、KDA 的 RecoverSSM commit metadata 和 prefill checkpoint）。覆盖 GDN、Mamba1/2、ShortConv、PleShortConv 非 spec batch、ROCm/NVIDIA Kimi-K3 KDA。
- **影响**：Qwen3.6-35B-A3B + DFlash 有 46 个 group（30 个 GDN），该优化可显著减少每步 CUDA 调用和 metadata 构建开销。是 MRV2 架构下 hybrid 模型性能的关键改进。

#### 3. PR #58868：集成 GPU mmap 权重页预取（GB10）
- **技术解读**：在集成 GPU（DGX Spark/GB10）上，共享权重加载器直接从 safetensors mmap view 执行 `param.copy_(loaded_weight)`，PyTorch 将 pageable 指针传给驱动 copy，导致 page fault 发生在 copy 内部。GB10 上每 800 KiB 张量 1.7-3.0 ms vs CPU 先 fault 的 0.08-0.64 ms。新增 `copy_weight_(dst, src)` 在集成 GPU 上每页 touch 一字节再 copy，用于 26 个 copy 站点。离散 GPU 上关闭（增加 0.022-0.028 ms/tensor）。
- **验证**：在 4× GB10 上 DeepSeek-V4.1-Flash TP4，`read_ahead_kb=128` 时加载时间从 205-207s 降至 149-151s（-27%），且 TP 切片位置差异缩小。
- **影响**：针对 NVIDIA GB10 集成 GPU 的加载性能优化，对 AMD 平台无直接影响，但方法可借鉴。

#### 4. PR #57251（已合并）：SimpleCPUOffloadConnector 的 Prometheus 指标
- **技术解读**：通过 `KVConnectorStats` 管道暴露 CPU offload 连接器遥测，5 个 series：`save_outcomes_total{outcome}`、`load_blocks_total`、`used_blocks`、`pending_store_blocks`、`info{backend,page_cache,lazy_offload,capacity_blocks}`。调度器侧，传输路径不变。行为变更：`reset()` 现在用自上次 drain 以来的 outcome 种子新的 `BoundaryStoreStats`，避免跨 cache reset 丢失窗口。
- **影响**：提升 KV offload 的可观测性，便于运维诊断（如 `pending_store_blocks` 持续增长表示 transfer 卡住）。

#### 5. PR #58830（已合并）：限制 per-request 多模态 processor kwargs
- **技术解读**：API 客户端可发送 per-request `mm_processor_kwargs` 和 `media_io_kwargs`，流入多模态媒体加载和 processor 构建/尺寸计算。不可信覆盖可强制极端图像/视频设置导致内存耗尽。默认拒绝非空 per-request 多模态 kwargs，新增 `--trust-request-mm-kwargs`（默认 `False`）供可信部署 opt-in。服务端 `--mm-processor-kwargs`/`--media-io-kwargs` 和离线 `LLM` 用法不变。
- **影响**：重要的安全加固，防止 DoS 攻击。

### 💡 值得关注的问题

1. **ROCm kpool indexer block table 正确性（Issue #58858）**：GLM-5.3-Flash 在 gfx942/gfx950 共享路径上可能存在 pool 写入 padding、位置别名 block 0 的正确性 bug。报告者无 MI300/MI355 验证，**需要 AMD 硬件用户确认或排除**。这是本周期最值得 AMD 社区跟进的正确性隐患。

2. **Gemma4 MTP / spec decode 崩溃根因未修复（Issue #42261）**：跨 drafter 家族、跨硬件的相同崩溃签名（`indexSelectSmallIndex` 断言）强烈暗示 vLLM spec-decode input-prep 路径的竞态。@SoluMilken 提出关联 #37132 的修复假设，但未被验证，Issue 已被自动关闭。**建议社区重新开启并针对 #37132 做 A/B soak test**，尤其影响 Gemma4/Qwen3.5 等 MTP 用户。

3. **Hybrid 模型 profiling 阶段显存开销（Issue #42147）**：`_init_minimal_kv_cache_for_profiling` 对 hybrid 模型（8 个 KV cache group、block_size 2096）预留约 8 GiB 仅用于 profiling，导致小显存 GPU OOM。`VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0` 命名误导。**建议改进 profiling 内存估算或提供更细粒度的跳过选项**。

4. **WSL2 V2 runner 阻塞 copy 修复（Issue #58849）**：报告者发现 `NonUvaBuffer.uva()` 的 `copy_()` 使用阻塞模式，导致每 decode step 16 次 `cudaStreamSynchronize`。两行 `non_blocking=True` 修复即可获得与 pinned memory 相同的性能提升（~12%）。**建议尽快复现并合并**，这是低风险高收益的性能修复。

5. **RoPE IR 迁移的 ROCm 路径（PR #58838 / Issue #58841）**：历史上多次失败的 IR 迁移方向再次尝试，本次保留 matcher 并补全 AITER provider。**需关注评审中是否对 `MatcherRotaryEmbedding` 的保留和 AITER 分发解耦达成共识**，以及 `DeepseekScalingRotaryEmbedding`/mRoPE 的后续覆盖计划。

6. **DeepSeek V4 a4w4 默认值扩展的验证缺口（PR #58869）**：草稿状态，仅跑过内核级 cosine-similarity，缺少 GSM8K 精度和 AgentX 性能扫描。**在验证完成前不应合并**，否则可能引入 ROCm 上 DeepSeek V4 的精度回归。

7. **DeepSeek V4 Flash 的 DeepGEMM 架构支持（Issue #41027）**：SM120/消费级 GPU 和部分 Hopper 配置（8×H100）上 `hyperconnection.hpp:56` 断言失败。vLLM 侧缺乏对 DeepGEMM 失败的友好降级。**建议评估是否在 DeepGEMM 不可用时自动回退到其他 GEMM 后端**，而非直接崩溃。

8. **AITER v0.1.23 升级的兼容性（PR #58867）**：虽然 diff 显示无移除或签名变更，但 `resolve_activation_dtype()` 的重构涉及 MoE 激活 dtype 选择。**建议在 AMD CI 通过后，额外在 MI300/MI350 上做 MoE 精度回归**。

9. **推测解码的 CUDA graph 模式回退（PR #58863）**：Qwen GDN RecoverSSM 的 builders 声明 `AttentionCGSupport.NEVER`，默认 `FULL_AND_PIECEWISE` 回退到 PIECEWISE。在 breakable CUDA graphs 下会掉到 NONE（无 CUDA graphs），本 PR 修复为 PIECEWISE。**FULL graph 支持是后续工作，需关注其对性能的影响**。

10. **安全默认值变更（PR #58830）**：per-request 多模态 kwargs 默认拒绝是 breaking change（虽然更安全）。**依赖 per-request `mm_processor_kwargs` 的部署需要显式设置 `--trust-request-mm-kwargs`**，建议在 release notes 中突出。
