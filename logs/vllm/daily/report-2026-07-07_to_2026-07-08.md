### 🎯 AMD/ROCm 生态相关动态

本周期 AMD 生态是项目的核心焦点，贡献了大量高质量的 PR，涵盖性能、正确性和平台适配：

1.  **新功能与性能优化 (PRs)**:
    -   **`#47921 [feat: Add AMD NPU vision support for Qwen2.5-VL]`**: 由 AMD 员工提出来的一项重大新功能，通过 FlexMLRT 框架将 Qwen2.5-VL 的视觉编码器卸载到 **Ryzen AI NPU** 上执行，而语言模型部分则保留在 GPU。这为在 AMD 统一内存架构（APU）上高效运行多模态模型奠定了基础。
    -   **`#47896 [FlyDSL decode-attention kernel for 4-bit TurboQuant KV cache]`**: 由 **aditi-amd** 提交，为 MI355X (GFX950) 引入了全新的 **FlyDSL** 解码注意力内核，专门优化 TurboQuant 4-bit KV 缓存。此内核利用 CDNA4 指令集，是 vLLM 在 AMD 平台上进行极致量化和性能优化的关键一步。
    -   **`#47842 [Avoid extra reshape kernel in Qwen GDN output projection]`**: 来自 **mjkvaak-amd** 的优化，通过重构 Qwen 模型的 GDN（Gated Dense Network）输出投影逻辑，消除了一个多余的 Inductor 生成的重塑/拷贝内核，直接提升了推理性能。
    -   **`#47947` 和 `#47945` [Add tuned selective_state_update config for MI300X]**: 由 **vanshbhatia-amd** 提交，为 Mamba 模型在 MI300X 上的 `selective_state_update` 内核分别增加了 fp16 和 fp32 的调优配置。在典型解码范围内，性能提升高达 `1.9x - 2.1x`，弥补了此前仅有 NVIDIA 设备拥有专用配置的空白。
    -   **`#47943 [Add tuned selective_state_update float32 config for MI355]`**: 同样来自 **vanshbhatia-amd**，为 MI355 增加了 fp32 状态缓存的配置，使其与 NVIDIA 设备和 MI355 的 fp16 配置保持对等功能。

2.  **Bug 修复 (PRs & Issues)**:
    -   **`#47854 [Fix EAGLE3 layer0 acceptance collapse]`**: 该 PR 修复了 ROCm 平台上 EAGLE3 推测解码的一个关键崩溃问题。问题源于第一层 draft 解码器的输入预处理路径在 ROCm 上会产生对齐问题，导致 token 接受率急剧下降。修复后，即使默认路径下的性能也得到了显著改善。
    -   **`#47950 [Sleep mode + speculative decoding cause crash]`**: 此 PR 修复了在 ROCm/MI250 上同时启用睡眠模式和推测解码时的崩溃问题。根本原因是库查找逻辑 (`find_loaded_library`) 错误地匹配到了 `libcudart_stub.so`，现已通过更严格的文件名匹配模式修复。
    -   **`#47836 [Bug: Loading Qwen GPTQ MoE model failed]`**: 一个涉及 ROCm 平台加载 GPTQ 量化 MoE 模型的 Bug。社区成员 **hammadkhaliq-del** 在短时间内定位到问题（由某次提交导致），并发现该问题已在 `main` 分支的最新提交中被修复，充分体现了社区的快速响应能力。

3.  **平台适配与 CI 改进 (PRs)**:
    -   **`#47766 [Key sparse-MLA persistent metadata on per-request context lengths]`**: 该 PR 修复了 ROCm 平台上稀疏 MLA（Multi-Layer Attention）在长文本场景下的输出崩溃问题。问题的原因是缓存键没有区分不同上下文长度的预填充块，导致元数据冲突。
    -   **`#47912 [Fix pooling startup workspace lock]`**: 修复了由于 CUDA 图捕获与 Workspace 锁不一致导致的 ROCm V1 工作器启动失败问题。
    -   **`#47894 [Fix empty-tensor .max() crash in AITER FA]`**: 修复了在语音转文字模型预热时，因 `cu_seq_lens_cpu` 为空张量导致 AITER FA 后端崩溃的问题。
    -   **`#46904 [Refresh ROCm base images]`**: 改进了 ROCm 镜像的 CI 流程，确保基础镜像变更能被充分测试和发布。
    -   **`#47928 [The Rock / AMD: Add spawn method in vision examples]`**: 修复了多模态示例因 `fork` 进程方式导致 CUDA 重初始化失败的问题，增加了 `spawn` 方法。

### 💬 高热度讨论分析

本周期内有两个讨论热度非常高的议题，值得深入分析：

1.  **`#40076 [Feature: Per-request timing metrics in response body]`**
    -   **核心议题**: 是否应在 OpenAI 兼容 API 的响应体中，增加一个可选的 `metrics` 字段，用于返回请求粒度的时序数据（如排队时间、预填充时间等），以便进行计费、SLA 监控和延迟调试。
    -   **观点与立场**:
        -   **支持方（`nv-nedelman-1`, `lawcontinue`, `gkowarzyk`, `bartlettroscoe`）**: 认为该功能有实际生产需求，尤其是在多租户计费和请求级延迟分析方面。他们指出，Prometheus 和 OpenTelemetry 无法完美满足这两个场景（Prometheus 是聚合数据，OTEL 有延迟且需要额外查询）。`llama.cpp` 已提供类似的 `timings` 对象，证明了该功能的实用性。
        -   **反对方（`robertgshaw2-redhat` 为主）**: 认为应将时序信息通过 OpenTelemetry 链路追踪来处理，而不是修改早已明确的 OpenAI API 响应格式。使用响应体会“污染”标准协议。
        -   **中间派/调和方（`vrdn-23`）**: 提出可以将此视为一种折中方案，并讨论了在头部（Header）或响应体中实现的优劣。最终维护者团队倾向先在响应体中实现一个基于 openai 未正式公开的扩展字段。
    -   **最终结论**: 该 Issue 于本周期被关闭，但其精神已在 PR `#47920` 或相关工作中被采纳。社区决定以 **`VLLM_USE_LOGGING_STATS=1`** 的方式，在日志和响应中提供这些指标，而不修改 OpenAI 的 schema。

2.  **`#47836 [Bug: Loading Qwen GPTQ MoE model failed]`**
    -   **核心议题**: 加载 GPTQ 量化的 MoE 模型时失败，错误信息为 `IndexError: index 0 is out of bounds for dimension 0 with size 0`。
    -   **观点与立场**:
        -   **报告者 (`hnhyzz`)**: 提供了详细的复现步骤和环境，证明该 Bug 与特定的 MI100 适配无关，是一个通用问题。
        -   **分析者 (`hammadkhaliq-del`)**: 迅速定位到了问题的根因——一个近期提交改变了 `load_weights` 的调用方式，导致在 GPTQ 模型中未正确跳过为 WNA16 方法创建的占位符张量。
        -   **维护者**: 确认这是一个已修复的问题。
    -   **最终结论**: 报告者通过更新到最新 `main` 分支解决了问题。该 Bug 的修复已合入主线。这是一个典型的通过社区协作快速定位和验证 Bug 的案例。

### 🛠️ 重点技术变更

1.  **`#47924 [RFC+prototype] Compile the decode step e2e** (Draft)**: 这是一份重要的技术RFC，探索了将 `torch.compile` 扩展到整个解码步骤，包括 KV 缓存管理。初步数据显示，KV 缓存管理的 CPU 开销是已捕获 GPU 计算部分的 `5x`。该 RFC 提出的方法（B.1 部分）证明了将 slot-mapping 内核移入 CUDA 图是可行的，为减少解码延迟开辟了新路径。

2.  **`#47921 feat: Add AMD NPU vision support for Qwen2.5-VL`**: 如前所述，这是一个开创性的工作。它定义了 vLLM 与 NPU 协同工作的模式（CPU ONNX 预处理 → NPU 推理 → CPU 后处理），并通过环境变量 (`VLLM_VISION_NPU_CACHE`) 灵活启用，对主流模型在 AMD 平台上的部署有重要参考价值。

3.  **`#47948 [MoE] Add flashinfer.moe_ep all2all backends`**: 该 PR 为 vLLM 的 MoE 架构引入了两个全新的专家并行（Expert Parallel）通信后端，基于 FlashInfer 的 `moe_ep` API。这为在 NVIDIA GPU（CUDA 13+）上运行大型 MoE 模型提供了更多通信策略选择（低延迟和高吞吐），进一步削弱了对 DeepEP 等第三方库的依赖。

4.  **`#47888 [Bugfix] Avoid blocking model launching when no system ffmpeg`**: 这是一个“小修大补”的典型。它解决了 `torchcodec` 库在系统缺少 ffmpeg 时导致整个 vLLM 服务无法启动的严重问题。通过将 import 错误从启动时推迟到实际使用视频解码时抛出，保障了其他功能（如纯文本 LLM）的可用性，体现了对用户体验的细致考虑。

5.  **`#47823 Simplify offload-completion barrier`**: 该 PR 简化了 KV 缓存卸载完成后的验证机制。从原先复杂的 ZMQ 事件监听，改为轮询 `reset_prefix_cache` 端点的成功状态。这不仅移除了复杂的依赖，也使测试逻辑更加健壮，减少了因时序问题导致的测试不稳定。

### 💡 值得关注的问题

1.  **安全风险 – 恶意附件**：多个 Issue（`#47934`, `#47930`, `#47958`）中出现了用户上传 `.zip` 附件的可疑行为，已被维护者标记为恶意软件并封禁用户。虽然问题已处理，但这警示社区需要加强对 Issue/Comment 中链接和附件的审查，防止社工攻击。
2.  **功能性缺陷 – 单次增量导致工具调用丢失**：Issue `#47907` 和 `#47955` 报告了 `gigachat3`, `granite` 等工具解析器在流式输出时，如果整个输出作为一个 Delta 返回，会丢失函数调用参数。这表明流式输出和最终输出在工具解析路径上存在不一致，需要修复以为用户提供可靠的流式服务。
3.  **长期存在问题的关闭 – 前缀缓存问题**：有 29 天历史的 Issue `#20261`（前缀缓存忽略视觉输入导致并发错误）在本周期被关闭。该问题由 Qwen2.5-VL 用户报告，虽然有多个用户复现，但似乎未得到根本性解决。虽然被标记为已关闭，但相关 Bug 是否完全消除需新版本用户验证。
4.  **生态依赖**：`#47859` 和 `#47888` 揭示了 vLLM 依赖于外部库（`fastokens` 和 `torchcodec`）时可能遇到的启动问题。尽管已修复，但这提醒贡献者在引入新依赖时需要更加谨慎地处理缺失或版本不兼容的情况，避免影响主要功能的启动。
5.  **Transformers 升级影响**：长时间悬而未决的 PR `#41359` (Bump Transformers 版本) 终于合并，这解决了多个由于 Transformers 版本过旧导致的问题，但也可能引入新的兼容性问题。未来几天的 report 应关注其是否对模型加载或 Inference 产生副作用。
