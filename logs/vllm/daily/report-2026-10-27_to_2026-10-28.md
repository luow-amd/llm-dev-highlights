### 💬 高热度讨论分析

#### 1. Issue #41789 — Gemma4 MTP 投机解码接受率仅 0.2%（9 条评论，已关闭）

**核心议题**：`gemma-4-31B-it-AWQ-4bit` + MTP assistant 在 5090 上平均 draft acceptance 0.2%。报告者 maxin9966 又追加 26B-A4B 模型，acceptance 全为 0。

**多方观点**：
- **KrxGu**（维护者视角）：指出多处混淆因素——`num_speculative_tokens=4` 会触发多次同层 forward 降低接受率；模型 generation config 覆盖了 `temperature=1.0/top_k=64`。建议用 `num_speculative_tokens=1`、`--generation-config vllm`、temperature=0、关闭 prefix caching 隔离。
- **marcinbrzezanski**：在 L40S 上按上述隔离后**仍能复现**近零接受率（RedHatAI FP8-Dynamic）。
- **tbooher89**：关键指出 `vllm/vllm-openai:gemma4-0505-cu130` 镜像基于 #41745 的**早期 commit**，后续已有「量化 base + 未量化 draft」的修复；改用 nightly 后 NVFP4 26B 可达 30–80% 接受率。
- **Myziot**：提出假设——**MTP drafter 必须与主模型量化精度一致**，量化/未量化混搭在数学上必然失配；实测未量化 draft + FP8 主模型的接受率确实异常。
- **GeorgeAndreiBals**：指出 **CPU 后端（Xeon）上 MTP 接受率也为 0%**，暗示这是独立于量化的 CPU 路径问题。

**争议焦点**：是「量化不匹配」的预期行为，还是「过时镜像 + 真实 MTP 对齐 bug」+ 「CPU 后端未实现」的复合问题。

**结论**：因 90 天无活动被 stale 自动关闭，但**根因并未被单一修复覆盖**——量化匹配假设与 CPU 路径缺陷值得后续跟踪。

#### 2. Issue #60160 — Qwen3.8-27B-FP8 MI355X AITER=1 高并发精度崩塌（5 条评论，已关闭）

**核心议题**：TP4 MI355X 上 `VLLM_ROCM_USE_AITER=1`，并发 ≥128 时 GSM8K 从 96% 降至 64%，大量响应 ≤5 token 或异常长；关掉 AITER 恢复 96.7%。报告者 weathon 已排除 attention backend、model runner、prefix caching、AITER FP8 linear kernel。

**多方观点**：
- **Kalex14566**（第三方验证工具 VORYTAL 作者）：主动提出用其工具做 AITER on/off 的首个分歧点定位，`@tjtanaa` 表示欢迎。
- **giuseppegrossi**（AMD）：在最新 ROCm nightly 上**无法复现**，c256 下 GSM8K 稳定 97%，列出可能的修复候选（AITER bump #59794/#62486、custom all-reduce 等）。
- **weathon**（报告者）：用旧镜像 `36768d1` 做对照，确认**旧镜像仍复现（65.88%）**，新镜像 `0.32.1rc1.dev361+g83c078d95` 达 **96.74%**，明确「改善来自镜像而非环境」，同时 c1 场景 13/14 指标持平。

**争议焦点**：初期怀疑是 attention backend 或 kernel 问题，事实证明确为 AITER 组件（未最终定位到具体 kernel）在特定 nightly 中被修复。

**结论**：确认为镜像版本问题，**已解决并关闭**。这是一个「高并发下 greedy 输出受 batch 组成影响」的典型分布式正确性案例，对 AITER 的回归测试覆盖有启示。

#### 3. Issue #64204 — Qwen3.5 AOT 编译缓存无法加载（2 条评论）

**核心议题**：Windows 构建 + torch 2.11 下，warm start 报 `Kernel index 1 not found in id_to_kernel`，AOT 缓存加载失败并重编译。

**多方观点**：
- **cipheraxat**：在 Linux + torch 2.14 上无法复现，指出 **官方 v0.32.0 pin 的是 torch 2.13**，怀疑是 Windows 构建的 torch 2.11 特有问题。
- **harsHdokyc**：从 torch 侧确认——**torch 2.14 的 `aot_compile_types.py` 才序列化/恢复 Triton kernel side table**，2.11 缺此能力；同时指出 `_compute_code_hash` 缺 `encoding="utf-8"` 是另一个独立 Windows 问题。

**结论**：**非 vLLM bug**，是 Windows 构建的 torch 版本落后所致，建议升级 torch。

#### 5. PR #61903 — H100/H200 CuteDSL BF16x3 Router GEMM（8 条评论，已合并）

**核心议题**：SM90 上 fp32 router 权重的 32+ token 路径此前是 CUDA core 上的 fp32 SGEMM，本 PR 用 CuteDSL BF16x3 替换。作者 ischencheng 最初用 Triton 实现，后按项目惯例重写为 CuteDSL `VllmJitKernel`。

**讨论焦点**：
- **gau-nernst** 提问：为何不用 hpc-ops 的 2-term BF16 high/low split（#49312 已是 opt-in）？
- **ischencheng 论证**：2-term 只保留 fp32 的 16/24 有效位，1024 token 时 MAE 5.7e-6~7.4e-6，而 3-term 为 3e-7~4e-7，**低于被替换的 fp32 SGEMM（0.8e-6~1.4e-6）**，因此坚持 3-term。
- **风险提示**：ERNIE-4.5 在 ≤128 token 场景上 kernel 比 fp32 GEMV 慢（9.6 vs 7.2µs），作者因此把 GB200 的 48-token 规则改为 Blackwell-only。

**结论**：数值论证充分后合并。体现 vLLM 对「性能提升不能牺牲数值保真度」的严格要求。

### 🔥 热门话题与趋势分析

**1. AMD KV cache 量化格式的「军备竞赛」**
今日 5 个新 PR 直接围绕 MXFP4/NVFP4 KV cache 展开（#64120/#64121/#64123/#64198/#64199），覆盖 DSv4.1、GLM-5.3、MiniMax-M3、Qwen3.8、Qwen4Exp 五个模型家族。核心驱动力是**同样的 HBM 存更多 token**（272 vs 512 vs 1024 B/token/head），这是长上下文推理的关键瓶颈。gfx950 的 e2m1 + e8m0 与 Blackwell 的 NVFP4 形成明确的平台对标。

**2. MonoKernel / 专用解码内核成为 AMD 的性能主战场**
`amd-dlimpus`、`okorzh-amd`、`hyukjlee` 三人贡献了 MonoKernel TP8、mHC Sinkhorn 移出关键路径、Markov sampling 分片、K2 sentinel all-reduce 等一套组合拳，典型收益 **ITL/TPOT −4%~−7%**，且强调「bit-exact」或「bitwise 一致」。

**3. RDNA3 与老 gfx 架构的持续补位**
#52970（RDNA3 AITER）、#63978（MI250X SiTU）、#64084（gfx942 Quark MXFP4）、#64045（R9700 int4）显示 AMD 生态正从 MI300X/MI355X 向**面向边缘/工作站的 Radeon、上一代 CDNA2（gfx90a）、消费级 RDNA3** 扩散。

**4. CI 正确性守门加强**
#64176（ROCm sync check 允许列表）、#64087（KV head 丢失修复）、#59668（gfx942 双卡交叉验证）、#64176 提及的「16 个 AMD CI 组变红」——表明 AMD CI 从「能跑」走向「能抓回归」。

**5. 投机解码（DSpark/MTP）双平台并进**
NVIDIA 侧 #64033（top-k Markov walk 单 kernel）、#64031（ROCm 侧词汇分片 Markov sampling）、#63996（MRV1 drafter layout 缓存 bug，接受率 51%→63%）三线并进，接受率与 TPOT 是共同指标。

### 🛠️ 重点技术变更

**1. PR #53166 — Kimi-K3 MLA chunked-context gather 融合（已合并，AMD 侧里程碑）**
在 `AiterMLAImpl._compute_prefill_context` 中用 AITER `gather_kv_b_proj` 一次 launch 完成原先 4 个 kernel（gather+dequant、`kv_b_proj` 扩展、两次 slice-assign）；DCP>1 保留原路径。同时把 `_concat_k_nope_k_pe` 切到已合入的 `fused_kimi_k3_mla_kv_concat`。**这是 AMD 侧首次在 MLA prefill 上下文路径上实现完整融合**，标志着 AITER 与 vLLM 核心 attention 抽象的耦合加深。

**2. 系列 PR #64120/#64121/#64123/#64198/#64199 — ROCm 上的 MXFP4/NVFP4 KV cache 矩阵**
这组 PR 不是单一变更，而是**为 AMD 建立与 NVIDIA 对称的「低精度 KV cache 生态」**：DSv4.1 `mxfp4_ds_mla`、GLM-5.3 `mxfp4_mla`、MiniMax-M3 `mxfp4`、Qwen3.8 `mxfp4_qsa`、Qwen4 NVFP4。共同模式：定义 `KVQuantMode.CUSTOM`、新增 cache writer 与 split-K 读取、使用 `tl.dot_scaled`（bf16×e2m1）原生 scaled-MFMA。对长上下文服务容量有**近 2× 提升**，但多数为 draft 且 stack 在其他 PR 上，落地周期值得观察。

**3. PR #60154 — DSv4/4.1 inverse RoPE + MXFP8 量化折叠进 AITER sparse MLA store（已合并）**
原先 attention 之后单独跑 `rocm_inverse_rope_rows_` 和 MXFP8 量化，现在 AITER kernel 在 store 阶段直接完成，配合 `inv_rope_positions`/`out_mxfp8` 参数。输出吞吐 **+0.76%~+1.75%**、TPOT −0.7%~−1.7%，且 GPQA/NIAH 略有提升。展示了**把后处理 kernel 折叠进 attention epilogue** 这一通用优化范式。

**4. PR #64004 — gfx942 Kimi-K3 MXFP4→int4 requant 19× 加速（已合并）**
TP8 纯张量并行下 requant 从 19min15s 降至 **59s**，server 启动 1348s→235s，权重**逐字节一致**。这解决的是 gfx942（MI300X/MI325X）用户无法忍受的启动延迟，使 int4_per_group_32 量化配置在大模型上变得实用。

**5. PR #64106（Issue）— Kimi-K3 MI355X FP8 KV cache 精度崩塌**
虽为 Issue，但因直接指向**官方 recipe 缺陷**（`recipes/models/moonshotai/Kimi-K3.yaml` 默认 FP8 KV），影响面大：任何遵循 recipe 的用户都会得到 GSM8K 0.305 的模型。目前由 AMD 侧接手但尚无修复 PR，是今日**最需社区关注**的正确性问题。

### 💡 值得关注的问题

**1. Issue #64106 — Kimi-K3 官方 recipe 的 FP8 KV 精度缺陷（最高优先级）**
影响所有按 recipe 启动 Kimi-K3 MI355X 的用户，且「silently breaks accuracy」而**无任何 warning**。建议：(a) recipe 侧改为 `auto` 或加 warning；(b) 定位 AITER FP8 KV 写入/读取的具体 kernel；(c) 补充 KV dtype 的精度回归测试。目前 `@giuseppegrossi` 接手但无 PR。

**2. PR #64135 已知缺陷：DSv4.1 原生 ASM 与 attention overlap 不兼容**
作者 `Fangzhou-Ai` 自述 compressor-layer overlap 会 stall，临时方案是禁用 attention 辅助流（牺牲性能）。这是 DP 部署的关键路径问题，**需要 AITER 或 vLLM 侧的 overlap 调度修复**，否则原生 ASM 的收益要打折。

**3. PR #64142 — 重新合入 AITER preshuffled FP8 block-scale GEMM**
该 kernel 曾导致 DSv4 GSM8K 跌至 **0.0008**，根因**尚未识别**即重新合入（GLM-5.3 精度未退化，但 DeepSeek-V4-Pro 的回归测试仍 pending）。建议在合入前必须补上 DSv4/R1 的 GSM8K 门禁。

**4. Issue #63997 — NixlConnector 不同 block size 分区失败（Gemma 4 + HMA）**
`Mramaran` 已给出根因（`_sync_block_size_with_kernel` 对每个后端取单一 kernel block size，而 model runner 按 group 取不同值），并主动请缨修复。**PD 分离 + 混合 KV cache 管理器的组合仍不稳定**，KV connector 的 block geometry 需要系统重构。

**5. PR #64060 系列「stacked on」依赖链风险**
`#64123→#61529`、`#64198→#64111`、`#64121→#61662+#60321`、`#64120→#57523→#57463` 等多层堆叠 PR 同时 open，任何一个底层 PR 延迟都会拖累整条链。**建议社区关注这些链的合入顺序**，必要时用 feature branch 方式推进。

**6. Qwen4Exp QSA 命名与 NVFP4（#64110、#64199）**
两 PR 同时动 QSA 的 cache 布局与 indexer 命名，`peakcrosser7` 的重新命名 PR 与 `lesj0610` 的功能 PR 存在潜在冲突，需要协调。
