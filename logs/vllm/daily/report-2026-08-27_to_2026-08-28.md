### 🎯 AMD/ROCm 生态相关动态

本周期 AMD 相关动态非常丰富，是当之无愧的焦点。以下按类别梳理：

#### 1. 构建与依赖修复

- **[Bug] ROCm profiler 挂起**（#54087 → 修复 PR #54171）：`rocprofiler-sdk 1.3.2` 的 queue interposition 存在 bug，导致在 ROCm 上启动 torch profiler 时引擎无限期挂起。`simondanielsson` 定位到根因是 rocprofiler-sdk 缺少两个上游修复（ROCm/rocm-systems#7924、#7796），并提交了在构建阶段 cherry-pick 这两个补丁的 PR。**临时缓解方案**：设置 `ROCPROFILER_QUEUE_INTERPOSITION=0`。`jamesETsmith` 确认在 MI355X（gfx950）上同样复现。
- **[Bugfix] 把 ROCm 排除在 >=160GiB batch token 档位之外**（#54205）：#51726 按显存容量（≥160GiB）设置更大的 `max_num_batched_tokens`，但误伤了 MI300X（192GB）和 MI325X（256GB），导致 DeepSeek-V4-Pro 在 1M context 下 KV cache 初始化失败。该 PR 将新档位限定非 ROCm 平台，恢复 AMD 原有行为。
- **AINIC 仓库升级**（#54112）：升级默认 AINIC repo 以提供 `libionic 54.0-187-1`，这是 MI355X 上 MoRI-EP 和 NIXL 所必需的。

#### 2. Quark 量化与 MoE 相关

- **[Bug] Quark FSE 兼容性检查误伤 Qwen MoE MXFP4**（#54206，`mjkvaak-amd`）：`is_shared_expert_quant_fse_compatible` 用子字符串 `shared_expert` 匹配 Quark 的 exclude 列表，但误匹配了 `shared_expert_gate`（路由器 gate，本就是 BF16），导致每个 Qwen MoE Quark 检查点都无法启用 fused shared experts（FSE）加速。这是一个回归（#51695 引入），此前 Qwen 本地检查使用带尾随点的`"shared_expert."` 可正确区分。该 bug 让 ROCm 上的 AITER FSE 优化形同虚设。
- **[PR] 将 fused shared-expert gate GEMM 路由到平台 dispatcher**（#54185，`mjkvaak-amd`）：解决 FSE 路径绕过 ROCm 的 tuned GEMM 选择器、直接落到 Tensile kernel 导致性能减半的问题。改后走 `dispatch_unquantized_gemm`，在 ROCm 上可自动获取 AITER tuned kernel。

#### 3. 内核性能优化（AITER 融合）

- **Kimi-K3 ROCm 内核系列**（多位 AMD 工程师）：
  - #54103：KDA decode 改用 ATOM 的 `fused_sigmoid_gating_delta_rule_update` kernel，并在 MTP+ReplaySSM 下启用 `_replayssm_kda_fwd_kernel`。
  - #54063 / #54066 / #54068：将 MXFP4 量化融合进 AITER linear（KDA decode、MLA gated o_proj），消除独立 quant kernel。
  - #54121：Kimi-K3 C4 decode 在 gfx950 上保持 dense top-k metadata，避免背包（repack）开销。
- **DeepSeek-V4 ROCm 优化**：
  - #54134（`LiuYinfeng01`）：将 FHMoE（heterogeneous fused MoE）从 TP8/DP1 扩展到 TP1/DP8，使用 RCCL 通信和原生 FP8 shared-expert + MXFP4 routed-expert 混合内核。GSM8K 从 94.77% 到 94.54%，差异在噪声范围内。
  - 已合并 #53540：融合 SWA 的 q/kv RMSNorm + FP8 group quant 为单个 AITER HIP kernel（2.90x 加速）。
- **fused clamped SwiGLU**（#54074，`JohnQinAMD`）：消除 ROCm 上 `SiluAndMulWithClamp` 的 6 个 eager kernel，改用 fused op，kernel 提速约 2.3x，decode 阶段每步节省 1.94ms。
- **GDN readout fp32 精度修复**（#54146，`JackDanger`）：在 MI50（ROCm）上发现非 Blackwell GPU 的 GDN decode 因 fp16 溢出导致输出 NaN 并触发 `!!!!` 重复 token。修复为按 SSM state 精度物化输出。

#### 4. MRV2 与 ROCm 兼容性

- **[Bugfix] MRV2 进程内 shutdown 释放 KV cache**（#54162，`okorzh-amd`）：AMD CI 上暴露的测试失败（内存不释放）。根因是 MRV2 的 `free_before_shutdown` 只清理了 registry，未像 MRV1 那样切断 layer 与 KV cache 的引用关系，导致进程内关闭引擎后显存仍被占用。已修复并在 AMD CI 验证。
- **MRV2 全部模型默认化**（#53183 已合并）：这对 ROCm 影响深远——`Moondream3` 等多模态模型因此从 MRV1 切到 MRV2，间接暴露了 #54152 中的 MoE all-reduce 竞态 bug（见热门讨论）。

#### 5. 其他

- **Benchmark FP8 dtype 一致性问题**（#54067 报告 / #54071 修复）：`benchmark_moe.py` 用平台 FP8 dtype 转权重但硬编码 `float8_e4m3fn` 构建 config，导致 gfx942（FNUZ）上 `--dtype fp8_w8a8` 调优不可用。已修复。
- **prefix-prefill tiling 与 KV page size 解耦**（#54194，`ZhengGong-amd`）：针对混合 mamba+attention 模型在 ROCm 上的非 2 幂 page size（544/1040/1056），解除 kernel tile size 对 page size 的依赖，恢复 128/64 tile。
- **GraniteMoeHybrid 量化权重加载修复**（#54052，`Priyjain-amd`）：FusedMoE 重构后 expert mapping 未更新，导致 per-expert 量化检查点 KeyError。

### 💬 高热度讨论分析

#### 1. [Bug] 可选依赖 boto3 破坏所有模型的架构解析（#54153，7 条评论）

**核心议题**：系统里安装了一个损坏版本的 boto3，`except ImportError` 只处理"未安装"而不处理"装坏"的情况。当 boto3 导入时抛出 `AttributeError`（pyOpenSSL/cryptography 不匹配导致），整个模型架构检查过程就被中断，即使用户根本不用 S3。

**不同观点**：
- `false200`：提出修复方案并希望接手——复用 `import_utils._has_module` 把任何导入失败都当作"不可用"，同时建议扩大范围修复 `torchcodec` 的同类问题。
- `aniketwaghh`：补充分析，确认问题在于 `except ImportError` 无法捕获 `AttributeError`/`OSError`，并关联到已存在的 #54097（torchcodec）。建议将其泛化为通用可选依赖处理问题。
- `ryoichi-kurihara`（issue 作者）：认可修复方向，但明确表示 "issue 的核心是：一个我不使用的可选依赖损坏，不应导致非 S3 路径失败"。建议 `torchcodec` 放入单独的 PR。

**当前状态**：`false200` 接手实现，讨论收敛到"一个 issue 对应一个 PR"的原则。

#### 2. [Bug] torch profiler 在 ROCm 上挂起（#54087，5 条评论 + 修复 PR）

**核心议题**：rocprofiler-sdk 1.3.2 的 queue interposition 功能导致 ROCm 上任意 torch profiler 启动后引擎无限期挂起，输出 "Async signal handler still waiting on signal"。在 MI300X 和 MI355X 上均复现。

**观点与措施**：
- `simondanielsson`（报告者）：提供四个长期修复选项：请求 ROCm 团队 backport、自行 cherry-pick、pin 到 develop 分支、以及临时环境变量 `ROCPROFILER_QUEUE_INTERPOSITION=0`。
- `jamesETsmith`：确认 gfx950 也受影响，为复现提供数据点。
- 最终 `simondanielsson` 在 #54171 中实施 option 2（构建时 cherry-pick 两个修复），并验证 patch 干净应用。

**当前状态**：修复 PR 打开可直接合并，但 vLLM 后续需要升级到包含两个上游修复的 rocprofiler-sdk 版本，而非永久维护构建补丁。

#### 3. [Bug] DeepGEMM 在 sm_121 上报"支持"但实际崩溃（#54125，2 条长评论）

**核心议题**：GB10（sm_121）上 DeepGEMM 被选中（`support_deep_gemm()` 接受整个 capability family 120），但实际运行即触发 CUDA fault。

**讨论演变**（出现纠错与多方验证）：
- 报告者 `jschmied` 最初认为是 capability family 检查过于宽松。
- `jahnclawdmonet` 实际追到根因：**属性名不匹配**——`ModelOptFp8PbWoLinearMethod` 中 kernel 存在 `self.w8a8_block_fp8_linear`，但 `process_weights_after_loading` 却检查 `hasattr(self, "fp8_linear")`，导致 DeepGEMM 的权重重处理（UE8M0 requantization）被静默跳过，最终以非法内存访问失败。
- `jschmied` 回复"请把标题视为不准确"，并进一步补充：**仅修复 guard 还不够**——对于 FP32 block scale 的检查点，即使修复 guard 后依然崩溃。这说明 ModelOpt FP8_PB_WO 导出格式本身存在兼容性问题（也关联 #54126）。

**当前状态**：仍在讨论中，涉及模型量化格式兼容性、kernel 选择逻辑和不同平台行为，是一个多层嵌套的复杂问题。

#### 4. [Feature] cuBLAS router GEMM 在 family-120 上启用（#54048，4 条评论）

**核心议题**：GB10/sm_121 上 router GEMM 的 bf16→fp32 路径使用了低效的独立 copy kernel，导致 logits 精度损失。`hclsys` 提议将 cuBLAS tier 从 `allow_specialized_router_gemm` 门控中解耦。

**讨论亮点**：
- `gau-nernst` 指出 Ampere（sm80/86/89）也支持 `out_dtype=fp32`，建议扩大范围；并提示 `torch.addmm` 可处理 bias。
- `hclsys` 最初保持保守范围以控制风险，但在 `gau-nernst` 验证后，扩大门控到所有 `is_cuda()` 平台，并将 bias 支持留作 follow-up。

**当前状态**：PR 已更新为统一开启 CUDA 平台的 fused cuBLAS router GEMM，是平台统一化的一次小胜利。

#### 5. [PR] GLM-5 masked-MHA 路由逻辑存在疑inconsistencies（#53785，合并前审查）

**核心议题**：合并前审查发现两个深层问题——`masked_mha_workspace_fits` 对 batch 大小敏感，导致同一 policy limit 下不同 batch 的实际行为不同；以及 GLM-5 在 TP4 时 num_local_heads=16 会选择 FlashInfer，但新的路由表只有 TP8 的 FlashInfer 条目。

**不同观点**：`simon-veitner-redhat` 指出规范有歧义，`MatthewBonanni`（PR 作者）回应并补充了 workspace guard 的测试以澄清。最终合并。

ModelOpt FP8_PB_WO 存在多种导出约定（#54126）、NVFP4 权重加载路径崩溃（#54173、#40885）、Quark 的 FSE 检查（#54206）——量化工具链（ModelOpt、Quark）与 vLLM 加载器之间的协议需要更严谨的定义与交叉测试。

### 🛠️ 重点技术变更

1. **PR #53183: "Use MRV2 for all models by default"（合并）**——vLLM 运行时的分水岭。MRV2（生产级模型运行器）成为默认路径，仅 ROCm 的部分模型保留 MRV1。直接影响：性能、内存管理、编译管线的统一，也意味着未来新特性（如 #54166 的 Sampling Mask Replay）只需面向 MRV2 开发。

2. **PR #53540: Fuse SWA q/kv RMSNorm and q FP8 group quant for DeepSeek-V4（合并）**——ROCm 上典型的 kernel 融合优化：将 2 个 launch 减为 1 个，消除中间 BF16 写回；同时让 attention 和 indexer 共享预量化结果，decode 步长直接提速 2.9x。这是 AMD 性能工程团队持续蚕食 kernel 开销的代表性工作。

3. **PR #54204: 修复 liveness monitor 误杀健康 EngineCore**——`POLLNVAL/POLLHUP` 被误认为进程死亡，导致正常的 EngineCore 被 SIGTERM。修复要求"真正的 exit code"才判定死亡。这是进程管理健壮性的重要修复，对多进程部署 + 长时间运行的稳定性意义重大。

4. **PR #54012: FlashInfer native CP for MLA decode（合并）**——DeepSeek/Kimi 系列 MLA 注意力在 DCP 下使用 FlashInfer 原生 context parallel mask，替换手动 flatten 的临时方案。为 Kimi-K3 DCP8-DCP8 提供零错误运行的验证数据，是 DCP 的重要一步。

5. **PR #54070: Disk-backed PLE table（VLLM_PLE_DISK_OFFLOAD_DIR）**——将 Qwen3.8-Flash-Next 的 47.68GiB n-gram 表映射到磁盘文件的方案，创新性地利用系统 page cache 与 `MADV_RANDOM` 控制读取放大。让 96GB 显卡也能跑该模型，是"大表放不进显存"场景的实用解法。

### 💡 值得关注的问题

1. **ROCm 平台对新模型的支持节奏**：Kimi-K3、Qwen3.8-Flash-Next、GLM-5 在 AMD 上的适配正在快速跟进（多个 open PR 属于"serve still needs #51392"这种依赖链状态），建议关注这些 PR 的依赖阻塞情况，尤其是 AITER 版本要求（#54095 需要 AITER >= 0.1.20）。

2. **ModelOpt FP8_PB_WO 导出格式兼容性**（#54125、#54126、#54173）：同一检查点在不同 block scale 导出约定下的加载/推理路径存在多个互相纠缠的 bug。模型量化工具厂商与 vLLM 之间的"协议"需要设立兼容性测试套件。

3. **ROCm profiler 修复的长期方案**：PR #54171 采用构建时 cherry-pick，但 vLLM 与 rocprofiler-sdk 的版本绑定关系需要显式化，否则这个问题会在下次版本升级时重新暴露。

4. **MRV2 在 ROCm 上的性能差距**：#53183 明确说明 ROCm 部分模型仍保留 MRV1"until MRV2 performance is fixed for those"。随着 Moondream3 等问题被逐个发现并修复，建议社区关注 ROCm 上 MRV2 的 benchmark 追踪。

5. **GLM-5 masked-MHA 的批次敏感路由**：即期来看，PR #53785 已合并，但其 workspace 限制（128MiB 固定）在 batch > 1 时会让真实路由行为与阈值表不一致——如果生产环境出现 GLM-5 长上下文性能突降，值得回头检查此逻辑。
