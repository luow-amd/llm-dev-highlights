### 🎯 AMD/ROCm 生态相关动态

本周期**AMD生态动态极其丰富**，全面覆盖内核性能优化、新特性支持、Bug修复和CI稳定性。这表明AMD在vLLM上的投入正在加速，并深度整合其“AITER”和“FlyDSL”高性能计算库。

**1. 内核融合与性能优化（重点）**
- **PR #40710** ([Aiter][ROCm] RMSNormGated+GroupedQuantFP8 fusion): 由 `tpopp` 提交，将RMSNorm和Grouped Quantization FP8融合为一个AITER内核，减少了36/48层的内核启动开销，在保持精度（lm_eval匹配率不变）的前提下提升了Qwen3Next模型的decode性能。
- **PR #40711** ([Aiter][ROCm] gdn_linear_attn kernel fusion): 同样由 `tpopp` 提交，为Qwen3Next模型融合了GDN线性注意力相关内核，进一步减少内核开销，性能提升1-4%取决于batch大小。
- **PR #40697** ([ROCm][Kimi-Linear] Wire FlyDSL gated delta rule decode kernel): 由 `ChuanLi1101` 提交，这是一个**性能提升巨大的PR**。它将Kimi-Linear模型的KDA（Kimi Delta Attention）解码路径从Triton/FLA切换到了AMD的FlyDSL内核。微基准测试显示，对于Kimi-Linear-48B-A3B模型的典型解码形状，每个KDA层可节省约52微秒，预计将带来18-24%的TPOT提升。该PR处于草稿状态，正在等待GPU端到端验证，但内核级别的优化效果已明确。
- **PR #40687** ([ROCm][Perf] Support N=5 in wvSplitK skinny GEMM kernels): 由 `mgehre-amd` 提交，扩展了wvSplitK瘦GEMM内核的N支持范围（从4扩展到5），以覆盖Eagle3推测解码（1个原始Token+4个推测Token）的验证步骤。在AMD Strix Halo上测试，Qwen3-8B的TPOT中位数提升12.3%。

**2. Bug修复与兼容性**
- **PR #40763** ([Bug] Fix GLM-5.1 running error on ROCm platform): `qli88` 修复了GLM-5.1在ROCm上因AITER MLA实现要求num_heads>=16而导致的错误，通过添加头数填充工作绕过了此问题。
- **PR #40754** ([Bugfix][ROCm] Fix gemm_a4w4 call to use updated AITER API signature): `chelnnexy` 修复了`quark_ocp_mx.py`中调用`gemm_a4w4`时使用旧AITER API的问题，该问题导致MXFP4 GEMM在ROCm上行为异常。修复后，在MI355X上成功验证了Llama-3.1-405B-MXFP4模型的加载和精度。
- **PR #40686** (fix(rocm): remove workaround causing invalid argument on Qwen3.5 with TP=2): `aaab8b` 移除了ROCm平台上一个旧的workaround，该workaround导致了Qwen3.5模型在TP=2时执行`wake_up`操作时出现“invalid argument”错误。

### 💬 高热度讨论分析

本周期内，以下议题引发了较多讨论：

**1. Issue #40699: [Bug]: Qwen3.5系列离线推理与API Server服务性能差距巨大**
- **核心议题**: 用户 `Katono5` 报告在使用Qwen3.5系列模型时，vLLM的离线推理（`LLM.generate`）与OpenAI兼容的API Server推理之间出现了约10个百分点的performance gap。用户已保证了`input_ids`对齐、使用相同的`qwen_vl_utils`处理器和采样参数，但差距依然存在。
- **观点与立场**:
    - **用户 (`Katono5`)**: 确认是API Server端性能差于离线推理，并提供了详细的复现代码。认为可能是API Server的内部处理（如chat template、请求调度）与离线推理存在未对齐之处。
    - **开发者 (`DarkLight1337`)**: 首先要求用户展示调用方式，并提醒vLLM不会像Transformers那样自动运行`qwen_vl_utils`，可能导致处理差异。后续引导用户提供调用vLLM API的客户端代码以进一步排查。
    - **其他用户 (`ZJY0516`)**: 询问该性能差距是否仅在多模态（视觉）场景下出现，还是纯文本场景也存在，试图定位问题范围。
- **争议焦点**: 核心争议在于**API Server的输入预处理或运行时调度**是否引入了离线推理中不存在的事务。用户坚称预处理代码一致，但开发者倾向于认为问题可能源于vLLM API server与离线模式之间的细微差别（如`qwen_vl_utils`集成、异步调度）。
- **当前状态**: Open。开发者正在引导用户提供更详细的调用代码以定位根因。这是一个可能影响部署选型的严重性能问题，需要密切关注后续进展。

**2. PR #40681: [Model] 支持Hy3 Preview模型**
- **核心议题**: 集成腾讯发布的Hy3-preview模型，包括模型支持、推理解析器和工具调用解析器。
- **观点与立场**: 此PR主要讨论技术验证。
    - **提交者 (`stevenkuang-tencent`)**: 提交了模型支持代码。
    - **社区贡献者 (`andyluo7`)**: 在AMD MI300X (8卡) 上成功构建并验证了该模型端到端运行，提供了详细的构建指南和测试结果，证明PR在ROCm平台上同样工作良好。
- **当前状态**: 已合并。这是一个典型的社区协作案例，提交者提供代码，其他贡献者在不同硬件上验证，加速了新模型的支持速度。

**3. PR #40744: [Frontend] 在传入 `--omni` 参数时委托给vLLM Omni**
- **核心议题**: 解决vLLM Omni插件与vLLM主项目因入口点劫持（entry point hijacking）导致的安装顺序依赖和卸载冲突问题。
- **观点与立场**:
    - **提出者 (`alex-jw-brooks`)**: 提出当前方案存在严重问题，建议改为在vLLM的CLI中检测`--omni`参数，然后直接调用vLLM Omni的入口点，而不是让Omni劫持CLI入口。这样可以避免安装顺序问题和卸载时破坏vLLM。
    - **vLLM Omni开发者 (`hsliuustc0106`, `lishunyang12`)**: 表示认可这是一个长期存在的问题，并同意此方案。`lishunyang12` 要求同步在vLLM Omni端移除劫持代码。
- **当前状态**: Open，等待进一步审批。这个讨论解决了一个插件集成架构的合理性问题，有助于提升用户体验。

**4. Issue #40675: [RFC] 支持Intel ARK量化工具包**
- **核心议题**: Intel提议将他们的自动舍入内核（ARK）量化工具集成到vLLM中，为Intel平台上的AutoRound格式提供原生支持。
- **观点与立场**:
    - **Intel提议者 (`Zhenzhong1`)**: 指出类似于AMD的Quark为AMD生态提供原厂量化支持，Intel需要ARK来完善其Intel平台的量化工作流。强调这是性能优化的关键。
    - **社区开发者 (`yiliu30`)**: 表示赞同，并提出了两点具体建议：1) 更新文档以介绍ARK及其支持矩阵；2) 考虑将ARK的op注册为PyTorch自定义算子，以兼容`torch.compile`功能。
- **当前状态**: Open。这是一个架构层面的RFC，确定了vLLM量化生态将进一步多元化。Intel主动对标AMD Quark的做法也体现了硬件厂商的竞争。

### 🛠️ 重点技术变更

1.  **PR #40697: [ROCm] Kimi-Linear Gated Delta Rule Decode Kernel**: 这是一个**性能里程碑**，通过调用AMD FlyDSL库，将Kimi-Linear KDA解码内核性能提升近4倍。它不仅展示了AMD在非Transformer结构（如线性注意力）上的能力，也证明了“硬件厂商定制库 + vLLM”合作模式的巨大潜力。

2.  **PR #40760: [New Model] DeepSeek V4**: 对社区最重要的新模型支持之一。由Inferact团队提交，并注明所有组件高度耦合、涉及手动融合内核，**警告他人不要随意修改**。这通常意味着该实现进行了大量定制优化以达到最佳性能，也意味着维护风险较高。

3.  **PR #40676: [Core] 通过pinned block保留混合注意力模型的Prefix Cache**: 解决了Gemma-4等SWA+Full混合注意力模型的prefix cache几乎为0的问题。引入`is_pinned`概念，使已完成的请求的缓存块得以保留，避免了被FIFO队列快速回收。这对长序列、高并发场景下的缓存命中率提升至关重要。

4.  **PR #39878: [Build] 默认CUDA切换至13.0，更新架构列表**: 这是一个影响所有用户的基础设施变更。CUDA 13.0成为默认版本，并移除了Volta (SM70/SM75) 支持，这符合PyTorch的策略。用户需要确保其环境已更新到支持CUDA 13.0的驱动。

5.  **Issue #40696: [Feature] Mamba混合模型的Prefix缓存完全失效**: 这是一个重要的**设计挑战**。用户`Gaodzlearn`详细分析了Mamba混合模型（如Qwen3.5）因attention block size被迫对齐到528 tokens（Mamba页面大小）而导致prefix缓存对短提示完全失效的问题，并提出了4种解决方案（包括解耦block size）。该Issue的后续处理方向将直接影响混合注意力模型的效率和可用性。

### 💡 值得关注的问题

1.  **Qwen3.5 Offline vs. API Server性能差距 (#40699)**: 该问题如果被证实是一个普遍存在的bug，将严重影响用户的部署选择，尤其是对精度要求高的场景。社区需要尽快定位根因并提供fix。
2.  **混合模型Prefix缓存有效性 (#40696)**: 用户提出的方案4（解耦Mamba和Attention的block size）可能是最根本的解决方案，但工程实现复杂。这个设计决策将影响vLLM对新兴混合架构模型（Qwen3.5, Gemma-4等）的支持质量。
3.  **FIPS合规性问题 (#40741, PR #40764)**: 将`opencv-python-headless`变为可选依赖的提议，对于在政府、金融等需要FIPS合规环境中部署vLLM至关重要。该问题的解决将扫清vLLM在这些场景的部署障碍。
4.  **Intel ARK量化工具包RFC (#40675)**: 这是硬件生态竞争在软件层面的体现。社区需要评估引入一个新的量化工具包所带来的维护成本与性能收益，并决定其与现有量化框架（如Quark, torchao）的关系。
5.  **EPLB与自定义MoE模型的兼容性 (#40740)**: `assert`断言失败暴露了EPLB（Expert Parallelism Load Balancing）功能对模型架构的强假设。随着更多厂商推出自己的MoE实现（如Phi-mini-MoE），vLLM需要标准化MoE接口或扩展EPLB的兼容性。
