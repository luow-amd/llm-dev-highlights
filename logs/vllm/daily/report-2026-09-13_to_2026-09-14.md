### 🛠️ 重点技术变更

#### 1. #56512 — Engram async prefetch + DP sharding（已合并，DeepSeek-V4.1）
将 Engram n-gram 表的查找从主 stream 内的 inline 执行改为**在 forward 入口用 per-layer side stream 预取**（n-gram hash ids 在 decoder layers 运行前已全部已知），halved grid 为主 stream 留出 SM；`embed()` 只做 stream wait。配合 DP sharding 与 `MAP_SHARED` 宿主机表。**影响**：189 GiB 级别的 Engram 表在 TP/DP 布局下不再必须全复制，且 UVA 查找的延迟被隐藏到主流程序之外。这是 V4.1 长上下文服务的**内存可行性关键**。

#### 2. #56464 — DeepSelect TopK 集成（已合并）
通过 CMake FetchContent 引入 DeepSeek 的 DeepSelect（MIT），为 DSA sparse indexer 的 decode top-k 提供 7 种可选后端（`auto`/`deep_select`/`cooperative`/`persistent`/`per_row`/`flashinfer`/`torch`），并新增 `KernelConfig.sparse_indexer_topk_backend`。使用 PyTorch stable ABI（`STABLE_TORCH_LIBRARY`, `USE_SABI 3`），仅编译 sm_100a/sm_103a。reviewer `ywang96` 给出"**approve with comments**"，但标记了一个 **major correctness 问题**：`_sparse_indexer_topk_row_ends` 的 `(B,1)` 分支缺少 `max(0, ...)` clamp，短 prompt + spec decode 时会产生负 `end` 传入 kernel（reference kernel 有 clamp）。**影响**：DSA 路径首次拥有可插拔的 top-k 后端，但负 `end` 案例需在后续 PR 修复。

#### 3. #56305 — Triton/FlashInfer 组合用于多模态前缀注意力（已合并）
用 Triton image masks + FlashInfer causal attention 组成可复用 composite（`TRITON_FLASHINFER`），HND 布局 + 64-token page。B300×4 TP 上 `gemma-4-31B-it`：文本 BF16 KV 在 conc=128 时 output tok/s 从 6891 → **9405**，TPOT 17.9 → **13.0 ms**；FP8 KV 下固定 5 req/s 时 TTFT **降低 34.5%**。

#### 4. #55235 — ROCm MiniMax-M3 decode top-k 调优（已合并）
gfx950 上当 `topk==16` 且 graph capacity ≤128 sparse blocks 时，使用单一 **B128/C1/W2/S1** CTA 配置替代 B512/C16。production 74-block capacity 下 selector+sparse table 加速 **26.7–28.8%**；精度契约不变（BF16 index cache、FP32 score、确定性排序），121 passed / 13 skipped。

#### 5. #55802 — 移除 DCP indexer interleave guard（已合并，争议性）
删除 `DeepseekV32IndexerMetadataBuilder` 中对 DCP + `interleave > 1` 的 9 行拒绝检查，并补充 TP1 完整 KV 的注意力输出回归测试。**作者 `stu-cao` 的诚实披露值得注意**：原 guard 引用 GSM8K 失败（#46076），但 **"该历史失败从未被 root-cause"**；4 次对照实验得 −11/+23/+3/−10，**不构成一致性结论**；PR 描述明确标注 "Draft: ... accuracy equivalence is not established"。**影响**：解锁 DCP + NIXL（interleave 64）配置，但留下了未闭环的精度疑云。

### 💡 值得关注的问题

**1. #56712（Open，高严重度）— 借用方法导致的 EngineCore 崩溃**
`DiffusionGemmaForConditionalGeneration` 通过**类级赋值借用** 7 个 Gemma4 方法，但不运行 Gemma4 的 `__init__`，因此 `self._enable_mm_lora` 不存在，任何图片请求触发 `AttributeError` 并**杀死整个 EngineCore**（而非单请求失败）。`he-yufeng` 已确认 root cause 并指出修复方向分歧：
- #54309 的现有修复：在借用方**设置该 flag**（逐点修复）
- 其 review 建议：**在读侧加固** `getattr(self, "_enable_mm_lora", False)`（修复整类未来借用者）
这是一个"类级方法借用"反模式的典型案例，值得作为架构决策讨论。

**2. #56699（Open，未定论）— HiSparse 在 P/D host import 下的 CUDA launch failure**
NIXL P/D 部署中，decode 侧 HiSparse 在持续 host import 下 3/3 复现 `unspecified launch failure`。开启 `CUDA_LAUNCH_BLOCKING=1` 后失败点从 `_finish_mirror_phase → event.synchronize()` **移动到 FULL CUDA graph 的 `replay()` 内部**，说明真正 fault 的是被重放的图内 kernel，前者只是异步错误的收集点。这是一个尚未定位到具体 kernel 的硬故障，且涉及 #55398 的 adaptive host/GPU import 逻辑。

**3. #56668（Open）— CPU-only 机器上 81 个 kv_connector 测试失败**
#54042 把 `CPUAttentionBackend.get_supported_kernel_block_sizes()` 从 `MultipleOf(16)` 改为 `MultipleOf(32)`，导致 `tests/v1/kv_connector/unit/` 下 81 个测试在 worker 构造时报 `ValueError: No common block size for 16`。**根因是 CI lane 设计**：这些测试未标 `cpu_test`，只在 GPU lane 运行（`-m 'not cpu_test'`），因此永远选不到 CPU attention backend。这直接损害了**无 GPU 贡献者**的本地测试能力，属于流程性缺陷。

**4. #56701 / #56709（Open）— KV Offload 与 MTP 保留历史的不变量缺口**
`SlidingWindowSpec.extra_retained_tokens > 0` 时，offload lookup 与 producer store mask 使用**注意力窗口**，而 block manager 分配使用**窗口 + extra**，导致"报 hit 后尝试加载从未被存储的 chunk"。这是一个典型的**跨模块不变量未对齐**问题——RFC（#56701）与实现（#56709）在同一周期提交，但契约层面（"offload 是否应覆盖完整保留区间" vs "外部 hit 时只分配注意力所需区间"）仍需社区裁决。

**5. PR #56732 引发的路线图问题**
`njhill` 明确表示 cpu-ngram 即将废弃、MRV2 为 GPU-only，但作者追问 "ngram-cpu 对 vllm-cpu 是否还有用" 后**无人回应**。这暗示 vLLM 的 CPU 推理路径与 GPU-first 的 MRV2 演进之间可能存在未公开的张力，值得维护者澄清。
