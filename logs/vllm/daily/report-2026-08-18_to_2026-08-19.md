### 💬 高热度讨论分析

**1. Issue #52693（4 条有效讨论）— 流式输入零 token 续传崩溃**

- **核心议题**：resumable 会话中零 token 续传导致 `Invalid request status: RUNNING`，进而 `EngineDeadError` 杀掉整个引擎，且可由普通聊天流量触发（9 次引擎死亡/5 实例/4 配置）。这是 #52471 的后续。
- **参与者观点**：
  - sseanliu（报告者）通过三次插桩分析逐步修正根因认知：初判零 token 生成，后经状态捕获（`num_computed=382 < num_prompt=670`、同时在 running 和 waiting 队列）确认为 **pipelining race**——请求在上一 chunk 仍在 prefill 时就已被重新入队，严格串行客户端难以复现，本地 audio+vision 路径可稳定触发。
  - ZireaelK 在 `main` 上 100% 复现，指出在 AsyncScheduler 下表现为 `request.num_output_placeholders >= 0` 处 `AssertionError`，根因是 `_update_request_as_session` 未将上一轮 in-flight 的 batch 标记为 stale。
- **当前状态**：修复 PR #52717 已提交——continuation 在 `RUNNING` 期间保留在 `streaming_queue`，stop 后转移到 `WAITING_FOR_STREAMING_REQ`，并拒绝双重 waiting 队列成员资格。

**2. Issue #52735 + 修复 PR #52771（3 条讨论）— OffloadingConnector 与 MTP/EAGLE 投机解码不兼容**

- **核心议题**：KV 块写入 CPU 内存但从不读回（`kv_offload_cpu_cache_usage_perc` 请求结束后归零），`max_tokens=1` 的 A→finish→A 流程可稳定复现。
- **参与者观点**：
  - Mahnoor-Zaffar 初步判断是 retention 机制问题，主动提出认领调查。
  - kamb-code 已先在处理（提醒"有人已经在查"），给出纯 CPU 的单元级复现，并发布三方缺陷链：①all-groups drafter 回退逻辑（共享权重 MTP 模型无 `is_eagle_group` 标注时，所有组被误判为 drafter 组导致整个 offload 层被清零）；②未加宽 volatile-tail 导致 sibling 组 chunk 粒度错位；③drafter 组 trailing chunk 的永久存储空洞。
  - greglechin（报告者）在 Intel Arc Pro B70 上验证修复：`CPU_to_GPU` 传输量从 0 变为 0.710s（对比冷缓存 load 时间 0.767s），证明完整 prefix 已从 CPU 层恢复。
- **争议点**：对 "drafter KV 一个 chunk 的陈旧只降低 speculative acceptance，而清零整个 offload 层是严格更差的权衡" 这一 trade-off 是否在所有拓扑成立，kamb-code 表示数据优于理论，欢迎进一步对拍。

**3. Issue #52833（2 条讨论）— GLM-5.2 MTP 零接受率**

- **核心议题**：`amd/GLM-5.2-MXFP4`（Quark 量化 + AITER MoE）在 MI355X 上启动正常但 MTP 草稿零接受（每一位置 0.000）。四种配置交叉验证后均无法达成有效接受。
- **参与者观点**：
  - tianxiaojiang4 主动撤回 SGLang 对比数据，承认那条线来自对方 `SGLANG_SIMULATE_ACC_LEN=2.99` 的模拟配置，不是真实测量——学术诚信值得肯定；真实测量值仅在 bf16 KV 时 pos0 有 0.046 接受率。
  - 关键未解问题：关闭 `--enable-expert-parallel` 后直接 `hipErrorIllegalAddress`——怀疑 EP 依赖的 MoE 后端（aiter）与 MTP 验证路径存在更深层冲突。
- **当前状态**：已 CC ROCm 维护者（hongxiayang/tjtanaa 等），尚无明确结论。

**4. PR #52696 — 稀疏索引器 FP16 logits（6 条讨论）**

- **核心议题**：WoosukKwon 提出将稀疏注意力索引器 logits 默认改为 FP16（CUDA），并支持显式 `float16/float32` 覆盖。统一内核寄存数从 57 降至 32，occupancy 从 49.7% 提升至 94.9%。
- **参与者观点**：
  - LopezCastroRoberto 指出此前的 BF16 尝试（#40811 已关闭）——DeepSeek-V4 QAT 过程本身将索引分数量化到 BF16（论文 99.7% recall），但由于未获得显著加速关闭了 PR。
  - WoosukKwon 回应：FP16 相比 BF16 精度更优（中位 recall 99.96%），且 logits 超过 FP16_MAX（65,536）的概率极低，认为 FP16 是更优选择，并邀请对方 review。
- **当前状态**：已合入测试模型（DeepSeek-V4 Flash 64-head MXFP4 索引器），pre-commit 失败已修复，CI 触发中。

### 🔥 热门话题与趋势分析

**1. 混合架构模型（GDN/KDA/MLA）是绝对主线**

围绕 Kimi-K3、GLM-5.2、MiniMax-M3、Qwen3.8 等混合注意力模型（线性注意力 + 全注意力 + MLA）的适配、性能与稳定性工作占据半壁江山。Kimi-K3 尤其密集：gfx942 路线图（#52803）、fused KDA decode 下放（#52293）、FlashInfer GEMM+AllReduce 融合（#52687，最高 1.54x）、Mamba prefix caching 内部 checkpoint（#52789，TTFT 最高改善 25.5%）、ngram spec-decode 内存错误（#52792）。

**2. 投机解码与 KV offload 的交互难题**

MTP/EAGLE/ngram/DSpark 多种投机解码方法与 OffloadingConnector/Mooncake 等 KV 传输系统的组合不断暴露边界问题：#52735（offload 命中率为零）、#52792（stride 切片）、#52832（producer partial tail 未持久化）、#52804（KIMI+RHAI Dspark cache page size 不匹配）。这反映多级缓存 + 投机验证在混合模型上的正确性仍需系统性加固。

**3. 在线量化和量化仿真正确性**

Quark 在线量化插件文档（#52736）、FSE 在线量化适配（#51695）、OCP MX 仿真 QDQ 绕过（#52704）表明 vLLM 正在向「量化方法可插拔化 + 仿真精度可验证」方向演进，且 AMD 团队在中间的角色非常关键。

**4. Rust 前端持续迭代**

ERNIE 4.5 parser（#52841）、多模态处理器缓存（#52685）、gRPC 预处理特征直传（#52722）、KV-connector telemetry 修复（#52755）、版本信息嵌入（#52593）、DP 大小归属精简（#52575）——Rust 前端已进入功能补全和细节打磨阶段。

**5. 新硬件支持**

SM121（DGX Spark/GB10）构建目标（#52708）、XPU int8 MoE 使能（#52712）、AMD Zen CPU CI（#52748）——多硬件平台覆盖仍是重要事项。

### 🛠️ 重点技术变更

**1. PR #51695（已合并）— FSE 优化选择标准化与抽象化**

将融合共享专家（fused shared-expert）检测从 qwen3/quark 特定逻辑提升为跨模型统一的解析器：基于任意量化配置验证 FSE 兼容性、拒绝不兼容的请求配置，并强制模型内所有 MoE 层状态一致（混合状态时报错 `NotImplementedError`）。这是后续在线量化接入 FSE 的基础设施级重构，同时在 MI350 与 H100 均通过 29 项测试。

**2. PR #52293（已合并）— gfx942 融合 KDA decode**

将 #50654 的融合 KDA decode 从 gfx950 扩展到 gfx942，构建与运行时双重门控同步放宽。由于内核仅依赖 wave64、DPP permute、bf16 等 CDNA 通用原语，无需源码修改。这是 Kimi-K3 在 MI325X 上提升 decode 效率的关键一步（尽管报告显示端到端收益目前受其他瓶颈限制）。

**3. PR #52112（已合并）— ROCm int4/int8 量化修复**

三个独立缺陷：①Triton MoE 后端缺失 asym 量化；②缺失 SWIGLU `UNINTERLEAVE` 激活重排；③错误的 `GROUP_SIZE==-1` 断言。合并后 MiniMax-M3-AWQ-INT4（TP4）与 Qwen3-235B-GPTQ-Int8（TP8）方可在 ROCm 上正确产出，补齐了 #44120 引入的回归。

**4. PR #52836（已合并）— 回滚 DeepSeek-V4 eager 工作区复用**

WoosukKwon 主动回滚 #49236 中的 model-wide `DeepseekV4EagerScratchPool`：模型级 scratch pool 绕过了缓存分配器的流/事件生命周期跟踪，可能让生产者在消费者仍使用时覆盖共享工作区。回滚恢复分配器的原有生命周期语义，直至安全的跨流同步机制实现。这是社区对「为性能牺牲隔离性」的一次方向修正。

**5. PR #52771（开放）— OffloadingConnector 在 MTP/EAGLE 下丢失全部 offload 命中**

三层缺陷叠加：all-groups drafter 回退（共享组 MTP 模型没有自标注导致整个 offload 被清零）、sibling 组 chunk 粒度错位、trailing chunk 永久存储空洞。报告者在 Intel Arc B70 上硬件确认修复，单元测试覆盖三条崩溃路径。

### 💡 值得关注的问题

1. **GLM-5.2 MTP 零接受率的根因归属**（#52833）：涉及 Quark 量化权重 + AITER MoE + MTP 验证的三角关系，且关掉 EP 直接报 `hipErrorIllegalAddress`，可能暴露 EP 与 spec-decode 的架构级冲突，而非单纯内核选择问题。这是 AMD 平台 spec-decode 可用性的关键拦路虎。

2. **流式输入 pipelining race 的修复走向**（#52693/#52717）：修复 PR 改动 scheduler 队列成员资格语义（引入 `WAITING_FOR_STREAMING_REQ` 状态），涉及面较广。AsyncScheduler 下同类问题以不同断言出现（#52693 中 ZireaelK 的发现），需确认修复对两代 scheduler 均有效。

3. **OffloadingConnector 的失败语义设计**（#52838）：AMD 员工 okorzh-amd 的 PR 将「传输故障即引擎崩溃」改为「故障降级为 cache miss」，揭示了 `requires_kv_delivery=False` 声明与 `transfer_async` 同步抛错之间的设计矛盾。此问题不仅影响 AMD，也是 KV offload 这类 best-effort 组件的通用架构议题。

4. **DeepSeek-V4 eager workspace 回滚的连锁效应**（#52836）：回滚恢复了分配器后备缓冲区，但 #51430 已将 Q/KV 插入等操作移入 CUDA Graph 捕获区域，该回滚在 V2 runner 上不影响 TTFT，但 V1 runner 的 eager 区域会重新引入分配开销——需要社区持续测量两代 runner 的性能差距。

5. **Mamba 混合模型 KV-scale 校准缺失**（#52793）：混合模型因 recurrent state 未初始化全面禁用 `--calculate-kv-scales`，导致 scale=1.0 的 fp8 KV 在 200k+ 长上下文中出现检索错误甚至 GPU worker 死亡。按层类型校准的意义已从「性能改进」上升为「正确性问题」，值得在长上下文评测中重点跟踪。
