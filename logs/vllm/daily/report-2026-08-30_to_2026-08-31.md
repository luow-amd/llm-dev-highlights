#### 🔴 新模型与架构支持

1. **[PR #54432] [ROCM] Enablement of Hy4-Preview on gfx950**（`jamesETsmith`，WIP）
   - 在 #54160 基础上为 AMD MI355X（gfx950）添加 Hy4-preview 的完整 AMD 实现：模型、MTP、注意力、iHC、MoE 和 ROCm 后端，新增 `vllm/models/hy_v4/amd/` 独立目录。
   - **关键技术点**：泛化了 ROCm Triton ragged sparse-attention kernel 以支持 Hy4 的 absorbed 512 latent + 64 RoPE 维度及 512-wide value 输出，同时保持 DeepSeek V4 行为不变；复用 ROCm/AITER sparse indexer 和 portable eager iHC 路径。
   - 当前限制：仅支持 unquantized FP16/BF16 KV cache，FP8 KV cache 作者明确暂不支持但在计划内。
   - 状态：WIP，存在 merge 冲突。

2. **[PR #54494] [ROCm][Kimi-K3][DCP] Enable MLA query replication**（`YukioZzz`）
   - 为 Kimi-K3 的 ROCm 路径启用 `dcp_q_replicate` 机制——将 query projection 按 DCP 组切分，每组 rank 只投影本组完整 head 集，跳过每层一次的 MLA 全量 all-gather collective，以冗余计算换取每层一个 collective 的消除。
   - 复用 DeepSeek-V2/V3 已有的 `DCPGroupColumnParallelLinear` 选择逻辑，通过新加的 `resolve_dcp_q_replicate()` 统一裁决规则（环境变量覆盖 `ParallelConfig.dcp_q_replicate`；要求 DCP 激活且 PCP 禁用）。
   - **PCP 排除是承重逻辑**：`DCPGroupColumnParallelLinear` 假定 DCP 组是连续 TP rank 段，PCP>1 时组变为跨步布局，会导致 replicated head 顺序与 `_local_view()` 不匹配。

3. **[PR #54466] [ROCm] Wire indexer_kv_dtype through on the MiniMax-M3 AMD path**（`wjabbour`）
   - 修复 ROCm 路径 MiniMax-M3 稀疏注意力忽略 `indexer_kv_dtype` 配置的问题（AMD 侧强制 bf16，而 NVIDIA SM100 路径可用 fp8）。直接后果是 AMD 路径 KV 字节数多 ~32%，并发瓶颈提前出现。
   - 已由作者关闭（非合并），但揭示的 AMD-vs-NVIDIA 吞吐差距值得追踪。

### 💬 高热度讨论分析

#### 1. Issue #53505 —— Hybrid Mamba + SpecDecode + KV Connector 损坏问题（7 条长评论）

- **核心议题**：Hybrid Mamba 模型（`mamba_cache_mode=align`）在投机解码开启且挂载 KV Connector（LMCacheMPConnector）时输出损坏（U+FFFD 垃圾、96k token 失控循环）。即使 connector 传输 0 token 也会触发，说明损坏路径在"connector 条件化 prefix-cache 协调逻辑"而非 KV 内容。
- **多方观点**：
  - **JiataiWang** 指出 #50344 已将 per-group divergent local hits 限定为 connector 显式声明 `supports_divergent_local_hybrid_hits` 才启用（LMCache 不声明，NIXL 才 opt-in），因此 **v0.27.1 tag 仍走 `get_computed_blocks_for_connector`**，但 main 上 LMCache connector 应与无 connector 同路径。
  - **uraniumchonk**（报告者）backport #50344 后验证 **损坏依旧**，排除了该嫌疑分支。
  - **ch2lab** 另辟蹊径，在 SM120 上定位到具体根因：`postprocess_mamba_fused_kernel` 的 **backward copy**——当 `new_num_computed` 恰好落在 `block_size` 边界时，postprocess 计算 `dest_block_idx < src_block_idx`，把刚 forward 迁移的 running state 又覆盖回旧状态，损坏 GDN/linear-attention 状态。
  - **kamb-code** 提醒混杂因素：#54165 分支已包含 #51865（has_prefill fence），如加载 MRV2 FULL graphs 则 #51865 的修复本身可能是独立候选。
- **结论**：uraniumchonk 在 0.28.0 + #54165 上 24 小时生产验证（8 并发 agent 会话、~500 请求、40M prompt token）零异常，LMCache 命中率 96.4%，确认修复。**注意**：这是长期追踪 issue 的闭环，本周期内关闭。

#### 2. Issue #54426 —— Qwen3.8-Flash-Next QSA 路径启用 fp8_e4m3 KV cache 的 RFC（2 条深水评论）

- **核心议题**：Qwen3.8-Flash-Next 的 QSA 路径拒绝非 bf16 KV dtype，但实际上大部分机制已就绪，只缺 QSA Triton kernel 的 **read 侧**。作者 Nanetnounou 提供了针对 `0.1.dev20073` 的工作补丁，单机（DGX Spark, GB10）测得 KV pool ×1.79、并发度 +79%、NIAH 5/5。
- **关键讨论**：
  - jschmied 在 **第二台 GB10** 上 corroborate：应用到相同 build（17 hunks 零失败），KV pool 比率 ×1.72（与单机 ×1.79 相差 <4%），并发度 4.11× → 7.07×。他发现绝对数字因 checkpoint 不同相差 38%（该机器 NVFP4 experts + FP8 dense + FP8 lm_head），**"比率可复现而总量不复现"** 是更令人信服的结果。
  - jschmied 随后 **撤回前一评论中的 decode 性能警告**：n=2 时 fp8 比 bf16 慢 5.6%，但 n=6 时均值反而 +2.6%（37.22 vs 36.28 tok/s），两臂范围高度重叠，**2 个样本/臂根本无法分辨 5% 差异**，之前不该下方向性结论。
- **当前状态**：open，等待更多机器 corroboration。作者强调"此 RFC 的价值在于四个非显而易见的集成点"。

#### 3. PR #53896 —— Qwen3.8-Flash-Next 模型支持合并（7 条评论，多用户实测反馈）

- **核心议题**：新模型支持合并前社区实测暴露多个配置组合不工作。
- **各方观点**：
  - **nichdiekuh**（SM120 2×RTX PRO 6000, NVFP4 checkpoint, `VLLM_PLE_CPU_OFFLOAD=1`）：权重加载成功，但 PLE offload worker 启动失败——`ngram_embedding` 作为 `VocabParallelEmbedding` 只有 `.weight`，没有 `.weight_scale`。
  - **peakcrosser7**（作者）：NVFP4 的 PLE-offload **暂不支持**，请用 BF16/FP8。
  - **OsakaTX**（2×DGX Spark）：`_get_ple_embedding_quant_method()` 仅识别 `Fp8Config`，但 RadixArk checkpoint 是 **hybrid 量化**（routed experts 为 ModelOpt NVFP4，PLE 表存为 FP8 shards），导致 gate 返回 None，加载失败。
  - **jhsmith409**（SM120 TP=1，`vllm/vllm-openai:qwen38-flash-next`）：**启动后静默挂起**——无异常、无日志、端口不监听、EngineCore 100% CPU、主机 RAM 不涨（~48GB PLE 表从未加载），且 `VLLM_PLE_OFFLOAD_READY_TIMEOUT` 不生效。
  - **vadiklyutiy** 呼吁作者明确列出"支持/不支持"配置矩阵；**gau-nernst** 回应称已在 GB300/GB200/H200/MI355X 上验证三个官方 checkpoint。
- **讽刺之处**：模型正式合并了，但 PLE offload 的配置兼容性问题在合并时仍未解决。

#### 4. PR #54364 —— 池化请求先截断再 padding 的前端 bug 修复（5 条评论，含维护者互动）

- **核心议题**：`_token_padding` 在 `_token_truncation` 之前运行，导致 `truncation_side="left"` 时截断保留下来的全是刚 pad 的 token，模型吃进的是纯 padding。
- **讨论过程**：
  - DarkLight1337 转达 claude 的审查意见，Hotragn 验证属实后追加修复了 `token_type_ids` 的 **平行副本逻辑**（`io_processor.py` 的 pad/truncate 顺序同样错误）。
  - Hotragn 对 CI 中一个 schemathesis 500 失败做了严谨的 "not this diff" 论证：`ChatCompletionRequest` 从不设置 padding，且失败原因是 generated body 中 `bad_words: ["\u0085"]`——U+0085 对 `str.lstrip()` 是空白，触发 `update_from_tokenizer` 的 `ValueError`，与本 PR 完全无关。
- **当前状态**：已合并。

#### 5. PR #52033 —— ROCm 双流解码重开（7 条评论）

- **核心议题**：双流 decode 在 Qwen3.5 + DP2EP 上出现 gsm8k 准确率劣化导致 revert 后重新提交。
- **关键脉络**：simondanielsson 从"无法复现"到"找到启发式"——**routed experts 是否量化输入** 是安全启用多流的分界。未量化时同一 tensor 被 hidden state 和 shared expert 输入共享，不同流里并发写读即竞态。当前方案不新增 envvar、hipgraph safe，DSv3/类 DSv3 量化模型获得重叠，Qwen3.5 自动回退单流。
- **当前状态**：已合并（本周期内），是 ROCm 性能优化的重要一步。


### 🔥 热门话题与趋势分析

**1. Qwen3.8-Flash-Next 成为当前绝对热点**
- 模型支持合并（#53896）、PLE offload 的多种配置组合问题、fp8 KV cache RFC（#54426）、QSA 索引器 prefill/decode 分离（#54513）、CPU offload 的 ragged PLE ID（#54431）——模型从内核到前端到量化的全链路都在快速迭代，但社区实测显示 **配置兼容性矩阵尚未完整**（NVFP4+offload、hybrid quant、TP=1 挂起）。

**2. 投机解码正确性与内存安全**
- Hybrid Mamba 损坏（#53505 闭环）、结构化输出 + 草稿 token 身份丢失的 fail-open 漏洞（#54437 + #54442）、EAGLE/MTP 在 M-RoPE 模型上 KV slot 错位（#54498）、CUDA graph 默认尺寸回归（#54418）。投机解码与 KV cache 管理、结构化约束、多模态位置编码的交互是当前 bug 高发区，也是社区最活跃的调试领域。

**3. 在线 RL / 权重热更新语义**
- RFC #54443 讨论 weight version metadata 的语义缺口——`/pause mode="keep"` 允许请求跨版本生成，但现有 `/weight_info` 和 draft #53199 各自只提供一个标量，无法表达 "v7 生成 [0,57)、v8 生成 [57,128)" 的 token 跨度真相。这是 RLHF 控制面走向成熟的标志性设计讨论。

**4. 前端协议层 bug 丛生**
- 本周期大量前端 bug 集中在 **token 截断/偏移量/掩码的一致性**：`prompt_token_offsets` 不随截断收缩（#54407）、`prompt_is_token_ids` 不随截断收缩（#54509）、pooling 先 padding 后截断（#54364）、chat-template content format 与工具解析器组合崩溃（#54486/#54491）、prefix-caching 导致确定性输出改变（#54490/#54487）。一是说明 OpenAI API 兼容面越来越宽、参数组合爆炸；二是说明**参数交互验证不足**。

**5. ROCm 注意力后端选择成为反复出现的主题**
- #54438/#54440 与 #45916/#52684 的讨论表明：ROCm 上的 attention 后端选择不再是简单的静态优先级问题，需要按 **实际生效的 kernel 路径** 来排名，而非声明式能力。RDNA 与 CDNA 的分化（head_size 128 vs 256、custom HIP vs Triton）让这个问题更复杂。

**6. AI 辅助贡献规范化**
- 多个 PR 显式声明 AI 协助（Claude、Codex、ZCode Agent），且 AGENTS.md 的 AI agent 自我评估要求被 bot 自动回复反复引用。同时出现 AI 辅助导致的 **归属失误**（#54435 与 #47988 重复）和 **不成熟 PR 被作者快速关闭**（#54456）——开源社区的 AI 协作规范仍在演化。


### 🛠️ 重点技术变更

**1. [PR #53896] Qwen3.8-Flash-Next 模型支持（已合并）**
- 完整支持 Qwen/Qwen3.8-Flash-Next 及其 FP8/NVFP4 变体，覆盖 GB300/GB200/H200/MI355X 和 TP2/TP4/TEP4 等配置；支持 MTP 投机解码、PLE CPU offload（BF16/FP8）。验证数据由 Inferact 提供并公开在 recipes.vllm.ai。
- **影响**：这是 vLLM 对齐最新 Qwen 旗舰模型的重要一步，但社区实测暴露的 PLE offload 组合缺口需要在后续 PR 快速补上。

**2. [PR #52033] ROCm 双流 decode 与 hipgraphs（已合并）**
- 在数据并行 + expert parallel（DP+EP）下启用双 CUDA 流并行执行 MoE 的不同部分，并通过"routed experts 输入是否量化"的启发式自动规避竞态条件（Qwen3.5 禁用 / DSv3 启用）。
- **影响**：对 ROCm 上 MoE 模型的 decode 吞吐是显著的架构级优化，且无新增环境变量、hipgraph-safe，是 AMD 团队在 ROCm 核心路径上的重要交付。

**3. [PR #54418] 投机解码 CUDA graph 默认尺寸内存安全修复（已合并）**
- 将 #50488 引入的超默认上限（H200 上 2176/6400 token）的 uniform-decode capture sizes 收回平台既有默认 ceiling（512/1024）内。特殊跨步尺寸若在 ceiling 内仍获得 FULL decode graph；超宽 batch 回退 eager，避免启动 OOM。
- **影响**：H200 上 nightly CI 的 FULL graph OOM 和 KV cache 被挤压到 0.94 GiB（需求 5.12 GiB）的回归被精准修复，且**保留** #50488 的动态 tier 推导和 safe off-stride 覆盖，未做全量 revert。

**4. [PR #49274] GroupCoordinator.isend_tensor_dict 非阻塞化（已合并，窗口期落定）**
- 修复两个缺陷：(1) 元数据通过同步 gloo send 发送，超过 eager threshold 时变成 rendezvous，virtual-pipeline 折返点可死锁；(2) 即弃调用者不保留 pickled buffer 导致 use-after-free。
- 修复方式：新增 `isend_object` + `_RetainedHandle` 自保留 FIFO，`send_tensor_dict` 语义保持不变。
- **性能影响**：PP2+TP2 在 16k in/1 out 场景 +47%，PP4 同场景 +65%；持续 prefill 和 prefill+decode 混合场景基本持平或 +3~5%。维护者 njhill 在 4×GB200 上复现了作者的结论。
- **意义**：这是 PP 可扩展性和虚拟流水线（vllm-ascend）的底层通信修复，对长 prompt prefill 场景有显著价值。

**5. [PR #54410] MXFP6 SM120 原生线性层后端（新增）**
- 在 CUDA SM120（Blackwell）上为 Quark/OCP MXFP6 权重的 dense 线性层增加原生 MMA 后端，替代软件模拟；无 API 变更，不支持的配置自动 fallback。逻辑 UE8M0 scale 转换为 SM120 MMA layout，非 128 倍数的 K 维补零。
- **影响**：这是 #52347 的 Dense 部分，标志着 vLLM 在下一代低精度格式（MXFP6）上的硬件原生路径开始落地；Fused MoE 的对应工作仍在后续。

### 💡 值得关注的问题

1. **Qwen3.8-Flash-Next 配置兼容性矩阵不完整**（PR #53896 相关）
   - NVFP4 + PLE CPU offload 不支持、hybrid-quant checkpoint 不触发 FP8 PLE path、TP=1 启动静默挂起（PLE 表从未加载）。新模型虽然合并，但这些社区实测路径的修复尚无对应 PR，建议作者补充明确的支持矩阵文档并加速跟进。

2. **结构化输出 + 投机解码的 fail-open 漏洞**（#54437 / #54442）
   - 草稿 token 身份丢失导致 grammar mask 退化为全允许（fail-open），请求可静默生成不符合 grammar 的输出。PR #54442 提供了 fail-closed 修复，但 hand-off 身份修复（root cause）仍未落地，PP 可并行 drafter 一旦落地该问题将立刻激活。

3. **M-RoPE 模型上 EAGLE/MTP KV slot 错位**（#54498）
   - V1 model runner 将 M-RoPE temporal 维当作绝对序列位置计算 KV slot，**任何含图的 prompt** 的投机解码都会读写错误 slot，接受长度下降。纯文本路径不受影响，因此容易被忽略，但多模态 + 投机解码是明确的热门组合。

4. **ROCm 注意力后端选择逻辑的"声明 vs 实际"错位**（#54438 / #54440）
   - 静态优先级按"声明的能力"排名，但 RDNA 上 custom HIP kernel 只在 head_size 128 实例化，导致 256 head_size 模型选到更慢的后端（decode 差距可达 10.74x）。#54440 的定向修复合理，但深层问题是 ROCm attention 后端的 **能力矩阵应该在 selector 内显式表达**，而非用优先级隐式表达。

5. **在线 RL 的 weight version 语义缺口**（#54443 RFC）
   - 请求可跨权重版本存活（`/pause keep` 是已发布功能），但现有元数据只给引擎当前版本或请求准入版本，无法描述 token 级生成归属。KV reuse 跨版本是另一个正确性问题（#48312）。这关系到在线 RL 数据新鲜度的可信度，需要社区尽早定案。

6. **FP8 KV cache 扩展到新模型架构**（#54426）
   - Qwen3.8-Flash-Next QSA 路径的 fp8 KV cache 补丁已具备初步实测证据（KV pool ×1.72-1.79，无 decode 回退），但尚未 PR 化、第二台机器 corroboration 也只有一例。该模型的 KV 容量瓶颈在统一内存设备上非常突出，值得持续关注。
