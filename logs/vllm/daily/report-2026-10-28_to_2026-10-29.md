### 🛠️ 重点技术变更

#### 1. [#64381] Packed KV planner：按"保留字节最少"选 block width（amd-dlimpus）

- **问题**：原规划器把 state bucket 封顶到最宽的 paged group，导致很多窄 group 各自按 request 保留 block，浪费内存。
- **方案**：在所有候选 block width 中选择"每个 max-length request 保留字节最少"的那个；当前 width 恒为候选，因此**不劣于**旧策略。
- **实测**：MI355X 上 DeepSeek-V4.1-Flash（stock FP8 KV）**+2.5% KV tokens**（eager 12.2M → 12.5M；graph 11.7M → 12.0M）；Qwen3.8-Flash-Next / DeepSeek-V4-Flash / MiniMax-M3.1-Flash 的 group 划分完全不变。
- **影响**：为 #64120（更小 KV 记录）从 **−9% 变为 +19% 容量**奠定基础。
- **验证**：`test_contiguous_kv_packing.py` + `test_kv_cache_planning.py` 92 passed（main 上 91），新增测试在 main 上失败。

#### 2. [#63179] ROCm：块状量化 + GEMM 融合（alexm-redhat，已合并）

- **两大优化**：
  - **tiny-M 融合**：M ≤ 8 时块状 GEMM 前原本要单独跑 `_mxfp8_quant_triton_kernel`，现在把量化融进 GEMM 的 K 循环、在寄存器内完成——**一次 launch 替代两次，激活值无往返**。
  - **lm_head skinny-GEMM 守护**：`wvSplitK_hf_sml` 对远超 L2 的权重（如 TP4 下 DSpark draft vocab-parallel lm_head 分片约 315 MiB）带宽崩塌；现按 `VLLM_SKINNY_GEMM_MAX_WEIGHT_BYTES`（默认取硬件 L3 大小，MI355X 256 MiB / MI300X 128 MiB，通过 amdsmi 读取）回退到 hipBLASLt。
- **精度**：融合路径与旧两段路径 **bit-exact**；额外加了 QDQ 高精度参考（rel err < 5e-3）。
- **实测**：DSV4.1-Flash TP4 on MI355X，ROCm-10 nightly，**中位 decode ITL −2.27%**（5.498 vs 5.625 ms），独立 per-run range 完全不重叠。
- **工程亮点**：kill switch 从 `VLLM_DEBUG_DISABLE_*` 改为运行时按硬件派生上限——避免每条 serving 路径一个 env var。

#### 3. [#64111] MiniMax-M3.1-Flash 新模型完整落地（zyongye，已合并）

- **NVIDIA 侧**：Blackwell SM100/SM103/SM107 上 NVFP4 routed experts + NVFP4 KV/index-K（MSA CUTLASS Q8KV4）；DSpark 投机解码；decoder 侧多个融合内核（QKV+indexer MXFP8 epilogue、SM100 fused dense GEMM1、persistent QK-norm/RoPE/KV-insert、小 batch MoE finalize 融入 all-reduce+Gemma norm、DeepGEMM NVFP4 MegaMoE）。
- **ROCm 侧**：gfx950 NVFP4 KV + NVFP4 indexer、FlyDSL per-layer mono decode、small-M MXFP8 linear tuning，gfx942 有 fallback。
- **验证**：`tests/kernels/attention -k minimax_m3` 219 passed / 64 skipped；模型相关 689 passed / 5 skipped / 3 failed（已定位）；自定义 all-reduce 57 passed。
- **意义**：这是本周期内**单 PR 体量最大、影响模型最多**的新模型落地，且 NVIDIA/ROCm 同步支持。

#### 4. [#64356] Batch-sharded draft logits 重构（TheEpicDolphin，已合并）

- **问题**：#63554 用"持久 slot"分配 rank，导致每个 rank 的本地负载取决于 slot allocator 的随机分布，且 shape 每步变化、无法 CUDA graph capture。
- **方案**：按 batch position `i` 分配 `rank = i % tp_size`、`row = i // tp_size`；用 `inverse_row_mapping` + Triton `stale_drafts` 内核无损处理"行被后续请求覆盖"的情况（仅当步 acceptance 下降，rejection sampler 走重采样）。
- **影响**：为 DSpark 后续"sharded sequential Markov block"的 CUDA graph 捕获铺路。
- **验证**：Buildkite CI 通过；作者注明失败测试已由 #64238 修复。

#### 5. [#64295] RFC：副本间共享 GPU KV cache（TianDi101）

- **核心洞见**：在 72-GPU rack 中，HBM 层 KV cache 目前对其它副本不可见，只有 offload 到 L2/L3 才能共享，导致同一 block 被重复存储在多卡 + L2/L3。
- **方案**：把 72 个私有 GPU KV cache 池化为"L1 共享池"（AMD Helios 72×MI455X ≈ 31 TB；NVIDIA NVL72 同量级），带来五点收益：有效容量放大、**负载均衡不再损失命中**、rack 内延迟优于 L2/L3、减轻重复写、HBM 作为主共享池。
- **意义**：这是**对 AMD rack-scale 架构（Helios + MI455X）非常具体的正面论述**，明确把 AMD 硬件列入 vLLM 未来 KV 架构的核心场景。

### 💡 值得关注的问题

#### 1. 🔴 **AMD 生态闭环的关键缺口**

- **#64275**：自适应验证的 profiling 循环在 KV cache 分配后仍不释放 allocator cache（累积至 ~25 GiB），在 4×MI355X + `--gpu-memory-utilization 0.95` 下确定性复现。**这不是 ROCm 专属问题**（Model Runner V2 代码平台无关），但恰好在 AMD 大显存配置上首次暴露。建议维护者在 profiling 循环里加入 `empty_cache()` / 分阶段释放。
- **#64322**：DSpark draft 路径的 **INT4 通信在 MI355X 上受限**，导致 InferenceX 的 DeepSeek-V4-Pro AgentX 配方无法完全认证。需要 DSpark 团队跟进。
- **#64373（GLM-5.3-Flash）**：MXFP8 在全 196 层量化 vs 只量化 128 层 non-KDA，**后者会缩短 reasoning**——这提示在线量化对推理模型的 reasoning 长度可能有系统性影响，值得在广泛模型上验证。

#### 2. 🟡 **KV 架构的长期方向**

- **#64401（大页 KV allocator）** vs **#64295（L1 共享）** vs **#64237（分布式 FS tier）**：三条 RFC 在**同一周**提出，分别管理"块大小规则"、"跨副本共享"、"FS 层统一配额"。三者如何共存/分层，是接下来 KV 子系统的核心设计决策。
- **#64381** 为 #64120 打开 +19% 容量的路径，但需注意 packed 路径的非 DeepSeek 模型（Qwen3.8-Flash-Next、MiniMax-M3.1-Flash）**group 划分完全不变**，即优化只对特定模型形状生效，建议扩大 benchmark 覆盖。

#### 3. 🟡 **MRV2 / DBO 的验证缺口**

- algebra-MCX 系列（#64351、#64353、#64382 等）全部标注"仅 CPU 单测通过"，**尚无任何端到端 GPU 模型正确性验证**。这类工作在合并前必须解决"如何获得 GPU 资源"的问题，否则容易在落 main 后出现分布式正确性回归。
- **#64293** 已给出 H200 上的部分 serving A/B（虽未建立 E2E speedup），是当前 MRV2 系列中验证最扎实的一条。

#### 4. 🟡 **跨平台一致性**

- **#64252（Intel XPU）** 修复的是 `attn_sink` 在 XPU DeepSeek-V4 sparse MLA 上被**静默忽略**（softmax 在 1 键场景误差达 105–118%）。这提示其他后端（尤其新加入的 CPU/XPU/ROCm）可能也有类似的"参数接受但不生效"问题，建议增加跨后端的 sink 一致性测试。
- **#64329（FlashInfer q_scale）**：BF16/FP16 查询仍被乘上 FP8 q_scale 导致输出错误——**#53754 已闲置 2 个月且只测 helper 未测 forward**，这是个典型的"看似已修实际未修"陷阱。

#### 5. 🟢 **安全 / 错误处理**

- **Issue #31683 衍生的 #46415**：FastAPI `ValidationException.__str__` 通过 `_format_endpoint_context()` 泄露**服务器绝对安装路径、行号、函数名**给所有客户端。虽然本 Issue 已 stale 关闭，但这条泄露路径至今仍需独立跟进。
