### 🎯 AMD/ROCm 生态相关动态

本周期 AMD 生态异常活跃，按主题可分为三块：**Quark 量化链路修复**、**ROCm 性能优化**、**ROCm 高级特性合入**。以下逐项分析。

#### 1. Quark 量化链路：多个命名/匹配缺陷集中暴露

这是本周期 AMD 生态最集中的问题域，共 4 个 Issue/PR 互相关联：

- **#54641（新 Issue）**：`packed_modules_mapping` 中的 identity 条目（如 `"gate_up_proj": ["gate_up_proj"]`）会静默禁用 `layer_quant_config`。QuarkConfig 的两个查找路径都将 `shard_name == layer_name` 视为"无分片信息"，导致混合精度 checkpoint 使用错误的量化方案，直到权重加载时才以 shape mismatch 失败。该模式在 GLM-4.1V、Plamo3、Molmo 等模型中是既有写法，影响面广。AMD 工程师 **liulanze** 已在 #54702 中携带修复并致谢报告者。
- **#54547（新 Issue）**：Quark MXFP4 checkpoint 对多模态模型完全不可加载，根源是 **exclude 列表使用 checkpoint 张量命名，而 vLLM 使用模块命名**；GLM-5.3-Flash 的 loader 做了 3 处前缀重写，导致 1550 条 exclude 条目无一匹配。还叠加了融合模块名（`gate_up_proj`）与 `packed_modules_mapping` 缺失、`is_layer_skipped` 收到 FusedMoE 整体而非分片名等共 4 个粒度错配问题。本质上反映了 Quark 的导出格式与 vLLM 的模块化加载架构之间缺乏统一命名契约。
- **#54573（新 PR，`fxmarty-amd`）**：修复 #51695 引入的回归——共享专家融合（FSE）兼容性检查对 Quark 产出模型的误判，导致 `amd/GLM-5.2-MXFP4` 的 FSE 被错误禁用。`fxmarty-amd` 代休假的 `xuebwang-amd` 提交以加快合入。评论中还发现 `projection_names` 参数为 `None` 时 `resolve_layer_fused_shared_expert` 路径会直接 `TypeError`，暴露了新老代码路径的覆盖差异。
- **#54556（新 PR）**：修复 Quark 量化的 GLM-5.3 MXFP4 checkpoint 中 FP8 block scale 以 `.weight_scale` 存储、而 vLLM 参数名为 `.weight_scale_inv` 的加载 `KeyError` 问题。

**影响分析**：Quark 是 AMD 主推的大模型量化工具，上述问题表明 AMD 与 vLLM 在 checkpoint 格式契约上仍处于"逐一打补丁"阶段。特别是 #54547 揭示的多模态命名空间问题，影响所有多模态架构，建议社区推动在 Quark 导出端与 vLLM 加载端建立统一的规范化层。

#### 2. ROCm 性能优化：MiniMax-M3 成为主战场

- **#54682（新 PR）+ #54681（已关闭 Issue）**：`Fangzhou-Ai` 优化 MiniMax-M3 在 gfx950 上的 decode indexer 与 top-k。核心是：按请求实际 block 数映射 score 计算、将 decode top-k 选择与稀疏页表构建融合、支持确定性排序与 CUDA-graph 重放。与 #52664（走 AITER）和 #54432（prefill/FP8）错位竞争，保留 vLLM 自有的 ROCm Triton BF16 路径。审查者 `liuzijing2014` 要求补充端到端 reasoning 精度评估。
- **#54535（新 PR，`weitliao`）**：在 #52664 之上保持 MiniMax-M3 ROCm 稀疏路径使用 AITER 融合 QK-norm，并支持 packed LBHNC SHUFFLE K/V 页跨度与 FP8 index cache 直通，gfx950 上 17 个测试通过。
- **#54594（新 PR，`andyluo7`）**：HY V4（MiniMax 系）在 gfx942/gfx950 上的图模式推理优化。基于能力进行 MXFP8 分派（无原生 MX 支持的设备将 checkpoint 权重一次性转为 AITER block FP8），支持原生 MTP k=3、共享专家融合与 AITER SiLU。
- **#54571（新 PR，`shen-shanshan`）**：为 DeepSeek-V4 在 ROCm 上启用 CSA 双流重叠（dual-stream overlap）。
- **#54706（新 PR，`AIwork4me`）**：修复 RDNA3（gfx11）W4A16 split-K 非确定性。根因是标量与 WMMA 路径用 CAS 原子以执行序累积窄化后的 bf16/fp16 部分和；修复为"FP32 per-split 部分和 → 固定升序 FP32 归约 → 最终一次 cast"，不改变 dispatch/kernel，且同等输入下精度反而提升（M=1 max abs error 从 0.028 降至 0.0061）。这是对消费级 RDNA3 采样稳定性的重要修复。
- **#54580（新 PR，`i-kosarev`）**：修正 ROCm AITER 组合测试的 `expert_map` 语义——AITER 内核需要 0/1 expert mask，而测试框架统一传了 index map，导致 4 个组合在 gfx950 上 GPU 内存访问错误。

#### 3. ROCm 高级特性合入：MLA DCP、前缀缓存、基础镜像

- **#51705（合并）**：ROCm AITER MLA 在 decode 上下文并行（DCP）下支持因果多 token 验证。实现逐 token 的 rank-local 因果 KV 窗口、物理 block 到 subpage 的展开、以 BF16 + 自然对数 LSE 完成跨 rank 合并。该 PR 经历数轮 rebase 与 `andyluo7` 的修复式协作后合入，是 ROCm 推测解码对齐 CUDA 能力的关键一步。
- **#53598（合并）**：Kimi-K3 在 DCP 下正确服务前缀缓存命中。将全注意力/MLA 缓存管理器按进程 DCP 大小构建，而 Mamba 等复制状态组保持 DCP size=1，并修正按组哈希对齐保留逻辑，修复混合前缀缓存命中。
- **#49925（合并）**：ROCm 容器切换到 TheRock 7.14 预览版本，同时保持 Python 3.12 与 Ubuntu 22.04。维护者 `njhill` 特别指出 TheRock 包含 ROCm 系统级修复，是 extensible KV cache 功能的前置条件。
- **#50622（合并）**：拆分 AITER CK 与 Triton MXFP4 W4A16 为独立后端（`AITER_MXFP4_BF16` / `AITER_TRITON_MXFP4_BF16`），使 gfx942 上 gpt-oss 能默认走 Triton a16w4 路径。社区用户在 DeepSeek-V4 上验证时额外发现：后端选择 hardcode 列表未包含新后端、round-up 逻辑对 DeepSeek-V4-Pro TP8 造成 33%/rank 显存膨胀、aiter 模块路径搬迁导致 import 兼容问题——这些反馈对后续完善很有价值。
- **#53155（合并）**：将 GLM-5.2 留在 Model Runner V1 并禁用默认 breakable CUDA graph，修正 #52861 在 ROCm 上的遗漏回归。
- **#54546（新 PR，`YukioZzz`）**：声明 Triton MLA 在 ROCm 上支持非因果多 token DCP；`okorzh-amd` 的 #54639 因被该 PR 覆盖而关闭。

**小结**：本周期 AMD/ROCm 生态呈现出明显的"多线并进"态势：Quark 侧在补命名契约的课，性能侧以 MiniMax-M3 为样板在 gfx950 上深耕，功能侧则通过 #51705、#53598 等合入使 ROCm 在 DCP/MLA/前缀缓存上与 CUDA 差距进一步缩小。AMD 员工（`fxmarty-amd`、`okorzh-amd`）与核心 ROCm 贡献者（`YukioZzz`、`andyluo7`、`Fangzhou-Ai`）形成了稳定协作网络。

### 💬 高热度讨论分析

#### 1. [#54521] Qwen3.8-Flash-Next 贪婪解码非确定性（10 条评论，本周期最热）

**核心议题**：`temperature=0` 的 5 个字节相同请求返回不同输出。报告者最初将其与 Qwen Sparse Attention（QSA）的 `indexer_budget` 阈值（超过后从密集注意力切换为 top-k 子集选择）关联。

**参与者与观点演变**：
- **bankjaneo（报告者）**：最初观察到仅在上下文超过 `indexer_budget` 时发散；随后自我纠正，发现触发条件是 **prompt 长度**而非总序列长度。
- **jschmied（独立复现）**：在 GB10/TP1 上复现，但发散从 582 token（远低于阈值）就出现，且关掉 MTP 仍然发散，直接否定了"阈值触发"假设。进一步定位：sm_121 上 `use_cooperative_topk` 永远为 False，所有请求都走 `persistent_topk`——一个已知存在数据相关错误返回值问题的 op。
- **jahnclawdmonet**：在另一对 DGX Spark 上复现，确认发散随配置的 budget 移动。
- **LopezCastroRoberto（NVIDIA 侧）**：要求测试 #53287 的 topk 版本。
- **bankjaneo 最终定位两个独立缺陷**：
  - **Bug A**：`persistent_topk` 返回的 index 集合正确但**顺序非确定**，QSA 对排列敏感；在 `expand_qsa_block_indices_cuda` 前对 blocks 排序可完全修复近边界区域（2039 token 从 10/10 发散变为 1/10）。
  - **Bug B**：在长上下文下，**集合本身**也会变化，且与 tie 密度（k-th threshold 附近的并列值密度）有关，而非行数。`qsa_mqa_paged` 与 `qsa_sparse_paged_attention` 均确定，唯一非确定环节就是 `persistent_topk`。

**争议焦点**：最初围绕 `indexer_budget` 阈值是否成立；后续转向内核层面——非确定性 tie-breaking 如何在 QSA 消费端放大为文本损坏。该 bug 对泰语等 token 密度高、相似标记多的语言影响尤为严重（声调符号丢失/重复/换位），HTTP 状态仍 200，属于静默错误。

**当前状态**：open。Bug A 可通过排序规避，Bug B 等待 #53287 验证。

#### 3. [#54526] Eagle3 模型加载失败（3 条评论）

**核心议题**：无法加载用 Speculators 训练的 Eagle3 drafter。

**关键定位（`he-yufeng`）**：这是配置键布局不匹配。Speculators 将 `eagle_aux_hidden_state_layer_ids` 写在 draft config **顶层**，而 vLLM 按顺序只读取 `num_aux_hidden_states` 键、嵌套的 `eagle_config.eagle_aux_hidden_state_layer_ids`、以及硬编码默认值 3。用户的 drafter 有 4 个 aux 层，vLLM 按 3 层建 fc，导致 4096×16384 与 4096×12288 的 shape 不匹配。修复 PR #54598 已附带覆盖全部 5 个解析分支的单元测试。

**观点**：`fynnsu` 提供绕行方案（直接用 speculative 模型路径加载，去掉 `speculative_config`），同时确认这确实是个 bug，并提到 #51338 正在做更全面的 CLI 解析更新。

**当前状态**：open，等待 #54598 合入。

### 🛠️ 重点技术变更

1. **[#51705] ROCm AITER MLA DCP 因果多 token 验证（合并）**
   这是 ROCm 推测解码的关键拼图。实现上不再复用单 token 的 Gluon/ASM 路径，而是为每个验证 token 计算全局因果边界到 rank-local KV 长度的映射，将物理 KV block 展开为分段 AITER MLA 所需的 bounded subpages，并以"BF16 输出 + 自然对数 LSE"支持跨 rank 归约。合并前经 `andyluo7` 的多轮修复式协作，最终在 MI355X 上完成 DCP8+DSpark+FP8 KV+GSM8K-200（81.5% EM）的完整验证。该 PR 使 ROCm 在 DCP 多 token 验证上与 CUDA 对齐。

2. **[#53896] Qwen3.8-Flash-Next 模型支持（合并）**
   这是当前最复杂的模型接入之一：Qwen4Exp 架构 + QSA 稀疏注意力 + PLE（ngram embedding）CPU offload + MTP 推测解码，覆盖 BF16/FP8/NVFP4 三种权重格式与 GB300/GB200/H200/MI355X 平台。合入后仍有遗留问题：NVFP4 PLE offload 未支持、SM120 上启动挂起、FP8 PLE 路径对混合量化 checkpoint 的探测条件过窄（#54521 与 #54559 即为运行期暴露的缺陷）。

3. **[#49445] 请求队列上限控制（合并）**
   为 vLLM 引入 `--max-num-queued-reqs` 与 `--max-num-queued-tokens` 两个准入控制旋钮，在 `AsyncLLM.add_request` 同步拒绝超限请求（HTTP 503），避免无界队列导致的不可控 TTFT 膨胀。讨论中与其他方案（#49330、#28458）形成互补：前者希望放在 engine-core，该 PR 坚持放在 IPC 链最前端，成本最低；#39492 将解决多 API server 之间的计数同步。

4. **[#54702 / #54641] Quark `layer_quant_config` identity 条目修复**
   修复了"模块映射到自身"时 QuarkConfig 两个查找路径把 identity 条目当作"无分片信息"从而跳过 per-layer 配置的问题。修复方式是从两个方法中提取公共的 `_match_layer_quant_config()`，identity 分支走真实验证，而真正融合的模块（`fused_qkv_a_proj` 等）语义保持不变。这一小修复关系到所有使用 identity packed mapping 的模型（GLM-4.1V、Plamo3、Molmo 等）能否正确加载混合精度 Quark checkpoint。

5. **[#54706] RDNA3 W4A16 split-K 非确定性修复**
   修复 gfx11 上 `RDNA3W4A16LinearKernel` 的采样级非确定性。根因是 K-split 部分和被窄化到 bf16/fp16 后通过 CAS 原子累加，最终值取决于 CAS 完成顺序。修复将 epilogue 改为"FP32 per-split partials → 固定升序 FP32 归约 → 一次最终 cast"，`k_split==1` 走原始直接 store。验证覆盖 100 次调用 1 distinct、16,640 次 GEMM 零事件，且在 M=1 时精度反而提升。这提醒我们：非确定性 bug 同样存在于消费级 ROCm 平台。

- **遗留回归**：SM120 上的稀疏 MLA decode 回归（`eidx must be contiguous`）仍未修复，依赖 #41834；Qwen3.8-Flash-Next 的 NVFP4 PLE offload 仍不可用。

### 💡 值得关注的问题

1. **`persistent_topk` 数据相关非确定性（#54521）**：不仅影响 Qwen3.8-Flash-Next，所有在 SM120/GB10 等使用该 op 的稀疏注意力模型都可能受影响。Bug B（tie 密度导致集合变化）截至目前仍无合入修复，建议有相关硬件和业务依赖的团队跟踪 #53287。
2. **vLLM main 的 SM120 稀疏 MLA decode 回归**：DSv4 在 SM120 上无法服务（与 FlashInfer 版本无关），需要 #41834（SM12x 支持）合入才能解决。SM120 设备用户短期内应锁定带修复的 fork 或版本。
3. **Quark 与 vLLM 的 checkpoint 命名契约（#54547、#54641、#54573、#54556）**：四个问题同源，都指向命名/匹配粒度不一致。建议 AMD Quark 团队与 vLLM 维护者共同定义一个标准化的"层名/张量名双视图"导出规范，而不是逐个模型打补丁。
4. **GDN "all" cache mode 去留（#54637）**：维护者表示考虑移除，但 #54637 和 #54612 都在该模式上投入大量工程。在维护者明确方向前，外部贡献者应谨慎在该模式上叠加新功能，避免返工。
5. **Eagle3/Speculators 配置兼容性（#54526）**：第三方训练工具产出的 config 布局与 vLLM 的读取顺序不一致，且默认值会掩盖错误（静默按 3 层而不是 4 层建 fc）。建议 vLLM 在 config 解析时对"使用默认层数"给出 warning，并推动 Speculators 侧对齐。
6. **#54627 与 #54145 的调度特性组合**：两个 PR 分别控制 prefill 的"节流节奏"和"小 prefill 延迟释放"，看起来方向互补。若均合入，需要明确定义组合时的优先级和交互语义——F21HGG 已在评论中提出这一点，值得维护者提前设计。
