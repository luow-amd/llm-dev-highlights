### 🛠️ 重点技术变更

#### 1. PR #50597（已合并） - SiTU 去特殊化
**影响指数：★★★★★**

将 `Mxfp4MoEMethod` 中的三个 Kimi-K3 SiTU 特殊分支（后端选择、size round-up 旁路、独立 weight shuffle）全部删除，改为基于 `MoEActivation.SITU` 激活类型路由。这意味着 ROCm gfx950 上 MXFP4 权重的 SiTU 支持从"单一模型绑定"进化为"通用能力"，显著降低后续 MoE 模型的适配成本。

#### 2. PR #52402（Draft） - gfx942 原生 FP8 MFMA
**影响指数：★★★★☆**

通过位转换（bitcast）将 OCP `e4m3fn` 转为 `e4m3fnuz`，绕过软件 fp8→fp16 展开，直接使用 gfx942 原生 fp8 MFMA 指令。这一技巧利用了两种格式位布局几乎一致的特点，仅需预处理 `0x80` 字节，配合 LDS 占用率修正（1 字节而非 2 字节），使默认配置的 kernel 不再被错误拒绝。7.85× 的内核级加速和 4.05% 的端到端提升充分展示了原生指令路径的威力。

#### 3. PR #52363（开放） - 手动 CUDA RoPE KV-cache 融合
**影响指数：★★★★☆**

Llama 模型上首次实现模型可见的 RoPE+KV-cache 融合调用点。与 #43355（pass 级方案）不同，此 PR 采用 caller-owned Q 和 cache-only K/V 数据流，分离 RoPE 与 cache 的 token 域，支持 NHD/HND stride。ROCm 保留现有 `RopeKVCacheFusionPass`，CUDA 端取消该 pass 注册。这是手动融合迁移（#43224）的关键一步。

#### 4. PR #43107（已合并） - CI GPU↔CPU 同步检测
**影响指数：★★★★☆**

新增 `VLLM_GPU_SYNC_CHECK` 环境变量，通过 `torch.cuda.set_sync_debug_mode` 在模型前向和采样器执行期间检测 GPU-CPU 同步。异步调度已成为 vLLM 默认路径，主 CUDA stream 上的任何意外同步都会损害性能。此工具使此类回归在 CI 中被自动捕获，是性能守护基建的重要补充。

#### 5. Issue #52247 - EngineCore 无超时卡死
**影响指数：★★★☆☆**

当 GPU 内核永不终止时，`AsyncModelRunnerOutput.get_output()` 中的 `copy_event.synchronize()` **无超时、无诊断、无恢复**。引擎进程存活、`/health` 返回 200、SIGTERM 被忽略，且在 `step_with_batch_queue` 中阻塞点后的 `_process_aborts_queue()` 永远无法执行，取消请求无法排出。社区提出的修复方案（将事件等待纳入 `VLLM_ENGINE_ITERATION_TIMEOUT_S` 预算，使用 `event.query()` + 有界 sleep）方向正确，但需等待官方实现。

### 💡 值得关注的问题

1. **EngineCore 超时机制的缺失（#52247）**：GPU 内核永不终止时的无限制阻塞是生产环境的定时炸弹。需关注 `VLLM_ENGINE_ITERATION_TIMEOUT_S` 能否扩展至 CUDA event 等待，以及超时后的恢复策略（提出者明确不尝试进程内 GPU 恢复）。

2. **FlashInfer 自动调参的多节点死锁（#52291）**：在无 GPUDirect RDMA 的集群（GB10/DGX Spark）上 100% 复现，涉及 5 个版本组合。社区建议在同步路径上附加 autotune session/round ID，使调度分歧显式失败而非无限等待。此问题直接影响中小型集群的可用性。

3. **DeepSeek-V4 编码器的空 `<think>` 块（#52253）**：虽然 #52254 已提交修复，但此问题揭示出一个更深的验证盲区——官方 golden fixtures 无 "tools present + reasoning absent" 组合的覆盖。建议上游补充该测试向量。

4. **ROCm BF16 MLA 在 gfx950 上的 JIT 失败（#52312）**：AITER FA（Opus）的 BF16 路径参数类型不匹配。非默认 MLA 后端（TRITON_MLA）用户会直接暴露在此问题下，需要 AMD 侧修复 OPUS FMHA 的 JIT 签名兼容性。

5. **Muse Glimmer 镜像供应链治理（#51655 评论）**：从 fork 构建 Docker 镜像并发布的流程值得审视。社区的质疑虽未阻止合并，但镜像构建可追溯性需要明确策略。

6. **SM12x（GB10/RTX 50）的 DeepSeek-V4 支持碎片化**：`o_proj` 的 DeepGEMM 路径在 SM12x 上因 layout 判定错误失败（#52357），MoE 又因 `layout.hpp:97` 无法启用。多个 PR 正在并行修补，但社区需要一条清晰的"消费级 Blackwell 支持"路线图。

7. **AMD CI 中的 EngineCore 关闭竞态（#52281）**：`shutdown_timeout=0` 导致引擎核心在释放 ROCm 资源前被 SIGKILL，GPU 内存 120 秒无法回收。此修复虽为 ROCm 限定，但该模式对多架构的 shutdown 语义设计有参考价值。
