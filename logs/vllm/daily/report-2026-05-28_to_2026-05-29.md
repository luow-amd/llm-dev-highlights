## 💬 高热度讨论分析

### 1. Issue #43941 – 多模态缓存回收导致 EngineCore 无限循环
**核心议题**：特定请求序列（先超长上下文导致 400，再发送相同图片）触发 `EngineCore` 在多模态缓存回收时进入无限循环，服务完全挂起。

**观点碰撞**：
- 报告者 @Afanmin 详细分析了双缓存架构（预处理阶段和推理阶段各维护一个 mm-cache）之间的不同步。第一阶段拒绝请求后，预处理缓存保留了图片条目，但推理阶段因请求未进入推理流程而未缓存。后续请求命中预处理缓存但推理缓存丢失，引发异常，随后的回收机制因所有条目被“固定”无法驱逐而陷入死循环。
- 报告者提出了一个补丁思路：在 `popitem` 中增加 `if lru_key in self.order` 检查，防止无限循环。
- 其他参与者未直接参与，但该问题揭示了 vLLM 多模态缓存设计的脆弱性。

**当前状态**：Open，提交者已给出简化修复方向，但可能需要更系统的双缓存同步设计。

### 3. Issue #40340 – MoRI 连接器高并发挂起（已合并·修复 PR #40344）
**核心议题**：1P1D 部署 DeepSeek-R1 (TP8 EP8 on 2xMI300X)，当并发 >= 128 时 MorIIO 连接器无限挂起。

**讨论焦点**：
- 报告者 @simondanielsson 指出多个根因：ADMA `ring_tail` 指针溢出导致卡死；`notify_cq()` 繁忙等待阻塞 worker 循环；WRITE 模式下 KV block 提前回收导致死锁等。
- @tjtanaa 要求移除调度器（scheduler）中的改动，改用现有 `update_connector_output` 钩子实现。
- @chaeminlim-mb（MangoBoost 团队）确认此 PR 也修复了他们团队在 TP=16 对称 1P1D 上遇到的相同断言失败，并验证了 512 并发通过。

**当前状态**：Merged #40344（已于 5/28 合并）。

---

### 4. PR #43270 – NUMA 绑定改进：自动 PCT 核心选择 + EngineCore 跨节点扩展（已合并）
**核心议题**：改进 `--numa-bind` 行为，让 EngineCore 支持多 NUMA 节点，并在 DGX B300 上自动绑定至 PCT 优先级核心。

**讨论焦点**：
- @vadiklyutiy 发现 DGX B300 (Xeon 6776P) 上 PCT 核心频率约 4.6 GHz vs 普通核心 2.3 GHz，但内核不暴露 PCT 成员关系，需手动推断。当前实现基于型号和 ACPI CPPC `highest_perf` 值判断。
- @Harry-Chen 建议使用 `intel-speed-select` 工具检测，但 @vadiklyutiy 指出该工具默认未安装且需 root，因此坚持静态白名单方式，同时提议创建跟踪 issue 以将来通用化。
- 最终方案：PCT 检测通过 CPU model name 匹配 6776P/6962P/6774P 并读取 `highest_perf`，同时将 EngineCore 的 cpus_allowed 扩展至整个 DP shard 涉及的 NUMA 节点，避免 worker 绑定到其他节点时因 `cpus_allowed` 限制而失败。

**当前状态**：Merged #43270。

---

### 5. PR #43864 – 修复 Ray DP 后端端口分配问题（已合并）
**核心议题**：PR #42585 引入的延迟端口分配（`tcp://host:0` 占位符 + 事后收集实际地址）对 Ray DP 不起作用，因为 Ray 在 `.remote()` 时序列化 `addresses`，而其后进行的重绑定无法传播到 actor 进程，导致 actor 连接端口 0 永久挂起。

**讨论**：
- 提交者 @vadiklyutiy 在描述中承认未对 Ray 后端进行门控。
- 测试者 @danisereb 在 TP1DP8 (GB200) 和 TP1DP16 (4xGB200) 上验证修复有效。
- 修复简单：在 `run_multi_api_server` 中判断 `data_parallel_backend != "ray"` 时才走新路径，Ray 仍使用原来的 `get_open_port()` 方式（存在 TOCTOU 竞争）。

**当前状态**：Merged #43864。

## 🛠️ 重点技术变更

1. **PR #43679 – Tilelang MHC on ROCm**（合并）
   这是 vLLM 首次在 AMD 端使用 Tilelang 替代手动编写的 Triton 内核。Tilelang 提供跨后端编译能力，允许同一内核源码编译到 CUDA 和 ROCm，大幅降低维护成本。DSv4 的 MHC（Multi-Head Cache）部分启用后，需要验证 MTP 接受率保持正常。此 PR 标志着 vLLM 通用内核策略的重要转折。

2. **PR #43331 – 默认启用 aiter top-k/top-p 采样器**（合并）
   此前因精度问题硬编码禁用，修复后重新启用。性能收益显著（中位 ITL 降低 14%，吞吐提升 14%）。此举减少了 ROCm 路径上对原生采样器的依赖，为后续统一采样器提升奠定基础。

3. **PR #43270 – NUMA 绑定改进**（合并）
   解决多 GPU 跨 NUMA 节点部署时 EngineCore 绑定范围过窄导致 worker 启动失败的问题，并自动利用 Intel PCT 优先级核心。这对 DGX B300 等新硬件的性能至关重要。

4. **PR #40687 – wvSplitK N=5 支持**（合并）
   为投机解码的验证阶段（batch=5）启用快速 HIP 内核，避免回退至 hipBLAS，解码吞吐提升 14.2%。对 Eagle3 和 MTP 的用户直接影响较大。

5. **Issue #43941 – 多模态缓存无限循环**（Open）
   暴露了 vLLM 多模态缓存双缓存架构的同步缺陷。修复需要同时考虑缓存条目生命期管理和回收算法的健壮性，具有较高系统设计价值。
