### 🛠️ 重点技术变更

#### 1. `rocm_block32_gemm.py` — gfx950 原生 MXFP8 32×32 block scale GEMM（#58510）

**技术要点**：
- 直接消费 checkpoint 存储的 `[N/32, K/32]` E8M0 block scale，不再由 ModelOpt loader 展开为 per-row scale。
- 两条 kernel：大 M 用 tiled，小 M 用 packed（将 K panel 打包进 MFMA 行、保留 block-diagonal 乘积，使少量 token 也能以全宽流式加载权重）。
- **单 XCD 内 in-launch split-K**：tile 的多个 split 在同一 XCD 的 L2 中汇合，正常情况最后一次 program 在同 launch 内完成规约，不引入第二次 launch；只有 graph capture 首次 launch 时无计数器，才走独立的 reduce launch。
- N/K 为 `constexpr`，M 为 runtime（`do_not_specialize`），避免服务端按 batch size 反复编译。
- tile/split-K/MFMA 形状/occupancy 来自 MI355X 上针对 V4.1-Flash 十个投影 tuning 的表。

**影响**：声称中位数 **1.49× 加速**，TPOT -4.8%。同时被 #58659 补充 AITER 归属声明，是本周 AMD 侧最重量级的一次合并。

#### 2. ROCm sparse decode reduce 直接输出 MXFP8（#58456）

**技术要点**：`_sparse_attn_decode_reduce_kernel` 在逆 RoPE 之后直接在寄存器内做 MXFP8 量化（每 32 lane 一个 E8M0 scale），存量 e4m3 + scale；`wo_a` 改用 `tl.dot_scaled` 的 grouped MXFP8 GEMM 读取 checkpoint 原始 MXFP8 权重，不再构建 bf16 copy（每层约 33.5 MB @ TP2）。prefill 走 `rocm_inverse_rope_mxfp8_rows` 将 bf16 输出一次旋转+量化到同一 MXFP8 工作区。

**影响**：完整打通 `sparse partial → reduce + inv RoPE + MXFP8 quant → grouped MXFP8 GEMM → wo_b` 这条与 SM100 一致的数据流，是 AMD DeepSeek-V4.1 路径向 NVIDIA 路径对齐的关键一步。

#### 3. PLE n-gram table CPU offload 在 ROCm 落地（#57497）

**技术要点**：Qwen4Exp PLE n-gram 表在 pinned host memory 中，通过 UVA 视图在 GPU 侧读取；使用自定义 op `qwen4_exp_amd_ple_ngram_embedding_pinned`（`mutates_args=["output"]`）避免 Inductor autotuning 时物化 bf16 副本导致 OOM。同时把 PLE 存储类搬到 `qwen4_exp/common` 供 NVIDIA/AMD 共用；启用 gate 放宽为 `is_cuda_alike()`，ROCm 默认开启。

**影响**：FP8 表约 51 GiB 的 `Qwen3.8-Flash-Next-FP8` 可在单 MI300X 上服务（表完全驻留 host RAM），现场部署（8× Radeon AI PRO R9700 TP8）也已报告验证。作者的 AIME/GSM8K/guidellm 全套 eval 显示"offload ON vs OFF 结果 bit-identical（max diff 0.0）"。

#### 4. Mamba Kernel CI 拆分（#58592）

**技术要点**：将单一 `(H200 MIG 35GB) Mamba Kernels` 拆为四个内容命名的 job（SSD Single Example、SSD Continuous Batch、Ops、GDN），MI250 镜像同步拆分。每个文件/文件夹作为完整单元运行，避免 case-level sharding 重复支付 per-process setup。

**影响**：三次迭代的公开验证过程（build 90995 / 91011 / 91028 / 91048）表明设计从失败到收敛的完整路径；最终两 lane 全部通过，成本开销 +5.5（base）/ +3.8（mirror）worker-minutes，符合预算。这是一份优秀的 CI 优化工程记录。

#### 5. Parallelize Triton warmup（#58582）

**技术要点**：在 `VllmTritonJitKernel.compile_many` 中用 `AsyncCompileMode` + 最多 4 个编译线程并行 warmup。**ROCm 保持串行**——AMD CI build 90984 在 MI300/MI355 并发代码生成时触发 LLVM `GCNRegPressure.cpp` 断言。

**影响**：既是一次 CUDA 侧启动时间优化，也为 AMD 侧并发编译限制留下了明确的复现记录和后续修复线索（triton-lang/triton#11567）。

### 💡 值得关注的问题

1. **v0.30.0 ROCm 镜像缺补丁（#58575）** — GLM-5.3 在官方镜像上完全无法启动，属于发布回补缺口，建议优先排查 0.30.0 → 0.31.0 之间的 cherry-pick 流程。
2. **gfx1201（RDNA4）性能回退（#58639）** — V2 runner 的 PP 侧流与 async output copy stream 在 RDNA4 上触发约 17 µs/dispatch 惩罚，影响 PP 场景下的解码吞吐（可降至 1/2）。目前仅有 issue，无 PR；需评估是否引入 stream 复用或队列配置的官方机制。
3. **ROCm 自动 attention backend 选择（#46596 悬而未决）** — 即便开启 AITER，auto-selection 仍偏向 `ROCM_ATTN` 而非 `ROCM_AITER_UNIFIED_ATTN`，导致"最优路径需手动指定"，直接影响用户开箱体验。
4. **AMD CI 并发编译限制** — LLVM `GCNRegPressure.cpp` 断言阻断了 warmup 并行化在 ROCm 上的应用，这是上游 AMD 编译器问题，需跟踪 triton-lang/triton#11567。
5. **社区关于 AITER 归属的流程性反思** — #58510/#58659 事件应促成一条明确规则：即使 PR 描述被 AI 精简，来源同仓库/上游的代码片段必须保留 SPDX/许可声明，不能依赖 PR 描述承载法律信息。
6. **量化后端选择时机重构** — MXFP8 系列正在把 kernel 选择从 `__init__` 迁到 `create_weights`（#54223），涉及压缩张量、INC、online 三个 scheme，是潜在回归风险点，值得持续监控。
7. **KV Connector 家族快速扩张** — Mooncake (#58520)、MoRIIO (#58585)、UMBP (#58568)、NIXL (#58642) 并行推进，接口与语义复杂度上升，可能需要在架构层面统一抽象。
8. **DeepSeek-V4.1 Flash DSML tag 前导空格（#58640）** — 由于当前 vLLM 复用 V4 parser 处理 V4.1 Flash 输出，新增的 DSML tag 前导空格会破坏状态机匹配与参数正则，导致 tool call 参数无法流式返回；建议关注专门的 V4.1 parser 分支（已有 willweimike 着手）。
