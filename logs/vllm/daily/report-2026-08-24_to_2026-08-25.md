### 💬 高热度讨论分析

#### 1. #53505 — Hybrid Mamba (align) 在推测解码 + KV connector 下产生不可控输出损坏

> 争议层级：**技术根因定位**　·　状态：**Open**

**核心议题**：Hybrid Mamba 模型（mamba-cache-mode align）在启用推测解码并挂接任何 KV connector 时（即使传输零 token）会产生输出损坏（数值垃圾、96k token 失控生成），且与 connector 传输的内容无关，而是 connector 改变了 prefix-cache 的调度路径。

**关键观点**：
- **JiataiWang（vLLM 维护者）**：指出 #50344（commit d6941300）已经把"per-group divergent local hits"限制在 connector 显式宣告 `supports_divergent_local_hybrid_hits` 时才启用。LMCacheMPConnector 默认不宣告，因此 main 分支上 LMCache connector 应走与无 connector 相同的 fixed-point 路径。#50344 虽先于 v0.27.1 发布，但该 commit 不是 v0.27.1 的祖先——用户使用的 v0.27.1 标签仍会触发有问题的分支。
- **uraniumchonk（Issue 报告者）**：将 #50344 backport 到 0.27.1 后**复现依旧**（约 40 分钟后出现字节级垃圾输出）。作者认为腐蚀跟随 "connector-conditional prefix-cache path" 而非 KV 内容，且其实验矩阵证明关闭 spec decode 或拔掉 connector 即可消除问题。

**争议焦点**：即使修复了已知分支选择问题，问题仍然存在——说明 `get_computed_blocks_for_connector` 与 mamba recurrent state 恢复不一致的假设可能不完整，或存在第二个未发现的相关 bug。目前双方在等待更精确的定位补丁。

#### 2. #52023 — draft_model 推测解码在 draft hidden_size > target 且 TP>1 时启动崩溃

> 争议层级：**诊断-修复闭环**　·　状态：**Closed**（由 #52193 修复）

**核心议题**：TRT-LLM 融合 allreduce+RMSNorm workspace 的 `hidden_dim` 仅按 target 模型的 hidden_size 分配；当 draft 模型 hidden_size 更大时（如 Qwen3-4B draft_hidden=2560 vs Qwen3-30B-A3B target_hidden=2048），TP>1 下 workspace 溢出并抛 `check_trtllm_allreduce_fusion_workspace_metadata` 崩溃。

**关键讨论过程**：
- **seongyun1104（报告者）** 提供 A/B/C 隔离矩阵：同一模型对在 TP=1 正常（接受率 83.8%）、TP=2 崩溃、调换为 smaller draft 后正常，直接锚定 workspace 尺寸问题。
- **khushali9（修复者）** 在无法访问 GPU 的情况下推送 DIAG 补丁，要求 seongyun1104 在 2×H100 NVL 上运行——DIAG 输出精确定位 workspace 在 **`AllReduceFusionPass.__init__`（编译期 eager 创建）** 而非运行时 forward，且穿过了 `get_fi_ar_workspace()` 单例链。
- **Yusufchy（第三方评论者）** 指出 khushali9 最初关联的 #50877/#50932 是 MNNVL 路径（Lamport buffer），与本案的 trtllm 路径是**两个后端**，不应混淆——这一提示避免了修复方向的偏移。
- **khushali9 的结论**：采用 `max(target_hidden, draft_hidden)` 在 init 创建时统一尺寸，并增加 `draft_model_config is None` 守卫；同时明确"不做运行时重建"以避免 CUDA graph 捕获后旧指针悬空。

**最终结论**：修复合入 #52193。该 Issue 是"用户提供高质量复现矩阵 + 维护者设计诊断补丁 + 第三方帮助隔离后端"的优秀协作案例。

### 🛠️ 重点技术变更

#### 1. [Model Runner V2] batch-sharded sampling（#50465，merged）
将 target logits 的物化内存从 `O(batch × (spec+1) × vocab)` 降为 `O(batch × (spec+1) × vocab / P)`（P=tensor parallel size）。核心是 `compute_logits_local` 计算 vocab 切片，配合 batch 维度的 all-to-all 而非 logits 的 all-gather，同时将 sampler 在 TP ranks 上并行化。**意义**：降低 prefill/decode 峰值内存，尤其为后续 draft logits 分片铺路。

#### 2. CUDA graph 内存预留：#53306（merged）→ #53581（fix）→ #53644（revert 提议）
#53306 在启动期为 MRV2 分析 CUDA graph 内存使用并将其纳入 KV cache 自动容量规划（对齐 MRV1 行为），是 MRV2 默认化的重要前置。合并后立刻暴露 Kimi K3 的 KDA 实现直接索引缺失的 per-layer metadata 导致 `KeyError`；#53581 用与通用 GDN 路径一致的 missing-entry guard 修复。但 **#53644 随即提出整体回滚 #53306**——暗示该 profiling 机制对部分模型的内存扰动校验仍未充分信任。

#### 3. [Model] 移除 10 个废弃模型架构（#53608，merged）
完整删除 Arctic、Chameleon、Cheers、fairseq2-Llama、FireRedLID、GritLM、HCXVision、MPT 的实现/文档/测试/示例，同时移除 `RWForCausalLM`（→Falcon）等 3 个别名。所有受影响 checkpoint 将获得"v0.28.0 起不再支持"的明确报错。累计模型面上游清理净减 5500+ 行。

#### 4. MNNVL Lamport mailbox 修复（#53000，merged）
确认 CUDA multicast 地址必须用 `multimem.*`（PTX ISA）写入；mailbox 载荷即就绪信号，volatile 读 + 重试机制下无须 release/acquire 与 `fence.proxy.alias`。三缓冲清理从 `(epoch+1)%3` 改为 `(epoch+2)%3`，彻底避免快 rank 发布的 N+1 阶段被慢 rank 误擦除。这是 GB300 双机 TP8/EP 场景下 DeepSeek-V4 输出正确性的关键修复。

#### 5. [ROCm][Perf] SWA 融合 RMSNorm + FP8 量化（#53540，open）
ROCm 专属优化。通过单内核完成 q/kv RMSNorm（fp32 累加）与 q latent 的 per-1x128 FP8 量化，消除 bf16 中间写读与重复量化，使 attention 与 indexer 共享预量化结果。**2.90x 的内核级加速是 ROCm AITER 生态成熟度的积极信号**，但其 TTFT 退化提示融合内核的调度时序仍待调优。

### 💡 值得关注的问题

1. **#53644 Revert #53306 的走向**——MRV2 的 CUDA graph 内存分析被回滚意味着 MRV2 默认化进程将推迟，但 batch-sharded sampling（#50465）的合入又说明 MRV2 仍在加速进化。两者的冲突如何调和值得关注。
2. **#53505 Hybrid Mamba 腐蚀问题**——即便应用了 #50344 修复，问题仍复现。这暗示 SpecDecode + connector + hybrid cache 三者之间存在未记录的交互缺陷，建议社区优先补齐 connector 分支的集成测试矩阵。
3. **#53629 MoE 权重变换在磁盘流式加载时应用**（RFC，open）——将量化/权重变换从"加载后处理"前移到"流式读取时"，可显著减少峰值内存与启动时间，但会挑战现有的 checkpoint 校验与容错逻辑，值得跟踪。
4. **#53600 SM120 稀疏 MLA warmup 缺失**——DeepSeek-V4-Flash 在 RTX PRO 5000 上长序列 decode 落回 `tactic=-1`，反映出 FlashInfer autotune 覆盖与动态 topk 宽度计算之间的脱节。#53605 已提交修复，但需要确认更宽的 `extra_topk` 维度（如 mixed batch 场景）是否也被覆盖。
5. **#53563 SM90 DSA 与 LiteTopK 的设计重叠**——这可能会影响后续稀疏注意力索引器的技术路线选择。建议维护者尽快介入，明确是独立实现还是合并到 LiteTopK。
6. **#53595 `prefix_cache_retention_interval` 默认 0 且不记录日志**——align 模式下 prefix cache 静默只保留语义 checkpoint，用户可能无感知丢失缓存收益。该问题涉及 KV cache manager 的可观测性，建议在文档与启动日志中显式暴露。
