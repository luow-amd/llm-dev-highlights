### 📊 每日开发状态摘要

本周期 vLLM 共产生 **133 个新 PR、57 个合并 PR、38 个新 Issue、27 个关闭 Issue**，开发节奏保持高位。核心进展集中在 **AMD/ROCm 平台的性能与工程化**：ROCm 10.1 工具链升级落地、多个 libtorch stable ABI 迁移、ShardQ 并行在 ROCm 上的模型覆盖扩展，以及 gfx950/MI355X 上的 MoE 重叠与注意力内核优化。同时，前端安全（`chat_template_kwargs` 覆盖）和量化内核正确性问题引发多轮讨论与快速修复。值得注意的是，多个 Issue 出现"多人同时认领同一修复"的协作摩擦，以及 stale bot 集中关闭了一大批长期无活动的旧 Issue。

### 🎯 AMD/ROCm 生态相关动态

本周期 AMD 生态异常活跃，覆盖**运行时工具链、内核迁移、并行策略、量化正确性、非 AITER 回退路径**五个方向。

#### 1. 运行时与工具链
- **#62536 [已合并] ROCm 10.1 + MORI v1.2.4 升级**（rasmith）。这是本周期最重要的 AMD 基础设施变更：`rocm-smi_lib` 在 10.1 中被移除，改用 `amd-smi`；需要 AITER `v0.1.28.post1` 以避免 10.1 编译器的性能回退；更新内核符号映射工具以识别新编译器的 device code；Ray 也需升级以适配 `amd-smi`。同时修复了因 `rocm-smi` 移除而损坏的 KV connector 测试。
- **#64752 [已合并] HSA_TOOLS_LIB 存在时跳过 RTLD_GLOBAL 提升**（gurpreet-dhami）。解决 `libtorch_cpu.so` 的 RTLD_GLOBAL 提升与外部 HSA profiler（如 rocm-trace-lite）互相排斥、导致零内核记录的问题，新增单元测试覆盖 ROCm/CUDA 两条路径。

#### 2. Libtorch Stable ABI 迁移（第三步）
- **#70391 [新增] ROCm paged attention 迁移至 stable ABI**（giuseppegrossi）。将 `paged_attention` 从 `_rocm_C` 移至 `_C_stable_libtorch`，是 #67551 系列（RFC #26946）的第三步。附带 `--offload-compress` 覆盖所有 ROCm 扩展，wheel 从 300.4 MiB 降至 192.9 MiB。
- **#70436 [新增] Octave KV cache 迁移**（giuseppegrossi）。同一迁移序列的延续，描述尚为空，属于进行中工作。

#### 3. 并行与性能优化
- **#70331 [新增] gfx950 大 eager routed MoE 的 dispatch/combine 重叠**（fanxingran）。`VLLM_ROCM_MOE_SPLIT_AG_RS=1` 在 DeepSeek-V4.1-Flash、4×MI355X、并发 384 下，评分输出 **+5.77%**，P95 TTFT **−10.34%**，KV 容量不变。
- **#70343 [新增] EPLB 重排门控改为逐层负载失衡**（shen-shanshan）。现有 ROCm 门控对所有 MoE 层求和后测量失衡，逐层热点相互抵消导致几乎跳过所有重排。改为逐层测量后，Qwen3-30B-A3B DP8+EP 均衡度 0.80 vs 0.76，DeepSeek-V4.1 DEP8 离线回放吞吐 +15.7% vs +13.9%。
- **#70485 [新增] prefix_prefill 内核跳过空 query tile**（SRKRZ23）。这是 `ROCM_ATTN`（MI300X 默认后端）的 chunked prefill 热点。共享 16K 前缀场景下请求吞吐 **+26%**，平均 TTFT **−39%**，输出逐位一致。
- **#70443 [新增] rocm_fp8_mqa_logits 的融合 Triton BF16-WMMA 回退**（charlie12345）。在 AITER MQA logits 不可用（RDNA gfx1100/1151/1201 或非 AITER ROCm）时，避免 `[H, M, N]` fp32 中间张量，峰值内存降低 20.5–38.4×，速度提升 7.1–20.7×。
- **#70409 [新增未合并即关闭] RX 9060 XT (gfx1200) 的 W8A8 block-FP8 GEMM 调优配置**（Bye-legumes）。仅新增 16 个 JSON 配置文件，补齐 #68325 未覆盖的 RDNA4 SKU。关闭原因未见说明，可能因配置提交策略调整。
- **#70422 [新增] 按精确 VRAM 统计测量 CUDA graph 捕获内存**（Bye-legumes）。`hipMemGetInfo` 每次分配至少计 2 MB，导致 PIECEWISE 捕获内存被严重高估（Qwen3-4B 报 4.0 GiB，实际 0.6 GiB），直接影响 KV cache 预算。
- **#70396 [新增] ROCm 解码阶段 PCP + FULL cudagraph**（simondanielsson）。修复 #70233，描述待补全。

#### 4. 正确性与兼容性
- **#68806 [已合并] MiniMax-M3 gfx942 原生 QK-norm/RoPE 回退移除**（**afriedri-amd**）。#64111 后 MI300X + AITER sparse PA 在 warmup 崩溃（KV 布局不匹配），移除无法复现的 `_USE_GFX942_NATIVE_QKNORM_ROPE` 门控。修复后 588 tok/s vs 保留门控并修 layout 的 388 tok/s，融合路径可恢复 ~34% 性能。
- **#65427 [已合并] top_k_per_row_decode 不拆分行 ≤ k**（**xaguilar-amd**）。Mistral Large 4 在 MI325X 262K 上下文、k=2048 场景下，短行从 43–142 µs 降至 5–10 µs，TPOT −15%~−27%，吞吐 +17%~+36%。
- **#70427 [新增] INT4 per-token-head KV cache 保持零在量化范围内**（AndreasKaratzas）。修复全同号行被裁剪的问题，Llama-3.2-1B BOS 行误差从 21–28% 降至 2.3–2.9%，同时写内核提速 1.2–10.1%。明确声明**不是** #69766 精度缺口的修复。
- **#70448 / #70447 [新增]**（charlie12345）。前者移除非 AITER/non-gfx950 的 `SparseAttnIndexer` 注册门槛，让 RDNA3/3.5/4 可用稀疏 MLA 回退；后者为 DSv4.1 AMD 路径补上 `swa_cache_layer.bounded_replay` 检查，防止非 CDNA3/4 GPU 上的长上下文静默输出损坏。
- **#67218 [已合并] MoRIIO WRITE 模式释放 prefill 块**（kliuae）。修复 decode 提前释放或复用 transfer id 时 prefill KV 块泄漏，GSM8K 精度不变。
- **#47159 [已关闭] GPTQ qzeros 断言失败**。giuseppegrossi 在 MI300X 复现并定位为 `TritonW4A16LinearKernel.process_weights_after_loading()` 对 AutoGPTQ 布局的误转置；hnhyzz 指出非对称量化与对称量化需要分别处理。该 issue 从 6 月持续到 11 月才关闭。

#### 5. ROCm 战略级 Feature Request（simondanielsson 连发三条）
- **#70403 / #70401 / #70402**：为 GLM-5.3-Flash、DeepSeek V4.1、DeepSeek V4 引入 ShardQ 并行（按 query token 切分 indexer + sparse attention，通过 a2a 交换）。核心背景是 NVIDIA 侧 #63956 已让 ShardQ 成为 TP 下默认稀疏 MLA prefill 路径，而 ROCm 侧 GLM-5.3-Flash/DSv4.1 仍每 rank 复制完整 indexer 和全序列稀疏注意力。NVIDIA 参考数据：DSv4.1 在 1M 上下文 TTFT 提升 **1.66×**。#70230 已为共享路径启用，但这两个模型因自有 ROCm 后端被排除在外。三条 issue 均指向同一系统性缺口，预期后续会合并为统一实现。

> **小结**：本周期 AMD 侧呈现"**工具链升级 + ABI 迁移 + 内核级性能**"三线并进。`-amd` 后缀贡献者（afriedri-amd、xaguilar-amd）与高频 AMD 贡献者（giuseppegrossi、charlie12345、simondanielsson、Bye-legumes、shen-shanshan）构成主力。ShardQ 的系统性补齐是未来最值得跟踪的 ROCm 方向。

### 💬 高热度讨论分析

#### ① Issue #70385 / PR #70390 — `chat_template_kwargs["tools"]` 覆盖引发 HTTP 500
**议题**：`OnlineRenderer.preprocess_chat` 将请求提供的 `chat_template_kwargs` 合并到服务器构建的 `tools` 之上，且 `"tools"` 未列入 `SERVER_OWNED_CHAT_TEMPLATE_KWARGS`。后果有二：(1) 静默覆盖工具 schema、绕过 `tool_choice="none"`；(2) DeepSeek V3.2/V4/V4.1 渲染器因未捕获 `KeyError: 'function'` 返回未认证 HTTP 500。

**多方观点**：
- **Dyslex7c（报告者）**：详细定位根因，随后承认"忘了在描述里说明自己正在修"，并提交 PR #70390。
- **Raj102002 / four1er**：均表示想接手修复，存在重复认领。
- **mercant1982（独立验证者）**：用完整原生 vLLM 树 + 真实 FastAPI 路由跑 64-case 测试；主线 32 失败，仅将 `"tools"` 加入保留列表后 64 全过；进一步补测 `conversation`/`messages`/`image_order`，36 个用例从"20 个 200 + 16 个延迟 400"变为"全部 400 且参数名正确"。

**争议焦点**：保留关键字集合的边界应如何界定（是否包含内部渲染器参数）；以及对未认证请求应返回 400 还是 500。**结论**：PR #70390 已采纳 `tools`/`conversation`/`messages` + DeepSeek V4.1 的 `image_order`，并将 DeepSeek 渲染器的 `KeyError` 映射为 400，测试覆盖扩展到 72 个 API 记录。

#### ② Issue #47159 — GPTQ qzeros 形状断言（9 条评论，跨 5 个月）
**议题**：`triton_w4a16_gemm` 对 qzeros `[K//group_size, N//8]` 的断言在 GPTQ 模型上失败。

**观点分歧**：
- **giuseppegrossi**：在 MI300X 复现，认为根因是代码把 compressed-tensors 布局 `[N//8, K//group_size]` 的转置逻辑错误地套用到 AutoGPTQ 模型上，应加布局分支判断。
- **hnhyzz**：认为需要**两个 PR 并存**——非对称量化模型加载时 qzeros 仍可能被误转置（需要 giuseppegrossi 的修复），而对称量化模型根本不应创建 qzeros（需要此前的那个 PR）。
- **giuseppegrossi 追问**：为何先前 PR 被关闭未合并。

**结论**：Issue 已关闭，但两个修复方向的分工在讨论中才被澄清，反映出量化权重布局处理长期缺乏统一契约。

#### ③ PR #70326 — Qwen4Exp 预填充上下文并行（PCP）
**议题**：为 Qwen4Exp NVIDIA 实现加入实验性 PCP，覆盖 QSA、Gated DeltaNet、PLE。PCP4 相比 TP4EP4，327K–655K 输入 TTFT 降低 21.5%–39.5%，GSM8K128 118/128 vs 117/128。

**观点**：
- **gau-nernst（审阅者）**：连续质疑——与 TEP+SP、PP 相比如何？是否考虑独立 DP + shared PLE（#67004/#68684）？并直言"这个 PR 触及太多地方，审阅和批准会花很久"。
- **erictanjn（作者）**：补充三方案对比表——PP4 冷 prefill 最低（13.2s），PCP4 在 90% 缓存前缀下最优（1.8s），且生产负载高前缀复用，故选择 PCP；暂未尝试独立 DP + shared PLE，当前聚焦长请求 TTFT SLO。

**争议焦点**：在大范围改动与已有并行方案之间如何取舍。**状态**：open，审阅者明确表达了对审阅成本的担忧。

#### ④ PR #69778 — CUTLASS block-FP8 线性层融合 SiLU-and-mul
**议题**：让已有的 `silu_and_mul_per_block_quant` 融合对 `CutlassFp8BlockScaledMMKernel` 可达。Qwen3.6-35B-A3B-FP8 每 decode step 节省 40 次 down_proj 启动。

**观点**：
- **hclsys**：在 GB10 上测得 TPOT 基本持平（c1 18.30→18.44 ms），指出 decode 受专家权重读取限制，融合收益被掩盖；并报告两臂 greedy 输出不同。
- **Johnsonms（作者）**：解释第二个 commit 使融合路径与未融合逐位一致，GB10 上应无速度/输出差异；hclsys 随后确认重构后三 prompt greedy 一致。

**结论**：已合并。讨论体现了"小 GPU 上性能收益不可见 ≠ 无价值"的工程判断。

#### ⑤ Issue #70373 — Qwen3 reasoning parser 强制 `skip_special_tokens=False`
三人几乎同时表示认领（lidoraz、pk954061458、themanoj-025），最终 themanoj-025 提交 PR #70405。问题涉及三条路径叠加（`ParserEngine.adjust_request` 强制关闭、`Qwen3Parser.extract_reason_content` 思考关闭时原样返回、`DelegatingParser.parse_delta` 视为 reasoning 结束），属于典型的"多方并发修复"协调场景。

### 💡 值得关注的问题

1. **ROCm ShardQ 覆盖缺口（#70401/#70402/#70403）**：GLM-5.3-Flash、DeepSeek V4/V4.1 在 ROCm 上仍每 rank 复制完整 indexer + 全序列稀疏注意力。NVIDIA 侧已有 1.66× 的 TTFT 收益参考，ROCm 侧实现需在 #70230、#67208、#65555 之上叠加，且受 gfx950-only 与 16 头 tile 限制。这是 AMD 长上下文竞争力的关键短板。

2. **`vllm._custom_ops` 张量校验体系缺失**：连续 5 个 Issue 指向同一类问题（stride/对齐/空 batch）。建议评估在算子入口统一加 `TORCH_CHECK` 或引入集中式校验工具，而非逐个补丁。

3. **#70428 / PR #70437 GLM-4.7 结构化标签 500**：畸形 tool schema（string/list/bool property）在 `VLLM_ENFORCE_STRICT_TOOL_CALLING=1` 下产生 `AttributeError`/`TypeError`。PR 采用宽松回退（`AnyTextFormat`），但"拒绝 vs 宽容"的策略仍需与 OpenAI schema 校验规则对齐。

4. **#70417 / PR #70439 MTP shift 内核竞态**：warp 间缺少屏障导致窗口偏移两位，虽不影响最终输出正确性（target model 会验证），但降低接受率。修复仅 2 行 + 回归测试，但暴露了 Triton 内联 kernel 中 in-place 依赖的普遍风险。

5. **INT4 KV cache 精度（#69766、#70427）**：#70427 明确只修复"零不在范围内"的窄案例，与 bf16 的精度差距仍未闭合（Llama-3.2-1B logprob 偏移不变）。需要更高层面的量化方案评估。
