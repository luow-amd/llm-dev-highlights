### 💬 高热度讨论分析

1.  **`[Bug]: Combination of sleep mode and speculative decoding cause crash (ROCm / MI250)` (#47548)**
    -   **核心议题**: 在 ROCm 平台上，同时启用 sleep mode 和 speculative decoding 会导致 vLLM 启动时崩溃。
    -   **参与者观点**:
        -   **`OlofKalufs` (报告者)**: 提供了清晰的复现步骤，分别测试了单独启用两个功能都正常，但组合使用时崩溃。
        -   **`souvikDevloper`**: 经过深入分析，指出根因是一个已在主分支被修复的库解析 bug。他详细阐述了崩溃的步骤：`CudaRTLibrary` 在 ROCm 平台优先查找 `libcudart`，而 `tilelang` 库加载了 `libcudart_stub.so`，导致错误的库被绑定。由于发布分支 v0.24.0 未包含此修复，因此问题重现。他还指出了另一个相关的 PR (#41746) 正在加强 `find_loaded_library` 的防护逻辑。
    -   **争议焦点**: 无明显争议。原报告者和分析者一致认为是已修复的 bug 在发布版本中的回退问题。
    -   **当前状态**: `open`。这是一个已知问题的报告，问题的修复方案已在主分支上，正在等待下个版本发布或用户从源码构建。

2.  **`[Bug]: REGRESSION : FP8 KV cache FlashInfer no longer available as attention backend on SM75 (Turing) in v0.24.0` (#47549)**
    -   **核心议题**: 用户在升级到 v0.24.0 后发现，FlashInfer 注意力后端不再适用于 SM75 (Turing) 架构的 GPU（如 Quadro RTX 8000），导致 FP8 KV 缓存无法使用，性能大幅下降。
    -   **参与者观点**:
        -   **`ptempier` (报告者)**: 详细对比了 v0.23.0 和 v0.24.0 之间 FlashInfer 后端的可用性变化，并以具体数据说明了性能衰退（约 5-11 tok/s 降至 0.8-1.1 tok/s）。
        -   **`yanghui1-arch`**: 指出该变动源自 PR #45375，原因是 FlashInfer 在 SM75 上存在共享内存的 bug。建议用户在问题解决前降级至 v0.23.0。
    -   **争议焦点**: 无争议。这是一个已知的**主动的功能回退**，并非意外回归。社区选择牺牲 SM75 上的 FlashInfer 支持以避免更严重的 bug。
    -   **当前状态**: `open`。等待上游 FlashInfer 修复其在 SM75 上的 bug。

3.  **`[Perf] Maintain persistent penalty statistics instead of per-step CPU rebuild in V1 sampler` (#47540)**
    -   **核心议题**: 优化 V1 模型运行器中惩罚（重复度、频率等）采样器的性能。当前实现在每个解码步都在 CPU 上重建一个大的 token ID 矩阵，开销随对话历史线性增长。
    -   **参与者观点**:
        -   **`xiaguan` (PR 提交者)**: 提出了一个显著的性能优化，通过维护持久化的统计信息（`PenaltiesState`）来替代每步重建，移除了昂贵的 CPU 操作和同步点。
        -   **`njhill`**: 回应并提出了一个架构层面的问题，询问提交者是否可以迁移到 MRV2 (Model Runner V2) 上来，因为 MRV1 正在被废弃。
        -   **`xiaguan`**: 确认了 MRV2 是未来方向，但同时指出其生产环境使用的 MoE 模型（如 GLM）并不在 MRV2 默认支持的架构列表中，询问 MRV2 对这些架构的生产稳定性。
    -   **争议焦点**: 此讨论的核心是 **优化方向 vs. 架构迁移**。提交者提出的优化非常有价值，但维护者建议直接迁移到即将成为主流的新架构上。这反映了 vLLM 社区中一个常见的权衡：是继续改进旧架构（MRV1）还是全力投入新架构（MRV2）。提交者对 MRV2 在其特定模型上的稳定性表达了合理的关切。
    -   **当前状态**: `open`。讨论处于初期，等待进一步的技术澄清和决策。

### 🛠️ 重点技术变更

1.  **`[Kernel] ReplaySSM: cache SSM inputs instead of state for faster standard and speculative decode (Mamba2 + GDN)` (#47576)**
    -   **技术解读**: 这是一个由 Dao AI Lab 和 NVIDIA 合作提交的尖端 PR。它引入了一种全新的 SSM 解码优化方法。传统方法在每个步长都需要读写完整的循环状态，这是内存带宽瓶颈。ReplaySSM 通过缓存最近的输入和周期性检查点来重构状态。这带来了三大好处：1) 减半了标准解码中的显存流量；2) 在推测解码中实现“免费”的拒绝/回滚，无需保存状态快照；3) 支持更高效的并行验证。
    -   **影响**: 对 Mamba2 等 SSM 模型的推理速度和吞吐量有**革命性**的提升，特别是在长序列和推测解码场景下。

2.  **`[Perf][Frontend] Add opt-in incremental prompt-encoding cache for multi-turn chat` (#47583)`
    -   **技术解读**: 此 PR 针对多轮对话场景，解决了前端 re-tokenize 整个对话历史的性能瓶颈。它实现了一个基于 LRU 的增量编码缓存，仅对新增加的文本进行 tokenize。核心技巧是利用 BPE tokenizer 的 `pre_tokenizer` 确定安全的重用边界，确保 token 准确。
    -   **影响**: 能**显著降低**大模型在多轮对话中的首 token 延迟（TTFT），生产数据表明可使 TTFT 从 0.92s 降至 0.47s，对于长上下文场景效果尤为明显。

3.  **`[AMD][NVFP4] Add aiter backend for NVFP4 MOE runtime on gfx950 (non-native)` (#47553)`
    -   **技术解读**: 此 PR 为 AMD `gfx950` (MI350/MI355) 平台引入了用于 NVFP4 MoE 模型的专用 `aiter` 后端。它利用 ROCm 的 `aiter` 库实现了**2-3 倍的 MoE 内核加速**和 30-40% 的端到端模型推理加速（非原生 NVFP4 支持，基于 BF16 MFMA）。
    -   **影响**: 这是 AMD 平台追赶 NVIDIA 在低精度 MoE 模型上性能的关键一步，显著提升了 MI350 系列在运行如 `Qwen3-30B-A3B-FP4` 等模型时的实用性。

4.  **`[Bugfix] Match the mapped filename in find_loaded_library` (#47586)**
    -   **技术解读**: 修复了一个危险的底层库加载错误。`find_loaded_library` 函数通过子字符串匹配来查找加载的库，这会导致它错误地匹配到 `tilelang` 的 `libcudart_stub.so` 桩库，而非真正的 `libamdhip64.so`。修复方案是通过精确匹配文件名的 `名称.so[.*]` 模式来杜绝误匹配。
    -   **影响**: 对于同时使用 vLLM 和 TileLang 的环境，此修复消除了一个**非确定性、且可导致后台工作进程崩溃**的严重 bug，并正确启用了 `VLLM_CUDART_SO_PATH` 环境变量的备用方案。

5.  **`[Bugfix] [EPLB] Avoid Silent Accuracy Corruption in Quark MXFP4 EPLB` (#47588)`
    -   **技术解读**: 修复了在特定后端下启用专家负载均衡（EPLB）时，Quark MXFP4 MoE 模型会**静默**产生错误输出的问题。根因是权重转换后，被内核使用的张量未在 `named_parameters()` 中注册，导致 EPLB 在平衡专家时移动了 `scale` 张量，但未移动对应的权重张量，从而导致数据错位。
    -   **影响**: 这是一个**难以察觉的严重 bug**，会导致推理结果出错而不报错。此修复对于任何在生产环境中使用 Quark MXFP4 量化模型并启用 EPLB 的用户至关重要。

### 💡 值得关注的问题

1.  **Speculative Decoding 与 Sleep Mode 的兼容性 (`#47548`)**: 此问题已在主分支修复，但尚未发布。对于希望在 ROCm 集群上同时利用这两个功能的用户，需要关注下个版本的发布计划。
2.  **WSL2 上 UVA 不可用的回退方案 (`#47579`)**: 由于 WSL2 上未启用 Pinned Memory，导致默认的 V2 模型运行器因需要 UVA 而崩溃。相关补丁正在讨论，建议 WSL2 用户持续关注此 issue 以了解进展或临时方案。
3.  **FlashInfer 在 SM75 上的回归 (`#47549`)**: 这并非传统意义的 bug，而是一个主动的功能裁剪。用户需要明确，若在 SM75 上运行 v0.24.0+ 版本，将无法使用 FlashInfer 后端和 FP8 KV 缓存。
4.  **Quark MXFP4 EPLB 的静默精度问题 (`#47588`)**: 尽管修复 PR 已提交，但该问题的严重性值得所有使用 Quark MXFP4 模型的用户警惕。在相关修复合并之前，使用 EPLB 时应进行充分的正确性验证。
5.  **NVFP4 KV 缓存与 FlashInfer/SM75 的限制 (`#47548`, `#47549`)**: 当前 vLLM 生态中对 FP8 或 NVFP4 这类新型数据类型的支持仍处于早期阶段，特定硬件组合（如 SM75）或特定功能组合（如 speculative decoding + sleep mode）可能会出现限制或 bug。部署时应仔细核对硬件和功能兼容性。
