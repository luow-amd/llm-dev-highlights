## 💬 高热度讨论分析

> 说明：本周期数据中，评论条数绝对值并不高（多数为 1–5 条），但少数讨论技术浓度和多方参与度很高。以下按“信息密度 × 参与方多样性”选取。

### ① #63867 — ROCm sliding-window prefix-prefill 跳过被 mask 的 context tile（已合并，讨论最深入）

**核心议题**：对 sliding-window 模型，ROCm Triton prefix-prefill 是否应跳过窗口外 KV tile 的读取。声称 MI300X 上 32k 上下文 / 512 window / head 256 时 kernel 时间最多快 **38.37×**。

**多方观点：**
- **`mjkvaak-amd`（审阅）**：指出改动**未 gate 到 gfx942 / ROCm**，而 `ROCM_ATTN` 在所有 arch 的候选列表里都排在 Triton 前面；建议（a）考虑更严格 gate 到 ROCm，（b）在不同 `get_cdna_version()` 上做更充分测试，（c）补充相关模型的 e2e 性能与质量验证。
- **`amd-sriram`（性能验证）**：给出关键反例——**对 GLM，本 PR 只在 DSpark draft model 跑在 `ROCM_ATTN` 时才有帮助**（GLM-5.3-Flash 32k 下 +68% 吞吐），但如果把 draft model 直接切到 `TRITON_ATTN`、不打这个 PR，吞吐相同甚至略高。这从根本上动摇了“为什么必须改 kernel 而不是换后端”的前提。
- **`phambinhfin`（作者）**：逐条回应——仅 `ROCM_ATTN` 调用此 kernel，非 sliding 层汇编一致；补充了 gfx950 与 GLM 数据。
- **`okorzh-amd`（关联性）**：指出 #61433 会把 spec-decode draft 移出 `ROCM_ATTN`，届时 DSpark 加速不再适用；#54194（已合并）是本 PR block 对齐的前提。
- **`AndreasKaratzas`**：追问是否做了 accuracy 测试。

**争议焦点**：**性能收益是否具备普适性，还是绑定在一条即将被废弃的代码路径上**。最终合并，但“换后端 vs 改 kernel”的取舍讨论很有代表性。

### ② #69504 — 削减 Humming MoE 每层 host 开销（跨硬件三方验证）

**核心议题**：A100 上 Humming MoE 层 host 时间 ~470µs 对 GPU ~255µs，TTFT 比 Marlin 差最多 24%。PR 削减 vLLM 侧 host 开销 483→409µs（−15%）。

**多方观点与交叉验证：**
- **`hclsys`（GB10 / DGX Spark / Grace ARM CPU 独立复现）**：非 eager 下“无差异，噪声以内”；eager 下 c1 有约 4–5% 吞吐提升，8/32 持平。
- **`Abhayrkhot`（作者）**：认可并解释——**节省只在 host 是瓶颈时显现**；在 GB10 上每层 stream ~310MB 专家权重（~1.1ms @273GB/s）已盖过 host 时间；eager decode 单 token 只读 8 个路由专家（~20MB/层），所以 c1 有收益。
- **`hclsys`**：追加 4 组交替顺序的干净测量，确认结论。

**价值**：这是一次教科书式的**跨架构（x86 A100 vs ARM GB10）性能 claim 交叉验证**，并且结论明确（“收益条件性成立，无 SM121 回归”），没有陷入无谓争论。

### ③ #69473 — Qwen3-VL 视频 prompt 在 transformers ≥5.10 下嵌套 vision marker（Bug，2 条评论）

**核心议题**：HF processor 行为变化导致每帧 marker 被嵌在外层 `<|vision_start|>…<|vision_end|>` 内，多出 2 个 token，使 Cosmos3-Super 等模型的 greedy 输出偏离官方参考。

**观点交锋：**
- **`four1er`**：表示在复现并准备修 `_expands_only_video_token`。
- **`ashirwad19`（对修法提出异议）**：指出 #69474 的“三元组目标 `[vision_start, video_pad, vision_end]`”方案会让**仅含裸 `<|video_pad|>` 的 prompt 匹配失败**（`PromptUpdateMismatchError`），而 `test_qwen3_vl_pruned_video_prefix_cache_hit` 正是用裸 placeholder 构造 prompt，GPU 测试会挂。提出替代方案：保留 `[video_token_id]` 目标，在请求含视频时折叠嵌套对。

**争议焦点**：**修复嵌套的正确做法是“改匹配目标”还是“改匹配后的折叠”**，且要兼容现有裸 placeholder 用法。目前 Issue 仍 open。

### ④ #69439 — 可复用 KV 压缩层 RFC（架构级讨论）

**核心议题**：为 P/D 传输与 L2/L3 分层 KV 存储设计统一的压缩架构，首个集成 Mooncake P/D 与 Mooncake Store。

**观点：**
- **`staryxchen`（扩展性视角，三条建议）**：（1）**Phase I 就对齐后端无关接口**，而非推到 Phase II，否则未来接 LMCache 等要返工；（2）连接器/存储只应看到不透明的 `(addr, nbytes)` buffer 集合 + 版本化 descriptor blob，不应感知 codec 的内部分布；（3）P/D 与 Store 用同一最小契约；（4）**`plan(...)` 同时承担了启动期 workspace 预留和执行期规划两种职责，应分离**。
- **`Liuzedooong`（作者）**：全盘接受，将按建议修订 RFC 与 roadmap。

**状态**：RFC 认可度高，但 API 契约尚未定稿，后续三条 stacked PR（#69441 / #69527 / #69528）已先行提交。

### ⑤ #57196 — XPU 实现 stateless_init_device_torch_dist_pg（已合并，长周期审查）

横跨 2 个多月（9/16 创建，11/24 合并），Intel Habana 贡献者 `tzielinski-habana` 多次 ping 审阅、追问 Intel CI 失败是否阻塞（`jikunshang` 直到 11/13 才回复问“什么场景需要”）。反映**非 NVIDIA/AMD 平台审阅资源紧张的现状**。

## 🛠️ 重点技术变更

### 1. #66749（已合并）— FlashInfer CuTe-DSL 无量化 MoE 成为 Hopper 默认后端
新增 `FlashInferCuteDSLSm90Experts`，覆盖 bf16/fp16、TP/EP、`silu`/`swigluoai`/`situ`/`gelu_tanh`/`relu2_no_mul`、确定性 top-k combine、CUDA graph 可捕获。**默认的 fused finalize 不可复现但快约 1.6%**；确定性路径用两阶段 float32 finalize。相对 Triton：Mixtral-8x7B TP8 −12% TPOT / +13% 吞吐；DeepSeek-V2 −6% TPOT。**意义**：这是对 #41306（Hopper 上 MoE 默认从 Triton 迁到 FlashInfer CUTLASS 后回归）的正面回应，且作者在讨论中主动把默认立场从“等 FlashInfer 0.7.5”改为“现在就默认”。

### 2. #69442 — AITER v0.1.30 升级与 FlyDSL 阻塞
这是本周期**风险最高的 AMD 基础设施变更**。改用预编译 wheel 简化构建，但 v0.1.30 的 `flydsl==0.5.1` 缺少 `gpu.binary`，直接破坏 MiniMax M3 Specialized Decode 与 DeepSeek-V4.1 Mono Decode numerics。同时把 fp16 + `swiglu_limit` 的未量化 MoE 从 AITER 回退到 Triton（AITER v0.1.29.post1 曾静默丢弃 clamp，v0.1.30 改为抛异常）。**需持续跟踪 post1 发布**。

### 3. #69511 — DeepSeek-V4 FP8 `wo_a` cos/sin cache 跨层共享（ROCm）
单点释放 **5.13 GiB/GPU** 并全部转为 KV cache（+2.4% token 容量），输出 bit-identical，CUDA graph 与 weight reload 均兼容（仍经 `refill_derived` 原地重填）。**意义**：这是典型的“每层重复分配大表”反模式修复，收益远大于大多数 kernel 微优化，且零精度代价。

### 4. #69616 — DP+EP+AG/RS 下 fused shared experts 修复（ROCm）
all-gather `topk_ids` 后，共享专家列使用的是源本地行索引，导致 token 的共享专家在每个 rank 上重复计算或全不计算。GLM-5.2 MXFP4 DP4+EP 在 MI355X 上 GSM8K **0/200 → 196/200**。**意义**：这类“静默算错”在分布式配置组合里最难发现，且此前一个正确性配置直接不可用。

### 5. #69568 — Grammar-as-a-Drafter RFC（结构化输出 × 投机解码）
把 grammar 已确定的强制 span 从 `EngineCore` 的 `StructuredOutputManager` 直接作为 draft，绕过模型 drafter，**可越过任意 drafter 的 horizon K_M**，对 MTP/EAGLE3/DFlash/n-gram/无 drafter 均适用，且与 #62130 的 draft-logit masking 正交。评论中 `ravismash` 提供 CPU 实测：`disable_any_whitespace` 下强制 span 占比从 12–15% 提升到 31–49%，并追问 benchmark 是否用了该模式、以及 tool-call grammar 至今忽略该开关（#68990）。**意义**：若落地，可能是结构化输出场景下投机解码收益的结构性提升。
