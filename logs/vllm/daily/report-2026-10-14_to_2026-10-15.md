### 🛠️ 重点技术变更

#### 1. Issue #61673：Cascade attention + SimpleCPUOffloadConnector 的 KV 前缀串用（严重正确性）
- **现象**：批内 15 个请求共享 2048-token head，第 16 个请求 O 与它们无任何共享，却被调度为 `num_common_prefix_blocks=[128]`，并对 O 用第一个请求的 KV block 解码。O 的输出出现"is red"等只存在于其他请求共享 head 中的短语。
- **根因（推测）**：connector 有一次 CPU store 在飞，为该 head block 增加了 1 个引用计数，使"被 15/16 请求持有"的 block 看起来像被全部 16 个持有。
- **影响**：这是**跨请求数据泄漏 + 静默错误输出**，在多租户/敏感场景下风险极高。V2 model runner 因传 `common_prefix_len=0` 不使用 cascade，故不受影响。
- **状态**：OPEN，尚无关联修复 PR，值得最高优先级关注。

#### 2. PR #61573 + #61662 + #61694：AMD MonoKernel 三连
- Qwen3.8-27B（#61573）、GLM-5.3-Flash（#61662）、Kimi-K3（#61694）在 MI355X 上分别验证了 mono decode / mono MoE / mono verification 的性能增益，单步内核数从 1699→220（GLM）、输出吞吐 +21%~+34%（Qwen3.8）。**这是 AMD 把"用极致内核工程榨干 MI355X"作为差异化竞争力**的集中体现。

#### 3. PR #61649：FlyDSL 内核迁移到公共 API
- 把 TurboQuant/UltraQuant 的 FlyDSL decode 从 `ArithValue`/`scf.*`/`buffer_ops`/raw MFMA 等私有或不稳定接口重写为 `fx.*` 公共 API，净减 916 行，并修复 pinned stack 下内核加载失败静默回退 Triton 的问题。**这对 AMD 内核生态的长期可维护性意义重大**——只有建立在稳定 API 上的内核才能持续演进。

#### 4. PR #60276：Online Quantization 扩展到 MOE（已合并）
- 把 re-quantization API 从线性层扩展到 MOE，实现 **compressed-tensors / modelopt / Quark NVFP4 → any online MOE 方法** 的转换。这意味着部署方可以在服务时把已量化 checkpoint 转成目标硬件最擅长的量化格式（如 NVIDIA→MXFP4、AMD→FP8），无需离线重训。是量化部署灵活性的关键一步。

#### 5. PR #61595：ROCm AITER 默认开启策略（DRAFT）
- 若落地，MI300/MI355 用户在安装 AITER 后将**默认开启** AITER 后端。潜台词是"AMD 硬件跑 vLLM 应该开箱就用 AITER"。但作者自己标注了两大风险：**数值变化**（未 pin backend 的 recipe 会变）、**运行时崩溃不可控**（通过支持检查但实际 fault）。这一决策值得社区重点审视其灰度策略。

### 💡 值得关注的问题

1. **#61673 Cascade attention + CPU Offload 的 KV 串用**——跨请求数据泄漏级别严重性，尚无修复 PR，建议优先定位。受影响配置需明确：`--no-disable-cascade-attn` + `SimpleCPUOffloadConnector` + V1 model runner。

3. **#61658 异步查找在共享 secondary tier 下返回过期 absent 判定**——新贡献者 kjoshiDTX 已表示接手。该 bug 在多实例共享 `root_dir` 的 fs tier 下会导致"磁盘上已有 block 却持续 miss"，与 #61187 只覆盖本实例写入形成互补修复需求。

4. **#61621 / #61622 CUDA driver context lock 阻塞其他线程**——step-start 的 `.cpu()` 拷贝等待上一 step 时 libcuda 持有 context-wide lock，导致其他线程的 CUDA 调用（含 KV connector、异步拷贝线程）阻塞大半个 step。修复方案（pinned + event wait）已提交 PR #61622，对多线程组件共存场景影响显著。

5. **#61738 宽 spec-decode verify 在混合 GDN 模型上的静默早停**——Qwen3.5 类模型 `num_speculative_tokens ≥ 7` 时在第 8 个生成位置采到 EOS，greedy 顺序解码却正常，且 ngram_gpu 与 MTP 两种 runner 均复现。这类"宽 verify forward 本身"引发的问题定位难度极高，报告极为详尽（51K 字符）。

6. **KV checksum 系列（#61578/#61580）的方向确认**——多租户隐私 vs 复杂度的权衡仍在进行，维护者倾向 opt-in 安全网，但需观察核心侵入性是否可控。

7. **BYOG RFC（#61698）与 fast-track merging RFC（#59665）的联动**——若"贡献者自建 eval image + 提交结果"模式被采纳，将显著改变 vLLM 的 PR 评审流程与 CI 成本结构，是治理层面的重要决策点。
