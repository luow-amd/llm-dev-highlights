#### 1. Issue #52454：Quark INT4 模型加载失败（AMD MI100）

- **报告者**：`hnhyzz`（使用 AMD MI100 加载 `amd/Qwen3.8-27B-Quark-Qronos-INT4-W4A16`）
- **核心错误**：`QuarkConfig.apply_vllm_mapper()` 将结构化字典列表误当作字符串列表处理，导致 `AttributeError: 'dict' object has no attribute 'endswith'`。
- **技术影响**：Quark 是 AMD 主力量化工具，此问题直接阻断 AMD 量化模型在 ROCm 平台的加载。
- **修复进展**：`sylvesterkaczmarek` 已提交 PR #52474，仅对全字符串列表应用 mapper，结构化列表原样保留，并附带回归测试。**PR 已关闭（未合并，可能是重复或主动撤回）**，需持续关注后续替代 PR。

#### 2. Issue #52442：Kimi-K3 SiTU MoE 静默垃圾输出（ROCm/gfx950, MI350X）

- **报告者**：`stefanskiasan`
- **根因**：aiter 库环境变量 `AITER_SITUV2_A8W4=1` 与 vLLM 侧 `VLLM_ROCM_USE_AITER_MOE_SITUV2_A8W4` 未同时设置时，kernel 采用 **interleave 布局**，而 vLLM 按 **separated 布局**洗牌权重，导致两者不匹配，**无任何报错地产生垃圾输出**（实测 `2+2` 得到 `' 0. 4. 0. 0. 4'`）。
- **严重性**：静默错误、无 warning，普通用户极难察觉；修复方式是必须显式设置两个变量。报告者建议 vLLM 能从 aiter 库侧自动推导布局，避免此类无声失败。
- **状态**：Open，`karimitanii` 请求认领。

#### 3. PR #52426：修复 DeepSeek-V4 在 ROCm 平台的 MRV2 回归

- **作者**：`qli88`（AMD 员工）
- **问题**：PR #51430 和 #51768 将 DSv4 从 MRV1 切换到 MRV2 后，**ROCm 平台无法运行**。
- **验证**：在 ROCm 平台以 `VLLM_ROCM_USE_AITER=1` 完成 DSv4-Pro-0813 的 GSM8K 评测，准确率 0.9378。该 PR 也标注了 `mrv2` 标签，是确保 MRV2 迁移不脱离 AMD 平台的关键补丁。

#### 4. PR #52478：ROCm 睡眠模式唤醒时 MI300 间歇性 GPU 内存故障

- **作者**：`AndreasKaratzas`（AMD 员工）
- **问题**：ROCm CI 中 MI300 在唤醒（重映射约 172 GiB）时约 0.53 秒处触发 GPU fault，两个 Buildkite CI 构建均命中同一签名。
- **分析**：PR #44972 添加的 allocator-wide `hipMemset` 是唯一设备级操作，被判定为高置信 vLLM 触发源。本 PR 改为仅清零 Mamba/GDN 状态视图，避免全量清洗 KV 缓存，并保持打包缓存偏移、步长不变。
- **状态**：Open，需 MI300 硬件复现验证。

#### 5. 已合并 PR #49515：ROCm CI 无 GPU 任务平台选择

- **作者**：`AndreasKaratzas`

### 💬 高热度讨论分析

#### 1. Issue #52434：`ParallelLMHead` 缺少 `output_size_per_partition` 属性（5 条评论）

- **议题**：在 DGX Spark 上加载 `Qwen3.6-35B-A3B-NVFP4-Fast` 时崩溃。
- **各方观点**：
  - `Raditya0902`（初判）：认为问题在 NVFP4 量化配置缺少 ParallelLMHead 分支，引用了 #40999 的模式。
  - `SyaOtiLan`（深入追踪）：实际根因是 **CompressedTensorsW8A8Fp8.create_weights() 未存储 `input_size_per_partition`/`output_size_per_partition`**，而 `ParallelLMHead` 不像普通 LinearBase 自带这些属性。
  - `Raditya0902` 表示认可并让位，`SyaOtiLan` 随即提交 PR #52451 修复。
- **焦点**：初判方向有误，靠二次追踪才定位到真正的 FP8 路径，而非 NVFP4。体现复杂量化栈下根因定位的困难。

#### 2. PR #52460：Mamba cache `"all"` 模式在 MRV2 下回退到 `"align"`（4 条评论）

- **议题**：MRV2 未实现 `block_idx_last_scheduled_token_prev_step_d`，导致混合 Mamba 模型在 `--mamba-cache-mode all` 下启动崩溃。
- **各方观点**：
  - 作者 `bandham-manikanta` 增加 MRV2 下自动回退到 `"align"` 模式的逻辑。
  - `Slach`（Issue 作者）实测验证有效。
  - `njhill`（审阅者）提出关键质疑：**新注入的 unsupported-feature 检查与回退逻辑存在顺序依赖**，两者互相"中和"——无论谁先执行，用户都可能遭遇非预期的静默降级（缓存模式或 MRV2）。
- **结论**：作者已根据意见更新逻辑，但 njhill 指出"一个机制即可，两个机制互相矛盾"的设计问题尚未完全解决，值得后续 review 关注。

### 🔥 热门话题与趋势分析

#### 1. 推测解码（MTP/DSpark）成为最大问题源

本周期大量 Issue 围绕 MTP/DSpark 展开，且表现出多维度缺陷：

- **多模态模型误告警**（#52481）：MTP draft 模型缺少 multimodal processor 的误导性日志。
- **TP≥2 加载失败**（#52480）：drafter 权重 shape 与 TP 世界大小不匹配。
- **KV cache 兼容性**（#52475）：`turboquant_*` KV cache 与 MTP 组合导致重复崩溃（232 次重复 token 的静默失败）。
- **流式文本损坏**（#52469）：引号边界处词语丢失，非流式正常，llama.cpp 同场景正常。
- **睡眠唤醒不重载草稿权重**（#52479）：Level 2 wake 后 draft 权重缺失，acceptance 降为 0，约 2 倍减速。

这些高频问题表明推测解码在多种硬件/量化/KV 缓存组合下的鲁棒性仍显不足。

#### 2. 新架构密集适配期

- **DeepSeek-V4**：TP/EP 校验、MRV2 迁移、SM120 稀疏 MLA、ROCm 回归，都指向这是一个跨平台重投入的模型。
- **Gemma4**：parser 默认值、heterogeneous head_dim 在 XPU 的适配（3 个 PR）、CI 崩溃问题，持续产出。
- **Qwen3.5/3.6**：NVFP4 加载、MTP 配置、FP4 + DSpark 的组合支持仍有缺口。

#### 3. 量化后端碎片化

vLLM 同时支持 FP8（多个子型）、NVFP4、INT4（Quark/AutoRound）、MXFP4、TurboQuant 等，导致 bug 常常出现在"量化类型 × 模型架构 × 硬件"交叉点上。本周期 **#52434（FP8）、#52454（Quark INT4）、#52475（TurboQuant）、#52480（NVFP4）** 均属此类。

#### 4. MRV2 迁移阵痛

MRV2 是当前主线重构，但 Mamba 缓存（#52460）、DeepSeek-V4 ROCm（#52426）、MTP 结构输出（#52477）等问题都因迁移而集中发酵。

### 💡 值得关注的问题

1. **MTP/推测解码可靠性系统性风险**：从流式损坏、KV 不兼容、wake-up 不重载到 TP 加载失败，建议社区考虑将 MTP/DSpark 作为"高危特性"进行更严格的组合测试矩阵（量化 × KV × 并行度）。
2. **DP 负载均衡器对 prefix cache 的破坏**（#52463）：#47420 的 tie-break 轮转导致多轮会话命中率从 81.6% 降至最低 7.8%，端到端吞吐下降 2%-13%。PR #52464 的 prefix-affinity 方案提供了部分缓解，但高层设计仍需讨论。
3. **静默数据损坏类 bug 增多**：AITER 布局不匹配（#52442）、MTP 流式丢字（#52469）、turboquant 重复崩溃（#52475）均无报错。这类问题对生产环境危害极大，建议在关键路径增加状态校验或告警。
4. **Qwen3.5 MTP 在 TP≥2 不可用**（#52480）：Shape 不一致的根因可能与 speculative decode 的 drafter 加载路径有关，影响所有 Qwen3.5 系列的多卡部署，需优先排查。
5. **MRV2 与旧特性交互的迁移策略**：Mamba cache `"all"` 模式和 `mamba_cache_mode` 的校验逻辑冲突说明，MRV2 应在设计上集中管理"支持/不支持特性"的声明，而非散落多处 check，避免相互中和。
