1.  **PR #40892 `[ROCm][DSv4] Make AITER sparse MLA decode cudagraph-clean`**
    *   **贡献者**: `ChuanLi1101` (AMD 员工)

    *   **状态**: 开放中，需解决合并冲突。

2.  **PR #40889 `[ROCm] Add AITER-accelerated MLA decode for DeepSeek V4 on MI355X`**

4.  **PR #38503（合并） `[ROCm][Engine] Fix GPU memory leaks in engine shutdown and test workaround for async KV prefix cache reset`**
    *   **贡献者**: `AndreasKaratzas` (AMD 员工)
    *   **内容**: 这是本周期的关键修复之一。该 PR 修复了 ROCm 平台在引擎关闭时导致 GPU 内存泄漏的三个问题：
        1.  `lru_cache` 错误地缓存了绑定方法，导致模型权重无法释放。

        3.  `GPUWorker.shutdown()` 未释放模型权重、KV 缓存等资源。
        此外，还为异步 KV 缓存前缀重置的测试问题提供了临时解决方法。
    *   **状态**: **已合并**。对 AMD 平台的稳定性至关重要。

5.  **PR #40767（合并） `[CI][AMD][BugFix] Fix deadlock occuring in test_moe_layer`**
    *   **贡献者**: `rasmith` (AMD 员工)
    *   **内容**: 修复了在 MI300 上运行 `test_moe_layer` 测试时出现的死锁问题。原因是 `WeakValueDictionary` 缓存了 `DeepEP` 缓冲区，当垃圾回收时，部分弱引用被非确定性回收，导致并行工作线程间的通信出现死锁。通过在每次测试后插入 Barrier 来清除缓存，从而避免了死锁。

### 💬 高热度讨论分析

1.  **Issue #40880 & #40831: MTP/TurboQuant/CUDA Graph 导致输出退化**
    *   **核心议题**: MTP 或 Ngram 推测解码与 TurboQuant KV Cache 及 CUDA Graph 结合使用时，在 Qwen3 模型上会输出大量重复、退化的 token（例如工具调用失败、长上下文检索循环）。
    *   **参与者观点**:
        *   **@noonghunna (报告者)**: 通过严谨的“隔离矩阵”测试，逐步排除了 MTP 特定、混合注意力模型特定等假设，最终将问题根源锁定在 **CUDA Graph 捕获/重放层**，而不是注意力计算或 Triton 内核本身。他提供了关键证据：关闭 CUDA Graph（`--enforce-eager`）后问题消失。
        *   **@Sandermage (贡献者)**: 独立复现了问题，并进一步剖析了根因：`TurboQuantAttentionImpl._prefill_attention` 的 cudagraph 捕获路径错误地将 spec-decode 的验证批次视为“第一块 prefill”，设置了错误的 `cu_seqlens_k = cu_seqlens_q`，导致注意力仅关注当前块的 token，忽略了所有先前的 KV 缓存。
        *   **后续发展**: @noonghunna 发现 #40880 的 MTP 问题未在 #40831 的 v7.13 修复集（主要针对 Ngram）中得到解决。@Sandermage 随后快速响应，推出了 v7.14 补丁集（P64-69），专门修复了 MTP 路径下的 `cu_seqlens_k` 问题。@noonghunna 在多台设备上验证了 v7.14 的修复效果。
    *   **争议焦点**: 在最终根因锁定前，对问题的归属（GDN 层问题 vs. 注意力路由 vs. CUDA Graph）有多个假设，通过层层递进的实验逐步验证并排除。
    *   **状态**: #40831 和 #40880 均已关闭（分别为 v7.13 和 v7.14 修复），体现了社区协作高效解决问题的典范。

### 🛠️ 重点技术变更

1.  **PR #40338 `[LoRA] MoE LoRA Refactor`（已合并）**
    *   **技术解读**: 这是一个重大的架构重构。原有的 MoE LoRA 实现通过“猴子补丁”方式修改 FusedMoE 内核的方法，导致代码难以维护、调试和扩展。该 PR 将 LoRA 作为 MoE 模块的“一等公民”，引入了 `MoELoRAContext` 这一明确的数据结构，将 LoRA 状态和计算封装起来，通过常规的函数参数传递给 MoE 内核。这极大地提高了代码的**可读性、可维护性和可扩展性**，为未来支持 EP（Expert Parallel）和更多量化后端的 LoRA 奠定了基础。

2.  **PR #38503 `[ROCm][Engine] Fix GPU memory leaks in engine shutdown`（已合并）**
    *   **技术解读**: 此 PR 修复了引擎关闭时 GPU 内存泄漏的三个根因。对于使用 AMD GPU 的用户而言，这解决了在长时间运行、热加载模型或频繁重启服务场景下的潜在不稳定性。特别是 `gc.freeze()` 后未 `unfreeze()` 的问题是一个通用的 Python 陷阱，此修复对其他平台也有借鉴意义。

3.  **PR #40889 & #40892 `AITER-accelerated MLA decode`**
    *   **技术解读**: 这两个 PR 代表了 AMD 平台在 DeepSeek V4 推理上的关键性能突破。**PR #40889** 直接替换了 PyTorch 参考实现，获得了 2-3x 的加速。**PR #40892** 进一步使其兼容 CUDA Graph，这是解锁 GPU 极致利用率的关键一步。这表明 vLLM 团队正积极利用 AMD 的 AITER 生态来弥补 CUDA 生态的差异。

4.  **Issue #40880 的根因分析过程**
    *   **技术解读**: 该 Issue 的讨论本身就是一个精彩的“bug 根因分析”案例。通过设计“隔离矩阵”，作者@noonghunna 逐步排除了多种可能性（MTP 特异性、模型特异性、模型 RNN 假设、注意力路由假设），最终通过对比 `cudagraph_mode=NONE` 和 `cudagraph_mode=FULL` 的实验结果，将问题锁定在 **CUDA Graph 的重放逻辑**。这种系统性的调试方法值得学习和推广。
