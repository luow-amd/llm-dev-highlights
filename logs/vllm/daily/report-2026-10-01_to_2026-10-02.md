### 💬 高热度讨论分析

#### 1. #57978 [ROCm][Perf] Parallelise AITER MLA page-index expansion over token chunks

- **核心议题**：AITER MLA 的 `_expand_page_indices_kernel` 只按 request 维度并行，每个 request 内串行遍历 token。低并发长上下文时单个 workgroup 拖慢整个 GPU。
- **观点与立场**：
  - 作者 `fululi12` 强调这是 kernel 级 microbenchmark，不声称端到端吞吐提升；低并发长上下文下 61.6µs/调用、7 次/步、占 34.9ms step 的 1.23%。
  - 评审 `chilkotiKartik` 建议尾块 early return、确认无 atomics，并认为长上下文下可降至个位数微秒。
  - 作者随后采纳 early return，并补充 131k–1M 上下文下 13.3×–82.1× kernel speedup。
  - `dllehr-amd` 参与 review，AMD CI 一度需要 unblock。
- **争议焦点**：是否应声称端到端收益。作者非常谨慎，只提供 kernel 数据；评审认可设计但要求更多验证。
- **状态**：已合并（2026-10-01）。修复对任何 ROCm MLA 模型低并发场景都有意义。

#### 2. #59705 [ROCm][Perf][MiniMax-M3] Fused sparse-layer decode (mono decode kernel)

- **核心议题**：将 MiniMax-M3 的 57/60 稀疏层融合成单个 FlyDSL kernel，覆盖 norm、attention、双 all-reduce、MoE，默认在多项条件下自动启用。
- **观点与立场**：
  - `ChuanLi1101` 提出多项要求：补充 vLLM 端 A/B 性能（不能只用 ATOM 数据）、确认 indexer context-parallel 缺失、增加输出对比、修复临时 KV-cache profiler TODO、避免 per-step per-rank info 日志、增加显式 opt-out。
  - `akii96` 指出 #59653 + ROCm/aiter#6047 是同一 ATOM#2419 移植，并发现 race：done flag 早于 writes 完成，约 0.6% 请求 stale KV 乱码，GSM8K 不显示；修复在 aiter#6047。
- **争议焦点**：内核融合带来显著 decode 加速，但默认启用、缺少 opt-out、与另一 PR 重复、存在正确性 race。
- **状态**：开放中，预计需要补充验证、修复 race、增加 opt-out。

#### 3. #54805 [ROCm][BugFix] Revert AITER PA gluon decode from ROCM_AITER_FA

- **核心议题**：AITER PA gluon decode 要求 uniform query length，但 scheduler 在 speculative draft 截断或 token budget 裁剪时会产生 ragged decode batch，导致 MiniMax-M3 + EAGLE3 + shuffle KV 中止。
- **观点与立场**：
  - 作者 `ukannika` 选择回退 pa gluon，保留 shuffle layout fix，等待 AITER 侧提供 per-row query length 后再恢复。
  - `rasmith` 感谢修复，并列出受影响模型：Llama-3.1-8B、MiniMax-M2.7、Qwen3-30B-A3B、Qwen3-235B-A22B 等。
  - `JWhiteCat` 补充 gluon decode 中 `k_scale`/`v_scale` 硬编码问题，FP8 KV 下 decode logits 可能被错误缩放。
- **争议焦点**：回退 vs 等待 AITER 修复；恢复 gluon 路径需要同时解决 ragged batch 和 KV scale 问题。
- **状态**：已合并回退。对 AMD 平台稳定性是重要修复。

#### 4. #58623 [Distributed] Enable custom all-reduce under VLLM_BATCH_INVARIANT

- **核心议题**：`VLLM_BATCH_INVARIANT=1` 原先强制关闭 custom all-reduce，并将 NCCL 固定到单 channel；但 custom all-reduce 的 backend 选择依赖 tensor size，会破坏 batch invariance。
- **观点与立场**：
  - 作者 `sfeng33` 提出使 backend 选择 size-independent，使用 1-stage kernel 固定 rank 顺序，并对超过 `max_size` 的输入分块 all-reduce；同时 gate 掉 AITER all-reduce 和 QuickReduce。
  - `mosafariuk` 建议移植 #50505 的 determinism 测试，并指出 `fused_allreduce_gemma_rms_norm()` 仍存在 size-dependent 分支，影响 MiniMax M3、Kimi K3、DeepSeek V3.2。
  - `sfeng33` 回复这些模型尚未在 batch invariance 验证列表中，本 PR 仅覆盖 communicator 路径。
  - `yewentao256` 询问 `inp_size % 16` 检查是否仍 size-dependent，作者认为实际验证的 hidden size 都是 8 的倍数，不影响。
- **争议焦点**：是否应将 batch invariance 扩展到 fused norm 路径；size 依赖是否完全消除。
- **状态**：已合并。对确定性推理和 AMD AITER/QuickReduce 路径有重要影响。

#### 5. #59055 [RFC]: Release all releasable GPU memory in sleep mode (tracking)

- **核心议题**：sleep mode 下即使只管理 weights 和 kv_cache，DeepSeek-V4 仍每 GPU 驻留 14–21 GiB；需要归因并释放 WorkspaceManager、runner state、CUDA graph pool 等。
- **观点与立场**：
  - 原作者 `penguin-wwy` 列出各 PR 对应释放项，并指出最终剩余 5.6–6.2 GiB/GPU，主要是 CUDA graph executables 和 CUDA context。
  - `AlanFokCo` 支持优先 buffer offload，认为 graph discard/lazy recapture 应单独评估；提醒销毁 GraphExec 不保证驱动返还物理内存；建议区分 custom-allreduce copy fallback 与禁用 NCCL graph registration。
  - `github-actions` 自动 CC ROCm 相关人。
- **争议焦点**：哪些内存可释放、如何释放、性能与安全权衡。
- **状态**：已关闭，相关 PR 多数已合并或推进中。

### 🛠️ 重点技术变更

#### 1. #59739 MXFP4 KV cache + 原生 FP8×FP4 稀疏 MLA（ROCm）

这是 AMD 长上下文稀疏注意力的重要一步。每个 512-wide latent 存为 256B E2M1 codes + 16 inline E8M0 scales，共 272B/token，而 bf16 为 1024B，KV 容量提升 3.76×。gfx950 上使用 FP8×FP4 scaled MFMA 原生内核直接计算。MI355X TP4 下 16k–130k context 输出吞吐 +6.1%~8.5%，GSM8K 97.42% vs 96.97%，GPQA 持平或略优。该 PR 若合并，将显著增强 AMD 平台长上下文服务能力。

#### 2. #59575 Qwen3.8-Flash-Next gfx950/MI355X 优化 tracker

该 Issue 是 AMD 旗舰模型在 MI355X 上的性能优化路线图，涵盖：
- PLE tables 在 Quark checkpoints 下不量化加载（#59443）；
- QSA fused pre-indexer（#57947），预期 +10.8% @8k/1k、+5.2% @60k/600；
- FlyDSL QSA indexer 与 sparse GQA（#59437）；
- HyperConnection FlyDSL two-stage `combine_and_mix`，预计 decode +10%；
- GEMM preshuffled MXFP4 配置；
- GDN decode 激活量化融合。
该 tracker 串联多个 PR 和 AITER 依赖，是观察 AMD 平台大模型推理优化方向的关键入口。

#### 3. #59705 / #59653 MiniMax-M3 融合稀疏层解码

两个 PR 同源，均移植 ROCm/ATOM#2419，将 MiniMax-M3 的 57 个稀疏层融合为单个内核，覆盖 attention、双 all-reduce、MoE。声称 decode 最高 2× 加速。但评审指出缺少 vLLM 端 A/B、默认启用无 opt-out、indexer context-parallel 未接线，且 `akii96` 发现 done flag race 导致约 0.6% 请求 stale KV 乱码。该方向潜力大，但必须解决正确性和可回退性问题。

#### 4. #57978 AITER MLA page-index expansion 并行化

该修复针对 ROCm MLA 在低并发长上下文下的 kernel 串行问题。原实现仅按 request 并行，`num_reqs=1` 时单 workgroup 处理整个序列。新实现增加 token chunk 维度，MI355X 上 131k 上下文 13.3×、384k 45.7×、1M 82.1× kernel 加速。虽然端到端收益小，但消除了长上下文低并发场景的明显瓶颈，且适用于所有 ROCm MLA 模型。

#### 5. #58623 VLLM_BATCH_INVARIANT 下启用 custom all-reduce

该 PR 解决 batch invariance 与 custom all-reduce 的冲突。原先 `VLLM_BATCH_INVARIANT=1` 强制 NCCL 单通道，关闭 custom all-reduce。新方案使 backend 选择与 size 无关，使用 1-stage kernel 固定 rank 顺序，并对大输入分块 all-reduce，同时 gate 掉 AITER all-reduce 和 QuickReduce。该变更对确定性推理、可复现性和 AMD ROCm 上的 all-reduce 路径都有影响。
