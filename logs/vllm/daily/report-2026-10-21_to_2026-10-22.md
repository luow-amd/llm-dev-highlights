### 💬 高热度讨论分析

#### 1. #57832 — MiniMax-M3 上下文并行稀疏 indexer（9 条评论，已合并）
- **核心议题**：TP>1 时每个 rank 重复流式读取完整 index-K cache，是否可通过 block 分片消除。
- **观点交锋**：
  - **ChuanLi1101（评审者）**：逐条列出硬伤——`_decode_score_chunks` 被调用但从未定义、`VLLM_ROCM_MINIMAX_INDEXER_CP` 未注册进 `envs.py`、5 个 commit 全部缺 DCO `Signed-off-by`；并质疑"每步 `torch.full` + 全矩阵 MAX allreduce 对 cudagraph/通信量的影响"，要求对比公开 InferenceX 表，指出 conc=20 时 ITL/吞吐回退。
  - **peymanr（作者）**：承认 TP=4 下"每个 rank 只对自己 head 的 block shard 打分再合并"的精确性论证不成立，**主动撤回此前 +23%、EAGLE3、GSM8K 等全部数据**；改为 all-gather index query → 对全部 head 打分 → 打包 `(score, global_block_id)` int64 键交换 top-k → 按 head 合并，并提供 `tests/distributed/test_minimax_m3_indexer_cp_tp.py` 逐 head 对比全上下文参考。
  - **后续调整**：开关从环境变量迁移到 `AttentionConfig`（`{"minimax_m3_indexer_cp": true}`），并改为启动期硬拒绝（非 bf16 index cache、TP=1、非 ROCm、与 fused decode 同时启用均报错）。
- **结论**：默认关闭、opt-in；代码更精确但复杂度上升，性能收益需在 AITER indexer（#57840）落地后重新评估。

#### 2. #60683 — Kimi-K3 专用解码（9 条评论，已合并）

#### 3. #60808 — MoRIIO READ 在 forward 前等待全部读取（9 条评论，已合并）

- **观点**：
  - **dllehr-amd**：担忧"强制等待所有 KV load"可能造成真实性能威胁，要求提供 before/after 的 Perf/Accuracy 数据，并询问 #60636 是否已覆盖该问题。

### 🔥 热门话题与趋势分析

**1. AMD MonoKernel / 专用解码成为主线（最显著趋势）**
`--monokernel` 从 RFC #60904 快速铺开到 Kimi-K3（#60683）、MiniMax-M3（#62712、#62994）、Qwen3.8-Flash-Next（#63032）、DSv4.1（#63027）、HY4（#58509）。共同模式：**按模型把 decode 关键路径写成一个/多个持久化 FlyDSL kernel，TP all-reduce 走 peer memory，层内复用 vLLM 已加载权重**。收益集中在低并发（c=1~16）的 TPOT 与 TTFT。风险在于**每模型独立代码树**带来的维护成本、以及跨 rank 失败必须 fail-stop 而非 hang。

**2. 推测解码持续升温**
DSpark（confidence head、Markov walk int8 #62958）、EAGLE3（#62994、#62897 竞态）、MTP、DFlash2（#62851 数值一致性）、DSpark + DCP（#62990）。趋势是把 **spec decode 的 host 侧开销**（备份 token id 竞态、metadata 构建、confidence head GEMV）当作一等性能目标。

**3. 构建系统与 CI 债集中暴露**
ROCm 侧 `_rocm_C` 触及 2 GiB relocation 上限被迫回退 7.6x 编译加速（#62983）；build 优化三件套需用演示分支联合度量（#62921）。NVIDIA 侧 cu129 镜像的 `torchcodec` CUDA 13 依赖（#60406）在 release 与 nightly 持续失败，多人复现。**"构建/打包/测试基础设施"已成为跨平台共同瓶颈。**

**4. 量化后端多样化与正确性**
NVFP4/FP8/MXFP4/FP4 并行推进；MoE 量化路径出现多处**静默正确性 bug**：Nemotron NVFP4 在 `torch.compile` 下 GSM8K 从 0.30 掉到 0.006（#61749，`needs_exact_strides` 标签修复）、GLM-5.3-NVFP4 在 EP+PCP>1 下双重 all-reduce 导致输出乱码（#62945 + 修复 #62947）、b12x head_dim 64 首次 forward 崩溃（#63011）、b12x `fake_mode` 属性错误（#62984）。

**5. KV Cache 与解耦式服务**
MoRIIO（#60808、#62832、#63031）、NIXL UCX（#62905）、sleep mode、tiered offload（#62932）、scale-out token 路径（#57052）。关注点从"能不能传"转向**传输竞态、睡眠/唤醒后的重新注册、以及 CP 下的分片读取效率**。

**6. b12x 后端稳定性**
Blackwell（SM120）上的 b12x attention/linear 后端在完整生产 flag 下连续暴露问题：`fake_mode` 未加守卫（#62984）、head_dim 64 的 NUM_MMA_KV 无有效 shared-memory 分配（#63011）。维护者倾向"指向 FlashInfer 内置的已修复 b12x"而非在 vLLM 侧打补丁。

### 🛠️ 重点技术变更

#### 1. #62983 — 回退并行编译 paged attention（已合并）
**技术解读**：`_rocm_C.abi3.so` 内嵌的 `.hip_fatbin` 已达 ~1.94 GiB，其中约 80% 是未压缩的 GPU 调试信息。把 attention 拆成 12 个编译单元会让每份调试信息重复复制，直接越过 2 GiB 的 PC-relative relocation 上限（mold 报 `R_X86_64_PC32 against .eh_frame out of range`）。回退仅留下 ~64 MB 余量。
**影响**：短期解除 ROCm 10.0 nightly 阻塞；长期需在 `-Xarch_device -g0`（−74%，牺牲 GPU 源码级调试）与 `--offload-compress`（−96%，保留调试信息但需 ROCm ≥ 6.2 且冷启动重编译）之间取舍。#62921 已证明三件套联合可再省 34%–42% 构建时间，但必须先解决体积上限。

#### 2. #57832 — MiniMax-M3 上下文并行稀疏 indexer（已合并，opt-in）
**技术解读**：M3 的 indexer 每个 query token 需对全上下文所有 block 打分；TP>1 时 index-K cache（单 head 复制）被每 rank 全量流式读取。方案：all-gather index query（每 token 4×128 bf16）→ 每 rank 只对 `1/P` 的 round-robin block shard 打分**全部 head** → 每候选打包 int64 `(score, global_block_id)` 做 top-k → all-gather 交换 → 按 head 精确合并。交换量与上下文长度无关（`P × heads × k × 8` 字节/token）。
**影响**：为长上下文、大 decode batch 的 TP 并行提供可扩展路径；默认关闭且要求 bf16 index cache，属于保守落地。

#### 3. #61749 — MoE custom op 要求精确 stride（已合并）
**技术解读**：`vllm.moe_forward`/`moe_forward_shared` 从 `needs_fixed_stride_order` 改为 `needs_exact_strides`。Nemotron-3-Nano NVFP4 在 FlashInfer TRTLLM MoE 后端 + `torch.compile` 下，hidden dim padding（2688→2816）的 stride 假设被编译器打破，导致 GSM8K 从 0.303 掉到 0.006（46% invalid）。
**影响**：修复是两行标签改动，但揭示了 **custom op stride 契约与 torch.compile 交互**的系统性风险；作者明确说明此前 #52383 的"把 pad 移进 op"方案会破坏 ROCm 的 RMSNorm+pad fusion（#34636）。

#### 4. #52712 / #62994 — MiniMax-M3 MonoKernel（已合并 + 扩展）
**技术解读**：layer 3–59 的 FFN 半层（TP all-reduce → residual → post-attn RMSNorm → FP32 router top-4 → shared/routed BF16×MXFP4 experts → 最终 all-reduce）作为一个持久 FlyDSL launch。要求 TP4/gfx950/fp8 KV/`aiter` MoE/`VLLM_ROCM_SHUFFLE_KV_CACHE_LAYOUT=1`。扩展 #62994 让 EAGLE3 的 verify 行（>1 token/request）也能走 FFN kernel——因为 FFN 是 per-row 且不读 KV，只需放宽 host 侧路由校验。
**影响**：证明 MonoKernel 架构可自然吸收推测解码验证阶段；c=1 TPOT −12.5%、输出 +13.6%，GSM8K 差异在噪声内（0.892 vs 0.900，McNemar p=0.69）。>4 并发（>16 verify 行）回落 stock 路径。

#### 5. #62405 — `process_weights_after_loading` 统一用 `replace_parameter`（已合并）
**技术解读**：PWAL 中 `layer.x = Parameter(...)`、`setattr`、`Parameter(layer.x.data)` 等"重新注册新 Parameter"的写法，会丢失已加载对象的类、`weight_loader`、维度属性与 `processed_weight_dims`。改为 `replace_parameter` 保留原对象，覆盖 MXFP4/6/8、NVFP4（CUTLASS/FlashInfer/FBGEMM/PyTorch/Humming）、compressed-tensors、**Quark**、INC、ModelOpt、AutoAWQ、Marlin FP4、CPU AMX MLA、DeepSeek-V4 CPU attention 等 141 处。
**影响**：为量化权重在加载后保持可识别性提供统一基础，是后续 weight-offload、参数级追踪、以及 Quark/ModelOpt 混合精度加载（#63001）的前置条件。

### 💡 值得关注的问题

1. **#62844 — Gemma4 多模态在 MI210/ROCm 7.2.3 上负 KV cache**（open）：视频编码器 profiling 预留 2496 token 预算，直接把可用 KV cache 压为负值；0.28.x 无此问题，属 0.32.0 回归。建议 AMD 侧尽快复现并检查 `_process_video_input` 的 warmup 预算计算。

2. **#60406 — cu129 镜像 `torchcodec` 依赖 CUDA 13**（已关闭但需确认修复落地）：release 与 nightly 均失败，多人跨 GPU/driver 复现，`vllm/multimodal/media/audio.py` 仅捕获 `(ImportError, RuntimeError)` 未捕获 `OSError`。**打包流水线的依赖解析需与 CUDA 主版本严格对齐**。

3. **#62851 — Qwen3.6 GDN 贪心解码与 batch 相关数值不一致**（open，深度报告）：同一前缀经 prefill 重建 vs 经 decode 续写会产生不同下一 token，load 下 preemption/recompute 触发；作者已提交两部分 PoC 补丁（含 `VLLM_SPECULATIVE_TOKEN_PARITY`）与回归测试。涉及 **GDN 线性注意力的 batch 不变性**这一底层假设，值得核心团队评估。

4. **#62945 / #62947 — GLM-5.3-NVFP4 在 EP + TP>1 + PCP>1 下静默乱码**（open）：NVIDIA DSv3.2 decoder 的 `reduce_results=False` 与 `use_all2all_kernels` 强制 `skip_final_all_reduce=False` 导致**两次 all-reduce**，输出被 `tp_size` 缩放。作者已提最小修复，并建议后续让 `layer.py` 的公式查询 `output_is_reduced()`。**"静默错误 + 0 分 GSM8K"是最高优先级风险类别。**

5. **#62984 / #63011 — b12x 后端在 Blackwell 生产配置下连续崩溃**（open）：`fake_mode` 未加守卫、head_dim 64 无有效 `NUM_MMA_KV` shared-memory 分配。评审建议**指向 FlashInfer 内置的已修复 b12x**或在 PyPI 上 bump 版本，而非在 vLLM 侧打补丁——涉及"依赖修复 vs 本地绕过"的治理决策。

6. **#63026 — Ascend SHM 通知邮箱内存增长**（open，非 AMD 但涉及通用路径）：libzmq 4.3.5 的 CONFLATE 文档明确警告入站 socket 未及时处理会内存增长；作者在 x86_64 CPU 上用未修改的 MessageQueue 复现并给出 ABBA 数据（87KB vs 2KB）。**该路径为平台无关代码，可能影响所有使用 SHM 通知的部署**。

7. **ROCm 测试"假绿"治理**：#46261 揭示测试因 ImportError 被静默 skip 数月；#62996/#62907 又暴露 AITER v0.1.26 的 `ck_moe_stage2` 与 W4A16 宽度约束回归。建议在 ROCm CI 中增加**测试收集数/跳过数基线监控**，避免再次出现"测试存在但从未执行"。

8. **#62983 的技术债**：回退后 `_rocm_C` 仅剩 ~64 MB 余量，下一次 kernel 增长可能再次触顶。`--offload-compress` 的模块加载解压开销尚未在 GPU 上测量，是 reland #62475（7.6x 构建加速）的关键前置。
