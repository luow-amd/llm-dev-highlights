### 🎯 AMD/ROCm 生态相关动态

本周期 AMD 生态相关活动量非常大（约占所有活动的 30%），反映出 vLLM 对 AMD 平台的投入正在系统性加强。以下按类别梳理：

#### 1. 关键回归与修复（高优先级）

- **Issue #51151 `[Bug][Regression] #50879 causes wrongful hipMalloc to be loaded on ROCm due to tilelang load`**（fxmarty-amd）
  - 这是本周期最严重的 ROCm 回归问题。PR #50879 将 `nixl_ep` 的导入从全局改为惰性导入，副作用是破坏了此前"意外地"在 tilelang 加载前将真正的 HIP runtime（`/opt/rocm/lib/libamdhip64.so.7`）注入全局符号表的行为。tilelang 导入时先加载了 `libhip_stub.so`，导致 AITER JIT 编译出的 .so 绑定到 HIP stub，进而引发分配失败和测试崩溃。
  - **修复方案**：作者提交了 PR #51176（直接 revert #50879，已合并）和 PR #51159（延迟 tilelang 导入，仅对 ROCm 生效的 `_tilelang_jit` 惰性装饰）。同时提出 `_has_module` 不应真正导入模块（Issue #51162，参考 transformers 的 `find_spec` 优先做法）。

- **已合并 PR #50649 `[ROCm][Bugfix] Kimi-K3 Fix KDA NaN on mixed batches and racy autotune config`**（kliuae）
  - 修复了 Kimi-K3 在 ROCm 上的两个正确性问题：混合 decode+prefill batch 中 decode 序列被错误送入 chunk kernel 导致 NaN；`recompute_w_u_fwd_kernel` autotune 配置 `num_stages=4` + `num_warps=4` 存在竞态。该 PR 将 KDA 逻辑复制到 `kimi_k3/amd/kda.py` 后独立修复，5-shot GSM8K 准确率从 0.8901 提升至 0.9082。

#### 2. AITER / MLA 性能与功能完善

- **PR #51171 `[ROCm][MLA] Reach FULL cudagraphs for AITER MLA speculative decoding`**（yudigege86）
  - 解决 ROCm 上 speculative decoding（DSpark draft + Kimi-K3）无法进入 FULL CUDA Graph 的双重问题：`TritonMLAMetadataBuilder` 将 DSpark draft group 误报为 `UNIFORM_SINGLE_TOKEN_DECODE`，以及 `AiterMLAImpl.forward_mqa` 在捕获区域内存在 host sync 和基于刚读回的值的分配。

- **PR #51119 `[ROCm][MLA] Use saturated Gluon split bucket for CUDA graphs`**（LiuYinfeng01）
  - 将 `AiterMLADecodeMetadata.min_kv_seq_len` 默认值从 1 改为 16384，避免 FULL CUDA Graph 捕获时被 dummmy decode metadata 固定在单 split 拓扑，导致长序列下 Gluon split 并行度无法发挥。该问题通过 Kimi-K3 TP8 100K 上下文实测发现（TPOT 87-90ms 远高于预期）。

- **PR #51195 `[ROCm][MLA] Dispatch gfx942 verify to Gluon`**（maeehart）
  - 将 gfx942（MI325X）上验证过的 Kimi-K3 多 token verification shapes 调度到 CDNA3 Gluon MLA kernel（源自 ROCm/aiter#4582），限 12 BF16 query heads、QLEN=4（batch ≤16）。

- **PR #51216 `[ROCm][AMD] Enable preshuffled sparse indexing for 16-token blocks`**（jamesETsmith）
  - 修复 `--block-size 16` 时禁用 AITER preshuffled FP8 paged-MQA 路径的问题。实测 paged-MQA kernel 从 28.53µs 降至 7.84µs（3.64×），输出吞吐 +2.52%。

- **Issue #51115 `[CI Failure] test_mha_attn_varlen_forward_aiter_fp8 on MI300X`**（vhagor）— AITER fp8 attention varlen 在 MI300X 上测试失败。

- **已合并 PR #51083 `[ROCm] Relax MLA rope+cache test tolerances for bf16`**（Rohan138）— 48 个 bf16 失败全部来自 ~1 ULP 的浮点差异（在 bf16 分辨率下 16-32× 超出原定 `atol=0.001`），放宽为 `atol=0.02`（bf16）、fp8 `rtol=0.15` 等。

### 💬 高热度讨论分析

#### 1. Issue #51140 — Gemma 4 31B 高上下文输出乱码（5 条评论）

**核心议题**：在 ~60K+ context 下 Gemma 4 31B 输出变为乱码。用户 `frenzybiscuit` 已用 base weights 和 PTQ/W8A16/INT8 等不同量化方式验证，排除特例。

**讨论过程**：
- `skyloevil`（vLLM 开发者）先引导用户做受控消融实验：逐步排除 speculative decoding（MTP）、prefix caching、async scheduling 的影响，并要求提供 token 数和原始输出。
- 用户反馈：去除 MTP/prefix cache/async scheduling 后问题依旧；`--enforce-eager` 有缓解但未彻底解决；24K context 下问题消失。
- `skyloevil` 接着要求做 chunked prefill 的 `max_num_batched_tokens` 梯度测试（2048/8192/32768），以分离是否为 memory access 越界或内核调度问题。

**当前状态**：Open。该问题已收敛为长上下文 + chunked prefill 条件下的确定性崩溃（与 MTP/前缀缓存无关），等待用户第二批实验数据。

#### 2. PR #51116 — KV Offload 的 MADV_POPULATE_WRITE fallback（6 条评论）

**核心议题**：`SharedOffloadRegion` 在 Linux < 5.14（RHEL 8 等）上调用 `madvise(MADV_POPULATE_WRITE)` 返回 EINVAL，导致 KV offload 无法启动。该 PR 提出用 `|= 0` 的 NumPy 读改写触发页错误。

**讨论焦点**：
- `orozery` 认为已有的 #44913（guygir）方案更干净，但 stalled 在 pre-commit/CI 失败上。
- `Etelis` 同意让 `Alex-ai-future` 去辅助 #44913 而不是合并这个 PR。
- `Alex-ai-future` 配合做了分支合并和修复（根因是 Python 3.12+ 的 `mmap.mmap` 不可子类化/打补丁），但 pre-commit 又因其他问题失败。

**最终结论**：PR 被引导向 #44913 合并修复，而非双线推进。中间反映了社区维护者对 PR 质量的把控（不轻易接受临时 workaround）。

#### 3. PR #51157 — SigLIP 文本 prompts 强制 padding 到训练长度（5 条评论）

**核心议题**：SigLIP 训练时 `padding="max_length"` 且无 attention mask，无 padding 的文本 embedding 与图像 embedding 不对齐，导致 `/v1/embeddings` 静默返回错误向量。修复方案是模型声明 `get_default_tok_params`。

**观点冲突**：
- 作者 `Hert4` 认为应在模型层声明（因为 `SiglipTextTransformer.forward` 无 attention mask，最后位置池化严重依赖 padding 位置）。
- 维护者 `DarkLight1337` 质疑"硬编码"到所有 SigLIP checkpoint 是过度推断，建议放到 example 文件中。
- `Hert4` 后续提出更优雅的 gating 条件：检查 tokenizer 的 `model_input_names` 是否含 `attention_mask`，有则 opt-out——但发现 SigLIP 1/2 均不含，仍需依赖 `max_position_embeddings`（两个版本 tokenizer 的 model_max_length 分别是 64 和 1e30）。

**当前状态**：Open。该讨论触及了多模态模型 `get_default_tok_params` 扩展点设计的边界（checkpoint 特定属性 vs. 架构固有特性）。

#### 4. Issue #51200 — MiniMAXGemmaRMSNorm 无条件调用 FlashInfer CUDA kernels（3 条评论）

**核心议题**：`vllm/models/minimax_m3/nvidia/model.py` 的 `MiniMAXGemmaRMSNorm.forward` 无条件调用 FlashInfer 的 `gemma_rmsnorm`，在非 CUDA 平台（如 AWS Neuron trn2）上首次 forward 即崩溃。

**观点交锋**：
- 作者 `wagnerpatriota` 做了细致的 root cause 分析，指出 `vllm/models/minimax_m3/amd/model.py:221-250` 已有可移植 Triton 实现，并建议复用。
- 维护者 `wangxiyuan` 回应："`vllm/models/../nvidia` 目录下的模型就是只支持 NVIDIA GPU，这是设计目标。要跑其他平台请自行新增 `<platform>` 实现或接入插件。"——摆明了多平台目录隔离的架构立场。
- 作者坚持核心问题在于 **nvidia/ 目录内遗漏了平台检查**，与目录隔离是两回事。

**当前状态**：Open。涉及 vLLM 多平台模型代码组织方式的设计争论。

### 🛠️ 重点技术变更解读

1. **PR #51176 + #51159：tilelang/HIP stub 符号污染回退与延迟加载**
   - 这是本周期最有价值的防御性修复。`tilelang` 导入时通过 `libtvm_runtime.so` 全局加载 `libhip_stub.so`，破坏了 AMD 平台上 "真实 HIP runtime 优先" 的 AITER 依赖。修复组合体现了 vLLM 对 ROCm ABI 环境的深入理解，也为后续推进 `_has_module` 不导入模块的规范化铺路（Issue #51162）。

2. **PR #51125：w13 shard count 属性化**
   - 将 gated/non-gated MoE 的 w13 分片计数从各量化后端重复的局部变量提升为 `FusedMoEConfig` 级属性。这是 MoE 代码库中影响面大但行为保持 bit-for-bit 兼容的稳妥重构。

3. **PR #51171：AITER MLA speculative decoding 的 FULL CUDA Graph 支持**
   - 修复了两个独立问题：(1) DSpark draft group 被 metadata builder 误判为 UNIFORM 单 token decode；(2) forward_mqa 在图捕获区域的 host sync 与依赖读回值的分配。这使 ROCm 上 Kimi-K3 DSpark 对比 piecewise 模式减少大量 launch 开销。

4. **PR #51119：Gluon split bucket 饱和化**
   - 直接揭示了 vLLM 调优与 AITER python wrapper 交互的经典问题：FULL CUDA Graph 捕获时的 dummy input 会把 AITER 内核配置永久固定为次优分支。默认 `min_kv_seq_len=16384` 是对 CUDA Graph 集成模式的务实修正。

5. **PR #50992：ARC 批量驱逐的线性化**
   - ARC 缓存替换策略在批量驱逐时维护单调迭代器，避免每次候选收集都从列表头重扫。10K 缓存替换一半时从 696ms 降至 4.9ms，是 CPU offload manager 中实际的性能瓶颈修复。

### 💡 值得关注的问题

1. **tilelang/HIP stub 问题的根因尚未根治**：PR #51176 和 #51159 是防御性缓解，真正的修复需要 tilelang/TVM 上游修正符号加载逻辑（PR 描述中已注明 follow-up 项）。在修复落地前，ROCm 上任何新增的惰性导入都有重新激活此问题的风险。

2. **Gemma 4 31B 高上下文乱码的波及面**：Issue #51140 尚未定位。该问题与 `--enforce-eager` 部分相关但未完全解决，暗示可能涉及 FA4 长序列的 mask_mod/causal 交互（与已合并 PR #50294 中发现的 FA mm_prefix causal 修复同源）。建议同步跟踪用户的 `max_num_batched_tokens` 梯度测试结果。

3. **RDNA3 AITER 支持缺失（#51136）**：大量消费级/专业级 RDNA3 用户（W7900/7900 XTX）被排除在 AITER 之外，而 AITER 上游已声明实验性支持。若 vLLM 正式支持 RDNA3 或有 Quark 量化用户群体，这是需要排期的整合任务。

4. **平台特定模型代码的审查边界**：Issue #51200 中 nvidia/ 平台目录内的代码缺少平台 guard 的问题，提示需要建立更严格的 CODEOWNERS 和跨平台 CI（至少是 import-time smoke test on CPU/Neuron），不能依赖"目录隔离"作为唯一的平台保障。
