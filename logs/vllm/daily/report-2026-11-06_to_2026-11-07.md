### 💬 高热度讨论分析

#### ① Issue #56900：Qwen1.5-MoE 在 torch.compile 下输出退化（已关闭，7 条评论）

**核心议题**：H100 + vLLM 0.28.0 下，`Qwen/Qwen1.5-MoE-A2.7B-Chat` 开启 `VLLM_COMPILE` 即产生重复 token 的退化输出，`NONE` 模式正常。

**多方观点**：
- **CarrotSwordsman**（H20 + cu129）：无法复现，提示可能与环境（cu130）或卡型相关。
- **catmcgee**（报告者，随后密集自证）：
  - 同卡对比 cu129 / cu130 **都复现**，排除构建差异；
  - 将首个分歧定位在 post-attention RMSNorm；
  - 显式切换 native `fused_add_rms_norm` 只改变输出但**不恢复正确性**；
  - `DYNAMO_TRACE_ONCE`（mode 2）同样复现，说明**并非 vLLM 自定义 backend 独有**。
- **Id545**：最终定位到 native MoE top-k router——Inductor 可能暴露逻辑 `[M,60]` 但 row stride `(64,1)` 的张量，而 `moeSoftmax/moeSigmoid` 用 `num_experts` 推进行指针，导致除首行外读错 logits；提出传播 `stride(0)`，并指出与 PR #53131 的区别。

**争议与结论**：争议在于是否由 cu130 或卡型导致（catmcgee 用同卡对比推翻），最终定性为「Inductor 逻辑布局 + 自定义 kernel stride 假设」不匹配，并给出修复方向。

#### ② Issue #52833：GLM-5.2 MXFP4 在 MI355X 上 MTP 接受率 0%（已关闭，5 条评论）

**核心议题**：MI355X（gfx950）上 GLM-5.2 MXFP4 的 MTP 每位置接受率为 0.000，且关闭 EP 触发 `hipErrorIllegalAddress`。

**不同立场**：
- **tianxiaojiang4**（报告者）：主动**更正自己的 SGLang 对比**——SGLang 的 `accept len: 3.00` 是被 `SGLANG_SIMULATE_ACC_LEN=2.99` 模拟出来的，不是真实验收，体现严谨性，并指出无真实参照。
- **vllmellm**（AMD）：给出新启动命令（`VLLM_USE_V2_MODEL_RUNNER=1` + 关闭 FP8BMM/FP4BMM），acceptance length 达到 3.00。
- **xuebwang**（AMD）：独立给出相同结论并**定位根因**——GLM-5.2 故意将 MLA 权重（含 `kv_b_proj`）存 BF16，而默认开启的 AITER MLA FP4 BMM 在加载后静默重量为 MXFP4；提交 PR #53123，EP8 接受率恢复至 44.8%。

**争议焦点**：默认开启的 AMD 优化路径是否应具备"模型权重 dtype 感知"能力。结论是关闭特定 AITER 路径可恢复，长期修复依赖 #53123。

#### ③ PR #63349：MOE oracle 去重重构（已合并，7 条评论）

**核心议题**：消除 MOE oracle 中 7~8 份重复逻辑（`make_log_backend`、`_return_or_raise`、prepare/finalize 组装），生产代码净 -307 行。

**不同观点**：
- **selimfedakar**：独立验证等价性，指出一处**未文档化的行为变化**——直接继承 `FusedMoEExperts`（既非 Modular 也非 Monolithic）的 out-of-tree 类，从原先 `False` 变为抛 `NotImplementedError`，建议在 claims 中说明；另建议说明新 `ValueError` 使失败在 `python -O` 下仍有效。
- **fxmarty-amd**（作者）：对"值得写进 claims"的回应是"**不值得**"；并解释保留 `_post_init_setup` 中冗余 assert 是为未走 `make_moe_kernel` 的路径（如 Humming）兜底。
- **SyaOtiLan**：询问未量化 oracle 的后续 slice 是否可接手。

**争议焦点**：重构 PR 是否应显式记录边界行为变化。最终合并，说明该差异被认为影响面极小（仅 out-of-tree 类）。

#### ④ PR #63890：ROCm TP all-gather 使用 AITER IPC（已合并，6 条评论）

**核心议题**：ROCm gfx950/gfx942 小 TP all-gather 由 RCCL 切到 AITER IPC。

**多方观点**：
- **frida-andersson**（reviewer）：要求先在 gfx942/gfx1250 验证或加 gate；并追问 `revcomm`/`mut_reg` 等实验镜像的归属。
- **okorzh-amd**（作者）：承认无 MI300X/gfx1250 硬件，先 gate 到 gfx950；解释实验镜像。
- **frida-andersson**：在 MI325X（gfx942）上实测 overlay ITL 改善（-140µs/-50µs），建议扩 gate。
- **okorzh-amd**：采纳，gate 扩至 `cdna_version in (3,4)`，gfx1250 保留 RCCL。
- 后续 dllehr-amd 参与，okorzh-amd 补充 GSM8K 准确性数据。

**结论**：典型的"作者缺硬件 → reviewer 补验证 → 扩大适用范围"的良性协作，最终合并。

#### ⑤ Issue #66141 / PR #66152：AITER MLA 静默错误（评论少但技术密度极高）

fululi12 的跟进分析指出：缺陷不是"漏一个条件"，而是 `mla_asm_decode_remap_gfx950` 中 **两条独立 if 链**的交互——chain 1 无条件把 qlen 3/4 映射到 `sub_Q=64`，chain 2 的 gfx950 override 只在 `persistent` 时补救。fululi12 在两个独立、更新的 ROCm/torch/aiter 栈上复现（qlen4 的 `cos_diff` 从 0.898 升到 0.998），并明确 PR #66152 只是 vLLM 侧缓解，真正修复需 aiter 侧（fululi12 无写权限）。

### 🛠️ 重点技术变更解读

1. **ROCm 构建加速系列（#62718 + #63365，均合并）**
   将超大 kernel translation unit 按"实例化轴"拆分（skinny GEMM 按 kernel family、MUSE-Spark 按 head_dim），并裁剪 torch 头文件。9-arch 冷构建 **1263s → 472s**，`_rocm_C.abi3.so` 2011→126 MiB。**影响**：显著降低 AMD CI 成本，是后续 ROCm PR 吞吐的基础设施收益；#66092 进一步把该经验固化为评审规范。

2. **#52833 根因与 #53123 修复：默认优化路径破坏模型精度**
   GLM-5.2-MXFP4 刻意保留 BF16 MLA 权重，AITER MLA FP4 BMM 默认开启并静默重量化。**影响**：暴露"默认开启的平台优化"需感知 checkpoint 的量化意图；短期靠关闭 env 恢复，长期需内核侧尊重源 dtype。

3. **#66141 / #66152：AITER fp8 MLA decode 静默错误**
   `gqa_ratio=16, qlen 3/4, non-persistent` 下 `cos_diff` 高达 0.998。**影响**：这是"正确 shape/dtype、无警告、错误数值"的最危险一类 bug；vLLM 侧拒绝配置是必要缓解，上游 aiter 一行补丁是真正修复。

4. **#66030 Kimi-K3.1 模型文件（split 1/5，已合并）**
   引入 `KimiK31ForConditionalGeneration`、DSA indexer、NVIDIA 专用 decode、packed KDA/DSA hybrid cache。**影响**：K3.1 在 main 可导入但尚不能 serve（需 split 3/5 #66037）；分 5 步落地是大型模型合入的范式。

5. **#61816 MXFP4 MoE padding NaN 修复（已合并）**
   AITER a8w4 用 `torch.empty` 分配 scratch，padded 区域在特定调用序列后未写 → FP8 下 0xFF=NaN。**影响**：修复 AMD CI 偶发 `dsv41-mono-decode-numerics-amd` 失败；过程中还修正了 gpt-oss TP1 pad 翻倍导致 live 行被 CK-Tile 跳过的问题。
