## 💬 高热度讨论分析

### 1. #64874 — [ROCm][GLM-5.3-Flash] “Workspace is locked” AssertionError（8 条评论，已关闭）

**核心议题**：GLM-5.3-Flash 在高并发 decode 下，`rocm_fp8_paged_mqa_logits` 所需 workspace 超出 profiling 阶段预留的大小（265 MB → 384 MB），引擎约 6 分钟后崩溃。

**多方观点**：
- **adenzhou1350（源码级分析）**：建议参考通用 ROCm profiling 路径，decode logits 走 workspace manager，同时**保留** prefill logits 峰值对应的独立 `torch.empty` 预留，因为 GLM 仍在 gathered K/scale 视图存活时调用 prefill logits 函数。
- **GuoxiangZu（报告者）**：认同拆分方案，并在 MI308X（gfx942）上稳定复现（TP8、MTP5、`--max-num-seqs 128`），指出 `--max-num-seqs 64` 可规避；后续在 MI355 上验证 #65092 修复有效，报告“KV cache 10,226,729 → 10,217,389 tokens（−0.09%）”，与 workspace 被预留到 384 MB 一致。
- **vllmellm（AMD 侧维护者）**：确认 gfx950 上同样复现，并给出修复 PR #65092。

**争议焦点**：decode workspace 与 prefill 峰值如何分离预留而不互相侵占。**结论**：按 adenzhou1350 的拆分方案解决，#65092 合并，#64874 关闭；GuoxiangZu 后续报告在 AgentX 256k 长上下文、并发 48/64 下运行 1 小时无 workspace 错误。

### 2. #66244 — Qwen2.5-0.5B CUDA illegal memory access（2 条评论，深度技术分析）

**核心议题**：在 `max_num_batched_tokens=1000, max_num_seqs=1` 时初始化 warmup 触发非法内存访问。

**观点与结论**：
- **ziywang50** 用 `CUDA_LAUNCH_BLOCKING=1` 复现后定位到 V2 model runner 的 `_dummy_run`：当 `max_num_batched_tokens > max_num_seqs * max_model_len` 时，dummy batch 的 `seq_len = 1000 > 448`，越界 block-table 行（与 #53658 同类）。给出三行复现表：1000/1 崩溃、448/1 正常、1000/3 正常。
- 讨论修复选项：① 校验时拒绝或钳制该配置；② 在 `_dummy_run` 中封顶并加断言。指出 `SchedulerConfig.verify_max_model_len` 已检测到该情况但只警告（#17853 的有意选择），并澄清该 1000-token dummy size 在运行时永远不会被真实调度达到。
- **状态**：Issue 仍开放，等待维护者选择修复方向。

### 3. #66302 — llama4_pythonic 模板给所有工具参数加引号（2 条评论）

**核心议题**：`tool_chat_template_llama4_pythonic.jinja` 用 `"%s" | format(...)` 把所有参数渲染成字符串，导致布尔/整数/None 类型丢失，且字符串内引号会破坏 `ast.parse`。

**观点**：
- **ziywang50**：询问是否由报告者修复，若否则愿意接手，提议按类型渲染 Python 字面量（字符串加引号并转义，`True`/`False`/`None`，数字裸写）。
- **pra2107tham**：确认会作为下一个任务单独提 PR，不在当前 PR 中混入。

**状态**：#66346 已提交对应修复 PR（基于 #66299 堆叠），说明模板与解析器的一致性是个反复出现的问题（同日 #66299 也在修 gemma3_pythonic 模板）。

### 4. #66332 — /v1/audio/transcriptions 拒绝 `stream_include_usage=false`（1 条评论）

**核心议题**：表单数据在 `mode="before"` 校验器中仍是字符串，`bool("false") == True`、`not "false" == False`，导致逻辑反转。

## 🛠️ 重点技术变更

### 1. #63373 — [Core] Remove Model Runner V1（已合并）
**影响最大**：移除 V1 模型运行器，标志 vLLM 的调度/执行架构完全收敛到 V2。该 PR 同时带 `rocm`、`performance`、`speculative-decoding`、`torch.compile` 等大量标签，涉及面极广，是项目架构演进的重要里程碑。

### 2. #57810 — [Core][KVConnector] 在 pause/sleep 期间保留卸载的 KV 层（已合并）
**面向 RL 场景**：`pause`/`sleep` 原本会驱逐外部 KV connector 层（CPU/SSD 卸载），但 RL rollout 的 `sleep(1) → train → wake_up()` 流程中这正是恢复廉价的来源。新增 `clear_connector_cache=False` 选择性保留，默认仍为驱逐（因为块哈希不覆盖权重）。2×GB200 上测 16 个 ~19.5k token 请求的回放。

### 3. #65092 — [Bugfix][ROCm] 修复 GLM-5.3-Flash workspace 锁定崩溃（已合并）
ROCm 大模型服务稳定性的关键修复。在 profiling 阶段为 decode logits 预留最坏情况 workspace，同时保留 prefill 峰值的独立 `torch.empty` 预留。已在 gfx942（MI308X）和 gfx950 上验证；GSM8K 99%、AgentX 256k 长上下文零错误。

### 4. #64994 — [Perf][DCP] MLA decode 输出在 A2A merge 前上投影（已合并）
Kimi-K3 在 MI355X 上 TP8/DCP8 验证：A2A 每头传输从 514 降到 130 个 bf16 值，decode-bound C16/C32 吞吐 +0.6%/+1.1%，p90 交互性 +1.4%/+2.8%。条件是 `W_UV` 未量化，且不影响 PCP/symmetric-memory/ag_rs 路径。

### 5. #65508 — [ROCm][Perf][MiniMax-M3.1] NVFP4 稀疏 decode 内核直接输出 MXFP8 给 o_proj（已合并）
在 ROCm 上每层 decode 原本有 60 次独立的 MXFP8 量化 launch（每次 ~4.4–4.6 us）。新增 `fp8_out` 变体在最后 store 时直接写 E4M3 + E8M0 scale，与单独量化逐位一致。作者与 reviewer 就 decode-only 与 graph capture 的交互做了多轮讨论，最终补上 dispatch 测试。
