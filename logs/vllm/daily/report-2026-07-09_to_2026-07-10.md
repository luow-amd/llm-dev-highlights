### 🎯 AMD/ROCm 生态相关动态

本周期 AMD 生态是绝对的核心议题，涵盖基础设施、性能优化、Bug 修复和社区协作等多个方面，显示出 vLLM 对 AMD 平台支持的显著加速。

1.  **分布式推理 CI 建设 (Distributed Inference CI)**
    *   **Issue #48117**: 社区成员 `lcskrishna` 提出 RFC，建议为 ROCm 上的分布式推理（特别是分离式 P/D 和 Wide-EP）建立专门的 CI 管线。该 RFC 指出，当前没有持续验证 ROCm 上分离式推理的 CI，导致在多节点/RDMA 等关键路径上的回归问题只能被延迟发现。此 RFC 计划使用 Buildkite + Slurm，覆盖 MoRI-IO KV 连接器驱动下的 P/D 拓扑和专家并行拓扑。这表明 AMD 生态正从“可用”迈向“可靠”，CI 是其中关键一步。

2.  **性能与内核优化 (Performance & Kernel Optimization)**
    *   **PR #48159** (`giuseppegrossi`): 为 AMD MI350X 添加了 Mamba SSU (selective state update) 在 float16 和 float32 下的调优启动配置，以提升 Mamba 层解码吞吐量。这是对之前 MI355 和 MI300X 所做配置工作的延续，表明 AMD 正系统性地为其不同代次的 GPU 进行性能调优。
    *   **PR #45149** (`tvirolai-amd`，已合并): 为 ROCm 上的 DSV3.2 稀疏 MLA 后端启用了 MTP (Multi-Token Prediction) 场景下的 `UNIFORM_BATCH` 图形捕获模式，显著提升了结合 MTP 时的推理性能。
    *   **PR #48179** (`micah-wil`): 修复了 Fused MoE 中，在某些 AMD CI 测试中出现的 MoE 工作区在锁定后意外扩展的 Bug。该修复通过预先分配 MoE 工作区到最坏情况大小来防止运行时锁定错误。
    *   **Issue #48111**: 社区成员 `simondanielsson` 提出希望在 ROCm 上支持双流解码（用于重叠共享专家计算和路由专家路径），并指出在 ATOM 推理引擎的 DPA 部署中，这能减少约 20% 的 MoE 层耗时。
    *   **PR #48158** (`yewentao256`): 移除了一个未使用的 ROCm 内核 `combine_topk_swa_indices_ragged`，清理了代码库。

3.  **注意力机制与模型支持 (Attention & Model Support)**
    *   **PR #47404** (`zihaomu`，已合并): 修复了 ROCm AITER 稀疏 MLA 后端在 CUDA Graph 重放时的一个竞争条件，通过在元数据更新后同步流（stream sync），解决了图重放可能观察到过期元数据导致的内存错误问题。`Fixes #47196`。
    *   **Issue #48172** (`GodRishUniverse`): 请求在 AMD ROCm 的 `ROCM_ATTN` 注意力后端增加对 Prefix LM 内核的支持，以便在使用 `mm_range_tensors` 的多模态模型上也能使用优化的 ROCm 注意力内核。
    *   **PR #47366** (`peizhang56`，已合并): 修复了 AMD CI 中因 CUDA 图形捕获内存预留不足导致的 OOM 问题，关键修复是在 ROCm 上重新启用了 CUDA 图形内存分析并添加了内存回收等待机制。

4.  **基础设施与CI (Infrastructure & CI)**
    *   **PR #48146** (`charlifu`，已合并): 将所有 AMD ROCm 测试步骤的超时时间统一设置为 180 分钟，以应对 AMD CI 资源波动。
    *   **PR #48169** (`peizhang56`，已合并): 将剩余的 AMD CI 步骤（如Engine、Samplers测试）从旧的 `mi250_1` 代理池迁移到 `mi325_1` 池，统一了测试硬件平台。
    *   **PR #48154** (`micah-wil`，已合并): 部分回滚了 PR #47912 中关于“修复池化工作空间锁”的修改，因为该修改在某些 AMD CI 测试中引发了新的失败。

5.  **其他 AMD 相关动态**
    *   **Issue #48106**: `simondanielsson` 请求实现 `PrefillDelayer` 以减少 DPA 服务中的 prefill/decode 干扰，主要用例是在 `gfx950`（AMD GPU）上运行 DeepSeekV3，并计划自己实现。
    *   **Issue #48191**: `functionstackx` 请求 vLLM 能支持 MoRI 的统一内存后端池（UMBP）KV 缓存卸载，以实现与 SGLang 的功能对等。
    *   **PR #48173** (`Rohan138`): 针对 ROCm 平台，修复了 Block-FP8 MoE 在张量并行（TP）时，因中间大小不能被 `block_n` 整除而导致的权重加载失败问题。解决方案是向上取整填充。

### 💬 高热度讨论分析

本周期内，几个 RFC 和长生命周期 Issue 引发了较多的讨论。

1.  **Issue #48117: [RFC] 为 ROCm 建立分布式推理 CI**
    *   **核心议题**: 提议为 AMD ROCm GPU 建立专门的分布式推理 CI 管线，以持续验证分离式 P/D 和 Wide-EP 等复杂场景的稳定性和准确性。
    *   **不同观点**:
        *   **提议者 (`lcskrishna`)**: 强调当前缺乏自动化测试覆盖，导致 ROCm 上的分离式推理路径（特别是 KV 传输和 RDMA）的回归问题只能被人工、延迟发现，是项目的一大风险。提议使用 Buildkite + Slurm 作为技术栈。
        *   **社区成员 (`rehan243`)**: 支持该提议，分享了自己在其他平台遇到的类似 KV 传输瓶颈问题，并提供了关于如何使用 Slurm `salloc` 命令的建议，同时也询问了技术细节（如使用 RoCE 还是普通以太网卡）。
        *   **社区成员 (`functionstackx`)**: 询问此 CI 管线何时能包含对 AMD Pollara NICs 的支持。
    *   **争议焦点**: 主要在于**技术实施的可行性和时间表**。讨论集中在如何高效地分配 Slurm 节点、使用何种网络技术（RoCE vs. 以太网），以及对 Pollara NICs 这类特定硬件的支持优先级。
    *   **当前状态**: Open。该 RFC 已获得 AMD 团队成员的关注（`AndreasKaratzas`, `dllehr-amd` 等被 CC），是 AMD 生态建设中的一个关键讨论节点。

2.  **Issue #35169: [Bug] Step-3.5-Flash 推理时的内存访问错误（ROCM）**
    *   **核心议题**: 一个长期存在的关于在 ROCm 上运行 Step-3.5-Flash 模型时发生内存访问错误的 Bug。
    *   **不同观点**:
        *   **用户 (`ColinZ22`)**: 报告了在 ROCm 环境下的内存访问错误。
        *   **维护者 (`hongxiayang`)**: 初期建议使用 `PIECEWISE` 编译模式作为临时解决方案。
        *   **其他贡献者（`edwinlim0919`, `BowenBao` 等）**: 通过深入分析，逐步将问题定位到 Triton 注意力后端，并给出了更优的解决方案：使用 `ROCM_ATTN` 或 `ROCM_AITER_UNIFIED_ATTN` 后端，并提供了详细的性能对比数据，证明 AITER 后端性能显著优于 Triton 后端。
    *   **争议焦点**: 从“如何绕开 Bug” 演变为“选择哪个最佳实践后端”。社区经过大量测试和讨论，最终形成了使用 AITER 注意力后端作为推荐方案的共识。
    *   **当前状态**: Closed (因长时间无活动自动关闭)。尽管已被关闭，但这个长达数月的讨论过程本身极具价值，它记录了 AMD 社区如何协同诊断复杂硬件兼容性问题，并最终建立了 AITER 后端的权威地位。

3.  **PR #45149: [ROCM] 为 DSV3.2 稀疏 MLA 启用 UNIFORM_BATCH 图形捕获模式**
    *   **核心议题**: 为提升 MTP 推理性能，需在 ROCm 的稀疏 MLA 后端启用 UNIFORM_BATCH CG (Cuda Graph) 模式。
    *   **讨论过程**:
        *   **提交者 (`tvirolai-amd`)**: 提交了性能优化代码，并提供了详细的性能测试对比数据，显示在 MI350X 上启用 UBATCH 后，输出 token 吞吐量提升 5-25%（视并发度而定），而对准确率无影响。
        *   **审核者 (`AndreasKaratzas`, `divakar-amd`, `tjtanaa`)**: 提出了对测试命令、接受率的影响等具体问题的审查意见。提交者均一一回复并补充了数据。
        *   **争议焦点**: 主要围绕**测试的充分性**。审核者要求确认修改对模型的接受率（acceptance rate）没有负面影响，提交者通过对比测试证实了无变化。此外，`mergify` 机器人多次因 pre-commit 检查失败而阻止合并，暴露了自动化流程与人工审查间的协作摩擦。
    *   **当前状态**: Merged。这是一个典型的成功性能优化 PR 的生命周期：提出 -> 审查 -> 补充证据 -> 解决 CI 问题 -> 合并。

### 🛠️ 重点技术变更

1.  **PR #47404: [ROCm] 在图形重放前同步稀疏 MLA 元数据**
    *   **影响**: 解决了在 AMD ROCm AITER 稀疏 MLA 后端使用 CUDA Graph 时的一个隐蔽数据竞争问题。该 Bug 可能导致图重放时使用错误的（过期的）元数据，造成程序崩溃或输出错误。这个修复对于需要高性能（因此依赖 CUDA Graph）且使用 MLA 架构的模型（如 DeepSeek V3/4）至关重要。

2.  **Issue #48148: [RFC] 移除群组激活排序 (`actorder=group`) 支持**
    *   **影响**: 这是一个重要的架构决策。它计划分两步，首先从压缩库（compressed-tensors, llm-compressor）中移除该特性，防止新模型使用；其次是从 vLLM 推理核心中移除相关逻辑。虽然会影响一些使用旧版本 quant 的模型，但能极大简化代码，并为采用更快的量化内核（如 Humming）铺平道路，长期来看对提升推理性能是有利的。

3.  **PR #47366: [CI/Build][AMD] 修复 ROCm OOM 问题**
    *   **影响**: 修复了 AMD CI 中一个顽固的 CUDA 图形捕获 OOM 问题。核心创新在于重新启用了 ROCm 上的 CUDA 图形内存分析，并添加了内存回收等待机制。这使得系统能正确预留图形捕获所需的内存，避免了引擎初始化时的 OOM。该修复还提升了代码的可移植性，使其能适应不同的 GPU 显存大小。

4.  **PR #48179: [Bugfix] 将共享 MoE 工作区预分配至最坏情况大小**
    *   **影响**: 修复了 Fused MoE 内核中一个可能在工作区锁定后尝试扩展工作区的 Bug。该 Bug 会影响所有使用 MoE 的模型，特别是在 AMD CI 环境中有较高的复现概率。预先分配足够大的工作区防止了运行时的意外错误，是提升 MoE 模块稳定性的重要一环。

5.  **PR #48085: [Bugfix] 修复 `KVBlockZeroer` 中的竞态条件**
    *   **影响**: 修复了在 MRV2 异步调度 + 混合模型 + 推测解码组合下偶尔出现的 Crash。`KVBlockZeroer` 负责在释放 KV 缓存块时置零，其竞态条件会导致数据损坏。此修复对于保证混合模型（如 Mamba + Attention）在推测解码场景下的输出正确性至关重要。

### 💡 值得关注的问题

1.  **`Parallel_tool_calls` 接口兼容性**: Issue #48097 指出了 Responses API 中 `parallel_tool_calls` 参数处理的一个小 Bug，虽然看似微小，但反映了 API 生态兼容性中“魔鬼在细节”的特点。
2.  **DeepSeek V4 并发解析器 Bug**: Issue #48089 报告了 DeepSeek V4 在并发负载下，其推理和工具解析器会产生标签不平衡、泄露特殊 token 等严重问题。这直接影响到模型的可用性，亟待修复。
3.  **GLM 5.2 强制工具调用 Bug**: Issue #48095 报告了当设置 `tool_choice: required` 时，工具调用会失效。这暴露了 vLLM 在处理不同模型的特定约束时存在逻辑路径未覆盖的情况。
4.  **MoRI UMBP 卸载支持**: Issue #48191 请求在 vLLM 中实现对 AMD MoRI UMBP KV 缓存卸载的支持，以对标 SGLang 的功能。这反映了用户对在不同平台和框架间实现同等高级功能（如长上下文下的 KV 卸载）的强烈需求。
5.  **代码署名争议**: Issue #38942 虽然已关闭，但其提出的关于代码贡献归属的争议值得社区反思如何完善贡献者认可机制，以确保社区合作的公平性和激励机制。
6.  **Windows 和 ARM 等平台的支持**: PR #48139 (Windows port) 和 Issue #39415 (Blackwell GPU wheels) 揭示了社区对更广泛的平台支持（非 Linux x86_64）的需求，这可能是项目未来需要权衡的方向。
