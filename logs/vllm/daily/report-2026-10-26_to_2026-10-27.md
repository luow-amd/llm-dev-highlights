### 💬 高热度讨论分析

#### 1. #59478 — AITER FlyDSL INT4 QuickReduce 精度之争（8+ 评论）

- **核心议题**：是否应该用 FlyDSL 替换 INT4 QuickReduce 的 HIP 内核。
- **多方观点**：
  - **性能派（maeehart、mjkvaak-amd）**：MI325X/MI355X 上 TP8 提升 9–10%、TTFT 显著改善；"run 2 是 fluke"。
  - **质量派（amd-mghanimi、simondanielsson）**：Kimi-K3 NIAH 64k 下降 2.4pt、128k 下降 0.8pt；多次 nightly 波动显示 93.4%↔97.8%，质疑信号不稳。
  - **架构一致性派（dllehr-amd）**：主张 INT4 payload 内 **单一 QR 路径**（INT4 一律 FlyDSL，其余回退 HIP），避免"一半新一半旧"。

### 🛠️ 重点技术变更

#### 1. #63669 — MXFP4 成为 DeepSeek-V4 ROCm 默认 indexer K cache dtype（已合并，**平台级性能收益**）

- **技术要点**：DSv4 的 sparse indexer 在 gfx950 上默认采用 MXFP4 而非 FP8，压缩 token 从 132 B → 68 B。
- **影响**：DSv4-Pro TP8 MTP=2 下 **TTFT -30.7% (c1)/-13.3% (c4)/-8.5% (c16)**，TPOT -0.3%~-4.5%，KV 容量 +9.2%；GSM8K -0.16pt（近无损）。
- **边界清晰**：CUDA/XPU/CPU、DSv4.1、非 V4 模型均保持不变。
- **战略意义**：这是 vLLM 首次把"平台特定量化"设为 default，展示了 **AMD 侧有能力推动默认行为的平台差异化**。

#### 2. #48989 — AMD 上 DeepSeek-V4-Pro 的 P/D 分离 MORI IO

- **技术要点**：MoRIIOConnector 作为 KV producer/consumer，与 vLLM-router #192 联动，在 MI355X + AINIC 上实现 TP8 PD。
- **影响**：**AMD GPU 首次在生产级 P/D 分离场景中替代 NIXL/Mooncake**；MORI 作为 AMD 官方 KV 传输栈正式进入 vLLM 主线。
- **风险**：本 PR 从 7 月 17 日至今历经 5 次 rebase；MORI 版本钉在 `v1.2.1`。后续 #63674/#63854/#63855/#63856 已开始处理 MoRIIO 的健壮性问题（handshake、parking），表明该路径**仍在"打通到生产"的过渡期**。

#### 3. #59478 — AITER FlyDSL INT4 QuickReduce（已合并，**精度-性能权衡的样板**）

- **技术要点**：BF16 payload（16 字节对齐、INT4 级别）走 FlyDSL `QuickAllReduceInt4`，其余回退 HIP QR。`fuse_allreduce_rms` pass 对其 no-op 并警告一次。
- **影响**：TP8 上 AITER 测量 29–47% 内核加速；Qwen3.8-2.4T MI355X 1.044× 吞吐；但有 NIAH 长上下文精度争议。
- **后续**：**#61021（Fuse add-RMSNorm）/ #61020（MXFP4 epilogue）** 已在路上，实现"单一 QR 路径"的目标。

#### 4. #63712 — MI350P Muse Spark MonoKernel 硬编码 256 CU（Issue，**同 ISA 不同 CU 的参数化**）

- **技术要点**：MonoKernel 是 "one CTA per CU, fully co-resident" 设计，要求 `BLOCKS == num_compute_units`。MI355X 256 CU vs MI350P 128 CU 是**同一 ISA 但布局不同**的陷阱。
- **修复方向**：将 `O_ROUNDS`/`DOWN_ROUNDS`/`U_ROUNDS`/`POOL_CTAS`、split-KV、K1 GEMV 全部按 `BLOCKS` 参数化，`SUPPORTED_WIDTHS = (256, 128)`。
- **影响**：AMD GPU 家族可能存在更多"同 ISA、不同 CU 数"的 SKU；本次修复是**未来硬件适配的范式**。

#### 5. #63761 — Qwen3.5 int32 token offset 溢出（Kernel 级硬件正确性）

- **技术要点**：`_fused_qk_rmsnorm_rope_gate_kernel`（10,240 行 stride 首个越界 token 209,716）、`store_cache_checkpoints_kernel`（12,288 → 174,763）、`_fused_post_conv_kernel`（8,192 → 262,144）三处 int32 计算应转 int64。
- **影响**：`--max-num-batched-tokens ≥ 209,717` 时 Qwen3.5-9B 会在 startup profile 直接 illegal memory access——**大 batch prefill 场景隐患**。代价：1.1%–2.2% kernel 时间（8k tokens 时约 36 µs/step）。
- **跨平台**：#51406（ROCm 上为该 kernel 开绿灯）会继承该 bug 与本修复。

#### 6. #63256 — RL 权重加载的 ParamMeta 所有权声明（已合并，**架构级简化**）

- **技术要点**：`ParamMeta` 上声明 `owners` / `mesh_shape` / `placements`，引擎在 `trainer_init` 即据此规划，不再运行时交换；`iter_full()` 与 `iter_local()` 二择一。
- **影响**：NCCL broadcast / IPC / Sharded RDT / NCCL M2N 各自**在 trainer_init 时 fail-fast** 拒绝不支持布局；Pipeline-parallel trainer 场景可在 NCCL 上实现（待 #62557 完成）。
- **意义**：为 RL fine-tuning 场景大规模集群的正确性提供了静态契约。
