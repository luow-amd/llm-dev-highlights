### 🎯 AMD/ROCm 生态相关动态

**本周期是 AMD 生态的高光时刻**，共涉及 15+ 个 PR/Issue，覆盖 AITER 内核、Kimi-K3 适配、Quark 量化、CI 修复与设备兼容性四个维度。以下按类别详细展开：

#### 1. Kimi-K3 on AMD：从不可用到 23 倍提速

- **[#50817] Enable AITER MXFP4 MoE on gfx942 and optimize tile configs for MI325X**（用户 `seanfilimon`，标签: performance/rocm/quantization/kimi/k3）  
  这是本周期最具影响力的 AMD 相关 PR。它解除了 Kimi-K3 在 MI325X (gfx942/CDNA3) 上的三个阻塞点：MLA decode 的 `AssertionError`、MoE 回退到 dequantise-to-BF16 的慢速路径、以及 AITER MoE tile 形状错误地按 CDNA4 配置。实测数据：**解码 4.27 → 99.67 tok/s（23x），prefill 吞吐 3,522 → 6,537 tok/s（1.9x）**。该 PR 还附带了一个预测性分析——根据 HBM 流量预估 4.4 tok/s，与实际测量 4.27 tok/s 高度吻合，体现了作者对内存带宽瓶颈的深刻理解。目前 PR 处于 need-rebase 状态，社区反响热烈（6 条评论，含多位维护者点赞）。
  
- **[#50582] [ROCm][Kimi-K3] AITER MoE 环境变量清理**（用户 `hongxiayang`，已合并）  
  将 `AITER_SITUV2_A8W4` 重命名为 vLLM 规范的 `VLLM_ROCM_USE_AITER_MOE_SITUV2_A8W4`，并缓存到 `rocm_aiter_ops` 中避免每次 forward 读取环境变量。同时将 K3 SiTU 的“跳过 round-up”逻辑从 MoE 方法移入 oracle。该 PR 还移除了用户侧需要手动设置 `AITER_BF16_FP8_MOE_BOUND=0` 的要求，改为 vLLM 内部自行设置。

- **[#50813] [ROCm][Quark] 为 K3 启用 opt-in SiTUv2 A8W4 routed MoE**（用户 `LiuYinfeng01`）  
  这是 **Quark 生态** 的重要 PR：允许 K3 Quark `w_mxfp4_a_mxfp4` checkpoint 走 AITER SiTUv2 A8W4 路径（激活从 MXFP4 动态量化到 FP8）。该 PR 是 opt-in 设计，需显式设置 `AITER_SITUV2_A8W4=1` 且设备为 gfx950 才生效，默认路径不变。同时保留了 K3 的 TP8 原生 intermediate size 384（不做 512 round-up），避免权重膨胀和 OOM。

- **[#50847] [ROCm] 直接返回 Kimi-K3 MLA 输出**（用户 `LiuYinfeng01`）  
  消除 24 层 MLA 中每层 `num_tokens * 7168 * 2` 字节的冗余中间拷贝。确定性收益是减少分配/拷贝，但短期基准测试显示中位数 TPOT 差异在噪声范围内。

- **[#50855] [ROCm] 跳过全fresh Kimi-K3 KDA 状态拷贝**（用户 `LiuYinfeng01`）  
  在全 fresh prefill 批次中，从 CPU 元数据直接判断可跳过 dense gather、zero-fill、final-state 分配和 scatter。TP8 下每层每请求状态 0.75 MiB，batch=128 时原来需物化 96 MiB 的零初始状态和 96 MiB 最终状态张量。

- **[#50928] Kimi-K3: 按有效 MoE TP 大小分片 intermediate**（用户 `hongyeon-yu`）  
  该 PR 修复了一个内存浪费问题：padding 计算错误地使用了 tensor-parallel world size，而实际上 MoE 是按 `dp_size * pcp_size * tp_size` 分片的。在 TP16 下浪费 **+7 GiB/rank**，TP32 下浪费 **+35 GiB/rank**。作者明确标注 ROCm 路径（AITER 派生 pad width）有潜在越界风险，但无 MI300 实机验证，属代码路径论证。

### 🔥 热门话题与趋势分析

#### 1. Kimi-K3：vLLM 当前最热门的“压力测试模型”
Kimi-K3 在本周期出现频率极高（新增 5+ 相关 PR/Issue），且横跨 NVIDIA（TP8/PP3/EP/FlashInfer）和 AMD（MI325X/MI355X/AITER）平台。高频问题包括：KDA 预填充崩溃、MLA decode 内存访问错误、MoE 分片与显存管理、共享专家复制开销。**这反映了前沿 MoE+SSM 混合架构对推理引擎的全面挑战**，vLLM 正在经历“用最强模型打磨平台能力”的阶段。

#### 2. Speculative Decoding 的工程化阵痛
DSpark 相关 issue 集中爆发：
- #50877：FlashInfer MNNVL allreduce buffer 不足（NVLink-only 路径）
- #50924：guided-decoding 时 grammar bitmask 宽度不匹配（4040 vs 4041）导致 EngineCore 崩溃
- #50953：LMCache + DSpark 在 ROCm 上的 CUDA 依赖污染
- #50932：MNNVL 3-buffer 旋转导致的 workspace 预算计算错误

这些问题的共性：**投机解码引入了额外的张量/通信路径，在特定后端（FlashInfer、AITER、NCCL）的组合下暴露出各自假设的边界条件**。vLLM 对 DSpark 的适配已从“功能可用”进入“边界条件收敛”阶段。

#### 3. AITER 成为 AMD 生态的“战斗前线”
本周期所有 AMD 性能相关 PR 都直接或间接依赖 AITER（AMD 的 Triton 内核库）。AITER 版本升级（0.1.16.post5 → 0.1.19）引发的 `memory access fault`（#50859）就是例证。**AMD 在 vLLM 中的策略已经明确：通过 AITER 提供高性能内核，vLLM 负责正确的门控与 dispatch**。两个仓库的联动（vLLM PR + AITER PR 协同修复）也展示了 AMD 的全栈投入。

#### 4. 设备能力检测的规范化
多个 PR（#50417 protocol 检测、#50951 设备名别名、#50817 arch_only decorator）都指向同一个主题：**平台能力检测从散落的 `on_xxx()` 硬编码走向统一的、显式的 capability 描述**。这对多平台（CUDA/ROCm/XPU/CPU）支持的可维护性至关重要。

#### 5. 多模态可观测性与资源控制
- #50824/#50875（Prometheus 多模态预处理指标）——媒体下载/解码延迟对 TTFT 的可观测性诉求。
- #50819（Gemma4 视频 token 预算）——小显存设备上的 encoder cache profiling 启动失败。
- #50860（resumable session 内存泄漏）——多模态会话场景的 unbounded host memory 增长。
  
  这些 PR/Issue 表明多模态推理正在从“能跑”走向“能运维”。

### 🛠️ 重点技术变更

#### 1. [#50817] AITER MXFP4 MoE for Kimi-K3 on MI325X（23x 解码加速）
**技术要点**：
- 修复 MLA decode 的 `AssertionError`（针对 `n_local_heads == 0` 场景）
- 将散落的 `on_gfx1250()` 检查收敛为 `use_aiter_mxfp4_triton_moe()` 单一谓词
- 拆分 CK-only 的 de-interleave 逻辑（Triton 路径直接消费 checkpoint 的 interleaved 布局，因为应用 de-interleave 后 cosine 相似度仅 0.034）
- 基于 HBM 流量估算性能（预测 4.4 tok/s vs 实测 4.27）验证了瓶颈模型的准确性

**影响**：这是 AMD 平台首次能以接近实用的速度运行 2.75T 参数级 MXFP4 模型（99.67 tok/s TP8）。它证明了 AITER Triton MoE + MXFP4 是 AMD 高端计算卡的有效组合。

#### 2. [#50859] AITER Triton MoE routing 的 NaN/Inf 处理 Hotfix
**技术要点**：
- 根因：AITER 0.1.19 中 `PR#4198` 的改动导致 routing kernel 错误处理含 `inf/-inf/nan` 的行。当 vLLM 使用 HIP Graph 且 `tokens_unpadded=7, tokens_padded=8` 时，最后一行是虚拟数据，包含未初始化值。
- vLLM 侧修复 + 上游 AITER #4530 根治。

**影响**：此 bug 的教训是“**图形重放 + padding 数据 + 内核中的 NaN 处理假设**” 三个因素的组合。对任何使用 CUDA Graph 的推理引擎都有参考价值——padding 行的数据并非总是无害的。

#### 3. [#50928] Kimi-K3 MoE intermediate 按有效 TP 分片
**技术要点**：
- 根因：`KimiMoE` 的 padding 使用了 tensor-parallel world size，但 `FusedMoEParallelConfig.make()` 实际按 `dp_size * pcp_size * tp_size` 分片，导致 shard 宽度计算错误。
- 在 EP 模式下，MoE `tp_size` 直接坍缩为 1，导致每个 rank 分配完整 padding 而不是 shard。
- 影响：TP16 下每个 rank 浪费 +7 GiB，TP32 +35 GiB。

**影响**：这是对**并行维度理解**的深度修正。PR 还标注了 ROCm 路径上的潜在 AITER pad width 越界风险（3904 vs 1024），为 AMD 侧后续修复提供了线索。

#### 4. [#43615] AITER/FP8 支持 gfx120x
**技术要点**：
- 引入 `@arch_only(*preds)` 装饰器，将 MI3xx-only 的 CK/ASM 内核与 gfx12x 的 Triton 内核分离。
- `AiterFp8BlockScaledMMKernel` 在 gfx12 上支持 Triton linear，但 `can_implement()` 会拒绝 untuned (N,K) 形状，自动 fallback 到 `TritonFp8BlockScaledMMKernel`。
- gfx12 默认关闭 AITER RMSNorm（内核在 RDNA4 上损坏），MI3xx 默认保持开启。

**影响**：这是 AMD 消费级显卡（RDNA4）获得高性能内核支持的关键一步。此类平台差异化门控（而非一刀切启用/禁用）是 vLLM 平台抽象的正确演进方向。

#### 5. [#50911] TokenSpeed MLA 支持 DSpark 非因果多 token
**技术要点**：
- DSpark draft 模型一次 forward 生成多个非因果位置，TokenSpeed 内核已支持 `causal_mask`，但 vLLM 未透传该元数据。
- PR 将 `attn_metadata.causal` 透传给 `tokenspeed_mla_decode`，并广告非因果多 token 能力。
- 性能：在 B200 上并发 64 时从 2.81 ms → 386 us（**7.3 倍加速**），端到端 Kimi-K3 TP8 测试中 aggregate output tok/s 从 1369 → 2350（71% 提升）。

**影响**：这是 NVIDIA 侧投机解码性能优化的代表作，展示了“元数据透传”这类小改动可能带来数量级收益。它与 AMD 侧的 AITER 优化形成呼应——**投机解码的 draft 阶段是当前吞吐瓶颈**。

### 💡 值得关注的问题

5. **SM120 的 DeepGEMM 自动禁用不一致**（#50829/#50893）：`should_auto_disable_deep_gemm()` 在 dense block-FP8 和 MoE 路径的行为不一致，导致 Qwen3.6-35B-A3B-FP8 在 Blackwell 上错误使用 DeepGEMM。这类“分散判断”是 vLLM 中平台能力检测规范化的典型反面教材。
