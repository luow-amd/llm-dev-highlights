## 💬 高热度讨论分析

### 1️⃣ #66784 — Qwen4Exp HyperConnection padding reload 确定性（8+ 条评论）

- **核心议题**：修复 `begin_direct_reload` 后 padding 行残留非确定性数据；作者希望以最短路径修复。
- **观点分歧**：
  - **hao-aaron**：现有修复"可用但可以更简单"——`begin_direct_reload` 整体 zero 参数，不需要专门 zero padding rows，也不需要记录 row range。
  - **gau-nernst**：质疑为何不将 `PaddedMergedColumnParallelLinear` 提升到 `linear.py` 统一，其他模型也有类似 padding。
  - **hao-aaron 二次回应**：`layerwise` reload 依赖 `weight_loader_numel`，目前无法简单共享，**建议等 direct reload 成为默认后再统一**。
- **结论**：按 hao-aaron 建议保持 PR 范围限定在 Qwen4Exp；后续会有独立 PR 覆盖其他 padding。

### 2️⃣ #59116 — SMG 与 MoRI-IO PD Disaggregation（7 条，已关闭）

- **核心议题**：ROCm PD disaggregation 使用 SMG 路由时，DP attention / 异构 TP 场景失败。
- **多方观点**：
  - **functionstackx**：DP attention 和异构 TP 必须可用，PD 的 Pareto 特性要求 prefill 少并行 / decode 多并行。
  - **chunfangamd**：连续三轮给出实测证据（两节点 MI355X、DeepSeek-R1-0528 FP8、MoRI v1.2.3），最终交付 **"小 prefill TP + 大 decode TP + DP attention"** 组合在 SMG 1.13.0 上 12 请求全部 200 OK，decode 端 38,384 external KV tokens 100% 匹配。
- **争议焦点**：问题归属 SMG 侧 vs vLLM 侧，最终拆分为 SMG#2798（DP 注册）、vLLM#61726（WRITE head 双向映射）等多处协同修复。
- **结论**：关闭，但仍有 "SMG 版本滞后于 main" 的隐患，hongxiayang 建议后续在 smg-project 提 issue。

### 3️⃣ #61498 — Kimi-K3 MI355X MonoKernel vanilla decode（6+ 条）

- **核心议题**：能否让不使用 speculative decoding 的 vanilla decode 也享受 monokernel 性能。
- **观点**：
  - **jamesETsmith（作者）** 主动给出 GSM8K A/B 结果（96.21→96.74）、多种并发吞吐数据。
  - **Fangzhou-Ai（AMD）** 质疑："vanilla decoding 的 use case 是什么？"
  - 作者回复：无 MTP/DSpark 的普通推理同样需要低 decode 延迟，MI355X 在 Kimi-K3 场景需要提供完整的 decode 路径覆盖。
- **结论**：合并。**结论是 vanilla decode 在生产环境仍有广泛用途**，不是"只服务 spec decode 用户的附赠品"。

### 4️⃣ #66792 — Exact Triton top-k/top-p kernel（3 条，技术含量最高的争论）

- **核心议题**：作者提交新的精确 top-k/top-p Triton kernel 后，与已有 #64130（MI325X 上的 split top-k 小批路径）如何取舍。
- **多方观点**：
  - **phambinhfin**：在 MI325X（gfx942）上实测新 kernel 在 batch=1 时 39.4µs，**比 #64130 的 24.2µs 慢**，但 batch≥128 时反超；建议作者**引入 #64130 的小批 split 路径**。
  - **tomasruizt（作者）**：接受"单一实现更易维护"，主动请求 phambinhfin 提供 patch；同时开启 gfx942 支持。
  - **DimensionSTP**：指出 #60104 的边界回归在新 kernel 上通过，主分支仍有 keep-all bug，希望作者**顺便 review #60104**。
- **争议焦点**：单实现 vs 多路径混合、小 batch 场景的实测差距（24 vs 39 µs）。
- **当前状态**：open，作者正在合并 #64130 的测试用例与小批优化。

### 5️⃣ #66775 — QuickReduce reduce-scatterv 技术细节（技术审查中）

- **核心议题**：DP MoE combine 用 reduce-scatterv 替代 all-reduce slice 的适用边界。
- **观点**：作者（cpersson-amd）给出完整对比表（INT8/INT6/INT4 编解码、±333 行不均匀输入 <5% 开销、nrmse 0.086 vs 0.107）；但**未讨论与当前默认 allgather_reducescatter 后端的动态切换策略**，这可能是 review 中会追问的方向。

## 🛠️ 重点技术变更

### 1. **#66862 [Core][Rust] Rust 引擎核心（WoosukKwon，Draft）**
- 覆盖 block hashing、KV cache manager、scheduler、NIXL/Mooncake 的 scheduler 半段；全部 bitwise 对齐 Python 实现，可通过 `VLLM_USE_RUST_CORE=1` 切换。
- **影响**：如果落地，意味着 vLLM 可以在高 QPS 场景将 CPU 开销降低至 ~1/5，**这是 vLLM V1 架构之后最重要的内部重构方向之一**。值得重点跟踪。

### 2. **#61498 [ROCm][Perf] Kimi-K3 MI355X MonoKernel vanilla decode**
- 将 Kimi-K3 的 monokernel 从 only-spec-decode 扩展到 vanilla decode。**c1 吞吐 +46.2%**，GSM8K 精度严格/宽松均略有提升。
- **影响**：MI355X 在 80K 输入 Kimi-K3 场景下与 NVIDIA GB300 的差距被显著压缩，是 ROCm 生产可用性的关键里程碑。

### 3. **#66775 / #66771 / #66842 — DSV4.1 DeepSeek Flash 在 AMD 上的通信/并行优化三件套**
- reduce-scatterv（#66775）+ 本地 MXFP8 量化（#66771）+ PCP（#66842）：分别对应 **MoE combine、AllGather 前量化、prefill 激活切分**。
- **影响**：在 DP4 / TP2+PCP2 等配置下叠加可达 **-15% 以上 prefill 时间**，是 AMD 在 DeepSeek V4.1 大规模 serving 上的经济性保障。

### 4. **#66844 / #66938 — Mamba Hybrid 前缀缓存的两个里程碑**
- #66844 RFC：引入 FlashState 论文的 exact-end states + whole-state eviction；#66938 落地 mid-block resume。
- **影响**：直接作用于 Kimi-K3.1、GLM-5.3-Flash 等 hybrid attention 模型；**agent traffic（多轮对话 + 长工具调用）场景下可消除高达 1,796 token 的重复 prefill**。

### 5. **#66885 / #66886 — 两个正确性/安全问题（Yunzez）**
- #66885：**跨租户 vision-LoRA 缓存投毒**——caller-controlled UUID 可伪造 LoRA tenant 的 encoder cache key，`EncoderCacheManager` 直接命中。
- #66886：`MultiModuleMTPSpeculator` 复用 slot 时未 reset，**请求 B 的 draft model 会在 A 的输入上运行**（带完整 PoC）。
- **影响**：这两个问题不涉及远程代码执行，但在多租户/多模态部署下会造成**输出污染**；#66885 尤其应在开启 `enable_tower_connector_lora` 前修复。建议打上 security 相关 label。
