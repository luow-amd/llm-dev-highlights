#### 讨论 2：`#55132 [Bug][ROCm] Sparse-MLA indexer 预留 32 GiB workspace`（Issue，open）

**发起人 stefanskiasan**的完整分析包含了尝试修复后的失败复现：

- 核心发现：按 `max_num_batched_tokens`（8192）预留 decode-logits workspace，在 1M context 下为每个 token 预留一整行 fp32——而 decode 实际只需 `max_num_seqs × (投机+1) = 256` 行。profling 后 `WorkspaceManager.lock()` 冻结大小，32 GiB 从 KV cache 池中永久扣减。
- **矛盾焦点**：作者按 decode 上界修改后，KV cache 增加了 21.7%（2,799,936 → 3,407,312 tokens），但随后每次启动都在 graph capture 后的第一个 decode 步骤死于 GPU memory fault。**过度预留反而规避了某种越界写**——说明 AITER 的 `rocm_fp8_paged_mqa_logits` 或上游 indexer 存在依赖大 workspace 掩盖的实际越界。
- 截止窗口结束无维护者回应修复方案，需要后续跟踪。

**价值**：该讨论是一份高质量的“root cause + 修复尝试 + 隐藏假设挖掘”的档案，对 AITER sparse-MLA 的正确性审计有直接帮助。

### 🔥 热门话题与趋势分析

**1. GLM-5.3-Flash 成为当日绝对焦点**（3 个新增 Issue、4+ 个新增/合并 PR 关联，且 #53906 刚刚合入）。主要问题集中在 Sparse-MLA/kpool indexer 在 MTP decode 下的越界、混合 block size 的虚拟分页、NVIDIA/AMD kpool kernel 的一致性等问题。GLM-5.3-Flash 属于新型混合 KDA+MLA 架构，其 KV cache 呈现 group 混合、page 大小不均的特征，正在推动 vLLM KV cache 管理层向更通用方向演进（如 #55219 的 generic packed KV layout）。

**2. MRV2（Model Runner V2）迁移的阵痛**。表现于三个方向：**（a）** CUDA graph capture 策略与 MRV2 不兼容导致的性能回退（#55139 PP performance drop、#55095 graph fallback for noncompiled models）；**（b）** MRV2 特性补齐——DCP metadata 初始化、streamed PP transport、GDN hybrid decode path 优化（#55260）；**（c）** 工作负载从 V1 向 V2 切换后，许多此前隐藏的路径假设被暴露，如 #55139 中 MRV2 下默认启用导致的性能回退，以及 #55188 DCP error message platform-aware 修复。MRV2 仍是 vLLM 最重要的主航道。

**3. 稀疏注意力（Sparse MLA）从“单个模型特性”变成“跨模型基础设施”**。DSv4、GLM-5.3、Qwen3-Next、MiniMax-M3 全部使用不同变体的稀疏 indexer。本日的多个 PR（#55219、#55239、#55201、#55264、#55184）反映了使 sparse-MLA kernel 通用化的努力——包括 kpool 索引校验、FlashInfer SM120 calibrate、FP8 E4M3 可移植转换。vLLM 正在从“为 DS 特调”走向“为稀疏注意力建通用层”。

**4. 量化与精度仍是高争议区**。AITER MXFP4 对齐值 256→128 的更改需要上游 aiter 修复否则会静默损坏输出；AWQ 的 ROCm 路由修改成功提升 decode 但拖累 prefill；fp8 KV cache 在 hybrid 模型上无法生效（#55196）。跨硬件、跨量化格式的一致性保证成为生产级推理的长期挑战。另一个值得注意的议题是 compute graph 的数值可复现性：persistent_topk 的不确定性（#55122）和 CUDA graph 与 eager 输出不一致（#55238）正在获得更高的优先级。

**5. RFC 型 Issue 显示出社区对**“部署可观测/可运维”**的诉求上升**：#55259 提出将 forward-path 自检集成到 vLLM 核心而非外部（NVIDIA Dynamo 的 out-of-tree 实现）；#50179（P2P 控制面）从内核优化转向系统级可调度性。


### 🛠️ 重点技术变更

**1. `#53906 [Model] add GLM-5.3-Flash support`（已合并）— 新模型 day-0 支持范式演进**

GLM-5.3-Flash 的合入本身只是开始，其后续问题暴露了复杂混合架构对 KV cache 层设计的压力。它使用 hybrid KDA + MLA + kpool indexer，引入 `block_size=1152` 的混合分页和 288-entry 非对齐存储块，直接暴露了#55280（kpool 32-page split 越界）、#55219（generic packed KV layout 替换模型专用分组）等深层架构问题。该 PR 也创下了 ROCm 版本支持的大讨论先例（gfx942/gfx950 的镜像覆盖问题）。

**2. `#54845 [ROCm][Perf] Add low-M FP32 router GEMM for gfx950`（已合并）— AMD 低延迟 router 优化**

MiniMax-M3 的 router 层要求 FP32 权重 + FP32 accumulation，使用 `torch.linear` 在低 M（1-32）时 launch 开销占比过高。该 PR 新增 Triton kernel 将 M≤32 的 router GEMM 延迟降低 50% 左右。评审质量高：CI 覆盖补齐、M 改 runtime 参数避免 33 次重编译、ROCm 模块命名规范化、消除重复校验、删掉恒为 1 的 `waves_per_eu`。先合入此 PR 后，当日 #55235 继续在 MiniMax-M3 decode selector 上加倍下注（-27-29%），形成同一模型多 PR 协同的串行优化链。

**3. 已合并的 GLM/DCP 相关修复 `#54908 [Bugfix][DCP] Materialize prefill keys on non-owner ranks`**

修复了 GLM-5.3 密集 prefill 在 DCP 下消费未初始化 K 行（#54907）的关键 memory-safety bug：非 owner rank 在 DCP 下仅因本地 slot 为负即提前返回，导致 `kv_c_out`/`k_pe_out` 未被写入。修复通过将 **materialization 与 cache ownership 分离**，使 pid 1 即使不拥有缓存也照常产出 K 行。这类 DCP 下的按 rank 分片 + 归一化/RoPE 融合 kernel 语义问题在多个模型中反复出现（#50095 GLM-5.3、#54907），预示着未来 kernel 开发中需要统一的 DCP-aware 契约。

**4. `#54651 [Core] Triton split-row top-p sampling`（已合并）**

将 top-p 过滤的 Triton kernel 扩展到 batch 0~64 全域（移除 `batch >= 8` 限制），并修复了 mixed-batch 中 grammar-constrained 行的 top-p 过滤正确性问题。更底层的是：论文式地揭示了**跨 launch 的 top-p 不稳定性源于多 token 共享采样边界时的 GPU reduction 顺序差异**，并提出了确定的边界处理策略。该 PR 对采样质量、batch 不变性（配合 #55249）和长尾延迟均有改善，是同日合入的影响力最大的运行时修复之一。

**5. `#55099 [Hardware][AMD][Bugfix] Relocate ROCR/CLR build + rocprofiler improvements`（AMD CI 基础设施重构）**

将 ROCR+CLR 从 base stage 的依赖项移到独立 stage，使得未来 ROCR/CLR 更新不再强制重建 vLLM 全镜像；同时以 7.2.4 特定 backport 解决 CI teardown 中偶发的 hang 问题（对应 #51174/#51173 revert）。此类基建优化虽然不可见，但对 AMD CI 的交付效率有直接贡献，也是 AMD 平台与 NVIDIA 平台 CI 并行度拉平的关键举措。

### 💡 值得关注的问题

1. **`#55132`（ROCm Sparse-MLA workspace 32 GiB 超量预留）**：修复尝试陷入“修小则崩、不修则浪费 21% KV cache”的两难，暗示 AITER 路径存在被大 workspace 掩盖的越界写。该问题不解决，1M context 模型在 ROCm 上的可用 KV cache 将始终被显著压缩，且 32 GiB 的浪费会让 MI355X 部署的显存经济学进一步恶化。此 issue 目前仅有一条 bot 路由记录，需要 ROCm 相关维护者尽快跟进。

2. **`#53906` 合入后 GLM-5.3-Flash 在 ROCm 上的可服务性**端口分叉：#55239 修复了 gfx942 的 MTP 路径，但 #55280 的 kpool 32-page split 问题仍开放；ROCm 镜像缺少 gfx942 目标的问题直接违反了用户预期——在 `vllm/vllm-openai-rocm` 镜像名之下实际只有 gfx950 可用，当前社区印象中“ROCm 约等于 gfx950”的说法需要纠正或等待新的双目标镜像发布。

3. **`#55170` SM120/121 NVFP4 W4A16 vs W4A4 kernel 选择缺陷**：当前静态 kernel selection 让 cuTe-DSL 的 W4A16 kernel 在支持 FP4 activation 的 GPU 上被优先选择，白白浪费 FP4 tensor core。该 PR 提出了静态选择的改进方向，但真正完善的混合调度需要 #54614 的 per-forward 动态选择。

4. **MRV2 量化/图捕获的组合爆炸风险**：#55095 的复杂度侧面反映了 MRV2 × CUDA graph capture × 平台条件 × 模型架构的矩阵已经大到难以靠全局策略覆盖，作者以大量 fallback 条件（“default unset graph modes to FULL_DECODE_ONLY at O2/O3 and NONE at O0/O1”、“gfx950 DSv4 MRV2 default to NONE”）应对——这种 patch-on-patch 的堆叠模式是否可持续，值得关注。

5. **CDNA 与 Hopper/Blackwell 之外的老架构受支持程度偏低**（见 #55184 与 #55173 对 SM80/SM86 的关注）：SM80 相关支持修复的 PR 合并，将 DeepSeek V4 的 FP8 E4M3 转换通过共享 helper 统一化；能够看出 NVIDIA 老架构也不是总能得到完整支持，这些修正整体上提高了 kernel 的可移植性。
