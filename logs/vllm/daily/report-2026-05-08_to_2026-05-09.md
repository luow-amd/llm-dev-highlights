### 🎯 AMD/ROCm 生态相关动态

本周期 AMD 相关活动非常活跃，是代码合并和提交的主流之一，主要集中在性能优化、Bug 修复和 CI 兼容性上。

**已合并 PR：**
1.  **#40711 [Aiter][ROCm] gdn_linear_attn kernel fusion** (by `tpopp`): 一个重要的 ROCm 性能优化。该 PR 通过融合 GDN（Gated Delta Network）中的多个 Triton 内核，显著降低了解码步骤中的内核启动开销（20-26us/层），将项目级的 TPOT（每个输出token的时间）提升了 5-8%。
2.  **#39280 [ROCm][Perf] Add Fused Shared Expert (FSE) support for Qwen3-Next** (by `nholmber`): 针对 Qwen3-Next 模型的性能优化。该 PR 将共享专家（Shared Expert）的计算融合到 AITER MoE 内核中，消除了对共享专家的独立前向传递，大幅提升了 MI355X 上的解码吞吐量。
3.  **#41634 [CI][ROCm] Ship RIXL with `vllm/vllm-openai-rocm`** (by `simondanielsson`): 修复了 RIXL（AMD的RDMA库）在官方 ROCm Docker 镜像中缺失的问题。现在 `vllm-openai-rocm` 镜像内置了 RIXL，使得 AMD 平台能够使用 NixlConnector 进行 PD（Prefill/Decode）分离部署，功能上与 NVIDIA 平台对齐。
4.  **#41895 [Bugfix] Fix XPU/ROCm compatibility in spawn_new_process_for_each_test** (by `dzhengAP`): 修复了 ROCm/XPU 平台上由于 `fork` 和 `spawn` 进程模型不兼容导致的 CI 测试失败。
5.  **#41802 [ROCm] use HIP_VERSION variables...** (by `pmaybank`): 修复了使用最新 ROCm 7.13 版本时，因 `atomicAdd` 重复定义导致的编译错误，避免了构建失败。

**新增 Part/Issues：**
1.  **#42123 [ROCm][Attention] Use AITER as fallback for flash_attn_varlen_func** (by `TheTom`): 这是在 ROCm 平台上的一项关键改进。当上游的 `flash_attn` 库不可用时（例如在某些AMD云镜像上），vLLM 将回退到使用已集成的 AITER 的 `flash_attn_varlen_func` 作为后备方案。这避免了因回退到 O(N²) 的 PyTorch 原生注意力实现而导致长上下文 OOM 的问题，增强了 ROCm 平台的鲁棒性。
2.  **#42129 [Inductor] Fast-path Inductor fallback for vllm::*/vllm_aiter::* custom ops** (by `okorzh-amd`): 这个 PR 解决了在大量使用自定义算子（如 `vllm::all_reduce`）的模型上，TorchDynamo 的 Inductor 后端在进行图捕获时，由于尝试序列化深层的 IR 图而导致的性能回退问题。通过将这些算子的回退路径标记为“快速路径”，显著减少了 `torch.compile` 的编译时间，避免了挂起。这对于在 AMD 平台上运行如 Kimi-K2.6 这样的大型模型有重要意义。
3.  **#42072 [ROCm] Restore fast top_k_per_row kernels for sparse MLA when topk_tokens=2048** (by `frida-andersson`): 恢复了在 MI355X 上用于稀疏 MLA（Multi-head Latent Attention）的专用 C++ 内核，这能显著提升 DeepSeek-V3.2 模型的 TPOT 性能（从~26ms 恢复到~18ms）。
4.  **#42061 [ROCm][Bugfix] Re-tag AITER MoE weights as preshuffled after replace_parameter** (by `maeehart`): 这是一个重要的 Bug 修复。当使用 AITER 的 MoE 后端时，权重 shuffle 操作后的 `is_shuffled` 属性未能正确传递，导致 AITER 运行时选择了非优化的内核路径。该 PR 修复了此问题，确保了 AITER 的优化内核被正确调用。
5.  **#42062 [ROCm] Enable gluon paged MQA logits on gfx950 (MI355X)** (by `frida-andersson`): 修复了 MI355X（gfx950）被错误路由到慢速两阶段内核路径的 Bug，使其能够使用 MI300X 上的单核 gluon 路径，显著提升了相关性能。
6.  **#42098 Use `hidden_pad` and `intermediate_pad` from vLLM #34301** (by `rebklee`): 优化了 AITER MoE 内核的 padding 策略，在 MI355X 上为 GPT-OSS-120B 模型带来了约 8% 的吞吐量提升。
7.  **#42088 [aiter] Qwen3Next shared expert fusion improvements** (by `tpopp`): 这是一个与 #39280 相关的后续改进请求，旨在继续优化 Qwen3-Next 的融合共享专家性能。
8.  **#42040 [Bugfix] Fix LOGITPROC_SOURCE_ENTRYPOINT test to use spawn-compatible dist-info registration for XPU/ROCm** (by `dzhengAP`): 修复了在 XPU/ROCm 平台上由于使用不兼容的 `fork` 进程模型，导致自定义 logits 处理器的测试失败。该 PR 确保了 CI 在这些平台上的正确性。
9.  **#42104 [CI] set max transformers version for skywork model** (by `divakar-amd`): 修复了因 Transformer 5.x API 变更导致的 Skywork 模型兼容性问题。

### 💬 高热度讨论分析

本周期高热度讨论主要集中在 Gemma 4 的 Bug 和 MTP 相关的兼容性问题上。

**1. Issue #42085: GPU block pool exhaustion with `SimpleCPUOffloadConnector` + Hybrid KV Cache Manager**
*   **核心议题**: 在使用 `SimpleCPUOffloadConnector` 和混合KV缓存管理器时，第二个长上下文请求会导致 GPU 块池耗尽和断言错误。
*   **观点与立场**: 用户 `v1b3coder` 详细描述了问题的复现步骤和输出日志。这是一个明确的功能Bug报告。
*   **状态**: 未关闭，待开发者处理。

**2. PR #42060: `runai_streamer` + MTP drafter fails to load weights**
*   **核心议题**: 当使用 `runai_streamer`（一种从S3等源流式加载模型的方式）与 MTP 推测解码一起使用时，引擎会报错，因为 draft 模型试图从本地缓存路径而非原始 S3 URL 加载权重。
*   **不同参与者的观点**:
    *   **`wizche` (问题报告者)**: 描述了详细的复现步骤和对比实验（不带MTP是好的，带MTP就会坏）。
    *   **`SoluMilken` (贡献者)**: 迅速响应并定位了问题（在 `vllm/config/speculative.py` 中），随后立即创建了修复 PR #42079。这个流程显示了高效的社区协作。
    *   **`wizche`**: 对快速响应表示感谢，并等待 Docker 镜像构建后测试。
*   **讨论焦点**: 问题的根源在于 MTP 的配置文件错误地使用了本地缓存路径而非原始S3 URL，偏离了 `runai_streamer` 的工作模式。
*   **当前状态**: 修复 PR 已创建。

**3. Issue #42096: Qwen3-VL Performance regression at upstream main**
*   **核心议题**: 报告了在 GB300 硬件上，最新的 vLLM nightly 版本相比一个多月前的版本，在服务 Qwen3-VL 模型时出现了显著的性能回退（TTFT P99 延迟增加了 55-67%）。
*   **不同参与者的观点**:
    *   **`Victor49152` (问题报告者)**: 通过详细的基准测试数据精确地量化了回退（TTFT, TPOT, LAT），并列出了三个浅层问题。
    *   **`wangshangsam` (维护者)**: 迅速指派了团队成员（`soodoshll`, `BolinSNLHM`）进行跟进，并询问了具体的测量方法。
    *   **`Victor49152`**: 提供了测量方法（MLPerf Endpoints），并分享了一个关于 `flashinfer_autotune` 问题的临时解决方案（升级 flashinfer 版本）。这体现了用户社区的自助能力和贡献。
    *   **`ywang96` (维护者)**: 要求在一个更简单的配置（不涉及 flashinfer/cuda graph）下进行测试，以帮助隔离问题根源。
*   **讨论焦点**: 精确测量并隔离性能回退的来源，并识别出与 `flashinfer_autotune` 相关的次要问题。
*   **当前状态**: 分配了负责人，正在积极排查中。

**4. Issue #42109: RFC - Disaggregated Speculative Decoding with Standalone Parallel Draft Model**
*   **核心议题**: 提出了一种新颖的分离式推测解码（Disagg-SD）架构，将 draft 模型部署在独立的 GPU 上，通过网络通信，以实现 draft 和 target 计算的完全重叠，从而解决现有方案中 draft 模型“窃取”target 计算的瓶颈。
*   **不同参与者的观点**: 目前只有一个长篇的RFC帖子，详细阐述了动机、设计（ZMQ通信、推测缓存）、和预计算结果。尚无其他社区成员的评论。该 RFC 提供了一个对 spec-decode 领域有深远影响的新思路。
*   **讨论焦点**: 这个RFC本身尚未引发讨论，但其提出的架构很有启发性，很可能会引起社区的广泛关注。
*   **当前状态**: 新提案，待社区讨论。

### 🔥 热门话题与趋势分析

1.  **Gemma 4 的“阵痛期”**：本周新增的 Issue 中有大量与 Gemma 4 模型相关的问题，涵盖了 **推理解析器（Reasoning Parser）** 导致的分隔符泄露 (#39885, #42103, #42105)、**工具调用（Tool Calling）** 中的浮点数值错误 (#42047)、**JSON 解析器超时** (#42110) 以及 **推测解码不兼容** (#42068)。这表明虽然 Gemma 4 模型很受欢迎，但其在 vLLM 上的集成还不够成熟，存在大量边缘 case 需要修复。

2.  **推测解码（Spec Decode）/多Token预测（MTP）的活跃开发**：这是一个持续的热点。讨论集中在 `DFlash` 与量化 KV Cache 的兼容性 (#42068, #42102)、`MTP` 与 `runai_streamer` 的兼容性 (#42060)，以及 `P-EAGLE` 在 Gemma 4 上的接受率悬崖 (#42004)。同时，一个关于分离式推测解码的RFC (#42109) 提出了一个更架构性的新方案，显示社区正积极寻求更优的 spec-decode 实现。

3.  **MoE（混合专家模型）的持续优化**：MoE 仍是性能优化的主战场。这表现在多个方面：AITER 的 MoE 权重修复 (#42061)、Qwen3-Next 的融合共享专家 (#42088)、`MXFP4` 模式下 MoE 的输出错误 (#42118)，以及 CUTLASS 对 MoE 的支持 (#42089)。这表明无论是 NVIDIA 还是 AMD 平台，MoE 都是提升性能的关键领域。

4.  **AI 编译器（TorchDynamo/Inductor）交互问题**：随着 vLLM 越来越多地依赖 `torch.compile`，与 Inductor 后端的交互问题开始成为 Bug 和修复的焦点。例如 #42129 修复了 Inductor 在遇到大量自定义算子时的编译挂起问题，以及 #42070 修复了 CUDA Graph 捕获与 `torch.compile` 的冲突。这表明模型推理的“最后一公里”优化非常依赖于编译器的正确和高效工作。

5.  **KV Cache 管理与 Connector**：新的 `OffloadingManager` (#42050)、`Bounded early prefetch` (#42086)、LMCache 的 `prompt_embeds` 内容遗漏 (#42119) 以及 `expandable_segments` 与 `NixlConnector` 的不兼容性 (#41237) 等PR/Issue，表明社区在持续改进 KV cache 的管理、传输和卸载机制，以支持更长的上下文和更复杂的部署架构（如PD分离）。

### 🛠️ 重点技术变更

1.  **PR #42098: 使用 `hidden_pad` 和 `intermediate_pad`**：这是一个结构性的性能优化。它将 MoE 层的 padding 逻辑与 vLLM 早期 (#34301) 建立的标准对齐，而不是在 AITER 部分自行其是。这带来了 8% 的吞吐量提升，是软硬件协同设计的典范。

2.  **PR #42089: 修复 FlashInfer CUTLASS MXFP4-MXFP8 MoE**：修复了因 `is_sf_swizzled_layout=False` 硬编码不当导致的严重输出错误。这个回归问题导致 NVIDIA B200 上的 GPQA 评测持续失败数日。该 PR 展示了在混合精度计算中，一个微小的参数错误如何导致灾难性的后果。

3.  **Issue #42096 / PR #42085: Qwen3-VL 性能回退 / CPU Offload 的块池耗尽**：这两个问题凸显了长上下文和大模型部署的挑战。性能回退是进化中的常见问题，而 `SimpleCPUOffloadConnector` 的块池耗尽则是一个设计/实现缺陷，表明新功能（混合 KV 管理）可能隐藏着 edge cases。

4.  **Issue #42047: Gemma 4 工具解析器流式错误**：这是一个优雅的 Bug 报告和分析。用户不仅报告了问题，还深入分析了流式 `diff` 更新逻辑的缺陷——因中间状态序列化差异导致最终结果错误。这体现了社区深度参与项目的能力。

5.  **PR #42121: 移除 Tree Attention**：这是一个重要的清理操作。代码维护者 `LucasWilkinson` 决定移除一个当前完全不支持、且短期无计划支持的功能。这减少了代码和技术债务，简化了后续重构，是良好工程实践的体现。

### 💡 值得关注的问题

1.  **Issue #42063: Qwen3.5-397B 在 Blackwell GPU 上加载挂起**：这是个大模型推理的严重问题。一个 397B 参数的模型在顶级数据加载硬件上挂起，原因不明，没有 OOM 或错误消息。需要紧急关注，可能涉及模型加载器、内存管理或特定的 NVIDIA 驱动问题。
2.  **Issue #42109: 分离式推测解码 RFC**：这个 RFC 提出了一个潜在的重大架构变更。虽然目前没有评论，但它值得密切关注。如果社区支持和实施，它可能彻底改变 vLLM 的推测解码架构，带来显著的性能优势。
3.  **Issue #42064: 认证绕过漏洞**：`/inference/v1/generate` 路径未在前端认证中间件中覆盖，导致即使设置了 `--api-key`，攻击者也可以绕过认证进行无限制的推理。这是一个安全漏洞，必须优先修复。
4.  **Issue #42125: LoRA 同名重载导致前缀缓存污染**：这个 Bug 报告非常专业，描述了在运行时使用相同 `lora_name` 加载不同权重时，vLLM 可能会重用旧版本适配器的前缀缓存，导致输出结果错误。这对于需要频繁动态更新 LoRA 的生产环境至关重要，这个问题值得投入资源解决。
5.  **Issue #42087: DeepSeek-V4-Flash 产生空白回复**：DeepSeek-V4-Flash 是当前最受关注的模型之一，但在特定配置下（EP + DP）会输出空白。这看起来是一个模型推理路径上的严重Bug，需要尽快定位和修复，以维持对主流模型的支持。
