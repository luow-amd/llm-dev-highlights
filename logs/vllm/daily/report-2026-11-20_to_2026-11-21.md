#### 1. #69058 HF3FS connector 失败 load 未上报 failed block IDs（6 条评论）
- **核心议题**：HF3FS KV connector 在 load 失败时仍报告 finished，`get_block_ids_with_load_errors` 始终为空，scheduler 将未填充 block 当作 prefix-cache hit，最终返回 HTTP 200 但输出错误。
- **观点与分工**：
  - `ZYZ666-RGB` 希望承接修复，范围是上报 failed block IDs 并增加 CPU 回归测试。
  - `lkhun9311` 表示已本地复现并修复，指出两个额外问题：① `start_load_kv` 按 128 block 分批，`_load_futures[request_id]` 每批覆盖，非最后一批失败会丢失；② `kv_load_failure_policy=recompute` 下失败请求回到 WAITING 后会反复匹配同一 remote keys，形成无限重试。
  - `ZYZ666-RGB` 已保留所有 load futures 并加多 batch 测试，但尚未覆盖 recompute 重试循环；双方讨论合并实现以避免重复。
- **争议焦点**：修复范围是否应同时覆盖 recompute 死循环；如何合并两套实现并保留 attribution。
- **状态**：Issue open；`ZYZ666-RGB` 已开 **#69095**，声称上报 failed block IDs、保留所有 batch、防止 recompute 重复 load；仍需 GPU/E2E 验证和人工 DCO。

### 🛠️ 重点技术变更

#### 1. #61214：gfx942 的 AITER Triton MXFP8 MoE 后端（已合并）
这是本周期对 AMD 生态影响最大的合并项之一。此前 gfx942 上 MXFP8 MoE 模型会回退 `EMULATION`，把 expert 权重解包为 BF16，导致显存占用高、KV cache 容量小。新后端让 expert 权重保持 MXFP8：
- Hy4-preview-FP8 每 GPU 模型内存 195.8→109.1 GiB；
- KV cache 688K→2.69M tokens；
- 8K/32K/128K 输入下输出吞吐 +13-23%；
- GSM8K 保持 96.82%。
这使得较大的 MXFP8 MoE 模型可以在 192GB MI300X 上更实用地部署，是 gfx942 量化 MoE 的关键使能。

#### 2. #67550：ROCm 注意力融合进一步减少小算子 launch（已合并）
该 PR 在 FP8 KV-cache 场景下，把原本融合 kernel 之后额外的 `k_out` FP8→BF16 dequant，以及 FP8 query quant，折回 QK-norm+RoPE+KV-cache 融合 kernel。覆盖 `ROCM_AITER_FA`、`ROCM_ATTN`、`ROCM_AITER_UNIFIED_ATTN`，减少每层额外 launch 开销。对于 decode 小 batch、层数多的模型，这类 launch 开销会累积，属于典型的 ROCm 端到端 TPOT 优化。

#### 3. #68920 / #68946：ROCm breakable CUDA graph 默认值回归
GLM-5.3 在 8×MI325X gfx942 上因 ROCm breakable CUDA graph 默认架构列表缺少 `GlmMoeDsaForCausalLM`，mixed prefill/decode 步骤回退到 `FULL_DECODE_ONLY`，仅捕获 1.4-1.8 GiB 图；手动 `VLLM_USE_BREAKABLE_CUDAGRAPH=1` 可捕获约 10 GiB 图并赢回 3-9% decode。根因是 #53155 清空 ROCm breakable 默认、#56360 移除 MRV1 例外，而 AMD 专用 `DeepseekV32Model` 又没有 `@support_torch_compile`。**#68946** 添加 `GlmMoeDsaForCausalLM` 和 `DeepseekV32MTPModel`，但尚未在 gfx942 实机验证，是当前 AMD 图执行路径的重要待办。

#### 4. DSv4.1 FlyDSL 性能栈：#69097 等系列
以 #69097 为代表，AMD 正在为 DeepSeek-V4.1-Flash 在 MI355X 上建立 `amd_kernels` 路由框架和 AITER FlyDSL 调用点。示例数据：AgentX c256 总吞吐 185,582→201,188 tok/s/GPU（+8.4%），P90 交互性 107.4→148.3 tok/s/user（+38%）。但该 PR 为 DNM/draft，依赖 #67850、Inferact/amd-kernels、AITER v0.1.29.post1 + FlyDSL 0.5.0，且存在 merge conflict。该系列的技术价值高，但离可合并/可默认启用仍有距离。

#### 5. #66586：gfx94x 上 compressed-tensors 的 e4m3fnuz KV-scale ×2（已合并）
gfx94x 的 FP8 是 e4m3fnuz，最大值为 240 而非 e4m3fn 的 448，因此按 e4m3fn 校准的 KV scale 需要 ×2。`CompressedTensorsKVCacheMethod` 替换了 `BaseKVCacheMethod` 的 hook 但未调用 `super()`，导致 scale 减半、key 在写入 FP8 cache 时被裁剪。修复后：
- key 饱和比例从 0.9-1.5% 降至 <0.001%；
- FP8 KV-cache GSM8K PPL 与 BF16 KV-cache 的差距从最高 20.5% 降至 0.7% 内；
- 单元测试无 ROCm skip，H200 Quantization job 也会运行。
这是典型的“平台 FP8 格式差异导致静默精度损失”问题，对 MI300 系列 compressed-tensors 部署很关键。
