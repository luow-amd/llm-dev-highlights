**新增 Issue（侧重 Bug 报告）**：

1.  **[Bug][ROCm] Sparse indexer clears the full max_model_len logits buffer every decode step: 17% throughput on a 1M context** (#55373)
    - 提交者：stefanskiasan（多次提交高产用户）
    - 核心内容：指出现有 ROCm 的 `flash_mla_sparse` 路径（AITER 实现）在每个 decode 步骤会无条件清理长度为 `max_model_len` 的巨大 logits 缓冲区，造成纯开销。通过精细的 profiling 和消除该步骤后的 A/B 测试，证明相关操作可安全移除，在长上下文中可带来显著性能提升（17%吞吐）。
    - 影响：这是一个极有价值的性能优化指示，直指 ROCm 特定实现与 CUDA 路径在 `clean_logits` 行为上的不一致。

2.  **[Bug][ROCm] QuickReduce converts bf16 to fp16 without saturation: activations above 65504 silently become inf** (#55345)
    - 核心内容：发现 ROCm QuickReduce 在将 bf16 数据打包为 fp16 时使用了不饱和的类型转换。由于 bf16 动态范围远大于 fp16，当一个超大数值（>65504）出现时，会被转换为 inf，注入并污染整个归约结果，且异常在调试中极难察觉。
    - 影响：该 Bug 影响所有启用 QuickReduce 的量化模式，是一个严重的数值正确性隐患。提供了精确的修复补丁方案。

3.  **[Bug][ROCm] gfx950 FP32 router GEMM is unreachable for DeepSeek-family models: shape (6144, 256) is listed but the weight is bf16** (#55351)
    - 核心内容：指出 #54845 为 gfx950 引入的 FP32 Router GEMM 专用 Kernel 从未被激活。原因是模型的 router 权重虽然声明为 FP32 输出，但权重本身仍以 bf16 存储，导致 Kernel 的触发条件 `self.weight.dtype == torch.float32` 无法满足。提交者提供了修复验证并坦率地指出该修复在其测试环境上并未带来正面效果。
    - 影响：该问题揭示了硬件特性代码实际生效路径中的断层，是软硬件协同适配中的典型案例。

4.  **[Bug][ROCm] Startup crash (bare AssertionError) when the AITER custom-AR cutoff is below the fused allreduce+RMSNorm compile range** (#55344)
    - 核心内容：发现当用户通过环境变量将 AITER 自定义 AllReduce 的运行时上限设置得过低，并启用了 fused AllReduce+RMSNorm 编译 pass 时，会因编译范围和运行时允许范围不一致，导致启动时直接崩溃，且报错信息不明确。
    - 影响：该 Bug 暴露了配置解析与编译传递之间缺乏一致性校验的问题。关联修复 PR 为 #55347。

5.  **[Bug][ROCm] numa-bind is a silent no-op on ROCm images (numactl not installed)** (#55416)
    - 核心内容：报告 ROCm 官方 Docker 镜像未安装 `numactl` 命令，导致 `--numa-bind` 参数静默失效。提交者通过详尽的性能测量给出了铁证，证明了数据的可靠性，充分体现了该用户严谨的技术态度。
    - 影响：对多路 CPU 主机上的性能调优用户是个重要提示。

6.  **[Bug] gfx950 top-k policy is gated on topK==1024, leaving index_topk=2048 models (GLM-5.x) on the generic 10-way split** (#55327)
    - 核心内容：继续 sizzlecar 提交者在 gfx950 性能调优上的探索。发现针对 gfx950 的优化 Kernel 路径仅对 `topK==1024` 的模型启用，而 GLM-5.2/5.3 这类 `index_topk: 2048` 的模型无法利用该优化，导致在特定上下文下比长上下文更慢等异常现象。
    - 影响：模型特定配置对硬件优化路径的覆盖问题。

### 💬 高热度讨论分析

1.  **[RFC]: Tile-union QSA sparse attention for prefill（#55394）**（Issue）
    - 核心议题：是否可以将相邻 Query 行的 K/V 索引合并为一个“块并集”，在 Prefill 阶段用单次访存和独立掩码处理多个 Query 行的注意力计算，以实现 ~4.7% 的 TTFT（首字延迟）降低。
    - 观点：gau-nernst 认为该方向与现有 prefill/decode 拆分思路一致，但提出了一些实现细节问题，包括不能只支持单请求 batch、需要进一步测试、以及建议用 PR 形式展开讨论。
    - 状态：该 PR 内部仍在 Draft 审阅中。

2.  **多个与稀疏索引 / top-k 相关的讨论（#55314）**
    - 核心议题：在 DSA 稀疏注意力索引器中，当 top-k 候选数量超过共享内存 stash 的容量边界时，会出现候选项被悄无声息地丢弃的数值 bug，导致 top-k 选择可能与 `torch.topk` 不等价。
    - 观点：作者对比了多种 top-k 路径，并将 stash 溢出描述为一种理论缺陷，指出这是并行稀疏注意力实现中长期存在的边界问题。
    - 状态：PR #55314 作为 Bug 修复已修复了四条 top-k 路径，并加入了针对模糊场景的回归测试。

3.  **[Bug]: --numa-bind is a silent no-op on ROCm images（#55416）**（Issue）
    - 核心议题：尽管 `numactl` 不存在于镜像中，`--numa-bind` 参数依然能静默启动并行。
    - 观点：stefanskiasan 在提交时会附带自行验证的修复补丁，同时因为自己也遇到了相同的瓶颈，所以会先通过数据和环境才能给出结论。这次也不例外。提交者对特性的完整度要求较高、给出了深度剖析。
    - 争论点：涉及对基于 `taskset` 的替代方案在不同硬件上性能效果截然相反的实验现象的解释，以及应用该配置的可能副作用。
    - 状态：等待维护者审查 #55416 分支。

4.  **EAGLE3 投机采样在流水线并行上的变更（#50514）**

### 🛠️ 重点技术变更

- **[Bugfix][Quantization] Register Quark per-block FP8 scales as weight_scale** (#54770)
  - 这是对 AMD 开源的 Quark 量化工具与 vLLM 之间集成方式的根本性修正。以往走的是权重量化方法的通路，从而使得在模型处理内部解算权重时能使用任何有效的量化格式，例如 fp8 分块量化。将对 Quark 检查和 DeepSeek-V4 FP8 权重切分的修复，合入更通用的入口，让该修复能惠及除特定模型外的其他场景，避免模型或场景的堆栈解耦现象被反复“堆补丁”。
- **[AMD][kimik3][ROCm][Perf] Fuse MLA q/kv RMSNorm in AMD Kimi-K3 MLA wrapper** (#52494)
  - 在代码层面采用 AMD/NVIDIA 的后端分离，针对 ROCm 平台的 Kimi-K3 模型将两个算子融合成一个 AITER Kernel。
- **[Bugfix][DSv4] Seed the -1 sentinel in the prefill sparse index workspace** (#55299)
  - 修复一个极为隐蔽的未初始化内存问题。调用方提供的缓存空间不会自动填充哨兵（-1）。当数据分块与图捕获操作使工作区发生旋转时，同一段工作空间内的数据存在被残留或不安全索引读取。
- **[Bugfix] Make `mm_device_do_normalize` encoder-cudagraph safe** (#55370)
  - 该修复针对多模态模型的视觉编码器（vision encoder）中，由于使用 cudagraph 捕获路径而跳过归一化传入模型的操作，而直接向后端传递了 uint8 图像像素值。这个 PR 也是将归一化正式纳入视觉塔塔的行列，并同步落入到 Qwen2/2.5-VL 的实现中。

### 💡 值得关注的问题

- **ROCm 镜像的基础依赖缺失**：`numactl` 未被打包，导致性能关键参数的静默失效。公开的 Issue 关联的修复方式能降低用户使用时的性能感知混乱。
- **KV Connector 集成范围的持续扩大**：多个方向的 KV Connector（Mooncake, NIXL）正在通过对 P/D 前缀协议载入与卸载路径的不断推导来实现其落地，这个逻辑正在显式要求 KV 存储抽象层与框架的分块等底层实现密切交互。
- **“标准路径”之外的特异性分支**：本轮多个 PR 表面都在从“模型/进程都能跑通”走向“被多个语境正确覆盖”的阶段。为保证模型本身的优化调度不因另一种算法策略被绕开，需要长期贯彻更严格的规格语义和一致性校验，确保优化尽量全模型界别生效。
- **历史 Issue 的自动关闭机制**：在关闭相关陈旧问题时，不仅剔除了完全失效的讨论，还会同步清理因修复长期没进版本的用户经验贴。
