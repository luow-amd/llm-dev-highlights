### 🎯 AMD/ROCm 生态相关动态

本周期内，AMD/ROCm 生态是 vLLM 开发的核心焦点之一，贡献活跃且技术含量高，具体动态如下：

1.  **新贡献：AITER FP8 ASM Prefill 后端 (PR #44544)**
    -   **贡献者**: `simondanielsson` (AMD 员工，用户名含 `-son`)
    -   **内容**: 为基于 AITER 的 MLA 注意力后端新增了一个针对 `gfx950` (MI350) 的 FP8 ASM Prefill 内核。该 PR 通过创建一个独立的 Prefill 后端，支持了分块 Prefill（chunked prefill），解决了之前非因果 ASM 内核在分块场景下的回退问题。这对于在 AMD GPU 上高效运行 DeepSeek 系列模型至关重要。

2.  **性能优化：消除稀疏 MLA 热循环中的 FillFunctor 内核启动 (PR #44527)**
    -   **贡献者**: `frida-andersson` (AMD 员工，用户名含 `-son`)
    -   **内容**: 针对 ROCm 上的稀疏 MLA 解码路径，通过使用持久化工作区（workspace）替代每次迭代都启动的 `torch.full` 和 `topk_indices_buffer` 填充操作，消除了两个无数据输出的 HIP `FillFunctor` 内核。此举将解码热循环中的内核数量减少了 **40%**，并对 `DeepSeek-v3.2` 模型进行了性能基准测试。

3.  **PyTorch 编译优化：支持 GLM-4 MTP 草案 (PR #44508)**
    -   **贡献者**: `omirosh` (AMD 员工)
    -   **内容**: 为 `Glm4MoeMTP` 类添加了 `@support_torch_compile` 装饰器，使其能像 `DeepSeekMTP` 一样享受 Inductor 的融合优化（如 AITER AllReduce + RMSNorm 融合、量化融合）。这将提升在 AMD GPU 上运行 GLM 模型时的推测解码性能。该 PR 已在 Mi355X 节点上进行了测试。

4.  **Bug 修复：修复 ROCm 上的 Quark 量化 MoE 检查点兼容性 (PR #44542)**
    -   **贡献者**: `kewang-amd` (AMD 员工，用户名含 `-amd`)
    -   **内容**: 这是一个关键的兼容性修复，涉及两个问题：
        1.  **`mxfp4_utils.py`**: 在将输入传递给 Quark 的 `mx.dq_mxfp4` 内核前，添加了 `.contiguous()` 调用。这修复了在 MLA 分块 Prefill 场景下，由于输入张量是切片视图（non-contiguous）导致的内核断言错误。
        2.  **`quark.py`**: 修复了当 Quark 量化配置文件中只包含逐专家（per-expert）蒸馏模式（如 `...experts.*.down_proj`），而没有其父路径（`...mlp.experts`）时，FusedMoE 无法正确匹配配置，回退到全局量化方案并导致崩溃的问题。该 PR 添加了子路径探测（probe）回退机制。

5.  **CI 修复：修复 ROCm 集成测试中的依赖问题 (PR #44600)**
    -   **贡献者**: `AndreasKaratzas`
    -   **内容**: 修复了两个问题：
        1.  在构建镜像时，将 `tools/` 目录也打包进 `export_vllm` 工件，解决了因缺少 `install_torchcodec_rocm.sh` 脚本导致的测试失败。
        2.  将 `tensorizer` 从 `2.10.1` 升级至 `2.12.1`，以兼容 Python 3.14 环境，修复了在 `rocm 7.14` 基础镜像上的导入崩溃。

6.  **代码重构：改进 DeepseekV4Attention 的 ROCm 和 NVIDIA 代码共享 (PR #44569 - 已合并)**
    -   **内容**: 由贡献者 `WoosukKwon` 提交。此 PR 对 `DeepseekV4Attention` 进行了纯代码重构，通过类继承将 ROCm 和 NVIDIA 的分发逻辑清晰分离，并移除了两个本质上为空的操作类。这虽然不改变功能，但显著提升了代码的可维护性，利于未来 AMD 平台的长期演进。

**总结**: 本周 AMD/ROCm 的贡献集中在**性能优化**（消除冗余内核、利用 torch.compile）、**硬件支持**（为 MI350 `gfx950` 添加 FP8 ASM 内核）和**生态系统兼容性**（修复 Quark 量化模型的加载和运行错误）。这体现了 AMD 团队在 DeepSeek 模型推理方面持续深耕，并积极解决实际部署中的问题。

### 💬 高热度讨论分析

1.  **Bug: Gemma 4 12B 无法正常启动并运行 (Issue #44494)**
    -   **核心议题**: 用户报告 `google/gemma-4-12B` 模型在 vLLM 0.21.0 和 0.22.0 上都无法正常工作，显示矩阵乘法形状不匹配的错误。
    -   **观点整理**:
        -   **用户侧**: 多位用户在 NVIDIA RTX 6000 Pro Blackwell 和 24GB 消费级 GPU 上复现了此问题。`rumjie` 用户定位出根因：Gemma-4 12B 模型在不同层使用了不同的 `head_dim`（滑动窗口层 256，全局全注意力层 512），而 vLLM 代码库中存在 TODO 注释表明尚未支持这种异构 `head_dim` 配置。
        -   **维护者侧**: `Sunt-ing` 用户指出，使用 `transformers==5.10.2` 时，代码会回退到 Transformers 实现，导致失败。而在最新的 `main` 分支上（已包含 #44429 PR），12B 模型已能成功初始化并运行。`mgoin` 也建议用户使用包含 #44429 的 nightly 版本。
    -   **争议焦点**: 无。这是一个明确的功能缺失导致的 Bug，且已被快速修复。
    -   **当前状态**: 仍为 **open**，但根因已被社区识别，并且在最新的开发版中已修复。这更多地成为了一个提醒用户使用最新版本的 Issue。

2.  **Bug: GLM-5 FP8 在长序列输入时 OOM (Issue #44545) 及 BF16 KV Cache 输出乱码 (Issue #44550)**
    -   **核心议题**: 用户在 H200 x 8 集群上运行 GLM-5.1 FP8 模型时发现两个严重问题：(1) 使用 FP8 KV Cache 时，长序列输入导致 `flash_mla_cuda.sparse_decode_fwd` OOM；(2) 回退到 BF16 KV Cache 时，长上下文生成出现乱码。
    -   **观点整理**:
        -   **用户 (cjackal)**: 报告了问题，并提供了详细的复现步骤和错误栈。他确认 OOM 问题在设置 `--kv-cache-dtype fp8` 时触发。
        -   **维护者 (MatthewBonanni)**: 询问了启动时报告的 KV cache 大小，并请求用户为 BF16 乱码问题单独创建一个 Issue，以便分开追踪。
    -   **争议焦点**: 无。这是一个需要深入调试的复杂 Bug，涉及 FlashMLA 内核与 KV Cache 量化协同工作的问题。KV Cache 容量和内存分配的边界条件可能是导致 OOM 的原因。
    -   **当前状态**: 两个 Issue 均为 **open**，等待进一步调查。

3.  **Bug: 先验提示缓存 (APC) 在分散式推理中报告错误的命中率 (Issue #44607)**
    -   **核心议题**: 在使用 `NixlConnector` 进行分散式 Prefill/Decode (PD) 部署时，对于全新的、无 APC 命中的请求，`usage.prompt_tokens_details.cached_tokens` 返回了 100% 的命中率，严重误导了监控指标。
    -   **观点整理**:
        -   **用户 (linzm1007)**: 报告了 Bug，认为 `cached_tokens` 错误地将通过 `NixlConnector` 从 Prefill 端传输过来的所有 KV 块都算作了缓存命中，而 OpenAPI 语义下它应只反映自动前缀缓存（APC）的命中情况。
        -   **贡献者 (adhithyamulticoreware)**: 迅速分析了根因，指出 `PrefillStats` 中已分别追踪了 `num_local_cached_tokens` (本地 APC 命中) 和 `num_external_cached_tokens` (外部 KV 传输)。他提出修复方案：仅使用 `num_local_cached_tokens` 来填充 API 返回的 `cached_tokens` 字段，并发出了一个 PR。
    -   **争议焦点**: 无。错误定位清晰，社区贡献者提供了明确的修复方案。
    -   **当前状态**: **open**，但已有明确的修复计划。

### 🛠️ 重点技术变更

1.  **PR #44569: [DSV4] Refactor DeepseekV4Attention** (已合并)
    -   **技术解读**: 该 PR 对 DeepSeek V4 的注意力层进行了架构级别的代码重构，通过类继承清晰分离了 ROCm 和 NVIDIA 的实现。这虽然不改变功能，但其技术价值在于极大地提升了代码的可维护性和扩展性。未来新增 AMD 或 NVIDIA 特有的优化内核时，开发者可以更清晰地定位和修改代码，降低了多平台支持的成本。

2.  **PR #44581: [Feature] KVarN KV-Cache Quantization** (新提交)
    -   **技术解读**: 该 PR 引入了一种全新的 KV Cache 量化方法，其算法核心在于对每个 128-token 的 tile 应用 Hadamard 旋转和 Sinkhorn 迭代方差归一化，使数据分布更均匀，再进行非对称量化。技术亮点是声称可以突破“压缩率与吞吐量/精度”的 tradeoff，在 3-5 倍压缩下实现超过 FP16 的吞吐量和 FP16 级别的精度。如果能被证实和合并，将是 KV Cache 量化领域的一个重大进步。

3.  **PR #43447: [Prefix Caching] DeepSeekv4 SWA Cache Retention** (已合并)
    -   **技术解读**: 该 PR 解决了 DeepSeek V4 模型因滑动窗口 (SWA) 缓存频繁更新导致的**前缀缓存命中率极低**的严重问题。根因在于，新请求的滑动窗口不断分配和释放 block，导致旧请求被缓存的 block 被快速回收。修复方案是：将“未被缓存的 block”放入空闲队列开头（优先分配回收），将“已缓存的 block”放入队列末尾（尽量保留）。这个优化对长上下文和高并发场景下的 DeepSeek V4 服务性能提升至关重要，测试显示命中率从 0% 提升至 89.4%。

4.  **PR #44542: [Bugfix] Quark-related fixes for ROCm** (新提交)
    -   **技术解读**: 这是解决 AMD 平台与 Quark 量化工具链兼容性的关键 PR。它修复了两个真实世界中会遇到的错误：一是内存非连续性问题（`.contiguous()`），二是量化配置匹配逻辑缺陷（子路径探测回退）。这些 Bug 如果没有修复，将导致 AMD 用户无法直接使用 Quark 工具量化并部署模型，这对 AMD 生态的落地部署形成了直接障碍。

5.  **PR #41980: use split_group for pytorch process group creation** (已合并)
    -   **技术解读**: 该 PR 将 vLLM 的进程组创建方式从 `torch.distributed.new_group` 迁移到 `torch.distributed.split_group`。`split_group` 利用 NCCL 的 `ncclCommSplit` API，在现有父通信器上“分裂”出子通信器，避免了 `new_group` 每次创建子组都需要进行完整 bootstrap 的昂贵开销。这个改变不仅提升了大规模集群下 vLLM 的启动速度，更重要的是为未来迁移到下一代通信库 `torchcomms` 铺平了道路，具有前瞻性的架构意义。
