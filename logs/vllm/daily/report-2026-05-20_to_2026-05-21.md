### 🔥 热门话题与趋势分析

1. **工具调用（Tool Calling）与流式处理的稳定性**  
   本日多个 Issue 和 PR（#43244、#43221、#43247、#43243、#31871、#38973）都围绕工具调用在流式模式下的正确性展开。问题集中在：
   - `previous_response_id` 丢失函数调用历史。
   - 推理结束时 thinking 与 tool_call token 在同一 delta 中引起的截断。
   - XML 解析器对 JSON 布尔值/空值的处理错误。
   - Hermes、DeepSeekV3、Qwen3 等多种 parser 的兼容性。

   趋势表明，随着模型原生支持工具调用（如 Qwen3.5、Gemma4），vLLM 急需完善流式工具调用的端到端测试和统一解析框架。

2. **AMD 生态持续加码**  
   从环境变量调优（QuickReduce）、新硬件支持（MoRI）、核心内核修复（fp32 leak）到 CI 改进，AMD 团队在多个层面贡献代码。ZenCPU 量化支持的引入表明 vLLM 正在向更广泛的 AMD 平台（不仅仅是 GPU）扩展。

3. **性能优化从“整个图”回归“手动融合”**  
   RFC #43224 明确提出了从 `torch.compile` 全图融合回归手动融合的路线图，计划逐个弃用编译器融合 pass 并在模型代码中手动调用。这与当前行业对可维护性、可移植性的追求一致，但也增加了模型适配工作量。

4. **推测解码（Speculative Decoding）持续演进**  
   Gemma4 MTP 支持（#43241）、EAGLE3 在 MRV2 上的问题（#40551）以及 DFlash + SWA 的 FlashInfer 元数据分组（#43200）表明，推测解码是当前活跃的开发领域，尤其关注多模型（Eagle/Medusa/DFlash）在 Model Runner V2 上的融合。

### 🛠️ 重点技术变更

1. **[Kernel] Fuse Qwen2/3-MoE shared-expert sigmoid gate into a Triton kernel** (#43190)  
   - 将原本 3 个 HBM 写回内核（线性投影 + sigmoid + 逐元素乘）合并为单个 Triton 内核，消除中间张量分配。  
   - 在 MI355x 和 NVIDIA H100 上均有收益，通用性通过 shape guard fallback 保证。  
   - 与 AITER FSE 共存，当 `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS` 启用时自动禁用。

2. **[Fix] fp32 residual dtype leak in GemmaRMSNorm.forward_native** (#43242)  
   - 修复 Gemma 系列模型中残差路径被错误提升为 fp32 的问题。该问题导致后续层（如 DFlash 解码）与混合精度期望不符，引发精度损失。  
   - 在 MI300 上验证通过，对 Gemma4 等新模型至关重要。

3. **[Perf][gpt-oss] Downgrade triton_kernels to v3.5.1** (#43135)  
   - 回退 `triton_kernels` 版本从 v3.6.0 到 v3.5.1，并修复路由逻辑，恢复 gpt-oss 模型解码性能从 230.1 tok/s 回 307.4 tok/s。  
   - 使用 `SparseMatrix` 不存在时回退到旧的直接路由模式，避免三内核启动开销。

4. **[Perf][Gemma4] Batch vision encoder calls for image and video processing** (#43169)  
   - 将 Gemma4 视觉编码器中的 patch embedding → encoder → pooling → projection 分解为批量处理，消除图像/帧之间串行循环。  
   - 动态批次大小自适应，在 8×A100 上对 Gemma4-26B 实现 1.5-2× 吞吐提升（高 QPS 场景）。

5. **[Frontend][RFC] Rust front-end integration** (#40848)  
   - 引入基于 Rust 的替代前端进程（`vllm-frontend-rs`），通过 `VLLM_USE_RUST_FRONTEND=1` 启用。  
   - 旨在提供更低延迟、更高并发的 HTTP 处理能力，同时保持与现有 Python 前端的兼容性。  
   - 作为 RFC 实现被合并，标志着 vLLM 前端架构的重要演进方向。

### 💡 值得关注的问题

1. **EngineCore crash 在生产环境中的 P0 等级**  
   Issue #43226 描述了 async KV 传输与请求中止之间的竞态条件，导致 `Scheduler._update_from_kv_xfer_finished` 中 assert 失败，会硬崩溃 EngineCore。尽管 PR #33377 部分修复了类似问题，但此路径仍被遗漏。社区建议立即采用类似容忍机制。

2. **配置 YAML 展开功能缺失**  
   Issue #43252 指出 `vllm serve --config=...` 仅接受路径但不解析 YAML 内容。对于依赖配置文件的部署场景，这是一个功能性缺失。

3. **Rust 前端集成后的长期演进**  
   合并的 PR #40848 引入了 Rust 前端作为可选项，但尚未暴露完整的功能（如流式、工具调用等）。后续需要社区投入维护和功能对齐，避免出现两套前端功能不对称的情况。

4. **编译器融合到手动融合的迁移计划**  
   RFC #43224 的库存清单列出了大量需要迁移的 fusion pass，涉及 CUDA 和 ROCm 两个平台。社区需要协调资源，确保在删除编译器 pass 时不引入性能回归（benchmark 约束）。目前已有贡献者主动认领任务（如 A1c0r-Z 负责 `rope + kv_cache_write`）。

5. **DeepSeek-V4 启动时间优化**  
   Issue #43189 反映了 DeepSeek-V4-Flash 模型启动需要约 8 分钟。社区提供了临时方案（跳过 DeepGEMM 预热、禁用 FlashInfer autotune），但缺少正式的启动加速文档和系统性优化。
