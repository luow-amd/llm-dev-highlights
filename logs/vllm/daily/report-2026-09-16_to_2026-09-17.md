### 一、严重 Bug 与崩溃修复

#### 1. #57227【最高优先级】gfx950 GLM-5.3-Flash 16K chunk prefill 内存访问故障
- **现象**：8×MI350X（gfx950）TP8，首个 16K chunked prefill 时 8 个 rank 全部触发 `Memory access fault`；decode 和 ≤8K prefill 稳定。
- **排查结论**：报错者 `mustafayildirim` 通过差分实验定位到根因**不是 aiter kernel，也不是内存布局**，而是 `VLLM_USE_BREAKABLE_CUDAGRAPH=1` 与 JIT 编译在惰性 CUDA graph 捕获期间的交叠。
- **关键数据**：`breakable=1 + cudagraph on` → 崩溃；`breakable=1 + --enforce-eager` → 干净；**`breakable=0 + cudagraph on`（57 个 FULL graph）→ 干净，repro ×2 通过**。
- **社区验证**：`simondanielsson` 独立复现，发现不仅 16K，`--max-num-batched-tokens 8192` 也会失败，问题不局限于特定 chunk 大小；且官方 MI350X recipe 默认就会触发。
- **状态**：open，等待维护者确认修复方向。

#### 2. #57288 gfx942 DeepSeek-V4.1 graph capture 段错误

## 💬 高热度讨论分析

### 1. #56443 DeepSeek-V4.1-Flash DSpark 在 SM90 上 CUDA device-side assert（8 条评论，已关闭）

**核心议题**：4×H200 + Marlin MXFP4 MoE 回退 + DSpark K=5 spec decode，draft warmup 阶段崩溃于 `map_draft_to_target`。

**多方观点**：
- **UmutAlihan（报告者）**：坚持认为崩溃在 DSpark 路径，指出 #56448 只改了 DFlash 的 profiling 逻辑，而 DSpark 是不同的路径（`dspark/speculator.py:128` → `_sample_logits`）。
- **wangyicong52（修复者）**：DSparkSpeculator 继承 DFlashSpeculator，profiling 问题会级联；512 req × 5 query = 2560 > 2048 输入 buffer，异步 CUDA 错误延后到 `map_draft_to_target` 暴露。已在 4×H20 复现 RED→GREEN。
- **CyFeng16（第三方）**：H200 baseline（无 EP、max-num-seqs 16、mbt 8192）48h / 36607 请求 0 错误，说明该配置不在故障条件内，提供了有价值的对照。

**争议焦点**：DSpark 与 DFlash 是否为同一 bug？根因是 Marlin/MXFP4 还是 profiling dummy batch 超限？

**结论**：**报告者最终确认 #56448 覆盖此问题**，验收长度 2.05–3.80，per-position acceptance 0.85/0.70/0.55/0.41/0.27。已关闭。

### 2. #56242 Mooncake P2P 跨 Encoder 缓存（8 条评论，已合并）

**核心议题**：多 Encoder 场景下，重复图像能否跨 Encoder 复用 embedding。

**多方观点**：
- **gty111**：建议 P/D 直接从 Store 拉取 embedding，而非经 E 中转。
- **jiaran-king（作者）**：本 PR 有意分离"Encoder 输出复用"与"E→P/D 投递"；直接读取会引入第二投递源，需协调来源选择、完成、失败回退，建议 follow-up。
- **jiangkuaixue123**：提出 router 层基于内容标识的缓存感知路由是否可替代共享 Store？
- **jiaran-king**：**两者互补**——路由提升局部性但不保证命中，Store 提供跨 Encoder 复用；可同时启用。

**争议焦点**：架构选择（P2P 中转 vs 直接 Store 读 vs cache-aware routing）。

**结论**：合并。作者采纳了"每个 client 复用一个 CPU header buffer"的优化，warm PUT 处理时间 **~19% 提升**（1×1MiB: 1.466→1.183 ms）。

### 3. #42384 DeepSeek-V4-Pro TP=16 FP8 block-shape 校验失败（6 条评论，已关闭-stale）

## 🛠️ 重点技术变更

### 1. #57132 — 紧急 revert 修复 DeepSeek-V4 精度崩溃（已合并）
**技术解读**：main 分支上 DeepSeek-V4 的 GSM8K 从 0.95 掉到 0.0053，直接 revert #56433（AITER 预打乱 FP8 block-scaled MM kernel）+ #51692 恢复正确性。这暴露了 AITER 线程化 kernel 重构（`AiterPreshuffledFp8BlockScaledMMKernel` 覆写 `apply_weights` 而不再走 `apply_block_scaled_mm`）与现有调用约定的不一致。**影响**：main 精度恢复，但两个被回退的优化需要重新设计提交。

### 2. #55934 — triton_kernels 3.8 mxfp4 MoE 支持（已合并）
**技术解读**：上游 API 大改（`matmul_ogs`→`matmul`、`RoutingData`→`RaggedTensorMetadata`、`weight_scale`→`b_mx_scale`，并移除 kernel 内 scatter+topk-reduce）。PR 增加版本 dispatcher，同时前向修复其他 AITER_MXFP4_W4A{8/16} 后端，并把 ROCm triton_kernels 提交钉到 `releases/internal/3.8.x`。**影响**：gpt-oss-120b 和 DSV4 在 MI300X/MI355X 上的 mxfp4 路径全部可用，W4A16 block-pin 策略在 gfx942 需 autotune。

### 3. #57185 — 从 generation 返回最终 prompt hidden state（新功能，open）
**技术解读**：允许生成实例通过 opt-in 请求返回最后一个 prompt token 的 hidden state，从而用**同一加载模型**同时提供生成与 embedding proxy，避免第二个实例。学术依据 PromptReps / PromptEOL / E5-V。**影响**：为"一份权重两种用途"的部署形态提供 vLLM 原生支持，涉及 scheduler / rust / frontend 多模块，已有 rebase 冲突。

### 4. #57240 — HiSparse 在 ROCm 上启用（已关闭，需重新提交）
**技术解读**：把 #53781 的 HiSparse（稀疏 MLA KV cache 大部分驻留 pinned host memory，按 indexer 选中行按需拉回）移植到 ROCm/CDNA3+（gfx950 验证）。核心是 dense `[tokens, topk]` 索引与 AITER ragged flat list + indptr 之间的桥接。**亮点**：作者指出修复了一个**平台中立代码的 bug（CUDA 同样受影响）**，是让 GLM-5.3 输出从乱码恢复一致的原因。

### 5. #57202 — MiniMax-M3 decode indexer 按可用工作分块（open，验证详尽）
**技术解读**：按可用 block 数限制 score/partial-top-k chunk，避免短上下文下产生无用 producer 与部分结果。作者展示了完整的 RED→GREEN 过程：原始 11 PASS/1 FAIL，根因为 TF32 截断使 FP32 oracle 的 close-cutoff 排序反转，修复仅针对测试（seed 149 + 转 BF16），未放宽任何容差或 kernel。8×SM120 TP8 + EAGLE3 K5 真实请求验证 4104 次 launch。

## 💡 值得关注的问题

### 1. 【最紧急】#57227 breakable cudagraph 在 gfx950 上的崩溃
影响官方 MI350X GLM-5.3-Flash recipe 开箱即用性，多 rank 全崩。已定位到 `VLLM_USE_BREAKABLE_CUDAGRAPH`，但**是否应以默认关闭 breakable 作为修复，还是修复捕获逻辑本身**，需要维护者决策。同时 `simondanielsson` 的复现表明问题比 16K 更广。

### 2. 【架构】#57185 hidden state 返回与 runner 单实例约束
vLLM 每个实例只选一种 runner 类型，该 PR 试图在同一生成实例中提供 embedding proxy。涉及 scheduler、rust 前端、mrv2 多模块，需评估对调度模型的影响。

### 3. 【进程】#57296 KV 事件 tier-scoped clear 的兼容性
`AllBlocksCleared` 升级为 `TierBlocksCleared(medium=...)` 是**破坏性变更**：不识别新 tag 的 reader 会丢弃整个 batch。作者用 `isolate_tier_clear_batches()` 限制爆炸半径，但 KV-aware router / 外部 cache index 的迁移路径仍需明确。

### 4. 【精度】#57134 FP8 KV cache 在 NoPE 稀疏 MLA 下的 Q 不量化
作者选择"Q 保持模型 dtype、FP8 KV 行在 Triton kernel 内反量化"，与其他路径的 Q 量化策略不同，数值影响需长期跟踪。

### 5. 【待闭环验证】#57198 / #57197 FlashInfer autotune & MiniMax EAGLE3 PP
两者均保持 draft，作者明确声明未完成 PP1 对照、冷/热缓存、质量与性能验证。SM120 上 autotune 能到达并写出独立 cache 文件，但冷启动 420s 未就绪的原因未解。

### 6. 【流程】#57191 Quark MXFP8 支持被关闭
该 PR 功能完整（8 文件、+300/−241、gsm8k 91.6%），但被 Mergify 因与 #57071 的 head commit 冲突而阻断后关闭，**有价值的 MXFP8 支持可能需要重新提交**，建议关注后续。

### 7. 【配置一致性】官方 recipe 与实际实现偏差
#42384（TP=16 不可用）、#57227（MI350X recipe 即触发崩溃）表明 recipes.vllm.ai 的验证覆盖面可能需要加强，尤其是 AMD 平台的配方。

---

**总结**：本周期 vLLM 的核心矛盾集中在**异步执行（CUDA graph / 流 / PP）与新型稀疏注意力/量化路径的交互**上，AMD 平台既是问题高发区也是修复最密集区。AMD 团队通过性能追踪 Issue（#57149、#57230）+ living table 的方式系统化管理优化路线，值得其他硬件后端借鉴。DeepSeek-V4 精度回归的紧急 revert 提醒：激进的内核重构需要配套端到端精度门禁。
