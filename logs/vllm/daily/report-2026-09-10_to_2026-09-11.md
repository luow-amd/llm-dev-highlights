### 1. #50706 — Mistral3 多模态 profiling 失败（11 条评论，已关闭）

**核心议题**：默认初始化 HF 格式 Mistral Small 3.2 24B 时，在合成多模态 profile run 阶段抛出 `Failed to apply PixtralProcessor on data={'text': '[IMG]'}`。

**不同观点与排查过程**：
- **manunicholasjacob（报告者）** 给出根因：该 checkpoint 同时携带 HF tokenizer 文件与 `tekken.json`，transformers 5.x 的 `AutoTokenizer` 会返回 `MistralCommonBackend`（覆盖声明的 `LlamaTokenizerFast`），而 mistral-common **故意不编码文本中的特殊 token**，导致 `[IMG]` 被 tokenize 成字面字符，placeholder 计数不匹配。
- **juliendenize** 建议尝试 `load_format="hf"` / `tokenizer_mode="hf"` / `config_mode="hf"`，但报告者验证**四种组合全部失败**，因 backend 选择不依赖于这些 flag。
- **hmellor（维护者）** 补充上游背景：transformers 的设计决策是遵循 tokenizer auto mapping 的意图，只要安装了 mistral-common 就会走 `MistralCommonBackend`，`tekken.json` 的存在与否不参与决策。
- **流程性争议**：报告者的修复 PR #50752 因 `pre-run-check` 要求作者有 4 个已合并 PR（他 0 个），CI 从未运行，形成"贡献者门槛-修复无法验证"的僵局。**这是社区流程设计中值得关注的摩擦点。**

**结论**：issue 已关闭，但修复路径依赖具备写权限的维护者加 `ready` 标签。

## 🛠️ 重点技术变更

### 1. 【#48247】AITER 自定义 AG/RS 合并 — ROCm DP 通信原语

DP attention + TP experts 场景下，均匀 decode batch 的 AG/RS 从 NCCL/RCCL 切换到 AITER 实现。AG 分 3 次调用（hidden / topk_weights / topk_ids，AITER 无 grouped AG）。**关键约束**：仅在 DP 进程组生效，不触碰 TP/EP 集合通信。1k/1k TPOT 约 **3%** 提升（并发 1–256）。可通过 `VLLM_ROCM_USE_AITER_CUSTOM_AR=0` 关闭。

### 2. 【#54038】Kimi-K3 KDA prefill 融合 kernel reland — gfx950 构建门控

原 #52606 因 gfx90a 构建失败被 revert。本 PR 以**平台门控编译**的方式解决跨架构构建问题（现代 vLLM 处理平台特化 kernel 的标准模式）。技术上：prologue + 两阶段 recurrence 融合，recurrence 直接读写 paged state cache（消除 gather_initial_state 与最终 scatter），状态更新沿 K 维度与 chunk token 维度再拆分以提升 CU 占用率，TTFT 降低约 **5%**。新增 `--kda-prefill-backend=fused` 且支持时默认启用。

### 3. 【#56228】DeepSeek-V4.1-Flash 模型定义合并 — 从 #56214 拆分

从超大 PR #56214 中按目录拆分，只含 `vllm/models/deepseek_v4_1/`（含 nvidia / amd / common 三路径）及对 `vllm/models/deepseek_v4/` 的修改。Rebase 冲突解决方式值得注意：将 `QUANTIZE` toggle、`NOPE_DIM` rope offset、UE8M0 scale packing 移植到 #50176 引入的 `VllmTritonJitKernel` 新类结构上，并保留 `launch_pdl=current_platform.is_arch_support_pdl()`。

### 4. 【#56098】ROCm 多流共享专家 + wvSplitKrc 修复 — 正确性与性能并重

定位到 #48223 被 revert 的正确性根因：`wvSplitKrc` 使用静态 buffer 但被多流并发访问。修复方案为**扩容 8x（每 buffer 7.5 MiB，共 60 MiB）+ 按流分槽**，超出容量时回退到 on-demand 分配（安全但有开销），并处理"stream A capture、stream B replay"场景。同时修复 `wvSplitKrc` 在特定 GEMM 形状下静默截断 readback 的潜在 bug，以及 `topk_topp_triton` buffer cache 与 KV cache 段复用导致的无法释放问题。

### 5. 【#56343】ROCm 大 H2D 拷贝分阶段 — 权重加载 2.1x 加速

DeepSeek-V4.1-Flash 权重 475 GiB，每次 tensor 的 H2D 源都是 file-backed page；超过 `GPU_PINNED_MIN_XFER_SIZE` 时 HIP runtime 会注册这些页，每次注册的 MMU notifier 让 KFD 挂起进程 GPU 队列，**无错误无警告，只是变慢**。将阈值上调到 4 GiB 使权重级传输走 staging 路径：**231.75 s → 108.31 s**。该 PR 与 sglang#37720 是同一机制在 vLLM 侧的对应修复。

## 💡 值得关注的问题

### 1. ROCm Docker 镜像发布流程断裂（#56384，开放中）
官方 recipe 页面指引的 `vllm/vllm-openai-rocm:deepseekv41-flash-0909` tag 在 Docker Hub 上不存在，多个镜像站均 404/403。**这直接影响 AMD 用户按文档部署 DSv4.1 的体验**，建议关注 AMD 团队如何修复镜像发布与 recipe 同步机制。

### 2. gfx942/gfx950 上新架构的硬编码假设（#56314 / #56359 / #56380）
连续出现的 ROCm bug 都源于**针对 DeepSeek MLA 的硬编码假设被其他模型复用**：
- AITER `mla_a8w8` kernel 硬编码 576B 行宽
- MXFP4 intermediate size 硬编码 256 对齐
- indexer storage page 粒度未随 `MLAAttentionSpec.storage_block_size` 传导

**建议**：随着 NoPE MLA（GLM）、稀疏 MLA（DSv4）、MTP 等变体增多，需要在 AME/AITER 层建立参数化或形状守卫机制，避免静默内存越界。

### 3. DeepSeek-V4.1 在 ROCm 上的运行时稳定性（#56347）
`FULL_DECODE_ONLY` + 异步调度在第 3 个 decode token 确定性 segfault，`--no-async-scheduling` 可规避。这是一个**异步调度与 CUDA Graph 交互**的深层问题，可能与 #56349（breakable CUDA graph 自动启用）有重叠但可能独立。需 AMD runtime 团队介入定位。

### 4. DeepSeek-V4.1 AMD 路径的双重反量化 bug（#56214 讨论）
andyluo7 在 8×MI300X / gfx942 上发现 `EmulationMxfp8LinearKernel.process_weights_after_loading()` 将 `wo_a.weight` 转为 BF16 但保留 scale 元数据，`_get_cached_wo_a_bf16()` 随后重复应用 scale。修复仅一行（`wo_a.weight.element_size() == 1` 守卫），但影响**所有 gfx942 MXFP8 路径的正确性**。该修复已推到 fork，等待 rebase 后合入。

### 5. 静默配置失效类问题（#56283 / #56319）
`--cpu-offload-gb` 被接受并出现在 non-default args 中，但 `NoopOffloader` 静默选中、权重从未 offload，**唯一症状是 OOM**。提交者 raj-parihar 与 shoemoney 的协作过程值得关注：shoemoney 明确表示"这不是竞争关系，你的修复才重要"，展现健康的社区协作。根因疑似 `VllmConfig` 跨 `context.Process` pickle 边界时 `cpu_offload_gb` 丢失，但双方都未能从源码确认。

### 6. 贡献者流程摩擦（#50706 / #56213）
- #50706：修复者无 4 个已合并 PR，CI 永不运行，形成修复无法验证的僵局。
- #56213：harelhuang 提交 functionalization 修复后，DengZhiyuan-math 表示"我也在积极处理 #56041，能否比较方案"。

**建议**：项目可考虑为高质量首次贡献提供 `ready` 标签代理机制，或建立重复工作的 early-coordination 渠道。
