#### 🚀 性能优化

**1. [#62371](https://github.com/vllm-project/vllm/pull/62371) [ROCm][Compile] Fuse AITER static FP8 quant into MLA attention output（已合并）**
- 贡献者：AndreasKaratzas
- 技术要点：新增 `RocmMLAAttnFp8StaticQuantPattern`，对齐非 MLA attention 的 `RocmAttnFp8StaticQuantPattern`（#58099）。在 DeepSeek-Coder-V2-Lite-Instruct-FP8 上，MLA 输出量化融合匹配的层数从 0/27 提升至 27/27。
- 关键细节：仅做匹配反而使 decode 慢 2.4%，原因是融合路径先算 bf16 再 `QuantFP8 + copy_`；最终改为让 AITER quant 直接写入 FP8 输出，性能恢复中性。作者明确这是 **parity 而非加速**——真正的加速需要 v_up_proj BMM 直接输出 FP8。
- 验证环境：MI300X + AITER v0.1.25 + `VLLM_ROCM_USE_AITER=1`

**2. [#62270](https://github.com/vllm-project/vllm/pull/62270) [ROCm][Perf][MiniMax-M3] Enable the fp8 indexer cache on gfx942（开放）**
- 贡献者：akii96
- 在 MI325X (gfx942) 上解锁 `indexer_kv_dtype=fp8`，Triton scorer 使用 e4m3**fnuz** 缓存。KV cache 容量从 4.55M 提升到 6.02M tokens（**+32%**），长上下文吞吐提升 +4.0%、TPOT 改善 -5.3%。gfx950（MI350）与 CUDA 路径保持不变。

**3. [#62381](https://github.com/vllm-project/vllm/pull/62381) [ROCm][Perf] Skip the AITER packed GDN path under speculative decoding（开放）**
- 贡献者：zhentaocc
- 在 Qwen3.8-27B + DFlash2 投机解码下，AITER packed qkvz/ba 路径从未走到 decode kernel，只增加 unpacking 开销。改为回退通用 `forward_cuda`，单 MI355X 上吞吐 +1.5%~1.7%，每步 GPU 时间减 400–600 µs。GSM8K 从 0.785 微降至 0.783（3 道题）。

**4. [#62131](https://github.com/vllm-project/vllm/pull/62131) [ROCm][Perf][DSv4.1] Mono decode for the DSpark draft layers（已合并）**

**5. [#61819](https://github.com/vllm-project/vllm/pull/61819) [ROCm][DSv4] Overlap the unfused shared expert with AITER MegaMoE（已合并）**

**6. [#62335](https://github.com/vllm-project/vllm/pull/62335) [ROCm][Perf][DSv4.1] Tune MoRI decode dispatch grid（已关闭）**
- 贡献者：karverma-amd（AMD 员工）
- 作者自行关闭并公开了重要的**反向工程经验**：在均匀 8k/1k 合成流量上 MoRI 128×16 网格带来约 4% TPOT 改善，但在**生产级 131k token 且 rank 不均衡**的真实场景中端到端回归约 15% TPS。原因：MoRI dispatch/combine 有 grid-wide barrier，会等待最慢 rank，更宽的网格让更多 CU 在等待中空闲。作者指出真正瓶颈是暴露的 combine all2all（约占 47% 设备时间），需要 fused-combine MoE 路径解决——这是一条对社区理解 MoRI/EP 性能模型极有价值的负面结果。

### 💬 高热度讨论分析

#### 1️⃣ [#62383](https://github.com/vllm-project/vllm/issues/62383) — Qwen4Exp 在 262,144 原生上下文边界 CUDA 崩溃（4 条评论，持续升级中）

**核心议题**：v0.32.0（含 release 镜像与 nightly）中，单个 prefill 一旦 token 数超过模型的 `max_position_embeddings = 262,144`，EngineCore 立即报 `CUDA error: an illegal memory access was encountered`。v0.31.1 正常。

**不同观点与发现**：
- **timebubble（报告者）**：系统性二分发现 **MTP 投机解码 + CUDA graphs 同时开启**才会触发；去掉任一即恢复（eager 或关闭 MTP 时 262,416 token 可通过）。进一步收缩阈值至 (260,207, 262,190]。
- **wtogami**：在 **SM120 (RTX PRO 6000)**、TP=1、YaRN factor=2.0→512K 上独立复现，证实触发关键是**原生 262,144 边界**而非外推比例；日志显示 `NVRM: Xid 31 MMU Fault: FAULT_PDE ACCESS_TYPE_VIRT_READ`，是**越界读**；受害 kernel 在 FlashInfer GDN、CUTLASS fused-MoE epilogue 等之间漂移，说明是"检测点"而非"根因"。
- **时间维度**：报告者确认 release 镜像同样复现，排除 nightly 特有问题。

**争议/待定焦点**：根因尚未定位。报告者已排除 attention page size 对齐假设（262,190 已崩溃，未到 82 页边界）；`mrope_positions_factor()` 的 RoPE 缓存假设也被 wtogami 部分否定。当前指向 `rejection_sampler.py` 与 cudagraph 在 MTP 路径下的交互。

**状态**：Open，无官方回应；影响 v0.32.0 生产可用性的严重 bug。

#### 2️⃣ [#45800](https://github.com/vllm-project/vllm/issues/45800) — MiniMax-M3 在 FlashInfer MNNVL all-reduce 上 hang（9 条评论，已因 stale 自动关闭）

**核心议题**：2-node TP=8 非 MNNVL 拓扑上，`fused_allreduce_gemma_rms_norm` 路由至 FlashInfer all-reduce，后者**自动选择 MNNVL backend**，最终在 `torch._symmetric_memory.rendezvous` 死锁（CUDA graph capture 43/51 卡住）。

**不同角度**：
- **lazariv（报告者）**：`MNNVL 0`、`NVLS_NCHANNELS 0` 表明无多节点 NVLink fabric，但 backend 仍被 auto-select。py-spy 显示堆栈终止于 `flashinfer/comm/trtllm_mnnvl_ar.py` 而非 NCCL。
- **rehan243（社区）**：连续猜测 NCCL 版本、`CUDA_MODULE_LOADING=LAZY`、驱动更新三条路径，均被报告者以证据驳回（NCCL 2.28.9 正常、LAZY 无效、HPC 平台无法升级驱动）。该讨论典型反映了社区排障时"经验猜测 vs 系统性证据"的往复。

**争议焦点**：问题本质是 **FlashInfer 的 backend auto-selection 缺少对非 MNNVL 拓扑的可达性检查**，而非 vLLM 侧；但 vLLM 作为调用方是否应增加拓扑守卫（如显式传入 `backend=PYNCCL`）尚无定论。

**状态**：2026-10-19 因 90 天无活动被 bot 关闭，问题**实际未解决**；社区应关注是否可以 reopen 或转 issue。

#### 3️⃣ [#48019](https://github.com/vllm-project/vllm/issues/48019) — Text PEFT LoRA 对 wrapper 模型静默 no-op（8 条评论，仍未解决）

**核心议题**：PEFT adapter 键以 `base_model.model.model.layers.0...` 形式加载后，strip `base_model.model.` 得 `model.layers.0...`，但 wrapper 模型（如 Qwen3-VL）实际模块位于 `language_model.model.layers.0...`，无匹配 mapper 规则，adapter 加载成功却完全不生效。

**多方观点演进**：

- **VBS2004（修复者）**：定位到 `qwen3_vl.py` 的 `hf_to_vllm_mapper` 缺 bare `"model."` 规则，提出"追加到最后"的方案；参考 `qwen2_vl.py` 已有先例。
- **ErenAta16（扩展调查）**：确认 llava、pixtral、gemma3_mm、minicpmv4_6、rvl 等 **9 个模型** 有同样问题；发现 `fuyu.py` 已从 main 移除故剔除。
- **Scope 分歧**：讨论明确两种路径——(a) 先合 Qwen3-VL 最小修复（#48022），再单独提交全量修复（#48149）；(b) 统一在 `_mark_language_model` 层做通用修复。社区倾向 (a)，但通用方案仍未落地。

**状态**：Open，部分修复已提交（#48022、#48149）；**新增发现 PaddleOCR-VL 也有同类问题**（wangxiaofanw 提交 #61811）。核心抱怨是"silent no-op"——应至少增加 warn/error，但未实现。

#### 4️⃣ [#62259](https://github.com/vllm-project/vllm/pull/62259) — DeepSeek DSML 工具调用截断参数修复（6 条评论，已 APPROVED 待 merge）

**核心议题**：DeepSeek V3.2/V4/V4.1 的 DSML parser 在 `max_tokens` 截断或 stop string 时，`_PARTIAL_PARAM_RE` 仅在 `partial=True` 生效，导致流式与非流式输出不一致（一个输出截断 JSON，一个输出空 `{}`），且长参数重复正则转换呈二次复杂度。

**多方验证**：
- **JohnZhao01**（4×H200 端到端）肯定效果但指出两个问题：(1) V4.1 单测未传 `tools`，parser 实际未被调用；(2) partial close marker 残留在参数值里。
- **deep1blue** 逐条修复，并新增 5 个 cut point × partial True/False 的测试。
- **smiyamoto3** 发现第三个问题：**重复参数名**（`name="city"…>Paris` 后再出现未闭合 `name="city"…>Lyon`）会污染流式输出，deep1blue 修复后 APPROVED。
- 修复效果：非法 JSON 截断工具调用从 28.6%/43.3% 降至 **0%**。

**争议焦点**：流式与最终转换语义一致性的边界条件（重复名、partial marker、非字符串值）需系统性覆盖——这是 LLM tool parser 的一类通用问题。

#### 5️⃣ [#62365](https://github.com/vllm-project/vllm/pull/62365) — DSv4.1 bitwise batch invariance（3 条评论，PR 仍 Open）

**核心议题**：28 commit 的巨型 PR，让 DeepSeek-V4.1-Flash 在 `VLLM_BATCH_INVARIANT=1` 且 CUDA graphs 开启时，token/logprob 与 batch 组成、chunk size、prefix cache 命中无关，可用于 RL on-policy 训练。

**不同观点**：
- **ISEEKYAN（review 者）** 在 GB200 上用前 4 层 proxy 模型发现：**short prompt（≤16 token）在 PIECEWISE graph 与 eager 下不一致**（token 114044 vs 13265），且各自内部确定。后续更正："不是 race"，而是 graph 内 capture 的 per-step preparation（compressor state、KV insert、indexer preparation）可能存在副作用。长 prompt（≥131 token，超出 capture range）与 eager 一致。

**争议焦点**：BI 语义与 cudagraph 边界的交互尚不清晰，PR 作者需回应 ISEEKYAN 的 4 层 proxy 复现。这是 RL 场景 batch invariance 正确性的关键路径。

### 🛠️ 重点技术变更

**1. [#62074](https://github.com/vllm-project/vllm/pull/62074) Reflection Beam-1.0 新模型支持（已合并）**
- 501B MoE（23B active），混合 sliding-window (RoPE) + full-attention NoPE，per-head Q/K norm、sigmoid output gate，DeepSeek-V3 式 FP32 router MoE，sandwich norms + depth-scaled residuals。配套 DFlash2 drafter、Beam/beam reasoning parser、专用 tool call parser。
- **意义**：day-0 支持商业新模型，同时引入 MNNVL one-shot/two-shot all-reduce 与 MoE finalize 融合（[#62366](https://github.com/vllm-project/vllm/pull/62366) 复用）。

**2. [#60896](https://github.com/vllm-project/vllm/pull/60896) CUDA < 13 上为 SM80-SM90 构建 fused GDN MTP decode（已合并）**
- `FUSED_GDN_DECODE_ARCHS` 只在 CUDA ≥ 13.0 分支设置，此前所有 CUDA 12.x 发布镜像（含 cu129）**完全缺失 GDN spec decode kernel**，只能走 Triton 回退。
- 验证：A100 + nvcc 12.9 下 71 passed/29 skipped → **102 passed**；kernel 时间为 Triton 路径的 0.48–0.76 倍。
- **影响**：显著提升 CUDA 12.x 上 GDN 模型（Qwen3.8-Flash-Next 等）spec decode 性能。

**3. [#62338](https://github.com/vllm-project/vllm/pull/62338) Sliding-window cache hit 跳空洞（开放）**
- 将 `find_longest_cache_hit` 的 O(max_num_blocks) 从右向左扫描替换为 strided probe lattice。128K token 请求、4K window、冷 cache：`get_cached_block` 调用从 8192 降至 33 次，函数级 4.49 ms → 0.021 ms（**~200x**）；同时修复 `sliding_window=1` 无 EAGLE 时的非终止循环。
- **意义**：prefix caching 调度的经典热点；用 **7,339,584 案例** 穷举证明 hit 语义零变化，是高质量的性能 PR 范式。

**4. [#62326](https://github.com/vllm-project/vllm/pull/62326) `process_weights_after_loading` 保持参数对象（开放）**
- 建立全局不变量：PWAL 之后每个 loader-visible 参数在**同名、同对象**下注册，`replace_parameter` 默认 `copy_` 而非重新注册，`prefer_copy=False` 为显式 opt-out。被消费的参数保留空存储，重命名走 `move_parameter`。
- **意义**：RL refit / 权重热重载的正确性基础；影响整个量化与模型加载栈。

**5. [#62307](https://github.com/vllm-project/vllm/issues/62307) `kv_transfer_params` 覆盖 chat template（Open）**
- 渲染器在无 KV connector 时仍接受 `prompt_token_ids` 替代 render，绕过 template/truncation/tokenization。首现于 0.27.0 (#48145)。
- **意义**：虽被定性为"仅影响请求者自身响应"，但属提示注入面；建议的修复（检查 connector + 检查 endpoint）尚未提交 PR。
