### 💬 高热度讨论分析

#### 1. PR #49347「在线 MXFP4 量化」——AMD 范围 vs NVIDIA 兼容性争议

这是本周期争议最激烈的 PR。NVIDIA 用户 **bvolpato** 在 RTX 5070 Ti（SM120）上实测发现三个问题：① 自动后端选择器选了 FlashInfer 但该后端不支持 capability 120，启动失败；② 强制 Marlin 后 20 道算术题仅对 3 道（BF16 基线 19 道），质疑小模型精度；③ 通用 CUDA 上 MoE 会选择 MXFP4 emulation kernel 但未安装 `amd-quark` 导致启动崩溃。

AMD 维护者 **AndreasKaratzas** 回应："The PR is trying to add online quantization support of MXFP4 for AMD hardware. We do not have access to the hardware you are referring to and it is also outside the scope."——表面 AMD 定位。但 **fxmarty-amd** 随后以更缓和的方式接手，指出公平对比应是与离线 MXFP4 checkpoint + marlin 比较而非 BF16，并将 flashinfer 后端能力和精度问题分别引导至独立 PR/Issue。最终 PR 合并，但 NVIDIA 侧的兼容性问题仍未完全解决。

**争议焦点**：AMD 维护者是否应为一通用特性（在线量化）承担在非 AMD 硬件上的兼容性责任。

#### 2. PR #48534「MoRIIO READ 模式 per-layer barrier」——正确性 vs 性能的对立

edwinlim0919 提交的修复解决了 MI300X P/D 分离场景下 READ 模式 KV 数据未就绪即被注意力读取的竞态问题——通过引入 per-layer completion barrier 并要求 PIECEWISE CUDA graph。但 AMD 工程师 **tjtanaa** 报告：该 PR 导致 MiniMax-M3 在 TP<->TP 场景下输出吞吐下降 65.53%，因为禁用了 fullgraph 模式。

作者坚持正确性优先："without this PR, the decode node is not guaranteed to have all of its KV data transferred"，并称已在 concurrency 1024 下复现精度问题。随后 **tanpinsiang** 在 MI355X 上做了对照实验：MiniMax-M3 高并发下无精度差异，但吞吐从 4,830 tok/s 降至 4,038 tok/s、TPOT 从 28.97ms 恶化到 88.19ms；而 DeepSeek-R1-0528 上精度确实从 93.78% 提升至 96.06%。

**争议焦点**：不同模型/负载下正确性与性能的权衡取舍不同——MiniMax-M3 无精度收益却承担大幅性能损失，DeepSeek-R1 收益显著。该 PR 最终合并，但后续 follow-up（#49643）正在讨论如何恢复 FULL CUDA graph 模式。

#### 3. Issue #51454「DP8 vs TP8 for single-KV-head MLA」——并行策略的实证研究

stewtong 发布的深度性能报告：单 8×B200 节点上，DeepSeek-V4-Flash-0731（304B/13B active，MLA，1M context）在 TP8 下 KV 容量仅 20.43x 最大并发，而 DP8 达到 156.9x（7.7x 提升），因为 MLA 的单一 KV head 无法在 TP 维度切分导致 KV cache 被复制 8 倍。实测 1M context 并发 8 时 TTFT 从 314.1s 降至 91.3s（3.44x）。作者还在评论中补了同节点对照实验，排除跨节点误差，并向 recipes 仓库提交了将 DP8 设为默认策略的建议（#762）。

虽然评论数不多，但每一条都是高质量的数据补充，展示了社区对大规模长上下文推理性能的实证精神。

### 🛠️ 重点技术变更

**1. PR #49347「online MXFP4 量化」（已合并）——量化范式升级**
用户可直接对未量化模型启用 MXFP4，无需预先离线量化。配套提供了 `downcast_to_mxfp` 的 Triton 回退实现，统一 XPU/AITER/fallback 三路。对 AMD 生态的意义在于：`amd-quark` 产出的 MXFP4 checkpoint 和线上实时量化现在可以共享同一套推理路径，降低了用户使用 MXFP4 的门槛。

**2. PR #47972「DeepSeek-V4 Quark NVFP4 支持」（已合并）——AMD 量化模型接入**
为 Quark 增加了 per-block FP8 支持（`QuarkW8A8Fp8PerBlock`），并将 DeepSeek-V4 特定的 fused 模块映射移出通用配置，避免架构知识泄漏到 QuarkConfig。还统一了 NVFP4 MoE fused w13 的 global-scale 处理逻辑，与 ModelOpt/compressed-tensors 的行为一致。

**3. PR #51434「DeepSeek V3.2 序列并行优化」（已合并）——全层 SP 数据流**
此前 SP 仅对 MoE 层启用，导致 dense/MoE 边界反复做全量-切分转换。此 PR 将 hidden/residual 状态在所有 decoder layer 保持序列切分，dense MLP 在 SP 下复制（每 worker 多占 0.63 GiB 显存），并使用优化后的 communicator collectives。这是对 DeepSeek-V3.2 数据流的一次系统性重塑。

**4. Issue #51454「DP8 vs TP8 for MLA 长上下文」——部署最佳实践实证**
该报告用严谨的实验数据证明：对单 KV head 的 MLA 模型，TP 并行会复制 KV cache，而 DP8（配合 EP）可提升 7.7 倍 KV 容量、3.44 倍 TTFT。它直接影响 1M context 场景的部署选型，建议 recipes 将 DP8 设为 B200 默认。

**5. PR #51402「不拆分读写同一 batch 的 prefix 依赖步骤」（已合并）——CI 间歇性失败的根因修复**
AMD CI 中 `test_dbo_dp_ep_gsm8k` 约每两次跑失败一次，GSM8K 精度锁死在 0.65 或 0.60 二选一。根因是 microbatch 将一个请求计算 prefix、另一个请求读取该 prefix 的步骤拆成两半，读者先于写者执行、读到全零 KV。修复方式是通过已有的 `allow_microbatching` 钩子在检测到同步骤跨请求 prefix 依赖时禁用 microbatch，并已合并。

### 💡 值得关注的问题

1. **DeepSeek-V4-Flash 结构化输出崩溃（#51467）**：单次 `response_format: json_object` 请求即硬崩 EngineCore 和所有 TP worker（tensor size 4040 vs 4041）。涉及 DSpark 投机解码 + FP8 KV + TP4，影响面大，目前无评论、无修复 PR，建议保持关注。

2. **在线 FP8 输出完全损坏（#51456）**：`--quantization fp8` 在 Qwen2.5-1.5B 上产生乱码且永不 EOS（100% 触达 max_tokens）。在线量化是新功能，此问题若蔓延到更多模型将削弱用户信任。

3. **AMD MI300 CI hang 的处理方式争议**：两个 MI300 CI hang 被维护者以"don't panic"关闭，未做根因调查。考虑到 hang 发生在与 KV offloading 调度完全无关的 PR 上（`OffloadingConnector` 出现 0 次），可能是环境级别的不稳定而非代码回归，但社区用户明确表达了"需要调查"的诉求。

4. **MoRIIO FULL CUDA graph 模式缺失（#49643）**：PR #48534 为了正确性强制 PIECEWISE，导致 TP 场景 65% 吞吐损失。RFC #49643 提出的恢复 FULL graph 方案值得关注，它决定了 P/D 分离 + KV transfer 能否在高性能场景落地。

5. **Kimi-K3 工具解析器流式原始标记泄漏（#51412）**：`<|close|>message<|sep|>` 标记原样进入 content，影响生产可用性。

6. **混合稀疏注意力 + Eagle 的 prefix 缓存全 miss（#51441）**：特定 prompt 长度（非 256 倍数、1536+[1,127]）触发完整 cache miss，这会影响带投机解码的长上下文场景的命中率，已有 PR #51295 提出修复。
