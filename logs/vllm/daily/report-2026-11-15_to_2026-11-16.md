### 💬 高热度讨论分析

#### 1. #67802 — FP8 动态 per-tensor amax 混入 CUDA-Graph 填充的陈旧 Token ID（2 条评论，技术深度高）

- **核心议题**：V2 model runner 为 CUDA graph 分配持久 buffer 并按捕获尺寸填充，但内核只写 `[0, num_tokens)`，padding 行保留上一批次或 warmup 的陈旧 token id。dense FP8 线性层在 `x.view(-1, K)` 上做单一 per-tensor `amax` 归约，**padding 行直接污染量化 scale**，导致同一 prompt+seed 因引擎请求历史不同而产生不同 greedy logits，且异常值会粗化有效 token 的量化精度。
- **讨论过程**：
  - `brianosaurus` 确认诊断在当前 main（`919d45fc3a`，`model_runner.py:1650-1651`）成立，并在 CPU nightly 复现：B 的动态 per-tensor scale 在历史 A1 后为 0.014718、A2 后为 0.154018，**per-tensor 12/12 行不同，per-token 0/12 不同**，精确锁定到 per-tensor 路径。
  - 他提出两个设计选项：**(A) 复用 `is_padding` mask**（如 #62138 对 MoE 的做法 `masked_amax_scale`），但需把 mask 通过 forward context 传递到每个 dense per-tensor-FP8 层；**(B) 每步清零 padding 行**，改动小但可能无法消除异常值对 scale 的影响。
  - 询问是否应等 #62138 落地。
- **争议焦点**：mask 透传的侵入性 vs 清零的彻底性；以及是否将本修复与 #62138 绑定。
- **当前状态**：Open，等待作者 `Yunzez` 回应设计选择。这是一个**影响确定性与静默精度退化**的正确性 bug，优先级应较高。

#### 2. #67750 — 单内核融合 top-k/top-p 采样器（4 条评论，性能回归的快速迭代）

- **核心议题**：v1 在种子请求或无法使用 FlashInfer 时走多 pass 路径（`apply_top_k_top_p_triton` 写回 HBM + `gumbel_sample` 重读），新增 `fused_topk_topp_sample` 寄存器内完成过滤与采样。作者在 A100 上报告 96 组配置位级一致，32k vocab batch 64 下 2.78–3.76x。
- **不同角度**：
  - `hclsys` 在 **GB10 (sm121)** 复测：96/96 通过，但指出 **batch 1 变慢**（152k vocab topk_partial 0.016→0.094 ms，topp_whole 0.079→0.250 ms），且 **unfiltered 在作者版本中反而走了融合内核而变慢**；还发现与 **#59804** 的 tie-breaking 行为分歧（24 个并列 logits、k=20、p=0.8：stock 保留 20，融合内核保留 24）。
  - 作者 `bandham-manikanta` 回应：已修复 dispatch，unfiltered 回退标准路径（A100 上恢复 ~0.08–0.09 ms）；batch 1 慢是单 program 不跨 SM 拆分导致；#59804 相关逻辑暂与 main 保持一致，等其落地后跟进。
  - `hclsys` 复跑新 commit，确认 unfiltered 已与 stock 对齐。
- **结论/状态**：Open，跨平台（A100 + GB10）验证闭环，剩余问题为 batch 1 小开销与 tie-breaking 待 #59804。**展示了 vLLM 性能 PR 的典型 review 模式：第三方硬件复测 + 作者快速修正。**

#### 5. #67849 — MXFP4 MoE 在 TP 部署优先 b12x（作者自我撤回，性能与精度的取舍）

- **核心议题**：`_get_priority_backends()` 在 `moe_backend=auto` 的 MXFP4 MoE 路径从不提供 b12x，尽管 `B12X_MXFP4_MXFP8`/`B12X_MXFP4_BF16` 在 SM120 上比 DeepGEMM 便宜。作者在 8×RTX PRO 6000 上测得吞吐提升。
- **转折**：作者 `positive666` 自行做数值对比后**主动撤回**——同 checkpoint、TP8、temperature 0、10 prompts×32 tokens 下，DeepGEMM vs DeepGEMM 对照为 **320/320 token 完全一致**，而 DeepGEMM vs b12x 仅 **47/320 (14.7%) 一致**，中位 |dlogprob| 0.039、最大 13.22、top-5 Jaccard 仅 **0.124**。作者判断 b12x 的 MXFP8 激活路径与专家校准不匹配，"不是一个舍入差异，而是不同分布"。
- **意义**：这是**性能优化因精度风险被主动否决**的典型案例，对照组设计（同后端两次重启）严谨，值得作为 MoE 后端选型的参考。状态：Closed（未合并）。

### 🛠️ 重点技术变更

#### 1. #65992 — DeepSeek-V4.1 融合 mHC seam 改为 AITER 单 launch HIP Mega-MHC（Merged，ROCm）

gfx950 上每个 decoder 层有 2 个 fused delayed mHC seam（DSpark draft 另有 1 个），此前由 AITER 的**两次 launch 的 Triton 内核**（#58655）承担，#59802 的 gates 跑在侧流。本 PR 改用 AITER 的 HIP Mega-MHC（ROCm/aiter#6520），**一次 launch 完成 seam**：微基准每 seam 16–41% 提升，C256 解码步约 1% 关键路径、4096 token prefill 步 1.6–1.9%。精度方面 GPQA Diamond 88.64%±0.76 vs main 89.08%±1.35，剔除 65,536 token 截断后 91.9% vs 91.7%。**影响**：这是把"每层必跑路径"从两次 launch 压到一次的典型收益，虽单次收益小，但乘以层数后对 DP/EP 大并发下的 launch 开销敏感场景有累积价值；也验证了 AITER 的 HIP 内核可替换 Triton 实现而不损精度。

#### 2. #65658 — PP 阶段间张量改走 SDMA copy engine（Merged，ROCm）

ROCm 上 NCCL send/recv 的 peer copy 是占用发送方 CU 的 blit kernel，实测 8192³ bf16 GEMM 在旁路 201 MiB 拷贝时**慢 5.1x**。本 PR 新增 `--pp-sdma-handoff`：接收阶段分配 3 个槽位并共享 CUDA IPC，发送线程经两个 SDMA 引擎拷贝（不占 CU），通过 `/dev/shm` 的 `ready`/`freed` 计数器同步槽位复用。关键工程细节：选择 ctypes 调用 `hsa_amd_memory_async_copy_on_engine` 而非 HIP API，因为 HIP 7.16 的 `hipMemcpyBatchAsync` 前缀标志对 D2D 无效，而 `hipMemcpyDeviceToDeviceNoCU` 在 MI355X 上 peer copy 返回 `hipSuccess` 却实际跳过拷贝。**限制**：仅 PP2×TP1、gfx950、单节点、eager。**影响**：为 PP 场景提供了不干扰计算的 stage hand-off 通道，`njhill` 已提出抽象化以支持 #66677。

#### 3. #62708 — RDNA 加载时 int4 LM head 量化（Merged，ROCm）

新增 `int4_per_group_32_asym`（非对称 uint4，每 32 输入通道一组 scale+zero point），在加载时量化未量化的 fp16/bf16 `ParallelLMHead`，走平台混合精度线性内核（gfx11/gfx12 为 `RDNAHybridW4A16LinearKernel`），无 C++ 改动。动机：Qwen3.6-35B-A3B 的 lm_head 为 248320×2048，约 970 MB/token，在 Strix Halo（211 GB/s）上每步 4.5 ms，是解码最大单项。**影响**：把"在线量化"从稠密层扩展到 LM head，对消费级/工作站 RDNA 的内存带宽瓶颈场景有直接意义；`fxmarty-amd` 的多轮 review 也把文档披露与测试命令纳入合并门槛。

#### 4. #66938 — Mamba mid-block 恢复 prefill 从 3 步压到 1 步（Merged，通用）

混合模型 "align" 前缀缓存下，若请求从中途 Mamba block 恢复且 prompt 在下一 block 结束，main 会分 3 步（停在 block 边界、停在 checkpoint、剩余）。本 PR 允许 checkpoint 状态**写入请求恢复时所在的 block**（其 block table 中），一次 forward 完成。Kimi K3.1 TP8+DCP8 示例：请求 2 TTFT 0.69 s → 0.25 s，`cached_tokens` 与前缀缓存计数器完全一致。构建在 #67717（防止 mid-block 越过的 block 获得完整 hash）之上。**影响**：对多轮 agent/编程对话这类"长前缀 + 短追加"的典型负载，TTFT 收益直接。

#### 5. #64641 — Daemon 到 Daemon 权重镜像（Merged，通用）

第二个副本的 daemon 从已加载副本填充分片而非重读 checkpoint，采用 #60086 的 storage-manifest + mover 数据面，但把镜像实现为"使用 `peer_cache` 加载格式的普通 daemon"。同主机走 CUDA IPC，跨主机走 Mooncake RDMA，比较 `WeightCacheKey` 指纹后才传输。DSv4.1-Flash 502 GiB 双节点传输 ~9.3 s（~54 GiB/s 聚合，4 块 RoCE 网卡）；Qwen3-30B-A3B tp=4 冷启动 230 s → 100 s（2.3x）。控制面纯 JSON 且在解码前鉴权（不接收不可信 pickled 数据）。**影响**：对大规模副本扩缩容与故障恢复的启动时间有实质改善。

### 💡 值得关注的问题

1. **#67802 FP8 amax padding 污染**：影响确定性（`seed` 不可复现）与静默精度，是量化正确性的高优先级 bug。需要维护者对"mask 透传 vs 清零"给出方向，并明确与 #62138 的依赖关系。当前仅 1 名贡献者跟进，建议增加复现环境覆盖。
2. **#67774 LoRA rank 校验位置错误**：`max_lora_rank` 检查只在 worker 的 `PEFTHelper.validate_legal` 执行，`InputProcessor._validate_lora` 不检查 adapter，导致超限 adapter 直接杀死引擎（`EngineDeadError`）且后续无 LoRA 请求也失败。**这是"校验应前置到前端"的设计模式问题**，同类问题可能在其他资源约束上也存在。
3. **#67834 FlexAttention 三个独立失败**：hybrid 模型 recompile limit 16、非 2 次幂 cache block size 启动拒绝、SM89/GB10 的 99 KiB smem 限制（GB10 sm121 实测 299008 > 101376）。已有两位贡献者认领 Part 2 与 #3 的复现，但 Part 1（动态 query 长度编译）尚无方案。
4. **#67862 MiniMax-M3.1 NVFP4 专家加载 192 vs 384**：与 AMD 侧 #67793 解决的是同一模型的不同平台后端问题；混合量化 checkpoint 的加载逻辑在多平台分叉，建议关注是否需要统一的 `RoutedExperts._load_w13` 分片语义。
5. **#67811 自适应 prefill 预算 RFC**：作者明确说明"仅 CPU 仿真、未在 GPU 验证"，TP 允许但未验证，请求级 p99 需另测。**在缺乏真实硬件数据前，不宜推动合入**，但方法论（软 step-time 目标、服务信用与老龄化、异步事件计时而非额外 device sync）有参考价值。
6. **安全修复的跟进**：#67764 关闭后 #67826 重开，扩展了重定向逐跳校验与环境变量开关；#67785 的 P2P allowlist 默认仅 loopback，可能影响现有跨主机部署用户的升级路径，**需要在 release note 中明确破坏性变更**。
7. **#67843 all-reduce 回归修复信息过少**：标题称修复 MI350 上 `ROCM_AITER_UNIFIED_ATTN` 的 all-reduce 回归，但描述仅一行、无复现条件、无验证数据，建议要求补充影响范围（是否影响已合并的性能 PR）后再评审。
8. **AITER/amd-kernels 依赖链**：#67861（AITER post1）→ #67850（需要 FlyDSL 0.5.0）→ Inferact/amd-kernels 后续合入，三者的合入顺序与 CI 缓存策略（`/ci rocm cache`）需要协调，否则 MI355X 镜像与 main 会出现版本漂移。
