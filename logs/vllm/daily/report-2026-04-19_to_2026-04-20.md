**新增 Issue:**
1.  **#40301 - Triton MXFP4 MoE 设备能力检查破坏 RDNA3.5 支持**：用户报告，vLLM中针对Triton MoE内核的设备能力检查被硬编码为 `< (11， 0)`，这错误地排除了所有映射到 `(11， 5)` 的 RDNA3/RDNA3.5 架构（如 gfx1151），导致模型加载失败。核心诉求是放宽此限制以支持AMD新架构。
2.  **#40297 - AMD nightly CI 持续失败**：报告显示，`mi355_1` 硬件的“Kernels Quantization Test”测试组自3月31日起持续失败，表明量化相关功能在AMD平台存在稳定性问题。

**已关闭 Issue:**
- **#25523 - ROCm/vLLM Docker 镜像缺少 MAGMA 和 LAPACK 支持**：此历时近一年的问题被关闭。根本原因是vLLM官方Docker镜像中PyTorch未编译MAGMA支持。维护者提供了基于 `rocm/pytorch` 官方镜像自建的临时方案，并承诺未来版本会加入支持。

**新增/活跃 PR (AMD相关):**

### 💬 高热度讨论分析
1.  **已关闭 Issue #17514 - “[Bug]: tool calling error”**
    - **核心议题**：用户在使用vLLM部署Qwen模型并启用工具调用时，服务器日志中反复出现“cannot determine if tools should be extracted”错误，但客户端仍收到200响应。
    - **观点与进展**：
        - **问题确认**：多名用户（`weiminw`， `shivamashtikar`）报告了相同问题，表明该问题影响多个模型和vLLM版本。
        - **根本原因分析**：维护者 `bbrowning` 通过分析指出，根本原因通常是**模型输出了不符合预期格式的无效工具调用内容**（如未闭合的标签），导致vLLM的解析器失败，从而回退到标准聊天补全流程。
        - **解决方案**：维护者建议用户检查并优化模型的指令遵循能力，或尝试其他工具解析器。此问题因长期无新进展而被自动化流程关闭。
    - **争议焦点**：无实质性争议，更多是问题排查与根因确认。
    - **当前状态**：已关闭。问题根源被定位在模型输出格式，而非vLLM核心逻辑。

2.  **已关闭 Issue #23992 - “vLLM Deployment of Qwen3-8B Model Streaming Output Tool Content Missing Issue”**
    - **核心议题**：用户发现使用vLLM部署Qwen3-8B模型时，非流式调用可以正常返回工具调用内容，但流式调用下工具内容缺失。
    - **观点与进展**：
        - **广泛影响**：问题在`coach00`， `old-kai`， `pcfreak30`等多个用户的回复中得到确认，影响Qwen系列不同规模的模型。
        - **关联修复**：有用户提及另一个PR（#22975）修复了非流式调用的问题，但流式问题依旧。
    - **争议焦点**：无。
    - **当前状态**：因超过90天无活动被自动关闭，但问题本身可能仍然存在，反映了流式工具调用支持的历史痛点。

3.  **已关闭 Issue #25523 - “[Bug]: MAGMA and LAPACK support for pytorch missing for rocm/vllm images”**
    - **核心议题**：vLLM官方提供的ROCm Docker镜像中，PyTorch未编译MAGMA和LAPACK库，导致依赖这些库的运算（如`torch.linalg.cholesky`）无法在GPU/CPU上执行。
    - **观点与进展**：
        - **根因定位**：AMD员工 `hongxiayang` 指出，镜像中的PyTorch是自编译的，未启用MAGMA。
        - **临时方案**：维护者 `gshtras` 建议用户基于已包含MAGMA的官方 `rocm/pytorch` 镜像自行构建vLLM。
        - **长期承诺**：维护者表示将在未来的镜像版本中加入MAGMA支持。
    - **争议焦点**：无。社区和维护者对问题的理解和解决方案达成一致。
    - **当前状态**：已关闭。用户需等待未来镜像更新或采用临时方案。

### 🛠️ 重点技术变更
1.  **PR #40270 - [Feat] GPU KV缓存可插拔逐出策略**：这是一个架构性改进。它引入了`GPUCachePolicy`抽象，并实现了`LRU`（默认）、`Two-Queue`和`ARC`三种策略，旨在解决生产环境中因LRU的“频率盲”特性导致的缓存污染问题。**影响**：为高性能、多租户、长上下文场景提供了潜在的显著性能提升空间，是核心调度层的重要演进。
2.  **PR #40281 - [Model] gemma4核心：量化推理+GGUF加载+融合MoE gelu_tanh**：此PR全面增强了Gemma4模型在vLLM中的支持，特别是修复了量化推理（AutoRound， AWQ）、GGUF格式加载以及融合MoE中`gelu_tanh`激活函数支持等关键路径的缺陷。**影响**：使Gemma4系列模型在vLLM中真正达到生产可用状态，覆盖了更广泛的部署场景（如量化、GGUF）。
3.  **PR #40303 - [Bug] 修复 JIT 加载下 shm_broadcast PyCFunction 描述符损坏**：修复了一个深层的、间歇性的生产环境崩溃问题。该问题在运行时动态加载C扩展库（如FlashInfer， Triton）时，会破坏CPython内部结构，导致分布式通信层崩溃。**影响**：极大地提升了使用动态编译内核（常见于优化路径）时vLLM服务的稳定性和可靠性。
4.  **PR #40273 (已合并) / #40313 (Revert PR) - 修复LoRA与MoE后端选择的兼容性**：该PR发现并修复了当使用LoRA适配器时，未量化MoE模型错误地选择了不支持LoRA的FlashInfer CUTLASS后端的问题，强制回退到Triton后端。**影响**：保障了LoRA与MoE模型联合使用的功能正常。其被快速创建Revert PR（#40313）的原因是合并后导致了CUDA CI中某个MoE层测试的失败，**这凸显了在复杂系统中，修复一个兼容性问题可能意外破坏另一个场景的测试覆盖，需要更全面的测试。**

### 💡 值得关注的问题
1.  **RDNA3.5 支持被错误排除**：Issue #40301 揭示了一个可能影响所有使用RDNA3/RDNA3.5 GPU用户的硬编码兼容性限制。需要社区尽快评估并修复，以支持AMD新一代消费级和APU硬件。
2.  **KV缓存逐出策略的引入**：PR #40270 提出的改进方案是一个重要的性能优化提案。其实装效果、对不同工作负载的影响以及最终是否会被合并，值得持续关注。
3.  **稀疏注意力MFU计算失真**：Issue #40315 指出，对于DeepSeek-V3.2这类使用稀疏注意力的模型，vLLM的模型FLOPs利用率（MFU）指标因仍使用稠密公式计算而严重失真，可能超过100%。这影响了该指标作为跨模型性能对比基准的可信度，需要修正。
4.  **MoE后端选择与功能兼容性的平衡**：PR #40273 的“合并-回滚”事件，反映了在众多可选的MoE计算后端（FlashInfer， Triton等）中，平衡性能最优与功能完备性（如支持LoRA）的持续挑战。如何设计更优雅的后端选择器是一个技术设计问题。
