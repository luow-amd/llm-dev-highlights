### 🎯 AMD/ROCm 生态相关动态

本周期 AMD/ROCm 生态是绝对重点，多项关键变更旨在解决 AMD GPU（尤其是 MI355X/gfx950）上的精度、性能和稳定性问题。

1.  **Bug 修复与性能调优（核心）**
    *   **PR #46952 (`xaguilar-amd`)**: **[Bugfix][ROCm][MLA] Pad FP8 MLA decode head count to a native value on gfx950 (fix AITER 0.1.16-post2)**。这是针对 AMD MI355X (gfx950) 的关键修复。当使用 AITER MLA 后端和 FP8 KV Cache 时，如果每 rank 的 heads 数不是 `{16, 64, 128}`（例如 TP2 时的 32 个 heads），AITER 内部会使用一个数值上有 bug 的 `fold` 路径。该 PR 通过将 head 数填充（padding）到下一个原生支持的数值（如 32→64）来绕过该 bug，从而恢复了模型（如 Kimi-K2.5）的 GSM8K 准确率（从 ~0 恢复到 ~0.93）。评论者 `ChuanLi1101` 确认这是一个临时的有效措施。
    *   **PR #46944 (`spandantiwari`)**: **[ROCm][Test] Fix test_per_token_group_quant_fp8 tolerance for 1-ULP FP8 rounding on gfx950**。修复了 MI355 (gfx950) 上一个不断失败的测试。问题源于 PyTorch 和 ROCm 的 Triton 后端在 FP8 量化时，对于处于两个可表示值中间点的输入，采用了不同的舍入方向（均为有效舍入）。该 PR 通过放宽测试容差来解决，而非修改内核。
    *   **PR #44313 (`omirosh`)**: **[ROCm][Perf] Add Fused Shared Expert (FSE) support for GLM-4.5/6/7**。这是一个重要的性能合并！将之前为 DeepSeek 和 Qwen3-Next 实现的 AITER Fused Shared Expert (FSE) 路径扩展到 GLM-4 MoE 模型家族。通过将共享专家折叠进 `FusedMoE` 内核，在低/中并发度下消除了单独的共享专家 MLP 前向计算，显著提升了性能。
    *   **PR #45033 (`xaguilar-amd`)**: **[ROCm][Perf][MLA] Add AITER FlashAttention MLA prefill backend (`ROCM_AITER_FA`)**。为 AMD gfx950 引入了基于 AITER 的 MLA 预填充后端。该后端直接调用 `aiter.flash_attn_varlen_func`，无需像上游 CK-tile 路径那样进行 V 维度填充，且返回的 `softmax_lse` 无需转置，从而减少了内核调用和 CPU 开销。在 gfx950 上自动选择，并会在其他架构上回退。

### 💬 高热度讨论分析

1.  **Issue #46941: `_qutlass_C` 模块缺失导致的告警刷屏**
    *   **核心议题**：当 vLLM 仅针对 SM8.6（如 RTX 3090）编译时，启动日志会因无法导入 `vllm._qutlass_C` 而高频重复打印 `WARNING`，严重影响生产环境诊断。
    *   **观点与立场**：
        *   **用户 `walmis` (报告者)**：描述了问题现象，认为对于不存在的模块，告警应仅打印一次或作为低级别信息。
        *   **分析者 `InfoSage05`**：精确定位了根本原因。`cuda.py` 文件中有两处导入尝试：一处是模块级别的 `logger.warning`（在行 45），每次导入都会触发；另一处在 `import_kernels()` 函数内，已正确使用 `logger.warning_once`（在行 233）。因此，模块级别的 `warning` 调用是告警刷屏的元凶。
        *   **用户 `hclsys`**：提出了一个关键疑问，即正在进行的 PR #46521（将 `_qutlass_C` 设为可选）是否也能解决此问题，并质疑它是否只是修复了错误路径，而非告警刷屏问题。
    *   **争议焦点**：没有实质性争议。问题原因清晰，解决方案（将 `logger.warning` 改为 `logger.warning_once`）明确。讨论更多是对根因的确认和不同修复方案（直接修改 vs. 依赖其他 PR）的考量。
    *   **当前状态**：**开放中**。`walmis` 确认 PR #46521 可以抑制告警，但问题 Issue 本身并未关闭。

### 🛠️ 重点技术变更

1.  **[Spec Decode] DSpark 推测解码支持**（PR #46995, #46965）：两项并行提交，旨在支持 DeepSeek 发布的 DSpark 推测解码模型。其核心创新在于**利用非因果滑动窗口注意力**，通过 SparseMLA 后端实现精确的近似，而非重写注意力逻辑。这有可能在保持推理速度的同时，显著提升模型的接受长度。这是推测解码领域的重要新方向。

2.  **[GLM5.2 Perf] MoE 通信优化**（PR #46635）：将 MoE 层的前向计算通信模式从 `all-reduce` 改为 `reduce-scatter`，声称可带来 3.1%-3.2% 的端到端吞吐量提升。这是一项典型的分布式系统优化，通过减少通信数据量来提升整体性能，同时改进也适用于 DeepSeek 系列模型。

3.  **[ROCm][Perf] GLM-4 Moe Fused Shared Expert**（PR #44313）：将 Fused Shared Expert (FSE) 技术扩展到 GLM 模型家族。这是一种在 ROCm 平台上通过 AITER 库实现的性能优化，将共享专家的计算合并到 MoE 内核中，是 AMD 生态性能持续提升的例证。

4.  **[Core] 在非 Blackwel  GPU 上启用 NVFP4 KV Cache**（PR #46963）：通过 FlashInfer 的 slot-mapping API 将 NVFP4 4-bit KV Cache 的支持下放到 Ampere 和 Hopper 等架构。这可以在无需升级硬件的情况下，为兼容的 GPU 带来近 3 倍的 KV Cache 容量提升，具有极高的实用价值。

5.  **[Bugfix] `_qutlass_C` 警告频刷**（Issue #46941 & 根因分析）：虽然只是一个告警日志问题，但其分析过程（`InfoSage05` 对 `cuda.py` 中 `logger.warning` 和 `logger.warning_once` 的对比分析）生动地展示了 vLLM 代码基中的一个常见模式问题。最终由用户提出的修复方案非常简洁优雅。

### 💡 值得关注的问题

*   **多个 AMD CI 长期失败**：在“已关闭 Issue”中，存在大量标记为 `stale` 的 AMD CI 失败报告（如 `mi300_1`, `mi355_1` 上的各种测试）。虽然这些 CI 问题大多已在内部被修复和关闭，但这暗示着 AMD 平台的测试稳定性仍需持续投入。PR #46978 系列正是为此而来。
*   **KV Offload 在 MTP 模式下不可用**：Issue #46971 和修复 PR #46972 揭示了一个严重问题：当启用 MTP/Eagle 等推测解码时，CPU KV Offload 功能的 Prefix Reuse 完全失效。这会导致长上下文场景下性能严重下降（TTFT 从 0.5s 退化到 47.7s）。预计该修复将很快被合并。
*   **FP8 KV Cache 在长上下文场景下的 OOM 现象**：Issue #46985 报告了一个令人困惑的现象：在一些模型（如 GLM-5.1-AWQ）的长上下文推理中，`fp8` 格式的 KV Cache 反而比 `bf16` 更容易 OOM。这违反了“低精度通常省显存”的直觉，可能需要深入排查内存分配或后端方面的 Bug。
*   **关于 KVCacheSpec 演进的 RFC（Issue #33789，今日被标记为 stale 关闭）**：虽然这个 RFC 因长期无活动而被自动关闭，但其中讨论的问题——如何处理多种不同 `kv_hidden_size` 的 Attention 层（如混合了不同 FullAttention 和 Mamba 的模型）——仍然存在。当前 vLLM 采用的是**对齐填充**方案，但长远来看，**多个独立的 BlockPool** 方案也可能被社区重新提上议程。
