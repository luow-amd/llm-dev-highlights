#### 2. #50781（Issue）：FlashInfer MLA workspace 溢出 + DCP 崩溃 —— 深度根因分析

- **讨论参与者**：`flexwang`（报告者） vs `thegoldenflow`（分析者）
- **核心议题**：`--decode-context-parallel-size 8` 下单请求即崩溃，vLLM 默认 FlashInfer workspace 394 MiB 远小于实际需要的 1.6 GiB。
- **关键技术观点**（thegoldenflow 两次长评论）：
  - **第一层**：vLLM 侧 workspace 是固定大小缓冲区，对 DCP/head 数/spec-decode 不感知
  - **第二层（更正后）**：FlashInfer trtllm-gen 的 softmax-stats slab 计算为 `sizeof(float2) * num_qo_heads * batch_size * round_up(max_q_len, 256) + 1 MiB`。DCP 触发的原因有三：① LSE 仅在 DCP 下请求（DCP reducer 需要）；② DCP all-gather 使 head 维度扩大 dcp_size 倍（8×8=64 heads）；③ batch_size 是每步全部 token（含 prefill），单个 ~12K prompt 即触发
  - 给出了精确的 workaround 数值（~2.39 GiB）和修正后的计算公式
- **当前状态**：该 Issue 已催生修复 PR **#50791**（thegoldenflow 提出，按 engine config 计算所需 workspace 大小）。这是一次高质量社区协作的范例。

#### 3. #50764（PR）：Anthropic cache_salt 空字符串导致 500 —— CI 随机失败排查

- **讨论参与者**：`omkar-droid`（PR 作者）、`noooop`、`AndreasKaratzas`
- **核心议题**：`test_openapi_stateless` 间歇性失败（500 而非 422），根因是 `cache_salt` 字段无 `min_length` 约束，OpenAPI schema 允许空字符串。Schemathesis 生成 `""` 后，内部验证器在转换阶段才拒绝，导致 500。
- **讨论亮点**：
  - noooop 观察到该测试在 AMD 设备上多次失败后重试成功，"不知道为什么有随机性"
  - AndreasKaratzas 深入分析："许多运行从未生成过空 cache_salt"，并认同 `min_length=1` 合理，同时指出**需要加强测试节奏**而非仅修字段
  - 讨论虽短，但揭示了 schema 驱动的属性测试与后端验证不一致导致的"随机 CI 失败"问题

#### 5. #50768（Issue）：Kimi 工具调用标记被错误处理为原始文本

### 🛠️ 重点技术变更

#### 1. #44972（已合并）：GDN sleep/wake VRAM 清零修复
- **技术深度**：定位到 amdgpu 驱动 `amdgpu_bo_release_notify()` 在旧版本（6.10.x）不清零 VRAM 的根因，通过跨进程 VMM 探针（写 0xAB + 释放 + 再分配 + 读取）证明了脏数据残留。修复将 `create_and_map` 中新增 memset 限定在 ROCm 路径，完全避开 CUDA 热路径
- **影响**：对 ROCm 平台上任何使用 sleep/wake 模式的 RLHF 训练至关重要

#### 2. #50791（新 PR）：FlashInfer sparse MLA workspace 动态计算
- **技术深度**：精确推导了 kernel 对 workspace 的需求公式，识别出三个叠加因素（LSE 仅在 DCP 下请求、DCP head 维 all-gather 放大、prefill token 走同一 MQA kernel 导致 batch 剧增）。修复方向为从 engine config 计算所需大小而非固定默认值
- **影响**：解锁 DCP 在 GLM-5.2 等 MLA 模型上的稳定使用

#### 3. #50733/#50735/#50736（PR 堆栈）：异构 TP 支持
- **技术深度**：三连 PR 实现 `--rank-gpu-id`/`--rank-gpu-memory-mib`（显式 rank 放置）、`--rank-tp-ratio`（非均匀 TP 切分）、非均匀 DCP token 分配。这是对 vLLM "均匀假设"的第一次系统性突破
- **影响**：允许用户在混合容量 GPU（如 32GB+20GB+20GB）上充分利用显存，而非被最小卡限制

#### 4. #50766（已合并）：serving_llama70B_tp4 基准测试配置修复
- **技术细节**：`tensor_parallel_size` 未显式设置时静默继承 defaults 的 `1`，导致名为 tp4 的基准实际以 tp1 运行。修复仅为 JSON 加一行
- **价值**：这是性能测试可信度问题，合入后长期运行的 perf.vllm.ai 数据将反映真实 tp4 性能

#### 5. #50808（新 PR）：FLy 推测验证策略
- **技术深度**：提出近似验证策略：在目标模型高熵位置（top-3 熵超阈值）、且后续窗口全部可接受时，**跳过单点拒绝**，继续接受剩余 draft token。设计上不重写接受逻辑，而是改写 native kernel 的输入（greedy 路径覆写 argmax，随机路径将 uniform sample 置 0）
- **影响**：为推测解码提供新的"开源-损失可控"的加速选项，可提升高熵场景下的接受长度

### 💡 值得关注的问题

1. **⚠️ CUDA graph 内存统计回归（#50780）**：自 v0.26.0 起，CUDA graph memory profiler 将估算器首次 FULL 采样的暂态内存误计为 graph 内存，导致混合 GDN 模型 KV cache 缩小 18–24%。报告者警告"单侧修复是危险的"——目前误计的 4 GiB 实际上充当了 GDN long-prefill 的激活空间，释放给 KV 池会触发 OOM。此问题涉及 profiler 语义设计和内存分配策略的双层调整，值得核心维护者深度参与。

2. **⚠️ DeepSeek-V4-Flash 在 SM120 上的多重"静默损坏"**：#50772（fastsafetensors）、#50773（fuse_norm_quant/act_quant）在同一模型上产生乱码输出，且均为静默失败（无报错、greedy 下可复现）。这两个问题叠加 #50774（FLASHMLA_SPARSE_DSV4 崩溃），说明该模型 + 新 GPU 组合尚无充分的端到端验证矩阵，用户在 DGX Spark/RTX 5090 上部署需格外谨慎。

3. **🆕 Rust 前端进程级 abort 风险（#50725）**：gRPC 请求输入即可触发 `panic=abort` 终止整个服务进程，影响所有并发请求。虽然修复 PR 已提交，但该事件凸显 Rust 前端从 Python 侧接收输入的**校验边界不足**，建议后续为所有入口添加 fuzz 测试（报告者已提供 harness）。

4. **🔄 弹性 EP scaling flag 永久锁死（#50778）**：`_scaling_elastic_ep` 仅在成功路径清除，异常/取消后导致所有请求永久 503。修复通过 try/finally 保证清除，但该问题揭示了弹性扩展路径缺乏**失败后的自愈机制**，值得运维用户关注。

5. **🤝 AMD perf 验证基建的可见性**：#50770 讨论暴露了 AMD 开发者无法查看 vLLM Buildkite `perf-eval` 管线的权限问题（404），以及新/旧两套 perf 管线之间的定位模糊。建议社区明确 perf 验证的文档和权限分配，避免 AMD 内核 PR 的合入前性能验证持续处于"盲区"。
