#### 1. [PR #51473] [ROCm][DSV4] Preserve native MXFP4 TP8 shard allocation（新增，待合并）
- **作者**：Fangzhou-Ai
- **技术要点**：DeepSeek-V4 的 3072 维 routed-expert 中间层在 TP8 下原生拥有 384 宽 MXFP4 分片，但 ROCm 通用分配路径将其舍入到 512，导致 33% 额外内存开销。该 PR 在 AMD DSV4 路径上引入专用 `RoutedExperts` 特化，保留原生 I384 分片（active shared-expert fusion 场景保留 I512）。
- **实测收益**（8x gfx950，TP1×DP8、EP-off）：每 rank 模型内存从 156.45 GiB 降至 125.20 GiB（**节省 31.25 GiB/rank**），KV 容量从 2,859,796 tokens 增至 5,226,632 tokens（**+82.76%**）。
- **影响**：这是 AMD 平台支持 DSV4 的关键内存优化，直接决定能否在 MI300/MI350 上以更大 batch/context 运行该模型。

#### 2. [PR #51511] [Bugfix][ROCm] Disable skinny GEMM on gfx1151（新增，待合并）
- **作者**：ciru-ai（首次贡献者，评论中@了 AMD 员工 `mgehre-amd` 和 `tjtanaa` 请求评审）
- **技术要点**：gfx1151（Strix Halo / Radeon 8060S）被通用 gfx1x 选择器错误匹配到 `wvSplitK`/`LLMM1` 路径，该路径功能正确但性能病态。A/B 实测：上游 0.266948 tok/s → 本 PR 9.535182 tok/s（**35.7x 加速**），响应文本完全一致。
- **根因数据**：5 步 profile 显示 1,265 次 `wvSplitK` 调用耗时 18.53 秒，占活跃 kernel 时间的 97.79%。硬件 discriminator 显示 `wvSplitK` 在 m=4096, k=2560, n=1 时比 `torch.linear` 慢 271 倍。

#### 3. [PR #51515] [Kernel][ROCm] Use naive block assignment for WNA16 MoE（新增，待合并）
- **作者**：ciru-ai
- **技术要点**：ROCm GPTQ/AWQ WNA16 MoE 在 decode batch 很小且 expert 稀疏时，仍调用 `moe_align_block_size` 做对齐。该 PR 在 Triton GPTQ/AWQ kernel 中引入 naive 模式（每个 program 处理一个 token/expert 对），绕过对齐开销。
- **实测**：Strix Halo 上 32-token decode 吞吐从 9.21 → 10.36 tok/s（**+12.5%**）；Ling 3.0 Flash 上 +22.83%。

#### 4. [PR #51457] [Test] Add ROCm AITER FP8 MLA prefill accuracy test（已合并）

### 💡 值得关注的问题

1. **P2P functional gating 契约（#51513）**：该 RFC 提议用 `gpu_p2p_access_check` 作为唯一裁决者（veto-only），并让所有 P2P consumer（NCCL、custom allreduce、symm-mem）都接入。这是为了解决 ACS+IOMMU 环境下 peer write 静默丢失导致挂起/数据损坏的问题。**影响面大，涉及 P2P 功能的安全契约设计。**

2. **DP pause 状态机的不可恢复缺陷（#51476）**：协调器的 `engines_running` 一旦置 True 就永远无法恢复 False，导致 drain 超时和请求不可见。`aoshen02` 同时提交了保守版（#51487，仅报告）和激进版（#51488，拒绝新请求）供评审选择，这是 DP 弹性扩缩容的关键决策。

3. **NVFP4 静默错误（#51525）**：显式选择 CUTLASS MoE 后端会在 SM120 上产生空输出而不报错。虽然 auto 模式不会选中该路径，但"不可见错误"对生产是严重威胁。社区讨论倾向 fail-fast 验证（检查 ModelOpt 检查点 scale 完整性）。

4. **DeepSeek-V4 的 torch.compile 使能（#51522）**：DSV4 decode 目前无法被 inductor 融合，虽然有报告称 GB10 上 GPU-busy 已达 99.9%（融合收益≈0），但在更高带宽 GPU 上融合窗口可能重要。方向是将 pybind 调用包装为 custom op 并 hoist 惰性导入。

5. **MRV2 上 DSD 功能失效（#51510）**：DSD 的设计目的是在高 batch 下自动降级到 K=0，但 MRV2 路径完全忽略动态 K，用户承担全量 spec decode 成本却零收益。此问题涉及调度器与 model runner 的接口契约，修复难度较高（作者尝试 3 种方案均未完全解决 CG shape 不匹配）。

6. **Mooncake P/D 全场景失败（#51518）**：在 B200 8 卡上所有传输配置（NVLink fallback、RDMA、TCP）均无法完成 KV transfer，且没有一种失败在启动时被拒绝。P/D 分离的成熟度仍有待验证，读者在部署前应谨慎评估。
