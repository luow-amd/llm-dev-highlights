## 🎯 AMD/ROCm 生态相关动态

### 1. 新发现的高优先级 Bug

#### 🔴 RDNA (gfx12) AITER 统一注意力强制启用（Issue #56021 + PR #56040）
- **问题**：`VLLM_ROCM_USE_AITER=1` 在 RDNA 上无条件把 `ROCM_AITER_UNIFIED_ATTN` 插到优先级首位，完全无视 `VLLM_ROCM_USE_AITER_UNIFIED_ATTENTION` 开关。该内核在 RDNA 上请求 **65792 字节 LDS，超过 65536 字节硬件上限**，导致引擎崩溃。
- **修复**：PR #56040（Thisish3）新增 `is_rdna_unified_attn_enabled()`，仿照已有 `is_rdna_linear_enabled()` 模式，使 RDNA 用户在保留 aiter 线性 GEMM 的同时规避统一注意力内核。
- **⚠️ AMD 官方立场**：`vllmellm` 明确回应 **"AITER 对 gfx1201 的支持目前不在路线图内"** —— 这是本周期最重要的方向性信号之一。

#### 🔴 ROCm DSv4 JIT 预热 PDL 编译失败（Issue #56030 → 已修复）
- **问题**：#50176 迁移 attention 内核后，JIT warmup 枚举了 `launch_pdl=True`，Triton 向 AMD hsaco 发射 NVIDIA PDL PTX（`griddepcontrol.wait`），AMD LLD 拒绝链接，EngineCore 启动即死。
- **修复链**：jimmy-adams 的 PR #56035 采用 `launch_pdl=current_platform.is_arch_support_pdl()` 方案并**覆盖了 #56048 遗漏的 `fused_inv_rope_fp8_quant.py`**，最终合并。这体现了社区协作中"择优合并"的良好模式。

#### 🟠 gfx942 GLM-5.3-Flash 内存访问故障（Issue #56037 + PR #56059）
- 报告者 zzw09773 详细论证了三类崩溃路径（混合长度 MTP 解码、prefill `_kpool_tail_seed_kernel`、等长短 MTP），**明确声明不是 #54296 的重复**，并附 `HIP_LAUNCH_BLOCKING` + `AMD_LOG_LEVEL=3` 实测证据。PR #56059 修复 prefill 尾部种子越界（`tslot` 携带主 KV 物理 id 而 tail 是每请求 1-block 环）。

#### 🟠 Whisper W8A8 秩-3 激活崩溃（Issue #56024 + PR #56029）
- `TritonInt8ScaledMMLinearKernel` 把 rank-3 `[1,1500,1280]` 张量直接传给 2D `triton_scaled_mm`，触发 `M, K = input.shape` 解包错误。PR #56029 按 #22278（cutlass）与 #33727（CPU oneDNN）已有模式展平前导维度。

### 2. AITER 索引器集成（PR #52664）—— 严谨的门控要求

**核心议题**：将 AITER 的 FP8 score+top-k 内核接入 MiniMax-M3。

**关键 review 意见（ChuanLi1101）**：
1. 必须门控到精确的编译契约（`topk_blocks == 16`、`score_type == "max"`、block/head=128）——因为 `score_type` 从未传进内核，非 max 配置会静默走该路径；
2. prefill `num_valid_pages` 硬编码 `PAGE_SIZE=128` 而非 `sparse_block_size`；
3. 要求补充 in-tree 测试与 vs-Triton 对比数据。

作者 ykamiset 逐一回应并补充完整测试数据，最终合并。**这是 vLLM 高性能后端集成"以契约门控换取正确性"的典型案例**。

### 3. Mooncake 异构 TP 修复（PR #52516）—— 多轮对抗式 review

chengy-sysu 连续两轮指出布局问题：
- 第一轮：Hybrid 请求绕过校验后进入错误的 GDN 切片路径（H20 上 3840 个 attention 内容正确但 SSM 状态全错）；
- 第二轮：按 padded page size 推导 per-head stride、FlashInfer NVFP4 KV 槽位映射错误。

作者 wangyicong52 逐项修复并补充 Mamba 原始路径保护，最终合并。**展现了 KV 传输域中跨 TP 布局的极高复杂度**。

### 4. DSv4 PDL 预热修复（PR #56035 vs #56048）—— 择优合并

两位贡献者对同一问题给出方案，jimmy-adams 的 #56035 **主动采纳**了 #56048 更简洁的风格（`launch_pdl=current_platform.is_arch_support_pdl()`），并补齐对方遗漏的文件，随后 #56048 作者主动关闭自己的 PR 并注明 "Superseded by #56035"。这是社区协作效率的正面样本。

### 5. RMSNorm 测试容差（PR #56117）—— 测试放宽引发质疑

- **AndreasKaratzas**："不太理解（比如这个 PR 接受多少比例的离群值？）我希望测试修改确实是因为 CI 失败。"
- **作者回应**：列出多次 CI build 失败证据（26-SM H200 agent 失败、16-SM 通过），并量化："2048x1024 下接受 28 个基线离群值（0.0013%），每次失败案例恰好只有 1 个翻转的 scale、至多 127 个离群值。"

**争议本质**：**测试容差放宽的可解释性边界**——维护者担心以"通过 CI"为由放宽数值断言会掩盖真实内核问题。

## 🛠️ 重点技术变更

### 1. ⭐ 【ROCm】多流共享专家解码大幅提速（PR #56098, mawong-amd）
- **技术内核**：根因定位到 gfx950 专属 skinny GEMM `wvSplitKrc` 的静态缓冲区多流竞争。修复方式是把分配扩大 8 倍并为每个流分配独立槽位，超限时回退按需分配；同时修复了一个特定 GEMM 形状下静默截断读取的正确性 bug。
- **影响**：Qwen3.5-35B-A3B 在 conc 64 下 **+30.7% 吞吐**，DeepSeek-V4-Pro +6.9%。**这是本周期 AMD 侧最有价值的性能变更**，因为它恢复并扩展了一个此前因正确性风险被迫回滚的优化。

### 2. ⭐ 【ROCm】AITER 索引器集成 MiniMax-M3（PR #52664，已合并）
- **技术内核**：把 AITER PR#4787 的 FP8 score + top-k 内核接入 M3 稀疏注意力，用 top-k 输出 attend page table，从而支持每 rank 多 KV head。
- **影响**：显著的 TPUT/TPOT/ITL 提升，且经过严格契约门控（gfx950、FP8 E4M3、top-k 16、block/head 128、≤8192 blocks）。

### 3. 【Bugfix】Kimi-K3 流水线并行支持（PR #53664，已合并）
- **技术内核**：为 Kimi-K3 声明 PP 能力，并在 `CommonAttentionMetadata` 不携带时推导 DCP-local MLA 解码序列长度。
- **影响**：PP2×TP4×DCP4 配置下 GSM8K 0.9545，扩展了长上下文模型的大规模部署拓扑。

### 4. 【Bugfix】Duplicated KV recv completion 不再杀死引擎（PR #56194）
- **技术内核**：`MultiConnector`（Nixl + LMCacheMP）聚合 `finished_recving` 时不去重，导致第二次完成后请求已处于 `RUNNING`，`assert RequestStatus.is_finished` 触发 EngineCore 崩溃。
- **影响**：修复一个**已发布配置**下的引擎级崩溃（`/health` 保持绿色直到进程死亡，只能重启恢复）。

### 5. 【Perf】SimpleCPUOffload DMA 描述符合并（PR #56110, Fangzhou-Ai）
- **技术内核**：MiniMax-M3 TP4 单 rank 118 个 KV region × 256 blocks = 30208 个 DMA 描述符，约 0.99GB 载荷。ROCm 侧合并连续映射（含降序 ID 支持，因 eviction 常产生成对降序物理块）。
- **影响**：显著减少描述符数量，且通过 `sum(run_length * bytes_per_block) == block_count * bytes_per_block` 的分区不变量证明零载荷变化。

## 💡 值得关注的问题

### 1. 🔴 AMD 对消费级/工作站 GPU 的支持边界（长期隐患）
&#35;44091 的关闭 + #56021 的官方回复，明确显示 AMD 在 vLLM 的投入锚定在 CDNA（MI300/MI355/MI350）数据中心产品线。**RDNA/R9700/gfx1201 用户目前无官方 AITER 路线**，社区情绪（"下次直接买 NVIDIA"）值得维护者关注，可能导致工作站用户分流至 llama.cpp 等竞品。

### 2. 🟠 RDNA 统一注意力内核的优先级排序决策未定
&#35;56040 的提交者明确指出，`backends.insert(0, ...)` 的优先级排序问题是**需要维护者决策的设计问题**，不应由贡献者猜测。此问题悬置。

### 3. 🟠 GLM-5.3-Flash 的三类崩溃尚未全部解决
&#35;56037（gfx942 内存访问故障）明确指出 PR #56059 **仅修复了 prefill 尾部种子路径（Crash D）**，混合长度 MTP 解码（Crash C）与等长短 MTP（Crash E）**仍未被覆盖**，且强调不能凭 #56059 单独关闭该 issue。这是一个需要持续跟踪的活跃稳定性问题。

### 4. 🟠 MiniMax-M3 在多个平台的正确性分歧
- #56149（venkywonka）：fuse decode top-k merge，明确与 AMD 实现 #55235/#53448 区分；
- #56150：split prefill index-score K loop，与 AMD #52059 共享测试文件需协调；
- #56151：将 FP8 索引器准入限制到 CUDA 支持设备。

**多个贡献者同时在 MiniMax-M3 的 common/CUDA 与 AMD 路径上工作，存在共享测试文件冲突风险，需要协调机制。**

### 5. 🟡 MoE 超显存方案的两条路线之争
&#35;56118（CPU 专家 + GPU 其余）与 #56177（GPU 专家池 + 设备端 planner）代表了不同的工程哲学。前者简单但跨设备开销大，后者保持 CUDA graph 内执行但复杂度高。社区需要就主流方向形成共识。

### 6. 🟡 测试容差放宽的可解释性规范
&#35;56117 的讨论显示，当内核数值差异在不同 SM 数的 agent 上表现不同时，如何在不掩盖真实 bug 的前提下稳定 CI，缺乏明确的项目规范。

---

**报告结语**：本周期 vLLM 的 AMD 生态呈现"高强度排障 + 高性能内核集成"的双轮驱动特征。值得注意的是，AMD 侧的技术投入正高度集中于数据中心产品线与前沿模型的 Day-0 使能，而消费级 GPU 支持的缺失正在累积社区不满。同时，多个前沿模型（尤其 GLM-5.3-Flash、MiniMax-M3）在 ROCm 上的稳定性仍未完全收敛，建议 AMD 与社区贡献者优先协同解决 #56037 中未覆盖的崩溃路径。
