### 🛠️ 重点技术变更

#### 1. **#67710 + #67711 — 请求级双向注意力（Gemma 4 PrefixLM）**
- **技术内容**：请求可携带 sorted/disjoint 的 `[start, end)` bidirectional spans；checkpoint 在 text config 声明哪些层应用 spans；KV block 按其覆盖的 spans 作为缓存 key。Gemma 4 在全注意力层启用。#67711 将 `bidirectional_spans` 暴露到 `/v1/completions`、`/classify`、`/pooling`、`/v1/embeddings`（chat 请求拒绝）。
- **影响**：为 Gemma 4 的多模态 PrefixLM 提供引擎级支持，是 RFC #67334 的核心；同时保持前缀缓存的正确性（span 与 causal 请求可共存于同一 cache）。
- **配套**：#67709（Gemma 4 全注意力层 opt out multimodal PrefixLM ranges，H100 上 153K-token 视频 TTFT 99.6s→85.1s）。

#### 2. **#63483 — 纯 TP 下的双批次重叠（DBO）**
- **技术内容**：MRV2 上，一个 DP rank、无 EP 时，microbatch 的 TP all-reduce 跑在独立 comm stream 上，与另一 microbatch 计算重叠。ROCm 上修复 hipBLASLt handle 预热导致的 GPU hang。
- **影响**：这是 M3.1 拆分出的引擎侧 PR，标志着 DBO 从实验特性走向生产就绪。

#### 3. **#67377 — DeepSeek-V4.1-Flash 的 AITER FlyDSL GEMM**
- **技术内容**：32×32 block-scaled MXFP8 线性层从 Triton block32 GEMM（21-31% MXFP8 峰值）迁移到 AITER 的 FlyDSL 调优内核；MXFP8 激活量化 357→172 µs（M=32768, K=8192），**输出 bit-identical**。
- **影响**：MI355X × 8 DP8+EP8 场景 **26,714 tok/s/GPU**，P90 interactivity 4.61 tok/s/user。权重 in-place preshuffle，显存不增（52.1 GiB/GPU）。

#### 4. **#67717 — Mamba `align` 前缀缓存正确性修复**
- **技术内容**：mid-block prefill resume 跑过 block 边界后，block 持有的是 resume-point 状态，但 `cache_blocks()` 仍按 full-block hash 发布，导致后续请求命中后加载截断状态生成乱码。
- **影响**：修复 SSM/混合模型前缀缓存的一个隐蔽数据正确性 bug，与 #53614 相关联。

#### 5. **#66821 — Qwen2 迁移至 Transformers 后端（已合并）**
- **技术内容**：删除 `vllm/model_executor/models/qwen2.py`；`Qwen2ForCausalLM` 走 Transformers backend；Qwen3 类被泛化以复用 Qwen2 的 attention 配置（`use_qwen2_attention`）；组合模型（Qwen2-VL、Qwen2-Audio、Kimi-Audio 等）内层仍用 native Qwen3 类。
- **影响**：从 ~30 个模型文件中消除大量重复，是 vLLM 模型层长期重构的里程碑；已知 gap 包括 Qwen2-VL/2.5-VL 在 CUDA graphs 下的 M-RoPE 位置复制问题、Quark checkpoint 的 `output_scale` 加载问题。

### 💡 值得关注的问题

1. **🔴 Issue #67692 — P2P KV Offload 未认证暴露完整 CPU KV Cache**
   - NIXL DRAM region 全量注册为单 region，`ConnectMsg` 在认证前发送，任意 peer 可 one-sided READ/WRITE 任意 block；peer 地址可由请求体 `kv_transfer_params` 完全控制，无 allowlist。**架构级安全缺陷，应优先响应。**

2. **🟠 Issue #67684 — GLM-4.7 tool parser 静默丢弃导致客户端死循环**
   - 需要 maintainer 对"未知工具名"语义做裁决（透传 vs 显式错误 vs 保持校验）。当前 `glm47` 与 `minimax_m2` 是仅有两个启用 `validate_tool_names=True` 的 parser，影响面明确。

3. **🟠 Issue #67720 — `--data-parallel-start-rank` 被静默替换为 0**
   - 三条独立路径（`--data-parallel-size-local` 省略、单 DP rank、外部 LB）均静默丢弃该 flag。混合 LB 多节点部署场景下，静默改 rank 比失败更危险。#67721 已提交修复（在 `ParallelConfig` 构造前校验），与 #67328 互补。

4. **🟡 PR #67623 — `Platform.validate_request` 在 Engine Core 执行的性能争议**
   - njhill 明确表示"希望避免 core 进程额外开销"。作者已改为 `EngineCore.__init__` 一次性决定 + 每请求一个布尔检查，但更根本的问题是：**平台能力协商是否应该前移到 Rust 侧启动时？** 这涉及 Rust frontend 与 Python platform 接口的长期设计。

5. **🟡 PR #67685 — Inkling 2 Small ROCm 支持存在合并冲突**
   - `needs-rebase` 状态，且 82% 行数是 NVIDIA 模块的复制（`vllm/models/inkling2/amd/`），长期看存在双维护成本。建议关注后续是否推动为共享抽象的 `inference_mode` 分支而非文件级 mirror。

6. **🟢 Issue #67696 — CPU 后端 `VLLM_BATCH_INVARIANT=1` RFC**
   - 作者 mosafariuk 报告 5 个独立失效源（fp32 matmul 行数依赖、OpenBLAS/MKL 差异等），macOS arm64 上 12/12 试验存在 logprob 差异。这是 CPU 后端可用性的重要议题，但需先由 maintainer 确认是否在 scope 内。

7. **🟢 Issue #67743 — LLaVA-OneVision 视频帧数不等崩溃**
   - 已由 #67744 修复（返回 2D embedding 序列），但同类问题（多模态 encoder 输出形状假设）可能影响其他视频模型，值得在 `embed_multimodal` 契约层面统一加强。
