### 1. #57042 — `[Kernel] Accumulate ranks in absolute order in 2-stage custom all-reduce`（5 条评论）

**核心议题**：`cross_device_reduce_2stage` 对 rank 指针做旋转，使每个 partition 的 owner 从自身 rank 开始累加；`cross_device_reduce_1stage` 则按绝对顺序 `0..N-1` 求和。二者共享 `packed_reduce`（累加进 float32），因此部分和在舍入时可能产生不同 bit。**触发条件**：1-stage 用于 ≤4 rank 的 512 KiB 以下、≤8 rank 的 256 KiB 以下，2-stage 用于之上——即按消息大小选择。

**不同观点与验证**：
- **mosafariuk（作者）**：旋转还使 2-stage 输出依赖总张量大小，即使不切换 kernel。`part = size / ngpus` 在 size 变化时移动归属边界，而每个 owner 从自身 rank 开始求和。
- **curvedinf（独立验证者）**：在未修改的 HEAD `241e9391e`、gfx1100、world size 4 上跑 GPU 内 in-vitro harness。fp32 下 **1-stage vs 2-stage（同 2048×5120）31.28% 元素 bitwise 不同**；**2-stage @1664×5120 vs @2048×5120（行前缀/“chunked-prefill seam”）14.86% 不同**；1-stage 控制组 0.00000。bf16 下全部为 0.00000（结构性零，因 bf16 累加器本身只有 8 位尾数）。curvedinf 原本是在准备提交自己 fork 上的 bug report 时发现此 PR。

**争议焦点**：这并非精度“bug”而是**两个 kernel 应返回相同 bit 的契约问题**，且 2-stage 的输出不应依赖于张量大小（因为 chunked prefill 会产生几何变化）。作者承认 curvedinf 的 seam 发现比 PR 原描述更强，并已将其纳入 PR body。

**当前状态**：Open，改动仅一行：`ptrs[i] = (const P*)_dp->ptrs[target]` → `_dp->ptrs[i]`（不再旋转 `ptrs`）。

> **附带关联**：curvedinf 同日提交 Issue **#57059**（ROCm 自定义 all-reduce 起始屏障完全 relaxed），两处均指向 `csrc/custom_all_reduce.cuh` / `custom_collective_common.cuh` 的同步语义缺陷，**合起来构成对 custom all-reduce 正确性的系统性审查**。

### 3. #57014 — hadacore_transform tail warp 竞态（3 条评论）

**核心议题**：`torch.ops._C.hadacore_transform` 在输入行数 > 8192 且 `rows % 8 ∈ {1,2,3,4}` 时，最后 `rows % 8` 行返回错误且 run-to-run 不同的值。fp16 / bf16、d = 32/64/128 均复现；RTX 4090（sm_89）、H100（sm_90）、A100-40GB（sm_80）均复现。

**机制共识**：
- **Yunzez（报告者）**：kernel 以 warp 为单位处理 `num_chunks` 个 256 元素 chunk；拷贝循环总是无条件 issue + commit `num_chunks` 个 `cp.async` group。当 padded chunk 数为奇数时，tail warp 只有 1 个真实 chunk（`real_num_chunks=1`, `diff_num_chunks=-1`）。masked wait 循环用 `switch (k + diff_num_chunks)` 索引，`k=0` 时求值为 `-1`，无 case，因此**不发 wait，warp 在异步拷贝落盘前就读 shared memory**。少量 block 时拷贝通常获胜，上千 block 时经常不。
- **he-yufeng（独立验证）**：核对当前 main 的 `hadamard_transform_cuda.cu` 后确认机制——commit 循环 L136–152 对每个 `k < num_chunks` 无条件 issue+commit；masked wait L340–375 读 chunk `k` 前需要 `cp.async.wait_group(num_chunks - k - 1)`。**最小正确修复是用 `k`（而非 `k + diff_num_chunks`）索引 switch。**

**关键转向**：he-yufeng 随后发现**该竞态已被开放 PR #53167（`hadacore: issue cp.async.wait_group on the partial-chunk warp`）修复，该 PR 自 2026-08-20 起一直未被评审**。他独立验证了 #53167 的 `llabs(diff_num_chunks)` 形式对两种行为都发正确 wait，`default: wait_group 0` 使负索引路径不可达，且同时阻止 tail warp 的 dummy `cp.async` 越界读。

**当前状态**：Issue 仍 Open。Yunzez 表示自己难以申请 GPU，希望 he-yufeng 来修；he-yufeng 回复“不必再修，需要的是让 #53167 被 review”，并在该 PR 下留下独立验证评论。

> **⚠️ 这是本周期最值得关注的流程问题：一个已存在的正确修复因未被评审而搁置近一个月，导致同一 bug 被重新报告。**

### 3. #57030 / #57031 — MRV2 在 1M 上下文 ROCm 上的两个缺陷
