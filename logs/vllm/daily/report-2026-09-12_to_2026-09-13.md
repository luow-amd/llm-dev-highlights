#### ③ PR #56610 — Elastic EP 死锁修复（平台特定 vs 通用机制之争）

**核心议题**：ROCm 上 elastic EP 扩缩容偶发挂死。

#### ④ PR #56122 — 双密钥 Gumbel-max 水印支持投机解码（架构 + 有效性双重讨论）

**核心议题**：让水印与投机解码共存。方案基于 SynthID-Text 补充材料的 Algorithm 6：draft token 用 key `k^D` 水印，target token（残差 + bonus）用 `k^T` 水印，**接受率用未加水印的分布计算，因此与无水印时完全一致**。

**多方观点**：
- **`tomasruizt`（reviewer）**：给出三条重构建议（用参数传入代替 `WatermarkedRejectionSampler` 子类、`DraftWatermarker` 抽 state 对象、`DualKeyGumbelWatermarker` 改用组合而非继承），并实际提交了两个 patch 分支。实测（H100，Qwen3.5-9B + MTP，c=8）：接受长度 -0.033%（p=0.82，无影响）、TPOT +1.72%（p=4.9e-8，显著）、TTFT -2.33%。
- **`simon-veitner-redhat`** 解释了另一个疑点：27B 模型检测率仅 22.7% 而 2B 有 72.7%，**根因是 27B 在 five-shot GSM8K 上熵极低（67% 的采样 token p(x)>0.999），而非 scheme 或 MTP 问题**；在普通散文上 27B 检测率 99-100%。他建议"文档应该这样写，而不是靠猜测"。

**结论**：已合并。是一次高质量的"架构-性能-有效性"三方论证。

### 🛠️ 重点技术变更

#### 1. #56562 — [Perf] Triton 融合 DSV4.1 input metadata 准备（已合并，WoosukKwon）
将 DSV4.1 每步执行的 token-to-request 映射与 indexer decode metadata 展开从 PyTorch 算子链改写为直接写入既有 buffer 的 Triton kernel。关键点：**必须从 device query boundaries 构建**，因为 DSpark adaptive verification 下 CPU boundaries 可能是陈旧的。测试覆盖了零长度请求、strided block table、padding 以及 **CUDA graph replay 时 CPU boundary 陈旧的场景**。这是 DSv4.1 走向 CUDA graph 全量化的重要一步。

#### 2. #56633 — [Perf][DSv4.1] 将 mHC post 块折叠进 delayed pre projection
DSV4 已有 `mhc_fused_tilelang` 在寄存器中计算 residual 并直接喂给 pre-norm GEMM，避免重读；V4.1 因需要在子层间传递 pre-mix 而无法复用。本 PR 新增 `mhc_fused_post_pre_delayed_tilelang`，一个 seam 上省掉 post kernel + split-k projection 重读 + pre epilogue。**Engram 注入时的 attention seam 例外**（Engram 会读取 post 与 pre 之间的 residual）。同时修正了 `MHCPreNormKernel.get_warmup_keys` 的 warmup 因子缺失（否则首个 decode step 会在 capture warmup 内部 JIT）。附完整的 GB300 autotuning 数据。

#### 3. #56629 — [5/N] 跨 TP rank 共享 HiSparse host cache（已合并）
用单个 mmap-backed pool 承载原本各 rank 复制的 HiSparse MLA host cache：TP rank 0 写入，peers 等待其 IPC event 后读取。设计上复用了 `SharedOffloadRegion` 的既有 barrier（TP CPU group）而不引入文件锁，creator 在 barrier 前完成 populate，所有 worker 映射完成后 unlink 文件以防 SIGKILL 后 backing file 泄漏。共享区 diff 从 164 行压到 85 行。**注意**：`#56650`（同一作者 `LCAIZJ` 提交的竞争版本）因本 PR 合并而在 22 分钟后关闭——作者在评论中主动指向 #56629，是一次干净的去重。

#### 4. #54985 — [Elastic EP] 跨重配置复用 CUDA graphs（已合并）
此前的 async preparation（#47288）与 eager 优化（#51885）已把大部分 elastic EP 步骤移出阻塞路径，但 CUDA graph 模式下的 kernel warmup 与重新捕获仍在 commit 时阻塞服务。本 PR 让既有 rank 复用 fused-MoE runtime 与 CUDA graphs，把工作从 commit 路径彻底移除。对 AMD 侧尤其相关——它与 #56610 修复的是同一场景的"另一半"（#56610 解决挂死，#54985 解决停机时间）。

#### 5. #56478 — [Kernel][Perf][Quantization] 修复 per-token-group 量化的奇数行性能悬崖（已合并）
`Gemma 4 31B FP8 @ TP8 / H100` 上发现：TP8 时 down-projection 输入宽度 2688，**奇数行数会启动 16 线程块，量化比相邻偶数情况慢约 4×**，一个 13,359 token 的 prefill 中额外耗时 35 ms，足以吃掉 FP8 GEMM 省下的约 30 ms。修复方式是用"下一个偶数行数"选择块几何，再用 ceil-div 与边界检查处理实际 group，**不 padding 不拷贝**，全块情况下边界检查被编译期消除。FP8 与 INT8 同时受益。

### 💡 值得关注的问题

1. **GLM-5.3-Flash 的"词沙拉"（#56605）仍是开放阻塞项**
   维护者一句"known issue due to tool call / vLLM frontend"并未附带修复计划或跟踪链接。这是**目前唯一一个明确影响真实生产 Agent 工作负载、且无 PR 在途**的高优先级缺陷。建议关注是否会有专项 issue/PR 跟进。

2. **ROCm 上 DSpark 的 `enable_adaptive_verification` 无法启用（#56620 自行关闭）**
   两道校验（device query lens + `AttentionCGSupport.ALWAYS`）都指向同一个根因：`DeepseekV41ROCMAiterSparseSWABackend` 只提供 `UNIFORM_BATCH`，缺少 varlen decode graph 支持。**当前 AMD 用户必须显式设 `enable_adaptive_verification:false`**，而随 V4.1 发布的 DSpark JSON 默认开启该选项——这是一个会直接导致开箱失败的用户体验缺口，应有文档或 recipe 侧修正。

3. **`#56638` 的测试缺失是合并阻塞点**
   reviewer 的核心指控很严重：Torch 回退被删除后，若 gfx950 上的 kernel 再次 OOB，"绿色 CI 会让它复活"。三种失败形状（`seq_len < query_len`、`seq_len == 0`、`compress_ratio == 0`）需要 `torch.equal` 级别的回归测试。**建议关注该 PR 是否按要求补齐测试。**

4. **KV 连接器的安全收敛仍在进行中**
   `jperezdealgaba` 的系列 PR 揭示了一个模式：用户可控的 `kv_transfer_params` 可以直接击穿 EngineCore（`KeyError` → 进程死亡），而 LMCache 的 token key 未绑定 salt/LoRA 意味着**不同 API 主体之间可能发生 KV 命中串扰**。`#56643` 的改动会使既有 multimodal LMCache 条目全部失效（作者已声明为预期行为），运维层面需要提前知晓。

5. **Mamba/hybrid 模型的跨 worker 配置传播问题（#56646，新提出）**
   2 节点 TP 下，`MambaModelConfig.verify_and_update_config` 在 head 进程内将 `mamba_cache_mode` 从 `"none"` 升级为 `"align"`，但该派生值**从未传播到 remote rank**，在开启 `--enable-prefix-caching` 时触发 `KV cache specs ... different across workers` 断言。作者附带了插桩断言的诊断。这是 hybrid 架构 + 多节点 + prefix caching 三者交叉的新问题类别，影响所有 GDN/Mamba 混合模型。

6. **MRV2 warmup 的反复（#56323 → #56654）**
   `WoosukKwon` 在 #56654 中撤销了 #56323 引入的 MRV2 专用 Triton JIT warmup 迁移，恢复 DFlash 与 multi-module MTP 的直接 kernel launch。PR 描述坦承"模型精度评测与端到端 serving benchmark 尚未运行；启动延迟与首请求编译效应未测量"。**这是一个值得跟踪的技术方向反复**——如果后续证明 warmup 迁移确有必要，可能需要以不同形式回归。
