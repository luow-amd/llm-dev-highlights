### 📊 每日开发状态摘要

### 🎯 AMD/ROCm 生态相关动态

本周期 AMD 生态动态非常密集，按主题分类如下：

**1. 新模型 ROCm 适配（重点）**

- **Issue #53943**（GLM-5.3-Flash on ROCm，8 条调试评论）：用户 `stefanskiasan` 在 8× MI350X 上系统性排查了 GLM-5.3-Flash 的 ROCm 支持。结论如下：构建本身干净，但经历了平台守卫误拦截 → `forward_hip()` 缺参 → MHC AITER 路径缺失 → `index_topk` 多模态配置缺失 → Triton kernel 重写 → 最终定位到 AITER 已存在所需内核但 `forward_hip` 无法传递 kpool 尾部参数的链条。该 Issue 暴露了两个关键架构性问题：**平台守卫过于粗糙**（将可修复的代码缺陷误判为 "NVIDIA only"），以及 **CUDA/ROCm 内核调度分歧**。
- **PR #53906**（GLM-5.3-Flash 支持）：社区在 H200/B200/MI300X/MI350X 均做了实测。`cabrinha` 明确警告：**gfx942（MI300X）与 gfx950（MI350X）是独立的 ROCm 缺陷**——官方 ROCm 镜像的 C++ 扩展仅针对 gfx950 构建，导出 gfx942 的 HIP 内核数为 0。`zzw09773` 进一步确认这是镜像构建问题而非代码问题。
- **PR #53896**（Qwen3.8-Flash-Next）：ROCm 侧验证覆盖 MI355X（BF16）。但 PLE offload 路径中对 NVFP4 权重不支持，且 TP=1 时 `uniproc_executor` 不 spawn offload worker 导致静默挂起（已由 `peakcrosser7` 修复）。
- **PR #53901**（Kimi-K3 DSpark + 流水线并行）：AMD 贡献者 `charxwu` 在 ROCm 上打通了 Kimi-K3 的 PP 支持，GSM8K 准确率达 0.9666。

### 💬 高热度讨论分析

**1. Issue #53943：GLM-5.3-Flash on ROCm 的深度调试（10 条评论）**

这是本周期最具技术含金量的讨论，完整展示了一次社区驱动的跨堆栈调试。核心议题是 **"平台守卫是否掩盖了本可修复的代码缺陷"**。

- `stefanskiasan`（主要调试者）通过 8 条评论逐步推进：发现平台守卫是"预防性"而非"承重墙"（目录中无 flashinfer/trtllm 依赖）；反复修正自己的结论（先写 Triton kernel 替代，后自己撤回——对照 DeepGEMM 参考实现发现缺 ReLU、因果掩码和内存布局错误）；最终定位到真正的阻塞：AITER 已存在所需内核，但 `forward_hip` 未传递 kpool tail 参数。
- `zzw09773` 补充了另一个独立阻塞：`Glm5NextProcessor.from_pretrained` 有一处裸文件读取（未走 HuggingFace hub），导致远程仓库 ID 无法直接使用。
- `andyluo7` 声称已有完整的 ROCm 实现（8×MI300X GSM8K 准确率 0.9704），作为依赖 PR 挂在 GLM-5.3 分支下。

**争议与启发**：社区对"平台守卫"的态度存在分歧——守卫能避免未验证硬件上的怪错，但也阻挡了本可修复的路径。`stefanskiasan` 的调试方法论（以 CUDA 为参照系、逐步移植而非禁用）被多位用户认可。

**2. PR #53896/#53899：Qwen3.8-Flash-Next 的发布前实测**

围绕新模型的 PR 吸引了两类讨论：量化兼容性（NVFP4 权重格式在 PLE offload 下的缺口）和 TP=1 场景的部署陷阱。`nichdiekuh` 发现 NVFP4 下 PLE embedding 加载失败，`peakcrosser7` 承认 "not fully supported yet"；`dolf3131` 报告了 TP=1 时 uniproc executor 不启动 offload worker 导致的静默挂起。`OsakaTX` 指出混合量化 checkpoint（NVFP4 专家 + FP8 PLE 表）在门控逻辑下无法激活 FP8 路径。最后 `jahnclawdmonet` 与 `dolf3131` 在 dummy vs real-weight 验证上互相印证，确认修复有效。

**3. Issue #53982：block_table 越界读的跨平台修复**

`zzw09773` 提供了完整的越界读证据链（含触发阈值随缓存分配器布局漂移的细节），`frank-suwen` 主动认领修复并询问是否同时覆盖 V1/V2 runner——展现了健康的开源协作模式。该 Issue 的本质是 **Triton kernel 中 mask 缺少边界项**，在 CUDA 上可能被显存布局掩盖，而在 ROCm 上更易触发致命故障。

**4. PR #53900：all2all 默认值回归**

`fxmarty-amd` 修复 #53311 引入的回归，但最终因 #53952 的 revert 而关闭。过程中 `ZJY0516` 催促推进，`arpera` 要求补充 collect_env 输出——体现了对复现信息的严格要求。

### 🔥 热门话题与趋势分析

**1. 新一代混合架构模型的适配潮**

GLM-5.3-Flash（线性注意力 + DSA）、Qwen3.8-Flash-Next（GDN + QSA + PLE）、Kimi-K3（MLA + KDA）共同构成"类 DeepSeek-V4 混合架构"家族。围绕此的三类核心技术挑战是：
- **无 RoPE 稀疏 MLA**：`qk_rope_head_dim=0` 时 FlashInfer SM120 与 AITER 均缺内核。这是本周期反复出现的主题（Issue #53963、PR #53969）。
- **KVCache 几何不一致**：缓存组的 block size 因 DCP/CP/混合缓存而不同，引发越界读（#53982）与 offload 恢复失败（PR #53917）。
- **投机解码与混合缓存的交互**：EAGLE + Mamba cache align 的共享前缀命中问题（PR #53945）。

**2. RNN/线性注意力模型的量化路径缺口**

多个 Issue/PR 指向同一模式——**架构支持与量化格式支持未对齐**：FP8/MXFP4/NVFP4 checkpoint 在特定模块（PLE、embedding、Mamba state）上的加载失败或静默乱码。这反映出压缩-tensors/ModelOpt 等量化生态快速演进中，vLLM 的"量化 × 架构"矩阵尚未完全覆盖。

**3. 自动回归与快速修复循环**

#53311（all2all 默认值）引发的连锁反应值得关注：该 PR 的 CI 仅覆盖 H200，未触及 L4/MI300 等多元配置。`vllm-agent`（自动化代理）在 24 小时内完成了回归识别、证据收集和 revert PR（#53952）。这显示了 vLLM CI 覆盖面在硬件多样性上的不足，也展示了自动化代理的价值。

### 🛠️ 重点技术变更

**1. PR #53952：恢复可移植 all2all 默认值（已合并）**

#53311 将 `flashinfer_nvlink_one_sided` 设为全局默认后，在 L4（无 NVLink 后端）、MI300（PowerMoE 初始化失败）、PP+DP 组合场景连环爆炸。本 PR 修复并新增单元测试固定默认值。这是"基础设施回归"的代表性案例——单一硬件上的优化不应以牺牲可移植性为代价。

**2. PR #53987：FLy 投机解码验证策略（AMD 开发）**

基于"熵门控"的延迟验证策略：标准拒绝采样在第一个拒绝位置截断整个 draft，FLy 发现当后续接受决策一致时，孤立的拒绝不需要截断。在 40 个配置上全部优于标准投机解码（1.07-1.94 倍）。这是 AMD 在投机解码算法层的原创贡献，且包含独立的 NVIDIA 验证。

**3. PR #53953：DeepSeek-V3.2/GLM-5.2 的 AITER 融合路径**

一次性引入 4 类融合，特别是 `fused_qk_rope_concat_and_cache_mla` 将 RoPE、拼接与 cache write 三合一——这是 MLA 路径上算子融合的深水区。设计上通过环境变量 opt-in，不影响默认行为，是一种稳妥的逐步渗透策略。

**4. PR #53969：SM120 NoPE sparse-MLA 修复**

零填充法解决 `concat_and_cache_mla` 的 `pe_dim==64` 断言：由于零 RoPE 向量对注意力分数贡献为零，这是位级精确的布局适配而非数值近似。对 GLM-5.3-Flash 在 GB10 上的支持是关键前置条件。

**5. PR #53945/+53923：EAGLE + Mamba cache mode align 的共享前缀修复**

解决了"全注意力命中某位置，但 EAGLE 截断 1 个 hash unit 后 Mamba 组在 block 边界无可恢复状态"的问题。4,416-token 的 Mamba block 中，64-token 的 drop 会损失 4,416 token 的复用——每次请求如此。修复方式是让 junction 对齐 hash grid 而非 block grid，并在 block-grid 位置接受恢复点。

### 💡 值得关注的问题

1. **#53943/#53963 交叉验证的架构性缺口**：无 RoPE 稀疏 MLA 在 SM120 与 gfx950 上同时缺失——这暗示 FlashInfer 与 AITER 两家内核库都未跟上 GLM-5.3 类模型的架构演进，"需要内核供应商协同"将成为常态。

2. **ROCm 镜像的架构单一性问题**：GLM-5.3-Flash 镜像只构建了 gfx950 而 gfx942 完全缺失（`strings` 检查结果为 0），而 `qwen38-flash-next` 镜像是双目标构建。需要建立镜像架构覆盖的自动化检查机制。

3. **手动维护的 allowlist 结构性问题**（#53983）：ROCm spec-decode 的 attention-metadata 白名单已手工打了至少三次补丁（#31714/#32877/#37887），且仅 ROCm 有此检查——CUDA CI 无法捕获遗漏。建议改为后端声明支持。

4. **前缀缓存 + MTP + 混合模型的三方组合**（#53912）：v0.28.0 仍存在输出损坏，且 `drop_eagle_block` 路径与 async-scheduling 竞态是两条独立但共存的根因。混合架构模型（Mamba/GDN + 全注意力）的 cache 复用语义尚需系统性梳理。

5. **#53952 仅修复了表象**：all2all 默认值回退是必要止血，但 #53311 暴露的 CI 覆盖盲区（多 GPU 型号 × 分布模式矩阵）未从根本上解决。建议在 CI 矩阵中强制至少一个 non-NVIDIA 配置 + 一个非 H100 NVIDIA 配置。
