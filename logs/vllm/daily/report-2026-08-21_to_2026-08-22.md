#### 2. ROCm 性能优化

- **PR #53301**：`[ROCm][Perf] Reuse graph-stable attention metadata across Kimi-K3 cache groups`（作者 JohnQinAMD）。针对 Kimi-K3 在 TP8 下运行 6 个 MLA 组 + 14 个 KDA 组时每组重复构建注意力元数据的问题，提出通过 4 个 hook（`share_reusable_metadata_buffers`、`can_reuse_metadata`、`update_block_table`、`get_metadata_reuse_key`）只重做 block-table 相关部分。AITER MLA 和 Kimi-K3 KDA 已实现。目前存在 merge 冲突需 rebase。
- **PR #53335**：`[ROCm][Perf][Attention] Add FlyDSL gfx950 prefill attention backend`。新增 `ROCM_FLYDSL_ATTN` 后端，将长 prompt 的 causal prefill 批次发送到 FlyDSL kernel，decode 仍回退到 AITER unified attention。通过批次形状判断调度路径以保证 CUDA graph 捕获稳定。依赖 ROCm/FlyDSL#1056 合并后方可使用。属于探索性方向。
- **PR #53283**：`[ROCm][Perf] Use wvSplitK for single-output GEMMs`。修复 Qwen 共享专家门控在 batch-1 decode 时落入通用 `F.linear` 回退的问题。扩展 Python dispatch 条件以支持 `M_in=1`，实测 BF16 `[1, 2048]`算子延迟从 119.5µs 降至 3.2µs（37.8x），纯 decode 吞吐提升 12.8%。

#### 3. 量化与 Quark 相关

- **PR #53278**：`[Bugfix][FP8 linear oracle] Verify scale dtype (e8m0 vs fp32) compatibility in FP8 linear backends`（作者 fxmarty-amd，AMD 员工）。修复 FP8 block-linear kernel 选择逻辑：FP8 和 Quark W8A8 FP8 路径现在通过 `kFp8Static128BlockE8M0Sym` 声明 E8M0 scale 存储，使选择逻辑能拒绝无法消费该格式的后端。具体修复了 HummingFP8、CutlassFp8BlockScaledMM、CPUFp8BlockScaledMM 三条路径，涉及 DeepSeek-V4-Flash 等目标模型。

- **PR #53268（已合并）**：`[ROCm][Test] Use platform FP8 dtype in ModelOpt FP8_PB_WO test`。修复 MI300 上测试硬编码 `torch.float8_e4m3fn` 的问题，改为通过 `current_platform.fp8_dtype()` 解析（ROCm 上为 e4m3fnuz）。

### 🛠️ 重点技术变更

#### 1. PR #53294：回滚 Kimi-K3 ROCm KDA 融合（已合并）

**技术解读**：KDA 融合 kernel（原 #52606）是一个性能优化亮点（prefill chunk 阶段 1.8-3.5x 加速），但 HIP 代码中直接使用 gfx950 专属的 `__builtin_amdgcn_mfma_f32_16x16x32_bf16` 内建函数，且未做架构保护。AMD CI 镜像包含 gfx90a 目标，因此在多架构编译时确定性失败。这次回滚暴露了 ROCm kernel 开发中"单架构优化 vs 多架构 CI"的矛盾。后续修复应通过编译器宏或运行时架构检查来隔离 gfx950 特化代码。

#### 2. PR #53278：FP8 block-linear scale dtype 验证（待合并）

**技术解读**：这是 FP8 kernel oracle 机制的重要改进。vLLM 现在通过 `kFp8Static128BlockE8M0Sym` 在 kernel 广告中声明 E8M0 scale 存储格式，使选择逻辑能拒绝不兼容的后端（如 CUTLASS 需要 float32 scale）。涉及 HummingFP8、Cutlass SM90/SM100/SM120、CPU 四条路径，是 DeepSeek-V4-Flash 等使用 Quark W8A8 路径模型正常工作的基础。

#### 3. PR #53231：Gemma 4 TurboQuant KV cache 支持（待合并）

**技术解读**：这个 PR 为 KV cache 接口增加了 `TQFullAttentionSpec`（TurboQuant 感知的 page_size_bytes），并解决了两个 GPU 层面的限制：ROCm CK flash_attn head_dim≤256 的限制通过 per-instance `_use_flash_attn` 标志规避；Gemma4Config 的 backend override 与 TURBOQUANT 的冲突通过跳过 FA3/Triton override 解决。这是"模型架构特性驱动 KV cache 抽象演进"的典型案例。

#### 4. PR #53222：AITER MoE token chunking（待合并）

**技术解读**：AITER 的 MoE 中间分配对 vLLM profiler 不可见是一个架构性盲区——vLLM 按 profiled 峰值分配 KV cache，但 AITER 的内部分配不受控。通过在 token 维度分块重复调用 AITER，将中间缓冲从 26.75GiB 降至可控范围，避免首个真实批次超预算崩溃。默认值为 0 保持原有行为，是 opt-in 的安全性设计。

#### 5. PR #53261：AITER MoE rank token 计数修复（待合并）

**技术解读**：这个 bug 非常隐蔽——`ExpertTokensMetadata.expert_num_tokens` 是 per-expert 向量，而 AITER 的 `num_local_tokens` 期望的是 rank 持有的总 token 数（单值）。在 EP=8 的 DeepSeek-R1 上，expert 0 的计数恰好为 0，导致激活量化被跳过，GEMM 输出 NaN，完整对话变成空字符串。修复展示了"跨框架接口契约不匹配"的风险。

### 💡 值得关注的问题

1. **Kimi-K3 ROCm 融合 kernel 的后续修复**：#52606 被回滚后，该性能优化需要以支持多架构编译的方式重新提交。AMD CI 对 gfx90a 的编译保护应该通过条件编译或运行时检查实现，而不是直接阻止 gfx950 特化代码。

2. **DFlash2 的跨平台稳定性**：DFlash2 仅在合并次日的 ROCm 上就被发现 acceptance 坍塌（#53323，ROCM_ATTN draft backend 下并发批处理时崩溃），加上合并前报告的 NaN（benchislett）和并发越界（timothysu），该架构在新硬件上的鲁棒性需要系统性验证。特别是 ROCm prefix-attention kernel 加载已驱逐 sliding-window K/V 的行为需要修复。

3. **AITER MoE 内存可见性**：#53222 揭示的 profiler 盲区问题在技术上应通过 AITER 提供内存查询 API 或在 vLLM 侧预分配 workspace 来根治。token chunking 可以缓解但不能消除超预算风险，且默认关闭。这是一个架构性隐患。

4. **DeepEP 超时默认值的分歧**：#53282 中 robertgshaw2-redhat 对 1800s 默认超时的反对是合理的——这在生产环境会让故障排障变得漫长。需要 DeepEP JIT 编译的时间优化而非一味拉长超时。

5. **KV cache key partitioning 的一致性缺失**：Issue #53194（RFC）提出了一个精辟观点：过去五个月的十个 bug 不是十个独立缺陷，而是一个"维度必须切分 KV cache keyspace"的不变量被反复违反。RFC 提议建立 conformance suite，这是根治类问题（cache_salt、LoRA identity、prompt_embeds 等维度被丢弃）的正确方向。

6. **旧 Issue 被机械关闭的风向**：本周期关闭的 29 个 Issue 中，大量是 stale bot 自动关闭的 90 天无活动 bug（如 #40302、#38738、#40354、#40374、#40381、#40435 等）。这些 bug 可能仍存在于当前版本，提醒社区需要重新评估 staleness 策略，避免真实问题被静默流失。
