### 🎯 AMD/ROCm 生态相关动态

本周为 AMD 平台贡献密集的一周，涉及性能回归修复、新硬件支持、BUG 修复与基础设施升级。

**🔴 关键性能回归（需要紧急关注）**
- **Issue #43153**: `[Bug][Perf Regression]: AMD MI355X Kimi K2.5/2.6 arch 38% perf regression`。从 vLLM ROCm v0.18.0 到 v0.21.0，Kimi K2.5 (INT4) 在 MI355X 上吞吐量从约 1,223 tok/s/gpu 降至约 753 tok/s/gpu（-38%）。用户 `functionstackx` 提供了详细的对比数据，并要求团队在 v0.18.0 到 v0.21.0 范围内进行二分定位。该 Issue 已被标记为 `bug` 和 `rocm`，并自动 @了 ROCm 相关维护人员。

**🛠️ 性能优化与 Bug 修复**
- **PR #43159** (`akash-amd`): `[DSv4][Performance][MoE] Optimize pack_bitmatrix Triton kernel for CDNA GPUs`。针对 MI355X 优化了 pack_bitmatrix 内核，通过使用更紧凑的 K_PAD 启发式策略、减少 warp 数、增加 HIP 快速路径等，使 DeepSeek-V4-Pro 端到端吞吐量提升 **5.4%**（154.87 → 163.2 tok/s），中位 ITL 降低 4.9%。该 PR 由 AMD 员工 `akash-amd` 与 `heachary` 合作提交。
- **PR #43147** (`akii96`): `[ROCm] Fuse Q pre-quant onto AITER static per-tensor FP8 path`。将 Q 张量的静态 FP8 量化操作合并到 AITER 的专用 HIP 内核中，避免动态分发开销。在 GPT-OSS-120B TP=2 上，TPOT 降低 **6.4%**，输出吞吐量提升 2.8%。该 PR 依赖 `ROCm/aiter#3276`。
- **PR #43067** (`chaeminlim-mb`): `[Bugfix] Gate persistent MLA metadata behind VLLM_AITER_MLA_PERSISTENT_METADATA`。修复了 AMD gfx942 上 DP=8 时持久化 MLA 内核导致内存错误的问题。将持久化元数据快速路径默认关闭，用户可通过环境变量 `VLLM_AITER_MLA_PERSISTENT_METADATA=1` 选择性启用。
- **PR #43068** (`chaeminlim-mb`): `[Bugfix] MoriAll2AllManager: pass num_qp_per_pe and quant_type explicitly`。修复了 gfx942 上 MoE FP8 场景下 MoRI 通信初始化失败的问题。显式传递 `num_qp_per_pe=2` 和 `quant_type="fp8_direct_cast"`，与 SGLang 配置对齐。
- **PR #43111** (`xaguilar-amd`): `[Bugfix][Compile] Bound Inductor OperatorIssue.operator_str to avoid IR __str__ recursion hang`。修复了 Kimi-K2.5-MXFP4 在 ROCm 上运行 torch.compile 时因 IR 递归字符串化导致的多分钟死锁问题。通过限制 `operator_str` 的递归深度解决。

### 💬 高热度讨论分析

本周期内评论数相对分散，没有出现极热门的单条讨论。以下选取相对活跃的几个进行梳理：

1.  **Issue #41964: AMD CPU 空闲 100% 问题**（9 条评论）
    - **核心议题**: 用户 `maikmerten` 报告即使在没有请求时，VLLM:EngineCore 线程也占用 100% CPU。strace 显示持续调用 `ioctl(AMDKFD_IOC_WAIT_EVENTS)`，呈现忙等待状态。
    - **不同观点**:
        - `indivats`（AMD 贡献者）尝试复现并请求更多信息。
        - `streber42` 在 MI300 集群上使用 `Qwen3.6-35B-A3B-FP8` 成功复现，并且发现所有 4 个 GPU 都报告 100% 负载（尽管功耗只有 30-50%）。
        - `maikmerten` 后续确认 vLLM 0.21.0 已经修复了 CPU 100% 问题，但 GPU 空闲功耗居高不下。
    - **最终结论**: Issue 关闭。CPU 问题已修复，GPU 空闲功耗问题可能属于驱动或底层行为，用户已注意到且在 `llama-server` 中也观察到类似表现。

2.  **PR #43101: PriorityRequestQueue 懒删除实现**（5 条评论）
    - **核心议题**: 作者 `KMnO4-zx` 提出将优先队列中的 `remove_request` 从 O(n) 优化到 O(1) 摊销复杂度，通过懒删除标记 + 定期压缩实现。
    - **不同观点**:
        - `njhill`（核心维护者）询问基准测试结果和端到端性能表现。作者提供了详细的微基准测试（70-7000x 加速），但承认没有 GPU 环境跑端到端测试。
        - `njhill` 进一步要求使用优先调度策略进行端到端基准测试。作者提供了模拟测试脚本，但 CI 验证需要维护者协助。
    - **当前状态**: PR 仍处于开放状态，需要更多数据支持。

3.  **PR #43056: Qwen3-VL 融合 QK-RMSNorm + mRoPE CUDA 内核**（6 条评论）
    - **核心议题**: 作者 `VinayJogani14` 将 Qwen3-VL 中的三个独立内核（q_norm, k_norm, rotary_emb）融合为一个，消除中间全局内存往返。
    - **不同观点**:
        - `Monishver11` 指出该 issue `#43021` 是他先创建的，并等待被分配，质疑工作冲突。`VinayJogani14` 诚恳道歉并提议协调，`Monishver11` 表示让作者继续推进。
        - CI 检查（Mergify）提示 pre-commit 失败，但作者澄清是 CI 门控问题（需要 verified/ready 标签），并非实际 lint 错误。
    - **当前状态**: 开放中，等待进一步审查。

4.  **PR #43169: Gemma4 vision encoder 批量处理**（3 条评论）
    - **核心议题**: 作者 `lucianommartins` 将 Gemma4 的视觉编码器调用从逐张图像/帧处理改为批量处理，显著提升并发吞吐。
    - **不同观点**:
        - `Isotr0py` 提出当前使用 HF 的 SDPA 导致高显存消耗，建议移植到 vLLM 原生 `MMEncoderAttention` 并使用 FlashAttention。作者同意，并创建了新 Issue #43178 跟踪此改进。
    - **当前状态**: 开放中，已获批准。

### 🛠️ 重点技术变更

1.  **PR #42828 (合并): Mooncake Store 连接器 HMA 支持**。为 Mooncake 存储连接器添加了混合 KV 缓存管理 (`HMA`) 支持，允许具有混合注意力布局的模型（例如 Full + Sliding-Window、DeepSeek V4）使用 Mooncake Store 作为外部 KV 池。引入了 `MooncakeStoreCoordinator`，用于在外部分布式键值集中查找最长缓存命中。

2.  **PR #42976 (合并): FlashInfer 单侧向 workspace 联合**。修复了 `FlashInferNVLinkOneSidedManager` 中的 Bug：当模型包含异构 MoE 层（如量化基础层 + 未量化 MTP 头）时，workspace 大小按第一个层分配，导致后续层溢出。通过将 workspace 增长为所有调用者的并集并在需要时重建 `MoeAlltoAll` 来解决。

3.  **PR #42540 (合并): 添加 humming-kernels 依赖**。将 `humming-kernels` 包添加为可选依赖，为未来将其作为默认 MoE/MXFP4 内核铺平道路。目前仍需要通过 `--quantization humming` 或 `--moe-backend humming` 显式启用。

4.  **PR #42347 (合并): 消除 GPU<->CPU 同步**。这是系列中的第 4 个 PR，通过消除调度、多模态处理等路径上的隐式 GPU-CPU 同步点，进一步提升了异步调度的性能。这是保持 CUDA 流并发性的关键步骤。

5.  **PR #43134 (待合并): 无需 --enable-sleep-mode 即可使用 MNNVL 进行 KV 传输**。解耦了 cumem (CUDA VMM) 分配器与睡眠模式，使得默认情况下 CUDA 和 ROCm 都能获得稳定的物理页面和 fabric 句柄支持。新增 `--enable-cumem-kv-cache` 选项（默认 True），极大地简化了用户使用 MNNVL 进行 KV 传输的体验。

### 💡 值得关注的问题

1.  **AMD MI355X 严重性能回归 (Issue #43153)**：这是当前最高优先级的 Bug。38% 的吞吐量下降对于生产部署是灾难性的。团队应在 `v0.18.0` 到 `v0.21.0` 之间迅速进行二分定位。用户已提供了详尽的 InferenceX 实时图表和配置变化，为排查提供了有力支撑。

2.  **RunAI 流式加载造成的数据竞争 (Issue #43163)**：用户 `bbartels` 精准定位到 commit `ac3dac545` 引入了 `_pending_wk_fp8`，该结构在 RunAI 流式加载器复用缓冲区时导致数据被覆盖，产生乱码输出。这是一个典型的多线程/流式加载下的数据竞争 Bug，需要紧急修复。提交者已提供了详尽的分析。

3.  **CPU 平台 KV 注入的重大 Bug (Issue #43059)**：`ExampleConnector` 在 CPU 后端的 KV 缓存注入存在两个严重缺陷：一是当 `attn_metadata` 为 None 时过早返回导致 KV 未被注入；二是对 CPU 5D KV 缓存布局的错误处理导致注意力状态损坏。这阻碍了 CPU 上的预填充-解码分离架构。作者已提交修复 PR (#43088)。

4.  **MoE 模型低 batch size 性能回退 (Issue #43096)**：用户 `Wats0ns` 报告了从 v0.19.1 到 v0.20.0，MoE 模型在 `max-num-seqs=10` 时吞吐量下降约 22%（2252 tok/s → 1750 tok/s）。该用户随后在 Issue #41306 中发现相同问题并关闭了此 Issue，表明可能是一个已知的、待解决的性能回归。

通过以上分析可以看出，vLLM 正处于快速迭代期，DeepSeek V4 和 AMD ROCm 生态是当前社区最关注的两大领域。同时，在 KV 传输、投机解码和性能调优方面也有大量创新工作。
