### ① #59642（已关闭）— Qwen3.8-Flash-Next 在 PD 分离服务中 MTP 接受率恒为 0.000

**核心议题**：149 个请求、360 个 SpecDecoding 窗口中 358 个报告 `Accepted: 0 / Drafted: 333`，三位置接受率精确为 `0.000`。drafter 本身在工作（持续以 ~33 tok/s 提议），KV 传输 149/149 成功。

**各方观点与排查过程**：
- `aijanai`（报告者）：强调"**恰好为 0**"是关键线索——若只是条件化不佳，位置 0 也应有偶然命中；且前两个窗口正常（0.204/0.118/0.054 与 0.551/0.326/0.191），说明 drafter 功能完好。
- `xzwgit`（独立复现者，8× RTX PRO 6000 SM120）：单节点复现同样症状，且**目标模型输出本身也退化为重复垃圾**（"Register Register Register..."）。随即做了关键反证实验：**移除 MTP 后 PD 仍然产生垃圾**（"ductductduct..."），由此判定 **"这不是投机解码 bug，而是 KV/mamba 状态传输本身损坏了解码侧上下文，0% 接受率只是附带损害"**。
- `xzwgit` 又提出 `clip_ssm_state_blocks` 只传最后一个 SSM block、而消费侧 3-read conv 窗口需要约 3 个尾部 block，改为 keep-3 后 no-MTP 路径修复；随后**主动撤回**该结论对 GB200 的推断（GB200 是 SM100 而非 SM120），并指出更站得住脚的分组是"单节点 PD vs 跨节点 PD"。
- `aijanai`：补充 PD MTP **k=1 时可用（53% 接受率），k>1 全崩**。
- 最终收敛：`aijanai` 通过 hot-patch 探针定位到 **目标 logits 从第一个 verify 步起即为 NaN**，逐层探针显示 hidden state 在 **PLE（`Qwen4ExpPLELayer` 短卷积）之后立刻变 NaN**——根因是 **NIXL 连接器对 PLE 短卷积状态的 KV 传输被截断**，修复在 **#59997**。
- `xzwgit` 交叉验证："block 选择不是第二层的变量（keep-1/3/all 在 MTP 下无区别），问题在传输长度而非选择"，与"stale、从未写入的列"而非"写入错误数据"的判断吻合（async-loaded block 免于清零）。

**争议焦点**：无实质对立，是一次罕见的高质量多方协同根因定位。唯一被提出又自我否定的假设是"SM120/DS-conv 架构分组"。

**结论**：Issue 已关闭，修复指向 #59997；同时暴露了 **qwen4_exp 混合状态（GDN/mamba + attention）在 PD 传输下的布局语义**是一个系统性风险面。

### ② #59412（已合并）— ROCm 池化索引器页对齐 kernel block 选择（GLM-5.3-Flash）

**核心议题**：GLM-5.3-Flash 在 ROCm 上**静默损坏 DSA 索引缓存**。`DeepseekV32IndexerBackend.get_supported_kernel_block_sizes` 在 ROCm 上对所有部署返回 `[1, MultipleOf(16)]`，导致 hybrid KV manager block（TP8..TP1 下 640/1152/2176/4352）被当作 kernel block，而 `prepare_kernel_block_sizes` 丢掉了 spec 的 `storage_block_size`（`index_kpool=4` 的 128/256-token 池页）。TP2@32K 下原始 block 表宽 16 列而实际需要 256 列 → page 0 到处别名；TP4 下直接写出 row buffer。

**不同角度的观点**：
- `amd-dlimpus`：在 MI355X TP2 命中同一 bug，**提交了替代方案 #59704**（在 `DeepseekV32IndexerMetadataBuilder` 内展开 block 表），但**主动关闭自己的 PR 让位于本 PR**，并提供 GPQA-Diamond 数据支撑影响面：未修复 80.81–85.35%（含退化/失控生成）→ 修复后 89.90–91.41%。
- `davidcanar`（gfx1151，2 机 TP2，Strix Halo）：用 score 级插桩定位到"needle-pool indexer 分数在 pool 7,295 之后**恰好为 0.0**"，7296 = 114 原始列 × 64 pool/页，与根因机制完全吻合。
- `jin-amd`（8× MI350X，TP4/TP8）：验证 TP4 下 index-cache 回环 2,372 pool 写入但只有 2,056 被正确读回（其余读到别的 pool 的 key）；修复后 2,372 个 slot **0 不匹配**，decode top-k 与 torch 参考重叠从 178/512 → **512/512**；needle retrieval TP4 2/15 → 15/15，TP8 8/15 → 15/15。
- `vllmellm`（作者）：回应 `simondanielsson` 的建议，**放弃"后端声明 page lattice"的通用方案，改用最小改动**（在 `prepare_kernel_block_sizes` 处优先使用 spec 的 `storage_block_size`，否则回退 `select_common_block_size`），理由是"其他所有调用方本来就把 `storage_block_size` 当作 kernel block"。
- `amd-dlimpus` 后续补充：在当前 PR head（`753fec5`）上复测 GPQA-Diamond，bf16 90.91%、MXFP4 89.90%，**失控生成从 13–18 降至 3–5**，与替代方案等效。

**争议焦点**：**通用抽象 vs 最小改动**的设计取舍。最终采纳最小改动，但把 `block_size_is_supported` 逻辑提到模块级供两处共用。

**结论**：已合并，并同时关闭 #59704，解决了 #55280 / #54359 / #56380 等同源 issue。

### ③ #60703（开放）— GLM-4.7 流式解析器在文中出现游离 `<tool_call>` 后静默吞掉后续全部内容

**核心议题**：`glm47_moe_config` 缺少 `(TOOL_NAME, "TOOL_START")` 转移。当模型在叙述中输出游离 `<tool_call>`（例如"我会为此发出一个 `<tool_call>`"）后，引擎进入 `TOOL_NAME` 状态，随后所有正文与**真实**工具调用的 opener 全部被追加进幻影调用的 name buffer；关闭时 `_accept_tool_name` 因 `validate_tool_names=True` 拒绝，且无内容回退 → 响应 HTTP 200、`finish_reason: "stop"`、**无 tool_calls、内容被截断、日志无告警**。作者 `nikoder` 指出生产表现为"agent run 在宣布工具调用后随机停止"，3 周内命中 4 次；并引用 #46040（GLM-5.2 在 ```` 内输出）与 #58227（同类 Qwen3 负载约 3.6% 生成含不平衡 opener）佐证模型确实会输出该 token。

**不同角度**：
- `he-yufeng`：**独立确认 + 边界情况矩阵**（5 个探针）。确认机制描述准确；应用单转移补丁（`(TOOL_NAME, TOOL_START) -> TOOL_NAME`，发出 TOOL_CALL_END + TOOL_CALL_START）后：正常 repro 可解析真实调用、连续两个游离标签只丢幻影、`<arg_value>` 内的字面 `<tool_call>` 原样保留。
- `michaelmanly`：通过 **Badgr** 重放，"被吞掉的真实调用"被判为不可接受结果——因为"请求的可用工具调用结果从未抵达，尽管流本身正常终止"。并提出一个**设计层面的问题**："是否应该在执行层检测这类静默坏结果并重试/回退，还是主要希望它作为一个校验错误被暴露出来？"

**争议焦点**：**解析器修复 vs 执行层兜底**的分工——即"前端解析器应当在状态机层面保持可恢复性"，还是"上层应当有 outcome-based 的验证/重试机制"。这是 tool-calling 可靠性架构的一个真实分歧点。

**当前状态**：开放，解析器修复正在推进中。

## 🛠️ 重点技术变更

### 1. #59412 — ROCm 池化索引器页对齐（已合并）

**技术解读**：这是本周期**影响面最大、定位最深**的 AMD 修复。问题的本质是**两套 block 语义的混用**：hybrid KV manager 以 manager block（640/1152/2176/4352 token）为单位管理内存，而 `Glm5NextIndexerCache`（`index_kpool=4`）以 storage page（128/256 token）为单位寻址索引缓存。写入侧（`get_compressed_slot_mapping`）与 gather 侧都以 `column = pos // storage_block_size` 寻址 block 表，但 block 表却按 manager 粒度构建。

**为什么危险**：`prepare_kernel_block_sizes` 丢掉 `storage_block_size` 后，`storage % kernel != 0` 的转换分支被跳过，**块表索引越界但不报错**——"page 0 到处别名"或"写出 row buffer"，最终表现为**检索分数恰好为 0**、长上下文召回失败、生成失控。这正是最难调试的一类退化。

**修复策略**：只在 `MLAAttentionSpec.storage_block_size` 存在且该组后端支持时采用它作为 kernel block，否则回退 `select_common_block_size`。CUDA 上 indexer 声明精确 `[64]`，storage block 校验失败 → 保持现有转换路径不变。**最小化改动面，同时把 `block_size_is_supported` 提取为共享逻辑**。

**验证质量**：三家独立验证（MI355X TP2/TP4、gfx1151 两机 TP2、8× MI350X TP4/TP8），并有 GPQA-Diamond 与索引缓存回环的量化对照。这是 AMD 生态协作的一个高质量范例。

### 2. #60731 / #60683 — ROCm Mono Decode（gfx942 / gfx950）

**技术解读**：这是 AMD 侧最有野心的架构改动。传统解码每层需要 32 个 kernel 启动（320µs），mono 路径把它压成 **2 个持久化 FlyDSL kernel**（115µs），并把 TP all-reduce 内联在 kernel 内通过 peer memory 完成。gfx942 上一次解码周期从 1901 个 kernel 降到 340，墙钟从 17.9ms 降到 7.2ms。端到端在 MI325X TP4 的 InferenceX AgentX 场景下交互性 P50 提升 **2.32×**。

**关键工程约束**（#60731 明确列出）：
- kernel 按固定形态编译，超出行数上限（gfx942 为 6 行）即回退 vLLM 路径——因此**并发 1 的"单用户 + 子代理"混合请求场景会部分回退**，作者诚实地指出 P90 由那 35 个 subagent 轮次决定（P90 274.51 而非 492）。
- KV connector 存在时禁用（其 copy kernel 在另一 stream 上可能持有 CU 而 mono CTA 自旋等待）。
- 精度：GSM8K 0.9257 vs 0.9340，McNemar p=0.22（27 vs 38，不显著）。

**审查反馈**（#60683）：`Fangzhou-Ai` 要求复用统一开关 `VLLM_ROCM_MONO_DECODE`，并把验证从 "gsm8k conc1" 扩展到**最大并发**与 **GPQA-Diamond / AIME / NIAH**——说明维护者对"仅用单并发 accuracy 证明 mono 路径"持保留态度。

### 3. #60700 → #60711 — W4A8 MoE 的 256 整除断言错位

**技术解读**：这是"把后端约束误置为全局约束"的典型案例。`#58427` 之后 W4A8 oracle 同时提供 **CUTLASS** 与 **HUMMING** 两个后端，HUMMING 无 256 限制。但 `create_weights` 里的断言对**所有**后端生效，且 `CutlassExpertsW4A8Fp8.is_supported_config` 又不检查形态——于是 `auto` 选中 CUTLASS 后在 `create_weights` 阶段报错，`--moe-backend humming` 也被同一断言拦死。结果：`intermediate=640` 的 W4A8 MoE **在任何后端都无法加载**。

**正确设计**：形态约束属于**后端的 `is_supported_config`**，`create_weights` 不应重复断言。`ischencheng` 的 #60711 正是这样做的，同时让 TP2 无 EP（每 rank 320）时给出**清晰的 group-size 错误**而不是晦涩的 assert。这个修复模式值得作为其他量化方法（W4A16、MXFP4、FP8）的模板。

### 4. #55686 — Quark MXFP4 共享专家在线量化融合（已合并）

**技术解读**：AMD 生态中**最具框架设计意味**的改动。矛盾在于：`VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1` 时 vLLM 不构造 `self.shared_expert` 模块，而 Quark 的在线量化需要按模块名匹配 `shared_expert.*`。作者的解法是**在 `RoutedExperts` 的权重加载路径中截获共享专家权重**（因为融合后它本来就要被写进融合专家的槽位），在此处量化并拷入正确的量化融合专家槽位，同时保留原 `quant_method`。

**设计价值**：
- 对 quant method **尽可能无感**（示例实现为 `QuarkOCP_MX_MoEMethod`，另用 `INCMxfp4MoEMethod` 证明可扩展性）。
- 明确划界：**本 PR 不实现 `experts` + `shared_expert` 的联合在线量化 + 融合**，`experts` 需已是量化状态。
- 保留 fused shared expert 的量化配置兼容性检查，可扩展到新精度。

**收益**：让 `amd/Qwen3.5-35B-A3B-MXFP4` 这类**只有路由专家是 MXFP4、共享专家是 BF16** 的 checkpoint 能够通过在线量化 + 融合获得与离线量化 checkpoint 同等的部署形态，而不必等待上游发布新 checkpoint。

### 5. #60703 — GLM 流式解析器状态机缺口

**技术解读**：`glm47_moe_config` 缺少 `(TOOL_NAME, "TOOL_START")` 转移。当引擎因游离 `<tool_call>` 进入 `TOOL_NAME` 后：
- 每个正文字符与真实工具调用的 opener 都命中 `StreamingParserEngine._on_terminal` → `transitions.get(key) is None` → `_emit_for_state`，在 `TOOL_NAME` 状态下**追加到幻影调用的 name buffer**（包含真实 opener 的字面文本）；
- 在 `TOOL_CALL_END` / finish 时，`_handle_tool_end` 与 `_emit_name_delta` 都因 `_accept_tool_name` 拒绝该正文"名称"而退出，**且无内容回退**（`get_streaming_fallback_content` 未生效）。

**失效模式之恶劣**：HTTP 200、`finish_reason: "stop"`、无 `tool_calls`、内容截断、**日志无任何告警**。生产表现为"agent 随机会话在宣布工具调用后停止"，且因触发条件取决于模型措辞而**间歇性**（重试同一请求通常成功）。

**修复方向与开放问题**：单一转移 `(TOOL_NAME, TOOL_START) -> TOOL_NAME`（发出 TOOL_CALL_END + TOOL_CALL_START）经 `he-yufeng` 的 5 个探针验证有效。但 `michaelmanly` 提出更深层的问题：**是否应在执行层检测这类"流正常终止但结果不可用"的情况并重试/回退**，而不是仅依赖解析器修复。这实际上是在讨论 **tool-calling 的可观测性与兜底责任边界**。
